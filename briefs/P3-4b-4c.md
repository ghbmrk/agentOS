## P3-4b-4c-corpus

**Goal:** corpus replay runs in `agentosd` from a corpus the signed binary vouches for, and a finding closes only when its own check ran on its own item.

**IDs:** LOOP-7 (bullet 3: published injection corpora), LOOP-9 (findings through `Report`, closed only on evidence). Tests carry `REQ: LOOP-7, LOOP-9`.

**Sources:** `reviews/security/2026-10-09-pr515.md` finding 3 (corpus not verified at load); #515 L3 release point (comment 6074498519: closure keyed on the item, not on item plus check); BOARD P3-4b-4c; loops S27, S28; #556's body (items deferred to 4c).

### Requirements (each with a failing test first)
1. **The corpus is part of the signed binary** (#515 Security 3). `loops.LoadCorpus` today reads whatever `items.json` it is given, and `tests/test_corpus.py` only checks the repository copy. The broker embeds the corpus with `//go:embed` in `broker/corpus` (recommended: no drive file is read, so the signed binary is the digest). `go:embed` cannot reach `assurance/corpora/`, so the package carries a copy (`broker/corpus/promptinject.json`) and `tests/test_corpus.py` asserts it is byte-identical to `assurance/corpora/promptinject/items.json`. If the builder pins a SHA-256 instead and reads the file from the image, `LoadCorpus` must refuse a mismatch before parsing, and the image must ship the file read-only. Record the choice in `broker/corpus` ASSUMPTIONS (new file) or loops S27. Tests: the embedded items equal the vendored file (Python); a changed byte in the copy fails that test (control); under the digest option, a file whose digest differs is refused and no item is replayed.
2. **Closure keyed on item plus check** (#515 L3). `CorpusProbe.Run` lists item IDs in `Checked`, and `runProbe` closes every open corpus finding whose subject was checked and not found again, so a check removed or renamed in `Checks` closes its open findings although it never ran. Make `Checked` carry one key per (item, check) pair that ran (or close by finding ID); `runProbe`'s close rule matches the same key. Tests, written to fail on main first: open a finding for item I under check A; run with `Checks` holding only B; the finding stays open and no cleared text is sent. Then run with A passing on I: it closes and the cleared text goes out once (S39).
3. **Corpus replay wired in agentosd.** `learn.go` passes the guard a `CorpusProbe` in `Probes`, with the embedded items and the in-process closed checks built from the production objects `agentosd` itself holds (no `Deliver`). Today `corpus.Checks(a *mail.Adapter, c owner.Commitments)` takes a mail adapter, and `agentosd` links no `broker/mail` in non-test code, so the alert-pattern and label checks have no production object in this process: the builder either adds a constructor in `broker/corpus` that takes only the checks whose objects are present (the code filter is `owner.SecretShaped`; the commitment filter takes the daemon's commitment configuration if it has one), or stops and reports the gap. Never pass a test-built adapter. S28 names the checks the box runs and the ones it does not; requirement 2 keeps the absent checks' findings from closing. Set an `Interval` stated in agentosd ASSUMPTIONS (recommended 24 h; a run is in-process and costs milliseconds). The probe uses no guest, no network and no model. A run's outcome reaches STATUS through the existing probe lines (`ProbeFailed`, findings). Tests: the guard agentosd builds lists the corpus probe; a weakened check (a planted code filter that misses) gives one High `corpus` finding through `Report`; a clean run reports nothing; a run with zero items fails closed (an error, not a pass).
4. **S28 says what is now wired.** Update loops S28: fuzz and in-process corpus replay run in `agentosd`; canary rounds, the machine probes and corpus replay through a real guest plane do not yet (P3-4b-4c). Add an agentosd ASSUMPTIONS row for the probe's interval and that it runs in Loop 2's slot.

**Threat check:** a corpus file swapped on the drive (requirement 1 refuses it); a finding closed by a run that never ran its check (requirement 2); the replay reaching a real owner surface (it is in-process, against fixed synthetic payloads only); a canary or secret in a report (none: payloads are synthetic, S27).

**Scope:** `broker/corpus/` (embed, copy of the corpus, tests, ASSUMPTIONS), `broker/loops/corpus.go` (`Checked` keys), `broker/loops/probe.go` (`runProbe`'s close key only), their tests, `broker/loops/ASSUMPTIONS.md` (S27, S28), `broker/cmd/agentosd/learn.go` (probe wiring), its test, `broker/cmd/agentosd/ASSUMPTIONS.md`, `tests/test_corpus.py`.

**Estimate:** ~90k. Checkpoint at 50k: requirements 1 and 2 green.

## P3-4b-4c-canary

**Goal:** the canary harness hands its targets only what they need, keeps a leak it saw even when the target also failed, and names every registered target in owner words with a stated containment.

**IDs:** LOOP-7 (bullet 1: canary rounds), LOOP-9, A5 (the harness). Tests carry `REQ: LOOP-7, LOOP-9`.

**Sources:** `reviews/security/2026-10-09-pr515.md` findings 2 (the harness half: `canary.py` hands `os.environ` to targets) and 5 (hits dropped when the target errored); `reviews/ux/2026-10-09-pr515.md` point 3 (registry labels and containment); loops S41 (plain names are the only source of LOOP-7 subject names).

### Requirements (each with a failing test first)
1. **Targets get a minimal environment** (#515 Security 2). `run_target` builds `env = dict(os.environ, CANARY_PLANT=…, …)`. Build it from an allow-list instead: `PATH`, `HOME` and `TMPDIR` set to a scratch directory, the `CANARY_*` variables, and any variable a registry entry names in a new optional `env` list (names only; values come from the parent, and a name outside a fixed allow-list such as `GOCACHE`, `GOFLAGS`, `GOTOOLCHAIN` is refused at load). Test: a parent variable set to a synthetic canary is absent from what a target sees (a control target that dumps its environment).
2. **A hit is kept when the target also errored** (#515 Security 5). `cmd_round` lets `outcome` "error" win over hits. When `kinds_hit` is non-empty, emit the finding as well as the error; the round still closes nothing, since an errored run is not a clean run. Test: a control target that leaks and then exits non-zero yields one finding and one error line in the round output, and `CommandProbe` (S26) treats the run as an error that still reports the finding. If `CommandProbe` drops findings from a run with errors, change it in `broker/probecmd/command.go` too, with the matching Go test.
3. **Registry names and containment** (#515 UX 3). Each product target in `assurance/canary-targets.json` has a plain name in `broker/loops/plainname.go` (S41 keeps that map the only source; no `label` field is added). A Go test in `broker/loops` reads the registry and fails on a target with no entry. Containment: since #558 a canary finding always offers STOP (S38), so a target without `contain` still gives the owner a step. State that in the registry's `note`, and say what the owner then reads. Test: the registry's targets all have entries; a target added without one fails (control: a temp registry).

**Threat check:** a target reading a broker secret from the inherited environment (requirement 1); a leak hidden by a crash after it (requirement 2); a canary value in the round output (the existing withhold path stays, and its test stays green).

**Scope:** `tools/canary.py`, `tools/canary_controls.py` (controls only), `assurance/canary-targets.json` (`note`, optional `env`), `tests/test_canary*.py`, `broker/loops/plainname.go` and its test, `broker/probecmd/command.go` and its test only if requirement 2 needs it.

**Not here:** running canary rounds on the box (P3-4b-4c, decision 1).

**Estimate:** ~60k.

## P3-4b-4c-tamper

**Goal:** a tamper round can no longer close a finding by doing nothing, never damages what it finds writable, and never blames the guest for the broker's own writes.

**IDs:** LOOP-7 (bullet 4), LOOP-9. Tests carry `REQ: LOOP-7, LOOP-9`.

**Sources:** `reviews/security/2026-10-09-pr548.md` points 2 and 3 (comment 6075894827); #548 L3 points 2 and 3 (comment 6075903379); BOARD rows P3-4b-4c-fresh, -restore, -attrib; loops S33, S34; LATER P3-4b-4b l6 and l8 (context only).

### Requirements (each with a failing test first)
1. **Positive control** (row -fresh; Security 4a 2; LATER l8). `TamperProbe` takes one control target: a broker-made, guest-writable file (a fresh temp directory the wiring mounts writable into the probe machine), passed to the guest with the real targets in an order the guest cannot tell apart. The control must change in every round; if it does not, the round fails (an error, not a finding), journals nothing and closes nothing. Tests: a fake `Attempt` that writes nothing fails the round and an open tamper finding stays open (fails on main, where it closes); a fake that writes everything gives the control change plus findings; the control is never reported as a finding.
2. **A fresh machine every round** (row -fresh). `Attempt` returns the machine that ran the writes; `Run` fails the round when the ID equals the previous round's. Producing a fresh machine from the signed image is the wiring's job (P3-4b-4c); this is the check that holds the wiring to it. Test: two rounds with the same machine ID; the second fails.
3. **A positive write never damages the target** (row -restore; Security 4a 3; L3 3). The guest script (`machprobe.Tamper`) writes only a new sibling named `.agentos-tamper-<nonce>`, created with `O_CREATE|O_EXCL`, for every target: a file target's sibling goes in the file's directory, a directory target's inside it. It never opens a target with `O_TRUNC` or for writing, and never removes one. The broker's verdict digests the target's parent directory listing as well as the target, so a sibling that lands is a changed target. The broker removes the siblings it finds after the verdict; S33 says a found target may still need restoring from the broker's copy if a different guest wrote it. Tests: a writable file target keeps its contents byte for byte after a round that reports it; the sibling is gone after the round; a read-only target gives no finding; the gVisor integration test (`TestIntegrationTamperProbeInAGuest`) still passes in the `machines` job.
4. **The broker's own writes are not tamper** (row -attrib; L3 2). A real `snapshots` directory changes on every checkpoint. `TamperProbe` takes a `Quiesce func(ctx) (resume func(), err error)` that the wiring uses to hold the broker's writers of the targets for the round, from the before-digest to the after-digest; a `Quiesce` error fails the round. Recommended over attributing changes by the nonce, which misses removal and mode changes. Tests: a fake broker writer that changes a target during the round gives a finding without `Quiesce` (the control, which shows the false High on main) and none with it; `resume` is called on every path, including a failed `Attempt` and a cancelled context.
5. **Records.** Update loops S33 and S34 (sibling write, control target, quiesce, fresh machine); `broker/machprobe/ASSUMPTIONS.md` for the new write rule.

**Threat check:** a guest closing a writable finding by skipping its writes (requirement 1); the probe destroying a grader or evaluator it found exposed (requirement 3); a false High from a checkpoint (requirement 4); the nonce or a host path reaching a finding or owner text (unchanged: `Subject` is the owner word, `Detail` a constant).

**Scope:** `broker/loops/machine.go` (`TamperProbe`), `machine_test.go`, `broker/loops/ASSUMPTIONS.md` (S33, S34); `broker/machprobe/` (`Tamper`, tests, ASSUMPTIONS); `broker/vm/gvisor/machprobe_test.go` and the test guest's `tamper` command in `broker/vm/gvisor/testdata/guest/main.go` (rebase over #556 if it lands first).

**Estimate:** ~110k. Checkpoint at 60k: requirements 1 and 3 green.

## P3-4b-4c-exhaust

**Goal:** an exhaustion round proves the guest pressed, judges limits against the configured budget rather than "set at all", and its texts say what the owner can do.

**IDs:** LOOP-7 (bullet 5), RES-1, LOOP-9. Tests carry `REQ: LOOP-7, RES-1`.

**Sources:** #548 Potency 2 and 3 (comment 6075866370), L3 4 (comment 6075903379), Security 4a 2 (comment 6075894827), UX 1 (comment 6075866370); BOARD rows P3-4b-4c-limits, -step, -fresh; loops S35–S38; LATER P3-4b-4b l3 and l4 (context only).

### Requirements (each with a failing test first)
1. **The guest must have pressed** (row -fresh, exhaustion half; Security 4a 2). Broker-side, `ExhaustProbe` reads the pressed machine's `memory.current`, `pids.current` and `cpu.stat` `usage_usec` at the start and end of the hold; each must rise. If one does not, the round fails (an error, not a finding) and closes nothing: a guest that does not press cannot make the timings look healthy. Disk: the machine's quota usage must rise too, read broker-side. Tests: a fake `Press` whose cgroup counters stay flat fails the round, and an open `slow` finding stays open (fails on main); rising counters pass.
2. **Limits judged against the budget** (row -limits; Potency 2, L3 4; S36). `limited` accepts any positive `memory.max` or `pids.max`. `ExhaustProbe` takes the configured per-machine limits (memory bytes, pids, disk bytes) from the wiring, the same values the broker writes when it creates a machine, and a limit is held only when it is set and at most that value; `cpu.weight` stays "below the broker's". Absent configuration fails the run closed. Name the claim that way in S35 and in LOOP-7's coverage line: "limits set at or under the configured budget, broker answered, machine preempted in time", not "pressure cannot starve the broker". Tests: `memory.max` set far above the configured value is a finding (fails on main); equal or lower passes; "max" or missing is a finding as before.
3. **The response target stays a stand-in** (row -limits; Potency 3; S35). Leave the 1 s figure, but S35 and the agentosd wiring comment say it is a stand-in until SPEC freezes a figure (RES-1). No test beyond the existing one.
4. **Texts carry a step or say nothing is needed** (row -step; UX 1). Since #558 a tamper finding offers STOP and an exhaustion finding ends "Nothing is paused and nothing is needed from you." (S38), and `TestFindingTextsNameNoIdentifiersAndNeverAlarmWithoutAStep` covers both. What remains: requirement 2 changes the "no limit" finding into "limit above budget", so its new `Detail` and owner text go through the same test in every containment state, and the text says it was only noticed, not paused, until P3-4b-3b decides containment (S37). Suggested wording: "A load test found an agent machine can use more memory than its budget. I noticed it only; nothing is paused and nothing is needed from you." The UX lens signs the wording. If the builder finds nothing left beyond the new detail, the PR says so and the row closes with this package.
5. **Records.** S35, S36, S37 as above. LATER P3-4b-4b l3 (no destroy step) stays for P3-4b-4c's wiring; do not take it here.

**Threat check:** a guest that idles to clear a `slow` finding (requirement 1); a limit too high to matter passing as enforced (requirement 2); an alarm with no step (requirement 4).

**Scope:** `broker/loops/machine.go` (`ExhaustProbe`, `limited`), `machine_test.go`, `broker/loops/secure.go` (`findingText`, the `CheckExhaust` case only), `ownertext_test.go`, `broker/loops/ASSUMPTIONS.md` (S35–S37); `broker/vm/gvisor/machprobe_test.go` (the real-guest test checks counters rise). Not `machprobe.Press`'s environment: that is P3-4b-3r-env.

**Needs:** P3-4b-4c-tamper merged (both edit `machine.go`, `machine_test.go` and S33–S37). P3-4b-3r-fuzz edits `findingText`'s `CheckFuzz` case; whichever lands second rebases.

**Estimate:** ~90k. Checkpoint at 50k: requirements 1 and 2 green.

## P3-4b-4c: box wiring and box acceptance

**Goal (unchanged from the BOARD row):** LOOP-7's probes run on the box through P3-4b-3a's runner, once the drive carries the harness and corpora (loops S28). **Acceptance:** on a box booted from a release image, a probe round ran and its run is visible in STATUS (#515 Potency 2). This needs the box: CI boots the image in QEMU (`image/ci_boot.sh`) but never starts `agentosd`, which waits for onboarding's `agentosd.env`.

**What it wires**, after the four packages above:
- The machine probes (tamper, exhaustion) in `agentosd`: a fresh probe machine from the signed image each round (the check is P3-4b-4c-tamper requirement 2), `Quiesce` over the snapshot writer, the control target, the configured limits, and a destroy step after each round (LATER P3-4b-4b l3). The probe script (`machprobe`) ships today only in the test guest (machprobe M3); running it on the box means a release-listed probe image.
- Canary rounds on the box, if decision 1 says so.
- #556's deferred items, once it merges (see "Overlap" above).

**Decisions needed before it can be sized** (each one question for the coordinator to put to Mark, with a recommendation):
1. **Canary rounds on the box.** The appliance carries no Python, and the registry's product targets run `go test` against the source (S28), so on a box they would test nothing CI does not. Options: (a) keep canary rounds in CI's daily assurance job and say so in S28 and LOOP-7 coverage; (b) port the round mode and its sweep to a Go release binary run through `probecmd`, with targets that plant canaries in the live box; (c) ship Python in the image. Recommended: (a) for the first release, with (b) as a LATER line, because a box target that plants into the live vault is new design and a sweep on the box adds no evidence until such a target exists.
2. **Which machine the machine probes run in.** This is the same question as P3-4b-3f (dedicated probe machine recommended, idle live machines, or per-effect attribution), and the probe image needs a release slot either way. Take the answer from 3f; do not decide it here.

**Then** the coordinator splits this section into buildable rows. The box acceptance (a probe round on a booted box shows in STATUS) stays on this row and is checked on hardware.
