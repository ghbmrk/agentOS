## Finding and evidence

[Review finding F1](../reviews/security/2026-10-08-architecture-review.md#f1) at main `7b753eb87f606ea2268ca536d429d47989dba196`.

**Confidence:** Reproduced with real owner and local-session logic; direct handlers, synthetic modem.
**Exposure:** The local page is enabled when agentosd is configured with a PageSocket. A successful sign-in must overlap a lock/reset event; this is not a login without a valid initial factor.

LocalSignIn accepts a code and computes its expiry under the owner lock, then sends a notification after releasing that lock. The session server reads the lock generation only after LocalSignIn returns. If RequireUnlock advances the generation while notification delivery is in progress, the server binds the old successful authentication to the new generation. Token validation compares generations but does not catch this association.

**Observed:** With notification delivery paused, RequireUnlock completed. After notification resumed, owner state was unlocked=false and locks=1, yet the new page token was valid and a code-free local RESUME returned 'Resumed' and cleared stopped state.

**Impact:** A security reset can fail to invalidate an authentication already in flight. A holder of the resulting token retains page access and can resume stopped work. The proof does not show approval of a new high-tier action without its separate code.

## Scope and intended change

`broker/owner/`, `broker/localsrv/`, `broker/localapi/`, `broker/localui/` and their tests/ASSUMPTIONS.md; only the session-authentication and invalidation paths.

Return the authentication generation together with expiry from the same owner critical section, bind the token to that generation, and reject it after any intervening lock. Keep notification delivery outside the critical section. Recheck generation when committing privileged page operations. Cover sign-in, refresh and RESUME against concurrent invalidation.

Do not expand authority or edit SPEC.md in this package. If the cited contract cannot decide a design choice, raise an L1 spec-diff proposal before implementation. Record changed assumptions in the affected package's ASSUMPTIONS.md.

## Acceptance tests

1. With a valid synthetic code, pause sign-in after owner authentication but before token issuance, invalidate the session with RequireUnlock, then finish sign-in. No resulting token may access a protected route or RESUME; a new successful authentication must be required.
2. Exercise the same boundary for refresh and for invalidation concurrent with a privileged operation. Assert the authenticated generation is checked at the operation's commit point, rather than recaptured after authentication.
3. Preserve ordinary sign-in/refresh, independent STOP, and the separate fresh-code requirements for high-tier actions. Add a deterministic concurrency regression and run the affected packages with the race detector on Linux.

Write the regression first and retain it in the repository. Link requirement markers to named passing tests; a marker alone is not completion evidence. Run affected Go packages and race tests on Linux, repository checks, fresh strongest-model L3 with an explicit threat check, and the tier-A lens screen. Close this row only with passing evidence against the implementation commit and coordinator acceptance; registration of this brief does not close the finding.
