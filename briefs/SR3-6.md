## Finding and evidence

[Review finding F6](../reviews/security/2026-10-08-architecture-review.md#f6) at main `7b753eb87f606ea2268ca536d429d47989dba196`.

**Confidence:** Reproduced with synthetic signed metadata and attestations.
**Exposure:** Update verification package and pending updater/attestor wiring. No live automatic installation was performed or established.

Verified caches the interim attestation decision. Adding the first outside attestor permanently ends that exception, but trustUnchanged validates only TUF root/targets state. A previously verified object can still report Security=true and be staged after the narrower policy has taken effect.

**Observed:** After NoteAttestors and a fresh verification, the new result correctly reported security=false. The old result still reported security=true, interim=true; Stage(old) returned nil.

**Impact:** An in-flight release can retain eligibility for the automatic security-update path under an exception the current policy has already retired. This finding is specifically the sticky interim-policy transition, not a claim of general signature forgery.

**Source anchors:** [`broker/update/store.go:1006`](https://github.com/ghbmrk/agentOS/blob/7b753eb87f606ea2268ca536d429d47989dba196/broker/update/store.go#L1006); [`broker/update/store.go:890`](https://github.com/ghbmrk/agentOS/blob/7b753eb87f606ea2268ca536d429d47989dba196/broker/update/store.go#L890); [`broker/change/pipeline.go:531`](https://github.com/ghbmrk/agentOS/blob/7b753eb87f606ea2268ca536d429d47989dba196/broker/change/pipeline.go#L531).

## Scope and intended change

`broker/update/`, `broker/change/`, `broker/apply/`, and their tests/ASSUMPTIONS.md; verification policy generation and automatic update eligibility.

Bind verified authorization to an attestation-policy generation, including the sticky interim flag and relevant allow-list. Revalidate it immediately before automatic proposal and activation, and invalidate pending automatic authorizations on narrowing changes. The explicit-owner path can remain available.

Do not expand authority or edit SPEC.md in this package. If the cited contract cannot decide a design choice, raise an L1 spec-diff proposal before implementation. Record changed assumptions in the affected package's ASSUMPTIONS.md.

## Acceptance tests

1. Verify a release under the interim exception using synthetic signatures. List the first outside attestor via NoteAttestors, then attempt Stage and automatic proposal/activation using the old Verified object. It must be rejected or reverified under current policy.
2. Remove that outside attestor and reopen the store. The interim exception must remain retired; pending/stored authorization must not restore it.
3. Exercise allow-list/policy narrowing and a change concurrent with automatic dispatch. The policy generation must be rechecked at the authority commit point, as well as the TUF root/targets generation.
4. Verify currently valid threshold releases still proceed and an otherwise valid release may use the explicit-owner approval path when permitted. Do not weaken signature, rollback or freshness checks.

Write the regression first and retain it in the repository. Link requirement markers to named passing tests; a marker alone is not completion evidence. Run affected Go packages and race tests on Linux, repository checks, fresh strongest-model L3 with an explicit threat check, and the tier-A lens screen. Close this row only with passing evidence against the implementation commit and coordinator acceptance; registration of this brief does not close the finding.
