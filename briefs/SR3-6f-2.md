# SR3-6f-2: Anchor the sticky outside-attestor record in the TPM (SR3-6-f2)

A release finding from L3 on #430 (SR3-6, merged 5ece9c3), filed as SR3-6-f2 and bound to P2-4b. Security 4a on #430 classed the same gap `later`, as the U7 class already recorded in U16 ([note](../reviews/security/2026-10-08-pr430.md), point 1). The row stays `release` under D-063 (one class, the strictest wins). SPEC rows: UPD-8, and U7 and U16 in `broker/update/ASSUMPTIONS.md`; acceptance A14.

**The gap.** The interim attestation rule ends for good once an outside attestor is listed: the store writes `outside_attestor_listed`, and the policy digest includes it (update/store.go:723, 794 and 809). Deleting that file, or the whole store directory, brings `outside=false` back. Interim keys then count again. That needs root write on the store, the U7 class. The fix anchors the record in a monotonic TPM NV counter on this PC. A counter at 1 or more, while the store says `outside=false`, fails closed.

**Hardware.** Building and testing this does not need hardware. `broker/tpmseal` counters run against swtpm on CI (ci.yml installs swtpm, and the TPM tests fail rather than skip without it), as P2-4d's vault rollback counter does. A run on a real TPM joins the hardware acceptance already queued for Mark (the S1 kit). It does not gate this row. The anchor is effective only on a trusted host, one that holds a TPM counter for this store (P2-4b). On an unknown host, or after a TPM clear, the store keeps today's exposure, and the brief requires saying so in U16.

**Why one package, and its size.** Three pieces, in three places:
- an injectable anchor in the update store;
- the counter in the vault process (the only importer of `tpmseal`);
- one request on the existing broker-only socket between them.

That is about 300 lines of code and tests. Split rule: if the checkpoint is passed with the socket piece red, ship the store side with its fake anchor (2a) on its own, and move 2b and 2c to a new brief. The store side is inert until wired, so this split is safe.

**Order.** After SR3-6f-1 merges: both touch the attestor policy's ASSUMPTIONS rows, and the digest must already be read per check. It is not needed before W5b: the gap needs root on the store, and SR3-6 already closed rollback by any ordinary path. Line references are from main at 99fa0fa.

**Reuse.** No new mechanism.
- Use `tpmseal.DefineCounter`, `ReadCounter`, `IncrementCounter` and `FindCounter` (broker/tpmseal/counter.go).
- Follow the `vault.Counter` pattern (broker/vault/rollback.go:55) and its TPM implementation `tpmCounter` (cmd/agentos-egress/trusted.go:400).
- The precedent for a module anchored through the vault process is recovery's forget log (`recovery.Factor.Counter`, set by the vault process; recovery F3). Follow it.

**Requirements** (local IDs under UPD-8 and U16):
- **SR3-6f-2a, the store side.**
  - `update.Store` gains an optional anchor with two methods, `Read() (uint64, error)` and `Raise() error`. `Raise` is monotonic and idempotent above zero.
  - When the store records an outside listing (`noteAttestors`, `FollowRoot`), it calls `Raise` before it writes `outside_attestor_listed`. If `Raise` fails, the write still happens, so the file is never weaker than today, and the error is returned.
  - `policy()` reports `outside=true` if the file exists or the anchor reads 1 or more. If the anchor read fails, `policy()` returns the error, and so `Security()` and `InterimAttestation()` are false and `Stage` returns `ErrPolicyMoved` (fail closed, as SR3-6f-1c pins).
  - A store with no anchor behaves as today.
- **SR3-6f-2b, the vault process side.**
  - `agentos-egress` keeps one NV counter for the update store on this PC. Name it by a fixed id distinct from vault ids, for example the SHA-256 of `"agentos update policy"` and the store's root key ID. Define it on first use.
  - The counter is served to agentosd as two requests on the broker-only socket (the model/verify socket admits the broker's uid only): read, and raise. There is no lower or reset request.
  - On a host with no TPM, or with the counter missing after a TPM clear, it answers "no anchor". The store then logs it, and STATUS says interim attestation is not anchored on this PC. It does not fail closed, because that would retire every interim release on a host without a TPM: a decision for Mark, not a builder. Record this decision in U16. If the builder finds U16 or SPEC already decides it the other way, follow that and say so.
- **SR3-6f-2c, the client.**
  - A small client in `broker/update`, or in an existing broker-side vault client if one exists, implements the anchor over that socket.
  - W5b or the agentosd wiring sets it on the store. This package does not edit `cmd/agentosd`. It adds one line to W5b's wiring conditions instead.

**Threat check for the reviewer.**
- Root on agentosd's files cannot lower the counter. The only TPM write is `IncrementCounter`, and the socket exposes no reset.
- A compromised agentosd can raise the counter. That only retires interim authority (it narrows), so it is acceptable. Check that this is the only effect.
- Every read error fails closed in `policy()`.
- "No anchor" on an unknown host is visible, not silent, and it is recorded in U16 as residual exposure. A host that had an anchor and then reports none (TPM cleared) is covered by the same rule. Say whether that is weaker than P2-4d's `ErrCounterMissing` handling, and why.
- The NV counter's auth value is not kept in agentosd's files.
