# SR3-6f-2: Anchor the sticky outside-attestor record in the TPM (SR3-6-f2)

A release finding from L3 on #430 (SR3-6, merged 5ece9c3), filed as SR3-6-f2 and bound to P2-4b. Security 4a on #430 classed the same gap `later`, as the U7 class already recorded in U16 ([note](../reviews/security/2026-10-08-pr430.md), point 1). The row stays `release` under D-063 (one class, the strictest wins). SPEC rows: UPD-8, and U7 and U16 in `broker/update/ASSUMPTIONS.md`; acceptance A14.

**The gap.** The interim attestation rule ends for good once an outside attestor is listed: the store writes `outside_attestor_listed`, and the policy digest includes it (update/store.go:723, 794 and 809). Deleting that file, or the whole store directory, brings `outside=false` back. Interim keys then count again. That needs root write on the store, the U7 class. The fix anchors the record in a monotonic TPM NV counter on this PC. A counter at 1 or more, while the store says `outside=false`, fails closed.

**Hardware.** Building and testing this does not need hardware. `broker/tpmseal` counters run against swtpm on CI (ci.yml installs swtpm, and the TPM tests fail rather than skip without it), as P2-4d's vault rollback counter does. A run on a real TPM joins the hardware acceptance already queued for Mark (the S1 kit). It does not gate this row. The anchor is effective only on a host with a TPM (P2-4b). On a host with no TPM the store keeps today's exposure, and the brief requires saying so in U16. A counter that was defined and is now gone (undefined through the owner hierarchy, or the TPM cleared) fails closed, as P2-4d's `vault.ErrCounterMissing` does (L3 on #572, point 1).

**Why one package, and its size.** Three pieces, in three places:
- an injectable anchor in the update store;
- the counter in the vault process (the only importer of `tpmseal`), with its defined marker and the owner's re-anchor;
- one request on the existing broker-only socket between them.

That is about 380 lines of code and tests, with the fail-closed missing-counter path and its re-anchor. Split rule: if the checkpoint is passed with the socket piece red, ship the store side with its fake anchor (2a) on its own, and move 2b and 2c to a new brief. The store side is inert until wired, so this split is safe.

**Order.** After SR3-6f-1 merges: both touch the attestor policy's ASSUMPTIONS rows, and the digest must already be read per check. It is not needed before W5b: the gap needs root on the store, and SR3-6 already closed rollback by any ordinary path. Line references are from main at 99fa0fa.

**Reuse.** No new mechanism.
- Use `tpmseal.DefineCounter`, `ReadCounter`, `IncrementCounter` and `FindCounter` (broker/tpmseal/counter.go).
- Follow the `vault.Counter` pattern (broker/vault/rollback.go:55) and its TPM implementation `tpmCounter` (cmd/agentos-egress/trusted.go:400).
- The precedent for a module anchored through the vault process is recovery's forget log (`recovery.Factor.Counter`, set by the vault process; recovery F3). Follow it.

**Requirements** (local IDs under UPD-8 and U16):
- **SR3-6f-2a, the store side.**
  - `update.Store` gains an optional anchor with two methods, `Read() (uint64, error)` and `Raise() error`. `Raise` is monotonic and idempotent above zero.
  - When the store records an outside listing (`noteAttestors`, `FollowRoot`), it calls `Raise` before it writes `outside_attestor_listed`. If `Raise` fails, the write still happens, so the file is never weaker than today, and the error is returned.
  - `policy()` reports `outside=true` if the file exists or the anchor reads 1 or more. If the anchor read fails, `policy()` returns the error, and so `Security()` and `InterimAttestation()` are false and `Stage` returns `ErrPolicyMoved` (fail closed, as SR3-6f-1c pins).
  - A store with no anchor behaves as today.
- **SR3-6f-2b, the vault process side.**
  - `agentos-egress` keeps one NV counter for the update store on this PC. Name it by a fixed id distinct from vault ids, for example the SHA-256 of `"agentos update policy"` and the store's root key ID.
  - On a TPM host, define the counter at the first read, not at the first raise, so a fresh host and a cleared one never look alike. Record that it was defined (its ref and auth) in the vault process's own sealed state, next to the vault's own anchors (the recovery forget-log precedent), never in agentosd's files.
  - The counter is served to agentosd as two requests on the broker-only socket (the model/verify socket admits the broker's uid only): read, and raise. There is no lower or reset request.
  - Once the vault process's state records the counter as defined, a counter it cannot find answers "anchor missing", never 0 and never "no anchor". The store treats "anchor missing" as a read error: `policy()` fails closed (2a), so `Security()` and `InterimAttestation()` are false. The vault process alerts the owner as it does for `ErrCounterMissing`, and the owner's existing re-trust of the PC (custody.go, the tier-4 path that calls `host.anchor`) also defines a new update counter and raises it to 1 before reporting it anchored: after a clear nothing shows whether an outside attestor was listed, so the interim rule ends there (it only narrows). There is no new owner page.
  - "No anchor" is answered only on a host with no TPM. The store then logs it, and STATUS says interim attestation is not anchored on this PC. That case does not fail closed, because that would retire every interim release on a host without a TPM: a decision for Mark, not a builder. Record it in U16 as residual exposure, with one more: root that deletes the vault process's state as well as the counter and the store loses the vault itself, which the owner sees (CRED-8 recovery), so that route is visible, not silent.
- **SR3-6f-2c, the client.**
  - A small client in `broker/update`, or in an existing broker-side vault client if one exists, implements the anchor over that socket.
  - W5b or the agentosd wiring sets it on the store. This package does not edit `cmd/agentosd`. It adds one line to W5b's wiring conditions instead.

**Threat check for the reviewer.**
- Root on agentosd's files cannot lower the counter. The only TPM write is `IncrementCounter`, and the socket exposes no reset.
- A compromised agentosd can raise the counter. That only retires interim authority (it narrows), so it is acceptable. Check that this is the only effect.
- Every read error fails closed in `policy()`.
- A counter that was defined and is gone fails closed, matching P2-4d's `ErrCounterMissing`; no route turns "missing" into 0 or "no anchor". "No anchor" is answered only on a host with no TPM, is visible in STATUS, and is recorded in U16 as residual exposure.
- The defined marker lives only in the vault process's state; agentosd cannot clear it.
- The NV counter's auth value is not kept in agentosd's files.

Delivery notes (builder, 2026-10-09):
- 2a also carries a record found with the anchor at 0 into the anchor (`TestExistingRecordCarriedIntoAnchor`), so a box that listed an outside attestor before this package is anchored at its next check rather than only at the next listing.
- The re-trust raises the new counter only when the vault recorded one this PC no longer has. A first trust on a fresh install leaves it at 0 (`TestFirstTrustLeavesInterimRule`); raising there would end the interim rule on every new box.
- The counter's auth is 16 random bytes as hex, as the vault's own counter: a raw random auth holds a zero byte about one time in eight, which `tpmseal.DefineCounter` refuses (T7). Found as a one-in-three swtpm flake; pinned by `TestUpdateAnchorAuthHasNoZeroByte`.
- Wire answers: GET `/update-anchor` and POST `/update-anchor/raise` give 200 `{"anchored":true,"count":n}`, 200 `{"anchored":false}` (no TPM), 409 (anchor missing), 503 (locked), 500 otherwise. The client maps only `{"anchored":false}` to `ErrNoAnchor`.
