# P4-4: Attestation schema

Board section: Phase 4: open source.

Attestation schema: public `schema.json` of enumerated values for result class, channel, hardware (vendor, model, firmware, each listed under the one above, `unlisted` for what is not listed yet) and software versions per component; no free text, serial number or timestamp; strict decoding; `update.Attest` refuses to sign and `update.ParseAttestation` refuses to accept a statement outside it, replacing the free `hardware_class` string (OSS-4, for attestations; hardware-database entries reuse the hardware list in their own package) ([assumptions](../broker/attest/ASSUMPTIONS.md)). Statements signed under a newer schema still parse and count, with unlisted values read as `unlisted` (potency PB1, A5). Only canonical bytes parse: one signature, keyid checked, payload and envelope re-encoded exactly (security C1, A8). Carry-forward: the publication package generates the attestor key in broker code from `crypto/rand`, never from owner data or an agent, and rotates it on a broker-set schedule (A6); the attesting package fills hardware from measured DMI and versions from the installed release, uses `unlisted` exactly when the measured value is not listed, and reports every listed component the release installs (security C2, A9); A1 runs add real PCs and firmware to the list; the hardware-database package publishes the schema as a signed TUF target so hardware is listed without a release (potency PR1, A1); once release manifests carry component versions, `agentos-release` refuses one whose versions `schema.json` does not list (potency PR2)
