## Evidence and owner effect

Actual public-interface probes at `e19274c` set host trust false and private-data permission false. A failed trust save renders `not_mine` unchecked; retry invokes TrustHost(true). A rejected API key renders private permission checked; retry produces SetPrivateOK calls [false, true]. Network join failure resets the selected SSID to the first option. No actual TPM, provider or private-data effect was invoked. See the review's UX4-1 and committed evidence results.json.

## Bounded scope

Own setup.go/pages.go view/input/error state and focused tests; coordinate with the authoritative hooks if an effect can succeed before its response is lost. Do not change initial normative defaults, add generic browser storage, or introduce a new consent framework.

## Acceptance

1. For host-trust, private-permission and network operations, render the owner's attempted non-secret choice after validation, transient failure and ambiguous response. Retrying that rendered form must preserve the choice. Test both directions, not only defaults.
2. Bind retained choices to the authorized setup context, current stage and enrollment generation. Another client, stale tab or reset must not import them or gain authority. No GET may apply a choice.
3. Distinguish requested, applied and durably saved state. Inject failure before effect, after effect and at persistence; reconcile or require an explicit informed decision instead of silently changing trust/privacy or reporting unverified success.
4. API keys, passwords, submitted approval codes and seeds stay out of durable form state, logs and rendered retry values. Keep a failed secret field blank and explain what must be re-entered; retain the associated selected provider/SSID safely.
5. Keep existing order, enrollment, recovery, CSRF, cookie and backend authorization checks. A change to already applied trust uses its guarded operation, not a cosmetic form edit.
6. Extend UX3-4: untouched plan/hosted private permission submits false under SPEC; explicit opt-in and opt-out each survive retry. Do not infer an API default from a different route type. Replace stale checked-default assertions when the route-specific UI lands.

## Potency, security and delivery

Avoids accidental permission expansion and repeated work. Adds bounded non-secret state handling, not prompts or saved credentials. Runtime changes touch tier-A paths: fresh strongest L3 with threat check and separate Security sign-off; any policy change first goes to L1.
