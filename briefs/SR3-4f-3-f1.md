# SR3-4f-3-f1: a security Concern that stays open gets one follow-up digest line

Board section: Security and architecture review (2026-10-08). Source: lens review on #614, point 3. Class release, tier A.

**Why it matters.** When `Recheck` finds that an installed image fails a security check and the applier is mid-install, the pipeline records `Concern` (`effect.go:948-952`) and the digest says once "failed a security check while it was being installed … Nothing is needed from you" (`digest.go:254-263`), then sets `ConcernSeen`. If the withdrawal never completes, the adoption stays `Reverted == ""` and nothing says so again. The owner is told it is handled and never learns it was not.

**What happens on main.** `Adoption` carries `Concern`, `ConcernScore`, `ConcernSeen`, `ConcernStarts` (`pipeline.go:312-319`) and no timestamp or pass count. `Recheck` revisits the adoption each pass and, for the handover case, calls `concern` again, which does nothing because `a.Concern != ""` (`effect.go:964`). No other path reads the age of a Concern.

**Requirements:** SR3-4f-3 (parent), OP-7, CH-12 (plain words), CH-19 (no unverified claims). Protected adoptions (owner-approved or attested-release images) already surface a Concern with an UNDO step and are out of this row.

**Fix.**
- Record on first Concern `ConcernAt` (time) and count `ConcernPasses` (each `Recheck` that finds the same adoption still unreverted with the same Concern).
- When a security Concern on an unprotected adoption is `ConcernSeen`, still `Reverted == ""`, and either one day has passed since `ConcernAt` or `ConcernPasses >= ConcernFollowUpPasses` (const, 3), `Digest` adds one line and sets `ConcernFollowedUp`. Never a second follow-up; clearing happens when the adoption is reverted.
- The line names the step. Open question the builder settles from `broker/apply`: the one owner action that resolves a stuck withdrawal (a restart from the Wi-Fi page is the expected one, since the applier settles on boot). If no owner action resolves it, the line says the box keeps trying and gives the day it last tried, not a step, and the PR says so (CH-19: never promise an action that does nothing).
- Persist the new fields in the pipeline state (`json:",omitempty"` so old state loads).

**Acceptance tests (REQ: OP-7, CH-12, CH-19):**
- T1 `TestOpenSecurityConcernFollowsUpAfterADay`: a handover Concern shown, then `Digest` after a day with the adoption unreverted: exactly one follow-up line, containing the step; a further `Digest` is silent.
- T2 `TestOpenSecurityConcernFollowsUpAfterNPasses`: same by pass count, with the clock held fixed.
- T3 `TestFollowUpSilentOnceReverted`: a revert between first line and the threshold means no follow-up.
- T4 `TestProtectedConcernKeepsItsUndoLine`: the protected-adoption path is unchanged.
- T5 state round trip: reload from saved state mid-count; the count and timestamp survive; an old state without the fields loads.
- Mutant: drop the `ConcernFollowedUp` guard; T1's second `Digest` fails.

**Out of scope.** Changing how the applier withdraws, regression (non-security) Concerns, and the first-line wording.

**Scope:** `broker/change/pipeline.go`, `effect.go`, `digest.go`, a new `broker/change/concern_followup_test.go`, `broker/change/ASSUMPTIONS.md`, this brief.

**Dependencies:** SR3-4f-3 (merged). The `broker/change` files overlap SR3-4f-2-r1-f2, which ships in P2-2a-f4's maintain batch; check D-111 at start and wait for it to merge if it is open.

**Usage estimate:** 60k tokens, checkpoint at 60k. Builder model: strongest (tier A: `broker/change/`).
