# OWN-card-flow: the new core's first-boot Owner Card, after the page authority and before enrollment

Work item #3470 (SPEC HW-1, CH-9, STO-2). Tier A: keeper units, `mkosi.finalize` and `agentos-enroll` are gate files, so each slice also needs the separate Security accept (OPERATING §7). Written 2026-10-27 against main at the commit this brief merges on. The design and its invariants were decided in `briefs/OWN-card-ca.md` ("Order on the new core", #3469); this brief adds how the confirmed card's factors reach enrollment, which no row owned, and splits the work into two sessions.

**Waits on:** slice a waits on #3477 (MIG-4-recovery-r2), which edits `cmd/agentos-enroll/main.go`, `mkosi.finalize`, the preset and `tests/test_image_keeper.py` (D-111). Slice b waits on #3167 (OWN-card-ca slice a, which waits on #3465 and #3478) and on slice a's merge. Readiness reads the code: the slice b builder checks that `card.DisplayConfig.Authority`, `firstboot.ErrNoAuthority` and `localui.PageTLS.Authority` exist as #3167's brief names them.

## Why

On the new core nothing makes the first-boot Owner Card's authority, and nothing hands the confirmed card's two factors to enrollment (`broker/clerk/seal/ASSUMPTIONS.md` STO-2c-h: "nothing in the image writes `/run/agentos-setup` yet"). The CI boot test enrolls only because it injects synthetic factors through a tmpfiles credential (`image/ci_boot.sh`, `KEEPER_FACTORS`). After #3167, a box without an authority holds at the card step. HW-1 needs the authority before the card, and the card's confirm before the store. So a box that boots the image today never makes its store from a real card.

## What exists (read 2026-10-27)

- `agentos-keeper-enroll.service` runs `agentos-enroll` while no store exists and both `/run/agentos-setup/passphrase` and `/run/agentos-setup/recovery` exist. It is `WantedBy=multi-user.target`, so its conditions are read once at boot. Nothing starts it after a confirm later in that boot. `ExecStartPost=` removes both factor files.
- `agentos-enroll` reads the passphrase (trailing newline trimmed) and the recovery key as 32 bytes of hex (`seal.RecoveryLen`, `factors()`), and calls `putPageCA`, which makes a new authority with `pageca.New`. `readSecret` refuses a file that is not regular, root-owned and 0600-or-tighter.
- `pageca.Marshal`/`Unmarshal` are the authority's sealed form (certificate plus PKCS#8 key, at most `pageca.MaxSealed`). `Unmarshal` runs `pageca`'s load checks.
- `card.StoreRecoveryKey(text)` turns the card's printed 40-symbol key into the store's 32-byte recovery key (MIG-4-recovery-len #3406). `card.Card.VaultPassphrase` is the store passphrase.
- The owner page runs as `agentos-localui` (`broker/cmd/agentos-localui/agentos-localui.service`). Like every main-side unit, it is masked from `/run/agentos-setup`. Its card step is `localui.CardBox`: the confirm provisions the old core's vault over `unlock.sock` (`UnlockClient.ProvisionCard`), and a rerun resets it (`ResetCard`).
- #3477 adds the keeper's first socket-activated one-shot: `agentos-keeper-rotate.socket` (`/run/agentos-keeper/rotate.sock`, `Accept=yes`, `MaxConnections=1`, group-only access) and `agentos-keeper-rotate@.service` (`agentos-enroll -rotate-recovery`, `StandardInput=socket`, one JSON request in, one word out, the factors only in memory). This brief reuses that pattern. It adds no new channel kind.
- `mkosi.finalize` forbids `systemctl` in any agentos unit's commands (`REBOOT_WORDS`), so no unit may start enrollment by command.

## Decisions (engineering choices within HW-1; no SPEC change)

1. **One binary, three new modes.** `agentos-enroll` gains `-stage-page-ca` and `-take-factors`, and enrollment gains `-page-ca-file` and `-page-ca-cert`. There is no new binary: the authority's key, the factors and the store are all enrollment's, and `agentos-enroll` already links `pageca`, `card`'s key derivation and `seal`. It is not a `tools/trusted_core.txt` root, so no D-159 row is owed. Slice a checks that with `tools/trusted_base.py` and adds the row if it reports growth.
2. **Stage the authority (`agentos-keeper-pageca.service`).** This is a oneshot with `RemainAfterExit=yes` in the keeper slice, listed in `KEEPER_UNITS`. It has `ConditionPathExists=!/var/lib/agentos-store/store`, runs `Before=agentos-keeper-enroll.service agentos-localui.service`, and is `WantedBy=multi-user.target`. It runs `agentos-enroll -stage-page-ca -page-ca-file /run/agentos-setup/page-ca -page-ca-cert /run/agentos-page-ca/authority.der`. It makes `pageca.New(pageca.DefaultName, buildTime(), nil)`. It writes `pageca.Marshal` to the staged path (0600 root) and then the certificate DER alone to the published path (0644 root). Each write goes to a hidden temporary name in the same directory (`O_CREAT|O_EXCL|O_NOFOLLOW`), then `fsync` and `link` to the final name, which fails if that name exists. So neither file is ever partly written under its final name, and neither is overwritten. **Rerun:** if both files exist, it does nothing and exits 0. If only the staged pair exists (a crash between the two writes), it publishes the staged pair's certificate. If only the published certificate exists, it refuses with fixed words and changes nothing, so a certificate without its key never gets a second, different key. It zeroes the marshalled bytes. No TPM: `DevicePolicy=closed` with no `DeviceAllow=`. It is not in `TPM_UNITS`.
3. **The published directory.** tmpfiles.d gets `d /run/agentos-page-ca 0755 root root -`, plus its `tmpfiles.allow` line. It is not a `KEEPER_PATHS` entry: the certificate is public, and the owner side must read it. Only root can create or replace a file there.
4. **The owner side reads it (slice b).** A new `localui.ReadAuthorityFile(path)` opens the file with `O_NOFOLLOW`, takes `fstat` of the open file, and refuses unless it is a regular file owned by uid 0, not group- or world-writable, and at most 4 KiB. It returns the DER, and the card's own check (#3167, `card.NewDisplay`) then runs on it. At first boot the card step takes its authority from that file. When the file is absent (an enrolled box, or a failed staging), it falls back to `PageTLS.Authority()` (#3167), which comes from the kernel after enrollment. With neither, it holds with the fixed no-authority line (decision 9).
5. **The confirm hands the factors over a keeper socket.** `agentos-keeper-setup.socket` has `ListenStream=/run/agentos-keeper/setup.sock`, `SocketUser=root`, `SocketGroup=agentos-localui`, `SocketMode=0660`, `DirectoryMode=0755`, `Accept=yes`, `MaxConnections=1`, and the same comment shape as #3477's rotate socket. `agentos-keeper-setup@.service` runs `agentos-enroll -take-factors -setup-dir /run/agentos-setup -page-ca-cert /run/agentos-page-ca/authority.der -state /var/lib/agentos-store`, with `StandardInput=socket`, `StandardOutput=socket`, `StandardError=journal`, `TimeoutStartSec=60`, and hardening as `agentos-keeper-rotate@.service`, with no TPM. The request is one JSON object of at most 8 KiB: `{"v":1,"passphrase":…,"recovery_key":…,"fingerprint":…}`, where `recovery_key` is the card's printed text and `fingerprint` is the one the shown card printed. The answer is one word:
   - `ok`: the factors are in place for enrollment, or the store was already made from this card.
   - `bad`: a malformed request, a passphrase that fails the card's shape check, or a recovery key that `card.StoreRecoveryKey` refuses.
   - `authority`: the fingerprint is not the published certificate's, or there is no published certificate and no store.
   - `taken`: other factors are already in place.
   - `kept`: the store exists and this passphrase does not open its passphrase slot.

   The one-shot validates first, derives the 32-byte key with `card.StoreRecoveryKey`, and writes `passphrase`, then `recovery` (hex), each by temporary name and `link` as in decision 2. `recovery` comes last because its existence triggers enrollment. If both already exist, it compares them in constant time and answers `ok` when they are equal, so a retry of the same card is idempotent (F10). It answers `taken` when they differ. When the store exists (decision 8), it opens the passphrase slot with the offered passphrase, answers `ok` if the slot opens and `kept` if it does not, and writes nothing. It zeroes every factor buffer. No factor, and no part of the request, reaches stderr, the journal or the answer.
6. **Enrollment starts on the factors (`agentos-keeper-enroll.path`).** The path unit has `PathExists=/run/agentos-setup/recovery`, `Unit=agentos-keeper-enroll.service`, and is `WantedBy=multi-user.target`. PID 1 watches the path, so no main-side unit and no `systemctl` is involved. The enroll unit gains `After=agentos-keeper-pageca.service`, `ConditionPathExists=/run/agentos-setup/page-ca` and `Wants=agentos-keeper-kernel.service`. With `Wants=`, the kernel's unit starts in the same boot once the store exists. Its own condition and `After=` already order it. Whether the kernel then runs setup-only on that boot is #2996's behaviour, not this row's. The test checks only that the unit is pulled in. Enrollment's `ExecStartPost=` also removes `/run/agentos-setup/page-ca` and `/run/agentos-page-ca/authority.der`. A failed enrollment keeps all four for a retry. The `.path` unit is named `agentos-keeper-enroll.path`. Slice a extends `mkosi.finalize`'s keeper check so that every `agentos-keeper-*.path` names only a `KEEPER_UNITS` unit and watches only under `KEEPER_PATHS`, with a mutant test.
7. **Enrollment binds the staged authority.** With `-page-ca-file` set, `putPageCA` reads the staged pair through `readSecret` (bounded at `pageca.MaxSealed`) and calls `pageca.Unmarshal`, which runs the load checks and checks that the key matches the certificate. It reads the published certificate with the same root-owned, regular-file, no-follow check and refuses unless `a.Certificate()` is byte-for-byte equal to it. Only then does it `st.Put(handoff.PageCAEntry, …)` the staged bytes as read, so the kernel serves exactly the printed authority. Every refusal is fixed words before the store is staged, and changes nothing. Enrollment zeroes the bytes it read. Without `-page-ca-file` (tests, and the `-restore` path, whose authority comes from the backup per MIG-4-recovery-f1), it keeps today's `pageca.New`. The image unit always passes the flags. A rerun after a crash restages the store from the same staged pair, so the fingerprint stays the printed one. That replaces the current comment's "a rerun … makes a new one".
8. **A crash between the hand-off and the latch.** The page saves its latch only after `ok`. If the box restarts after enrollment and before the latch, the page shows a new card whose authority comes from `PageTLS` (decision 4). Its confirm gets `ok` only if its passphrase opens the store, which a new card's never does. So it gets `kept`, and the page latches with the fixed line "This box already holds the keys of the Owner Card you confirmed before it restarted. Keep that card and throw this one away." That is safe: `ok` was only ever answered after a confirm, so the owner holds the earlier card. The keeper refuses the new card, so no card that does not open the store is ever accepted as the store's.
9. **The old core's vault keeps its provision until its own deletion row.** On confirm, `CardBox` calls the keeper first and the vault second. A keeper refusal stops before the vault. A vault failure after a keeper `ok` is retried by the page as today, and the keeper answers `ok` again for the same card. Nothing replaces the vault's role in this row, so PLAN §3's delete-in-the-same-PR rule does not yet apply. The vault call and `ResetCard` go with the row that deletes the vault. That row's builder deletes them, and this brief's ASSUMPTIONS row names it so it is not missed. **Reviewer check:** if a reviewer reads PLAN §3 as requiring the vault call's removal here, that is a design question for Mark (via the coordinator), not a fix in the build.
10. **UX: the no-authority hold line** (release finding on #3469). This replaces #3167's text with the page's style: "I can't make your Owner Card yet, because my page certificate isn't ready. Restart the box and open this page again. If you see this again, tell me in a text." The same text is used for `authority` answers. `kept` and `taken` get their own fixed lines. A keeper that cannot be reached gets "I couldn't save your Owner Card's keys. Wait a minute and confirm again."

Rejected (from #3469, unchanged): enrolling before the card is shown, and a second sheet after enrollment. Also rejected here: (a) agentosd (root, outside the mask) writing the factors, because it is the old core, frozen and serial-chained; (b) the page writing files into a spool that a keeper path unit moves, because a root reader would then parse a lower-privileged user's files, and the page could not learn the outcome; (c) the keeper drawing the card's secrets, because the page must hold them to show the card anyway, and the confirm would then need a second channel.

## Lifecycle matrix (integration owner: slice b, which wires the flow into the running path)

| Stage | Outcome | Slice |
|---|---|---|
| First boot, happy | pageca stages and publishes; the card prints that fingerprint; the confirm gets `ok`; the path unit starts enrollment; the store holds the same authority; the kernel's unit starts; the staged files are gone | a, b |
| Staging failed (no published cert) | the card step holds with the decision 10 line; no randomness drawn; enrollment never runs (no `page-ca`) | a, b |
| Page restarts before the confirm (no reboot) | the same published cert, so the same fingerprint, on a new card (F10) | b |
| Reboot before the confirm | tmpfs is empty; a new authority and fingerprint; a new card | a |
| Crash during staging, between the two writes | the rerun publishes the staged certificate; a published-only state is refused | a |
| Confirm retried with the same card | `ok`, nothing rewritten | a |
| Rerun card (`Again`) after a hand-off, before enrollment ends | the new card's confirm gets `taken`; the page holds with its fixed line; a reboot starts over | a, b |
| Fingerprint on the card is not the published one | `authority`; nothing written | a |
| Malformed, oversize or wrong-shape request | `bad`; nothing written; nothing logged but the word | a |
| Enrollment fails | the factors and staged pair stay; a rerun (next boot's tmpfs is empty, so a reboot starts over) | a |
| Enrollment crash after staging the store | the rerun uses the same staged pair; the same fingerprint | a |
| Staged pair and published cert differ (tampered) | enrollment refuses before staging; nothing changes | a |
| Restart after enrollment, before the latch | a new card from the `PageTLS` authority; its confirm gets `kept`; the page latches with the keep-that-card line | a, b |
| Enrolled box, later boots | pageca skipped; no published cert; the card latch is already confirmed; rotation uses `PageTLS` (#3167) | a, b |
| CI boot with injected factors | pageca stages first (ordering); enrollment stores the staged authority; `ci_boot.sh` still sees `enroll=ran kernel=active` | a |

It catches a unit outside the keeper group, and a widened socket.

**Recurring kinds to check (security and UX lens READMEs):** a guard that fails open on a missing file or a missing answer; raw error text on the page or in a fixed-class log; a root process parsing a lower user's input without a bound (the setup socket); a secret in a log or answer; a check by path that a rename can race (use the open descriptor); a scope that omits the test files the change forces; two names for one thing on the page (the "page certificate" here and the card's "page fingerprint" from #3167 must read as one).

## ASSUMPTIONS rows

- `cmd/agentos-enroll` (slice a): the staged pair is the only authority enrollment stores at first boot; staging never overwrites; `-take-factors` is the only writer of the factor files and answers only the five words; the image passes `-page-ca-file` always.
- `image` (slice a): `agentos-keeper-enroll.path` is how a confirm starts enrollment; `/run/agentos-page-ca` is root's and public.
- `localui` (slice b): the first-boot card's authority is the published file, then `PageTLS`; the confirm calls the keeper and then the vault; the vault call is removed by the vault's deletion row.
