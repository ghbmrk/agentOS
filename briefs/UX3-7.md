## Problem and evidence

A notice promising retrieval must address an existing policy-allowed result, or state truthfully that it is unavailable.

Evidence and fixed-main source anchors: [deep UX review, UX3-7](../reviews/ux/2026-10-08-deep-ux-review.md); [synthetic probes and limits](../reviews/ux/evidence/2026-10-08/README.md). Runtime remedies remain open after this brief is registered.

## Intended scope

broker/owner/ notification result contract, broker/cmd/agentosd/evidence.go, authenticated localsrv/localui retrieval; existing kept-reply custody. Coordinate with the existing package instead of building a competing flow. SPEC/DECISIONS are out of scope; any unresolved interaction or authority contract goes through an L1 spec-diff first. Record changed assumptions in the affected package.

## Acceptance evidence

1. Exercise short/long public/private outputs, the benign source-code sentence, and synthetic secret canaries. Keep disclosure filters conservative and credentials out of SMS, logs and stored display payloads.
2. Before emitting a retrieval pointer, durably retain only the authorized redacted payload under an immutable result/destination identity. If this fails or policy forbids retention, emit an accurate unavailable notice rather than a false pointer.
3. Across restart, failed delivery, storage failure, expiry and the twenty-first kept result, a pointer resolves to the exact authorized result or an authenticated expired/unavailable state. Never regenerate it from guest claims.
4. Unrelated owners/sessions/destinations cannot retrieve the result. Preserve private custody, bounded retention and goal-forgetting semantics; do not introduce a public relay or new remote destination.

## Security and potency constraints

Only the minimum truthful withheld-result path is proposed release. The broad CH-20p history UI and CH-20m remain later; CH-20w delivery alone does not preserve short filtered replies.
