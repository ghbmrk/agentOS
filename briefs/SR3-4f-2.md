**Today.**
- `unsettled` (effect.go:400) refuses every revert of a `Staged` adoption except `WhyFallback`: the owner's UNDO and Recheck's security and regression reverts get "Update N starts at the next restart; undo it after." That is right only between `Execute`'s pre-Install save and the boot that settles it (`Applying` set). A release can wait days in `Pending` for a free moment, and nothing can cancel it there.
- Three applier paths drop a pending release and leave its adoption `Staged` with nothing to settle it: `Tick`'s narrowing drop (apply.go:391), `Execute`'s `ErrPolicyMoved` drop (apply.go:571), and `schedule` replacing `Pending` with another adoption or version (apply.go:313). The digest (change/digest.go:90) keeps saying "starts at the next restart", and UNDO is refused for good.
- A security-authorized release whose attestor policy narrows after `Install` but before the restart is restarted into anyway: `restartIfHandedOver` (apply.go:432) never rechecks `rel.Security()`.

**Requirements** (local IDs under UPD-1, UPD-8, OP-4, OP-5, CH-12):
- **SR3-4f-2a (SR3-4-f3), withdraw before handover.**
  - `unsettled` refuses only while the applier holds the adoption in its handover window. Add to the applier a method, for example `Withdraw(adoption string) error`:
    - It returns `ErrApplying` while `Applying` names that adoption or `executing` is set for it.
    - Otherwise, if `Pending` names it, it drops `Pending` and `a.rel` durably (save first, then memory) and returns nil.
    - It returns nil for an adoption the applier does not hold.
  - The pipeline takes it through a small interface set by the wiring (for example `Pipeline.Withdrawer`). Call it before any state change in `revert`/`revertLocked`, and never while holding `p.mu`: the lock order is `a.mu` → `p.mu` (`Resume` holds `a.mu` while calling `StageFailed`). If the refactor makes that impossible for `revertLocked`, take the call out to its callers and say so in the PR.
  - With no `Withdrawer` set (tests, first boot), keep today's refusal: fail closed.
  - After a successful withdraw the revert proceeds as for any adoption: journaled, `OriginOwner` or `OriginPipeline`, with its own why.
  - The refusal text in the handover window says what is true: "Update N is being installed; undo it after it starts." (CH-12).
- **SR3-4f-2b (SR3-4-f4, SR3-6-f3 point 3), settle on drop.**
  - Add to `Stager` a method, for example `StageDropped(ctx, id string) error`, that reverts a `Staged` adoption with a new why `WhyDropped`. Like `StageFailed`, it is idempotent: an adoption already reverted is a success that changes nothing, and a `Confirmed` one is an error. `Check` admits it for `OriginPipeline` (effect.go:78).
  - The applier calls it, outside `a.mu`'s critical section or under the existing `a.mu` → `p.mu` order (never the reverse), and after its own state save. Use the same converge pattern as `Resume`: if the call fails, keep an obligation in saved state (for example `Dropped []string`) and retry it on the next `Tick`. Call it on:
    - `Tick`'s narrowing drop;
    - `Execute`'s `ErrPolicyMoved` drop;
    - `schedule` replacing a pending release whose adoption differs;
    - SR3-4f-1b's refused outcome (two unrecorded `Install` attempts): the release will not be retried automatically, so its adoption is settled now;
    - `Schedule` refusing a refused `Ref` with `ErrRefused`: Loop 3's next check adopts the same release again under a new ID, and that incoming adoption is settled with `WhyDropped` too, so no adoption is left `Staged` by a refusal. Until the owner calls `Retry`, each Loop 3 check may adopt and settle once more; record that in A5 (L3 delta on #572, option (a));
    - a not-handed abandon. Within one boot, while `Pending` still names the adoption, the release is still due and A5 holds: no settle. After a process restart `New()` has cleared `Pending` (SR3-4f-1c pins that), so nothing holds the release any more: settle at once. Decision (L3 on #572, point 3): settling at once is chosen over waiting for Loop 3's next check, because nothing would ever reschedule the old adoption ID after a restart, and waiting would need a second obligation kind tied to Loop 3. The cost is accepted: after a power cut between the pre-Install save and the handover, Loop 3 adopts the release again under a new ID, and a release without attestor authority is asked about again. Record this cost in A5.
  - Rescheduling after a drop: the reverted adoption is final. Loop 3's next check adopts again (a new adoption ID) under the current policy. The builder reads W5b's brief and states in the PR which adoption ID W5b passes to `Schedule`. If W5b would pass a reverted adoption, `Schedule` must refuse it (ask the pipeline through `Stager` or a lookup hook). If that cannot be decided from the code and briefs, stop and escalate to L1 rather than guess.
  - The digest line for a `Staged` adoption the applier does not hold in `Applying` says "Staged update N; it installs when the box is free". The line for one in the handover window stays "it starts at the next restart". If the digest cannot know which, use the first wording for all `Staged` lines and record why in change ASSUMPTIONS.
- **SR3-4f-2c (SR3-6-f3 point 4), a narrowing after Install.**
  - In `restartIfHandedOver`, for a release that was scheduled with `Security` set and whose `a.rel` no longer reports `Security()`, do not restart. Under `a.mu`, `Activator.Abandon`, then `Store.DropStaged`, then save `Applying = nil` with `Last` `doneNotHanded` (no fallback is recorded), and then `StageDropped`.
  - `a.rel` must still be set in this window. If a restart of the process lost it (it is never persisted), treat a `Security`-scheduled handover with no `a.rel` the same way: it fails closed. A non-security release goes on as today.
  - The window an unplanned reboot after `Install` leaves open (the image boots before the recheck runs) is out of reach here. Record it in apply ASSUMPTIONS.
