# UX3-1: Visible provider sign-in and bounded retry

**Class:** proposed release (P1); primary lane, unclaimed. This is a cross-lane advisory handoff, not adopted design or implementation authorization. Recheck current main and concurrent PRs before claiming work. **Requirements/acceptance:** ONB-3, ONB-4, ONB-5, ONB-8; A1. **Dependencies/overlap:** P2-2w c4.

## Problem and evidence

A fresh device-code provider must offer a visible start control; explicit pending/expired/declined/failed/connected states must support retry without resetting owner enrollment.

Evidence and fixed-main source anchors: [deep UX review, UX3-1](../reviews/ux/2026-10-08-deep-ux-review.md); [synthetic probes and limits](../reviews/ux/evidence/2026-10-08/README.md). Runtime remedies remain open after this brief is registered.

## Intended scope

broker/localui/; provider challenge projection in broker/cmd/agentosd/setuphooks.go only as required by c4. Coordinate with the existing package instead of building a competing flow. SPEC/DECISIONS are out of scope; any unresolved interaction or authority contract goes through an L1 spec-diff first. Record changed assumptions in the affected package.

## Acceptance evidence

1. GET fresh Connect AI and follow only rendered controls through start and completion. The empty map entry must never show an empty URL/code instead of Sign in. Retain a template-level regression; direct endpoint POST alone is insufficient.
2. Expire and decline a synthetic challenge, fail the provider temporarily, and restart where the provider supports it. Show the real status and offer a scoped new challenge; never reuse a known expired challenge as current.
3. Complete via API key and device code independently. Retain pairing, codes and recovery steps across retry. A different setup device cannot replace the pending challenge.
4. Keep provider sign-in separate from AgentOS authenticator codes, secrets in the vault, and current explicit private-route permissions.

## Security and potency constraints

No new authority or required setup step. Challenge lifecycle changes must match the actual provider contract; do not invent an expiry from wall time alone.
