Work items #3417 (MAIL-main-a), #3419 (MAIL-keys), #3420 (MAIL-unit), with #3421 (MAIL-reader-sock) and #3422 (MAIL-world), filed 2026-10-27. The remainder of MIG-4-run (#2682) for the mail clerk: the library (`broker/clerk/run` `MailHost`, `ServeMail`, `ServeClerk`) is on main, but no `cmd/` main runs it, no process gives it a key, and no unit starts it. #3059 (Gmail Connect in the image), #3015 (the IMAP connection process), #3121 (A21-image) and, through A21, the TN release rows wait on it. **Standing rules that apply.** D-154's keeper boundary (#2682 comment 6377262816): the mail clerk is a keeper process; only typed frames cross; a caller's side comes from the listener; the clerk ends its own TLS through `netguard`; it links no inference, guest, browser, reader, voice or owner-page server; it takes no clock or entropy from the main side. ### Slice b's mechanism (recommendation; settled in slice b's PR, not here)

The literal reading of option A, the kernel as the clerks' parent, does not work: the kernel's unit runs with `PrivateNetwork=yes` and no capability to change uid, so a child of it could neither reach the mail server nor run as `agentos-mail`. Recommended instead: each clerk's unit has `OpenFile=/run/agentos-kernel/clerk-<name>.key:clerk-key`; the service manager (uid 0) connects at every start and restart, and the kernel, admitting only uid 0 on that socket, writes that clerk's key and closes. The clerk gets it as descriptor 3. A process under the clerk's uid cannot reach the socket (peer uid check); root already can read any process. This keeps "no request path a clerk can call" and "every restart gets the key", and drops "clerks start only through the kernel" in favour of systemd's supervision. Any uid-0 process could also call that socket, agentosd (main side, root) among them, so the kernel should narrow it further: read the peer's pid from SO_PEERCRED and require `/proc/<pid>/cgroup` to be `agentos-keeper-<name>.service`, which also binds the socket to the right clerk. The main should check `LISTEN_FDNAMES=clerk-key`, which systemd sets for an `OpenFile=` descriptor. A root launcher forked by the unlock step was considered and rejected: it would be a long-lived root process, which STO-2b-1-v rules out. This drops "clerks start only through the kernel" from Mark's option A, so it goes to a Decisions card before slice b starts. Slice a does not depend on it: `clerkkey.Read` takes a pipe or a connected socket.

## MAIL-main-a in detail

**Process contract.** `agentos-clerk-mail -dir <state dir> -anchors <file> -kernel-sock <path> -kernel-uid <uid> -owner-sock <path> -owner-uid <uid> -planner-sock <path> -planner-uid <uid> [-imap-conn <path>]`, every path absolute.

1. **Refusals before the key is read.** Never root; `procguard.Isolate(kernel, owner, planner uids)` (refuses running as a peer, sets non-dumpable); the three peer uids distinct and positive, except that the owner side's uid may be 0 (agentosd runs as root, and `accountsock` calls as root today; #3059 sets it). The anchors file is read and checked next: owned by root (by the test's uid in tests, through an unexported field), not writable by group or other, not a symlink, at most `handoff.MaxAnchors` keys, in `handoff.ParseAnchors`' form; none or a bad file refuses. A refused start leaves descriptor 3 unread, as `agentos-kernel` does (`TestARefusedKernelLeavesTheKeysUnread`).
2. **The key.** `clerkkey.Read(f, "mail")` reads descriptor 3 to EOF under a small bound, from a pipe or a connected socket only: a versioned frame of the clerk's name and a 32-byte key. Another clerk's name, another length, trailing bytes, or a regular file refuse. `Key.Sealer()` and `Key.HandleSecret()` derive two separate keys from it (HKDF-SHA256, labels `agentos.clerk.sealer.v1` and `agentos.clerk.handles.v1`, the name bound into both), and `Wipe` clears it. `clerkkey.Marshal` is what slice b's kernel writes. It is a new package, not part of `clerk/handoff`, because the trusted core links `clerk/handoff` (tools/trusted_core.txt) and must not grow without Mark's `Trusted-core` decision.
3. **The clerk.** `run.OpenSecrets(dir, sealer)`; `run.NewMailHost(ctx, dir, sec, MailConfig{Anchors, HandleSecret, Sealer, Ask, World, Conn})`. `Conn` dials `-imap-conn` (the per-session connection process's socket, #3015); without the flag `Conn` refuses every session. It is never nil: `imapsmtp.New` would fill a nil `Conn` with `imapconn.Pipe()`, parsing IMAP in this process and undoing #2937 gap 2. `Ask` is a function that fails (no mail is classed, so the clerk acts on none); MAIL-reader-sock adds the frame and its flag. `World` returns an empty world with `Today` from this process's own clock (rule 5). TLS and the guard stay `MailConfig`'s defaults (`netguard`, rule 3).
4. **Sockets.** The kernel's: `proc.ListenClerk(kernelSock, kernelUID)` and `proc.ServeClerk(ln, host, anchors)`. The owner side's: `run.ListenMail(ownerSock, ownerUID)`, `run.ServeMail(ln, host, run.MailOwnerSide)`. The planner's: the same with `MailPlannerSide`. A socket that stops serving ends the process for its unit to restart. SIGTERM ends it cleanly.
5. **Links.** The main links no `infer`, `guest`, `browser`, `localui`, `localsrv`, `modelroute`, `tpmseal` or `clerk/seal` (rule 4; only unlock opens the store).

**Not in this slice.** Who writes the anchors file or the key (b); the unit (c); the reader process and the world source (their rows); a start-up check that the Secrets file opens under this key (a wrong key today fails at the first sign-in, which tells the owner to set the account up again; ASSUMPTIONS MAIL-main-a-4).

**Requirement IDs:** CLK-1, CLK-2, CLK-4, KRN-2, D-146, D-154 rules 1 to 5.

**Acceptance tests:**
- `broker/clerk/clerkkey/clerkkey_test.go::TestClerkKeyRoundTrip`: `Marshal` then `Read` gives the same key; another name, a short or long key, trailing bytes, another tag, the kernel's tag and an empty read are refused. Fails if a model clerk's key opens as the mail clerk's.
- `clerkkey_test.go::TestClerkKeyComesOnlyFromAPipeOrSocket`: a regular file is refused, a connected socket is read.
- `clerkkey_test.go::TestClerkKeysDeriveApart`: the sealer key, the handle secret and the raw key are pairwise different, and two clerks' sealer keys from the same raw key differ. Fails if one key does two jobs.
- `broker/cmd/agentos-clerk-mail/main_test.go::TestFlags`: each missing or relative path, a uid of 0 for the kernel or planner, a negative uid, and two equal uids are refused; an owner uid of 0 is accepted.
- `main_test.go::TestARefusedClerkLeavesItsKeyUnread`: as root or a peer's uid, the start is refused and descriptor 3 is not read.
- `main_test.go::TestTheAnchorsFileMustBeRootsAlone`: an anchors file writable by group or other, owned by another uid, in an open directory, a symlink, a directory, missing, empty, damaged, too long or with too many keys is refused, and through `start` the key stays unread.
- `main_test.go::TestTheKeyMustBeTheMailClerks`: another clerk's key, or a damaged one, opens nothing.
- `main_test.go::TestTheMailClerkServesItsThreeSockets`: the body run in-process with the test's uid on all three sockets: the owner side's `Status` answers, the planner's `Listing` is `ErrNoMailAccount`, a `do` on the kernel's wire reaches the mail clerk (`no-account`), and each socket refuses the other side's calls. Fails if a socket is served with the wrong side's table. (The view's anchor check is `kernel/proc`'s own, tested there.)
- `main_test.go::TestNoIMAPConnParsesNoIMAPInProcess`: with no `-imap-conn`, `Conn` is not nil and refuses every session.
- `main_test.go::TestTheMailProcessLinksNoMainSideCode`: `go list -deps` of the main has none of the packages in item 5.
- `main_test.go::TestRealMailClerkAsRoot` (root only, skipped otherwise): the built main runs as `nobody` under distinct peer uids, all its uids and gids nobody's; the owner side (root) is served and refused on the kernel's and the planner's sockets; the process is non-dumpable (its `/proc` files are root's). **Usage estimate:** a: about 90k tokens (main ~300 lines, handoff ~80, tests ~450). b: about 130k. c: about 70k.

**Lifecycle (integration owner: MAIL-unit).** First boot after setup: the kernel starts, then the mail unit, which gets its key and the anchors file and serves an empty account. Restart of the clerk: same key (derived, deterministic), same Secrets, the account comes back. Restart of the kernel: reboots the box (#2998), so the clerk restarts with it. Update: same store, same derivation, same key. Removal of the account: `removemail` on the owner socket. MAIL-unit's test matrix covers start, clerk restart and an update's reboot on the image; slices a and b test their own stage.
