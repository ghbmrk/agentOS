# 2573-f3 (clerk half of #2661): the browser clerk sends one exact, owner-approved submit

Board row: #2661 (class:release, tier A, lane:primary). Source: the round-1 reviews of PR #2611 (Security 6317300339, UX 6317274325, combined 6317282595, Potency 6317274712) and the combined delta review 6319449890. It builds on #2611, which is merged. Tier A, so the builder runs on the strongest model. Usage estimate: 120k tokens, with a checkpoint at 90k.

**Why (facts).** After #2611 the browser clerk sends reads only. On a session that may hold the owner's identity, the gate (`judgeClosed` in `broker/browser/gate.go`) refuses every action that may change state with `approval_required` and a filtered `to`, and `Clerk.Do` refuses every `post` step. So a logged-in browser cannot submit a form or press a button. CLK-3 allows such a submit only after the owner approves the exact request. D-147 (Mark, 2026-10-21) asks for one tap per task on the owner's accounts. This half builds the clerk side. The owner prompt, the tap and the step-4 wiring are sub B's.

## Requirements (from SPEC.md)
- **CLK-3, unknown submits:** "the clerk blocks every state-changing request and holds the first as the submit. The owner gets one high-risk approval (CH-10) in fixed wording from fields the clerk reads (origin, method and URL, the control's visible label, the body fields with their form labels, hidden fields listed) ... site text is quoted, length-capped and confusable-folded. Approval releases exactly the held request, only if it is unchanged apart from a recognized session or anti-forgery token."
- **KRN-8:** a clerk performs a step at most once, and an unknown result is reconciled, never resent blind.
- **CLK-2:** the clerk re-checks just before acting.
- **KEY-2:** the clerk's facts, not the planner, say what a step carries.

## Design
The approval is a key, so the kernel checks it and its log counts it. No new log entry or kernel type is needed.
1. A `read` step whose action needs approval is refused unsent, as now. Its result also carries an `Approval`: the fields the gate read, and `Print`, a keyed hash over them and the canonical request.
2. The owner's one tap per task issues a key narrowed to verb `post` on this clerk, with `LimitContent(<the task's prints>)`, `LimitUses(<their count>)` and an expiry. The prompt and the tap are sub B's.
3. The planner sends the action as `post{to: Approval.To, msg: <the request line>}` with content `Print`. The kernel admits it only under a key whose content set holds that print. The clerk's facts rebuild the approval from the page as it is now, so a claim that differs is refused (`claim`).
4. Just before sending, under the gate's lock, the gate rebuilds the approval again. It sends only if `Print` and `to` are unchanged. Each print is sent at most once in a process. The key's use count and the kernel's duplicate guard, both kept in the log, cover a restart.

## Package IDs
- **BRS-1 Prompt input.** `browser.Approval` is built only from fields the gate read: origin, page, verb, the control's role, its label (quoted, capped and confusable-folded) and target, the option, the text typed and submitted, the fields the agent typed on that page with their labels, and the canonical request (filtered). It carries no planner prose. Method and hidden fields are not in the accessibility snapshot, so `FieldsComplete` is false until the executor reports them (open point).
- **BRS-2 Exactly once, by canonical request.** `Print` covers `Request.Encode()`, never the raw `msg`. A reordered or re-spaced line is the same print, so it is not sent twice.
- **BRS-3 Unchanged at dispatch.** Any change to the label, target, page, typed fields or request changes `Print`, and the submit is refused unsent. Query values named in `Config.TokenParams` (the recipe's session and anti-forgery tokens) are left out of the hash, so a rotated token still sends.
- **BRS-4 Binding.** A redacted value is compared through an HMAC of its raw form. The HMAC key is random and held only by the gate, so one approval cannot match many targets, and the planner cannot test guesses against a print. The post's `to` must equal the approval's `To`. `to` alone releases nothing.
- **BRS-5 Probe never resends blind.** A post the clerk refused unsent probes `notdone`. One it saw succeed probes `done`. Any other post probes `unknown` (parks), including after a restart. A logged-out read probes from what `Do` judged and recorded, never from the refs the gate holds now. With no record, as after a restart, any line that names a ref probes `unknown` (combined 6319449890 points 1 and 2).
- **BRS-7 Bounded log detail.** A result's title, detail and refused-navigation list are capped, so a logged result is at most `MaxDetail` bytes. The snapshot stays whole, already bounded by `MaxSnapshot`, because the planner reads it.

K9 (a request id the driver echoes, #2609) needs the executor to echo the id. The executor lives outside `broker/browser`, so K9 stays with #2609.
