## Finding and evidence

[Review finding F3](../reviews/security/2026-10-08-architecture-review.md#f3) at main `7b753eb87f606ea2268ca536d429d47989dba196`.

**Confidence:** Reproduced at the gate's approval-item boundary; page rendering verified by source.
**Exposure:** LocalUI now permits grant requests, but ordinary pre-allowance creation and several adapter flows remain incomplete. The finding is about the shared grant approval path, not a demonstrated remote UI entry point.

The gate puts only short(spec) in owner.Item.Object. The local page renders that item's object/detail/amount/recipient fields. Although the short() comment promises that the page shows Describe(), the complete description is not carried on this approval path. Attention suggestions can show Describe earlier, which does not make the final approval complete.

**Observed:** The final item showed 'pre-allow invoice.send on mail, 50/day'. It omitted the recipient restriction, fixed template, 150000.00 amount cap, 25-per-record bound and seven-day hold from the actual rule. Describe(spec) contained all of them.

**Impact:** The owner cannot verify the actual scope on the card where approval occurs. Materially different grants can present the same visible scope. This undermines informed consent even if the underlying intent is immutable and correctly bound.
