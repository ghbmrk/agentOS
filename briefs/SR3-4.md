## Finding and evidence

[Review finding F4](../reviews/security/2026-10-08-architecture-review.md#f4) at main `7b753eb87f606ea2268ca536d429d47989dba196`.

**Confidence:** Reproduced in both transient-confirmation-error and crash-boundary scenarios.
**Exposure:** Merged update/apply packages; not yet constructed by agentosd. Fix before W5b and the real image activator are integrated.

Resume commits the update store and removes staged.json before confirming the change-pipeline adoption and clearing persisted Applying state. A failure between those stores leaves Applying present but its stage already consumed. On restart, CommitStaged refuses the missing stage (or the already-installed version), so the remaining steps are never reached.

**Observed:** After a successful boot and one interrupted settlement, three consecutive Resume attempts after reopening returned 'release 1 is not staged'. Installed version was already 1; pipeline confirmations remained zero; STATUS continued to report 'installing'. Tick refuses further updates while Applying remains set.

**Impact:** A recoverable I/O failure or process/power interruption can permanently block future updates and misreport health. Merely retrying on startup cannot repair the state.

**Source anchors:** [`broker/apply/apply.go:591`](https://github.com/ghbmrk/agentOS/blob/7b753eb87f606ea2268ca536d429d47989dba196/broker/apply/apply.go#L591); [`broker/update/store.go:942`](https://github.com/ghbmrk/agentOS/blob/7b753eb87f606ea2268ca536d429d47989dba196/broker/update/store.go#L942); [`broker/change/effect.go:389`](https://github.com/ghbmrk/agentOS/blob/7b753eb87f606ea2268ca536d429d47989dba196/broker/change/effect.go#L389).

## Scope and intended change

`broker/apply/`, `broker/update/`, `broker/change/`, and their tests/ASSUMPTIONS.md; installed/staged/adoption settlement and recovery only.

Make settlement an explicit durable state machine. Each step must be idempotent for the exact release digest/root and adoption ID. Reconcile already-installed matching releases and already-confirmed adoptions; preserve a retry obligation on save failure. Apply the same design to fallback/StageFailed. Test every boundary between the three stores.

Do not expand authority or edit SPEC.md in this package. If the cited contract cannot decide a design choice, raise an L1 spec-diff proposal before implementation. Record changed assumptions in the affected package's ASSUMPTIONS.md.

## Acceptance tests

1. Inject a confirmation I/O error after CommitStaged has durably installed the matching release and consumed staged.json. Close/reopen the stores, retry Resume, and converge to confirmed adoption with Applying cleared and accurate STATUS.
2. Cut execution before and after every durable settlement step across the update store, pipeline and apply state, including installed-state saved while staged cleanup is incomplete. Repeated Resume must converge without reinstalling or rejecting an already-installed matching release.
3. Key idempotence by the exact release digest/root and adoption ID. Reject a different release or adoption with the same version, and preserve the retry obligation after save failures (including ConfirmStaged's in-memory state).
4. Exercise fallback/StageFailed at equivalent boundaries. After recovery, Tick must admit a subsequent valid update; no duplicate adoption or spurious success is permitted.

Write the regression first and retain it in the repository. Link requirement markers to named passing tests; a marker alone is not completion evidence. Run affected Go packages and race tests on Linux, repository checks, fresh strongest-model L3 with an explicit threat check, and the tier-A lens screen.
