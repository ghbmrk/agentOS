# S8-W1-volume: per-provider login volume, kept out of every copy

Board section: Release rows carried from LATER.md (2026-10-10). Source: work item #1015 (from the S8-W1a inventory, #543; `docs/security/provider-worker-isolation.md` row "Credential login volume"). Tier A (vm, credentials, vault). On G1's plan-login path (Mark chose "Plan login", 2026-10-13): third in the chain #808 → #807 → this → #1014 → CAP-11-plan (#1314) → #1264. No real login reaches it before S8-live (#809) and the CRED-5 qualification pass (see CAP-11-plan).

**Why.** CRED-5's worker-held mode keeps a provider's plan login on "a per-provider login volume mounted only into that provider's workers", the one exception to CRED-1. At current main nothing stores, checks or mounts such a login, and the worker plane (`broker/vm/worker.go`, `broker/workers`) has no notion of one: a worker's files live in its overlay, `Manager.Park` takes a Full snapshot (`broker/vm/worker.go`) that runs `runsc checkpoint` and saves memory (`broker/vm/gvisor/gvisor.go`), and the worker tools return file contents and process output.

**Requirements:** CRED-5 worker-held W2 (volume holds the login only; schema checked at every mount) and W9 (removing a plan deletes the login), CRED-1 and CRED-7 (the login never reaches journal, logs, recall or a guest-bound result), CRED-8 (at rest, the login is protected by the vault's key hierarchy), A14 ("the login volume is absent from every snapshot, the recall index, and the journal"; "a file or hook written by one worker is absent in the next"), ARC-1 (the worker-held exception stays under CRED-1's conditions).

**How the login reaches the CLI (one path, shared with #1014 and CAP-11-plan).** S8 measured that Claude Code takes `CLAUDE_CODE_OAUTH_TOKEN` from its environment and that a `claude setup-token` token lasts a year with no refresh (`spikes/S8/RESULT.md`). So the volume holds one token file, read-only. A root-owned launcher in the provider image (owned by #807) reads it, exports `CLAUDE_CODE_OAUTH_TOKEN` and execs the CLI; the launcher's and CLI's `/proc/<pid>/environ` is the W1 surface #807 closes. The CLI never writes the volume, so nothing on it is writable. The sign-in output of `setup-token` is #1264's path and never passes through worker `exec` output or the journal.

**Change.**
- **At rest.** The token is stored as a vault entry keyed by provider declaration ID, encrypted under the vault's key hierarchy (`broker/vault/keyslot.go`). There is no separate encrypted data area on the box, and the login never sits on the drive in plaintext. A locked vault means no plan route (refusal reason `vault-locked`).
- **Mount.** Only `vm.Manager.CreateWorker`, for a provider worker whose spec names that provider, attaches the login. The vault process (`broker/cmd/agentos-egress`, the only vault reader) decrypts it into a sealed memfd and passes the fd to agentosd, which binds it read-only into the worker as a memory-backed file without reading it. The memfd is closed when the worker is destroyed. This adds a vault-side unwrap call: the builder extends `broker/vault/imports_test.go`'s allow-list or the vault package doc only as far as that call needs, and records the change as a Security decision in DECISIONS.md. If Security rejects fd passing, the fallback is the vault process creating the mount itself; the package does not ship a plaintext-on-drive path.
- **Schema check at every mount.** The declaration (CAP-11-plan) names the token's shape (allowed charset and prefix, length cap). For Claude the builder measures the shape against a stub matching the pinned CLI's documented format and records it in `ASSUMPTIONS.md`, never from a real login. A value off the shape refuses the mount, journals the refusal by provider ID only (no content), and sets the plan's sign-in line once.
- **Never mounted or named** into the guest, a builder or replay machine, another provider's worker, or any worker made by `fork`. A worker with a login attached is a broker-owned provider worker: `Manager.Workers(lineage)` never lists it, and every worker tool (`exec`, `read`, `write`, `checkpoint`, `fork`, `diff`, `rollback`) refuses its ID (shared with CAP-11-plan, which builds the tool-side refusal; this package builds the `vm` side).
- **No memory snapshot.** A worker with a login attached never takes a memory checkpoint: `Park` stops and destroys it without a snapshot, and `checkpoint`, `fork` and `rollback` refuse it in `vm`. A provider run is one-shot (CAP-11-plan), so nothing needs to resume.
- **Settings, hooks, MCP configuration, memory and transcripts** never come from the volume (W2): the worker gets them from the image (#807) or per-worker scratch destroyed with the worker.
- **Removal.** Deleting a plan deletes the vault entry and returns the provider's revoke location for the owner line (W9). The owner line itself ships with #1264.
- **Out of every copy.** The recall indexer, journal writer and snapshot pruner never see the token, since it is never on the drive or in an overlay; a test proves each. BAK-1 has no code at main: record in `ASSUMPTIONS.md` that BAK-1's brief must exclude plan-login vault entries or prove they back up only as vault ciphertext.

**Tests first.** The login attaches only to its provider's worker; a second provider's worker, the guest, a builder machine and a forked worker see nothing. The schema check refuses an off-charset value, an oversize value and an empty one; the refusal journals no content. A write to the login path fails inside the worker. `Park` on a provider worker with a canary in the stub's env and heap leaves no checkpoint file and no canary on the drive; `checkpoint`, `fork` and `rollback` refuse it; `Workers(lineage)` omits it. A canary login stored for a provider is absent from the drive outside vault ciphertext, the journal, the recall index, every snapshot, and guest-bound tool output (`tools/canary.py` patterns). A locked vault refuses the mount with `vault-locked`. A file or hook written into scratch by one worker is absent in the next. Removing the plan leaves no vault entry and no canary anywhere on the drive.

**Revert mutants (each must turn a test red).** Skip the schema check. Mount the login into a forked worker. Let `Park` take a Full snapshot of a provider worker. List provider workers in `Workers(lineage)`. Write the decrypted token to a drive path instead of a memfd. Keep the vault entry on plan removal.

**Threats Security must check.**
- Provider terms: S8 read Anthropic's terms on 2026-10-05; they forbid developers to "collect, store, or intermediate Claude.ai credentials". Whether the box storing the owner's own token in its vault counts is part of the terms verdict CAP-11-plan's qualification record must carry. This package does not decide it.
- The fd hand-off: agentosd holds a handle to plaintext between receipt and bind; prove it never reads, logs or forwards it.
- gVisor's gofer or a checkpoint path reaching the memory-backed file.
- A token value crafted to be valid shape yet carry a settings or hook payload the CLI would load (W2: settings only from the image).
- Log lines or error strings that echo the value.
