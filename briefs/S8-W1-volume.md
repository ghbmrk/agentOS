# S8-W1-volume: per-provider login volume, kept out of every copy

Board section: Release rows carried from LATER.md (2026-10-10). Source: work item #1015 (from the S8-W1a inventory, #543; `docs/security/provider-worker-isolation.md` row "Credential login volume"). Tier A (vm, credentials, vault). On G1's plan-login path (Mark chose "Plan login", 2026-10-13): third in the chain #808 → #807 → this → #1014 → CAP-11-plan (#1314) → #1264. No real login reaches it before S8-live (#809) and the CRED-5 qualification pass (see CAP-11-plan).

**Why.** CRED-5's worker-held mode keeps a provider's plan login on "a per-provider login volume mounted only into that provider's workers", the one exception to CRED-1. At current main nothing stores, checks or mounts such a login, and the worker plane (`broker/vm/worker.go`, `broker/workers`) has no notion of one: a worker's files live in its overlay, `Manager.Park` takes a Full snapshot (`broker/vm/worker.go`) that runs `runsc checkpoint` and saves memory (`broker/vm/gvisor/gvisor.go`), and the worker tools return file contents and process output.

**Requirements:** CRED-5 worker-held W2 (volume holds the login only; schema checked at every mount, which here is every serve of the login socket) and W9 (removing a plan deletes the login), CRED-1 and CRED-7 (the login never reaches journal, logs, recall or a guest-bound result), CRED-8 (at rest, the login is protected by the vault's key hierarchy), A14 ("the login volume is absent from every snapshot, the recall index, and the journal"; "a file or hook written by one worker is absent in the next"), ARC-1 (the worker-held exception stays under CRED-1's conditions).

**How the login reaches the CLI (one path, shared with #1014 and CAP-11-plan).** S8 measured that Claude Code takes `CLAUDE_CODE_OAUTH_TOKEN` from its environment and that a `claude setup-token` token lasts a year with no refresh (`spikes/S8-provider-workers/RESULT.md`). So the login is one read-only token with nothing to write back. A root-owned launcher in the provider image (owned by #807) fetches it from the login socket below, exports `CLAUDE_CODE_OAUTH_TOKEN` and execs the CLI; the launcher's and CLI's `/proc/<pid>/environ` is the W1 surface #807 closes. CRED-5's "login volume mounted only into that provider's workers" is realized as that per-worker socket: nothing in the worker holds the login as a file, and nothing is writable. The sign-in output of `setup-token` is #1264's path and never passes through worker `exec` output or the journal.

**Change.**
- **At rest.** The token is stored as a vault entry keyed by provider declaration ID, encrypted under the vault's key hierarchy (`broker/vault/keyslot.go`). There is no separate encrypted data area on the box, and the login never sits on the drive in plaintext. A locked vault means no plan route (refusal reason `vault-locked`).
- **Decision: does agentosd hold a plaintext fd to the login?** agentosd serves the guest socket, and the process split (ARC-1, CRED-1) keeps vault plaintext in the vault process (`broker/cmd/agentos-egress`, the only vault reader). The decrypt itself needs no vault change: `Vault.Secret` already exists in a listed importer, so `broker/vault/imports_test.go` is not widened and no new vault importer is added. The open question is only whether agentosd may ever hold the decrypted token. This brief chooses (b) as the default and (a) as the fallback; the builder adds the row drafted below to DECISIONS.md with the build.
- **Default (b): the launcher fetches the token; agentosd's code is never in the path.** For a worker whose spec names a worker-held provider, `vm.Manager.CreateWorker` asks the vault process over the existing agentosd-to-vault channel (`verify.sock`, as PV1 uses; it admits only the broker's UID, egress K7) to open a per-worker unix socket, sending only the worker name and provider ID, never a secret. agentos-egress creates the socket in a directory no UID but root and its own can traverse, decrypts the token with `Vault.Secret` into its own memory, and serves it once: peer check, schema check, write the token, close and unlink. agentosd writes the bind of that socket path into that worker, as vm V15 already does for service sockets under `--host-uds=open`, at a path #807's sandbox hides from tool subprocesses. Each control gives one property, and none gives more:
  - **The path bind** decides which machine can reach the socket: it is bound into that one worker and no other machine, guest included. (The guest and every worker run under the same runsc argv, so this, not a UID, is what tells them apart, as daemon B8 identifies a guest by its socket.)
  - **Serve-once and unlink** bound what reaches it: at most one connection gets the token, and the socket is gone afterwards.
  - **`SO_PEERCRED`** admits only the sandbox-side UID the builder measures for a connection from inside a worker and refuses every other host process with a different UID. It does not tell the worker from the guest (they share one host UID: `writeBundle` sets 0:0 with no mapping), and if the measured UID is root (a connection made by the gofer) it does not exclude agentosd either. The builder records the measured UIDs at each end in `broker/egress/ASSUMPTIONS.md` and the host-UDS setting in `broker/vm/ASSUMPTIONS.md` (the mechanism #1014's tunnel socket reuses).
  - **agentosd out of the path** is a property of agentosd's code, not of its privilege: it never opens, reads or relays the token, and the import and canary tests below prove that. agentosd runs as root (agentosd ASSUMPTIONS L7-6) and stays in the trust base as a root-owned host process outside every model-directed process, which ARC-1 already allows. What (b) adds over (a) is that the plaintext never enters agentosd's memory or any agentosd code path.
- **Fallback (a), only if Security finds (b) cannot be built under gVisor: fd passing through agentosd.** The vault process decrypts into a sealed memfd and passes the fd to agentosd, which binds it read-only into the worker as a memory-backed file without reading it, and closes it when the worker is destroyed. Precedent: agentosd ASSUMPTIONS PV1, where agentosd already relays an owner's API key to the vault process as a call argument without keeping or logging it. (a) ships with a no-read test (a canary login passed as the fd is absent from agentosd's journal, logs and responses, and agentosd's code never calls `read` on the fd: a test wraps the fd in a type with no read method) and the mutant "let agentosd read the fd into a buffer". The package ships no plaintext-on-drive path under either option.
- **Drafted DECISIONS row** (the builder assigns the next free ID at merge; text for Security to accept or amend): `| D-NNN | <merge date> | active | Plan logins (CRED-5 worker-held) reach a provider worker without agentosd holding plaintext: the vault process (agentos-egress) decrypts the login with Vault.Secret into memory and serves it once over a per-worker unix socket bound into that worker only; agentosd writes the bind and its code never opens, reads or relays the token. The per-worker path bind decides which machine reaches the socket; serve-once and unlink bound what reaches it; SO_PEERCRED admits only the measured sandbox-side UID and does not tell a worker from the guest, nor exclude root agentosd if that UID is root. agentosd stays in the trust base as a root host process (ARC-1); keeping it out of the path is a property of its code, proven by an import test and canary absence. Fallback, only on a Security finding that this cannot be built under gVisor: a sealed memfd passed through agentosd, bound read-only and never read (precedent: agentosd PV1). Either way, no new vault importer and no plaintext on the drive | S8-W1-volume brief (briefs/S8-W1-volume.md) |`
- **Schema check at every serve.** The declaration (CAP-11-plan) names the token's shape (allowed charset and prefix, length cap). For Claude the builder measures the shape against a stub matching the pinned CLI's documented format and records it in `ASSUMPTIONS.md`, never from a real login. A value off the shape is not served: the socket closes, journals the refusal by provider ID only (no content), and sets the plan's sign-in line once.
- **Never served or named** to the guest, a builder or replay machine, another provider's worker, or any worker made by `fork`. A worker with a login attached is a broker-owned provider worker: `Manager.Workers(lineage)` never lists it, and every worker tool refuses it. The 13 tools in `broker/workers` are `worker_create`, `worker_exec`, `worker_read_file`, `worker_write_file`, `worker_checkpoint`, `worker_fork`, `worker_diff`, `worker_rollback`, `worker_destroy`, `worker_list`, `worker_fit`, `worker_keep` and `worker_delete`: each one that takes a worker name refuses a provider worker's name, `worker_list` omits it, `worker_keep` never destroys or keeps one, and `worker_create` refuses a spec naming a worker-held provider (shared with CAP-11-plan, which builds the tool-side refusal; this package builds the `vm` side).
- **No memory snapshot.** A worker with a login attached never takes a memory checkpoint: `Park` stops and destroys it without a snapshot, and `checkpoint`, `fork` and `rollback` refuse it in `vm`. A provider run is one-shot (CAP-11-plan), so nothing needs to resume.
- **Settings, hooks, MCP configuration, memory and transcripts** never come from the volume (W2): the worker gets them from the image (#807) or per-worker scratch destroyed with the worker.
- **Removal.** Deleting a plan deletes the vault entry and returns the provider's revoke location for the owner line (W9). The owner line itself ships with #1264.
- **Out of every copy.** The recall indexer, journal writer and snapshot pruner never see the token, since it is never on the drive or in an overlay; a test proves each. BAK-1 has no code at main: record in `ASSUMPTIONS.md` that BAK-1's brief must exclude plan-login vault entries or prove they back up only as vault ciphertext.

**Tests first.** The login socket exists only in its provider's worker; a second provider's worker, the guest, a builder machine and a forked worker see nothing. agentosd's code never opens or reads the token: `broker/cmd/agentosd` links no package that dials the login socket (an import test), and with a canary login, an end-to-end worker create leaves no canary in agentosd's journal, logs, responses or core dump. A connection from a host process whose UID differs from the measured sandbox-side UID is refused before a byte is written. Only if the builder measures agentosd's UID to differ from the sandbox-side UID does a further test show a connection from agentosd's UID refused; otherwise that test is not written and the two code-path tests stand alone, and `broker/egress/ASSUMPTIONS.md` says which case holds. The socket serves once and is gone afterwards. The schema check refuses an off-charset value, an oversize value and an empty one; the refusal journals no content. Nothing in the worker's overlay or scratch holds the token after the launcher starts. `Park` on a provider worker with a canary in the stub's env and heap leaves no checkpoint file and no canary on the drive; `checkpoint`, `fork` and `rollback` refuse it; `Workers(lineage)` omits it. A canary login stored for a provider is absent from the drive outside vault ciphertext, the journal, the recall index, every snapshot, and guest-bound tool output (`tools/canary.py` patterns). A locked vault refuses the serve with `vault-locked`. A file or hook written into scratch by one worker is absent in the next. Removing the plan leaves no vault entry and no canary anywhere on the drive.

**Revert mutants (each must turn a test red).** Skip the schema check. Serve the login to a forked worker. Drop the `SO_PEERCRED` check (the other-UID refusal test goes red); only where the measured UIDs differ, also accept agentosd's UID (the agentosd-UID test goes red). Make agentosd dial the login socket (the import test goes red). Route the token through agentosd's channel instead of the socket (the canary-absence test goes red). Bind the socket into a second worker or the guest. Serve the token twice. Let `Park` take a Full snapshot of a provider worker. Let `worker_checkpoint` accept a provider worker. Let `worker_fork` accept a provider worker. Let `worker_rollback` accept a provider worker. List provider workers in `Workers(lineage)`. Write the decrypted token to a drive path instead of memory. Keep the vault entry on plan removal.

**Threats Security must check.**
- Provider terms: S8 read Anthropic's terms on 2026-10-05; they forbid developers to "collect, store, or intermediate Claude.ai credentials". Whether the box storing the owner's own token in its vault counts is part of the terms verdict CAP-11-plan's qualification record must carry. This package does not decide it.
- The agentosd decision above, matching the drafted row: under (b), agentosd is root and can reach the socket's directory, so check the claims per control: the bind puts the socket in that one worker and never in the guest or another machine; serve-once and unlink leave nothing for a second connection; `SO_PEERCRED` refuses other host UIDs and, as measured, does or does not exclude agentosd (it never tells the worker from the guest); and agentosd's code never opens, reads or relays the token (import test, canary absence). Under the fallback (a), prove agentosd never reads, logs or forwards the fd.
- The login socket's one-shot serve racing a second connection from inside the same worker before the launcher connects (#807's sandbox must hide the path from tools; the serve-once rule bounds the rest).
- gVisor's gofer or a checkpoint path reaching the memory-backed file.
- A token value crafted to be valid shape yet carry a settings or hook payload the CLI would load (W2: settings only from the image).
- Log lines or error strings that echo the value.
