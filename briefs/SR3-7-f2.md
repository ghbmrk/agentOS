# SR3-7-f2: size the cross-process pre-hold to the owner's route count

Release finding from the L3 review of #582 (SR3-7-f1), point 2 ([comment](https://github.com/ghbmrk/agentOS/pull/582#issuecomment-6079101491)). The same issue was raised as Security later 2 on #582 ([comment](https://github.com/ghbmrk/agentOS/pull/582#issuecomment-6079083139)), and the L3 delta (comment 6080072619) filed it as BOARD row SR3-7-f2. Anchors: OP-8, ARC-7, A4, and route `ASSUMPTIONS.md` R-SR3-7-f1.

**What happens on main (a67d6eb).**
- `modelroute.Rewrite` (`broker/modelroute/modelroute.go:186-193`) takes up to `MaxRetries` (3, line 105) extra holds before it forwards a call: `for n < MaxRetries && meter.Another(ctx) { n++ }`. It then sends the count as `Agentos-Attempts`.
- Each `meter.Another` (`broker/meter/usage.go:127`) holds the full `in+reserve` through `hold` (`broker/meter/meter.go:418-441`). That hold counts against the machine, task, share and overall caps until the call settles. A call that is served first time therefore holds 4×(in+reserve) for its whole life.
- The vault cannot use more extra attempts than it has spare routes. `route.failover` moves at most `len(rule[class])-1` times. Egress only clamps the header to `[0, MaxRetries]` (`callAudit.serve`, the `left > modelroute.MaxRetries` check, `broker/cmd/agentos-egress/server.go:251` at a67d6eb). Today's rules have two routes per class, so at most one of the three holds is ever spent.
- Near a cap, the unspendable holds can make a concurrent `Start` return `ErrExhausted` (`meter.go:418-441` → `admitShares`/`check`). The L3 finding notes that this can also send a spurious owner exhaustion notice from the refused caller.

**Decision taken here: size the holds, don't take them lazily.** Security later 2 on #582 explains why the holds are eager. Taking them before the call lets the cross-process bound be checked before anything is spent. A vault→broker callback per attempt would cost a round trip and add attack surface. So the fix keeps eager holds and stops taking holds that can never be spent.

**Requirements** (local IDs):

- **SR3-7-f2a (bound from the owner's rule):** `Rewrite` takes at most `min(MaxRetries, R)` extra holds. R is the largest `len(routes)-1` over the classes in the owner's base rule (`RoutingState.Owner`, `broker/modelroute/routing.go:30-34`).
  - Use the owner's rule, not the active rule. An adoption may only reorder the base routes (`reorders`, `broker/cmd/agentos-egress/routing.go:94`; `checkBase` lines 75-90), so the route count per class is fixed by the owner's `-rule` (`main.go:303`). The owner can edit the rule at runtime, and Loop 1 projects a learned order onto the new rule (W3-route-a: `project`/`projected` in `broker/cmd/agentosd/learn.go`).
  - The class is not known at `Rewrite` time: it is in the body, and the vault resolves it (`broker/route/route.go:524`). So the bound is the maximum over all classes, not per call.
  - The header carries the number actually held, as it does today.
- **SR3-7-f2b (unknown means today's behaviour):** if the count can't be read (nil source, an error, or a timeout), `Rewrite` uses `MaxRetries`. Holding too few holds only costs failover and never adds unmetered spend, because egress meters each attempt against the header. Holding too many is today's behaviour, so this fallback only ever moves the code toward main.
- **SR3-7-f2c (cheap and current):** the route count is cached by the broker process. It is refreshed when the owner's rule changes, or at most once per short interval. It is never read per call over the routing socket on the hot path.
  - Suggested shape: `modelroute.Config.Retries func() int`, wired in `agentosd` from the router it already holds (`routerOf(...).state()`, `learn.go:1175`). The builder may pick another shape that meets f2a-f2c.
  - Every `Config` built today (`broker/cmd/agentosd/main.go:1100` Forward, `learn.go:748` Evaluation, `build.go:112` builder Forward) gets the source, or deliberately keeps nil with a one-line comment.
- **SR3-7-f2d (record):** R-SR3-7-f1 states the sized bound: holds = min(MaxRetries, max over classes of routes−1), with unknown falling back to MaxRetries.

**Threat check for the reviewer.**
- Can a lower bound let an attempt run unmetered? Trace it: egress meters only `allowed` attempts, and `failed := make(..., min(allowed, MaxRetries))` (`modelroute.go:327`). An attempt beyond the header must be refused or uncharged-and-unsent, never sent free.
- Can anything outside the owner set R high or low? R comes from the owner's base rule, which has the owner's trust. A guest, task or adoption must not be able to change it. An adoption only reorders routes.
- Does the cached source block or race the proxy path? A stale value is either over (today's behaviour) or under (failover is lost for one refresh window). State in R-SR3-7-f1 which one the cache can produce.

**Out of scope.**
- Lazy or per-attempt holds (rejected above).
- A per-class bound, which needs the class at `Rewrite` time.
- Changing `MaxRetries`, egress's clamp, or `route.failover`.
- An upper bound on routes per class in `route.SetRule` (`broker/route/route.go:237`). That would go in a later row, if wanted.
