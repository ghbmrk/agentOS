# UX4-4: Make boot-to-page help truthful and compatibility reachable

**Owner:** primary coordinator routes to the existing package owner; unclaimed advisory proposal.
**Class:** release, P2. **Requirements / gates:** ONB-1, ONB-4, ONB-5, ONB-7, CH-7, HW-3, HW-8; A1/A6.
**Needs:** card/P2-1, S1, P2-2w c4; localui assumption L8 owner-facing compatibility; HOST-1c.
**Review:** [Onboarding UX](../reviews/ux/2026-10-08-onboarding-review.md#ux4-4--before-the-page-opens-the-owner-has-too-little-diagnostic-guidance), fixed source `e19274c36f7c2d81ad72d01b796aaa1eb36ba549`. Existing UX3 items remain in [PR #405](https://github.com/ghbmrk/agentOS/pull/405).

## Evidence and owner effect

Card render.go and the owners guide say absent box Wi-Fi means failure to boot the drive. The same symptom can arise after boot. There is no visible-SSID/join-failure branch. APConfig defaults to SAE-only and exposes a WPA2 compatibility opt-in; its owner-facing route is deferred. A phone that cannot join cannot enable it from a page reached over that network. These are source/acceptance gaps, not measured hardware failures.

## Bounded scope

Card/guide/help wording and the existing hardware qualification checklist. Freeze the first-release supported PC/phone/network contract with its owner. Any compatibility-policy change or new pre-join control needs a separate L1-approved package before implementation.

## Acceptance

1. Give bounded, observation-led help for no SSID; SSID visible but join fails; joined but page absent; page present but uplink unavailable. Every action names what the owner can observe, with a stop/escalation point and no claim that one symptom identifies one cause.
2. Qualify at least the required A1 PC vendors/floor and the supported iOS/Android paths. If WPA2-only support is retained, prove a deliberate authorized pre-join opt-in with that phone; otherwise disclose the supported-phone minimum before the kit is used.
3. Keep WPA3 default and client isolation. Nearby unauthenticated clients cannot downgrade the box; no automatic compatibility fallback. Do not disable Secure Boot, mount internal disks, or prescribe permanent firmware changes as ordinary onboarding.
4. Report no-monitor/no-keyboard success separately from one-time boot-menu recovery requiring a display/keyboard. S1 read-verify/rollback and power-off signals are not evidence of joinable AP, phone-only completion or A1 pass.
5. Print the unchanged or revised Owner Card on supported paper/settings and physically scan its Wi-Fi/passphrase QR routes on supported phones. Inspect sheet count, intact codes, legibility and detachable recovery storage; source marker counts are not print acceptance.
6. Use public fixture secrets only in captured evidence; pair hardware symptom results with tested corrective instructions. Extend HOST-1c/HW-8 disclosures rather than rewording away actual firmware impact.

## Potency, security and delivery

Reduces dead ends before the wizard exists. It adds qualified help, not an insecure universal fallback. Any narrower support promise or compatibility tradeoff is an L1 decision; card/runtime modifications are tier A.

Implementation must be claimed in the owning lane before coding. Intake does not close this item. Estimate/checkpoint: 20k tokens for the first scoped slice; split protocol, hardware and integration work before implementation if needed. Record progress at the checkpoint rather than treating it as a spending ceiling.
