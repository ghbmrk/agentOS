## Goal

A hang finding closes only on evidence that the fuzz child cannot forge, and a hang that starts after the step has made progress is still a finding.

## IDs

LOOP-9 (a finding closes only on evidence), LOOP-7. Tests carry `REQ: LOOP-7, LOOP-9`.

## Sources

- BOARD P3-4b-3h-r2: #586 L3 point 2 (comment 6080168120 lists it as a release point) and loop7 F13's own "If it changes". Today `closeHangs` reads the producing binary's digest from `<Dir>/hang.json`. Since #588, `<Dir>` belongs to `agentos-fuzz`, so a fuzz child running injected code can rewrite the record and pick which digest a later step is compared against. `Resolve`'s PASS lines and a good step's progress lines are also the child's own output (loops S32, loop7 F3, F13).
- BOARD P3-4b-3h-r1 (#586 records): the stall rule (F12) reads only the last exec count against the baseline. A worker that hangs after the count has passed the baseline ends in a clean step.
- loop7 F12 says "Only the last count is read: the coordinator prints it on stderr as it stops, after its workers". `run` returns `CombinedOutput()`, so a line the target writes can follow the coordinator's last line. `progressOf`'s regexes are line-anchored and the last match wins. The record overstates what the parse guarantees.

## Requirements (each with a failing test first)

1. **loops holds the producing binary** (3h-r2). Move the producer digest out of the child's tree and into loops' own state, on the open record:
   - A fuzz hang finding is reported with the producing binary's SHA-256. Suggested shape: a `Producer string` field on `loops.Finding`, set only for `CheckFuzz` with a hang detail, and saved on the record. Re-reporting an open hang finding replaces the producer with the newer one; this keeps F13's "a hang seen again records the newer binary".
   - `CloseTarget` compares `c.Binary` against the record's producer. It no longer trusts a `Closure.Produced` from its caller: drop that field, or ignore it and save the record's value in its place. It refuses a close when the record has no producer or when the digests are equal.
   - Remove `hang.json`: drop `readHangs`, `writeHangs` and `hangFile` from loop7. `hang` computes the digest and reports. `closeHangs` passes only the step's own digest and counts.
   - Tests:
     - a hang reported from binary A, then a good step of binary A, stays open (pins today's rule);
     - after the step's child wrote a file named `hang.json` claiming producer B, a good step of A still closes nothing (fails on main, where a forged record of B lets A close it);
     - a good step of binary B closes it, and the saved closure names A as the producer;
     - re-reporting from B, then a good step of B, closes nothing;
     - after a restart (`reopen`), the producer survives;
     - `CloseTarget` with a record that has no producer is refused;
     - no file named `hang.json` is read or written by loop7 (grep test, or a planted file left byte-identical).
2. **Existing state.** No box runs LOOP-7 yet: box row P3-4b-4c is queued and the image's fuzz release first shipped with #560. So there is no migration. A hang record that is open in a dev state with no producer stays open until it is reported again; STATUS shows it as it does today. Say this in F13. loop7 deletes no stale `hang.json`: the file is the user's and harmless once nothing reads it.
3. **A hang after progress is a stall** (3h-r1). Extend `progressOf` to keep the last two `execs` lines with their `elapsed` values. A step that exits 0 is a stall when:
   - its last two exec lines show the same count, and
   - they are at least one progress period apart. The engine prints every 3 s; use the elapsed fields, not wall time.

   The condition holds whatever the count is relative to the baseline. Keep today's rule (count never past the baseline) as well. A step with fewer than two exec lines is judged by today's rule only.

   Write down why a flat 3 s with one worker means one input ran at least 3 s. Decoders under fuzz run in microseconds, so that is a hang and not a slow input. Record it in F12.

   Tests:
   - fake Go-shaped output whose count rises, then stays flat across the last two lines 3 s apart, with exit 0: reported with `FuzzStallDetail` (fails on main);
   - the same with the last two lines under one period apart: not a stall;
   - a rising count: a good step.
   - One real-toolchain test: a planted test-only target under `broker/loop7/testdata/` hangs on the N-th call in its worker process (a package-level counter, so it hangs only after the count has moved). Run it through the runner with a short `FuzzTime`: it is reported. Gate it as P3-4b-3r-fuzz gated its planted hang (`-short`, soak) if it runs past 60 s on CI.
4. **The records say what the parse guarantees** (#586 L3 point 2). Correct F12: the progress lines come from the child's combined output, the regexes are line-anchored and the last match wins, so a target that prints a line shaped like the engine's can move the parse. Then state what that buys a hostile child:
   - a forged stall only raises a finding, which is a false open, never a false close;
   - a forged good step closes a hang finding only on a release binary other than the producer, and loops now holds that producer (requirement 1);
   - so a forged close needs a new signed release whose own target the input still compromises.

   Rewrite F13 accordingly: the producer is in loops' state, and `hang.json` is gone. Also update loops S30 and S32: `CloseTarget` takes its producer from its own record, and it still trusts its in-process caller for the step's counts. Do not split stdout from stderr in `run`; confine-r5 owns `run`'s output handling, and a split would not stop a worker that writes stderr.

## Threat check

- A fuzz child rewriting the record to choose its own comparison digest (requirement 1).
- A child forging progress lines (requirement 4 states the residual; requirement 1 keeps a forged close to a new release binary).
- A late hang ending in a clean step (requirement 3).
- A restart losing the producer and so leaving a finding no step can close (requirement 1's restart test).
- A false stall from a slow but honest input (requirement 3 needs a full flat period; the real-toolchain control).
