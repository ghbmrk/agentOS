# P2-2w c4e3 l1: a test drives the setup key check to its deadline

Work item #1362 (later; tier A). Source: L3 L1 on PR #1343 (https://github.com/ghbmrk/agentOS/pull/1343#issuecomment-6154220793). Without it, the setup key check's timeout is asserted only as a deadline bound on the request context, so a check that ignored its deadline, or a store after a timed-out check, would pass every test.

**Requirements:**
- CRED-5: a provider key entered at setup is stored only after the provider accepts it; a check that runs out of time stores nothing.

**Acceptance tests:** CRED-5: `TestSetupKeyCheckTimesOut` (new, `broker/cmd/agentos-egress/providers_test.go`); `TestSetupKeyIsCheckedWithItsProvider` still passes with the default wait.

**Implementation risk:** tier A. **Needs:** P2-2w c4e3 (merged, #1343).

## Scope (files)

- `broker/cmd/agentos-egress/providers.go`
- `broker/cmd/agentos-egress/providers_test.go`

## What to build

1. The key check's wait becomes injectable. The issue proposes a custody field, but the `custody` struct lives in `custody.go`, outside this scope; a package variable `setupKeyCheckWait` in `providers.go`, defaulting to `modelroute.SetupKeyCheckWait`, follows the package's existing test-hook pattern (`reanchorCrash`). The package's tests do not run in parallel.
2. A test sets the wait to 50 ms and a key-check RoundTripper that blocks until its request's context is done, then posts a key: the answer is 502, the vault holds no key for the provider, the answer carries no key, and the call returns within a bound well under the default wait.

## Out of scope

Changing the default wait or the error mapping.

## Estimate

About 30k tokens. The figure is a checkpoint, not a cap (docs/OPERATING.md §5).
