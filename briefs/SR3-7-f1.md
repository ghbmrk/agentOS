# SR3-7-f1: meter every upstream attempt, not only the served one

Release finding from Security 4a on #429 (SR3-7), point 1 ([note](../reviews/security/2026-10-08-pr429.md)), filed as BOARD row SR3-7-f1. `route.failover` (`broker/route/route.go`, `failover()`) moves to the next route on 429, 401, 500, 502, 503, 504 and 529. Only the served route's usage reaches the meter: through `WithUsage` in `Routed`, or through the `HeaderUsage` trailer that `agentos-egress` writes (`callAudit.usage`, served attempt only) and modelroute reads. If a provider bills a failed attempt, one call can spend several times its reservation while the meter charges one. Anchors: OP-8, ARC-7, A4.

## Step 0: provider documentation (done when the brief was written; the builder re-checks)

The question is whether a 5xx or overload response is billed. Neither provider's primary error documentation says so either way:
- **Anthropic.** [Claude API errors](https://platform.claude.com/docs/en/api/errors), read 2026-10-09, lists 500 `api_error`, 504 `timeout_error` and 529 `overloaded_error`, and advises retrying with backoff. It says nothing about billing for them. It also says that over SSE "an error can occur after the API returns a 200 response", so a stream can fail after output was generated. docs.anthropic.com is blocked by this environment's egress proxy; the platform.claude.com copy was reachable.
- **OpenAI.** [Error codes](https://developers.openai.com/api/docs/guides/error-codes), read 2026-10-09, describes 500 as "The server had an error while processing your request" and 503 as "Model temporarily overloaded". Neither entry mentions billing.
- Community threads are not primary sources and report both outcomes. One example is [openai community: billed for failed requests](https://community.openai.com/t/openai-keeps-billing-me-for-failed-requests/1027696). They settle nothing.
- No live call was made. Measuring this needs real keys and a provider failure on demand, and that is out of scope here.

**Decision (safe default):** since billing is undocumented, **meter every attempt**. Charge each failed attempt as the existing modelroute rule charges a call that may have reached a provider (`meter.Usage.Unanswered`: the call's full output reservation). There is one exception, below. The builder re-reads both pages at build time and records the date and result in `broker/route/ASSUMPTIONS.md`. If either page now states that failed requests are not billed, the builder may narrow the charge for that provider only, citing the page. Any narrowing is the reviewer's call, not the builder's.

## Requirements (local IDs)

- **SR3-7-f1a (charge failed attempts):**
  - Every upstream attempt that the router sent to a provider and then failed over from is charged by the meter.
  - **401 and 429** are rejected at admission and produce no output, so they charge input only: the call's input estimate.
  - **500, 502, 503, 504 and 529**, a transport error after the request was sent, and a stream error after headers, charge input plus the full output reservation. If the error body carries provider usage, charge that instead, but never less than the input estimate.
  - A failed attempt's partial-stream `OutputChars` count as they do for a served call (R14).
- **SR3-7-f1b (bound before spending):**
  - Before each attempt after the first, the router asks whether the call's reservation covers one more attempt at the SR3-7-f1a charge for the worst status. If not, it stops failing over and answers with the last provider status, plus `Retry-After` as today.
  - **In-process path (`Routed`):** use a context hook beside `WithUsage`; the meter extends the call's reservation, or refuses at the limit.
  - **Cross-process path (agentosd → modelroute → `agentos-egress`):** modelroute sends the attempt allowance in one of its own request headers, the way it sets `HeaderMachine`. That header is stripped from guest input, as `dropOurs` does today. A request with no allowance gets exactly one attempt (fail closed).
- **SR3-7-f1c (carry the count):**
  - Extend `route.Usage`, `modelroute.Usage` and `meter.Usage` with the failed attempts and their class: input-only count, full-reservation count, and any reported usage.
  - The trailer carries them even when no route served the call. Today `callAudit.usage` returns `""` when nothing was served, and the meter then sees only the guest-facing response.
  - `meter.Report` keeps one slot. The served usage and the failed attempts arrive in one value, so a second `Report` cannot overwrite the first.
- **SR3-7-f1d (record):** update `broker/route/ASSUMPTIONS.md`:
  - R14: failed attempts are charged.
  - R-SR3-7, or a new row: Step 0's sources and dates, the default, and that it is provider-dependent and unmeasured.
  - The `Routed` comment in `guest.go`.

## Controls that must keep passing

- `broker/route` tests: failover on every status listed, `Retry-After`, `CredentialRejected` once a day, and R-SR3-7's one reading.
- `broker/meter` tests for `NoResponse`, `Unanswered`, cache weights and `n`.
- modelroute's trailer scrubbing.
- A call that is served first time is charged exactly as on main.

## Threat check for the reviewer

- Can a guest raise its own attempt allowance? Check for a guest-supplied header surviving `dropOurs`, or a body field.
- Can any failed attempt go uncharged? Check a transport error, a stream cut after headers, and a provider status not in `failover()` that is still retried.
- Is the bound checked *before* the attempt is sent?
- Does a missing or unreadable trailer fall back to charging the full reservation (modelroute's `Unanswered` rule)?
