# SR3-4f-3: A staged image that fails a Recheck security evaluation does not boot, and the owner hears of it (SR3-4-f1)

A release finding from L3 on #434 (SR3-4, merged 0a2ca0d), filed as SR3-4-f1. Security 4a agreed with the class and added the silent-failure half ([note](../reviews/security/2026-10-08-pr434.md), "L3's points, rechecked"); UX on #434 raised the same half as point 2. SPEC rows: UPD-1, UPD-8 (a release that fails a security evaluation is not run), OP-5, CH-12; acceptance A7 and A14.

**Why one package.** It is one change to the handover window that SR3-4f-2 leaves refused: `Withdraw` answers `ErrApplying` from the pre-Install save until `Resume` settles. This package lets a Recheck security failure withdraw an image that is installed but not yet restarted into, and makes a refusal visible as a `Concern`. About 150 lines of code and tests. No split.

**Order.** Build after SR3-4f-2 merges; it extends that package's `Withdraw` and reuses its `StageDropped` settle. W5b does not need to wait for it: the boot it stops is a narrow window, and the risk exists today. Line references are from main at 99fa0fa; reread them after SR3-4f-2.

**Today.** `Recheck` (effect.go:558) sets `Concern` only for `protected` adoptions. For an unprotected one it calls `revert(..., WhySecurity)`. On a `Staged` adoption `unsettled` refuses that revert, and the error only joins Recheck's error list, so the image boots at the next restart and the owner is told nothing. After SR3-4f-2, the refusal is limited to the handover window, but within it the result is the same.

**Requirements** (local IDs under UPD-1, UPD-8, CH-12):
- **SR3-4f-3a, withdraw after Install, before restart.**
  - `Withdraw` takes the reason (for example `Withdraw(adoption, why string)`). For `why == WhySecurity`, when `Applying` names the adoption with `Installed` set, in the boot it was handed over in (`Booted().ID == pt.BootID`), and not `executing`, the applier withdraws the install: under `a.mu`, `Activator.Abandon`, then `Store.DropStaged`, then save `Applying = nil` with `Last` `doneNotHanded`. No fallback is recorded. It returns nil, and the pipeline's revert proceeds.
  - Every other case in the window keeps `ErrApplying`: while executing, before `Installed` is saved, and after a new boot (`Resume` decides). Recheck runs again on its next pass, so a refusal while executing is retried, not lost.
  - If `Abandon` or `DropStaged` fails, nothing is cleared and `ErrApplying` is returned with the cause wrapped. `restartIfHandedOver` must not restart into an adoption that a security withdraw has started on. Keep a durable flag on the point (for example `Withdrawing`) that `restartIfHandedOver` honours and the next `Withdraw` or `Tick` completes.
  - Owner UNDO and regression reverts keep the refusal in this window. Only a security failure justifies abandoning an install the box would otherwise start; record the reason in apply ASSUMPTIONS.
- **SR3-4f-3b, a refused revert is visible.** When Recheck's revert of an unprotected adoption is refused by the handover window (`ErrApplying` from `Withdraw`), set `Concern` (`why`, score) as for a protected adoption, and save. The digest and STATUS say what is true and what happens next, for example: "Update N failed a security check while it was being installed; it will be undone as soon as it starts." The words follow CH-12, are decided by the builder, and are pinned by a test. The `Concern` clears when the adoption is reverted.

**Threat check for the reviewer.**
- A withdraw may run only in the same boot as the install and only before any restart into it. After a new boot, only `Resume` decides. Trace every route to `Activator.Restart`, including one racing `Withdraw` across `a.mu` releases in `restartIfHandedOver`.
- A failed `Abandon` must leave the image unable to start through this applier, never reverted-but-bootable.
- No security failure is silent: either the image is withdrawn, or a `Concern` is saved and shown.
- No wedge: a withdraw left half-done is completed by the next `Tick` or `Withdraw`.
