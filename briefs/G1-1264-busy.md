# G1-1264-busy: A started plan sign-in comes back, and refusals spend no code

Board section: G1 (#1945). Source: #1941 Security finding 1 and the PUX review of the plan sign-in page (#1887, #1888, #1941). Tier: A. Builder: strongest model. Usage estimate: 120k tokens.

**Why.** The owner starts the plan sign-in on the home page, then taps "I signed in" or leaves before approving the provider's code. Home offers the form again; a fresh code-generator code is spent, and the answer is a busy text that names a code the page no longer shows and gives no time. The per-minute bound on starts also spends a valid code before refusing. Not owner-reachable until the Codex gate opens (#809).

## Requirements

- **G1-1264-busy-1** (ONB-9, CRED-5) While a sign-in the page started still waits, agentosd keeps its link, code and issuer with the session that started it. That session's home page shows them again in place of the form, and a second start from it returns them without a code and without starting anything. Another session gets them only after a good code-generator code, which then binds them to that session. Nothing is kept once the sign-in stops waiting.
- **G1-1264-busy-2** (ONB-9, CH-10) A start that would be refused as busy (a sign-in waits whose code agentosd does not hold) or past the per-minute bound is refused before the owner's code is checked, so no code is spent on it.
- **G1-1264-busy-3** (CH-12) Every text the plan sign-in form can show names a step that works in that state: the busy text names when to try again, and that time is the sign-in's own wait; the limited text does not claim wrong codes when the bound was starts.
