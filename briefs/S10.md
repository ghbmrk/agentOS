# S10: Personal-agent protocols (PACT, PAP)

Board section: Phase 0: harness and risk spikes.

Can AgentOS take part in the emerging personal-agent-to-business protocols without breaking SPEC §2? Owner request 2026-10-08 in a coordinator session. Not release-critical: this would class `later` (LATER.md) and was started only on the owner's explicit request. Protocols in scope: **PACT** (Personal Agent Consent & Trust Protocol; Decagon; A2A 1.0 + OAuth device flow; spec at openpactprotocol.org, code at github.com/openpactprotocol/openpactprotocol) and the **Personal Agent Protocol** (Meta and Sierra with partners; sierra.ai/blog/introducing-personal-agent-protocol). Claims relayed to the coordinator are unverified until checked against primary sources.

**Decision boundary, answered first.** SPEC §2 forbids a project-run server, an AgentOS account, vendor activation, and a public domain or certificate; DEP-2 rules out any required project-run service; ID-2 rules out a developer key. Can one box act as its own agent platform (self-issued signing key, no platform registry, no domain-hosted JWKS) and still be accepted by a conforming business host? If conformance needs a registered platform identity, a project-run issuer, or a domain the box publishes, the result is "not adoptable as specified" plus what the protocol would have to change, and the package stops after the spike. The same question is answered for PAP if its spec is published; otherwise the result records that it isn't.

**Deliverables.** `spikes/S10-pact/` with `QUESTION.md` and `RESULT.md`: protocol summary with SPEC evidence labels, the decision-boundary answer, a threat model (token theft, confused deputy between businesses, scope escalation via the Agent Card, business-agent injection, receipt forgery, replay), and a mapping checked against SPEC v0.12 (CRED-1, CRED-7, ARC-1, ADP-1, ADP-2, ADP-10, REV-2, REV-5, CAP-3, §8.1 step 8, CH-19, §9, DEP-3), reusing broker/egress, vault, grants and verb rather than duplicating them. Only if adoptable: `SPEC-DIFF.md` for an L1 PR, a tier-C prototype against a local mock business host with threat tests (synthetic keys and canaries only), and follow-on brief `S10b` for the tier-A broker work, gated on Mark approving the spec diff.

**Needs:** reachability of the spec and code hosts (or work from what is reachable, recorded in the PR); strongest model (credential-custody design that tier-A code would rest on).
