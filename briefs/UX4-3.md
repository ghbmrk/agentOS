# UX4-3: Qualify stable browser context across phone app handoffs

**Owner:** primary coordinator routes to the existing package owner; unclaimed advisory proposal.
**Class:** release, P2. **Requirements / gates:** ONB-1, ONB-5, ONB-6, CH-7, CRED-8; A1/A14.
**Needs:** P2-2w c4; existing P2-2w c2 r1 closed-enrollment work. L1 before any new transfer semantics.
**Review:** [Onboarding UX](../reviews/ux/2026-10-08-onboarding-review.md#ux4-3--same-phone-actually-means-the-same-browser-context), fixed source `e19274c36f7c2d81ad72d01b796aaa1eb36ba549`. Existing UX3 items remain in [PR #405](https://github.com/ghbmrk/agentOS/pull/405).

## Evidence and owner effect

At the reviewed revision setup authority is cookie-bound. Replacing that cookie with the same RemoteAddr yields the elsewhere page and recovery-secret reset, correctly refusing ordinary resume. The page calls this another phone, although browser contexts may differ on one phone. The synthetic probe proves context binding, not current iOS/Android captive-portal behavior.

## Bounded scope

First qualify/document the supported AP/captive-portal/full-browser and Messages/authenticator return paths. Localui stage titles, return instructions and elsewhere copy may follow. A new context-transfer protocol is outside wording scope and must be split after L1/security design.

## Acceptance

1. On qualified iOS and Android versions, test AP join → setup → SMS → setup → authenticator → setup → provider → setup, including closed portal/window, app suspension and same-context reload. Record which transitions share the authorized context, not just which device was used.
2. If needed, establish the stable full browser before pairing, with a tested owner instruction that works without a second device. The return destination must be the actual local setup page; do not promise an OS handler without testing it.
3. Same-context return resumes permitted progress without replaying completed enrollment. Changed context is described as another browser session and remains unauthorized; existing recovery/reset is accurately identified as a consequential recovery operation.
4. If a new transfer is necessary, first record an L1 decision and threat model: prove both contexts/current generation, bound lifetime and use, revoke old authority atomically, resist replay, CSRF, nearby AP clients and stale pages, and define interrupted transfer. Preserve current enrollment/reset proofs; SMS alone, shared IP/AP membership or a URL cookie cannot authorize seed access.
5. Never re-show a previously disclosed enrollment seed just to make Back work, transfer a live session in a query string, weaken closed-enrollment checks, or use ordinary recovery reset as the default navigation repair.
6. Keep seed replacement and reset generation invalidation test coverage and rerun the relevant A14 boundaries. Physical-device results and synthetic session tests remain separate evidence.

## Potency, security and delivery

Restores continuity while retaining the browser authority boundary. Prefer reliable existing handoffs over a new transfer mechanism; any new mechanism adds attack surface and requires L1 plus tier-A security review.

Implementation must be claimed in the owning lane before coding. Intake does not close this item. Estimate/checkpoint: 20k tokens for the first scoped slice; split protocol, hardware and integration work before implementation if needed. Record progress at the checkpoint rather than treating it as a spending ceiling.
