# UX3-2: Repair home networking after pairing

**Class:** proposed release (P2); primary lane, unclaimed. This is a cross-lane advisory handoff, not adopted design or implementation authorization. Recheck current main and concurrent PRs before claiming work. **Requirements/acceptance:** ONB-4, ONB-8, CH-7, CH-12; A1. **Dependencies/overlap:** P2-2w c3/c4.

## Problem and evidence

Allow the authorized setup device to repair its home-network dependency without erasing completed setup.

Evidence and fixed-main source anchors: [deep UX review, UX3-2](../reviews/ux/2026-10-08-deep-ux-review.md); [synthetic probes and limits](../reviews/ux/evidence/2026-10-08/README.md). Runtime remedies remain open after this brief is registered.

## Intended scope

broker/localui/ and the existing setup network-helper interface; no general network administration. Coordinate with the existing package instead of building a competing flow. SPEC/DECISIONS are out of scope; any unresolved interaction or authority contract goes through an L1 spec-diff first. Record changed assumptions in the affected package.

## Acceptance evidence

1. After pairing and enrollment, disconnect or reject home Wi-Fi. The visible flow offers repair, invokes JoinNetwork, and returns to the retained unfinished step.
2. Try a wrong password followed by a correct one, network disappearance, helper failure and process restart. Report a bounded safe reason and working retry; no infinite generic wait.
3. Attempt repair from another AP client or after setup authorization is invalidated. Reject without changing network configuration or exposing prior secrets.
4. Keep the network helper restricted to the existing join operation, with no shell input, enrollment reset, uplink listening or new owner authority.

## Security and potency constraints

Repair must be narrowly scoped to the same authorized setup device. Post-setup networking changes belong behind existing owner authentication.
