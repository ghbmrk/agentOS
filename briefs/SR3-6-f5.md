# SR3-6-f5: an anchor error holds attestation authority, not the whole check

Board row: issue #783 (SR3-6-f5). Source: release findings from the #600 reviews (Security 4a, comment 6081396179, point 3; UX lens point 1; lens 6083249380 point 1). Class: release. Tier: A (`broker/update`, `broker/cmd`). Builder: strongest model. Usage estimate: 90k tokens, checkpoint at 70k. Needs SR3-6-f2 (merged). Sits before W5b: this row takes over W5b's anchor-error condition clause.

**What happens on main (eed5253).**
- `Store.check` (`broker/update/store.go:527`) returns at once when `noteAttestors` fails. `noteAttestors` reads the anchor (`outsideListed`, `policy`) and raises it (`recordOutside`), so a locked vault's 503, an "anchor missing" 409, a PC without the chip the vault recorded, or a slow TPM fails every `Check`, the owner's path included, though only attestation authority rests on the anchor (U16).
- A failed raise in `recordOutside` returns before `writeAllowList`, so the noted list is not written either.
- `anchorsock` turns every non-200 into one generic error, so nothing can tell the owner which step works.
- On a PC with no TPM whose vault recorded a counter (`custody.updateAnchorLocked`, `broker/cmd/agentos-egress/custody.go:853-857`) the vault sends `noteCounterReset`, which says the copy check "was reset" and to trust this PC again; the counter is intact and `trust` answers `errNoTPM`, so that step cannot work (CH-12).

## Requirements (local IDs)

- **SR3-6-f5a (the check continues, with no attestation authority).** When `noteAttestors` fails only because the anchor did not answer (a `Read` or `Raise` error other than `ErrNoAnchor`), `Check` continues: the noted allow-list is still written, the interim rule is off, the allowed and pinned sets are empty, and the release's policy value never matches, so `Security`, `InterimAttestation` and `IndependentPasses` give nothing and `Stage` refuses an attested release. A release is still returned for the owner's path. Any other `noteAttestors` error still fails the check. `NoteAttestors` still returns the anchor error.
- **SR3-6-f5b (the owner sees the step).** `Result.Held` is the owner's line for a held check, empty otherwise, and `AnchorHeldLine(err)` gives it for an anchor error. It names only a step that works: a locked vault, "unlock the box with your card"; a counter that is gone, "unlock with your card to trust this PC again"; a vault whose counter is on a chip this PC lacks, "restart the PC" then "move the drive back to the PC you set it up on"; any other anchor failure, "restart the PC". It never carries raw error text. `anchorsock` maps 503 to `ErrAnchorLocked` and the vault's 409 to `ErrAnchorMissing` or `ErrAnchorElsewhere`, which the vault's 409 names in an `Anchor-Answer` header.
- **SR3-6-f5c (the vault's notice on a PC without the chip).** In that case the vault sends `noteAnchorElsewhere` (the issue's exact text), not `noteCounterReset`, once, under its own flag cleared where `counterReset` is (re-trust), so it cannot suppress a later genuine counter-reset notice. A test in the style of `TestHeldOwnerTextsNameOnlyStepsThatWork` pins that it and the held lines name only steps that work, are GSM-7 and fit three segments.
- **SR3-6-f5d (record).** Update ASSUMPTIONS U16; replace W5b's anchor-error clause with the wiring line (Loop 3 shows `Result.Held` in `Status().Line`).
