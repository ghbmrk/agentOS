## Goal

The corpus replay probes the commitment filter by the only route a guest has to it: an ADP-11 auto-reply that the guest composes in a thread the owner pre-allowed. A weakened filter is caught there, not only in-process.

## Requirements (each with a failing test first)

1. **A `Relay` route for an auto-reply.**
   - Add a method to `corpus.Relay`. Suggested: `AutoReply(ctx, text) (queued bool, err error)`, which has the guest compose `text` as a reply in a pre-allowed, verified thread.
   - The result is what the broker did, never what the guest says:
     - queued as an auto-reply means the filter missed;
     - a normal approval request means it caught the text.
   - A refusal by the gate for any other reason is an error that fails the run, not a "caught". This follows S42 and S44: the guest's own answer is never a verdict.
2. **The rig earns and verifies, never bypasses.**
   - In the replay rig, set up the following:
     - a mail thread whose starter is verified: the owner's copy in the Sent folder, as `threadVerified` accepts;
     - an isolated machine, as `Config.Isolated` requires;
     - a granted rule with `Reply: true` for that account.
   - Grant the rule through the same owner-approval path `relay.grant` uses today. If grant validation or the gate needs the earned count from CAP-6, earn it in the rig through the attention path. Do not change production code to skip it.
   - If no route exists without a production change, stop at the checkpoint. Report that as a finding: a release row against the owner of the gate.
   - Add a guest stand-in mode that composes the reply over MCP, as `reply`, `mail.label` and `mail.archive` do today.
3. **`PlaneChecks` gains the commitment filter.**
   - Add an entry with `Name: CommitmentFilter`, `Payload: CommitmentPayload` and a `Deliver` through `AutoReply`, where caught means `!queued`.
   - `Checks` keeps its in-process copy as a second probe. Write down why both exist: the plane copy needs a machine and runsc, so the in-process copy covers boxes and runs without them.
   - Tests:
     - `plane_test.go`: the entry is present and maps the broker's verdict both ways;
     - the rig: the clean replay through a machine reports nothing for the filter;
     - a control with a weakened `Commitments`, matching nothing, reports a miss for the filter. This is required by 4d's control rule (S45) and fails on main, where the filter is not replayed.
   - The host copy of the replay runs the same entry.
4. **The probe leaves nothing queued to send.** A missed auto-reply in the rig is queued with ADP-11's undo window. The rig cancels it, or its owner stand-in never sends, and a test asserts nothing was sent on any account.
5. **Records.**
   - loops S43: rewrite it to say the filter is replayed through the plane, and why the in-process copy stays.
   - Note the rig's earned and verified setup in S44 or a new row.
   - LATER: any part of ADP-11 the rig does not reach, such as CH-10 contact starters, as one line each.

## Threat check

- A probe that reports "caught" because the gate refused for an unrelated reason: thread unverified, machine not isolated, rule missing (requirement 1 makes those errors).
- A rig that reaches the filter by bypassing the earned or verified gates, so the probe tests a route no guest has (requirement 2).
- A replayed commitment text actually sent from an account (requirement 4).
- A guest's own claim taken as the verdict (requirement 1).
