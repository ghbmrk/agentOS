**Today.** `Resume` (apply.go:662) settles by the booted root. On the old root with `pt.Installed` set, it takes `default`: `DropStaged`, then `Pipeline.StageFailed`, then `FellBack[v]`. If a previous `Resume` already ran `CommitRelease` and `ConfirmStaged` and only the applier's save was cut, `StageFailed` returns "not a staged adoption" (the adoption is `Confirmed`) on every call. `Applying` stays set, STATUS says "Update N is installing", and `Tick` refuses every later update. Separately, `Execute` saves `Applying` (pre-Install), calls `Activator.Install`, then saves `Installed=true`; when that last save fails it abandons and returns NotApplied (apply.go:579–590). If it keeps failing, each new attempt installs again, and a bad image that a reboot happens to boot between attempts is never recorded as fallen back.

**Requirements** (local IDs under UPD-1, UPD-1a, OP-5):
- **SR3-4f-1a (SR3-4-f2):** in `Resume`'s old-root branch, when `pt.Installed` is set and the update store's `Installed()` already names this exact release (`Version == pt.To` and the root hash and manifest digest of `refLocked(pt)`; U17), the apply is settled as installed, not fallen back:
  - Call `Pipeline.ConfirmStaged(pt.Adoption)` (idempotent; it converges the cut between `CommitRelease` and `ConfirmStaged`). Never call `StageFailed` or `DropStaged`, and never set `FellBack[v]`.
  - Clear `Applying` and record `Last` with a new kind (for example `doneInstalledOtherRoot`). STATUS and the digest say, in CH-12 words, what is true and what happens next: "Update N is installed, but the box started the previous version. It will start N at the next restart." Or, if the builder finds the loader will not pick N again, say so and that the next update installs normally. Pick the sentence from what `Activator` actually guarantees and record it in apply ASSUMPTIONS.
  - After it, `Tick` admits the next scheduled update.
  - A release the store does not hold as installed keeps today's fell-back path exactly (`TestFallbackRevertErrorConverges` and its siblings keep passing).
- **SR3-4f-1b (SR3-4-f5):** Install is attempted a bounded number of times per release without a recorded outcome.
  - The pre-Install save records an attempt count for the release's `Ref` (in `point` or a small map in `state`). That save already must succeed before `Install` runs; keep it so.
  - After an attempt whose `Installed` save failed, a boot on the old root is not evidence that the release ran, so it is never recorded as a fallback (OP-5: the journal records only rollbacks that happened). At the second unrecorded attempt for the same `Ref`, `Resume`/`Tick` does not install again. It records a distinct outcome instead:
    - `Activator.Abandon` and `Store.DropStaged` as in the not-handed path; no `StageFailed`, no `FellBack[v]`;
    - clear `Applying`, record `Last` with a new kind (for example `doneUnrecorded`), and keep the `Ref` in saved state as refused: `Schedule` returns a new `ErrRefused` (wrapping the `Ref`) for that exact `Ref`, and `Tick` installs nothing for it;
    - STATUS and the digest say, in CH-12 words: "Update N could not be recorded as installed, twice. It will not be retried automatically; retry it from the local page." The owner's entry point is a new `Applier.Retry(ref update.Ref) error`: it clears the refusal and the attempt count for that `Ref`, saved first, so the next `Schedule` of it is admitted. W5b's existing "a way for the owner to retry" condition (apply A7) is what calls it; name `Retry` in A7, so no W5b brief line is needed.
  - The adoption stays `Staged` here, and so does any later adoption that `Schedule` refuses with `ErrRefused`. Settling both is SR3-4f-2b's job (it adds them to its drop paths); this package does not touch `broker/change`.
  - Name the bound in a constant (2) and an ASSUMPTIONS row.
  - `Activator.Install` is called at most twice for one `Ref` with no recorded outcome. A successful `Installed` save resets the count.
- **SR3-4f-1c (L3 later B on #434):** a test pins `New()`'s `Pending = nil` (it is load-bearing: a pending release's `*update.Verified` is never persisted).

**Controls that must keep passing.** All of `settle_test.go` and `apply_test.go`, in particular `TestConfirmationErrorAfterCommitConverges`, `TestCommitCutBeforeStagedCleanupConverges`, `TestStateSaveFailureAfterConfirmKeepsTheObligation`, `TestDifferentReleaseWithTheSameVersionIsNotSettled` (an installed release with the same version but another root or manifest is not this apply: it stays a fallback), `TestFallbackRevertErrorConverges`, `TestHandoverSaveFailureIsNotSuccess`, `TestUnabandonedHandoverIsAbandonedByTheNextTick` and `TestUnrecordedHandoverThenPowerCutIsNotAFallback` (one unrecorded attempt is still not a fallback).

**Threat check for the reviewer.**
- SR3-4f-1a must match the exact `Ref` (version, root hash, manifest digest), never the version alone: a store that holds another build of v as installed is a fallback, and the image must not be marked good.
- It must never turn a real fallback into "installed": the only input is the update store's durable `installed.json`, which `CommitRelease` writes only after a blessed boot of that root (U17).
- SR3-4f-1b must not let a failing state store make the applier install forever, and must not record a fallback for a release that never ran. It records no fallback at all: the old root booting after an unrecorded `Install` proves nothing about the new image (L3 on #572, point 2).
- No path wedges: every new branch either saves and clears `Applying`, or returns an error that the next `Resume` retries to the same result.
