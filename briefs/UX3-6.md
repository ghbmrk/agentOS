## Problem and evidence

Make every item of an existing approval batch inspectable remotely without approving, splitting high-tier consent into repeated codes, or requiring travel to the box.

Evidence and fixed-main source anchors: [deep UX review, UX3-6](../reviews/ux/2026-10-08-deep-ux-review.md); [synthetic probes and limits](../reviews/ux/evidence/2026-10-08/README.md). Runtime remedies remain open after this brief is registered.

## Intended scope

broker/owner/ approval detail rendering/parser and existing grant batch projections; no new grant authority. Coordinate with the existing package instead of building a competing flow. SPEC/DECISIONS are out of scope; any unresolved interaction or authority contract goes through an L1 spec-diff first. Record changed assumptions in the affected package.

## Acceptance evidence

1. Exercise 1, 4, 10 and 20-item batches with long valid targets. Every item is reachable by deterministic read-only page/item selection within the SMS segment bound; repeated selection is stable.
2. Every response identifies request, item range and expiry plus valid replies. Bind inspection to existing fingerprints; changed, expired and reissued requests cannot reuse stale views.
3. Keep one fresh code per batch, tier separation, local-only restrictions, exact canonical recipients and OP-3 checks at effect commit. An agent summary cannot replace broker facts.
4. Test partial YES, denial, restart and interleaved batches. Keep current unselected-item denial behavior unless L1 separately changes it; measure whether owners correctly predict which items will run.

## Security and potency constraints

Preserves batching potency and approval strength. Distinct from SR3-3 grant-rule completeness and CH-20m redirected reply retrieval. No automatic approval after reading the last page.
