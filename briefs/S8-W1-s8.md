# S8-W1 s8: Codex plan-login traffic, refresh included, goes through the forwarder

Board section: Phase 0: harness and risk spikes. Issue: [#2085](https://github.com/ghbmrk/agentOS/issues/2085) (release finding from the #1504 PR).

The managed config sets no `chatgpt_base_url`, so a Codex CLI on a plan login calls chatgpt.com directly instead of the in-worker forwarder (#1014), and the turn fails before any tool runs. With that key pointed at the forwarder, a refresh in the middle of a turn still ends the turn with "application network policy is unavailable" (measured on 0.162.1 for #1504).

**Requirements:** CRED-5, A14.

**Scope:** `guest/codex/managed_config.toml`, `guest/codex/ASSUMPTIONS.md`, `tests/test_codex_worker.py`, `tests/codex_worker/fake_endpoint.py`. Not `guest/codex/build-rootfs.sh` (#1720), not `broker/egress` (#1749 owns the refresh route).

**Approach:** pin `chatgpt_base_url` to the forwarder in managed config, checked statically like every other pin and exercised under the real CLI. Then measure why the request retried after a mid-turn refresh fails and whether any config 0.162.1 reads fixes it. If none does, record in ASSUMPTIONS why, what bounds it (the turn lost, what auth.json holds afterwards, whether the next turn completes) and a test that turns red when a CLI bump changes it.

**Acceptance tests:** `tests/test_codex_worker.py` `ManagedConfigTest` (the `chatgpt_base_url` pin), `CliSandboxTest.test_a_stale_login_refreshes_at_startup_through_the_forwarder` and `CliSandboxTest.test_a_mid_turn_refresh_loses_that_turn_and_the_next_completes` (opt-in: they need `AGENTOS_CODEX_CLI`), and the #1504 tests without their config edit. ASSUMPTIONS cites them. doclint clean.

**Needs:** S8-W1 (#1419), #1749.
