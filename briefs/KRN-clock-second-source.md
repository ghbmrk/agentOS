# KRN-clock-second-source: the kernel reads chronyd as its second time source

Board section: Defects and later findings on surviving packages. Work item #5391 (release finding from #5387, KRN-clock-b); folds in #5195 (one writer of the TIM-1 guard's `clock.json`).

**Problem:** the kernel process's only time source is the box clock (`kernelmain.go` passes `kernel.At(time.Now())`). Its unit has no network and no modem, so nothing can disagree with the box clock, and a box clock set ahead before a start moves `Earliest` for good: a held send ends early (KEY-8). `proc.onLog` also starts `Earliest` at the source's `Latest`, so even a wide source at the start would leak the stepped clock (hand-back comment on #5391). And once the box clock is behind the log (a flat CMOS battery), `Earliest` stays at the log's time plus the monotonic clock all run, even after network time is known, so every hold waits the power-off gap.

**Requirements:** TIM-1, KEY-7, KEY-8. The kernel process reads chronyd's tracking report (`REQ_TRACKING`, command protocol 6) over chronyd's command socket, read-only in its sandbox. A synced report gives true time as box + correction, within root delay / 2 + root dispersion; the source's reading is the hull of that interval and the box clock, so a disagreement widens it (the guard's restricted mode). An unsynced chronyd, chronyd's own local reference, a malformed or late reply, or no socket gives no lower bound (Earliest 0) and the box clock as Latest. `onLog` starts `Earliest` at the later of the log's last time and the source's `Earliest`, or the box clock when the source gives none (no worse than today, so an offline box keeps working); it then runs on the monotonic clock and rises to the source's `Earliest` whenever that is later. So a box clock ahead at a start with chronyd synced ends no hold early, a step while running moves `Earliest` only as far as chronyd vouches, and a box behind the log catches up once chronyd syncs. The reply socket is connected to chronyd's, so the host kernel delivers it only chronyd's datagrams. The kernel process links no `broker/clock` and opens no `Guard`, so agentosd stays the only writer of `clock.json` (#5195).

**Scope:** `broker/kernel/proc` (`chrony.go` new, `kernel.go` `onLog`, `kernelmain.go`), `broker/cmd/agentos-kernel` (`main.go` flags, `main_test.go`), `image/mkosi/mkosi.extra/usr/lib/systemd/system/agentos-keeper-kernel.service` (the one new exit: `/run/chrony` read-only and optional, the two flags, ordered after `time-sync.target`) and its pinned line in `image/mkosi/mkosi.finalize` (`KERNEL_EXEC_TEXT`), the reply socket's allow lines in `broker/kernel/privfile/pathops_allow.txt`, their tests and ASSUMPTIONS.

**Acceptance tests:** `broker/kernel/proc/chrony_test.go`: `TestTIM1AStartAheadWithChronySyncedEndsNoHoldEarly` (the box clock two days fast at a kernel start, a fake chronyd synced and saying so: the logged reading spans the two days and a grant's day-long hold issued just before the start is still running; with the box clock alone the same start ends it), `TestTIM1AChronyReplyGivesNoLowerBoundUnlessSynced` (unsynced, stratum 0, local reference, wrong version, type, command, reply, status, sequence, length, absurd bound or correction; no socket; a mute chronyd waits once, then not for the retry), `TestTIM1AChronyReadsTheHullOfBothSources`, `TestTIM1AChronyFloat` (chrony 4.5's own encodings), `TestTIM1AOnlyChronydReachesTheReplySocket` (a forger gets EPERM). `broker/kernel/proc/anchor_test.go`: `TestTIM1AStartBehindTheLogCarriesItsTimeForward` (a lone box clock as before; a vouching source starts at its Earliest and Earliest rises to it, never back). `broker/cmd/agentos-kernel/main_test.go`: `TestChronyFlags`, `TestTheKernelProcessOpensNoClockGuard` (#5195).

**Out of scope:** installing and configuring chrony (HOST-1b, #954): the kernel's uid reaching chronyd's socket (chronyd makes it 0755 in its 0750 `/run/chrony`) and a wait for sync that `time-sync.target` orders after; until then the kernel reads the box clock as today. Carrier time from a modem keeper (none exists on the capability-kernel design). Showing the reading's width in STATUS.

**Tier / gate:** tier A (`broker/kernel/proc`, `cmd/agentos-kernel`): L3 on the strongest model, the tier's lens screen and a separate Security accept. Trusted lines grow by 186; main is at 58,644 under the 59,120 ceiling (D-310), so no raise.
