# Clerk exit: assumptions

Built for MIG-4-exit (#2571, D-139 step 4), slice 1: the declaration-driven exit in `broker/clerk` (`exit.go`, `secrets.go`). Each row is a reading a reviewer may want to change.

| ID | Assumption | Spec basis | If it changes |
|---|---|---|---|
| MIG-4-exit-a | **A declared request shape fixes everything but argument values.** URL is https with a fixed host. A path slot is a whole segment, and the path holds no escapes, so the path checked at declare time is the path sent. A constant query may follow. `Query` maps a parameter to an argument, `Body` maps a field to an argument under a closed `Type` (JSON or form), and `Headers` are constants whose names come from one closed list of exact names: Accept, Accept-Language and User-Agent. The secret's header comes from a second closed list: Authorization and X-Api-Key. The lists are disjoint, so no fixed header is the secret's header, and the secret never goes in a header remotes commonly log. Every other name is refused, with no prefix or suffix pattern: the clerk's own headers, hop-by-hop headers, credential headers (X-Auth-Token, X-Amz-Security-Token and the like), request-reshaping headers (X-Http-Method-Override, X-Forwarded-*, X-Original-Url, X-Real-Ip) and version headers. A ported op that needs another header adds its name to one list, with a test. Each value is encoded by `url.Values` or `encoding/json` for its one place. A value that is empty, `.`, `..` or holds `/` is refused in a path slot. One op per verb per clerk. A GraphQL-style constant body and a read-back probe op are later items. | CLK-3 | A new place for a value is a new `Op` field with a test. |
| MIG-4-exit-b | **The exit gives back only an outcome and "http N".** Response bodies are drained, never returned, so a hostile page cannot reach the log or the planner. Reads that need a body go through the model clerk (CLK-7), a later slice. | CLK-4, CLK-7 | A body-returning op needs a quarantined reader. |
| MIG-4-exit-c | **Outcome from status, as a typed detail.** 2xx: ok. 401/403 auth, 402 declined, 404/410 notfound and other 4xx rejected are failed, because the remote refused before acting. 3xx (never followed), 408, 409, 5xx and no answer are unknown, left to the probe. 429 is unknown with phase notsent, so the probe answers notdone once Retry-After (seconds form only, capped at one day; a date form counts as 0) has passed and the kernel sends again under the same key. A detail is a code plus "http N", the host or an argument name. It never holds a value, a transport error or a secret, so nothing needs redacting. | KRN-8, CLK-2, CLK-4 | A remote with its own status semantics gets its own op field. |
| MIG-4-exit-d | **Probe is the clerk's own memory.** It answers `done`, `unknown` or `notdone` per idempotency key, held in memory, and the key is sent as `Idempotency-Key`. It answers `notdone` only when a resend is safe: a 429 after Retry-After, or an op declared `Idempotent` (the remote dedupes on the key, and the declaration asserts it). Any other key it has no record of is `unknown`, because a restart forgets. At most `kernel.MaxChecks` sends per key, then `unknown` until the kernel parks the step. Retrying a parked step is the owner's RETRY, tracked by #2620 (kernel side), which does not exist yet. The lock covers only the state table, never a request. | KRN-8 | Persisting the table is one store write. |
| MIG-4-exit-e | **One clerk, one sealed secret slot.** Each op's slot must be in the store, and NewExit refuses a store that holds more than one slot or a slot the clerk does not use, so two slots across ops are refused too. AES-256-GCM with the slot name as AAD, and no method returns plaintext. The opened bytes are wiped after the request, but the header string copied from them is not (Go strings are immutable), so that wipe is best-effort. The sealing key is supplied by the caller; binding it to the TPM is the `tpmseal` side. A slot has a kind from a closed list, `static` or `grant`, bound into the AAD, so a relabelled kind does not open. A declaration without `Refresh` needs a `static` slot and one with it a `grant` slot; each path opens only its own kind, so a grant never goes out as a bearer header. The store is durable when built with a write function: `Put` hands it the whole at-rest form and returns only after it returns, and a failed seal or write leaves the store unchanged. The caller's write must return only once the bytes are on disk (the core SSD, STO-2). The at-rest form is a JSON map of slot to `{kind, blob}`; the earlier slot-to-blob form does not load, and no store in that form was ever written outside tests (the clerk was not wired), so there is nothing to migrate and no writer of it may ship. | CLK-1, STO-2..4 | A `Sealer` backed by the TPM replaces `AESSealer`. |
| MIG-4-exit-f | **Slice 1 is additive.** `broker/{egress,holder,checker,vault}` and their `cmd/` binaries stay until their slices port and delete them, in that order; `tools/old_core.txt` loses a line per deletion. | D-139 | none |
| MIG-4-exit-g | **The exit owns its transport and dials only through the home-network address policy.** No proxy from the environment, no cookie jar, no redirects, TLS 1.2 minimum. Every dial goes through `netguard.Policy.DialContext` (DEV-2), which checks each resolved address after DNS, so rebinding is caught. `Declaration.Guard` is required; NewExit refuses nil. The clerk dials with no purpose, so no pin admits it and every non-public address is refused. A pin can be added when an op for a home device needs one. A refused dial fails as `blocked`, with nothing sent. | CLK-3, CLK-4, DEV-2 | The broker passes its one shared policy, so learned home prefixes are refused too. |
| MIG-4-exit-h | **A step's recipient is its object argument.** Check refuses (RClaim) a step whose `Recipient` differs from the verb's first argument, so key caveats judge what is actually sent. | KEY-2 | none |
| MIG-4-exit-i | **OAuth refresh keeps both tokens inside the clerk.** A declaration with `Refresh` names an https token endpoint (no userinfo, no fragment); its slot then holds a sealed JSON grant of `refresh_token`, `client_id` and `client_secret` only, checked at NewExit. The access token lives only in clerk memory, so a restart redeems again. The grant goes as an RFC 6749 §6 form body with client credentials in the body (Basic auth is a later item). A rotated refresh token is written to the durable store before the new access token is used. If sealing or writing fails, the clerk keeps the rotated grant in memory, the only copy of the live refresh token, and fails every step with `credential` until a later step saves it. A token is redeemed again at 90% of its `expires_in`, capped at one day, or after a 401, which is followed by exactly one resend under the same idempotency key (a 401 acted on nothing). A token endpoint answer of 400 or 401 (invalid_grant, invalid_client) fails the step with `reconnect <clerk name>`, nothing sent, and the clerk stops redeeming that grant: every later step gets the same detail with no token request, until `Exit.Reconnect` replaces the grant, durably, without enrolling the clerk again. `Exit.CheckGrant` is Reconnect's refusal without the write, for the owner side to run when it stages a grant, so a malformed grant is refused before the owner's tap (#2742 item 6). Any other refused or malformed answer fails with `refresh` or `refresh http N`. The token request is the clerk's own upkeep, not a Check'd step, and goes through the same guarded transport; because it can wait, the step is checked again before every send that follows it, the 401 resend included. Header and form strings are Go strings, so they cannot be wiped. | CLK-1, CLK-4 | Basic client auth, a read-back probe op or a GraphQL body each extend this row |
| MIG-4-exit-j | **One owner text per account, rendered elsewhere.** The clerk gives `reconnect <account>` as a typed detail and stops redeeming, so every step on that account carries the same detail. Turning it into the one owner text "reconnect <account>", sent once per refusal rather than per step and offering the sign-in step on the owner page, belongs to the package that maps clerk details to owner text (CH-12, OWN-17), which has not been ported; it dedupes on the detail. `Exit.Reconnect` trusts its caller to have proved the owner (CH-3). | OWN-17, CH-7, CH-12 | The owner-text package adds the template and the sign-in step, and calls `Reconnect`. |
| TN-gmail-api-c1 | **An API is an exit the clerk calls itself** (`clerk.API`, #2851). It shares the exit's shape checks, transport, guard and refresh-grant handling (`conn`), but its calls are named, take exactly their declared arguments, and hand back the answer's body, bounded by each call's `Max` (`toolarge` past it) and with the sent secret redacted. It runs no `Check`: its caller is a clerk that has already checked the step it serves (the mail clerk's `Do`) or is making its own read. JSON body fields in `Lists` go as one-element arrays, which Gmail's label lists need. | CLK-3, CLK-1, CLK-4 | A caller that skipped its own check would act unchecked; the API is reachable only from inside a clerk's process. |
| TN-gmail-auth-a | **Installed-app sign-in is the account clerk's own** (`clerk.SignIn`, #2852, D-150, D-154). `Begin` draws the PKCE S256 verifier and the state from the clerk's own entropy and returns only the consent address. `Finish` takes only the pasted address: it must be the declared loopback redirect exactly (http, 127.0.0.1 or ::1, its port and path), and then ends the waiting sign-in whatever it holds, so a state or code is never tried twice. The clerk redeems the code itself through the guarded transport and seals `refresh_token`, `client_id` and `client_secret` as the slot's grant. One sign-in waits at a time, for 15 minutes on the clerk's clock; a new `Begin` replaces it. Every return is a typed detail with no value in it. | CLK-1, CLK-4, D-154 rule 3, 5 | The owner page relays `Begin`'s address and the paste as one frame each way when the mail host serves Gmail (#2925) and the owner page is built (#2853). |
| TN-gmail-auth-b | **The grant is exactly the asked scope.** Each declared use maps to one scope, and the token endpoint's `scope` must equal it. A wider grant (Google's `include_granted_scopes` with an earlier grant) or a narrower one is revoked at once and never sealed (`scope`). A provider that omits `scope` from its answer is refused too, though RFC 6749 §5.1 allows it; Google always sends it. | CLK-9, A22 | A provider that omits `scope` needs a declared exception, with a test. |
| TN-gmail-auth-c | **The client registration is given once.** The household's client ID and secret come with the first `Begin` only. A reconnect after grant death (`Begin` with nil) reuses the client sealed in the dead grant, so the owner side never holds the secret again. Where the owner types it the first time is open: on the owner page it would pass through the main side once (asked on #2852). | CLK-1, D-150 item 6, D-154 | If the registration is entered on a keeper-side page instead, `Begin` stops taking it. |
| TN-gmail-auth-d | **The box revokes its own grant** (RFC 7009): `Revoke` posts the refresh token to the declared revocation endpoint and empties the slot on 2xx, or on 400 (Google's answer for a token it no longer knows, so already dead). Any other answer keeps the grant and says `norevoke`, so the owner can try again or revoke it in their Google account. | A22 Gmail | none |
| TN-gmail-auth-e | **Grant death is the exit's `reconnect`.** A refused refresh already stops the clerk (MIG-4-exit-i). `inbox.GmailReconnect` is its owner text and names both causes: the sign-in removed or run out, or a Google client still in *Testing*, which ends every grant after 7 days. Rendering it once per refusal is the owner-text package's (MIG-4-exit-j). | OWN-17, D-150 item 3 | none |
| TN-gmail-auth-f | **TLS hybrid key exchange is pinned by a test, not by config.** The clerks' transport (`guarded`) keeps Go's default curve preferences, which put X25519MLKEM768 first. `TestClerkTLSUsesTheHybridKeyExchange` checks that an API call and a sign-in's code exchange both negotiate it, so a `CurvePreferences` list or a `GODEBUG` that drops it fails CI. | #2571, D-149 | Pin `CurvePreferences` explicitly if a toolchain default ever changes. |
