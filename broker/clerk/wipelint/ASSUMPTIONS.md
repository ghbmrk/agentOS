# Sealer key-wipe lint: assumptions

Built for LINT-sealer-key-wipe-fu (#6349). Each row is a reading a reviewer may want to change.

| # | Assumption | Basis | If it changes |
|---|---|---|---|
| LINT-sealer-key-wipe-fu-1 | A sealer is anything whose method set, as a type or through its pointer, satisfies `clerk.Sealer` (`types.Implements`); a constructor is a function whose results hold one anywhere inside (a field, pointer, slice, map, channel or func result), found by type alone, so a package need not import clerk to be held. Any receiver or parameter that can hold or produce bytes (an interface, func, channel, uintptr or unsafe.Pointer included) is a possible key, so such a constructor is listed with every possible key classified as a key or not, and the rule fails when its possible keys change. | CLK-1, STO-2 | A sealer of another shape (a second interface, a func pair) gets its own interface in the rule. |
| LINT-sealer-key-wipe-fu-2 | Only linux binaries ship, so a file that only another platform compiles holds no key on a box; the files lintload.Unread reports (another tag set, cgo, non-Go) are listed one by one in `unreadOK` with why each holds no sealer. | HW-8, REV-CHK-lintload-2 | A second shipped platform adds a load for it. |
| LINT-sealer-key-wipe-fu-3 | A listed key is a byte slice, wiped by the builtin `clear(k)` as the statement right after the call, so the key dies straight after its last use, before anything can return. `defer clear(k)` is refused (#6383): it wipes only at the function's return, so the key stays live through the rest of the function, a serve loop's life included. A string cannot be wiped, a byte array passes by value and leaves the callee an unwiped copy, and a key behind a pointer, in a struct or map, or of a type the lint cannot read (any, a type set without terms) cannot be wiped by one statement at the call, so a listed key of those forms fails. | STO-2 | A key form a statement can wipe at the call, with no copy left in the callee, gets its own wipe shape. |
| LINT-sealer-key-wipe-fu-4 | `vendor/` and nested modules are other modules: their declarations are not read, so a use in broker of one of their functions that makes a sealer from a possible key fails unlisted. | CLK-1 | Vendored code that must itself wipe a key is held where broker calls it. |
| LINT-sealer-key-wipe-fu-5 | A sealer comes into being from a key through a call of a constructor, a conversion to a sealer type, a composite literal of one, or a return through an interface (any) result; the last three fail outside the body of a listed constructor with keys. A key stored into a sealer after it is made (a field assignment, an append, a channel send) and a sealer reached through reflect or unsafe are held by review. | CLK-1, STO-2 | A tree where keys reach sealers by assignment gets a rule for writes into a sealer's fields. |
| LINT-sealer-key-wipe-fu2-1 | A listed constructor with keys keeps, copies, builds and derives no key, so its callers' wipe is the only one owed (#6383). In its body each key parameter is only the operand of `len` or `cap` or an argument of a function listed in `keyUses`, never inside a func literal, and no other expression has the type of key bytes (a non-constant byte slice, byte array or string; the parameters classified as not keys aside). A `keyUses` entry (today `crypto/aes.NewCipher`) keeps no reference to the slice and returns no bytes; the lint checks the second, review the first. Key bytes carried inside an interface, func or channel value in that body are held by review. | CLK-1, STO-2 | A constructor that must derive a key inside (a KDF) gets a wipe shape for the derived key on every return path, held here. |
