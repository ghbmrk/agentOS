# Assumptions: HomeKit (HAP) controller (DEV-homekit part a, #3291)

What the package rests on. Brief: `briefs/DEV-homekit.md`; decision D-182.

| ID | Assumption | Serves | If wrong |
|---|---|---|---|
| HK-1 | **No Go HAP controller is reusable.** `github.com/AlexxIT/go2rtc/pkg/hap` (MIT, active) takes the controller key as raw bytes (`ClientPrivate []byte`), so the key could not stay behind a holder, and it ships inside a large application module; `github.com/MrEhbr/hc` (Apache-2.0) was last published in 2020 as a fork of the archived `brutella/hc`; `brutella/hap` is accessory-side only. The controller here uses the standard library (`crypto/ed25519`, `crypto/ecdh`, `crypto/hkdf`, `crypto/sha512`) and the vendored `golang.org/x/crypto/chacha20poly1305`. | DEV-1, CLK-1 | A maintained controller that takes a signer: replace `pair.go` and `frame.go` with it and keep the tests. |
| HK-2 | **SRP-6a is the one hand-written primitive.** RFC 5054's 3072-bit group, g = 5, SHA-512, user "Pair-Setup"; k = H(N ‖ PAD(g)), x = H(s ‖ H(I ":" P)), u = H(PAD(A) ‖ PAD(B)), K = H(PAD(S)), M1 = H(H(N) xor H(g) ‖ H(I) ‖ s ‖ PAD(A) ‖ PAD(B) ‖ K), M2 = H(PAD(A) ‖ M1 ‖ K), with PAD = 384 bytes. B with B mod N = 0, a B longer than the group, u = 0 and a salt that is not 16 bytes are refused. | DEV-3, DEV-10 | A real accessory that hashes unpadded values fails pair-setup with a proof error; part c shows it, and the encoding changes here with a new vector. |
| HK-3 | **The SRP vectors come from an independent second implementation, not aiohomekit (deviation from the brief).** Executing the downloaded aiohomekit package was refused, so `testdata/gen_srp_vectors.py` (Python standard library only, run with `python3 -I`) computes them; each formula in it was checked against aiohomekit 4.0.1 `aiohomekit/crypto/srp.py` read as text only, and agrees, including aiohomekit's fixed k constant. Two implementations in two languages agree; neither is an accessory. | DEV-3 | If aiohomekit's output differs, regenerate with it and fix whichever formula disagrees. |
| HK-4 | **The key holder signs; this package never sees the private key.** `KeyHolder` gives a pairing ID, the public key and signatures. Part b builds it over the sealed store (STO-2, CLK-1). `MemoryKeyHolder` is for tests and prints and marshals no field. | CLK-1, DEV-4, A16 | A holder that cannot sign in-process: the interface stays, the signer moves. |
| HK-5 | **One attempt per call.** `PairSetup` never retries, so the accessory's own try counter (HAP: 100, then MaxTries until reset) counts only the owner's attempts. A wrong code returns `ErrAuthentication` and the zero `Pin`. | DEV-10 | None known. |
| HK-6 | **Identity is the pinned key and ID.** pair-verify checks the accessory's signature over both ephemeral keys with the pinned LTPK and the pinned pairing ID; either differing is `ErrIdentity`, the connection is closed and nothing else is sent. Part b turns that into the KRN-7 line and the owner re-pin. | DEV-3 | None known. |
| HK-7 | **Every target heating/cooling state write is `actuate-physical`, by choice.** DEV-5 would let turning heat off be a secure direction; the brief makes every value (off, heat, cool, auto) need the code-generator code (CH-10), because any change can stop heating (frozen pipes, an occupant at risk) or start a heat or cool source, so neither direction is safe to cover with a standing key. This is stricter than DEV-5 on purpose. | DEV-4, DEV-5, CH-10 | If the owner wants "off" covered by a key, that needs the kernel table to name a secure direction for this row, and a decision. |
| HK-8 | **Rows are data.** `ThermostatRows`, `AdminRows` and `ClassFor` are the HomeKit Thermostat rows for the kernel-shipped table (DEV-4); the session does not consult them. Setpoints inside the owner's confirmed bounds are `actuate` with the prior value as inverse; outside, or with unconfirmed bounds, `actuate-physical`; display units are `change-account`; anything unmapped reads as `read` and writes as `actuate-physical`. | DEV-4, DEV-5 | The kernel table takes a different shape: convert the rows, keep the test. |
| HK-9 | **Writes keep to the resolved shape.** A write names a resolved `aid`/`iid` with `pw`, a bool or number in the characteristic's format, inside `minValue`/`maxValue`, on `minStep` from `minValue`, and in `valid-values` when given; anything else is `ErrRefused` before a byte is framed. String, data and TLV8 writes are refused. `c#` changing re-resolves `/accessories`. | DEV-4, CLK-3 | A thermostat needing another format: add it to `checkValue` with a test. |
| HK-10 | **Bounds on accessory input.** TLV8 at most 4 KiB and 16 items, fragments joined only after a full 255-byte fragment, repeated types refused; HTTP lines at most 1,024 bytes, 32 headers, bodies at most 256 KiB by length or chunks, no body without a length, no redirects; frames 1 to 1,024 bytes; `/accessories` at most 150 accessories, 64 services and 64 characteristics each; at most 1,024 events while waiting for one response. The first framing or transport error ends the session. | RES-1, KRN-2 | A larger bridge: raise the caps with a fuzz run. |
| HK-11 | **Timeouts and reach are the caller's.** The package works on an `io.ReadWriter`; part b dials only the pinned address and port and sets deadlines; the enforcer drops the vendor-cloud traffic (enforcer rules row). | DEV-1, NET-2 | None for part a. |
| HK-12 | **The synthetic accessory is in-test.** `accessory_test.go` builds a thermostat from this package's codec and an SRP server written there, instead of vendoring `brutella/hap` and its dependency tree (`brutella/dnssd`, `go-chi`, `xiam/to` and more) for tests. It shows the controller against the protocol notes, not against a real thermostat; part c does that. | DEV-1, HLD-3 | A disagreement on a real thermostat: record the exchange (keys replaced by canaries) as a test here. |
