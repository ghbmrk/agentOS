# Sealed store (STO-2a): assumptions

Built for STO-2a (#2828), the first of the four STO-2 rows (triage 2026-10-23): the store file, its slots and its derived keys, in `broker/clerk/seal`. Boot wiring and the mains are STO-2b, image units and first-boot enrollment STO-2c, unknown-host unlock with the approval code STO-2d. Each row is a reading a reviewer may want to change.

| ID | Assumption | Spec basis | If it changes |
|---|---|---|---|
| STO-2a-a | **One store key, wrapped by independent slots, never on the drive.** The key is 32 random bytes. A slot is `tpm` (a random 32-byte slot key sealed by `tpmseal.Seal` under the box's policy key, with the optional boot PIN), `passphrase` (Argon2id of the Owner Card's passphrase, at least 256 MiB, its cost stored in the slot) or `recovery` (HKDF of the 32-byte recovery key; it is random, so it needs no slow hash). Each slot holds AES-256-GCM of the store key under its slot key, with the store's ID and the rest of the slot as associated data, so a wrap moved to another store or slot does not open and a passphrase slot's cost cannot be lowered in place. A tpm slot's boot paths are left out of that data so an update can add one (`SetPolicies`); the file's MAC covers them, and the TPM checks each signature at unseal. So nothing on the SSD alone opens the store (`TestCanaryKeyIsNotOnTheDrive` looks for the store key, the derived keys, the recovery key, the passphrase and an entry, raw, hex and base64). | STO-2, A8, HW-5a | none |
| STO-2a-b | **The whole file is MAC'd under the store key, and only its canonical encoding parses.** HMAC-SHA256 under a derived key covers the version, the ID, every slot and the sealed entries. After a slot opens, Unlock checks the MAC and refuses the store (`ErrTampered`) if it fails, so a slot forged by someone with the drive but not the key (one that wraps a key of their own for this store's ID) makes the store refuse to open for everyone; a dropped slot is refused the same way. The MAC does not stop someone who **replaces the whole file** with a store of their own (a key they chose, a MAC under it). A passphrase or recovery unlock refuses it only because the owner's factor opens no slot in it; that is the intended defence for those factors, since the attacker does not know the factor. A TPM unlock cannot rely on that: sealing to this TPM under the box's policy key needs only its public half (`tpmseal.SealTo` with the SRK public, or `Create` on the live TPM), and the owner's signed boot paths are in the owner's file, so an attacker's tpm slot unseals on the genuine boot. So a TPM unlock must be given the store's **anchor**, a one-way HKDF value of the store key (`Store.Anchor`), and refuses a store whose key does not derive it (`ErrTampered`, `TestAWholeStoreUnderTheBoxsPolicyKeyDoesNotOpen`; STO-2a-k). Even an opened replacement would release none of the owner's secrets (the log, head key and clerk Secrets stay under the old key), but it would run on keys and approval-code verifiers the attacker chose. Separately, **STO-2b must never treat a log that does not decrypt, or a head key the enforcer does not recognise, as a fresh box**; it stops and asks the owner. A tpm slot that unseals to a key of the wrong length (planted with `SealTo` under the box's public key) is `ErrCorrupt`, not a panic (`TestAPlantedShortTPMKeyIsAnError`). The parser accepts only the bytes `encoding/json` would write for what it read (no spacing, duplicate keys or base64 padding bits the MAC would not see), so any changed byte is refused. The cost: a tampered file is a denial of service until the owner restores it; nothing opens wrongly. | STO-2, KRN-2 | none |
| STO-2a-c | **Bounds are checked before any key work.** The file is at most 1 MiB, holds 1 to 16 slots, a tpm slot at most 16 boot paths, a passphrase slot an Argon2id cost between 256 MiB and 4 GiB and time 1 to 64, and the entries at most 64 of 4 KiB each. A hostile drive cannot make the unlock step allocate or hash past them. The 1 s tuning of the default cost (time 1, 4 threads) is #826; each slot keeps its own cost, so a retune needs no migration. A passphrase under 16 bytes is refused at enrollment; the Owner Card's is seven words. | STO-2, HW-4 | #826 changes `DefaultArgon` only. |
| STO-2a-d | **Per-purpose keys come from one HKDF, each under its own label.** `agentos-store/v1/` plus `log` (the log's AES-256-GCM key, `run.KernelConfig.Key`), `head` (the ed25519 seed of the kernel's head-signing key, KEY-3's head domain, `run.KernelConfig.Sign`), `clerks` (the clerk root key, from which the kernel derives each clerk's key, MAIL-keys; it replaced `sealer/<clerk>` and `Store.Sealer`, which had no production caller), `entries` and `mac`, with the store's ID as salt. The store key is never rotated: that would change every derived key and orphan the log. "Rekey" is `Replace`, which puts a new slot in place of one in a single write (a new passphrase or recovery key, REC-4, or a TPM slot sealed again with a PIN). | STO-2, KEY-3, CLK-1, REC-4 | A store-key rotation would need a log re-encryption step of its own. |
| STO-2a-e | **The store key stays with whoever unlocked.** `Store` holds the key until `Close` wipes it; `LogKey`, `HeadKey` and `ClerkRoot` hand out derived keys only. SPEC puts the store key with the unlock step, which hands each process only its own keys (credential exceptions, CLK-1); that step and its hand-off over inherited descriptors are STO-2b. Go cannot pin memory or stop the runtime copying it, so the wipe is best-effort, as in `broker/clerk`'s Secrets. | CLK-1, STO-3 | none |
| STO-2a-f | **Entries hold what the kernel reads after unlock, as opaque bytes.** The approval-code verifiers (the CH-4 seed, the grid) and the box's policy key (HW-5a: its private half lives only inside the store) are entries under names the caller picks. The store seals them as one blob under the entries key. Checking a code belongs to the rows that read them. | STO-2, CH-4, HW-5a | none |
| STO-2a-g | **Every change is one atomic write.** Add, remove, replace, boot-path and entry changes encode the whole file, write a temporary file beside it (mode 0600), fsync, rename over the store and fsync the directory; a write that fails before the rename leaves the file and the in-memory store as they were. Once the rename is done the store takes the new slots even if the directory sync then fails (the error is still returned), so the next write cannot put a replaced slot back, and `AddSlot` and `Replace` still return the new slot's ID with that error (`TestAFailedDirSyncDoesNotReviveAReplacedSlot`). `Create` links into place and refuses an existing path. Removing the last slot is refused. All of them need the open store, and so the key. One process opens the store at a time (the unlock step, STO-2b); this package takes no file lock. The rename is marked `durable:exempt lifecycle:exempt`, as in `clerk/run/secrets.go`: broker/durable is old core (D-139), so the new core neither imports it nor grows its `stores.txt`, and the store is key material, not a lifecycle. | STO-2 | STO-2b adds a lock if a second writer appears. |
| STO-2a-h | **A tpm slot is tried only on its own TPM.** Unlock reads the TPM's storage-root name (`tpmseal.Identity`) and tries only slots sealed to it, so another PC's TPM gets `ErrNoSlot` and spends no dictionary-attack count. A TPM refusal (a boot path no policy signed, a wrong or missing PIN, lockout) comes back joined with `ErrWrongFactor`, so the caller can say why. The policies must be signed by the slot's policy key at enrollment and at `SetPolicies`. | HW-5a, STO-2 | none |
| STO-2a-k | **A TPM unlock is given the box's policy key and the store's anchor, neither from the drive.** `TPM.PolicyKey` and `TPM.Anchor` are required at Unlock (`ErrNoPolicyKey`, `ErrNoAnchor`). A tpm slot sealed under any other policy key is skipped before any unseal, so a store sealed under the attacker's own key gives `ErrNoSlot` (`TestAStoreSealedUnderAnotherPolicyKeyDoesNotOpen`). That pin alone is not enough, because sealing under the box's key needs only public data; the anchor commits to the store key itself, and after the MAC checks Unlock compares the key's anchor in constant time and refuses a mismatch (`TestAWholeStoreUnderTheBoxsPolicyKeyDoesNotOpen`, second Security blocker on #2834). Both values are public but integrity-critical: neither may come from the store file (its writer is the attacker) nor from inside the store (it is not open yet). The anchor never changes, since the store key is never rotated (STO-2a-d), and it does not stop rollback to an older copy of the owner's own store (STO-2a-j). Where both live, for example a TPM NV index written at enrollment that only the box's policy key can rewrite, or the signed image, is STO-2b (the unlock step that reads and passes them) and STO-2c (enrollment that writes them). | A8, HW-5a, STO-2 | none |
| STO-2a-i | **A core package of its own.** `broker/core/core.txt` lists `core clerk/seal`, so its write paths (`Create`, `Unlock`, `AddSlot`, `Replace`, `Put`, `ClerkRoot`, …) are refused to any non-core, non-wiring caller unless an `open` or `allow` line names it; its first callers (the unlock main and `clerk/run`, wiring) come in STO-2b. It calls `clerk.NewAESSealer`, a core-to-core call. Its `FuzzParse` is on the CI fuzz list. | KRN-2, ARC-1 | none |
| STO-2a-j | **The store file is not anchored against rollback here.** A copy of an older store file opens with the older slots (for example a passphrase since replaced). REC-4 already says a rotation protects only against copies made afterwards; the log's own rollback is caught by its anchors (STO-1). | STO-1, REC-4 | A TPM-counter binding of the store file would be its own row. |
| STO-2c-a | **Enrollment builds the store at a staging path and renames it into place last** (`cmd/agentos-enroll`). Order: free a dead attempt, create the store with its tpm slot under a new per-box policy key (HW-5a), add the passphrase and recovery slots from the Owner Card's factors (open point 1 of #2905: all three slots, so a store never exists with only its tpm slot), keep the policy key's private half as the entry `tpm/policy-key`, define the log's TPM counter and keep its reference and auth as `kernel/counter`, start the anchor's head file (`run.InitCounterAnchor`, owned by the kernel's uid), write and lock the pins, then rename. So a store at the final path always has pins, counter and slots that agree. A rerun finishes a staged store whose pins are locked (only the rename was left) and otherwise frees the staged store's pins and counter by its ID and starts again (`TestEnrollCrashAfterEachStep`, `TestEnrollCutAfterEachTPMCommand`, which cuts the TPM after each of its commands). Enrollment refuses, changing nothing, over a store, a log, a staged store that does not parse, or another store's locked pins on this TPM (`tpmseal.OtherPins`), so a drive whose store and log were deleted is not taken as a new box while the TPM still pins the old store (`TestEnrollRefusesAndChangesNothing`). **Limit:** someone who deletes the store and log and plants a staged copy of the old store gets that store renamed back, which is the owner's own store. `kernel/anchors` is not written here (open point 2, asked on #2905). | STO-2, STO-1, HW-5a | If open point 2 is settled as enrollment taking the owner's keys, they become a step before the pins. |
| STO-2c-b | **Rotation adds a tpm slot under the new key; it cannot re-seal the old one.** A sealed object's policy is `PolicyAuthorize` over the key it was sealed under (tpmseal T2), so `SetPolicies` changes boot paths but never the key. `-rotate` keeps the next key as `tpm/policy-key-next`, adds a slot under it, frees the pins and writes them with the new key, removes the old key's slots, then moves the entry. Unlock tries only slots under the pinned key, so after a crash the store opens under the old key (pins not yet freed), the new key (pins rewritten), or only by the passphrase or recovery slot (between the two), never under a key the owner did not enrol; a rerun, given the passphrase file when the TPM holds no pins, resumes with the same next key (`TestRotate`, `TestRotateCutAfterEachTPMCommand`). The new slot re-signs the old slot's boot paths of one PCR selection (`SlotInfo.Policies`, `tpmseal.Resign`), read before anything changes, never this boot's PCRs, which the unlock step has capped (#2977, tpmseal STO-2c-cap); a `-pcrs` that names none of its selections is refused (#2959, `TestRotateKeepsTheEnrolledPCRs`). After the cap the tpm slot opens nothing, so a rotation on a running box opens the store by the passphrase file and refuses without one (`TestRotateAfterTheCapOpensOnTheNextBoot`). | HW-5a, STO-2 | If pins gain a second key field, the window with no pins goes away. |
| STO-2c-c | **Owner auth stays empty** (#2905 item 4, the recommendation taken). Setting it would need the SRK persisted at enrollment so the boot unlock could salt to it without owner auth, and rotation and freeing to carry the auth from inside the store; that is more TPM state than this row needs. The TPM device allowlist (slice (ii) of #2905) bounds who can send owner commands on the running box to the trusted side. `TestOwnerAuthStaysEmpty` pins the reading: a raw owner command with an empty password succeeds after enrollment. **Limit:** root on the box, or another OS booted on it, can undefine and redefine the pins (tpmseal STO-pins-a); a firmware TPM clear removes the pins, counter and SRK, and the unlock then fails closed to the passphrase or recovery slot. | STO-2, HW-5a | If owner auth is set later, the SRK must be persisted first and `ReadPins` must still need no auth. |
| STO-2c-d | **A counter made by a create that reported an error is adopted or freed, never orphaned** (#2905 requirement from #2907). After `DefineCounter` fails, enrollment asks the TPM (`FindCounter`): a counter that exists, defined but never incremented or written, is finished and adopted in the same call; none, or a TPM that does not answer, returns the error. The staged store then never commits, and the rerun frees whatever the ID holds, so no counter the store does not record remains to read as a rollback (`TestCounterMadeByAFailedCreate`, cases 1, 2 and 5; cases 3 and 4 check the rollback check and a deleted counter still fail closed). Adopting a written counter is safe here because the ID is fresh and random and only this run knows the auth. #2906 does not arise: there is one store per box and no copy holds a pending counter. | STO-1, LOG-2 | If a store ever gets a second counter, each needs its own intent. |
| STO-2c-f | **The pins are found by the drive's store ID** (`ReadID`, `Pinned`). The ID is read before any key, so it is the drive's word. A changed ID finds no pins (`ErrNoPins`, fail closed) or another store's, whose anchor this store's key does not derive (`ErrTampered`), so the unlock step can take it from the file (`TestTheProductionPinSourceReadsTheTPM`). | STO-2a-k | None expected. |
| STO-2c-g | **The anchor's directory is removed, made and chowned through descriptors on `-anchor-dir`'s parent** (#2960). Enrollment runs as root and the parent may be the kernel uid's to write, so a symlink swapped in between the steps would otherwise redirect root's unlink or chown. `proc.InitCounterAnchor` takes a path, so it is given the directory descriptor's `/proc/self/fd` path, and its own owner check refuses a directory swapped in after the mkdir (`TestAnchorDirIsNotRedirected`; the chown case runs only as root). | LOG-2, STO-1 | If `/proc` is not mounted at enrollment, the head file cannot be started; if `proc` gains a descriptor form, use it instead. |
| STO-2c-h | **The keeper's units** (#2905 slice ii-b; D-154; `image/mkosi/mkosi.extra/usr/lib/systemd/system/agentos-keeper-*`). `agentos-keeper-enroll.service` runs enrollment once setup has put the Owner Card's two factors in `/run/agentos-setup` and while no store exists; `agentos-keeper-kernel.service` runs `agentos-unlock`, which execs the kernel, once the store exists, after enrollment. Both are in `agentos-keeper.slice`, named `agentos-keeper-*`, and listed in `mkosi.finalize`'s `KEEPER_UNITS`: that is the keeper group's one place. Every other `agentos-*` unit is main side by default: one prefix drop-in (`agentos-.service.d/50-main-side.conf`) makes the store's and the kernel's state directories and `/run/agentos-setup` inaccessible to it (tmpfiles.d makes all three at boot, so the mask has no `-` and holds on the setup boot; #2981), and the service manager opens no file and makes no directory for it at, under or above one (`OpenFile=`, `LoadCredential=`, `EnvironmentFile=`, `Standard*=file:`, `StateDirectory=` and the like), and the keeper's drop-in (`agentos-keeper-.service.d/90-keeper.conf`, read after it) lifts that for the keeper only. The only path in is the kernel's sockets in `/run/agentos-kernel` (0711, sockets only). The unlock unit sets `NoNewPrivileges=yes`, no `AmbientCapabilities=` or `SecureBits=`, and gets no descriptor past 2 (no `Sockets=`, `OpenFile=`, descriptor store, or `.socket` unit; #2899). The unlock step itself passes 3 and 4 to the kernel. Its restarts stop at three starts a boot (`StartLimitBurst=3`, `StartLimitIntervalSec=infinity`, no reboot action), so a crash loop spends at most six counter increments a boot (#2897, LOG-anchor-tpm-b). `mkosi.finalize` refuses a mutant of each rule (`tests/test_image_keeper.py`). CI's boot test enrolls with synthetic factors and finds the unlock step opening the store on two boots of one swtpm, then refusing at the owner's hardware keys. **Limits:** (1) the old core's broker (`agentosd.service`, root, frozen, D-139) gets neither the mask nor a device policy, as for UPD-10 (#917). For a root unit the mask and the device policy are defence in depth, not a boundary, since root can leave both. (2) Until #2905 open point 2 is settled, an enrolled box's kernel unit fails after three refusals at unlock ("holds none of your hardware keys"). ~~Nothing in the image writes `/run/agentos-setup` yet~~: the Owner Card confirm writes the factors there through the keeper's setup socket, and `agentos-keeper-enroll.path` starts enrollment on them (OWN-card-flow slice a, #3470; `broker/cmd/agentos-enroll/ASSUMPTIONS.md` OWN-a-2, `image/ASSUMPTIONS.md` OWN-a-image). Enrollment removes both factor files, and the staged page authority with its published certificate, once the store is made (`ExecStartPost=`; a failed enrollment keeps them for a retry, and a crash between the commit and that step leaves them until the next boot's tmpfs). | STO-2, STO-1, CLK-1, UPD-10 | When open point 2 lands, the boot test's refusal line becomes the kernel answering. |
| STO-2c-i | **The Go runtime never holds descriptor `handoff.KeyFD` (100) or `handoff.TPMFD` (101) in `agentos-unlock`** (#4474). The kernel's are those numbers, not 3 and 4, because the runtime opens its own (the poller's epoll and eventfd, made at the first file, pipe, socket or timer, even the scavenger's before main) at the lowest free numbers, and the move overwriting one let another thread's poll before the exec kill the step. Before the move, every descriptor above 2 is made close-on-exec (`close_range`), so only 0 to 2 and the moved two reach the kernel (`TestTheMoveLeavesTheRuntimesDescriptors`). | STO-2, CLK-1 | If the step ever holds about a hundred descriptors at once, the runtime's could reach 100: raise the numbers. `close_range` with its flag needs Linux 5.11; the step fails closed without it. |
| MIG-4-recovery-r2-1 | **`ReplaceAndPut` changes a slot and an entry in one write** (REC-4, BAK-1; brief MIG-4-recovery-r decision 4). It is `Replace` and `Put` under one lock and one `commit`, so a write that fails before the rename leaves the file and the open store at the old slot and old entry, and a crash leaves one pair or the other, never a mix (`TestReplaceAndPutIsOneWrite`, through the `writeTemp` seam). As with `Replace`, a directory sync that fails after the rename returns the new slot's ID with the error: the new pair is in place. | REC-4, BAK-1, STO-2 | If the store's commit gains a second file, the pair must still land in one rename. |
| MIG-4-recovery-r2-2 | **`agentos-enroll -rotate-recovery` is route A's root step** (D-201; brief r2). It reads one JSON request to the end of its stdin (8 KiB bound; the owner side ends its write half): `factor` (`passphrase` or `recovery`), `secret` (the factor's bytes, base64), `next` (the new key, 64 hex digits) and `approval` (the kernel's `handoff.Approval`, base64). It opens the store with that factor only, verifies the approval with the store's head key on the card route and unexpired, checks `Old` against the store's `RecipientEntry` (`""` for a store with none) and `Next` against `RecipientFor(next)`, then `ReplaceAndPut`s the one recovery slot and the new recipient. It answers one word on stdout: `ok`, or `request`, `factor`, `approval`, `stale`, `busy` or `store`, each of which changed nothing (`TestRotateRecoveryRefuses` compares the store's bytes); the reason goes to stderr, never a secret. The request buffer, factor and new key are wiped on return (`next` is decoded into a byte slice, never a string); `seal`'s own copies are its. It takes the store's lock, a `flock` on the `-state` directory, without waiting (`busy`); `-rotate` takes the same lock and waits, so neither writes back the other's replaced slots. A rename whose directory sync then fails answers `ok`: the store then opens only with the new key. A replayed approval is `stale` once the store's recipient has changed, unless it names the key the store now holds (MIG-4-recovery-r4c-1). | REC-4, BAK-1, STO-2 | If the owner side needs a streamed request, read one JSON value instead of to the end. |
| MIG-4-recovery-r2-3 | **The rotation's units are the keeper's** (brief decision 7). They are `agentos-keeper-rotate.socket` and `agentos-keeper-rotate@.service`, not the brief's `agentos-recovery-rotate`: only an `agentos-keeper-*` unit gets the keeper drop-in that lifts the main side's mask on `/var/lib/agentos-store`, and `mkosi.finalize`'s `KEEPER_UNITS` lists it. The socket is `/run/agentos-keeper/rotate.sock`, root's and `agentos-owner`'s group, 0660, `Accept=yes`, `MaxConnections=1`. The service has stdin and stdout on the connection and stderr in the journal, a 60 s bound as `TimeoutStartSec=60` (a oneshot is starting until it exits, and systemd ignores `RuntimeMaxSec=` on one; `mkosi.finalize` refuses that form), `DevicePolicy=closed` with no TPM (it is left out of `TPM_UNITS`), and the keeper's other hardening. The preset enables the socket. `tests/test_image_keeper.py::test_the_recovery_rotation_is_one_root_one_shot_per_connection` pins these settings. **Limit:** any process in `agentos-owner` can reach the one-shot, which still needs an Owner Card factor and a head-signed approval. | REC-4, STO-2, UPD-10 | When r4a's client lands, its socket path and the request form must match these. |
| MIG-4-recovery-r4c-1 | **A retry after a lost ok answers ok and writes nothing** (#3606; BAK-1, brief decision 6). When the owner side lost the one-shot's answer it keeps no switch, and the owner taps again for the same key, so the kernel, still at the old recipient, signs a fresh approval. If the request's factor does not open the store, the one-shot tries `next` as the recovery key; once open by either, if the store's recipient ID equals both the approval's `Next` and `RecipientFor(next)`, it answers `ok` without writing (every writer of the recipient, enrollment, this one-shot and unlock's route B, puts it with its key's recovery slot), and the owner side switches the kernel as after the first ok. A store opened only by `next` that is not already in that state answers `factor`. So a wrong factor with a current approval for the key already in place answers `ok`; nothing changes and the kernel still checks the approval's `old` (`TestRotateRecoveryRetryAfterLostAnswer`). | REC-4, BAK-1 | If the recipient entry is ever written without its slot, check that `next` opens the store before answering ok. |
