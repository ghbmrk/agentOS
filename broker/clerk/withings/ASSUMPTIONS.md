# Assumptions: Withings Body Smart reader (DEV-withings-ble part a, #3272)

What the package rests on. Brief: `briefs/DEV-withings-ble.md`.

| ID | Assumption | Serves | If wrong |
|---|---|---|---|
| WBS-1 | **The protocol is the source's.** Framing, commands, TLV layouts, the challenge and the measure codes come from `github.com/pierosavi/withings-local` (MIT, read at `eab5a03`), observed on one Body Smart at firmware 1311; the session flow is the source's `read_measurements`. No Withings material is in this package. The synthetic scale in `scale_test.go` follows the same notes, so the tests prove the reader against the notes, not against a scale. | DEV-12 | A first read on Mark's scale (part c) that disagrees: fix the parser here, and add the recorded exchange (with `kl` replaced by the canary) as a test. |
| WBS-2 | **Closed allowlist of whole frames.** `allowed` admits only the nine shapes the source's client sends, compared byte for byte for the fixed ones; it is checked in `Session.send`, the one call of `Link.Write`. SYNC_OK is on it, as reported harmless twice (source `docs/recon.md`); TIME_SET is not, although the phone app sends it. | DEV-4, DEV-12 | If SYNC_OK turns out to hide readings from the phone app, take it off the list; the scale then may ignore the next connection, which costs a weigh-in, not data. |
| WBS-3 | **`kl` stays with the prover.** The session gets only answers and a yes or no; `KeyProver` holds `kl` and prints no field. Part b builds the prover from the sealed store and part c runs the session on the enforcer, so the enforcer never holds `kl` (NET-2: no shared secret). | CLK-1, NET-2 | If the channel cannot carry a challenge and its answer (spec row s), the enforcer would need `kl`, which needs a spec change. |
| WBS-4 | **The scale is unverified.** It offers only its MAC string and the shared-`kl` proof, which anyone holding `kl` passes, so every reading is marked unverified (DEV-3). A scale that fails the proof gets DISCONNECT and nothing else. | DEV-3, DEV-8 | None for a read-only scale; an owner rule over its readings is never urgent. |
| WBS-5 | **Readings carry no scale text.** Name, MAC string and manufacturer ID are read only to reach the firmware number; a reading is a time, a code from a closed table, a decimal and a user slot. Unknown codes are counted, not returned. | DEV-8, PLN-3 | A useful unknown code: add it to `measures` with its meaning from the public API. |
| WBS-6 | **Bounds.** A session answers at most 32 scale requests and reads at most 256 messages in one reply; frames are at most 65,540 bytes by their u16 length; a stream out of sync ends the session. The record parser bounds the user array at 16. | RES-1 | Larger stores: raise `maxReplies`; a 5-byte header bounds memory regardless. |
| WBS-7 | **`kl` is lent, not held** (part b1, #3276). `Keeper.Open` is `clerk.Secrets.DeviceKey`: it opens a static slot under `device/` for one answer or one check and wipes the bytes after, so `kl` is in core memory only while one answer is computed: `answerFor` hashes one scratch buffer with `sha1.Sum` and clears it, so no digest state keeps it (short of copies the Go runtime itself makes). `KeyProver` (part a) stays for tests and holds a copy; the clerk never uses it. | CLK-1, STO-2 | A TPM-backed sealer replaces the AES one behind the same `Secrets`. |
| WBS-8 | **The prover is no reflection oracle.** A `Keeper` runs one session at a time (`Prove` waits for the turn), answers only the paired scale's MAC string, answers once and checks once per session in that order, refuses a check of the challenge it just answered, and never answers any of its last 16 own challenges. With one session at a time, only the current session's own challenge is outstanding, and it is drawn after that session's answer, so a peer cannot get it answered. Relaying a real paired scale's challenge from elsewhere is still possible and is part c's exposure to record (WBS-3). | CLK-1, DEV-3 | Concurrent sessions would need the prover to draw the own challenge itself. |
| WBS-9 | **Owner slots, marks and the rate limit.** Only the user slots the owner chose at connection go on the bus; other household members' readings and slot 0 are counted, never emitted, even if a host lists slot 0. Each owner slot has a mark, the newest weigh-in time emitted; the scale resends its whole store each time, so only newer weigh-ins go out, oldest first; one at or below its mark (a scale clock set back) is counted as stale. At most one read per `Gap` (1 min) connects; a read within it is coalesced and counted. At most `MaxEvents` (64, and never below one weigh-in's size) events per read, in whole weigh-ins; the rest wait for the next read with their marks unmoved, so nothing is lost. Delivery is at least once: a bus that refuses the k-th event of a weigh-in gets the earlier ones again, so b2's entry dedupes on (device, user, time, measure). The host keeps the marks across restarts (`MarksCopy`); without them a restart re-emits the store once. | DEV-8, RES-1, PLN-3 | A scale whose store is not resent whole would lose deferred readings: hold them in the clerk instead. |
| WBS-10 | **The bus is a function for now.** `Clerk.Emit` takes one `Event` (device, `private` label, unverified, the reading). The kernel has no device-report entry yet (KRN-1: the bus is the log) and no host runs the clerk; both are part b2 (#3293), behind the kernel slot and the agentosd slot. The package is not linked into a trusted process until then, so it needs no `trusted_base_parsers.txt` line yet; b2 adds `parser github.com/ghbmrk/agentos/broker/clerk/withings -- Withings scale BLE notifications`. | DEV-8, KRN-1, KRN-2 | b2 maps `Event` to the kernel's entry and wires the host. |
