# clerk/camera: assumptions

Built for CAM-clerk part (a), CAM-clerk-lib (#3514, `briefs/CAM-clerk.md`), against DEV-1, DEV-2, DEV-3, DEV-7, DEV-8, KRN-7, NET-2 (Cameras) and A16. `broker/clerk/camera` is the core's camera clerk library: dial, pin, client key, frame reader, capture gate, silence and tamper events. The decoder (b), retention (c) and the process and page wiring (d) are later parts. Each row is a reading a later change could overturn.

| # | Assumption | Basis | If it changes |
|---|---|---|---|
| CAM-clerk-1 | **The brief's open questions are taken at their recommendations** (asked on #3514): continuous capture with no retention is memory-only (c); the clerk is its own process (d); a spoofed node is turned off by the clerk alone, which stops dialing it, logs a KRN-7 line and raises the tamper event; nodes are learned from the enforcer's list (d). | #3514 comment 6455861897 | Each answer changes only the part it names. |
| CAM-clerk-2 | **The client key is a P-256 scalar of 32 bytes in a device slot**, lent per signature through `clerk.Secrets.DeviceKey`, as the HomeKit holder lends its seed. `ClientKey` keeps the public key and a self-signed certificate; each TLS signature lends, parses, signs and drops. The parsed `ecdsa.PrivateKey` is garbage, not wiped: Go offers no wipe of its internals. The node checks the certificate's key against its bundle's `Core` point only, so the certificate's fields are fixed. | Design point 1, CLK-1; `clerk/homekit/holder.go` | A slot format with a version byte, if a second key kind is ever lent here. |
| CAM-clerk-3 | **The pin is checked before the client key is used.** Go's TLS 1.3 client runs `VerifyConnection` on the server's certificate before it sends its own certificate and signature, so a node with another key never gets a signature (`TestSpoofedNodeRefused` counts the lends). | Design point 2 | A Go release that reorders this would fail that test. |
| CAM-clerk-4 | **The dial guard is `netguard`'s, with `PurposeDevice`**, as the HomeKit clerk dials. The clerk also refuses, at `Add` and again at each dial, an address that is not a literal private or link-local IPv4 address (not a /24's .255) or a unique-local or link-local IPv6 address. A global IPv6 home address inside the uplink's /56, which `devslot` admits, is refused here, since a camera on the box's own network has a private address. | DEV-1, DEV-2; `clerk/homekit` `checkAddr` | Admitting global /56 addresses means taking the home prefix in `Config`, as `devhost` does. |
| CAM-clerk-5 | **The DEV-8 limiter restates `devhost`'s rather than importing it**, because `devhost`'s is part of its `Host` (keyed by a driver declaration's reading kinds) and not exported; extracting it would edit `devhost`, outside this part's scope. It is the same rule: Burst events per window per camera and kind, the rest counted into one coalesced event, flushed on the host's timer. | Design point 7 | If `devhost` exports its limiter, this package should use it. |
| CAM-clerk-6 | **Silence is a read deadline of the node's interval** (default 30 s) on an open stream, and, when the stream cannot be opened or ends, the time since the last frame. A truncated frame followed by a hang-up is a transport end, judged by silence, not a stream fault; a frame the codec refuses is a fault. Recovery is the first frame after silence. | Design point 7 | — |
| CAM-clerk-7 | **Every node event is verified**, since every node is pinned by its TLS key (DEV-3); no unverified camera exists. Events carry the camera's ID (the core's name), the kind, the time and a count: no byte from the node. | DEV-3, DEV-8 | A camera without a key would need `Verified` set per node. |
| CAM-clerk-8 | **The status record is kept in memory only** (`LastStatus`) for part (d) to compare the running image and settings counter; it is never logged or put in STATUS. | Design point 6 | — |
| CAM-clerk-9 | **On request means a read step of a task that names the camera**, as the kernel admitted it; the stream lasts until the step's context (the task) ends. A continuous camera opens no stream for a step and an on-request camera none for `Run`. | DEV-7, design point 5 | A camera allowed both modes would make `Mode` a set. |
| CAM-decode-f1-1 | **Every owner change cuts the sink** (#3614): `SetCapture`, `Repin` and `Remove` call `FrameSink.Cut` under the node's delivery lock, and `Decoder.Cut` stops the camera's sandbox and drops its queue, returning once no frame fed before it can reach `Out`. A thermal frame out must carry the counter of the next thermal frame fed and come out within the stall deadline; a picture's counter is the sandbox's and is not trusted. | DEV-7, design point 4 | An H.264 decoder that may drop pictures (b2) keeps the picture counter unchecked. |
| CAM-clerk-10 | **Part (c) takes question 1 at its recommendation; Mark had not answered on #3514 when it was built.** With no owner-set retention a camera's capture is held only in its memory ring (`Store.Recent`), and nothing is written, not even a key. With one, frames are sealed into segments and kept that long. The 30-day evidence retention Mark set on 2026-10-27 is an owner setting that part (d) passes to `Store.Add` or `SetRetention`; the store has no default retention. | #3514 comment 6455861897; DEV-7 | An answer that keeps capture by default would make the default retention non-zero in (d); this file would not change. |
| CAM-clerk-11 | **Each camera's segment key is its own static device slot**, `device/camera-segments/<id>` (`SegmentSlots`), lent per call through `clerk.Secrets.DeviceKey`, so it never leaves the sealed store's lending (CLK-1). The store takes the slots as an injected `SegmentKeys`; part (d)'s process binds it to `clerk.Secrets` (Has/Put to make, DeviceKey to lend, Remove to erase), since `broker/core` refuses sealed-store write paths outside the core's listed wiring. The tests bind it to a real `clerk.Secrets`. Each segment is sealed under AES-256-GCM with a key derived by HKDF-SHA256 from the camera key and a random 32-byte salt kept in the segment, so each derived key seals one message and the nonce is fixed at zero. The AAD binds the camera and the file name, so a segment moved to another camera, or renamed to a later expiry, does not open. | Design point 1; brief part (c) | A TPM-bound key per segment would need a sealer call per segment; not needed while the slot is sealed. |
| CAM-clerk-12 | **Erase destroys the key before the files.** Disconnect (`Store.Erase`) and removing a retention erase the camera's key first, so a file a crash or a failed unlink leaves behind does not open again; then they delete the directory, the open segment and the ring. A camera disconnected while the store was down is erased by the first `Sweep`, which (d) runs after adding every connected camera; a connected camera `Add` refuses is `Keep`-ed instead, and the sweep leaves its directory and key until `Erase` (#3968). A key slot left without any directory opens nothing and is not swept: `SegmentKeys` has no listing. | DEV-7, brief lifecycle matrix (Disconnect, Restart) | If the sealed store gains a prefix listing, `Sweep` should erase unclaimed slots too. |
| CAM-clerk-13 | **Expiry is read from the segment's name**, the times of its first and last frames, so the sweep needs no key and opens no file. A clock set back delays deletion by that much; a name the store did not write, a torn write's `.tmp` and a directory that is not a camera ID are deleted. A camera's directory that is not a directory (a symlink) is removed, never followed. A failed deletion returns `ErrErase` ("capture not deleted"), apart from `ErrWrite` for a segment not written. | DEV-7 | — |
| CAM-clerk-14 | **Segments are written whole, through `privfile.WriteAtomic`**, in the store's own directory (this uid only, `privfile.Check`), as `kernel/proc`'s content files are. They are raw capture, not journal content: never in a backup, recall or the log (DEV-7, LOG-4), so they are not in the kernel's content store (KRN-content), whose items go into backups. | DEV-7: raw capture never leaves the box | If backups gain a local-only section, retained capture could move there. |
| CAM-clerk-15 | **The write rate cap is a byte budget per camera per minute** (default 4 MiB a second): frames past it go to the ring only, and the next segment's log line counts them. The ring is bounded by frames and bytes (defaults 300 and 32 MiB), and a segment closes at 10 s or 8 MiB. A sealed or unwritten open segment leaves memory at once. | Design point 8 | Owner-settable caps would be (d)'s page step. |
| CAM-clerk-16 | **On-request capture ends at `EndTask`**, which (d) calls when the step's `Capture` returns: the ring is dropped, and the open segment is written only under a retention. The store keeps no task identity: a camera is either continuous or on request (CAM-clerk-9), and no frame arrives after `Capture` returns, since the clerk hands frames only within it. | DEV-7, design point 5 | A camera allowed both modes at once would need the task in each frame. |
| CAM-clerk-17 | **libc's static start-up is the only file that may reference a network call in the decoder's link** (#3816). glibc 2.39's static `pthread_create`, which `runtime/cgo` calls, pulls in the resolver state and with it `socket`, `bind` and `sendto` (res_hconf, ifaddrs); none is reached from the decoder's code, and the gVisor namespace leaves no network to reach. `image/camdecode.sh` stops the build when the link map's cross-reference table shows a network call defined or used by any file outside `libc.a`, and when go env's cgo tools and flags or pkg-config's flags for libavcodec and libavutil differ from the pinned ones (`-latomic` included, as configure finds it on Ubuntu 24.04's gcc 13). | Link map of the build at this PR's head; `TestDecoderLinkHasNoNetworkCall` | A libc whose start-up references network calls from outside `libc.a` (musl, or a split libc), or a toolchain whose configure drops `-latomic`, stops the image build until the pin is reviewed. |
