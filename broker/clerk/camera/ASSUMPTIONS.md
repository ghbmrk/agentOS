# clerk/camera: assumptions

Built for CAM-clerk part (a), CAM-clerk-lib (#3514, `briefs/CAM-clerk.md`), against DEV-1, DEV-2, DEV-3, DEV-7, DEV-8, KRN-7, NET-2 (Cameras) and A16. `broker/clerk/camera` is the core's camera clerk library: dial, pin, client key, frame reader, capture gate, silence and tamper events. The decoder (b), retention (c) and the process and page wiring (d) are later parts. Each row is a reading a later change could overturn.

| # | Assumption | Basis | If it changes |
|---|---|---|---|
| CAM-clerk-1 | **The brief's open questions are taken at their recommendations** (asked on #3514): continuous capture with no retention is memory-only (c); the clerk is its own process (d); a spoofed node is turned off by the clerk alone, which stops dialing it, logs a KRN-7 line and raises the tamper event; nodes are learned from the enforcer's list (d). | #3514 comment 6455861897 | Each answer changes only the part it names. |
| CAM-clerk-2 | **The client key is a P-256 scalar of 32 bytes in a device slot**, lent per signature through `clerk.Secrets.DeviceKey`, as the HomeKit holder lends its seed. `ClientKey` keeps the public key and a self-signed certificate; each TLS signature lends, parses, signs and drops. The parsed `ecdsa.PrivateKey` is garbage, not wiped: Go offers no wipe of its internals. The node checks the certificate's key against its bundle's `Core` point only, so the certificate's fields are fixed. | Design point 1, CLK-1; `clerk/homekit/holder.go` | A slot format with a version byte, if a second key kind is ever lent here. |
| CAM-clerk-3 | **The pin is checked before the client key is used.** Go's TLS 1.3 client runs `VerifyConnection` on the server's certificate before it sends its own certificate and signature, so a node with another key never gets a signature (`TestSpoofedNodeRefused` counts the lends). | Design point 2 | A Go release that reorders this would fail that test. |
| CAM-clerk-4 | **The dial guard is `netguard`'s, with `PurposeDevice`**, as the HomeKit clerk dials. The clerk also refuses, at `Add` and again at each dial, an address that is not a literal private or link-local IPv4 address (not a /24's .255) or a unique-local or link-local IPv6 address. A global IPv6 home address inside the uplink's /56, which `devslot` admits, is refused here, since a camera on the box's own network has a private address. | DEV-1, DEV-2; `clerk/homekit` `checkAddr` | Admitting global /56 addresses means taking the home prefix in `Config`, as `devhost` does. |
| CAM-clerk-5 | **The DEV-8 limiter restates `devhost`'s rather than importing it**, because `devhost`'s is part of its `Host` (keyed by a driver declaration's reading kinds) and not exported; extracting it would edit `devhost`, outside this part's scope. It is the same rule: Burst events per window per camera and kind, the rest counted into one coalesced event, flushed on the host's timer. | Design point 7 | If `devhost` exports its limiter, this package should use it. |
| CAM-clerk-6 | **Silence is a read deadline of the node's interval** (default 30 s) on an open stream, and, when the stream cannot be opened or ends, the time since the last frame. A truncated frame followed by a hang-up is a transport end, judged by silence, not a stream fault; a frame the codec refuses is a fault. Recovery is the first frame after silence. | Design point 7 | — |
| CAM-clerk-7 | **Every node event is verified**, since every node is pinned by its TLS key (DEV-3); no unverified camera exists. Events carry the camera's ID (the core's name), the kind, the time and a count: no byte from the node. | DEV-3, DEV-8 | A camera without a key would need `Verified` set per node. |
| CAM-clerk-8 | **The status record is kept in memory only** (`LastStatus`) for part (d) to compare the running image and settings counter; it is never logged or put in STATUS. | Design point 6 | — |
| CAM-clerk-9 | **On request means a read step of a task that names the camera**, as the kernel admitted it; the stream lasts until the step's context (the task) ends. A continuous camera opens no stream for a step and an on-request camera none for `Run`. | DEV-7, design point 5 | A camera allowed both modes would make `Mode` a set. |
| CAM-decode-f1-1 | **Every owner change cuts the sink** (#3614): `SetCapture`, `Repin` and `Remove` call `FrameSink.Cut` under the node's delivery lock, and `Decoder.Cut` stops the camera's sandbox and drops its queue, returning once no frame fed before it can reach `Out`. A thermal frame out must carry the counter of the next thermal frame fed and come out within the stall deadline; a picture's counter is the sandbox's and is not trusted. | DEV-7, design point 4 | An H.264 decoder that may drop pictures (b2) keeps the picture counter unchecked. |
