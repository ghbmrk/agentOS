# camera: assumptions

Built for CAM-clerk part (a), CAM-clerk-lib (#3514, `briefs/CAM-clerk.md`), against DEV-1, DEV-2, DEV-3, DEV-7, DEV-8, DEV-10, CLK-1, KRN-7, NET-2 (Cameras and microphones), LOG-4 and A16. The brief's four open questions are built on their recommendations (#3514 comment 6455861897). Each row is a reading a later change could overturn.

| # | Assumption | Basis | If it changes |
|---|---|---|---|
| CAM-clerk-1 | **The pin is the SPKI hash of the node's device key**, computed from the 65-byte point the enforcer lists, so the device guard's `PinDevice` pin and the clerk's handshake check are the same value. The clerk checks the leaf's key exactly against its own camera's pin in `VerifyConnection`, not through `netguard.TLSConfig`, whose address-only path admits the key of *any* address-only pin. | Brief design point 2; `netguard.KeyHash` | — |
| CAM-clerk-2 | **A key mismatch is found before the node proves possession**, on the server's Certificate message, so any host at the pinned address can turn the node off by presenting another key. That is the brief's tamper response (question 3): the node is off, a KRN-7 line and an event go out, and the owner re-pins at tier 4. A matching key still has to sign the CertificateVerify, so it cannot be replayed. | Brief question 3, NET-4 | If off-by-spoof proves a nuisance, count refusals before turning off (a decision: it weakens the response). |
| CAM-clerk-3 | **The TLS parameters restate CAM-server's** (#3586, `camnode.ClientConfig`): TLS 1.3, X25519MLKEM768 only, no tickets, a self-signed P-256 client certificate. This package does not import `camnode`, the node's server, which is not on main and should not be linked into the core. | CAM-node brief design point 4 | When `camnode` merges, a shared definition in `camwire` (standard library only) would serve both; that is a CAM-node row. |
| CAM-clerk-4 | **The client key is lent for the handshake only.** `Config.Lend` is `clerk.Secrets.DeviceKey(ClientSlot)`, a 32-byte P-256 scalar; the clerk parses it into an `ecdsa.PrivateKey` inside the lend and drops it when the handshake returns. Go's TLS stack signs with it during the handshake and keeps no reference after (no resumption, no post-handshake auth in TLS 1.3 client code). The parsed key's internal copy is not wiped; the lent bytes are (`Secrets.with`). | CLK-1, A16; HK-14 does the same | An out-of-process signer: `Lend` becomes a `crypto.Signer` holder. |
| CAM-clerk-5 | **The home check is narrower than DEV-2's**: private or link-local IPv4 (no .255), unique-local or link-local IPv6, never a global IPv6 address inside the home /56. A camera node sits on the enforcer's LAN, which the enforcer addresses privately. The device guard checks the address again against the pin. | DEV-2, NET-2; HomeKit's `checkAddr` | A node on a global IPv6 address: take the home /56 as `devslot.Check` does. |
| CAM-clerk-6 | **The DEV-8 limiter restates `devhost`'s rule** (Burst per Window per source and kind, the rest counted into one coalesced event at the window's end, `Flush` on a timer) and emits `devhost.Event`s to a `devhost.Sink`, the device-report entry. `devhost`'s limiter is unexported and outside this row's scope; exporting one shared limiter is a later row. Windows close and are forgotten once they end, so the map holds only open windows. | Brief question 2 | Export `devhost`'s limiter and use it here. |
| CAM-clerk-7 | **Events are verified**: `Unverified` is false because the node proved its pinned key (DEV-3). They carry the camera id, a kind and a number (seconds since the last frame for silence) only. | DEV-3, DEV-8, brief design point 7 | — |
| CAM-clerk-8 | **Silence is a frame missing past the interval**, measured per frame read (a frame trickled slower than the interval counts as silence), and also across failed dials. One silent event per outage, one recovered event at the next frame. | Brief design point 7 | — |
| CAM-clerk-9 | **A framing fault ends the connection and raises a fault event**; the clerk redials with backoff. Only a stream that ended cleanly or went silent after frames resets the backoff, so a node that faults after each good frame keeps backing off up to `MaxBackoff`. | Brief design point 3, lifecycle row "hostile stream" | — |
| CAM-clerk-10 | **The capture gate trusts the caller for admission.** `Capture` takes a step the kernel admitted and checks only that it names this clerk, the read verb, a task and this camera; `Run` streams only a camera turned on continuous. The turn-on record itself (tier 4, DEV-10) is part (d)'s local-page step. | Brief design point 5 | — |
| CAM-clerk-11 | **Frames go out through `Config.Frames` alone**, synchronously, to the decoder feed (b) and the memory ring (c), which must not block. The status record is kept (numbers only) for STATUS. Nothing here writes to disk. | DEV-7, LOG-4, brief design point 6 | — |

The synthetic node in `helpers_test.go` is built on `camwire` with its key in memory and serves TLS on loopback; the guard's `Connect` hook sends the pinned home address there.
