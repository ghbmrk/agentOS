# Plan login clerk: assumptions

Built for MIG-4-plan-login-a (#3104, brief `briefs/MIG-4-plan-login.md`). `broker/clerk/plan` holds one consumer plan login, used only by its provider's CLI in a guest (CLK-7, PLN-5). It is the old core's plan route (`egress/codexlogin.go`, `exchange.go`, `worker.go`, measured on Codex CLI 0.162.1, #809), ported onto the clerk. Nothing imports the old code. Each row is a reading a reviewer may want to change.

| ID | Assumption | Spec basis | If it changes |
|---|---|---|---|
| MIG-4-plan-login-a0 | **Outside the trusted core.** Package `clerk` is linked by the kernel's process for its check (KRN-2cap roots), and this clerk parses a guest's requests and a provider's answers. So it is its own package, linked only by the model clerk's process (slice b), and adds no core line. The cost is that it cannot use `clerk.Secrets` (whose opener is package-private), so it keeps its own one-value `Store` over `clerk.Sealer`, and repeats `clerk`'s 12-line guarded transport rather than exporting it. | KRN-2, CLK-1 | Exporting an opener or the transport from `clerk` grows the core and needs a `Trusted-core:` decision. |
| MIG-4-plan-login-a1 | **One plan login, one clerk, one sealed value.** The `Store` holds a single blob, sealed with the plan's name as AAD, so a value sealed for another plan, or under another key, does not open and `New` refuses it. The blob holds the token set, the account and any stop together, so a stop survives a restart and is written with the login it concerns. A durable store hands its writer the whole at-rest form on every change, as `clerk.Secrets` does. | CLK-1, STO-2 | A second plan is a second clerk with its own store. |
| MIG-4-plan-login-a2 | **Placeholders are per guest and stand for fields, not values.** A guest's access, refresh and id placeholders resolve only for that guest, only for the field they were minted for, and only while the stored account is the one they were minted under. So a refresh keeps a guest's placeholders, and a sign-in to another account makes every old one dead. The id_token placeholder is an unsigned token that carries only the account claim and an expiry. Placeholders live in memory: after a restart a running guest's requests are refused until it is given a new token set. | CLK-1, CLK-7 | Durable placeholders would need their own sealed record. |
| MIG-4-plan-login-a3 | **The request is matched on method, path and the guest's role, never on its host.** A run guest reaches model, read and refresh endpoints; only a guest marked by `BeginSignIn` reaches the device and code steps. The clerk sends to the declared host over its own guarded transport, with only the declared headers. A credential, cookie, framing or reshaping header can never be declared, as a request header, an answer header or an answer prefix that could match one. Undeclared query keys, escapes, an upgrade or an encoded body are refused before anything is sent. A model call's body passes as sent: its schema is the model clerk's (MIG-4-plan-login-b). | CLK-3, CLK-4 | A provider that shares a path across hosts needs the host in the match. |
| MIG-4-plan-login-a4 | **A token answer is forwarded only in its declared shape**: a JSON object of exactly the declared fields, credentials swapped for the guest's placeholders, text only by declared pattern. It must name its account in the id_token at the declared claim. It is committed to the store before the guest sees it, since refresh tokens are single-use. An answer that cannot be sealed is dropped (`plan-save`), and the login stays as it was. | CLK-7 | none |
| MIG-4-plan-login-a5 | **Dropped and stopped (`unswappable`).** A 200 token answer out of shape, with no account, without both tokens after merge, or naming another account on a guest's refresh is dropped and stops the route for every guest and the sign-in. Only a release whose declaration has a new `Version` lifts it (requalify); `Resume` and `Remove` do not. A stop the store cannot record is held in memory, so the route fails closed until restart. | CLK-7 | A durable record outside the slot would cover a failed write across a restart. |
| MIG-4-plan-login-a6 | **A refused login is a declared error code, not a status alone.** SPEC says the refusal is declared as response statuses. A refresh answered 400 or 401 is refused only with a declared code (Codex: `refresh_token_expired`, `refresh_token_reused`, `refresh_token_invalidated`), because a guest can provoke a bare 400 (`invalid_grant`) by sending another `client_id`. It stops the route (`refused-login`) until `Resume` (`PLAN <plan> ON`, its caller proves the owner) or a sign-in commits a login. Any other error answer is dropped and stops nothing. | CLK-7 | If the spec keeps "statuses", a SPEC diff should say "statuses and error codes". |
| MIG-4-plan-login-a7 | **One refresh exchange per login at a time** (#1749). A refresh that arrives while one is in flight joins it, and each joining guest gets the same answer in its own placeholders. The exchange runs past the leader's cancellation, for at most 30 s, so a token that was spent is still committed. | CLK-7 | none |
| MIG-4-plan-login-a8 | **The injected token is redacted** from the answer's declared headers and from its streamed body. Only a tail that could begin the token is held back, so a stream is delayed by at most a partial match. An encoded answer, which the redactor cannot read, is refused. | CLK-4 | none |
| MIG-4-plan-login-a9 | **`SignedIn(guest)` is the sign-in's only success signal**: this guest's own code exchange committed the login. A login stored earlier does not count, and neither does anything the guest writes or its exit status. | CLK-7, ONB-3 | none |
| MIG-4-plan-login-a10 | **A refresh answer is judged only against the login it was made for** (#3105 Security 1). The login has a generation that `Remove` and every sign-in commit move. A refresh flight records it and resolves the token it sends in one step, under the commit lock, so the answer is judged against exactly the login whose token it spent. An answer that comes back after the generation moved is dropped (`plan-stale`): it is not committed, and it stops nothing, whether it is good, refused or out of shape. Otherwise the owner's own sign-out or account switch, raced by a guest's refresh, would leave a release-only stop. | CLK-7 | none |
