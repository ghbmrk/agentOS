# Plan login clerk: assumptions

Built for MIG-4-plan-login-a (#3104, brief `briefs/MIG-4-plan-login.md`). `broker/clerk/plan` holds one consumer plan login, used only by its provider's CLI in a guest (CLK-7, PLN-5). It is the old core's plan route (`egress/codexlogin.go`, `exchange.go`, `worker.go`, measured on Codex CLI 0.162.1, #809), ported onto the clerk. Nothing imports the old code. Each row is a reading a reviewer may want to change.

| ID | Assumption | Spec basis | If it changes |
|---|---|---|---|
| MIG-4-plan-login-a0 | **Outside the trusted core.** Package `clerk` is linked by the kernel's process for its check (KRN-2cap roots), and this clerk parses a guest's requests and a provider's answers. So it is its own package, linked only by the model clerk's process (slice b), and adds no core line. The cost is that it cannot use `clerk.Secrets` (whose opener is package-private), so it keeps its own one-value `Store` over `clerk.Sealer`, and repeats `clerk`'s 12-line guarded transport rather than exporting it. | KRN-2, CLK-1 | Exporting an opener or the transport from `clerk` grows the core and needs a `Trusted-core:` decision. |
| MIG-4-plan-login-a1 | **One plan login, one clerk, one sealed value.** The `Store` holds a single blob, sealed with the plan's name as AAD, so a value sealed for another plan, or under another key, does not open and `New` refuses it. The blob holds the token set, the account and any stop together, so a stop survives a restart and is written with the login it concerns. A durable store hands its writer the whole at-rest form on every change, as `clerk.Secrets` does. | CLK-1, STO-2 | A second plan is a second clerk with its own store. |
| MIG-4-plan-login-a2 | **Placeholders are per guest and stand for fields, not values.** A guest's access, refresh and id placeholders resolve only for that guest, only for the field they were minted for, and only while the stored account is the one they were minted under. So a refresh keeps a guest's placeholders, and a sign-in to another account makes every old one dead. The id_token placeholder is an unsigned token that carries only the account claim and an expiry. Placeholders live in memory: after a restart a running guest's requests are refused until it is given a new token set. | CLK-1, CLK-7 | Durable placeholders would need their own sealed record. |
| MIG-4-plan-login-a3 | **The request is matched on method, path and the guest's role, never on its host.** A run guest reaches model, read and refresh endpoints; only a guest marked by `BeginSignIn` reaches the device and code steps. The clerk sends to the declared host over its own guarded transport, with only the declared headers. A credential, cookie, framing or reshaping header can never be declared, as a request header, an answer header or an answer prefix that could match one. Undeclared query keys, escapes, an upgrade or an encoded body are refused before anything is sent. A model call's body is held to the declared `Body` (MIG-4-plan-login-b1). | CLK-3, CLK-4 | A provider that shares a path across hosts needs the host in the match. |
| MIG-4-plan-login-a4 | **A token answer is forwarded only in its declared shape**: a JSON object of exactly the declared fields, credentials swapped for the guest's placeholders, text only by declared pattern. It must name its account in the id_token at the declared claim. It is committed to the store before the guest sees it, since refresh tokens are single-use. An answer that cannot be sealed is dropped (`plan-save`), and the login stays as it was. | CLK-7 | none |
| MIG-4-plan-login-a5 | **Dropped and stopped (`unswappable`).** A 200 token answer out of shape, with no account, without both tokens after merge, or naming another account on a guest's refresh is dropped and stops the route for every guest and the sign-in. Only a release whose declaration has a new `Version` lifts it (requalify); `Resume` and `Remove` do not. A stop the store cannot record is held in memory, so the route fails closed until restart. | CLK-7 | A durable record outside the slot would cover a failed write across a restart. |
| MIG-4-plan-login-a6 | **A refused login is a declared error code, not a status alone.** SPEC says the refusal is declared as response statuses. A refresh answered 400 or 401 is refused only with a declared code (Codex: `refresh_token_expired`, `refresh_token_reused`, `refresh_token_invalidated`), because a guest may be able to provoke a bare 400 (`invalid_grant`); before MIG-4-plan-login-pin it could by sending another `client_id`. It stops the route (`refused-login`) until `Resume` (`PLAN <plan> ON`, its caller proves the owner) or a sign-in commits a login. Any other error answer is dropped and stops nothing. | CLK-7 | If the spec keeps "statuses", a SPEC diff should say "statuses and error codes". |
| MIG-4-plan-login-a7 | **One refresh exchange per login at a time** (#1749). A refresh that arrives while one is in flight joins it, and each joining guest gets the same answer in its own placeholders. The exchange runs past the leader's cancellation, for at most 30 s, so a token that was spent is still committed. | CLK-7 | none |
| MIG-4-plan-login-a8 | **The injected token is redacted** from the answer's declared headers and from its streamed body. Only a tail that could begin the token is held back, so a stream is delayed by at most a partial match. An encoded answer, which the redactor cannot read, is refused. | CLK-4 | none |
| MIG-4-plan-login-a9 | **`SignedIn(guest)` is the sign-in's only success signal**: this guest's own code exchange committed the login. A login stored earlier does not count, and neither does anything the guest writes or its exit status. | CLK-7, ONB-3 | none |
| MIG-4-plan-login-a10 | **A refresh answer is judged only against the login it was made for** (#3105 Security 1). The login has a generation that `Remove` and every sign-in commit move. A refresh flight records it and resolves the token it sends in one step, under the commit lock, so the answer is judged against exactly the login whose token it spent. An answer that comes back after the generation moved is dropped (`plan-stale`): it is not committed, and it stops nothing, whether it is good, refused or out of shape. Otherwise the owner's own sign-out or account switch, raced by a guest's refresh, would leave a release-only stop. | CLK-7 | none |
| MIG-4-plan-login-a11 | **The code shown to the owner is the one the clerk forwarded** (#3149). A device step that declares `UserCode` is read whole (at most 64 KiB) and its answer's top-level string at that key (Codex: `user_code` on `usercode`, as the #809 stub and CLI answer it) is recorded for that sign-in guest (`UserCode`); the run side shows a printed code only if it equals it. So a CLI that reformats the code (case, separators) fails every sign-in as `signin-code`: the live qualification (`spikes/S8-live/qualify.py`, run by `run.sh plan`) checks that the code the CLI prints, read as the run side reads it, equals the answered `user_code` (#3180 item 3). | CLK-7, PLN-5 | A CLI that reads the code under another key is a declaration change. |
| MIG-4-plan-login-a12 | **`Forget` is final** (#3149). It takes the commit lock, so it waits out a commit in progress and reports whether this guest's sign-in committed; a code exchange that answers after it is dropped (`plan-ended`) and stores no login. Its answer is still judged for shape first, as every token answer is (a5): a late 200 that is out of shape, names no account or lacks either token records an `unswappable` stop, which fails closed (#3180 item 1). An approval that lands after the owner's wall is therefore never stored behind a sign-in reported as timed out. | CLK-7 | none |
| MIG-4-plan-login-a13 | **No sign-in secret reaches the guest** (#3111, from #3105 Security 3). A device step declares the answer keys that redeem the sign-in (`Secret`; Codex: `device_auth_id` on `usercode`, `authorization_code` and `code_verifier` on `devicetoken`), and each is swapped for a fresh placeholder of that sign-in guest, held only in the clerk's memory. A step that `Takes` one (the poll's `device_auth_id`, the code exchange's `code` and `code_verifier`) is refused before anything is sent unless the key carries that guest's own placeholder for that secret, and goes out with the real value. So the clerk redeems only a code it was given itself, for the device session whose user code it recorded. Every device step is read whole (64 KiB) and passes an error answer's status only (the CLI reads only the status while it polls, and treats any other error as failed), and an answer that lacks a secret, or carries the value of any secret the guest holds (new or earlier, as is or JSON-escaped) anywhere else, body or passed header, is dropped (`plan-secret`) and stops nothing. A device answer body passes only as the clerk's own encoding of a JSON object, so an escape has one written form; a code exchange answer that carries one is dropped before the login is stored. `New` refuses a code exchange that does not take its code and verifier from a device step. The secrets go when the code exchange commits or the guest is forgotten. `code_challenge` passes: it is the verifier's public hash. | CLK-1, CLK-7 | A CLI that reads a pending poll's body, or a provider that sends the code by another route, is a declaration change. |
| MIG-4-plan-login-pin | **A refresh body is exactly the CLI's own, with its fixed values** (#3110, from #3105 Security 2). `Declaration.Refresh` maps every refresh key but `refresh_token` to the one value the CLI sends; a body with another value, a missing or extra key, or a non-string is refused before anything is sent (`plan-placeholder`), so a guest cannot shape the provider's answer into an `unswappable` stop. Codex: `client_id` `app_EMoamEEZ73f0CkXaXp7hrann` (the public `CLIENT_ID`) and `grant_type` `refresh_token`, as JSON, and no `scope`: read from codex-rs at tag `rust-v0.162.1` (`login/src/auth/manager.rs` `request_chatgpt_token_refresh`, `login/src/oauth/client.rs` `refresh`, which sends no `scope` and no `resource` there), and the ID found in the pinned `codex-0.162.1-linux-x64` binary (npm tarball matching `CODEX_INTEGRITY`). The issue asked for a capture; the source of the pinned tag is the CLI's own request builder, and `run.sh plan` now captures the live body and `qualify.py` checks it against the declaration at the next supervised run. The CLI reads `CODEX_APP_SERVER_LOGIN_CLIENT_ID` to override the ID; the guest image does not set it. A refresh's headers are declared the same way (`RefreshHeaders`, #5089): the clerk sends its own `Content-Type` and `Accept-Encoding` and the declared values, and none of the guest's, so no guest header (`Accept`, `Chatgpt-Account-Id`, ...) shapes the answer either. Codex: `Originator` `codex_cli_rs` (codex-rs `login/src/auth/default_client.rs` `default_headers`); the CLI's `User-Agent` names the guest's OS, so the clerk sends none, as the CLI's own device steps to the same host send none (`create_raw_auth_client`). A code exchange's `client_id` must be the refresh's (`checkCode`). | CLK-7 | A CLI bump that changes the body, the refresh headers or the code exchange's `client_id` is a declaration change, caught by `qualify.py` (which reads the declaration through `codexdecl.go`) on the requalification run. That the auth host serves a refresh without a `User-Agent` is read from the CLI's device steps, not yet from a clerk refresh. |

## MIG-4-plan-login-b: the guest's model endpoint and metering

| ID | Assumption | Spec basis | If it changes |
|---|---|---|---|
| MIG-4-plan-login-b1 | **A model call's body is held to the CLI's declared shape** (the old core's `checkResponses`, measured on Codex CLI 0.162.1, #809): only declared top-level keys, input item types and content part types; tools only in a top-level `tools` list, an `additional_tools` input item or a declared namespace, each one the CLI's own and of a client-side type (`namespace`, `function`, `custom`); `store` declared and forced to false on every call; `stream` declared and required to be `true` (`Body.Stream`), so the answer is the event stream whose usage is metered and the guest cannot choose the byte-count meter (#3128 Security 1); `tool_choice` a word or a client-side type; and no content source by address (only inline `data:` URLs); only a function tool's `parameters` schema is not looked inside. The clerk sends its own re-encoding, so the provider parses exactly what was checked. A declaration that lists a hosted key (background runs, provider-held prompts or conversations, server-side tool sources) or a hosted tool type is refused at `New`, as is a model endpoint with no body shape. A refusal names its rule, never a value (`plan-body <rule>`), and nothing is sent. | PLN-5(a), CLK-7, CLK-4 | A CLI release that sends a new key or tool is a declaration change, qualified with that release. |
| MIG-4-plan-pins-1 | **The body is measured on the pinned CLI, and `client_metadata` holds only the keys it sets** (#2115, #2117). The Codex declaration's `Version` is `codex-<CODEX_VERSION>-<n>`, tied by `TestCodexBodyIsMeasuredOnThePinnedCLI` to `guest/codex/build-rootfs.sh`, so a CLI bump requalifies the body in the same change. `Body.Meta` lists each `client_metadata` key with a byte cap; any other key, a longer value or a non-string is refused (`plan-body meta`). The Codex keys are the ones CLI 0.162.1 sets on an HTTP model call (codex-rs `core/src/responses_metadata.rs`): the installation, session, thread, window, turn, parent and root ids and the sub-agent label, at most 128 bytes each (the clerk's own cap: the CLI bounds none of them, and `x-openai-subagent` can carry any label), and `x-codex-turn-metadata`, a JSON blob of the turn's workspaces and tool list, at most 16 KiB (estimated at under 4 KiB for the 11 declared tools, not measured; its content is MIG-4-plan-pins-2). `mcp_attribution` is not declared: the image's requirements block MCP servers, so the CLI should not send it, and if it does the call is refused. The WebSocket-only keys (`traceparent`, `tracestate`) are not declared, since the managed config keeps WebSocket off. | PLN-5, CLK-7 | A turn blob over 16 KiB, measured on a live run, raises its cap by review; a CLI that sends a new key is a declaration change. |
| MIG-4-plan-pins-2 | **The turn metadata blob holds only what CLI 0.162.1 puts in it, and asks the provider for nothing it may not do for the plan** (#4580). `x-codex-turn-metadata` is a JSON text held to `CodexTurnMetadataPayload` (codex-rs `core/src/responses_metadata.rs`): every key optional except two, a function entry's `source` (#4678; the CLI always serializes it) and `kind` inside `source` (#4652); any other key refused, each value of its kind (text within a cap, a closed word list for `request_kind` and `compaction`, integer, bool), and its maps (`tool_namespaces_info`, `functions`) with capped keys; `workspaces` is dropped unread (MIG-4-plan-workspaces). `history_ingest_requested` and `analytics_enabled` may only be false: the image turns analytics off, so the CLI sends `analytics_enabled: false`; `history_ingest_requested` comes from `use_history_notes_extension` (session.rs `with_window_and_fork_metadata`): three paths turn it on. A config layer sets it under `[features] token_budget`; with no `token_budget` in any layer, the model catalog's token-budget defaults turn it on (token_budget.rs `apply_model_defaults`); and the `context_management` feature force-enables `token_budget` for a plan login whatever any layer sets it to (`apply_experimental_context`). The image's managed config pins both features off (#4595, `tests/test_codex_worker.py`): the `token_budget` pin closes the first two paths, and only the `context_management` pin closes the third, so neither pin stands in for the other. A correct CLI therefore sends it false; a CLI that sends it true is refused (fails closed). A tool's `source` must state its kind, and the kind may only be `harness`, since the image blocks MCP servers (#4652: a source with no kind is refused, not read by the provider's default); a config-supplied extra key is refused, since the image sets none. The clerk sends its own encoding of the blob it checked, so a repeated key cannot show the provider a value the clerk did not check, and the 16 KiB cap holds on that encoding too. The shapes are read from source, not a capture; `mcp_attribution` and `guardian_credits_requested` stay undeclared: the CLI adds `mcp_attribution` only when the provider's `include_internal_metadata` holds or its base URL is `https://` on an OpenAI host (model-provider `provider.rs`). The forwarder's base URL is `http://`, and the flag is runtime-only: `#[serde(skip)]`, so no config layer can set it (upstream test `runtime_internal_metadata_opt_in_is_not_serialized_or_configurable`), and only the built-in `openai` provider sets it. So the image has nothing to pin, and it is refused if sent (#4595). `TestPlanGuestCannotAskTheProviderToKeepOrAct` pins these refusals from literals. | PLN-5, CLK-7 | A live capture (#809, #3133) that shows another key or value fails closed (every turn refused) and is added by review. |
| MIG-4-plan-workspaces | **The provider never sees the guest's workspaces** (#4632). The turn blob's `workspaces` map carries the guest's repository paths (as keys), git remote URLs, latest commit hash and dirty flag; repo names and paths can name a private project, and a turn needs none of it. Its declaration is `KindDrop`: the clerk takes the key in any shape and deletes it from the blob it re-encodes, so it never reaches the provider. The provider already takes a blob without it: CLI 0.162.1 omits the key whenever it finds no git repository or before its async git read finishes (codex-rs `core/src/responses_metadata.rs` `non_empty_workspaces`, `core/src/turn_metadata.rs` `git_workspaces`); read from source, not a capture. `TestPlanTurnMetadataSendsNoWorkspaces` pins it from literals; `TestDropIsOnlyABareField` holds a drop shape to a bare object field. | PLN-5, CLK-7 | A live capture (#809, #3133) in which the provider refuses or degrades a turn without `workspaces` from a git checkout reopens this by review. |
| MIG-4-plan-login-b2 | **Every model call is metered, and one with no meter is refused** (`plan-unmetered`). `Do` calls the model clerk's `Meter` with the checked body after every other check has passed and before any byte is sent; its refusal is the call's answer. The settlement it returns is called exactly once: at the answer's end, at a read error, at close, or at once when no answer passes (a dial error, an encoded answer). | LOG-7, CLK-7 | none |
| MIG-4-plan-login-b3 | **Usage is what the stream's last event reports** on the clerk's own connection: `response.completed`, `.incomplete` or `.failed`, with whole `input_tokens` and `output_tokens` of at most 1e12. An event line over 4 MiB is passed on unread, and an answer that is not an event stream is not read for usage; either is then metered by the model clerk's own rules (MIG-4-plan-login-b6). `Sent` is false only for a call that never had a connection (net/http's `GotConn` never fired): a dial the home-network policy refused, or one held and then cancelled or past its deadline (#5108). A call cancelled after it had one counts as sent, even if no byte left, so the error is an over-count. `Done` is a 2xx event stream read to its end; any other answer is never done, so it is metered at its worst case. | LOG-7 | A non-streamed answer's usage would need its body buffered. |
| MIG-4-plan-login-b4 | **One plan, one pool, read as its tightest window** (RES-5, MIG-4-spend-b9). Codex states two rate windows of one pool (`X-Codex-Primary-*`, `X-Codex-Secondary-*`, 5 hours and a week). The reading is the window with the highest use, per mille rounded up, with that window's reset (unix s to ms); a tie takes the later reset. A reached limit (`X-Codex-Rate-Limit-Reached-Type`) reads as full, at the latest reset stated. A window whose use does not parse is no reading of it, and a missing or unreadable reset is 0, which the model clerk turns into its clock plus the declared window (`PoolWindowMS`) when it settles the call. The credits headers are not read. | RES-5 | A pool per window would need a route per window. |
| REV-PROOF-corpus-deny-fu-1 | **One pass list and one value check, in `clerk/header`** (#5278). The names a plan route may pass (`Names`) and the check on a declared header value (`Value`: not empty, visible ASCII and spaces only, no leading or trailing space) live in their own package, which this clerk, the model clerk and the old core's egress all use, so the lists and checks cannot drift. It is outside the trusted core. The only text it parses is its own embedded vendor list (`vendors.txt`), never bytes a guest or provider writes, so the trusted-base registry classes it inert. `Value`'s error names the rule that fired, and both clerks put it in their refusal. The model clerk names no provider (CLK-14). Egress (old core, D-139) checks a plan route's names against the same list byte for byte, passes an answer header only by a declared name that `header.Answer` takes, and holds a key check's values to `Value`; its corpus tests are one compact test in `egress/worker_test.go` (`TestEgressRefusesTheHeaderCorpus`), because the old-core ratchet counts every line under `broker/egress` and every import of egress from outside the old core. | CLK-3, CLK-7, CLK-14 | A second plan CLI's names join the one list, and every user of it is re-reviewed. |
| REV-PROOF-corpus-deny-fu2 | **An answer header passes only by its exact name, never one naming a credential, and the vendor names are data** (#5291, #5320). There are no answer prefixes: a declaration lists each answer header, the ten `X-Codex-` quota headers the pinned CLI reads among them, and `New` refuses one that `header.Answer` refuses: not on the list, or holding one of the header corpus's credential words (key, token, auth, secret, session, csrf, xsrf, signature, password, cookie, credential) in any case. So `X-Codex-Session-Token` or `X-Codex-Bearer` never reaches the guest (CLK-1), and `Session_id` may be sent but never comes back. The clerks and egress's `forbiddenHeader` refuse by that one word list (`header.Credential`). The list is unexported and `Names` hands out a copy, so no importer can widen it at run time. The generic names (Accept, Content-Type, User-Agent, Retry-After, X-Request-Id) stay in code; the vendor's names are a vendor-owned data file, `clerk/header/vendors.txt`, embedded at build (CLK-14), where a `#` starts a comment anywhere on a line and a name holding `*` is dropped. It sits here, not in `ghbmrk/agentos-private`, because the Codex declaration it serves is in this repository; moving the declaration moves the file with it. Every refusal names its rule: not on the allowlist, the clerk's own Content-Type, an empty, padded or control-character value, or an answer name naming a credential. | CLK-1, CLK-4, CLK-7, CLK-14 | A new quota header the CLI reads is not passed until review adds its exact name; one whose name holds a credential word cannot be passed at all. |
