# Assumptions: inbox slice (#2526, MIG-3)

What the slice rests on. Each line is a choice made to keep the slice small; none changes a requirement.

| ID | Assumption | If wrong |
|---|---|---|
| MIG-3-1 | The slice runs under the eval adapter natively and, in the image workflow, inside the booted QEMU image (#3117): `image/ci_boot.sh`'s slice boot runs a CI-built static `cmd/slice` from a read-only 9p share, with no network, over every request `image/slice_boot.py` writes, and the host checks the guest's outcomes with the harness. The image itself does not carry the slice: the kernel, planner and clerk are pure Go over `MemStore` and read nothing of the host. | Once agentosd starts the kernel and the mail clerk in the image (#2682 and the agentosd chain), run the cases through the image's own units instead of the shared binary. |
| MIG-3-2 | Keys and the clock are fixed (seeded ed25519 keys, ChaCha8 nonces, 2026-10-19 09:00Z). Two runs give one log, so the eval's replay check is exact. | None: production uses TPM-sealed keys and the real clock (D-141). |
| MIG-3-3 | The owner's first tap issues one standing root key (organize, trash, unsubscribe) to the holder. The planner gets that key narrowed with the hold caveat (600 s base, 24 h novelty); it cannot lift the hold. | A key without the caveat would dispatch irreversible steps at once; `Next` would not hold them. |
| MIG-3-4 | Earlier unsubscribes are replayed as steps already done under a root issued before the oldest one, so their senders are not novel. The real kernel gets this from its own log; the eval supplies only `prior_unsubscribes`. | A sender's first unsubscribe in the real log is novel as soon as it is the first. |
| MIG-3-5 | The planner sees a mail id, its class and, when VRB-2 holds, an opaque sender handle: `sender-` + 32 hex (128 bits) of HMAC-SHA256 of the address under the account's secret (at least 128 bits; `NewAccount` refuses less). The handle is also the kernel `Recipient` that novelty is judged on. It sees no header, body or address. One unsubscribe step goes out per handle. | Two senders sharing a handle needs an HMAC-SHA256 collision on 128 bits. A leaked secret lets its holder compute handles from addresses, not read them back. The eval fixes the secret so a run replays; a real account draws its own and keeps it with the clerk. |
| MIG-3-6 | One plan per action. A refused step rejects its whole plan (KRN-3), so grouping would let one refusal cancel the rest. | None; plans are cheap. |
| MIG-3-7 | The clerk treats trash on an account whose trash is kept fewer than 7 days as `delete-remote` and refuses it, because the trash is not then a restore point. The 7-day floor is SPEC VRB-2's trash rule. The clerk also trashes only mail the reader classes as spam or phishing. | A reader that misclasses a real mail as spam still trashes it, undoably, within retention. |
| MIG-3-8 | The organizational domain is the public suffix, by the Public Suffix List with its private part (golang.org/x/net/publicsuffix, already vendored), plus one label; a public suffix itself, an IP address (bracketed too) or an empty domain has none and aligns with nothing, and matches no provider-table entry (`TestAlignmentUsesThePublicSuffixList`). The lookalike check folds the sender's whole domain and refuses it when it reads as a known sender's or contact's organizational domain or a name under it while being another organization, since its own organizational domain can stop short of the part that imitates (`shop.rnyshopify.com` against `shop.myshopify.com`, `barclays.c0.uk` against `barclays.co.uk`; `TestLookalikeFoldsTheWholeDomain`). Fixture domains sit under the reserved `.test`, which the list's default rule treats as one suffix, as before. | The list is the one vendored with golang.org/x/net; a suffix added since then is read as one label shorter, so two sites under it align until the module is updated. |
| MIG-3-9 | The class of each mail comes from a fake reader. A real reader is a separate row. | The planner's output is a function of class only, so a better reader changes no code here. |
| MIG-3-10 | An alert (a bank or security notice) is never unsubscribed (only `bulk` is) and never trashed (only spam and phishing are), whatever the planner asks: both checks are the clerk's. The synthetic mailbox has no alert mail and the eval set is not edited here, so only the unit tests exercise it. | A real alert the reader misclasses as phishing is trashed, undoably. Follow-up: #2604 (MIG-3-R5). |
| MIG-3-11 | The in-process planner (`Plans`) stands in for PLN-5's `plan` command. It reads only the clerk's listing, as the command would. | The real command replaces `Plans`; the kernel, keys and clerk do not change. |
| MIG-3-12 | The unopened and first-mail ages are 90 days, a constant of the clerk (D-141). A sender with no `last_opened` entry has never been opened, so it is eligible once the first-mail age holds; an entry that is not a date, or a `today` that is not a date, makes the mail ineligible (`bad-date`). | A reader that drops opens it saw would unsubscribe a sender the owner reads. The real reader must report every sender it has seen opened. |
| MIG-3-13 | Eligibility is judged again when the hold ends: `Do` re-runs VRB-2 on the clerk's copy of the mail against the world as it is then. | A mail the owner opens during the hold is not unsubscribed. |
| MIG-3-14 | `Do` acts only on a request `State.Dispatched` answers for: the exact plan the log admitted, with that step in flight now. A request carries only the plan and the step index; the clerk takes the dispatch and hold from the log and the time from its own `Clock` (MIG-2-rel). A direct call that is not a dispatch cannot write the kernel's log, so the clerk records its refusal in its own list. | A clerk clock that drifts from the kernel's refuses a held step the kernel released early, never the reverse. |
| MIG-3-15 | The daily cap of 200 (VRB-2) counts organize and trash only, not unsubscribe, and is the key's, not the planner's. `PlannerKeys` derives two sibling keys from the root: one with `LimitVerbs(Organize, Trash)` and `LimitRate(DailyCap)`, one with `LimitVerbs(Unsubscribe)` and the hold. The cap is therefore checked at the clerk, counted from the log, and survives a restart; `kernel/key` gains no caveat. `Plans` still spends trash first and stops at the cap, and what it puts off comes back as one STATUS line counted by action. | A planner that ignored the cap is stopped by the clerk at the 201st action. The count is per key link and a key is used only with its last holder's signature (KRN-possession), so a planner cannot strip its key back to the root or derive a sibling from it; a second cap exists only if the home clerk, the root's holder, derives one. |
| MIG-3-16 | Labels live under `agentOS/` (VRB-2): `Do` refuses any label but exactly `agentOS/` plus the class the clerk assigned to that mail (`bad-label`), whatever the key allows, so the clerk never writes into the owner's own labels. | A provider with no nested labels needs a flat prefix. |
| MIG-3-17 | A sender with one eligible bulk mail and another mail classed spam, phishing or personal is still unsubscribed; eligibility is per mail found first. | Narrowing per sender is a later item: #2605. |
| MIG-3-18 | The eval's `keys_at_end` is read from the root key (signed for by its holder, the home clerk) and `owner_taps` from the log's widening entries, so a widened key or a second approval fails the eval. | None. |
| MIG-3-19 | **A DKIM pass counts only while current (#2602).** RFC 6376 `t=` and `x=` are read as at most 12 digits; a malformed one, or an `x=` not later than `t=`, fails the signature (`dkim-fail`). The world has only a day, so a signature counts only if signed before the end of that day (UTC) and not expiring before it: one that expires at any hour of today, or was signed tomorrow, is `dkim-not-current`, and a signature carrying either tag on a world whose day is unreadable is `bad-date` (`TestDKIMSignatureMustBeCurrentOnToday`). Verifying stays clock-free; `Evaluate` judges the day. | A signature expiring late today is refused a day early, which only delays an unsubscribe. |
| MIG-3-20 | **Domains compare in IDNA A-label form (#2602).** Every domain VRB-2 compares (the From domain, `d=`, the URL host, provider-table entries, history and `last_opened` addresses) is lower-cased and converted with golang.org/x/net/idna's registration profile, newly vendored with x/text's norm and bidi tables, so a Unicode name and its punycode are one name, and `last_opened` entries in either form all count (`TestIDNDomainsCompareInALabelForm`). A `last_opened` key the registration profile refuses falls back to IDNA's lookup mapping, so an open recorded under a fullwidth From still counts, since counting more opens only refuses more. A provider-table entry is compared as written (in A-labels) with the URL host's organizational domain, never widened to the entry's own organization. The registration profile maps nothing: a name with fullwidth or other mapped characters, an underscore, or an invalid punycode label has no organizational domain, so it aligns with nothing and fails closed (`dkim-unaligned`). A `d=` is looked up in A-labels (RFC 8616 section 4). | A legitimate sender whose domain IDNA refuses is never unsubscribable. |
| MIG-3-21 | **The lookalike fold is UTS #39's skeleton (#2603).** `skeleton` is NFD, each code point to its prototype in Unicode's confusables.txt 17.0.0 (SHA-256 `091c7f82fc39ef208faf8f94d29c244de99254675e09de163160c810d13ef22a`, from unicode-org/unicodetools `unicodetools/data/security/17.0.0/`, generated into `confusables_table.go` by `confusables_gen.go`), NFD, then lower case and the letter pairs confusables.txt leaves out (`w` to `vv`, `d` to `cl`), repeated to a fixed point (at most 4 rounds). Lower-casing after the mapping keeps `0` (to `O`) equal to `o` and `I` (to `l`) equal to `l`; `rn`/`m`, `0`/`o` and `1`/`l` from the old pair list are all in the table. Both the From domain as written, in its own case, and its U-label are folded against the known domain's U-label, so punycode and lower-casing hide nothing (`TestLookalikeUsesTheUTS39Skeleton`, `TestEvaluateRefusesALookalikeWrittenInCapitals`). There is no mixed-script check: a whole-script confusable that maps to no known domain is not refused. | A confusable outside confusables.txt and the two pairs (`ii`/`u`, `nn`/`m`) is unsubscribed from; add it to `readAlike`. |

## Live mailbox (MIG-4-mail-a, #2574)

What the mail clerk's live mailbox rests on. `broker/clerk/inbox/imapsmtp` is the clerk's IMAP and SMTP transport, moved from `broker/mail/imapsmtp` with its tests; `Live` (`mailbox.go`) is the mailbox over it and `Synthetic` the eval's.

| ID | Assumption | If wrong |
|---|---|---|
| MIG-4-mail-a-1 | **One transport, two transitional shims.** `broker/mail/imapsmtp` converts the transport's raw messages to `broker/mail`'s parsed ones and `broker/mail/mailtest` names the transport's test server; neither holds logic of its own. 2574b deletes both with `broker/mail`, once sub B's `corpus` and `cmd/agentosd` stop importing it (docs/LANES.md). | A shim that grows logic is a second copy; 2574b must find them empty. |
| MIG-4-mail-a-2 | **No side door.** A mailbox is called only from `Do`, after `State.Dispatched`, `clerk.Check` and the clerk's own rules (class, label, retention) pass, so an IMAP change is a checked, logged step like an exit request. `Read`, which lists and fetches the inbox, is the clerk's own upkeep and not a step, as the exit's token refresh is (MIG-4-exit-i). Every dial goes through `netguard.Policy.DialContext`, or to a literal loopback address in `Plain` mode for the test server only. | A path that called the mailbox outside `Do` would act without a key. |
| MIG-4-mail-a-3 | **Reads change nothing.** `Read` fetches with `BODY.PEEK`, so no mail is marked read (SPEC "Read state"), and reads the newest `DailyCap` inbox mails: one day of the clerk's organize and trash effects, so memory stays within `DailyCap` times the transport's `MaxFetch` (256 KiB). | An inbox past `DailyCap` unread mails leaves the older ones for a later read. |
| MIG-4-mail-a-4 | **A live mail is unclassified.** The mailbox gives a mail its id and raw text, never a class; the reader that classes mail is its own row (MIG-3-9). The planner skips an unclassified mail, and `Do` refuses an organize or trash of one (`unclassified`), so no label `agentOS/` alone is ever written. A class outside the closed list (bulk, spam, phishing, personal, alert) also leaves the mail unclassified, so a class never carries text into a label or a mailbox command. | Until a reader is wired a live account is read but not acted on. |
| MIG-4-mail-a-5 | **Organize is an IMAP keyword.** The label `agentOS/<class>` is set as a keyword on the mail where it is, so organize hides nothing. A server that does not keep keywords fails the read-back. Gmail's own labels (`X-GM-LABELS`) are a later item. | Organize is unknown on every step for such a server and the kernel parks it. |
| MIG-4-mail-a-6 | **Trash is a UID MOVE to the trash-role folder, never an EXPUNGE.** A server without MOVE (`no-move`), an account with no trash-role folder (`no-trash-folder`) and a folder renumbered since it was read (`renumbered`) are refused before acting. | A COPY, flag and EXPUNGE fallback would also remove mail the owner marked deleted. |
| MIG-4-mail-a-7 | **An effect counts only when read back (OWN-13, KRN-8).** A label counts when the mail's flags show it; a trash when the mail is gone from where it was under the same UID validity and a copy with its Message-ID arrived in the trash with this move: at or above the trash's UIDNEXT read just before it, under the trash's UID validity then (`FindSince`; `TestFindSinceSeesOnlyWhatArrivedSince`, against a test server that answers `n:*` with the last UID as RFC 3501 does). The mark is the one from before the mail's first move, kept for its resends until the next inbox read, so a move that landed but whose answer was lost is confirmed by the resend's read-back (`TestLiveResentTrashIsConfirmedByTheFirstMove`); after a re-read the moved mail is no longer in the inbox, so such a resend is answered `unknown-mail` though the mail was trashed (fail closed; a reason of its own is a later item), and if the trash is renumbered or another folder becomes the trash meanwhile, it parks (fail closed). A trash copy confirms one trash only: `Live` keeps the copies that confirmed one, so another mail with the same Message-ID whose own move was lost is not confirmed by it (`TestLiveTrashCopyConfirmsOneTrashOnly`). Two windows stay open, both needing the server to lose a move: a copy with the same Message-ID that the owner or another client files into the trash between the mark and the read-back, or one a second lost-answer move of a duplicate left unclaimed, confirms the lost one. Only the moved UID (UIDPLUS COPYUID, which go-imap v1's MOVE does not return) would close them. A trash whose server gives no UIDNEXT or UID validity is refused before moving, `NotDone` `no-uidnext` (`TestLiveTrashWithoutUIDNextIsRefusedBeforeMoving`). So an older copy already in the trash does not confirm a move the server lost (`TestLiveReadBackCatchesAnEffectTheServerDidNotKeep`, #2665), and the substring search the server runs on a sender's Message-ID looks only at mail that arrived since. A mail with no Message-ID cannot be found there, so its trash stays unconfirmed. An unconfirmed effect is `unknown` and not recorded as done. `Probe` answers from the clerk's memory: `notdone`, inviting a resend, only for organize and trash, which are idempotent (the keyword is set again, the moved mail is confirmed by the same read-back), and only until the step has made `kernel.MaxChecks` mailbox calls; then `unknown`, so the kernel parks it. An unconfirmed unsubscribe is never sent again (`unknown` at once): a one-click POST is not idempotent. | A probe that read the mailbox could settle an unknown step instead of parking it. |
| MIG-4-mail-a-8 | **The credential is the caller's.** `Live` takes the transport's `Credential` function and keeps nothing. Binding it to a sealed `clerk.Secrets` static slot belongs to the row that runs the clerk in a process, with MIG-4-exit's rewiring of `cmd/agentos-egress` (#2571), because `Secrets` opens a slot only inside `broker/clerk`. | Until then no process runs the live clerk. |
| MIG-4-mail-a-9 | **A live unsubscribe goes only to a public HTTPS name (#2601), and is on (#2841).** `NewLive` gives no `Poster`, so a mailbox made with it alone refuses live unsubscribes (`no-poster`). `(*Live).WithPoster` turns it on, with a `Poster` on the store's own address policy (`imapsmtp.Store.Guard`, DEV-2), so the POST reaches no address the mail servers could not (`TestLivePostsThroughTheStoresPolicy`); `clerk/run` calls it (`TestTheClerksMailboxHasAPoster`), now that a failing `Opened` read hands back the read mail it found and the clerk keeps it (MIG-3-R10b, run ASSUMPTIONS MIG-4-run-q), so after `ErrTooMuchReadMail` and the owner's deleting, a sender read within 90 days does not look never opened (#2830 L3 finding 1). The URL is parsed with `net/url` and must be `https`, port 443 (or none), to a DNS name of at least two LDH labels (no address literal, and no all-digit last label), with no userinfo, fragment, backslash, whitespace, control or non-ASCII byte, at most 2048 bytes, and its host must be the one VRB-2 aligned (`urlHost`), so no parser differential moves the POST to another host; anything else is `bad-unsubscribe-url` (`TestPosterRefusesBadURLShapes`, `FuzzPostURL`). The name is resolved once, every answer is checked (one special or home-network answer refuses the name: `egress-refused`, `TestPosterRefusesPrivateAnswers`) and the connect goes to a checked literal, so a second answer cannot rebind it (`TestPosterSendsOneClickToAPublicName`). No proxy, no User-Agent, HTTP/1.1, one connection, 30 s, response headers to 16 KiB and 4 KiB of body read. No redirect is followed, and a redirect or any non-2xx answer is unconfirmed, so the unsubscribe is never sent again (`TestPosterFollowsNoRedirect`); a POST that never got a connection (a name that does not resolve, a certificate that does not verify) is `post-not-sent`, nothing sent (`TestPosterSendsNothingWithoutAConnection`).  | A one-click endpoint that answers 3xx after acting is reported unconfirmed, not done: the owner sees an unknown outcome, never a second POST. `Do` holds the account's lock across the POST (MIG-4-mail-a-10), so a slow endpoint holds that account's other steps up to 30 s. |
| MIG-4-mail-a-10 | **One step at a time per account.** `Do` holds the account's lock across its mailbox call, at most the transport's per-operation timeout (60 s) per round trip. | A busy account waits; nothing runs twice. |
| MIG-4-mail-a-11 | **Flags are atoms.** go-imap writes flags into the command unquoted, so the transport refuses, before connecting, any flag in `SetFlags` or `Append` that is not an RFC 3501 system flag or a keyword atom (`ErrBadFlag`, the clerk's `bad-flag`). A space or a line break cannot add a flag or a command, whoever supplies the flag: the clerk, or the old adapter through the shim. The live mailbox also refuses, as `bad-flag`, any label that is not one of the clerk's `agentOS/` keywords, so a system flag such as `\Deleted` is never a label. | A flag with a space in it would need a quoted form IMAP does not have; none is used. |
| MIG-4-mail-a-12 | **A cheap change check (#2742 item 1).** `Live.Mark` lists the folders and asks each one's STATUS (UIDVALIDITY, UIDNEXT, MESSAGES, UNSEEN, and HIGHESTMODSEQ where the server has CONDSTORE, RFC 7162, `TestMarksCarryHighestModSeqUnderCondstore`) in one session, through `imapsmtp.Store.Marks`; it fetches no mail. A caller takes the `Mark` before a full read and keeps it once the read is done, whether it succeeded or failed for good (`ErrTooMuchReadMail`, so a lasting failure is tried again only when the owner's changes move the mark), and reads again only when `Mark.Same` says the mailbox changed, an error leaves no mark, or a ceiling well under 90 days has passed (`Opened` also moves with the day): mail arriving or leaving in any folder, a read or unread change in the unread count, a folder added, removed or renumbered (`TestMarkChangesExactlyWhenTheMailboxDoes`). `Same` fails closed: an empty mark, or a folder with no UID validity or next UID, is never the same (`TestMarkSameFailsClosed`), a folder whose STATUS fails gives no mark (`TestMarkFailsWithAFolder`), and nor does a STATUS reply that leaves out an item asked for, since a missing count reads as 0 (`ErrPartialStatus`, `TestMarksFailClosedOnAPartialStatus`). | Without CONDSTORE, one mail read and another marked unread together, with nothing else changed, leave the mark the same (`TestMarkWithoutCondstoreMissesASwappedRead`), so a caller still reads again after a ceiling; a server with CONDSTORE that keeps no mod-sequences for a folder (NOMODSEQ) is the same case. |

## Mail reader (MIG-4-mail-reader, #2654)

What the reader that classes live mail rests on. `Read` (`reader.go`) classes mail through an `Ask`, the quarantined model call; the alert guard (`alert.go`) is the clerk's.

| ID | Assumption | If wrong |
|---|---|---|
| MIG-4-mail-reader-1 | **The reader returns a class or nothing (PLN-2).** `Read` asks one fixed question with the mail after it, at most 16 KiB of the mail, and takes a reply only when it is exactly one class of the closed list, up to case and surrounding space; any other reply, or a failed or refused call, leaves the mail unclassified. Injected text can at most choose a class, and every class still meets the clerk's rules: trash only spam and phishing, unsubscribe only bulk under VRB-2, never an alert. `Ask` is bound to the model clerk (CLK-7), which admits and meters each read on the reading plan's key; which route reads (the local model once it passes HLD-3, else an API route the owner allows private data on, D-141) is the mail clerk's step-4 wiring's choice (D-139 step 4). | A reply format the model does not follow leaves mail unclassified: nothing is acted on and each one is recorded (-4). |
| MIG-4-mail-reader-2 | **The alert guard's first net is the clerk's (#2604, #2681).** A mail is an alert when the topmost Authentication-Results header is the provider's own (`World.AuthServ`), every DMARC result in it passes aligned with the From domain, the mail has one From header naming one address, and the sender is one the owner keeps as an alert sender (`World.AlertSenders`: the provider's security sender, services the owner holds an account with, senders marked financial or identity; an address, matched exactly, or a domain and its subdomains). A header whose DMARC results conflict, or a mail with two From headers or addresses, is never an alert by its sender, so a forged alert cannot reach the owner as one from a trusted sender (`TestTheSenderNetFailsClosedOnAmbiguousMail`). The From is unfolded and an encoded-word name in any charset is read as raw bytes before it is parsed, so a folded From or a windows-1252 or ISO-2022-JP name still names one sender (the same test's controls). The clerk refuses to trash an alert (`alert`) and gives no unsubscribe handle for one, whatever the reader said (`TestTheGuardHoldsForPhishingAndMatchesAddressesExactly`), and reads the world when the step runs, so a sender added later is guarded too. The guard never switches off silently: with no authserv-id or no alert sender the clerk trashes and unsubscribes nothing (`no-alert-guard`) and hands the planner no sender handle (`TestAnAccountWithoutAlertInputsRefusesTrash`). The mail clerk's step-4 wiring fills both, with no owner typing (#2832). SPEC sends an alert's trash to approval as `change-account`; until that path exists the clerk refuses it (`alert`). | Microsoft 365 and Outlook write Authentication-Results with no authserv-id, so on those accounts no header is the provider's and only the wording net guards, until #2832 adds a per-provider rule. An alert sender missing from the list is guarded only by the wording net and the class rules. A From that still does not parse, such as `Acme, Inc. <notice@bank.test>` with its comma unquoted, is not an alert by its sender: which address it names is ambiguous, so a real alert with such a header is guarded only by the wording net. Until #2832 lands a live account trashes and unsubscribes nothing. |
| MIG-4-mail-reader-3 | **The second net: alert wording or a code, whoever sent it (VRB-2, #2681).** `wordingAlert` reads the decoded subject and every text/plain and text/html part (quoted-printable and base64 decoded, HTML tags dropped and entities decoded, at most 64 parts and 64 KiB; a mail that does not parse is read whole) and calls the mail an alert when it carries one of broker/mail's `AlertPhrases`, one of CH-19's token formats, or a 4-10 character code with a digit within four words of a code word (`TestTheWordingNetMarksAnAlertWhoeverSentIt`). A phrase counts only at the start of a word (the character before it is no ASCII letter or digit), so "designing" holds no "signin" while "login attempts" and "sign-ins" still match and "signing" stays an alert (the safe side), and a year from 1900 to 2099 is a date, not a code, as CH-19 lets dates pass (#2888, `TestPromotionalWordingIsNotAnAlert`; eval M01 carries both), except a 4-digit number right after "code is" or "code:", which is a code. A word with a few digits (one run of three or more letters and one of digits, with fewer digits than letters or a year: SAVE20, SPRING25, SAVE2026) is a promo code, not a code (Mark, #2992, card answer cmsg_01R91wiieBzMSvPKFsAJVvuKLZEZiafi55reTbKfuYfpQ2). The phrases, formats and code words are copied, not imported: `broker/owner` and `broker/mail` link old-core packages (journal, durable, grants), and step 5 deletes broker/mail. The text is folded to lower case, runs of space made one, fullwidth forms made ASCII, Unicode digits made ASCII and format characters dropped; it is not CH-12's skeleton fold, because this net keeps a real alert, written plainly, and a sender who disguises its own wording only makes its own mail trashable, which its class already allows. Eval M20 was changed to phishing with no alert wording (#2774), so it is still trashed; M31 stays an alert. A plain `go test` replays the published injection corpus (`broker/corpus/promptinject.json`, read directly) with an alert's wording and a code in subject or body through the clerk's own trash and label checks (`TestTheInjectionCorpusHidesNoAlertAndGetsNoLabel`, LOOP-7). | A newsletter that carries alert wording ("sign in to your account") is never unsubscribed and spam that does is never trashed: the owner is asked or it stays, which costs leverage, not safety. A real alphanumeric code shaped like a promo code (a word of three or more letters with fewer digits, such as ABCD12) is not caught by this net; login codes are digits or mixed, so Mark took that side (#2992). A real 4-digit code that reads as a year and is not written right after "code is" or "code:" ("Your PIN: 2026", "2026 is your code") is not caught by this net. The owner's languages' phrases are not added yet (broker/mail's `Config.Phrases`), so a real alert in another language is guarded only by the first net and the class rules. If sub B moves or deletes `broker/corpus/promptinject.json`, the replay test fails rather than passing empty. |
| MIG-4-mail-reader-4 | **A failed read shows.** Every mail with no class from the closed list is recorded once, when the clerk reads it, as a refusal `{op: read, reason: unclassified}`, so a reader that fails reads as failed reads in STATUS, not as an inbox with nothing to tidy. | None: the refusal is the record. |
