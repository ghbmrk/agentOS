| MIG-4-run-a | **Option A: one process per credentialed clerk, and the kernel in its own process.** Each credentialed clerk (exit, mail, browser) runs under its own uid with its own Secrets directory, and the kernel runs in a separate process. One process holding every clerk's Secrets (option B) is ruled out by CLK-1. A clerk that holds no secret (the sim, the slice runner) may share the kernel's process. Decided by the coordinator on 2026-10-21 and recorded on #2682. | CLK-1, STO-3 | A clerk sharing a process gets a row of its own here. |
| MIG-4-run-b | **One call per connection, and the view travels with it.** The kernel sends `{op, request, view}`, and the clerk answers `{outcome, detail}`. The view is the log's answer for this request only: the dispatch record, the chain's grants, the enrollments, the revocation and stop state, the ledger uses before the dispatch for every scope the chain charges, as far as that scope's caps can count them (#2700 item 3: the last day plus 10 minutes for a day or rate cap, the step's task for a task cap, the newest N for a use cap of N; each cap counts the same on that list as on the whole ledger, so the view grows with the caps, not the log's age), and the one-off line for the chain's root (D-146). The one-off line is computed on the kernel's clock at the call, not the clerk's, because it folds every grant under the root; the two clocks are on one box within one call. A root the view does not name has line 0, so any spend asks for a second passkey. The clerk runs its own `Check` against that view and does no I/O to the kernel while it acts, so a kernel that dies mid-call cannot half-answer a check. The clerk sees the log only through the kernel. Before calling the clerk, the clerk's process refuses (`view`) a view that leaves out a charged scope's ledger, because that scope would read as unspent. A call past what the clerk reads (4 MiB, `maxCall`) is never sent (#2708 item 1). A root with tens of thousands of metered calls in a day could reach that size. The step fails as `too-large` rather than going out cut short and parking as unknown with a false warning that it may have happened twice. A probe that large counts no check. | CLK-2, STO-3 | A View method added to `kernel.View` is one field of the view. |
| MIG-4-run-c | **Each side admits only the other's uid.** The clerk's socket admits only the kernel's uid (`sockets.ListenPeers`). The kernel sends nothing to a socket whose peer is not the clerk's configured uid. A kernel that cannot reach its clerk, or finds the wrong uid, has sent nothing, so the step is `unsent` (`unreachable`): STATUS names its clerk and the kernel sends it again after `kernel.UnsentWait`, doubling up to `kernel.MaxUnsentWait`. A probe that cannot reach its clerk is `unreached` and counts no check (#2700). Once any byte of the call is written, a missing answer is `unknown` (`lost`), and the step is probed through the clerk (KRN-8). | CLK-1, KRN-8 | none |
| MIG-4-run-d | **The kernel logs only a bounded answer.** An outcome outside the op's closed list (`ok`/`failed` for a call, `done`/`notdone` for a probe) is read as `unknown`. A detail over 256 bytes, invalid UTF-8 or holding a control character is logged as `malformed`. The exit's details are typed codes (clerk MIG-4-exit-c), so honest details pass unchanged. | CLK-4, KRN-8 | none |
| MIG-4-run-e | **The Secrets file is replaced atomically, in the clerk's own directory.** The steps are: write `secrets.tmp` (O_EXCL, O_NOFOLLOW, 0600), fsync it, rename it over `secrets`, fsync the directory. A crash leaves the old form or the new one, each whole, and a leftover temporary is never read and is replaced by the next write. The directory and the file must belong to the process's uid, be closed to every other uid, and not be symlinks; anything else is refused, never repaired. The path is the clerk's own directory, so no configuration names another clerk's file. | CLK-1, STO-2 | The setup flow (after STO-2) creates the directory with the clerk's uid. |
| MIG-4-run-f | **The old slot-to-blob form is refused, not migrated.** A Secrets file in which any slot is a bare string is refused with `ErrOldFormat` and left as it was. No store in that form was ever written outside tests (clerk MIG-4-exit-e). | CLK-1 | none |
| MIG-4-run-g | **Nothing here holds a real secret before STO-2.** The sealer is `clerk.NewAESSealer` under a test key, and the log key and head key are supplied by the caller. No `cmd/` main, unit file or setup flow is shipped yet. The production `Sealer` (the store key released by the TPM or passphrase slot), the boot unlock, and the mains and units under `image/` wait for STO-2, per Mark's #936 answer. Until then only tests start these processes, by re-running the test binary. Hardening a clerk's process (`procguard.Isolate`, which refuses the kernel's uid and sets it non-dumpable) belongs in that main. Since STO-2b-1 the kernel's main and the unlock step exist (rows v to ab), but neither starts on a box yet: they wait on the pins (STO-pins) and the log anchor (LOG-anchor-tpm). The clerks' unlock and mains, and the units, are still to come. | STO-2, CLK-1 | The STO-2 slice adds the mains, the units and the Sealer. |
| MIG-4-run-h | **One lock around the kernel, and clerk calls outside it** (#2700). Every call into the kernel goes through `Kernel.With`. `Tick` takes the due calls (`kernel.Calls`, which logs each dispatch) under the lock; then, for each call, under the lock again, it makes the kernel's last check (`kernel.Send`) and takes the call's view, makes the call without the lock, and logs its answer (`kernel.Answer`) under it. So STOP, a revoke or STATUS never waits on a clerk, and a STOP logged while one call hangs stops every call after it. A call already sent when STOP lands is answered and logged as usual. A view shares no map or slice with the kernel's state, since it is sent outside the lock. | KRN-5, KRN-7, OWN-18 | none |
| MIG-4-run-i | **The log file is locked, not anchored, by this package.** `FileStore` takes an exclusive `flock` so a second kernel process cannot open the same log. The anchor (LOG-2: the phone, a TPM counter or the enforcer) is supplied by the caller. No anchor that lives on the log's own disk ships, so the tests use the in-memory anchor. | LOG-1, LOG-2 | The anchor's slice supplies a real `kernel.Anchor`. |
| MIG-4-run-j | **The mail password is opened inside broker/clerk at each connection, from a slot named for its account.** `SetMail` seals the password into the static slot `mail/<digest of every settings field>`. The transport's credential is `clerk.Secrets.Login` for that slot, which opens it at each IMAP or SMTP connection, and `Login` opens only slots under `mail/`. A clerk opened on one account therefore asks only for that account's slot. After a removal or a move to another server or sign-in name, it has nothing to send, and the old server sees no login (the old setup's MAIL-gen). A same-account password change takes effect at the next connection. `SetMail` puts the new slot, writes the settings, then drops every other `mail/` slot, and `RemoveMail` drops every `mail/` slot before the settings (#2704). A crash at any point leaves settings whose own slot holds their own password, and the next `SetMail` or `RemoveMail` drops any slot a crash left. One lock serializes the two. The password reaches the transport as a Go string that `clear` cannot wipe, which lives for one connection in the clerk's own process, as the exit's header does. | CLK-1, STO-2 | none |
| MIG-4-run-k | **Setup keeps the old refusals' wording, and a refusal writes nothing.** The address, server, sign-in name and password refusals are the old setup's (`cmd/agentos-egress/mailaccount.go`), word for word. | MIG-4-run-l | **A clerk process reads its mailbox once, at open.** `OpenMail` reads the newest inbox mails, classes them with the quarantined read it is given, and serves that listing. | MIG-4-run-m | **One kernel socket per caller, each with a closed table.** The kernel's process serves the frozen seam (docs/LANES.md) on one socket per side: `OwnerSide` (the owner seam's actions, and reads of the state they change: STATUS, line changes, held spend, pools, enrollments, tasks, the revocations, pauses and STOP, a plan's status, a key's grant) to the owner side's uid, and `MeterSide` (`AdmitSpend`, `Meter`, `Hold`, `AdmitPool`, `ReadPool`) to the model clerk's uid. A call a side's table lacks is refused and logs nothing, so the model clerk cannot STOP, issue, extend or read the owner's state, and the owner side cannot meter. Every call runs under the kernel's one lock at the kernel process's clock; the caller dates nothing but a pool reading's reset time, which can only keep a pool shut longer. A read is encoded under the lock, so the caller gets a copy and never `*State` or its `Apply`. One connection carries one call, at most 16 are served at once per socket and the rest wait in its backlog holding no descriptor, and a failed accept is waited out, so a side that floods its own socket cannot end or starve another's (KRN-7). A refusal crosses as its `*key.Refusal` with its code; the kernel's, key's and setup's named errors come back as the same values; any other error crosses as its text; no error ever crosses as success. A call never sent is `ErrUnreachable`; a missing answer is `ErrLost`, and the owner side reads the state the call would change before acting again. `OpenTask` and `EndTask` stay with the host and are on no socket. | CLK-1, CLK-7, KRN-7, LOG-7 | A call added to the seam is one row of one side's table, in the PR that edits docs/LANES.md. |

The clerk serves one call, a model call for a plan, on its own socket to the planner's uid only (`ServeModel`, `Model`). | MIG-4-run-q | **LastOpened is the clerk's own, and a failed read keeps every sender** (#2698 items 1, 2). `OpenMail` builds `World.LastOpened` from `inbox.Live.Opened` and the sealed record (row r); the rest of the world is the caller's. When `Opened` fails, every sender in the listing counts as opened today, so VRB-2 passes no unsubscribe (`recently-opened`), and STATUS says unsubscribing is paused, why, and what resumes it. The record takes in the read mail the failing read found (#2841): `Opened` hands back the record it began from, every entry kept since a read that did not finish cannot tell whose mail is gone (save the old ones a read past the bound drops, below), with each read mail it logged added, dated today; a failing read that logged none leaves the record as it was (`TestAFailingReadSavesTheSendersItFound`, `TestOpenedFailureKeepsEverySenderAndSaysSo`). A save that fails is told as on a good read. Too much read mail names no amount to delete: past the bound the read keeps only what fits, so how far past is not known. A read past the bound (`inbox.ErrTooMuchReadMail`) goes on through every folder and keeps, within `inbox.OpenedMax`, the newest read mail by arrival that the record lacks, dropping first the record's entries older than 90 days, which open nothing (a dropped one whose mail is still there is logged again, dated that day: fail closed), then its own oldest; the record's recent entries are never dropped (inbox MIG-3-R10b). So the mail the owner read most recently, which the owner may then delete, is what the record keeps, and its sender stays opened for 90 days (`TestAFailingReadKeepsTheSendersItFound`, `TestAFullReadKeepsTheNewestReadMail`). Since that mail stays charged in full while its entry is recent, deleting it frees nothing for 90 days. So the step names the only read mail whose deletion frees room, by when it arrived, which the owner's mail app shows (`inbox.TooMuchReadMailError`, `tooMuchNext`): the read mail the full read dropped, and, past the warm-up, mail the record first saw read more than 90 days ago (arrived by that day, so the span is then "on or before" a date); deleting the read mail in that span lets the next read pass. During the warm-up no record entry is old, so the span leaves out mail read long ago, which frees nothing then (#2891 UX finding 1; `TestTheTooMuchReadMailStepWorks` applies the step in both states over a sweep of bounds and requires the next read to pass). When the full read dropped nothing, the log it saved fits, and the owner is told the next try should get through, with no step. A record too large to read back at all (only after the bound shrinks) names no step. Residual (#2891 Security finding 1, L3 finding 1): the full read keeps the newest by arrival because IMAP keeps no read time, so a mail that arrived long ago but was read since the last good read can be dropped, and the step then names it; if the owner deletes it and its sender has no other kept entry, the next good read counts that sender never opened, and VRB-2 can pass an unsubscribe within 90 days of the read (behind the hold and STOP). It needs an account at the bound, about a million read mails, and is narrower than before #2841, when a failing read kept nothing; a follow-up keeps one entry per sender, listed senders first, before dropping by arrival. Live unsubscribes are on (`inbox.NewLive(st).WithPoster()` in `mailBox`, `TestTheClerksMailboxHasAPoster`; inbox MIG-4-mail-a-9). An empty LastOpened would read as "never opened" and let every unsubscribe through. | VRB-2, D-141 | none |

| MIG-4-run-t | **A read of the mailbox holds up nothing else, and the planner cannot drive sign-ins** (#2732 items 1, 2; #2698 item 5). `MailHost` reads the mailbox outside its lock, so the kernel's steps, probes and the owner's reads are answered during a read; re-reads that overlap a read for the same account share it. Setup, removal and the record's `told` write wait for the read in flight to end and keep the lock while they write, so a read never mixes two accounts' files and is always of the account as it is. A read that fails keeps the clerk the account last opened, so steps still reach it (each signs in afresh and judges the kernel's view), and STATUS says why. That clerk judges VRB-2 on the read dates of its last good read, not on a fail-closed answer: a sender the owner read since then can still be unsubscribed from until the next good read, behind the hold and STOP; failing every step closed instead would stop all mail work for a passing server fault. A read that fails again under the Mark of the failure before it, within the day, gets no further try until the Mark moves or the next day (#2742, #2768 review), so a server whose Mark works but whose read keeps failing makes at most two read attempts per Mark and day, each single-flight and stopped before the read-mail pass (`TestARepeatedFailureWaitsForTheMarkToMove`, `TestARepeatedFailureIsTriedAgainTheNextDay`); the cost is that a fault that passes after its second try is not read past until the owner's mail changes or the next day, and STATUS says so. A change check that fails for any reason but a refused sign-in reads nothing, and the last read goes on serving, but STATUS says so ("I could not check your mailbox for new mail", fixed words and a next step) until a check or a read works; while a failed read's line stands, that line is told instead (`TestAFailedChangeCheckIsTold`; #2742, #2768 review). The planner can still drive one STATUS session per re-read. A Mark whose sign-in is refused, the change check's or the read's own, is the read's failure, with no second sign-in. A pause in the record of read mail, lasting or not, is tried again when the Mark moves or the next day. The grant never enters the log or the kernel's process (CLK-1).
