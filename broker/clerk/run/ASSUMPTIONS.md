# Kernel and clerk processes: assumptions

Built for MIG-4-run (#2682) in `broker/clerk/run`. Slice 1 is the kernel's process and the exit clerk's process (rows a to i). Slice 2 is the mail clerk's process (rows j to l). Slice 3a is the kernel's sockets and the model clerk's process (rows m to o). Slice 3b is the mail process's own sockets and its record of read mail (rows p to s). The exit's owner-approved Reconnect (#2643 b) is row u. Each row is a reading a reviewer may want to change.

| ID | Assumption | Spec basis | If it changes |
|---|---|---|---|
| MIG-4-run-a | **Option A: one process per credentialed clerk, and the kernel in its own process.** Each credentialed clerk (exit, mail, browser) runs under its own uid with its own Secrets directory, and the kernel runs in a separate process. One process holding every clerk's Secrets (option B) is ruled out by CLK-1. A clerk that holds no secret (the sim, the slice runner) may share the kernel's process. Decided by the coordinator on 2026-10-21 and recorded on #2682. | CLK-1, STO-3 | A clerk sharing a process gets a row of its own here. |
| MIG-4-run-b | **One call per connection, and the view travels with it.** The kernel sends `{op, request, view}`, and the clerk answers `{outcome, detail}`. The view is the log's answer for this request only: the dispatch record, the chain's grants, the enrollments, the revocation and stop state, the ledger uses before the dispatch for every scope the chain charges, as far as that scope's caps can count them (#2700 item 3: the last day plus 10 minutes for a day or rate cap, the step's task for a task cap, the newest N for a use cap of N; each cap counts the same on that list as on the whole ledger, so the view grows with the caps, not the log's age), and the one-off line for the chain's root (D-146). The one-off line is computed on the kernel's clock at the call, not the clerk's, because it folds every grant under the root; the two clocks are on one box within one call. A root the view does not name has line 0, so any spend asks for a second passkey. The clerk runs its own `Check` against that view and does no I/O to the kernel while it acts, so a kernel that dies mid-call cannot half-answer a check. The clerk sees the log only through the kernel. Before calling the clerk, the clerk's process refuses (`view`) a view that leaves out a charged scope's ledger, because that scope would read as unspent. | CLK-2, STO-3 | A View method added to `kernel.View` is one field of the view. |
| MIG-4-run-c | **Each side admits only the other's uid.** The clerk's socket admits only the kernel's uid (`sockets.ListenPeers`). The kernel sends nothing to a socket whose peer is not the clerk's configured uid. A kernel that cannot reach its clerk, or finds the wrong uid, has sent nothing, so the step is `unsent` (`unreachable`): STATUS names its clerk and the kernel sends it again after `kernel.UnsentWait`, doubling up to `kernel.MaxUnsentWait`. A probe that cannot reach its clerk is `unreached` and counts no check (#2700). Once any byte of the call is written, a missing answer is `unknown` (`lost`), and the step is probed through the clerk (KRN-8). | CLK-1, KRN-8 | none |
| MIG-4-run-d | **The kernel logs only a bounded answer.** An outcome outside the op's closed list (`ok`/`failed` for a call, `done`/`notdone` for a probe) is read as `unknown`. A detail over 256 bytes, invalid UTF-8 or holding a control character is logged as `malformed`. The exit's details are typed codes (clerk MIG-4-exit-c), so honest details pass unchanged. | CLK-4, KRN-8 | none |
| MIG-4-run-e | **The Secrets file is replaced atomically, in the clerk's own directory.** The steps are: write `secrets.tmp` (O_EXCL, O_NOFOLLOW, 0600), fsync it, rename it over `secrets`, fsync the directory. A crash leaves the old form or the new one, each whole, and a leftover temporary is never read and is replaced by the next write. The directory and the file must belong to the process's uid, be closed to every other uid, and not be symlinks; anything else is refused, never repaired. The path is the clerk's own directory, so no configuration names another clerk's file. | CLK-1, STO-2 | The setup flow (after STO-2) creates the directory with the clerk's uid. |
| MIG-4-run-f | **The old slot-to-blob form is refused, not migrated.** A Secrets file in which any slot is a bare string is refused with `ErrOldFormat` and left as it was. No store in that form was ever written outside tests (clerk MIG-4-exit-e). | CLK-1 | none |
| MIG-4-run-g | **Nothing here holds a real secret before STO-2.** The sealer is `clerk.NewAESSealer` under a test key, and the log key and head key are supplied by the caller. No `cmd/` main, unit file or setup flow is shipped yet. The production `Sealer` (the store key released by the TPM or passphrase slot), the boot unlock, and the mains and units under `image/` wait for STO-2, per Mark's #936 answer. Until then only tests start these processes, by re-running the test binary. Hardening a clerk's process (`procguard.Isolate`, which refuses the kernel's uid and sets it non-dumpable) belongs in that main. | STO-2, CLK-1 | The STO-2 slice adds the mains, the units and the Sealer. |
| MIG-4-run-h | **One lock around the kernel, and clerk calls outside it** (#2700). Every call into the kernel goes through `Kernel.With`. `Tick` takes the due calls (`kernel.Calls`, which logs each dispatch) under the lock; then, for each call, under the lock again, it makes the kernel's last check (`kernel.Send`) and takes the call's view, makes the call without the lock, and logs its answer (`kernel.Answer`) under it. So STOP, a revoke or STATUS never waits on a clerk, and a STOP logged while one call hangs stops every call after it. A call already sent when STOP lands is answered and logged as usual. A view shares no map or slice with the kernel's state, since it is sent outside the lock. | KRN-5, KRN-7, OWN-18 | none |
| MIG-4-run-i | **The log file is locked, not anchored, by this package.** `FileStore` takes an exclusive `flock` so a second kernel process cannot open the same log. The anchor (LOG-2: the phone, a TPM counter or the enforcer) is supplied by the caller. No anchor that lives on the log's own disk ships, so the tests use the in-memory anchor. | LOG-1, LOG-2 | The anchor's slice supplies a real `kernel.Anchor`. |
| MIG-4-run-j | **The mail password is opened inside broker/clerk at each connection, from a slot named for its account.** `SetMail` seals the password into the static slot `mail/<digest of every settings field>`. The transport's credential is `clerk.Secrets.Login` for that slot, which opens it at each IMAP or SMTP connection, and `Login` opens only slots under `mail/`. A clerk opened on one account therefore asks only for that account's slot. After a removal or a move to another server or sign-in name, it has nothing to send, and the old server sees no login (the old setup's MAIL-gen). A same-account password change takes effect at the next connection. `SetMail` puts the new slot, writes the settings, then drops every other `mail/` slot, and `RemoveMail` drops every `mail/` slot before the settings (#2704). A crash at any point leaves settings whose own slot holds their own password, and the next `SetMail` or `RemoveMail` drops any slot a crash left. One lock serializes the two. The password reaches the transport as a Go string that `clear` cannot wipe, which lives for one connection in the clerk's own process, as the exit's header does. | CLK-1, STO-2 | none |
| MIG-4-run-k | **Setup keeps the old refusals' wording, and a refusal writes nothing.** The address, server, sign-in name and password refusals are the old setup's (`cmd/agentos-egress/mailaccount.go`), word for word. The old "a different credential under this name" refusal has no case here, because the clerk's Secrets file holds only its own slot. The owner's setup page reaches `SetMail` and `RemoveMail` on the mail clerk's own socket (row p), never through the kernel's process, which holds no credential (CLK-1). Before STO-2, only tests call them, under the test key (MIG-4-run-g). | CLK-1 | none |
| MIG-4-run-l | **A clerk process reads its mailbox once, at open.** `OpenMail` reads the newest inbox mails, classes them with the quarantined read it is given, and serves that listing. A later read is a new `OpenMail`, and so is a settings change: `MailHost` opens the account again after each setup and on the planner's re-read (row p), and the planner reads the listing on its own socket. The handle secret is given by the caller until the main exists (after STO-2). | CLK-2 | none |
| MIG-4-run-m | **One kernel socket per caller, each with a closed table.** The kernel's process serves the frozen seam (docs/LANES.md) on one socket per side: `OwnerSide` (the owner seam's actions, and reads of the state they change: STATUS, line changes, held spend, pools, enrollments, tasks, the revocations, pauses and STOP, a plan's status, a key's grant) to the owner side's uid, and `MeterSide` (`AdmitSpend`, `Meter`, `Hold`, `AdmitPool`, `ReadPool`) to the model clerk's uid. A call a side's table lacks is refused and logs nothing, so the model clerk cannot STOP, issue, extend or read the owner's state, and the owner side cannot meter. Every call runs under the kernel's one lock at the kernel process's clock; the caller dates nothing but a pool reading's reset time, which can only keep a pool shut longer. A read is encoded under the lock, so the caller gets a copy and never `*State` or its `Apply`. One connection carries one call, at most 16 are served at once per socket and the rest wait in its backlog holding no descriptor, and a failed accept is waited out, so a side that floods its own socket cannot end or starve another's (KRN-7). A refusal crosses as its `*key.Refusal` with its code; the kernel's, key's and setup's named errors come back as the same values; any other error crosses as its text; no error ever crosses as success. A call never sent is `ErrUnreachable`; a missing answer is `ErrLost`, and the owner side reads the state the call would change before acting again. `OpenTask` and `EndTask` stay with the host and are on no socket. | CLK-1, CLK-7, KRN-7, LOG-7 | A call added to the seam is one row of one side's table, in the PR that edits docs/LANES.md. |
| MIG-4-run-n | **The model clerk runs apart and meters through the meter socket.** Its provider holds a credential, so it runs under its own uid (row a), with `Meter` as its `model.Ledger`. The `now` that `model.Ledger` passes is ignored; the kernel dates every entry. A meter socket that cannot be reached, or whose answer is lost, refuses admission with `log-broken`, so no metered call starts on a ledger the clerk could not reach. `admitspend` answers the `kernel.Admitted` it logged and `meter` settles it by its sequence. A lost `Meter` answer is owed and retried by `model.Clerk`; the kernel settles an admission once, so a retry of one that landed is refused `ErrNotAdmitted`, which the clerk counts as recorded. A lost `admitspend` answer leaves its admission open, charged at its worst case (MIG-4-spend-e, #2731). The clerk serves one call, a model call for a plan, on its own socket to the planner's uid only (`ServeModel`, `Model`). A failed call crosses as its refusal, with its code, or as the fixed `ErrModelCall`: a provider's own error can carry its URL, a header or a key, so its text never leaves the clerk's process (CLK-1). `model.Clerk` runs calls at once; the kernel's reservations keep them inside the caps (MIG-4-spend-e). The key, the task and every cap come from the named plan in the log, never from the caller, so the planner's uid can spend only within a live plan's caps. Wiring this in place of `broker/meter` and deleting `broker/verb` and `broker/meter` (#2572 Step C) waits on sub B unhooking their importers (docs/LANES.md deletion rule). | CLK-1, CLK-7, LOG-7 | none |
| MIG-4-run-o | **The owner socket trusts its uid as the kernel trusts `With`.** Owner actions that carry no signature (STOP, RESUME, pause, unpause, revoke, reserve, retry, cancel, undo) are taken from the owner side's uid as the frozen seam takes them in-process: the socket moves the seam across a process boundary and adds no power. Every check the kernel makes itself still applies: an issue or a line change needs its co-signatures (D-146), a task approval an enrolled passkey's signature (CLK-3), an extension a key outside the held chain (LOG-7). Which owner gestures need a passkey before the owner side calls is sub B's (#2578). | OWN-18, KEY-6 | A signed owner proof at the kernel (KRN-ownerlink) narrows this to signed calls. |
| MIG-4-run-p | **The mail process has two sockets besides the kernel's, each with a closed table.** `MailHost` holds the open clerk and serves `MailOwnerSide` (`setmail`, `removemail`, `status`) to the owner side's uid and `MailPlannerSide` (`listing`, `reread`) to the planner's uid; a call a side's table lacks is refused and changes nothing. So the password goes from the owner's setup page to this process only (CLK-1). A setup refusal crosses in its fixed wording (row k). Each replacement and removal is told to the owner once, in the old setup's words ("The mail account was replaced on my Wi-Fi page.", "... removed ..."), through the `status` read, which hands each notice over once (CH-11); sub B's owner channel carries it. With no account open, a step is `failed` (`no-account`) and nothing is sent, and a probe is `unknown`. A step judged by the unbound clerk is checked against the kernel's view, which the clerk trusts by the kernel's uid (rows b, c); a request the log has not put in flight is refused (#2698 item 8). | CLK-1, CLK-2, CH-11 | none |
| MIG-4-run-q | **LastOpened is the clerk's own, and a failed read keeps every sender** (#2698 items 1, 2). `OpenMail` builds `World.LastOpened` from `inbox.Live.Opened` and the sealed record (row r); the rest of the world is the caller's. When `Opened` fails, every sender in the listing counts as opened today, so VRB-2 passes no unsubscribe (`recently-opened`), the record is kept as it was, and STATUS says unsubscribing is paused, why, and that it resumes after the next full read. An empty LastOpened would read as "never opened" and let every unsubscribe through. | VRB-2, D-141 | none |
| MIG-4-run-r | **The record of read mail is sealed, bound to its account and bounded before it is read** (#2698 items 11, 12). `seen.log` beside the settings is sealed under the clerk's `Sealer` with the account's slot as associated data, so a record altered, forged or carried over from another account does not load; a record over 320 MiB (`maxSeen`, the most `Opened` can keep at 320 bytes an entry) is not read. A record that does not load, or is missing, starts over today, which keeps every read sender opened for 90 days (fail closed), and STATUS says the record began again. A replacement for another account drops the record, a password change keeps it, and a removal drops it. Not covered: a rollback of the clerk's whole directory to an older copy, which restores the older record together with the older Secrets file. Refusing that needs a counter outside the disk, the same one STO-2 adds for the Secrets file; until then a rolled-back record loses only the entries for mail read and then deleted since the copy, since mail still in the box is dated again today. | VRB-2, CLK-1, STO-2 | STO-2's monotonic counter covers the record with the Secrets file. |
| MIG-4-run-s | **The owner is told about the warm-up, and the clerk's memory is sized for it** (#2698 items 3, 10, 13). Until the record has watched for 90 days, STATUS says until when the clerk unsubscribes from no sender the owner has read mail from before. On the first read after, the owner is told once how many senders became eligible, that each still waits its hold, and that STOP cancels it; the record keeps that it was told. The mail clerk's process holds up to `inbox.openedMax` (384 MiB) for `Opened`, one `Seen` batch (16 MiB plus 400 × 16 KiB, about 22 MiB), and, while the record loads, its sealed and opened copies (up to 2 × 320 MiB). Its unit (slice 4, after STO-2) sets `MemoryMax` to 1.2 GiB, which also leaves the Go runtime 128 MiB; an account near the bound fails closed and says so (row q). The wording of each held unsubscribe's own note is the owner channel's (MIG-3-R8, #2616). | VRB-2, D-141, A4 | Slice 4's unit sets MemoryMax. |
| MIG-4-run-u | **The owner's Reconnect is a change-account step under the owner's exact approval, naming a grant staged on the clerk's own socket for that plan** (#2643 b). `clerk.Exit.Reconnect` trusts its caller to have proved the owner; out of the kernel's process, `ExitHost` is that caller. The owner's side stages the new grant for one plan on the exit process's owner socket (`ListenExitOwner`, `ServeExitOwner`, `ExitOwner.Stage`, one call, the owner side's uid only, which is never the planner's), and gets back its SHA-256 digest; a later stage replaces an earlier one. The plan's step is `change-account` for this clerk (`target` the clerk's name, `value` the digest, content `grant:<digest>`, which the host's facts vouch for from the value). Its key is the clerk key narrowed by an enrolled passkey with the browser's exact-approval shape (CLK-3): that last link allows only `change-account`, only that content, one use, and expires within `MaxApproval` (15 minutes). The host checks the step with `clerk.Verify` against the kernel's view, like every step, and replaces the slot only when the target is this clerk (else `not-this-clerk`), the key is that exact approval (else `not-owner-approved`; the clerk key alone, the planner's own narrowing, or a narrowing the owner gave for anything else), and a grant is staged for this plan with the step's digest (else `grant-not-staged`). The staged grant is then wiped. A plan the owner cancels or STOPs cannot be submitted again under its ID (`kernel.ErrDuplicatePlan`), so a cancel also retires the grant staged for it, and the planner cannot carry it into another plan. The grant never enters the log or the kernel's process (CLK-1). The approval expires within 15 minutes and the exact approval is the gate (OWN-9), so the exit clerk's key must hold irreversible steps for less than that. Its hold and novelty windows (KEY-5) cover every irreversible verb of the key, not change-account alone. Each reconnect names a new grant, so its content is new and it always waits the full novelty window. Under a key whose window is 15 minutes or more, every reconnect expires during its hold and is left undone, and tapping again never helps; the way out is a key with a shorter window, a widening with its own hold (D-146). So sub B's exit clerk keys keep their novelty window under 15 minutes (`TestAReconnectOutlastsOnlyAHoldShorterThanItsApproval`). The approval also runs out while the key is paused or the core is down, which costs the owner one more tap. The kernel refuses the same change within 24 hours (KRN-8); a new sign-in gives a new grant and digest. A failed `Reconnect` (a grant that does not read, or one that would take the Secrets file past `maxSecrets`, which the writer now refuses so the file always reopens) is `failed` (`credential`), and the slot and file are unchanged. A step the host ran is `done` to a probe and is not run again; any other is `unknown`, since a restart forgets the staged grant too, so the owner stages and approves again. Which gesture asks for the passkey, and the page that starts the new sign-in, are sub B's (#2578). | CLK-1, CLK-3, OWN-9, KRN-8 | A spec rule for owner reconnects takes this row's place; an exact-step approval that skips the novelty window (#2742's kernel item) lifts the window condition. |
