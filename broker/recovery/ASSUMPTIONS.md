# Recovery and portability: assumptions

Built for PLAN P2-8 (REC-1 to REC-4, A8) against SPEC v0.12, on the vault's
key-slot file and vault process (P2-4a, stacked on its branch), the Owner Card
format (P2-2, PR #32), the owner channel (P1-5), and the grants package's
fixed wording (P2 grants). Each row is a reading of the spec, or a gap left for
a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| R1 | The recovery key is a third `vault.Factor` (`recovery.Factor`), so the drive has one key-slot file. It is 160 random bits printed as 32 card symbols in groups of four (card.Card.RecoveryKey). It is not stretched: its key-encryption key is HKDF-SHA256 under a 32-byte salt kept in the slot's opaque `Sealed` field. There is no check group, as on the card; a mistyped key parses and opens nothing. | REC-1, CRED-8, ID-1 | Add a check group to the card format and to `ParseRecoveryKey` together. |
| R2 | **Backups open only with the recovery key.** A backup is sealed to an X25519 public key derived from the recovery key and kept in the vault; the box holds neither the recovery key nor the data key's backup copy, and neither the card's passphrase nor a TPM opens a backup. The preamble carries only an ephemeral public key and a nonce prefix. Contents are a tar of every root (vault process directory, broker state directory) in 64 KiB AES-256-GCM chunks, numbered and with the last one marked, so reordering, truncation at a chunk boundary, and trailing data all fail. | REC-1, CRED-8 | Auto-decided: no lens worse (REC-1 names the recovery key). |
| R3 | **Restore** writes into a new directory only, never over a drive; a failure leaves nothing. Entries are refused unless every parent is a directory the restore itself created, files are created with `O_EXCL|O_NOFOLLOW`, and only regular files, directories, symlinks, and 0/0 whiteouts are allowed (as vm/overlay V17), so a crafted backup cannot write outside the target. The key-slot file must pass `CheckKeys`, and the recovery key must open the restored vault. Owners, setuid bits, and the overlay opaque marker are restored when the broker runs as root (`KeepOwners`). Restoring from the old drive itself is the same path: a backup piped into a restore. | REC-1, V17 | — |
| R4 | **A restored drive trusts no host.** Restore removes every TPM slot; adding a trusted host is the usual tier-4 action (CRED-9). It keeps the passphrase and recovery slots, so unknown-host unlock works on the new hardware. | CRED-9 | Auto-decided: security better, one tier-4 step for the owner. |
| R5 | **Restricted mode** is a vault entry (`recovery-state`): restore writes it restricted. While restricted, no grant or pre-allowance runs (`State.Permits`). The owner answers once, on the local page, for the whole standing list in fixed wording (`grants.Describe`), keeping some; the rest stay off for good and the broker revokes them in the journal. That answer is tier-4 (code plus local confirmation, or the recovery key). A malformed entry reads as restricted. A whole-vault rollback to an older copy cannot be seen from the drive alone; that is the V6 counter (P2-4b). | REC-2, CH-3 | Wiring into the grants gate is a follow-up (below). |
| R6 | **Spent budgets.** A restore cannot know what was spent after the backup or drive copy, so a budget period that began before the restore counts as fully spent; the next period starts normally. Raising a budget stays its own owner intent. | REC-2, OP-5 | Auto-decided: potency loses at most one budget period after a rare restore, and one code restores it. |
| R7 | **Lost phone:** the recovery key, entered on the box's Wi-Fi page, replaces the code-generator seed in the vault (`owner-totp-seed`, the vault process's entry) and returns an `otpauth://` link for the local page only. The grid is unchanged. The owner channel's session ends, and the next code must come from the new seed. | REC-3, CH-6, ONB-6 | — |
| R8 | **Lost number:** the recovery key, entered on the local page, yields an 8-digit pairing code that the owner texts from the new number, as setup proves the number (§8.1). Three wrong codes or 15 minutes end it, and the current owner number cannot complete it. The old number gets "the owner number moved to ...NNNN"; the new one is told to unlock with a code. The channel restarts on the new number with the session ended, so the old number's new holder gets no reply to anything, codes included. | REC-3, CH-3, CH-12 | — |
| R9 | **Rotation** replaces any subset of the card's secrets as one tier-4 action and returns the whole new card to print. The vault keeps the full card (`owner-card`), so rotating one part reprints all of it; anyone who can read that entry already holds the data key, which every part but the Wi-Fi password protects. Each printed secret is also its own vault entry, so the vault's whole-value redactor covers it (CRED-7). New values come from `card.Generate` (P2-2); the Wi-Fi name is kept. The passphrase and recovery slots are rewritten (proved by the current recovery key, which costs no Argon2id run) before the card is stored; if storing fails after that, the new card is still returned with `ErrCardNotStored` so it can be printed. Earlier copies and backups still open with the old values (CRED-8). | REC-4, CRED-8 | Auto-decided: UX better, security unchanged. |
| R10 | **A8 at rest.** `CheckKeys` mirrors the key-slot format field for field with unknown fields refused, so the plaintext key file can carry only TPM, passphrase, and recovery slots; a test proves the mirror against the vault. The scanner looks for the data key (unwrapped from the format alone), every vault value, and the card's secrets in raw, hex, base64/base64url and base32 at every alignment, UTF-16 and undashed forms for printed values, and any 15-byte fragment of a binary value. It runs over both drives and the backup in tests and as an A5 canary target with fresh canaries every CI run, and as `agentos-a8scan` on real partitions in the owner session. | A8, CRED-8, CRED-1 | — |
| R11 | This package imports the vault and runs in the vault process; the vault's importer list gains `recovery` and `cmd/agentos-a8scan`, and recovery's own imports test lets only those two import it. | ARC-1, CRED-1 | — |

## Follow-ups (not in this package)

- Wire into the vault process (`cmd/agentos-egress`, P2-4a/c): `Provision` at `init`, a `backup` and `restore` command, and local-UI operations for re-enroll, number change, re-confirm, and rotate (P2-2's page).
- The grants gate consults `State.Permits` and `BudgetRemaining` once the grants package and this one are both merged; `Reconfirm`'s declined list becomes revoke intents.
- agentosd persists the owner number that a number change returns, and restarts the channel on it.
- P2-4b: the V6 rollback counter, which also makes restricted mode survive a whole-vault rollback.
- When PR #32 merges, `Card` becomes `card.Card` and `card.Generate` is the `Generator`.
