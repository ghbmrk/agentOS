# Recovery and portability: assumptions

Built for PLAN P2-8 (REC-1 to REC-4, A8) against SPEC v0.12, on the vault's
key-slot file and vault process (P2-4a, stacked on its branch), the Owner Card
format (P2-2, PR #32), the owner channel (P1-5), and the grants package's
fixed wording (P2 grants). Each row is a reading of the spec, or a gap left for
a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| R1 | The recovery key is a third `vault.Factor` (`recovery.Factor`), so the drive has one key-slot file. It is 160 random bits printed as 40 card symbols: eight groups of four key symbols, each followed by one check symbol (a GF(32) weighted sum), so `ParseRecoveryKey` catches any one wrong symbol and any swap of neighbours and names the group ("group 5 looks mistyped"). It is not stretched: its key-encryption key is HKDF-SHA256 under a 32-byte salt kept in the slot's opaque `Sealed` field. | REC-1, CRED-8, ID-1 | P2-2's `card.Generate` prints `RecoveryKey.Text()` (same format). |
| R2 | **Backups open only with the recovery key, and restore only what this box wrote.** A backup is sealed to an X25519 public key derived from the recovery key; the vault keeps the public key bound to a hash of the recovery slot it belongs to, so a backup is never sealed to a key that no longer matches the drive (a mismatch, a missing entry, or one of another kind refuses the backup). The preamble carries only an ephemeral public key and a nonce prefix. Contents are a tar of every root in 64 KiB AES-256-GCM chunks, numbered and with the last one marked, so reordering, truncation and trailing data fail. The archive ends with an HMAC-SHA256 over every entry's restored fields and contents, keyed by a vault entry (`recovery-backup-mac`), verified after the restored vault opens and before anything is moved into place: anyone holding the public key can seal an archive, even with a genuine vault copied from the drive, but cannot make one that restores. | REC-1, CRED-8 | Auto-decided: no lens worse. |
| R3 | **Restore** writes into a new directory only, never over a drive; a failure leaves nothing. Every parent must be a directory the restore created; files are created with `O_EXCL|O_NOFOLLOW`; only regular files, directories, symlinks, and 0/0 whiteouts are allowed (V17). Owners, setuid and setgid bits, the opaque marker, whiteouts and absolute symlinks are restored only beneath the machine layers (`Layout.Layers`), owners only as root (`KeepOwners`), and never setuid on a uid-0 file or setgid to gid 0. Elsewhere a symlink must stay inside its own root. The vault root gets the vault's user, 0600 files and 0700 directories; top-level roots are 0700; the vault and key-slot file must be regular files. The owner session's unlock ends. **Restoring from the old drive** is the same path (a backup piped into a restore) without the MAC: nothing authenticates a drive's plaintext broker state, so the restore is marked `Unverified` and its owner number and grants count as the owner's only after the tier-4 re-confirmation. | REC-1, V17 | — |
| R4 | **A restored drive trusts no host.** Restore opens the restored vault and calls `vault.Rebase` with the recovery key, which drops every TPM slot together with the rollback anchors in one vault write and gives the vault a new rollback identity (P2-4d, T11 in `tpmseal/ASSUMPTIONS.md`); adding a trusted host is the usual tier-4 action (CRED-9), offered in the same local-page session as the re-confirmation. It keeps the passphrase and recovery slots, so unknown-host unlock works on the new hardware. | CRED-9 | Auto-decided: security better, one tier-4 step for the owner. |
| R5 | **Restricted mode** is a vault entry (`recovery-state`), read only under its own kind: restore writes it restricted. While restricted, no grant or pre-allowance runs. The owner answers once, on the local page, for the whole standing list in fixed wording (`grants.Describe`): pick grants to keep, **Keep all**, or **Turn all off** (an empty answer is refused). Afterwards only a kept grant, or one created after the answer, runs (`State.Permits`); every other standing grant is declined for good, across later answers and restores. The answer is tier-4 (code plus local confirmation, or the recovery key) and serialized. A malformed or wrong-kind entry reads as restricted. A whole-vault rollback is the V6 counter (P2-4b). | REC-2, CH-3 | — |
| R6 | **Spent budgets.** A restore cannot know what was spent after the backup or drive copy, so a budget period that began before the restore counts as fully spent, unless the owner picks **Start budgets fresh** in the same tier-4 answer; the next period starts normally. Raising a budget stays its own owner intent. | REC-2, OP-5 | Auto-decided: potency loses at most one budget period after a rare restore, and the same answer restores it. |
| R7 | **Lost phone:** the recovery key, entered on the box's Wi-Fi page, replaces the code-generator seed in the vault (`owner-totp-seed`, the vault process's entry) and returns an `otpauth://` link for the local page only. The grid is unchanged. The owner channel's session ends, and the next code must come from the new seed. | REC-3, CH-6, ONB-6 | — |
| R8 | **Lost number:** the recovery key, entered on the local page, yields an 8-digit pairing code that the owner texts from the new number, as setup proves the number (§8.1). Three wrong codes or 15 minutes end it; only an 8-digit body counts as a try, so other texts cannot use them up; the current owner number cannot complete it. The old number gets "the owner number moved to ...NNNN" with how to move it back (the recovery key on the local page); the new one is told to unlock with a code. | REC-3, CH-3, CH-12 | — |
| R9 | **The vault never holds the recovery key or the vault passphrase.** It keeps the card's operating values only (Wi-Fi, setup secret and code, grid seed), each secret also as its own entry for the redactor (CRED-7). So one vault read yields no factor that opens past backups or survives rotation of the slots. It does yield the data key, which opens drive copies until the data key itself changes (R10a). Cost: the box cannot reprint those two parts, and the redactor cannot match them (no agent ever sees them; they are typed only on the local page). | REC-1, REC-4, CRED-1 | Security's recommendation (review of #35); the UX cost goes to the arbitrator. |
| R10 | **Rotation is two-phase.** `BeginRotate` (tier-4) generates the new values and changes nothing; the local page shows the card with **Save card** and asks for one value back from it (last group of a new recovery key, last word of a new passphrase, last four of a new Wi-Fi password, the setup code, or the grid's check code). `Commit` applies it only on that answer, within 30 minutes and three tries. Replacing the passphrase or recovery slot needs a factor that opens the drive now: the old card's value (the page asks "Do you still have your current card?"; yes keeps the recovery key unless chosen, so old offline backups stay openable), or the vault process's TPM factor when the card is lost, which must replace the passphrase, the recovery key (arbitrator ruling B3) and the grid (R10a). Backups sealed to the lost key cannot be rewrapped: the box holds only the public key, so it cannot open them; after a recovery-key change the done page offers Back up now. A minimal **backup log** in the vault (`recovery-backup-log`: destination and date per backup, verified by reading it back) lets the done page and the next digest say "Backups made before DATE still open with your old card. Delete them from DESTINATIONS once the new backup is done." Once a backup under the new key is verified, the page offers "Delete the N older backups at DESTINATIONS now?" for destinations the box can reach, as a tier-4 answer, never automatically; declining keeps them and repeats the digest line once; unreachable destinations stay named instructions (arbitrator ruling on #35). Order: passphrase slot, recovery slot, backup key, card values; the caller applies a new Wi-Fi password last with a rejoin note. A failure after the first slot write returns the parts in effect with `ErrCardNotStored`, and the rotation marker (`recovery-rotation-pending`) stays until a rotation covering the owed parts completes; meanwhile backups are refused. Each slot rewrite builds its proof factor afresh (`Proof`), since the vault wipes a factor after use. The new card shows only the rotated parts; the owner keeps the rest of the old card. The done page turns the notes into actions (**Back up now**, destroy the old sheets). Earlier copies and backups still open with the old values (CRED-8). | REC-4, CRED-8 | Auto-decided after review: UX and security better. |
| R10a | **Rotation re-encrypts when a factor may be out of the owner's hands** (closes the gap #35 merged with). `vault.Rekey` keeps the data key, so a lost factor with an earlier keys file or backup would yield the data key, which opens *later* copies too, and the backup MAC key, with which a later backup could be altered outside its vault. So a **lost-card** commit and a **recovery-key** commit, once the slots are replaced, call `Box.Reencrypt` (the vault process's `custody.reencrypt`: a fresh data key with every owner slot rewrapped, a new policy key, and this and other trusted PCs resealed where possible, the rest counted in `Done.Retrust`; nil falls back to `V.Reencrypt`, which drops TPM slots) and put a fresh MAC key and a fresh code-generator seed (`Done.Enrollment`), since an earlier copy holds both (egress V7; security C1 on #64). The rotation is final only once a code from the new seed is confirmed: an enrollment marker, written before the seed, keeps `ShowEnrollment` ("Show the code again", on the Wi-Fi page with the recovery key, the new card's after a rotation) available until `ConfirmEnrollment` accepts a current code on the Wi-Fi page, with at most `MaxEnrollTries` wrong codes per showing (UX-64-1; L3 F1, F2). The rotation marker records everything a commit owes (slots, a lost card's setup secret and grid, and `refresh` for the re-encryption) and whether the card was lost; each completed part is dropped, the next rotation must include every owed card part (`ErrRotationOwed`), `Refresh` owes and pays only `refresh`, and an unreadable marker owes everything (L3 F3, F4). A typed passphrase that is not the proof is checked before anything changes (F5). A lost card must also replace the setup secret (ID-1) and the grid, whose seed an earlier copy holds; the page pre-ticks the Wi-Fi password with `LostCardWiFiNote` (security C2 on #64, amending B3). The done page shows `ResetNote`, `RetrustNote` for PCs to trust again (UX-64-2, also in the digest) and, after a lost card or Refresh, `ExposedNote` naming the credentials older copies still hold (security R1). Re-encryption rewraps the passphrase slot too, so that change needs the passphrase typed or replaced (`ErrNeedPassphrase`); one QR scan from the card in hand. A passphrase change with the card in hand does not re-encrypt (arbitrator ruling on #45). `Refresh` does the same for a removed trusted PC, with the card's recovery key and passphrase. A failure after the first slot write leaves the rotation marker, so backups stay refused until a covering rotation completes. The backup key is bound to the recovery slot's salt, which re-encryption keeps and `Rekey` replaces, so backups continue after a re-encryption. Copies and backups made before stay readable with the old factors (CRED-8). | REC-4, CRED-8, CRED-9 | Auto-decided: security better, UX near-equal (one passphrase scan on a recovery-key change; a lost card's new grid prints with the new card); lens gate on #64 added C1, C2, UX-64-1/2, R1 (arbitrator auto-decided). Was the escalated gap; option 1 (coordinator) merged #35 with it and blocked the wiring until this. |
| R11 | **A8 at rest.** `CheckKeys` mirrors the key-slot format field for field with unknown fields refused; a test proves the mirror against the vault. The scanner looks for the data key (unwrapped from the format alone), every vault value, the recovery key and the typed passphrase in raw, hex, base64/base64url and base32 at every alignment, UTF-16 and undashed forms for printed values, and any 15-byte fragment of a binary value. It runs over both drives and the backup in tests and as an A5 canary target, and as `agentos-a8scan` (key and passphrase read with echo off) from the box's own local page in the owner session. | A8, CRED-8, CRED-1 | — |
| R12 | **Reserved entries.** Each entry this package keeps is read only under its own kind and fails closed otherwise (no backup, restricted, no card). The vault process's `/credential` write accepts only a built-in adapter's credential name and never replaces an entry of another kind. | CRED-1, REC-1, REC-2 | — |
| R13 | This package imports the vault and runs in the vault process; the vault's importer list gains `recovery` and `cmd/agentos-a8scan`, and recovery's own imports test lets only those two import it. | ARC-1, CRED-1 | — |

## Conditions on the wiring (from the review of #35)

- `Auth{Code, Local}` must, once wired, be set only from vault-verified proof (the K7 verify token) and the unlock socket's peer uid, never from assertions by agentosd.
- The grants gate consults `State.Permits` (with the time the live broker recorded each grant) and `BudgetRemaining` before any recovery operation is reachable, and passes the complete standing list from the restored record to `Reconfirm`.
- While `State.Unverified` is set, the owner channel treats the restored owner number as unverified: no approval is sent to it until the re-confirmation.
- P2-1 mounts the state and vault partitions `nosuid,nodev`.
- P2-4b's V6 rollback counter covers `recovery-state`.
- QR or photo decoding of the card stays sandboxed (#32).

## Follow-ups (not in this package)

- **R10a wiring (W6, this thread):** the vault process must set `Box.Reencrypt` to `custody.reencrypt` (with this PC's boot PIN when it has one), never ship the nil fallback, and a test asserts it is set (potency PR1 on #64). The removed-host flow (`untrust`) takes the card's recovery key and passphrase and calls `Refresh`. Every flow that returns an `Enrollment` (lost card, recovery key, Refresh) ends the owner session and keeps the page on the QR code with **Show the code again** until `ConfirmEnrollment` matches a code, offers a grid rotation in the same flow, and shows `RetrustNote` on the done page and in the digest, naming PCs where names exist. After a partial commit (`ErrCardNotStored`) the page offers **Finish securing the box** through `Refresh` (security R2).
- On a lost-card rotation the page pre-ticks the Wi-Fi password with `LostCardWiFiNote` beside it (security C2).
- New package P2-8b (potency PR2): remove a PC now and re-encrypt later: the slot goes at once, and `Refresh` stays pending with a digest line until the card is scanned.

- Wire into the vault process (`cmd/agentos-egress`, P2-4a/c): `Provision` at `init`, the backup, restore and scan buttons, and local-UI operations for re-enroll, number change, re-confirm (with re-adding a trusted host), and two-phase rotate (P2-2's page).
- P2-2: print `RecoveryKey.Text()` (40 symbols with check symbols) and `GridCheck` under each grid; `card.Card` replaces `Card` and `card.Generate` is the `Generator`.
- agentosd persists the owner number that a number change returns, and restarts the channel on it.
- P2-4b: the V6 rollback counter, which also makes restricted mode survive a whole-vault rollback.
- P2-2's page: reprinting the card without rotating takes a QR scan of the current card (CRED-8 flow).
- Wiring: the backup command calls `BackupSum` and `RecordBackup`; the digest includes `DigestLine`; the done page shows `OldBackupsNote` and `OfferDelete`, and the caller deletes what `ApproveDelete` returns.
- New package (for BOARD): scheduled daily sealed backups to an owner destination, the backup's age in the digest, and a stale backup as an alert class.
