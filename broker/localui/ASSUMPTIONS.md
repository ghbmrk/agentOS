# Local web UI: assumptions

Built for PLAN P2-2 against SPEC v0.12 (§6.2 CH-7 to CH-9, §8.1, ONB-1 and
ONB-3 to ONB-8), plus P1-5's carry-forward (O4): the local UI offers RESUME and a
local unlock that clears challenge mode. Each row is a reading of the spec, or a
gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| L1 | **Sign-in is the local unlock.** One code-generator code or the asked grid cell signs the device in for the CH-3 unlock period and also unlocks chat by text, clears challenge mode and lifts the low-tier lock (`owner.LocalSignIn`). Joining the Wi-Fi already proves the card, so this is at least as strong as a texted `UNLOCK <challenge> <code>`. Local attempts count as wrong codes (CH-18) and have their own fixed 24-hour bound (24), durable across restarts. Per the arbitrator's ruling on #32: every sign-in is texted to the owner ("A phone signed in on the box's Wi-Fi at HH:MM. Not you? Text STOP."), coalesced under CH-15 to one text an hour that lists each sign-in; a wrong local code is texted on the first of a bound window and again when the bound is used up, and every wrong attempt is listed in the digest. When the bound is spent the page says sign-in here is paused for up to 24 hours and texting a code still works. | CH-7, CH-14, CH-18, O4 | `owner/local.go`. |
| L2 | RESUME: a signed-in device resumes with one tap; otherwise the RESUME form takes a code, which signs the device in first. A texted RESUME code issued earlier is voided. STOP needs no sign-in, as by text (its worst case is a pause). | CH-3, CH-11 | `resume`, `stop`. |
| L3 | Without sign-in, only `/status`, `/unlock` (and `/unlock/vault`, where P2-4 mounts the unknown-host unlock), `/box.vcf` and, until setup is done, `/setup` answer. The status page shows only boot progress, running or stopped, and whether codes are locked. Everything else, including pages later packages add with `Mount` (CH-8: live browser view, diffs and files, rules), needs sign-in. | CH-7, CH-8 | Route table in `server.go`. |
| L4 | Remembered devices live in memory (token hashes, at most 16), so a restart signs every device out. That is also what a boot on an unknown host needs (CH-14). A device's sign-in must lie within the channel's current unlock, so when the session locks (wrong codes, an unknown-host boot) every device is signed out; a later unlock that reaches past a device's own expiry readmits it until that expiry. The sign-in page says "7 days, or until the box restarts". | CH-7, CH-18 | Persist them if restarts prove frequent. |
| L5 | **CH-9 has three layers:** the listener is bound to the access point's address and, with `SO_BINDTODEVICE`, to its interface, so the home network or an agent machine's link cannot reach it even where routing would deliver the packet; every request's source must be in the access point's subnet and not the box itself; and `NftRules` accepts the UI port only from the access point and drops it everywhere else. `New` and `Listen` refuse a public, unspecified or loopback address. | CH-9 | — |
| L6 | Any host name other than the box's address is a captive-portal check or DNS rebinding: GET and HEAD are redirected to the box, anything else is refused. Posts carrying a cross-site `Origin` or `Sec-Fetch-Site` are refused, and the cookie is `SameSite=Strict`, `HttpOnly`. Pages set a CSP with no script, no framing, and no outside source. There is no TLS (CH-7: no domain or certificate); the WPA3 link protects the cookie. | CH-7, ONB-5 | — |
| L7 | Passthrough (ONB-5) forwards Wi-Fi clients to the uplink with address translation but not to private, link-local, CGNAT, loopback, "this network" (0/8), multicast or reserved destinations, so phones get the internet and not the home network; only replies reach a Wi-Fi client. Before passthrough, DNS answers every name with the box so the setup page opens by itself. This is stricter than ONB-5's text, which names only the box's internal parts. | ONB-5, CH-9 | `NftRules`, `DnsmasqConf`. |
| L8 | The access point itself is a seam: `AccessPoint` is the driver interface, and `HostapdConf`, `DnsmasqConf` and `NftRules` generate what it applies (WPA3-SAE with MFP required, WPA2-PSK only by `WPA2` opt-in, `ap_isolate=1`). The driver, the owner-facing WPA2 switch (which must warn that WPA2 is weaker), and the measured Wi-Fi-up time (ONB-4) come with the image on hardware (P2-1, A1, A6). **For P2-1's brief:** nothing applies `NftRules` yet; P2-1 applies it and A6 tests it, and adds the uplink's own subnet to the passthrough deny set when it is not private. Config values are validated so none can inject a line. | CH-7, ONB-4, ONB-5 | Hardware package. |
| L9 | **Setup is bound to the phone that paired.** Every phone that opens setup gets a setup cookie (SameSite=Strict, HttpOnly) and its own one-time pairing code. Before the owner's number is known any phone on the Wi-Fi may set up; once it is, only the phone whose code paired (or that typed the number and its code) sees or posts later steps, so another phone on the Wi-Fi can neither replace the number nor see the code-generator seed. Pairing by the card's setup code binds no phone: the reply texts a page code, and the phone that types it continues (3 tries, then a fresh code, at most 3 texts an hour). Other phones see "Setup is continuing on the phone that texted the box", and later steps show the number masked. Lost-device escape (arbitrator): the paired phone can start setup over, and any other phone can with the card's setup secret, printed as the reset secret on the recovery sheet (5 wrong tries an hour); starting over re-asks pairing, enrollment, the recovery acknowledgment and the trusted-PC choice. Setup pages are open without sign-in only until setup is done; then they redirect to status and their forms do nothing. Setup progress is persisted (`SetupStore`) without any secret; the code-generator seed stays in memory until the entered code confirms it, then goes to the vault (`Hooks.SaveCodeSeed`) and is wiped. Steps run in §8.1's order, and "this PC is trusted" is accepted only after enrollment and the recovery acknowledgment. Ethernet makes the network step a no-op. Setup is also treated as done when `Hooks.AlreadySetUp` reports an owner or an enrolled seed, so a lost state file never reopens enrollment. Hooks that write to the vault or render a QR code run outside the setup lock, so the modem loop's `OfferText` never waits on them. | ONB-3, §8.1, CH-4 | `setup.go`. |
| L10 | Pairing (ONB-6): the `sms:` link prefills `PAIR <one-time code>` to the box's number (`?&body=`, read by iOS and Android). A text `PAIR <code>` with that code or the card's setup code makes its sender the owner's number, and the box replies "AgentOS is running on [host]" from its own number. Wrong pairing texts are capped at 10 an hour, then the box is silent. Fallback: type the number, the box texts a 6-digit code (3 texts an hour, 3 tries, 15 min). The broker's modem loop calls `Server.OfferText` until an owner exists. | ONB-6, §8.1 | `OfferText`, `number`. |
| L11 | Enrollment accepts the code for the box's current 30-second step or one either side, since the phone's clock may differ slightly. A box whose clock is minutes off fails enrollment; that is visible at once and is a hardware-time matter (§13). | ONB-3 | Learn a clock offset at enrollment. |
| L12 | Connect AI waits only on the first-boot update (`Progress.Updated`), as ONB-4 says. An API key typed here goes to `Hooks.ConnectAPIKey` and is never kept, echoed, or logged; a device-code sign-in shows the provider's https page and code. Each connection asks once, ticked by default, whether that provider may see private data (CAP-9), passed through `Hooks.SetPrivateOK`. Setup finishes as soon as one provider reports connected, checked after each step and on each page load (so a device-code sign-in completed on the provider's site finishes it), and calls `Hooks.Finish` at most once, whose caller starts the owner channel and sends `AllSetText` (ONB-8): three example tasks suited to connected accounts, then "HELP for commands", within three GSM-7 segments. With no provider allowed private data, task text has no route unless it is PUBLIC (§5), so the examples are PUBLIC tasks without accounts. | ONB-3, ONB-4, ONB-8, CRED-5 | `aiKey`, `maybeFinish`. |
| L13 | Pages have no script; the status page refreshes itself while the box is starting (ONB-4), and the setup page only while it waits on the update with nothing to type, so a refresh never wipes what the owner is typing. | ONB-1, ONB-4 | — |
| L15 | **Condition for wiring (P1-7 or P2-1):** the local UI runs as its own uid and process, reaching the owner channel through a narrow socket authenticated by SO_PEERCRED, never inside agentosd, so a bug in an HTTP parser on the Wi-Fi cannot reach broker memory. The ARC-2 import test stays. The page footer and the contact card carry the box page address (card C10). | ARC-2, CH-9 | Wiring package. |
| L14 | Not built here: the live browser view (P2-6), diff and file review, the rules page, card rotation (REC-4, which setup should offer in one line once it exists), the DIY first-boot card page (§8.4), and the unknown-host vault unlock page (P2-4). Each mounts on `Server` without changing it. | CH-8, REC-4, CRED-8 | Later packages. |
