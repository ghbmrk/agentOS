# Local web UI: assumptions

Built for PLAN P2-2 against SPEC v0.12 (§6.2 CH-7 to CH-9, §8.1, ONB-1 and
ONB-3 to ONB-8), plus P1-5's carry-forward (O4): the local UI offers RESUME and a
local unlock that clears challenge mode. Each row is a reading of the spec, or a
gap left for a later package, that a reviewer may want to change.

| L1 | **Sign-in is the local unlock.** One code-generator code or the asked grid cell signs the device in for the CH-3 unlock period and also unlocks chat by text, clears challenge mode and lifts the low-tier lock (`owner.LocalSignIn`). Joining the Wi-Fi already proves the card, so this is at least as strong as a texted `UNLOCK <challenge> <code>`. Local attempts count as wrong codes (CH-18) and have their own fixed 24-hour bound (24), durable across restarts. Per the arbitrator's ruling on #32: every sign-in is texted to the owner ("A phone signed in on the box's Wi-Fi at HH:MM. Not you? Text STOP."), coalesced under CH-15 to one text an hour that lists each sign-in; a wrong local code is texted on the first of a bound window and again when the bound is used up, and every wrong attempt is listed in the digest. Untold sign-ins survive restarts and failed sends. A device is signed out by any lock (wrong codes, an unknown-host boot), even if the owner later unlocks by text: each device session keeps the channel's lock count from sign-in. When the bound is spent the page says sign-in here is paused for up to 24 hours and texting a code still works. | CH-7, CH-14, CH-18, O4 | `owner/local.go`. |
