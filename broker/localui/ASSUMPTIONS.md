# Local web UI: assumptions

Built for PLAN P2-2 against SPEC v0.12 (§6.2 CH-7 to CH-9, §8.1, ONB-1 and
ONB-3 to ONB-8), plus P1-5's carry-forward (O4): the local UI offers RESUME and a
local unlock that clears challenge mode. Each row is a reading of the spec, or a
gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| L1 | **Sign-in is the local unlock.** One code-generator code or the asked grid cell signs the device in for the CH-3 unlock period and also unlocks chat by text, clears challenge mode and lifts the low-tier lock (`owner.LocalSignIn`). Joining the Wi-Fi already proves the card, so this is at least as strong as a texted `UNLOCK <challenge> <code>`. Local attempts count as wrong codes (CH-18) and have their own fixed 24-hour bound (24), durable across restarts. Per the arbitrator's ruling on #32: every sign-in is texted to the owner ("A phone signed in on the box's Wi-Fi at HH:MM. Not you? Text STOP."), coalesced under CH-15 to one text an hour that lists each sign-in; a wrong local code is texted on the first of a bound window and again when the bound is used up, and every wrong attempt is listed in the digest. Untold sign-ins survive restarts and failed sends. A device is signed out by any lock (wrong codes, an unknown-host boot), even if the owner later unlocks by text: each device session keeps the channel's lock count from sign-in. When the bound is spent the page says sign-in here is paused for up to 24 hours and texting a code still works. | CH-7, CH-14, CH-18, O4 | `owner/local.go`. |
| L2 | RESUME: a signed-in device resumes with one tap; otherwise the RESUME form takes a code, which signs the device in first. A texted RESUME code issued earlier is voided. STOP needs no sign-in, as by text (its worst case is a pause). | CH-3, CH-11 | `resume`, `stop`. |
| L3 | Without sign-in, only `/status`, `/unlock` (and `/unlock/vault`, the unknown-host vault unlock, L16), `/box.vcf` and, until setup is done, `/setup` answer. The status page shows only boot progress, running or stopped, and whether codes are locked. Everything else, including pages later packages add with `Mount` (CH-8: live browser view, diffs and files, rules), needs sign-in. | CH-7, CH-8 | Route table in `server.go`. |
| L4 | Remembered devices live in memory (token hashes, at most 16), so a restart signs every device out. That is also what a boot on an unknown host needs (CH-14). A device's sign-in must lie within the channel's current unlock, so when the session locks (wrong codes, an unknown-host boot) every device is signed out; a later unlock that reaches past a device's own expiry readmits it until that expiry. The sign-in page says "7 days, or until the box restarts". | CH-7, CH-18 | Persist them if restarts prove frequent. |
| L5 | **CH-9 has three layers:** the listener is bound to the access point's address and, with `SO_BINDTODEVICE`, to its interface, so the home network or an agent machine's link cannot reach it even where routing would deliver the packet; every request's source must be in the access point's subnet and not the box itself; and `NftRules` accepts the UI port only from the access point and drops it everywhere else. `New` and `Listen` refuse a public, unspecified or loopback address. | CH-9 | — |
| L6 | Any host name other than the box's address is a captive-portal check or DNS rebinding: GET and HEAD are redirected to the box, anything else is refused. Posts carrying a cross-site `Origin` or `Sec-Fetch-Site` are refused, and the cookie is `SameSite=Strict`, `HttpOnly`. Pages set a CSP with no script, no framing, and no outside source; the vault unlock page alone adds one script allowed by its SHA-256 hash (L17). There is no TLS (CH-7: no domain or certificate); the WPA3 link protects the cookie. | CH-7, ONB-5 | — |
| L7 | Passthrough (ONB-5) forwards Wi-Fi clients to the uplink with address translation but not to private, link-local, CGNAT, loopback, "this network" (0/8), multicast or reserved destinations, so phones get the internet and not the home network; only replies reach a Wi-Fi client. Before passthrough, DNS answers every name with the box so the setup page opens by itself. This is stricter than ONB-5's text, which names only the box's internal parts. | ONB-5, CH-9 | `NftRules`, `DnsmasqConf`. |
| L8 | The access point itself is a seam: `AccessPoint` is the driver interface, and `HostapdConf`, `DnsmasqConf` and `NftRules` generate what it applies (WPA3-SAE with MFP required, WPA2-PSK only by `WPA2` opt-in, `ap_isolate=1`). The driver, the owner-facing WPA2 switch (which must warn that WPA2 is weaker), and the measured Wi-Fi-up time (ONB-4) come with the image on hardware (P2-1, A1, A6). **For P2-1's brief:** nothing applies `NftRules` yet; P2-1 applies it and A6 tests it, and adds the uplink's own subnet to the passthrough deny set when it is not private. Config values are validated so none can inject a line. | CH-7, ONB-4, ONB-5 | Hardware package. |
| L9 | **Setup is bound to the phone that paired.** Every phone that opens setup gets a setup cookie (SameSite=Strict, HttpOnly) and its own one-time pairing code. Before the owner's number is known any phone on the Wi-Fi may set up; once it is, only the phone whose code paired (or that typed the number and its code) sees or posts later steps, so another phone on the Wi-Fi can neither replace the number nor see the code-generator seed. Pairing by the card's setup code binds no phone: the reply texts a page code, and the phone that types it continues (3 tries, then a fresh code, at most 3 texts an hour). Other phones see "Setup is continuing on the phone that texted the box", and later steps show the number masked. Lost-device escape (arbitrator): the paired phone can start setup over, and any other phone can with the card's setup secret, printed as the reset secret on the recovery sheet (5 wrong tries an hour); starting over re-asks pairing, enrollment, the recovery acknowledgment and the trusted-PC choice. Setup pages are open without sign-in only until setup is done; then they redirect to status and their forms do nothing. Setup progress is persisted (`SetupStore`) without any secret; the code-generator seed stays in memory until the entered code confirms it, then goes to the vault (`Hooks.SaveCodeSeed`) and is wiped. Steps run in §8.1's order, and "this PC is trusted" is accepted only after enrollment and the recovery acknowledgment. Ethernet makes the network step a no-op. At every start where setup is not done, it is treated as done if `Hooks.AlreadySetUp` reports that Finish completed (the owner channel exists), so neither a lost state file nor a failed save after Finish reopens enrollment; an enrolled seed alone never closes setup, so a reboot mid-setup or after starting over resumes where it was. `AlreadySetUp` must read a durable marker Finish writes and answer true when in doubt; it is also asked after a failed Finish, so a Finish that fails after the owner channel exists still closes setup. Once setup is done no step changes its state (checked under the setup lock), and starting over is refused while Finish runs. The setup cookie lasts 7 days (`SetupCookieFor`) so it survives a browser restart; pairing codes beyond 8 phones evict the oldest; an enrollment checked against a seed that a restart replaced is not saved. Hooks that write to the vault or render a QR code run outside the setup lock, so the modem loop's `OfferText` never waits on them. | ONB-3, §8.1, CH-4 | `setup.go`. |
| L10 | Pairing (ONB-6): the `sms:` link prefills `PAIR <one-time code>` to the box's number (`?&body=`, read by iOS and Android). A text `PAIR <code>` with that code or the card's setup code makes its sender the owner's number, and the box replies "AgentOS is running on [host]" from its own number. Wrong pairing texts are capped at 10 an hour, then the box is silent. Fallback: type the number, the box texts a 6-digit code (3 texts an hour, 3 tries, 15 min). The broker's modem loop calls `Server.OfferText` until an owner exists. | ONB-6, §8.1 | `OfferText`, `number`. |
| L11 | Enrollment accepts the code for the box's current 30-second step or one either side, since the phone's clock may differ slightly. A box whose clock is minutes off fails enrollment; that is visible at once and is a hardware-time matter (§13). | ONB-3 | Learn a clock offset at enrollment. |
| L12 | Connect AI waits only on the first-boot update (`Progress.Updated`), as ONB-4 says. An API key typed here goes to `Hooks.ConnectAPIKey` and is never kept, echoed, or logged; a device-code sign-in shows the provider's https page and code. Each connection asks once, ticked by default, whether that provider may see private data (CAP-9), passed through `Hooks.SetPrivateOK`. Setup finishes as soon as one provider reports connected, checked after each step and on each page load (so a device-code sign-in completed on the provider's site finishes it), and calls `Hooks.Finish` at most once, whose caller starts the owner channel and sends `AllSetText` (ONB-8): three example tasks suited to connected accounts, then "HELP for commands", within three GSM-7 segments. With no provider allowed private data, task text has no route unless it is PUBLIC (§5), so the examples are PUBLIC tasks without accounts. | ONB-3, ONB-4, ONB-8, CRED-5 | `aiKey`, `maybeFinish`. |
| L13 | Pages have no script (the vault page's photo shrink, L17, is the one exception and optional); the status page refreshes itself while the box is starting (ONB-4), and the setup page only while it waits on the update with nothing to type, so a refresh never wipes what the owner is typing. | ONB-1, ONB-4 | — |
| L15 | **Condition for wiring (P1-7 or P2-1):** the local UI runs as its own uid and process, reaching the owner channel through a narrow socket authenticated by SO_PEERCRED, never inside agentosd, so a bug in an HTTP parser on the Wi-Fi cannot reach broker memory. The ARC-2 import test stays. The page footer and the contact card carry the box page address (card C10). | ARC-2, CH-9 | Wiring package. |
| L14 | Not built here: the live browser view (P2-6), diff and file review, the rules page, card rotation (REC-4, which setup should offer in one line once it exists), and the DIY first-boot card page (§8.4). Each mounts on `Server` without changing it. | CH-8, REC-4, CRED-8 | Later packages. |
| L16 | **Vault unlock page (P2-4e).** `/unlock/vault` is served when `Config.Vault` is set (`NewUnlockClient` on the vault process's `unlock.sock`), open without sign-in like `/unlock` (CH-7): an unknown-host boot has no signed-in device. It shows HW-5a's sentence at the point of use ("If this drive was out of your hands, unlock it only on your trusted PC."), takes the passphrase, then asks on the same phone for a code-generator code by the pending unlock's expiry; the passphrase alone opens nothing (egress K5, A8). The passphrase is never echoed into a page, logged, or kept after the call (the typed field's read buffer and the JSON request body to the vault are cleared; the passphrase's Go string copies are left to the collector). Residual (#50 security C4): someone who learns the Wi-Fi password can stand up a look-alike access point (WPA3-SAE does not authenticate the access point to a phone that knows the password) and phish the passphrase from a page that looks like this one; with a stolen drive that opens the vault offline, since the code-generator code only authorizes an unlock on a running box. Carry-forward to the card and setup copy: say not to share the box's Wi-Fi password. | CRED-8, HW-5a, CH-6, CH-7 | `vault.go`. |
| L17 | **Photo, not camera.** The page has no script (ONB-1) and plain HTTP gets no live camera, so the phone uploads a photo (`accept="image/*"`, which offers the camera on iOS and Android; iOS is expected to send its HEIC photos to a web form as JPEG [inference, check on the phones in S1]). The box decodes JPEG and PNG and finds the QR code with gozxing (`github.com/makiuchi-d/gozxing` v0.1.1, MIT, pure Go port of ZXing; vendored with `golang.org/x/text` v0.22.0 and `golang.org/x/xerrors`): hand-writing a QR detector robust to tilt, blur and uneven light would be the riskier choice, and no Go standard library decoder exists. Only the local UI links it, which runs as its own process (L15), never agentosd (ARC-2). The card holds two codes: a payload with a URI scheme (`WIFI:`, `otpauth:`, `http:`) is never the passphrase, so a photo of the whole card works, and a photo of only the Wi-Fi code says so. A larger photo is shrunk on the phone (#50 arbitrator): the page's one inline script, allowed by its hash in the CSP (`vaultCSP`), redraws a photo over 12 MP as a baseline JPEG of 12 MP before the form is sent, so a 48 MP camera photo just works; it fetches nothing and posts nothing itself, and without script the form sends the photo as is and the box's bounds (L18) apply, refused with "Type the passphrase words, or use a lower-resolution photo." Checked in headless Chromium under the page's CSP: an 8000x6000 JPEG arrived as a 4000x3000 baseline JPEG, and unchanged with script off. Measured on synthetic 12 MP photos: tilt up to 40°, mild keystone and blur decode in about 0.4 s on a cloud core; strong keystone fails, and the page then asks for a flatter photo or the typed words. | CRED-8, ONB-1, ARC-2 | `scan.go`. |
| L18 | **Upload bounds.** The photo is read part by part into memory (never `ParseMultipartForm`, which spools to a temporary file), so a photo of the passphrase never reaches the drive. At most 20 MiB and 24 MP (a 12 MP phone photo has room; a 24 MP baseline 4:2:0 JPEG decodes to about 36 MB), 12 MP for a progressive JPEG (Go's progressive decoder keeps every coefficient as an int32: an 8000x6000 4:4:4 one of 550 KB peaked at about 700 MB in the #50 L3 review, so 12 MP bounds it near 180 MB), and 16-bit channels refused, all checked from the header before decoding; reduced to 2048 px on the long side (then 1024 and 3072 if needed) before the search, every passphrase post spends an attempt (L19) before its body is read, photo or not, so scans are budgeted too; one upload at a time, admitted before the body is read and given 60 s to arrive, so parallel uploads cannot each hold a photo: a second upload meanwhile is refused, not queued. Go's image decoders and gozxing are memory-safe; these bounds are against exhaustion, a panic in them is reported as an unreadable photo (`scanSafe`), and `FuzzScanPassphrase` exercises them. `TestDaemonAndVaultProcessLinkNoScanner` keeps gozxing and this package out of agentosd and the vault process. The photo buffer (and any repeated photo part) is cleared on every path; copies inside the decoders are left to the collector. **Wiring condition:** the local UI's unit gets a memory ceiling (systemd `MemoryMax`, and `debug.SetMemoryLimit` in its main, #50 arbitrator) so even a decoder worst case cannot press on the broker and journal at the HW-4 floor. | CRED-8 | `MaxPhotoBytes`, `MaxPhotoPixels`. |
| L19 | **Typed fallback.** Typed words win over a photo when both are sent; the vault process normalizes (egress K3), so case and spacing do not matter. Wrong passphrases are not counted (egress K5), so someone with the Wi-Fi password but not the passphrase cannot lock the owner out. They could still starve the owner's attempt, since the vault's attempts share one slot spaced 2 s apart, so the page spends a budget before forwarding (passphrase and boot PIN alike): one attempt per 10 s and 20 an hour per phone address, and 120 an hour on the Wi-Fi as a whole, which bounds an attacker rotating addresses; refused attempts never reach the vault. A phone holding the pending unlock's cookie (it has given the passphrase) or signed in (it has given a code) is exempt from the Wi-Fi-wide budget, though not from its own (#50 arbitrator), so rotating addresses cannot starve the owner's PIN and code steps or a signed-in owner. An attacker can still spend the Wi-Fi-wide budget against a first try that has neither, so the vault process tells the owner of wrong passphrases, at most once per 10 minutes with a count (`custody.noteWrongPassLocked`). | CRED-8 | — |
| L20 | **The code goes to the phone that sent the passphrase.** The vault's ticket stays in the local UI's memory, bound to a random `HttpOnly`, `SameSite=Strict` cookie scoped to `/unlock/vault` on the phone that sent the passphrase. Another phone on the Wi-Fi sees that an unlock waits and when it ends by itself, and cannot answer it. There is no cancel button: the local UI cannot cancel only a pending unlock without racing a confirm that just opened the vault. Instead the waiting page offers "Start over on this phone" with the card: a new correct passphrase supersedes the pending unlock inside the vault process (egress K5), so a lost cookie or a local UI restart costs one more scan, not the 15-minute expiry; a wrong passphrase leaves the pending unlock alone. A wrong code keeps the form with the vault's tries left; a lockout shows the vault's retry time. CRED-8's flow text has the owner reply to the unlock text with the code; until the owner channel can reach the vault process for this (wiring package), the code is typed here, on the same phone, which keeps it on the box's Wi-Fi. | CRED-8, CH-4, CH-18 | Text reply: wiring package. |
| L21 | **Boot PIN and texts.** When the vault process's status reports `pin` (a trusted PC with a boot PIN, P2-4b, #42), the page asks for the PIN first and still offers the card. When the status reports `boot_changed` (a trusted PC booted a path the box never approved), the page shows #42's notice for the cause (box updated, Secure Boot changed, or unknown with a tampering warning) and offers "Keep this PC trusted" with the code, sent as `keep_trusted`; it is never ticked by default: `updated` and `secure_boot` come from the drive, so they only choose the wording (#42 T6), and a release the updater verified unlocks unattended without reaching this page. Before #42 the vault process sets none of these fields, so neither form shows. The owner texts about the unlock (pending, unlocked, wrong code with tries left, lockout) are not sent from this page: the vault process is the one place that sees every attempt, including one that skips this page, and reports through `custody.notify` (egress K6), which the wiring package routes to the owner channel. One code unlocks the box and signs the phone in (P2-4f; UX-50-1, PU1 on #50): after a confirm succeeds, the local UI signs the same phone in through the owner channel with `owner.UnlockProofPrefix` plus the confirmed ticket as the code, which the channel checks through `verify.sock` like any code (egress K7). The vault process accepts that proof once, within a minute of the confirm, so the local UI never gets a codeless sign-in and a ticket replayed later signs nobody in. If the channel refuses it (or there is no channel yet), the open page links to sign-in with the next code. Only the phone holding the ticket cookie is signed in. A typed sign-in code is never taken as such a proof, and a refused proof is not counted as a wrong code by the owner channel (the vault process counts a wrong one). | CRED-8, CH-14 | P2-4b, wiring package. |
| L22 | **Interrupted passphrase change (P2-4g, UX lens on #63).** When the vault process refuses a passphrase with "a passphrase change was interrupted; try your new passphrase", the page shows "A passphrase change was interrupted. Try your new passphrase, or your old one if that fails." (UX and potency on #93: the old one still opens when the change never took) instead of the wrong-passphrase line. When its status reports `change_unfinished` (the passphrase opened beside a change that never took effect), the code step and the unlocked page show "Your passphrase change did not finish; change it again." as a neutral notice, since the unlock worked Both lines are fixed and reveal only that an interrupted change exists. The vault answers "interrupted" for any passphrase that opens neither keys file while a staged file changes the passphrase, so a typo then also gets that line; the passphrase the unsealed change would have set is a plain wrong passphrase. A crash after the keys file was written but before the vault recorded it leaves the staged file equal to the keys file, so the old passphrase then gets the plain line. | CRED-8, CRED-9 | Vault process wording (egress K11). |
