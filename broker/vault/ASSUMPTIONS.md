# Vault: assumptions

Started with VAULT-REDACT (#1735) against SPEC CRED-7 and A14. Covers what `broker/vault`'s redactors rest on. Each row is a reading of the spec, with what changes if the reading is wrong.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| A1 | **Plan-login fields (VAULT-REDACT).** A `plan-login` entry (`KindPlanLogin`, written by `egress.PlanLogins`) is one JSON value holding a provider CLI's token set. `Redactor` and `HashRedactor` match its whole value and also every string inside it of `MinValueLen` (12) bytes or more, at any depth, each in the same encodings as any vault value, so a token echoed on its own is caught. Two kinds of string are not patterns. Strings under 12 bytes could match innocent text, and no real token is that short. Identifiers, meaning strings under a key `id` or ending `_id` (`isIdentifierKey`) such as `account_id` (a 36-byte UUID in #1747's Codex entry), are not secret, and the placeholder `id_token` the broker hands the CLI carries the account ID in its payload, so matching it would corrupt that login on every refresh and let a guest confirm a guessed ID. Every other key stays a pattern, so an unknown credential field is redacted by default. Other kinds are matched as whole values only. A value that is not valid JSON is matched whole. A JWT's three parts are not split: a lone part of an `id_token` echoed without its dots is not matched. | CRED-7, A14 | If another kind stores a structured value, add it to `redactValues`. If a provider names a credential field `*_id`, or keeps a non-secret identifier under another key that a placeholder echoes, change `isIdentifierKey`. If a provider's token is shorter than 12 bytes, lower the floor for that kind. |
