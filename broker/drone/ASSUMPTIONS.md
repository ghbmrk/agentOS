# Drone key-holder: assumptions

Each row is a reading of the spec, or a property the code relies on, that a
reviewer may want to change. Pin: ArduPilot `Copter-4.7.2`
(`fb773567896014da007bca58358704d4a0d8516f`, `sitl/ardupilot.pin`).

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| DRONE-sim-1 | **Channel 0.** Stock ArduPilot accepts every unsigned frame on `MAVLINK_COMM_0` and `RADIO_STATUS`/`RADIO` on every channel (`GCS_Signing.cpp::accept_unsigned_callback`, the same on `master` on 2026-10-28). `MAVLINK_COMM_0` is the first port whose protocol is MAVLink, so no parameter closes it. The aircraft's firmware therefore carries `sitl/ardupilot-signed-only.patch`, which makes that callback accept nothing. The SITL build applies it, and DRONE-enforcer's signed firmware build applies the same file. Decided on #3516 (issuecomment-6458401915, option A). | NET-2 Drones ("refuses an unsigned command"), A18 | **Upstream tracking:** on every pin bump, re-read `accept_unsigned_callback`. `build.sh` fails if the patch no longer applies, and `TestUnsignedFramesChangeNothing` fails if a port takes an unsigned frame. Drop the patch once upstream has an option that refuses unsigned frames on channel 0. |
| DRONE-sim-2 | MAVLink 2 signing is symmetric: the flight controller verifies with the same 32-byte secret the key-holder signs with. The secret therefore exists in the key-holder process and in the aircraft's storage (its EEPROM or FRAM), and nowhere else. | NET-2 ("only the enforcer holds the key"), P2 | A key extracted from the aircraft's storage signs commands. Physical custody of the aircraft is part of the trusted set, and DRONE-dock (#3518) keeps it in the locked dock. |
| DRONE-sim-3 | **Provisioning.** The first key goes over an unsigned `SETUP_SIGNING` frame, accepted only while the aircraft holds no key. It is sent on the physical set-up link (USB at the bench), never on the radio or the network. Once a key is stored, a re-key must be signed. | NET-2 | If the aircraft is ever wiped (a firmware reflash that erases its storage), it accepts unsigned frames until it is provisioned again. DRONE-enforcer's boot read-back fails on an unsigned aircraft, because nothing reads back over the signed link. |
| DRONE-sim-4 | Signatures carry a timestamp in 10 µs units since 2015-01-01, from the wall clock, strictly increasing per link (`Link.Send`). ArduPilot refuses a frame that is not newer than the last one on its (link id, system, component) stream, and keeps those streams across ports. After the aircraft reboots it accepts frames at or above its last saved timestamp, so about the last 30 s of captured key-holder frames can be replayed, in order, once. | NET-2 (replay) | The aircraft also refuses a frame signed more than a minute behind its own clock, and every boot sets that clock a minute past its last saved value, so two boots in quick succession put it more than a minute ahead of real time. The key-holder therefore signs no lower than the newest verified frame from the aircraft (`Link.peerTS`): neither its own clock stepping back nor repeated boots lock it out (`TestLinkFollowsTheAircraftClock`). The reboot window is narrowed by the key-holder's heartbeat (`Link.KeepAlive`, every second while the link is up, and `Dial` sends one at once): the first one the booted aircraft accepts raises its timestamp past every capture (`TestKeepAliveBeatsEverySecond`). What is left is the second or so between the aircraft's boot and that heartbeat, in which captured key-holder frames could be replayed in order at an aircraft that is disarmed and has not yet passed its pre-arm checks. |
| DRONE-sim-5 | The key-holder trusts only signed frames from the aircraft (`frame.Reader` with `InKey`, from system 1, component 1), and no captured one, whichever of the two clocks is wrong, with one exception below. Before its first answer the link anchors to the aircraft's signing clock: it sends `TIMESYNC` with a random nonce, and only a signed `TIMESYNC` echoing it (ArduPilot answers on the same channel, `GCS_MAVLINK::handle_timesync`) gives the anchor's timestamp and signing stream. After that a frame counts only on the anchor's stream, strictly newer than the last on it, at or above the anchor and at most the time since plus 10 s above it (`clockSlack`; the aircraft's clock moves one unit a frame and jumps only to a later GPS time), and a reply only when it is also at or above the request's timestamp, since ArduPilot raises its clock to the newest it accepts. That last rule proves a reply was signed after its request only while the aircraft's clock is not ahead of the key-holder's; the one answer that decides a mode change (follow leaving AUTO, DRONE-sim-18) is bound to a fresh nonce instead, and binding every reply so is owed to DRONE-enforcer. So an old capture is below the anchor, a capture signed by a clock pushed ahead (a GPS spoof) is above the bound, and a key-holder clock far behind an aircraft that has sent it nothing gets no anchor (`TestCapturedFramesAreNoAnswer`); once a verified frame arrives the key-holder signs at or above it (DRONE-sim-4). Heartbeats follow the same rule. | P3 | If telemetry ever arrives unsigned (for example a stock radio inserting `RADIO_STATUS`), it is dropped and counted (`Link.Dropped`), never trusted. A GPS jump ahead of the anchor mid-session, or the aircraft rebooting under an open link (its clock jumps 60 s at boot), fails the exchange under way, which drops the anchor so the next one re-anchors with a fresh challenge (`exchangeLocked`, `TestLinkReanchorsAfterAircraftBoot`): closed, and a heartbeat signed after the jump counts only after that re-anchor. A firmware that stopped answering `TIMESYNC` would leave every link unanchored: closed. The exception: an attacker who can step the enforcer's clock more than 60 s ahead, power-cycle the aircraft within 30 s and relay its radio can capture replies that a later anchor admits. DRONE-enforcer closes it with an authenticated time source or by capping the key-holder's timestamps once anchored. |
| DRONE-sim-6 | The parameter names and values in `derive.go` are from the pin's parameter docs: `FENCE_*`, `BATT_LOW_VOLT`, `BATT_FS_LOW_ACT` 2 (RTL), `FS_GCS_ENABLE` 1 (RTL), `FS_GCS_TIMEOUT` (2 to 120 s), `FS_EKF_ACTION` 1 (land), `FS_THR_ENABLE` 0, `RC_PROTOCOLS` 0 (no RC protocol decoded), `ARMING_SKIPCHK` bit 6 (RC), `SCR_ENABLE` 0, `RTL_ALT_M` (metres; 4.7 renamed `RTL_ALT`), `RALLY_INCL_HOME` 0, `MAV_GCS_SYSID` 255, `MAV_OPTIONS` bit 0 (only the ground station's system id), `MAVn_OPTIONS` 0 (signing not disabled on a port), `FS_OPTIONS` 0 (no failsafe continues a flight), `BATT_LOW_TIMER` 10 s, `AUTO_OPTIONS` 3 (bit 0 arming in AUTO, bit 1 take-off with no throttle raised: there is no receiver), `AVOID_ENABLE` 0 (DRONE-sim-18), `FENCE_OPTIONS` 1 (bit 0: the aircraft refuses any mode change while its breach return runs, `mode.cpp` "in fence recovery"). | NET-2 (limits as parameters) | A renamed parameter reads back as unreadable, and the aircraft refuses to arm: fail closed. A pin bump re-checks the list. |
| DRONE-sim-7 | SITL has three MAVLink ports, so the read-back covers `MAV1_OPTIONS` to `MAV3_OPTIONS`. The airframe's port count is DRONE-enforcer's to set in `Derive`. | NET-2 | A port missing from the list could have signing turned off by a signed write. Only the key-holder can make that write, but the read-back would not catch it. |
| DRONE-sim-8 | **Firmware.** SITL has no bootloader, so "unsigned firmware is refused" is not tested here. ArduPilot's secure bootloader (`Tools/scripts/signing/`) refuses an image that is not signed by a key it was built with. That clause is owed by DRONE-enforcer's hardware run (#3516 question 4). This row covers the in-flight paths that can load code: MAVLink FTP writes (test 1) and Lua scripts (`SCR_ENABLE` 0, test 6). | A18 ("refuses an unsigned ... firmware") | Until the hardware run passes, firmware refusal is an assumption, not a tested property. |
| DRONE-sim-9 | The owner key in this row is a test key, used in the tests only. DRONE-enforcer replaces it with the NET-4 passkey flow. The policy signature covers a domain string followed by the canonical record (`policyDomain`), and the canonical form is `encoding/json`'s marshalling of `Policy`, checked byte for byte at load. | NET-4 | A second signer of the same record format must produce byte-identical JSON, or its policies are refused. |
| DRONE-sim-10 | Geometry is checked on an equirectangular projection about the dock, for sites within 10 km of it (`maxSpanM`). Every waypoint, and every leg from the dock through the route and back, stays at least the fence margin inside the boundary and outside every no-fly zone. | NET-2 (boundary, no-fly zones) | A bigger site needs a better projection. The aircraft's own fence is still exact, because it holds the same vertices. |
| DRONE-sim-11 | The key file is exactly 32 raw bytes, mode 0600, a regular file (not a symlink or FIFO) owned by the process's user. `WriteKeyFile` never replaces an existing file, because that could be the only key the aircraft accepts. The owner check runs only when the test runs as root, which CI's SITL job does not. It is code-read otherwise. | P2 | — |
| DRONE-sim-12 | `RADIO_STATUS` sent unsigned only changes the telemetry stream rate (`stream_slowdown_ms`, at most 2 s). With the patch it is refused like any other frame, so a stock SiK radio's flow control is lost. That is acceptable, because the drone's link is not a SiK radio. | NET-2 | If a SiK-style radio is used, telemetry may be throttled. Nothing on the aircraft changes. |
| DRONE-sim-13 | The key-holder's state directory is part of its trusted base, like the key file. A restart re-verifies the stored policy's signature but has no older version to compare, so an older signed policy put there is loaded. The aircraft still refuses to arm on it until a load of the newer one reads back. | NET-4 | DRONE-enforcer keeps the directory on the enforcer's sealed store; if the directory can be written by anyone else, the version rule no longer holds across restarts. |
| DRONE-sim-14 | **RC.** `RC_PROTOCOLS` 0 stops the aircraft from taking up an RC protocol (`AP_RCProtocol::detect_async_protocol`), but not one it already decodes, which keeps working until a reboot. The aircraft reports an RC receiver in `SYS_STATUS` once it has decoded any RC input or override since boot, and nothing clears that before a reboot (`RC_Channels::read_input`, `GCS::update_sensor_status_flags`). So the read-back also refuses while that bit is set: with the policy in force from boot, no RC input is ever decoded. Stock SITL decodes RC from its first boot, so every first load is followed by a reboot (`newRig`), as provisioning a real airframe is. | NET-2 (no unsigned control path) | A firmware that clears the bit without a reboot, or decodes RC without setting it, would hide a live RC path. A pin bump re-checks both functions. |
| DRONE-sim-15 | **Flights.** A flight record (`flight.go`) is the owner's turn-on: an id of 32 hex digits, a route the policy in force names, the animal kinds it may follow (possibly none), and a not-after time at most 24 h ahead, signed over its own domain string (`flightDomain`) and canonical form like the policy. The key-holder records the id as used (`flights-used` in its state directory, replaced atomically, expired ids dropped, so a clock stepped back past a record's not-after could fly it again: DRONE-enforcer's trusted time source owns that) after the read-back passes and before the mission upload, so a flight that then fails to start has still used its record: the owner signs another. Zone flights (#3516 question 2) are a named route; there is no zone record. | NET-6 | A state directory written by anyone else could forget used ids (as DRONE-sim-13). A corrupt used set refuses every flight. |
| DRONE-sim-16 | **Mission.** A flight's mission is home (item 0, which the aircraft replaces), take-off to the first waypoint's height, the route's waypoints, and RTL, which lands at the dock's rally point (brief decision 8). The key-holder uploads it, sets AUTO, arms and starts it; nothing else arms the aircraft or uploads a mission. The aircraft's own pre-arm checks still apply: an arm before its EKF has a position is refused, and the record is spent. | NET-2, NET-6 | DRONE-enforcer may add a pre-arm wait; the record rule stays. |
| DRONE-sim-17 | **The core-side channel** is a line protocol on a local socket (`-core`), not MAVLink. Exactly `return_to_dock` is a command; `camera_fix <lat> <lon>` (plain decimal degrees) is a report for the GPS/camera check and never a command; every other line is refused with `refused` and logged quoted and cut to 40 bytes; a line over 128 bytes ends the connection. The reader takes 5 lines at once, then one a second, and pauses when over, so a flood waits; the rate is the key-holder's, so a reconnect does not refill it. One connection is served at a time. Who may connect is the socket's file permissions, which DRONE-enforcer sets for the core link. | NET-2, A18 (a camera gets no command except return to dock) | A second command would be a SPEC change. |
| DRONE-sim-18 | **Follow** is a stand-in here: the test calls `Holder.Follow` with target positions, as the onboard vision will on its own path (#3516 question 1, auto-decided; DRONE-enforcer owns the real path). It runs only on a flight whose record names animals, while the aircraft's signed heartbeat (at most 3 s old) shows it armed in AUTO or GUIDED, and steers by a guided velocity of at most 5 m/s. Once the aircraft returns by itself (breach, low battery, lost link) the flight is over and follow is refused. Follow leaves AUTO only on a heartbeat the aircraft signed after the call began: the link anchors afresh with a new `TIMESYNC` nonce and takes only a heartbeat on that stream strictly above the signed echo (`Link.FreshHeartbeat`), which holds whichever clock is ahead, since one merely received late, however long it was held, can predate a return the aircraft started since (ArduPilot starts a breach or low-battery return once); what remains is the one round trip between that heartbeat and the mode change, and `FENCE_OPTIONS` bit 0 makes the aircraft itself refuse GUIDED during a breach return. Still owed by DRONE-enforcer: the route's closing RTL item runs in AUTO, so a follow after the route ends would turn that planned return into GUIDED; the real vision path checks the mission's current item. ArduPilot's avoidance would stop a guided velocity short of the fence (`AVOID_ENABLE` defaults to fence and proximity), so the policy sets it to 0: the fence breach and its RTL are the bound (brief decision 9, `TestBreachLowBatteryLostLinkReturn`). | NET-2 | With avoidance on, a target outside the boundary would hold the aircraft at the fence instead of returning it. |
| DRONE-sim-19 | **The GPS/camera check** (#3516 question 3: kept; the spec-diff follows) takes camera fixes from the core side, which is untrusted, compares each with the aircraft's signed position, and after 3 consecutive fixes further apart than the policy's bound sends RTL. One agreeing fix resets the count. It acts only during a flight. A lying core can cause only a return. SITL's GPS glitch (`SIM_GPS1_GLTCH_X`) moves the reported position after the EKF's own glitch handling, which may also land the aircraft (`FS_EKF_ACTION` 1); either way it comes down. | NET-2 | N and the bound are policy and code values to tune on hardware. |
| DRONE-sim-20 | **Battery.** `BATT_MONITOR` 4 (analog voltage and current) is SITL's monitor and is read back so a monitor turned off fails the read-back; DRONE-enforcer sets the airframe's type in `Derive`, as with the port count (DRONE-sim-7). The low-battery return starts after `BATT_LOW_TIMER` (10 s) below `BATT_LOW_VOLT`. | NET-2 (low battery returns) | A wrong monitor type reads no voltage, so the low-battery return never fires: the hardware run checks it. |
| DRONE-sim-21 | **A return never waits behind a whole failing follow.** Every exchange takes the link's request lock in turn. `FreshHeartbeat` holds it for one try at a time: an anchor and a heartbeat round trip, each bounded by `freshTimeout` (3 s). Before each further try it waits, holding nothing, until no caller is still waiting for the lock (`Link.waiting`, counted by `lockReq`). So a core `return_to_dock` or a camera-check RTL that arrives during a failing follow goes to the aircraft after at most the rest of one try, about 6 s, never all three (`TestReturnWaitsOneFreshTry`). Releasing and re-taking a `sync.Mutex` alone is not enough: the releasing goroutine can re-take it before the woken waiter runs, so the return waited two tries in a mutant run. From #3609's Security accept (#3732). | NET-2 ("return-to-dock accepted") | A steady stream of other requests could hold off a follow's next try, which delays or refuses the follow and never a return. The aircraft's own failsafes don't depend on the link. |
