# Drone key-holder: assumptions

Each row is a reading of the spec, or a property the code relies on, that a
reviewer may want to change. Pin: ArduPilot `Copter-4.7.2`
(`fb773567896014da007bca58358704d4a0d8516f`, `sitl/ardupilot.pin`).

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| DRONE-sim-1 | **Channel 0.** Stock ArduPilot accepts every unsigned frame on `MAVLINK_COMM_0` and `RADIO_STATUS`/`RADIO` on every channel (`GCS_Signing.cpp::accept_unsigned_callback`, the same on `master` on 2026-10-28). `MAVLINK_COMM_0` is the first port whose protocol is MAVLink, so no parameter closes it. The aircraft's firmware therefore carries `sitl/ardupilot-signed-only.patch`, which makes that callback accept nothing. The SITL build applies it, and DRONE-enforcer's signed firmware build applies the same file. Decided on #3516 (issuecomment-6458401915, option A). | NET-2 Drones ("refuses an unsigned command"), A18 | **Upstream tracking:** on every pin bump, re-read `accept_unsigned_callback`. `build.sh` fails if the patch no longer applies, and `TestUnsignedFramesChangeNothing` fails if a port takes an unsigned frame. Drop the patch once upstream has an option that refuses unsigned frames on channel 0. |
| DRONE-sim-2 | MAVLink 2 signing is symmetric: the flight controller verifies with the same 32-byte secret the key-holder signs with. The secret therefore exists in the key-holder process and in the aircraft's storage (its EEPROM or FRAM), and nowhere else. | NET-2 ("only the enforcer holds the key"), P2 | A key extracted from the aircraft's storage signs commands. Physical custody of the aircraft is part of the trusted set, and DRONE-dock (#3518) keeps it in the locked dock. |
| DRONE-sim-3 | **Provisioning.** The first key goes over an unsigned `SETUP_SIGNING` frame, accepted only while the aircraft holds no key. It is sent on the physical set-up link (USB at the bench), never on the radio or the network. Once a key is stored, a re-key must be signed. | NET-2 | If the aircraft is ever wiped (a firmware reflash that erases its storage), it accepts unsigned frames until it is provisioned again. DRONE-enforcer's boot read-back fails on an unsigned aircraft, because nothing reads back over the signed link. |
| DRONE-sim-4 | Signatures carry a timestamp in 10 µs units since 2015-01-01, from the wall clock, strictly increasing per link (`Link.Send`). ArduPilot refuses a frame that is not newer than the last one on its (link id, system, component) stream, and keeps those streams across ports. After the aircraft reboots it accepts frames at or above its last saved timestamp, so about the last 30 s of captured key-holder frames can be replayed, in order, once. | NET-2 (replay) | If the key-holder's clock steps back more than a minute, its frames are refused until the clock passes the aircraft's saved timestamp: the aircraft fails safe, not open. The reboot window is closed by the key-holder sending a signed frame as soon as it sees the aircraft boot, which raises the aircraft's timestamp past every capture; DRONE-sim part b adds that and its test. |
| DRONE-sim-5 | The key-holder trusts only signed frames from the aircraft (`frame.Reader` with `InKey`, from system 1, component 1), and no captured one: each of the aircraft's signing streams must carry strictly increasing timestamps, and a reply answers a request only when its timestamp is at or above the request's (`Link.exchangeLocked`). That holds because ArduPilot raises its signing clock to the newest timestamp it accepts, so only a frame signed after it saw the request can answer it. A heartbeat counts only at or above the timestamp of the link's first frame, which `Dial` sends. A spoofed or replayed `PARAM_VALUE` or mission item therefore cannot make a read-back pass, even on a fresh link (`TestCapturedFramesAreNoAnswer`). | P3 | If telemetry ever arrives unsigned (for example a stock radio inserting `RADIO_STATUS`), it is dropped and counted (`Link.Dropped`), never trusted. If a firmware stopped raising its clock on receipt, no reply would answer and every read-back would fail: closed. |
| DRONE-sim-6 | The parameter names and values in `derive.go` are from the pin's parameter docs: `FENCE_*`, `BATT_LOW_VOLT`, `BATT_FS_LOW_ACT` 2 (RTL), `FS_GCS_ENABLE` 1 (RTL), `FS_GCS_TIMEOUT` (2 to 120 s), `FS_EKF_ACTION` 1 (land), `FS_THR_ENABLE` 0, `RC_PROTOCOLS` 0 (no RC protocol decoded), `ARMING_SKIPCHK` bit 6 (RC), `SCR_ENABLE` 0, `RTL_ALT_M` (metres; 4.7 renamed `RTL_ALT`), `RALLY_INCL_HOME` 0, `MAV_GCS_SYSID` 255, `MAV_OPTIONS` bit 0 (only the ground station's system id), `MAVn_OPTIONS` 0 (signing not disabled on a port). | NET-2 (limits as parameters) | A renamed parameter reads back as unreadable, and the aircraft refuses to arm: fail closed. A pin bump re-checks the list. |
| DRONE-sim-7 | SITL has three MAVLink ports, so the read-back covers `MAV1_OPTIONS` to `MAV3_OPTIONS`. The airframe's port count is DRONE-enforcer's to set in `Derive`. | NET-2 | A port missing from the list could have signing turned off by a signed write. Only the key-holder can make that write, but the read-back would not catch it. |
| DRONE-sim-8 | **Firmware.** SITL has no bootloader, so "unsigned firmware is refused" is not tested here. ArduPilot's secure bootloader (`Tools/scripts/signing/`) refuses an image that is not signed by a key it was built with. That clause is owed by DRONE-enforcer's hardware run (#3516 question 4). This row covers the in-flight paths that can load code: MAVLink FTP writes (test 1) and Lua scripts (`SCR_ENABLE` 0, test 6). | A18 ("refuses an unsigned ... firmware") | Until the hardware run passes, firmware refusal is an assumption, not a tested property. |
| DRONE-sim-9 | The owner key in this row is a test key, used in the tests only. DRONE-enforcer replaces it with the NET-4 passkey flow. The policy signature covers a domain string followed by the canonical record (`policyDomain`), and the canonical form is `encoding/json`'s marshalling of `Policy`, checked byte for byte at load. | NET-4 | A second signer of the same record format must produce byte-identical JSON, or its policies are refused. |
| DRONE-sim-10 | Geometry is checked on an equirectangular projection about the dock, for sites within 10 km of it (`maxSpanM`). Every waypoint, and every leg from the dock through the route and back, stays at least the fence margin inside the boundary and outside every no-fly zone. | NET-2 (boundary, no-fly zones) | A bigger site needs a better projection. The aircraft's own fence is still exact, because it holds the same vertices. |
| DRONE-sim-11 | The key file is exactly 32 raw bytes, mode 0600, a regular file (not a symlink or FIFO) owned by the process's user. `WriteKeyFile` never replaces an existing file, because that could be the only key the aircraft accepts. The owner check runs only when the test runs as root, which CI's SITL job does not. It is code-read otherwise. | P2 | — |
| DRONE-sim-12 | `RADIO_STATUS` sent unsigned only changes the telemetry stream rate (`stream_slowdown_ms`, at most 2 s). With the patch it is refused like any other frame, so a stock SiK radio's flow control is lost. That is acceptable, because the drone's link is not a SiK radio. | NET-2 | If a SiK-style radio is used, telemetry may be throttled. Nothing on the aircraft changes. |
| DRONE-sim-13 | The key-holder's state directory is part of its trusted base, like the key file. A restart re-verifies the stored policy's signature but has no older version to compare, so an older signed policy put there is loaded. The aircraft still refuses to arm on it until a load of the newer one reads back. | NET-4 | DRONE-enforcer keeps the directory on the enforcer's sealed store; if the directory can be written by anyone else, the version rule no longer holds across restarts. |
