# Recall wiring: assumptions

Built for BOARD P3-3b (part 2) against SPEC v0.12 (CAP-3, CAP-4, REV-5,
CRED-8) on the recall index and event bus (#38, #51). It closes the wiring
conditions in [recall/ASSUMPTIONS.md](../recall/ASSUMPTIONS.md) as listed
under W8; part 3 adds deletion reach (W9).

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| W1 | Three broker tools on the guest plane's MCP endpoint: `recall_search`, `owner_preferences`, `recall_note`. Identity (machine and fork lineage) comes from the socket; arguments are a closed set (unknown fields refused), bounded (query 1 KiB, note 16 KiB, 20 facts of 256 bytes, 16 kinds), and rate-limited per machine (burst 30, one per second), since a search scans the index. Errors the guest sees are fixed strings. | ARC-6, CH-2 | Tools grow with the owner-channel package. |
| W2 | `recall_search` scope: `public` reads public items with public statistics and leaves the machine alone; `owner` raises the machine to private first (REV-5). The default is `public` on a public machine and `owner` on a private one (K7). The tool's description says that `owner` narrows the machine's network, so an agent chooses knowingly. | REV-5 | — |
| W3 | Provenance is kept per fork lineage, not per machine: forks share memory and merges join it, so what one machine of a lineage read, all of it may hold. Every item a search returns is recorded (public ones too) durably before the guest sees the result. A note's `DerivedFrom` is the lineage's whole record at that moment, so deleting any source it read deletes the note (K2b). This over-approximates: a note is deleted when any earlier read is, which costs notes, never privacy. A long-lived lineage's record grows with what it reads (33 bytes per item per note); an epoch anchor item can replace the list if that matters. | CAP-3 | Epoch anchors. Small. |
| W4 | A note's kind (`agent`), label (the machine's, K4), receipt time (now, K9) and ref (`<lineage>/<key>`) are set by the broker. A public machine's note is public only while everything its lineage read is public (recall's derived-label rule). | REV-5, CAP-3 | — |
| W5 | The identity key is a 32-byte random entry (`broker-recall-identity`, kind `broker_key`) in the vault, created on first use and carried by the vault's backup, so source IDs survive a restore. `agentosd` fetches it from the vault process over the verify socket (`POST /recall-key`, only while the vault is open) and opens recall then; until the owner unlocks the vault the tools answer that recall opens after the unlock. Handing the key to `agentosd` adds nothing: it holds the index in plaintext memory. The local UI's credential write cannot replace it (wrong kind). | CRED-8, CAP-3 | — |
| W6 | `agentosd` opens recall, the bus with the index's keyer and its recall trigger, and the provenance record under `-recall` (0700), registers the bus's `ForgetSource` as a deletion hook, pumps the bus, and prunes tombstones daily by the 30-day policy (K8). Labels come from the VM manager (`DataLabel`, `RaiseLabel`), which egress and the guest plane read per request, so a raise has taken effect when it returns. Without machines there is no labeler, and owner-scope searches are refused. None of this is on the STOP path (ARC-2 test). | ARC-2, REV-5 | — |
| W7 | Not wired yet, and failing closed meanwhile: no owner-channel authenticator is passed (`WithOwnerAuth`), so preferences (K1) and lowering a label (K6) are refused outright; the owner channel has no preference or relabel command yet, and D1's PUBLIC tasks are not indexed as `task` items yet. No executor ingests into recall yet, so K3 has no caller. No adapter publishes events yet, so the bus runs empty. The vault redactor stays in the vault process; recall scrubs with its pattern scrubber. | CAP-3, D1 | Owner-channel and adapter packages. |
| W8 | Conditions: K2a, K2b, K4, K5, K7, K8, K9 are met here. K1, K3, K6 per W7. | CAP-3 | — |
| W9 | **Deletion reach (K2b, part 3).** A fork lineage the provenance record says was given deleted items, the first at T, is taken back from T: its machines go back to their newest snapshots from before T (the restore point; a snapshot is dated when its capture completes, vm V26) and its snapshots from T on are deleted; the reset time R is recorded durably in the provenance record at once; the journal intents it submitted (origin `guest:<lineage>`) from T until R are erased (journal A12, `Between`), which erases their replay recordings (replay R12); change-pipeline cases on those intents are removed (change C19); then the record forgets what the lineage was given from T until R, and the mark goes. What it reads and does after R is new and stays (#59 L3 2); a record given in the window and given again after R is recorded at the new time, so it stays held (re-review 1). The journal is erased up to when the last machine was back, since an intent submitted during the reset may be from a machine not yet reset (re-review 5). Before T nothing of the item can be in the lineage, because provenance is durable before the guest sees a result. An intent in flight keeps the deletion pending; it is retried every minute and again from the tombstones at every start, finishing a recorded reset rather than repeating it. A crash between the machine reset and its mark resets again: the error is on the side of taking back too much. A running machine restarts on reset, so the guest plane hands its unanswered owner messages out again (guest G5; #59 UX-59-3). In `agentosd` deletions reach the journal and, when machines run, the VM manager; the change pipeline and what learning keeps of the erased intents, when learning runs (change C19). The first production caller of `Index.Delete` must be an authenticated owner deletion or an owner-confirmed source deletion, never an agent request or an agent-triggerable source sync (security A1 on #59, change C19). Without machines nothing is taken back and notes derived from the item stay refused. **Cost:** a rollback loses the lineage's in-machine work since the restore point; W10 puts that to the owner. Threat check: the hook runs only on recall deletions (owner or source deletions, never a guest call); an agent that can delete sources can force rollbacks of lineages that read them and erase their intents' parameters, never their audit trail, decisions or results (Potency PR1, BOARD W7). | CAP-3, REV-4, OP-5 | Narrow the reset to machines that used the item, if that can be known. |
| W10 | **The owner decides lost work (Mark, 2026-10-05; #59 arbitrator).** "Work" is an action the lineage took since T (an intent succeeded, in flight, or of unknown outcome; denied or never-run intents do not count, #59 security B2) or a file changed in its machines since the restore point (`vm.ResetPlan`; memory is not measured; an unmeasurable layer counts). A lineage with no work is taken back at once, untold. One with work is asked about once per lineage, at its earliest deleted item (every open question for a later item, first ask, re-ask or one after a NO, found among the broker's own intents since T, is withdrawn through the gate as superseded, grants GR23; a YES that raced the withdrawal resets nothing and the owner is told the earlier question covers both, #59 L3 third review), by a broker intent `meta.recall.rollback` (origin `broker:recall`, executor `recall`) the grants gate asks as a low-tier text with fixed words that fit the caps and name the item by kind only: "forget a mail you deleted from agent, back to 08:12 Oct 5; 2 actions stay done", to which the owner channel adds ", cannot be undone" (the restore point is the real one, or "back before <the read>" when it could not be measured; a reset cannot recall what left the box, #59 security C1, UX-59-1). The line is fixed at the first ask. **While asking** the agent keeps running but is contained: no fork or merge (vm `Contained`), no pre-allowance (grants GR23), no note derived from the item (recall refuses anything derived from a tombstoned item, R6). **YES** runs it (`Reach.Execute`) and tells the owner the real count: "Done: agent forgot a mail you deleted and is back to 08:12 Oct 5. Its 7 actions since stay done; their details are erased." (UX-59-2), naming only the records that reset took back. The journal is erased to when the machines were back, not when the reset began (#59 L3 re-review 5). A deleted record read after the reset keeps the lineage contained until it is settled. An approval is stale, and undoes nothing, once the lineage no longer holds a deleted item it was given by T (#59 L3 4). A failed reset leaves the approval standing and Retry finishes it. **NO** (the owner's own, journal reason "not approved: owner"): the lineage keeps its work and the record, containment lifts, but notes derived from the item stay refused for good and its tombstone is kept past the prune policy while held (`Index.KeepTombstones`); STATUS says "<agent> still holds a record you deleted". A record deleted after a NO is a new question, asked once. **No answer** (expired, void, restart) is not a decline: the deletion stays pending and the lineage contained, and the question is asked again as a new one a day later (`ReaskEvery`), so a YES or NO is always possible (#59 L3 re-review 3). After a restart the day starts at the first sighting. Until the digest exists that is a text a day per held agent, an interim ruling (DECISIONS.md, #59 lens gate); the digest then carries it as one line under CH-15 pacing and quiet hours (BOARD W5). The item itself is gone from recall at once either way. Before recall opens after a restart (vault locked), which lineages hold a deleted record is not known, so every lineage is contained until the replay at open settles it; with recall not configured, none is (#59 L3 re-review 4). Recall configured but failing to open keeps every lineage contained, and STATUS says "Memory did not open; agents cannot fork or merge" (fail closed, #59 L3 third review). | CAP-3, OP-5, CH-10, CH-13 | The digest line and its YES/NO re-ask (BOARD W5); daily checkpoints of the main lineage so a restore point is near (BOARD W2). |

## A take-back's state and an unrecorded reset (W3-forget-reach)

Built for W3-forget-reach against RCH-1, RCH-2, RCH-3 and CAP-3. Covers `Reach.TakeBackOf`, `Reach.takeBack`, `Reach.Retry`, `Reach.OnTakenBack`, `LateExecutor.TakeBackOf`, `Config.OnTakenBack`, and `Provenance.TakeBackOf`, `MarkBack`, `Backs`, `TakeBacksNotDone`.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| T1 | **A take-back's state from `since` is lineage-blind** (as `Handled`): owed while any take-back recorded not done, any recorded reset not finished, or any unrecorded reset (`MarkBack`) from `since` exists on any lineage; done once one take-back from `since` is marked done and none of those is left; none otherwise. Not known only before recall opens (`LateExecutor`). `Handled` keeps its meaning and never says done. | RCH-1 | Key by lineage once callers hold it. |
| T2 | **A take-back is marked done once its machines are back, approved or not.** An unasked take-back (item 1's idle agent) gets the same done mark, so `TakeBackOf` can report it done (RCH-5). If that mark is lost to a failed write and a restart, the state after finishing reads none, never done. | RCH-1, RCH-5 | — |
| T3 | **An unrecorded reset is kept for Retry** (`MarkBack`): one record holding the take-back's lineage, `since`, and the reset's At and Until, which marks the take-back done (so the machines never go back again) and its reach owed. `Retry` records it with `MarkReset` and then finishes it like any reset, never calling `ForgetSince` again. If `MarkBack`'s own write fails it is kept in memory (as `MarkTakeBack`'s done), so within this process it is never repeated; across a restart the take-back's owed mark makes it run again, which errs on the side of taking back too much (W9). It holds times and a lineage, no task words. | RCH-2, CAP-3 | — |
| T4 | **With `OnTakenBack` set, `Retry` reports each take-back seen not done where a reset can finish (at the start of a settle, or before `Retry`'s own finishing) and done since, whatever finished it, once per `since`, after releasing `run`**, so the hook may call `TakeBackOf`; it does not send `TakenBack`. One a deletion's settle finished is reported by the next `Retry`, and `Owed` stays true until then, so `Service.Run` runs that `Retry` (#569 B1). The set is in memory: after a restart, the caller judges what it owed (agentosd `judgeAgent`). Unset, it sends `TakenBack` as before, now only once the reach is finished. A take-back finished by `TakeBack` itself is not reported (its caller saw the result). | RCH-3 | — |
| T5 | **`service.go` passes `TakeBackOf` and `OnTakenBack` through** (`LateExecutor`, `Config`): outside the brief's declared files, needed for the hook to reach `agentosd`; raised as a brief-gap finding. | RCH-3, RCH-4 | — |
