# camnode/se: assumptions

Built for CAM-node part (b2), CAM-server (#3513, `briefs/CAM-node.md`), against DEV-3, KRN-2 and A16. `broker/camnode/se` is the OPTIGA Trust M class secure-element driver behind `camnode.Element`, carried over from #3583 (closed unmerged; comment 6463126158 on #3513). Each row is a reading a later change could overturn.

| # | Assumption | Basis | If it changes |
|---|---|---|---|
| CAM-se-1 | **The driver follows Infineon's host library (MIT), not a board.** Frame layout, CRC-16/KERMIT, the I2C registers, command codes, tags and object IDs are read from `optiga-trust-m` `src/comms/ifx_i2c` and `src/cmd/optiga_cmd.c`; the presence bit `0x08` and the response layout are inferences. The tests' transcripts are built from that source, not recorded from an element, so part (d) records real transcripts and the driver is corrected against them before the node is trusted. No shielded connection, chaining or retransmission: any bad frame fails the call and the server fails closed. | Brief question 6 [Inference] | The shielded connection (a pairing secret between host and element) would bind the element to this board; a row once (d) has a board. |
| CAM-se-2 | **Objects:** the device key `E0F1` (only `CalcSign` and `GenKeyPair` name it; nothing reads it), the settings and image counters `E120` and `E121`, the committed bundle's SHA-256 in data object `F1D0` (camnode CAM-server-3), and the device key's public point in `F1D1`, written by `Generate` at provisioning. | camnode CAM-server-3 | — |
| CAM-se-3 | **Counters are 32 bits and count at most 255 per command.** `CommitBundle` and `RaiseImage` refuse a counter at or below the element's, or past 2^32 − 1, before anything is written, so a record never names a bundle whose counter the element cannot reach (the next start could not complete it). One bundle may step by camwire's `MaxCounterStep` (2^20), about 4,100 count commands, so numbering should step by small amounts. | OPTIGA monotonic counter objects | A 64-bit counter needs two objects or another element. |
| CAM-se-4 | **The device key's slot is locked at provisioning (part d), not here.** `Generate` makes the key and stores its public point; locking the key slot's and the counters' metadata and the element's lifecycle state is part of the live provisioning (#3583 Security, later finding). The server never calls `Generate`. | Brief design point 4 | — |
| CAM-se-5 | **The driver serialises its own calls**: the link carries one exchange at a time, and handshakes sign while a bundle commits, so every method holds the driver's lock for its commands (`TestOptigaConcurrent`). | camnode `Element` | — |
