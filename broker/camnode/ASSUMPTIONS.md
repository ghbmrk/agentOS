# camnode: assumptions

Built for CAM-node part (b1), CAM-server (#3513, `briefs/CAM-node.md`), against DEV-2, DEV-3, NET-2 (Cameras), NET-4, KRN-2 and A16. `broker/camnode` is the camera node's server and `broker/camnode/se` its secure-element driver; both link `broker/camwire` (part a). Part (b2) adds the sources, the image update and the binary. Each row is a reading a later change could overturn.

| # | Assumption | Basis | If it changes |
|---|---|---|---|
| CAM-server-1 | **A role belongs to a key, not to a request.** The bundle's core key gets the stream and nothing else; its enforcer key gets the settings channel and nothing else (camwire refuses a bundle naming one key in both roles). A client chooses no channel, so there is no channel switch to get wrong, and a key with no role fails the handshake. | Brief questions 1 and 2 | A third role (a second viewer) is a bundle field and a magic change. |
| CAM-server-2 | **The first bundle's window is a button held at power-on, for at most `ProvisionWindow` (10 minutes) or one bundle.** Any client key may connect in the window, and its bundle must name that key as the enforcer's, so the sender of the first bundle is the enforcer the node then trusts. A host on the home network that races the owner in the window provisions the node to its own passkey; the owner's bundle is then refused and the enforcer's page shows the node's fingerprint against the one printed on its case, so the owner sees it and resets. That residual is the brief's question 5 as answered. | Brief question 5, DEV-2 | A first bundle bound to a code shown on the node (a display) would close the race. |
| CAM-server-3 | **The owner pin lives in the element, the bundle on storage.** The element holds SHA-256 over the owner credential's RP ID and point (`OwnerDigest`); every boot verifies the stored bundle again against it and the element's settings counter, so a storage rewrite offline can only restore the bundle already in force. A node whose stored bundle fails admits no client until a button reset. | Brief design point 2 | — |
| CAM-server-4 | **An apply is ordered so a restart at any step recovers.** The bundle is written as pending, its owner pinned (first bundle only), the element's counter raised, then the bundle made current. At boot a pending bundle that verifies at or above the counter is finished; any other is dropped. A first bundle cut short before the pin leaves the node unprovisioned with its counter possibly raised; the owner provisions again with a higher counter. | Brief lifecycle "Restart" | — |
| CAM-server-5 | **Settings are checked against the declared ranges before the counter moves.** `Ranges` (modes, bitrate bounds, IR, thermal shape) is fixed in the node's image (part c); a bundle outside it is refused and burns no counter. | Brief test `TestSettingsWithinDeclaredRanges` | — |
| CAM-server-6 | **The OPTIGA driver follows Infineon's host library (MIT), not a board.** Frame layout, CRC-16/KERMIT, the I2C registers, command codes, tags and object IDs (key `E0F1`, counters `E120`/`E121`, owner pin `F1D0`, public point `F1D1`) are read from `optiga-trust-m` `src/comms/ifx_i2c` and `src/cmd/optiga_cmd.c`; the presence bit `0x08` and the response layout are inferences. The tests' transcripts are built from that source, not recorded from an element, so part (d) records real transcripts and the driver is corrected against them before the node is trusted. The driver runs without the shielded connection, chaining or retransmission: any bad frame fails the call and the server fails closed. | Brief question 6 [Inference] | The shielded connection (a pairing secret between host and element) would bind the element to this board; a row once (d) has a board. |
| CAM-server-7 | **The element's counters are 32 bits and count at most 255 per command.** A bundle counter above 2^32 − 1 is refused by `Raise`; one bundle may raise by up to camwire's `MaxCounterStep` (2^20), which is about 4,100 count commands, so release and bundle numbering should step by small amounts. | OPTIGA monotonic counter objects | A 64-bit counter needs two objects or another element. |
| CAM-server-8 | **The device key's slot is locked at provisioning (part d), not here.** `Optiga.Generate` makes the key and stores its public point; locking the slot's metadata and the element's lifecycle state is part of the live provisioning, where it is checked on the board. Until then nothing in the server calls `Generate`. | Brief design point 4 | — |
| CAM-server-9 | **The signer verifies before it releases.** Every handshake signature from the element is verified under the device key before TLS sends it, so a faulted element signature (a fault attack's lever on ECDSA) never leaves the node. The certificate itself is signed by a throwaway key; the element signs only handshakes. | Brief design point 4 | — |
| CAM-server-10 | **The node's TLS matches the edge link's.** TLS 1.3 only, X25519MLKEM768 only (D-149), ECDSA P-256 with SHA-256, no resumption; `ClientConfig` is the one client definition CAM-clerk and the enforcer use. | D-149, `broker/edgelink/tls.go` | — |
| CAM-server-11 | **The image counter is untouched in part (b1).** A manifest on the settings channel ends the connection until part (b2) stages updates. | Brief split | — |
