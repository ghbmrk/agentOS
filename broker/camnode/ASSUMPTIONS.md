# camnode: assumptions

Built for CAM-node part (b), CAM-server (#3513, `briefs/CAM-node.md`), against DEV-2, DEV-3, NET-2 (Cameras), NET-4, NET-7 and A16. `broker/camnode` is the node's server: one TLS 1.3 port, roles by pinned key, owner-signed bundles applied against the secure element's counters, and image updates to A/B slots. Part (b2) added the update rows, the element driver (`se/ASSUMPTIONS.md`), the capture (`capture/ASSUMPTIONS.md`) and the binary `broker/cmd/agentos-camnode` (the CAM-bin rows here). Each row is a reading a later change could overturn.

| # | Assumption | Basis | If it changes |
|---|---|---|---|
| CAM-server-1 | **The role is the key, not a request.** The bundle's core key gets the stream only and its enforcer key the settings channel only; nothing a client sends picks a channel, so "the enforcer asking for the stream" has no spelling. Any other key, or no certificate, fails the handshake. The bundle refuses one key in both roles (`camwire` `check`). | Brief questions 1 and 2 | — |
| CAM-server-2 | **The first-bundle window opens only when the button is held at power-on**, and that same press erases the bundle (brief question 5: "a full reset needs the button again"). One press is one window: the first bundle that verifies closes it, and so does `FirstBundleWindow` (10 minutes by the monotonic clock) passing, so a node reset and left unprovisioned cannot be claimed by a LAN host later (Security on #3586, finding 1). Within those 10 minutes a LAN host that races the owner can still win; the owner then sees their own provisioning fail and resets again. While open, any P-256 client completes the handshake, but its bundle must name that client as the enforcer, so whoever provisions is the enforcer the owner signed for. | Brief question 5 | A separate reset gesture would split erase from provision. |
| CAM-server-3 | **The element records the bundle's SHA-256 with the counter.** The store keeps bundles by digest and the element's record names the live one, so a store edited offline (an older bundle, another owner's first bundle) does not load: `New` returns `ErrAltered`, and only the button recovers. `CommitBundle` writes the record before the counter; a cut between them is completed by the next start (`TestRestartCompletesCommit`). The element needs one 32-byte data object besides its two counters [Inference: OPTIGA Trust M class elements have such objects; b2's driver confirms]. | Brief design points 2 and 4 | An element with no writable object would need the record signed by the device key instead. |
| CAM-server-4 | **Commit before apply.** A bundle is checked against the declared ranges, stored, committed (record, then counter), and only then given to the source; the counter is never raised for a bundle the node refuses, and no source sees settings that were not committed. | NET-4, brief design point 2 | — |
| CAM-server-5 | **The element signs TLS handshakes only.** The certificate is signed by a throwaway key, as on the edge link, and the signer passes only SHA-256 digests. The node cannot tell a CertificateVerify digest from another digest, so this rests on the server code being the element's only caller. | Brief design point 4; `broker/edgelink/tls.go` | A second use of the device key needs a domain-separated signing path in the element. |
| CAM-server-6 | **Key exchange is X25519MLKEM768 only**, as on the edge link (D-149); the core and the enforcer are this repository's Go, so both offer it. | D-149 | A client without it cannot connect. |
| CAM-server-7 | **One stream at a time.** A newer connection from the core key replaces the older, and a bundle that turns the stream off or changes the core key closes the stream at once. | NET-2 | — |
| CAM-server-10 | **A bundle the source refuses after commit stays committed.** The counter has moved and the bundle is the node's, so the enforcer gets a status with the new counter and the log says "bundle committed, source failed", then the channel ends; a restart applies it again. | L3 on #3586, finding 2 | — |
| CAM-server-11 | **Connections are closed outside the node's lock**, since a close sends close_notify, which a stalled peer can hold up while every handshake waits on the lock. | L3 on #3586, finding 3 | — |
| CAM-server-8 | **Timeouts use the node's monotonic clock only** (handshake 10 s, a write 10 s, settings idle 2 min). They bound a peer's hold on a connection; nothing is ordered by wall time. | Brief design point 4 ("no clock") | — |
| CAM-server-9 | **Manifests open an update on the enforcer's channel only**, after a bundle has applied (never in the first-bundle window); an image chunk outside an update ends the connection. | Brief split (b1 / b2) | — |
| CAM-b2-1 | **The signer verifies before it releases.** Every handshake signature from the element is verified under the device key before TLS sends it, so a faulted element signature (a fault attack's lever on ECDSA) never leaves the node. | Brief design point 4; #3583 | — |
| CAM-b2-2 | **An update is staged, armed for one boot, and kept only once the node is up.** A manifest must carry the release signature, the pinned owner's assertion, this node's fingerprint and a counter above the element's image counter (camwire `VerifyManifest`); its image is written to the inactive slot, hashed against it, armed as the one-shot boot and the board restarted. The trial boot verifies the manifest again with the owner, checks it hashes to the running slot, and once `Serve` has its listener marks the slot good, then raises the image counter. Mark-good comes first: a cut between them boots the new image as the default, whose start then raises the counter; the other order would leave the old image the default under a counter it is below. A trial that fails before `Serve`, or whose mark-good fails, is never kept: any failure of the binary once it has read the tryboot flag restarts the board without tryboot, so the bootloader boots the old slot at once (L3 on #3617, finding 3 and delta finding 2); a failure before that read, or a hang before `Serve`, still needs part c's unit to reboot on a failed or stalled start (`FailureAction=reboot` with a watchdog; Security on #3617, finding 3). A service restart within a trial boot that was already marked good and raised finds the counter equal and starts as settled. "Up" means the listener is open, not that a core has connected. | Brief design point 3, NET-7 | A health check beyond the listener (a frame from the source) would be a later row. |
| CAM-b2-3 | **A settled image needs only the release signature, and a rollback stops the node.** At every start the running slot's manifest must name this node and hash to the slot. Its counter equal to the element's is a settled image (no owner check, so an owner who re-provisioned since still starts it); above, on a boot that is not a trial, is a raise the power cut short or a boot partition edited offline to make an unapproved slot the default, which storage cannot tell apart, so the loaded owner's assertion is required (Security on #3617, finding 1); only a start with no bundle committed (a button start, or one before the first bundle), where the node is unowned, raises on the release signature alone, within `MaxCounterStep`; below, or the factory image (no manifest) under a counter above zero, is a rollback that only an altered boot partition reaches, and `New` returns `ErrRollback` so the camera stays off until re-imaged. | Brief design point 3 ("an image older than the counter is refused") | — |
| CAM-b2-4 | **At most `maxConns` (8) connections are served at once**; one past it is closed before its handshake, and a stream returns as soon as its connection ends even while no frame flows (L3 on #3617, finding 1), so no LAN host can make the element sign or hold goroutines without bound (#3588 item 2; #3583 Security, release finding 1). A LAN host holding eight idle handshakes can still keep the core out, one 10 s handshake timeout at a time. That is accepted: on an untrusted LAN (DEV-2) availability is never assured (a host can jam or ARP-spoof), and the core reports a camera that stops streaming. | DEV-2 | A per-peer cap if the core's reconnect proves starved in practice. |
| CAM-b2-5 | **Nothing is sent in the first-bundle window before a bundle applies** (#3588 item 3): a client that is not provisioning learns no uptime, image hash or counter. | Security on #3586 | — |
| CAM-bin-1 | **The listener is the binary's only socket.** systemd socket activation passes it as fd 3 (`LISTEN_PID`, `LISTEN_FDS`), or `-listen` opens it. `TestNoOutboundDial` runs the binary's `serve` path (everything after the hardware is open) in a network namespace of its own on a passed listener and finds no socket in that namespace; opening the element, the SPI device and the input device is not in that run, and `TestBinaryImportsNoDialer` covers those files by their imports and calls. | Brief acceptance `TestNoOutboundDial` | — |
| CAM-bin-2 | **The A/B slots use the Raspberry Pi bootloader's tryboot.** `autoboot.txt` on the boot partition names the default partition under `[all]` (with `tryboot_a_b=1`) and the one-shot under `[tryboot]`; the bootloader's device-tree node (`/proc/device-tree/chosen/bootloader/partition` and `tryboot`) tells the running partition and whether this is the one-shot; `reboot(2)` with `"0 tryboot"` asks for it [Inference: from the Raspberry Pi bootloader documentation; part d confirms on the board]. `autoboot.txt` is outside the signed boot image, so an offline edit can pick which signed slot boots, which CAM-b2-3 bounds. Each slot's signed manifest is a file on the data partition, removed before its slot is written. | Brief design point 3 | Another board needs its own `camnode.Slots`. |
| CAM-bin-3 | **The button is a gpio-keys input device**, read once at start with `EVIOCGKEY`, so "held at power-on" is "held when the service starts" [Inference: part c's device tree declares it]. | Brief question 5 | — |
| CAM-bin-4 | **`IRAuto` turns the illuminator on**, as `IROn` does: the parts list fits no ambient light sensor, so the node cannot tell day from night. | Brief parts | A light sensor makes auto a real mode. |
