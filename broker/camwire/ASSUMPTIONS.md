# camwire: assumptions

Built for CAM-node part (a), CAM-wire (#3513, `briefs/CAM-node.md`), against DEV-3, NET-2 (Cameras), NET-4 and NET-7. `broker/camwire` is the camera node's wire: the frame codec, the settings bundle, the image manifest and the owner-assertion check. The node (CAM-server, part b) and the core's camera clerk (CAM-clerk) both link it. Each row is a reading a later change could overturn.

| # | Assumption | Basis | If it changes |
|---|---|---|---|
| CAM-wire-1 | **The NET-4 loosening wait rests on the enforcer alone.** The node applies a verified bundle at once and has no clock, so NET-4's 10-minute cancel window for a loosening is the enforcer's to hold. A compromised enforcer can skip the wait but cannot forge the owner's assertion, so it can apply only a bundle the owner signed. This residual is accepted (brief, part a). | NET-4, brief design point 2 | A node with a trusted clock could hold the window itself; that is a new row. |
| CAM-wire-2 | **The owner credential is pinned by the first bundle and changes only by reset.** `VerifyFirstBundle` takes the credential the bundle names, proved by its own assertion, and only CAM-server's button window calls it (brief question 5). A later bundle naming another credential is `ErrOwner`. Replacing a lost passkey means the button reset, which the device key survives. | Brief questions 3 and 5 | An owner-signed rotation (old credential signs the new one) would add a field to the bundle and a version to its magic. |
| CAM-wire-3 | **The sign count is not checked**, as `kernel/key`'s ES256 check does not: synced passkeys report 0. Replay is stopped by the counters instead (CAM-wire-4). | WebAuthn §6.1.1; `kernel/key/passkey.go` | — |
| CAM-wire-4 | **Two counters, one per kind.** A bundle's counter is checked against the element's settings counter and a manifest's against its image counter, each strictly rising and by at most `MaxCounterStep` (2^20) per message, so one signed message can't exhaust a counter and lock the node out of every later bundle or image (Security on #3557, point 2); the caller raises the element's counter before it applies or marks an image good (CAM-server). A reset does not lower either counter. | Brief design points 2 and 3 | — |
| CAM-wire-5 | **The origin is exactly `https://<RP ID>`**, with no port, as `kernel/key` requires for the core's passkeys. The RP ID is lower-case letters, digits, dots and hyphens, so the origin has one spelling. | NET-4, CH-9 | If the enforcer's page serves on a port, the bundle carries the origin too. |
| CAM-wire-6 | **Authenticator data is 37 bytes unless the ED flag says extensions follow**; AT (a `create()`) is refused. Extension bytes are signed over but not parsed. | WebAuthn §6.1 | — |
| CAM-wire-7 | **The signature must be strict DER, at either S.** Only one spelling is accepted, but a high S is not refused: a signature here is never an identifier, so malleability gains nothing, and refusing high S would refuse real authenticators. | Brief part (a); compare KEY-7, where signatures are IDs | If a signature becomes an ID (a log entry keyed by it), normalise S as `kernel/key.AssertionSig` does. |
| CAM-wire-8 | **The release signature is one Ed25519 key over the manifest's bytes.** HW-10 and UPD-2's release tool sign with Ed25519; the node pins one release key in its image (part c) and the manifest's magic keeps that signature from serving any other release object. The boot ROM's own signature (part d's fused key) is separate and not checked here. | Brief question 4, HW-10, `cmd/agentos-release` | A threshold of release keys would make `Release` a list. |
| CAM-wire-9 | **This package restates the ES256 check rather than importing `kernel/key`.** The brief requires the standard library only, so the node's binary links no kernel; the checks match `kernel/key.VerifyAssertion` except for strict DER (CAM-wire-7) and the ED and AT flags (CAM-wire-6). | Brief part (a) | If the kernel's check changes, this copy is reviewed with it. |
| CAM-wire-10 | **Video is taken as Annex B by its start code only.** The codec checks the access unit opens with a three- or four-byte start code and is within 2 MiB; the payload past it is decoded only in CAM-clerk's sandbox. | Brief design point 1 | — |
| CAM-wire-11 | **A thermal frame's shape is the node's declared core**, passed to the reader (the zero `Shape` declares none, and thermal frames are then refused). A shape must fit 1 MiB, which a 640 × 512 Boson-class core does. | Brief design point 1 | A larger core raises `MaxThermal`. |
| CAM-wire-12 | **The core sends nothing on the stream channel.** No frame type travels to the node on it; CAM-server ends a stream connection on any byte from the core. | NET-2 ("a connection the core starts to the camera's stream port") | A pause or keyframe request would be a new type and direction. |
| CAM-wire-13 | **A manifest names the cameras its owner approved** (#3565, `AOSCAMM2`): a strictly ascending list of 1 to `MaxNodes` (32) device-key fingerprints, inside what both signatures cover, so one tap covers the cameras the owner picked and a compromised enforcer cannot replay it to another. `VerifyManifest` refuses a node the list omits (`ErrOtherNode`) before any signature check. `AOSCAMM1` is refused; no node shipped with it. | NET-4 ("each challenge commits to the change"), #3565 option (b) | A fleet over 32 cameras takes more than one tap per update, or `MaxNodes` rises within `MaxSigned`. |
