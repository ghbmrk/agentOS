# Attention optimizer: assumptions

Built for PLAN P3 ("attention optimizer", CAP-6) against SPEC v0.12, on the grants gate (#27) and the owner channel (P1-5). Covers `broker/attention`. Each row is a reading of the spec, or a gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| AT1 | **Batched, risk-tiered, with evidence** is already the owner channel's and the gate's: requests coalesce into batches split by tier (grants GR9, CH-13, CH-15), each line shows verified facts from the account's verifier or an `UNVERIFIED` prefix (GR5, CH-10, CH-12). This package adds the second half of CAP-6: proposing pre-allowances. | CAP-6, CH-10, CH-13 | — |
| AT2 | **Proposes, never enacts.** The optimizer holds no journal, gate, or owner-channel handle (a test checks its imports). A suggestion is a draft `grants.Spec` and one line of text. Taking it is the owner's own new-grant intent, which needs the code-generator code plus the local page (CH-3, grants GR3) and is validated by the gate like any grant. Declining is `NO <id>`. | CAP-6, ADP-9 | — |
| AT3 | **What earns a suggestion.** A class is an account, an action, and whether it is an in-thread reply (a `send` carrying `body`). Its run counts consecutive owner approvals that were verified (GR5) and not edited. A NO, an UNDO, or an edit (including a later owner "wrong" verdict, change C14a) resets the run. An unverified approval does not count, since no pre-allowance can match an unverified intent, but an unverified NO, UNDO, edit or wrong verdict still resets the run (ADP-11; L3 B1: the owner's rejection of an item the verifier could not read is still evidence); nor does an expired request, since silence is not a judgment (potency PA1). The threshold is 10 for ADP-9 rules, where any edit resets the run. **ADP-11 reply rules** follow the spec as written: a run of 20 unedited approvals, and any edit, NO, UNDO, or wrong verdict resets it (SPEC ADP-11, A15). Potency PA2 (the arbitrator's reading of Mark's D2: 20 unedited, edits not counting, at most 10% edited of the last 30) is built behind `Config.ReplyEditPercent`, default 0 (off), and is **pending a spec-diff** for Mark; SPEC ADP-11 says "A rejection or an edit resets the count". | CAP-6, ADP-9, ADP-11, OP-7 | Tune `Threshold`. |
| AT4 | **Never suggested.** reveal-or-create-secret (CRED-6) and reversible verbs (which need no rule); an account whose service publishes user content (`Config.UserContent`, required by `New` so a missing check cannot fail open; the SPEC egress-allowlist note on suggested pre-allowances, security review); and a class whose params, other than `record` (and a reply's `body`), were not the same plain strings every time, since ADP-9 allows only templated content. | CAP-6, ADP-9, CRED-6 | — |
| AT5 | **The drafted rule.** The fixed params are the constant ones. Recipients are fixed when every approval had the same set (never for replies, whose recipients are the thread's). Per record is 1, and per day is the median of the run's per-UTC-day counts, so bunching approvals into one day cannot raise it. An amount cap is the largest verified amount approved, with a 3-day edit hold whenever money moves (§17 risk 8). The owner's text is fixed wording within three GSM-7 segments (CH-12, UX-52-2): the evidence ("approved N times in a row since <date>, never changed"), a one-clause summary (per-day limit and "no money" or the amount cap), "To set it up, open the box's Wi-Fi page", and "Reply NO <id>". The full `grants.Describe` wording is `Detail`, shown on the Wi-Fi page where the owner confirms. | ADP-9 | The owner can narrow any bound on the local page before confirming. |
| AT6 | **After a NO**, the class is not suggested again until it earns twice the threshold more unedited approvals. `Due` offers a suggestion at most weekly; two unanswered offers count as a NO (UX-52-3). `Suggestions` lists them all for the local page without counting an offer. Short IDs default to `S1` ... `S99`, cycling so a declined ID is not reused at once (at most three characters); the wiring passes the owner channel's allocator (`Config.ShortID`, CH-12). | CAP-6, CH-12 | — |
| AT7 | **A10 split.** Each owner approval counts as avoidable if its class had already earned a suggestion when it arrived (a pre-allowance would have covered it), and as necessary otherwise. Only an eligible, verified, unedited approval can be avoidable; unverified, ineligible and edited approvals are necessary. A wrong verdict is a later judgment of an item already counted, so it is never counted again. | A10 | — |
| AT8 | **Wiring.** The grants gate calls `Observe` where an owner decision lands (with the verifier's facts) and when an owner edit or UNDO is recorded. The digest carries `Due(now)` (not `Suggestions`, so offers are paced). `NO <id>` maps to `Decline`. State is one JSON file (`change.FileStore` fits). None of this is wired yet. | CAP-6 | Wiring package. |
