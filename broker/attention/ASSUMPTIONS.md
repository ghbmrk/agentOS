# Attention optimizer: assumptions

Built for PLAN P3 ("attention optimizer", CAP-6) against SPEC v0.12, on the grants gate (#27) and the owner channel (P1-5). Covers `broker/attention`. Each row is a reading of the spec, or a gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| AT1 | **Batched, risk-tiered, with evidence** is already the owner channel's and the gate's: requests coalesce into batches split by tier (grants GR9, CH-13, CH-15), each line shows verified facts from the account's verifier or an `UNVERIFIED` prefix (GR5, CH-10, CH-12). This package adds the second half of CAP-6: proposing pre-allowances. | CAP-6, CH-10, CH-13 | — |
| AT2 | **Proposes, never enacts.** The optimizer holds no journal, gate, or owner-channel handle (a test checks its imports). A suggestion is a draft `grants.Spec` and one line of text. Taking it is the owner's own new-grant intent, which needs the code-generator code plus the local page (CH-3, grants GR3) and is validated by the gate like any grant. Declining is `NO <id>`. | CAP-6, ADP-9 | — |
| AT3 | **What earns a suggestion.** A class is an account, an action, and whether it is an in-thread reply (a `send` carrying `body`). ADP-9 groups contain canonical cohorts of the verified verb and fixed string parameters; a different template does not poison other cohorts. Each cohort's run counts owner approvals that were verified (GR5) and not edited. A NO, an UNDO, or a strict edit (including a later owner "wrong" verdict, change C14a) resets every cohort and reply history for that account/action, regardless of shape or verification. An unverified approval does not count, since no pre-allowance can match an unverified intent, but an unverified NO, UNDO, edit or wrong verdict still resets the run (ADP-11; L3 B1: the owner's rejection of an item the verifier could not read is still evidence); nor does an expired request, since silence is not a judgment (potency PA1). The threshold is 10 for ADP-9 rules, where any edit resets the run. **ADP-11 reply rules** allow light edits (potency PA2; Mark, 2026-10-05): at least 20 unedited approvals, edited ones never counting, with at most 10% edited among the last 30 answered replies, verified or not (`Config.ReplyEditPercent`, default 10; negative restores the strict run). The edit-rate window survives a reset, so a NO does not erase earlier edits. A NO, UNDO, or wrong verdict resets the run (SPEC ADP-11, A15). | CAP-6, ADP-9, ADP-11, OP-7 | Tune `Threshold`. |
| AT4 | **Never suggested.** reveal-or-create-secret (CRED-6) and reversible verbs (which need no rule); an account whose service publishes user content (`Config.UserContent`, required by `New` so a missing check cannot fail open; the SPEC egress-allowlist note on suggested pre-allowances, security review); and evidence whose params, other than `record` (and a reply's `body`), are not plain strings. Every ADP-9 cohort fixes exactly one such map; string-map order does not create a new cohort. Verified inputs remain a broker-only contract, not evidence of guest-supplied values becoming trusted. | CAP-6, ADP-9, CRED-6 | — |
| AT5 | **The drafted rule.** The fixed params are the constant ones. Recipients are fixed when every approval had the same set (never for replies, whose recipients are the thread's). Per record is 1, and per day is the median of the run's per-UTC-day counts, so bunching approvals into one day cannot raise it. An amount cap is the largest verified amount approved, with a 3-day edit hold whenever money moves (§17 risk 8). The owner's text is fixed wording within three GSM-7 segments (CH-12, UX-52-2): the evidence ("approved this template ... N times unchanged since <date>"), a one-clause summary (per-day limit and "no money" or the amount cap), "To set it up, open the box's Wi-Fi page", and "Reply NO <id>". The full `grants.Describe` wording is `Detail`, shown on the Wi-Fi page where the owner confirms. | ADP-9 | The owner can narrow any bound on the local page before confirming. |
| AT6 | **After a NO to a suggestion**, all account/action cohorts reset and each must earn twice the threshold more unedited approvals; new cohorts inherit that requirement, and bounded group metadata retains it through evidence expiry. `Due` offers at most one suggestion per account weekly across actions and cohorts; two unanswered offers count as a NO (UX-52-3). `Suggestions` lists them all for the local page without counting an offer. Short IDs default to `S1` ... `S99`, cycling so a declined ID is not reused at once (at most three characters); the wiring passes the owner channel's allocator (`Config.ShortID`, CH-12). | CAP-6, CH-12 | — |
| AT7 | **A10 split.** Each owner approval counts as avoidable if its exact eligible cohort had already earned a suggestion when it arrived and its fixed recipient/amount bounds match, and as necessary otherwise. This is a proposer-evidence estimate, not a simulation of dispatch quotas, per-record use, edit holds, or ADP-11 commitment checks (the grants gate enforces those). Only an eligible, verified, unedited approval can be avoidable; unverified, ineligible and edited approvals are necessary. A wrong verdict is a later judgment of an item already counted, so it is never counted again. | A10 | — |
| AT8 | **Wiring.** The grants gate calls `Observe` where an owner decision lands (with the verifier's facts) and when an owner edit or UNDO is recorded. The digest carries `Due(now)` (not `Suggestions`, so offers are paced). `NO <id>` maps to `Decline`. State is one JSON file (`change.FileStore` fits). None of this is wired yet. | CAP-6 | Wiring package. |

## POT-P5 draft proposal (primary review pending)

The following are proposed resource defaults in the explicitly requested draft PR, not adopted policy or a change to grant authority. ADP-11 still has one history per existing account/action reply class; no template cohorts are introduced for replies, and its 20 unedited/10% last-30 behavior is unchanged. This package does not wire W7, change gate enforcement, or claim live A10 gains.

| # | Draft assumption | Basis / review gate |
|---|---|---|
| AT9 | Keep at most 8 ADP-9 cohorts per account/action and 256 account/action classes. Refuse new live shapes at capacity without evicting earned evidence. Each retained template and recipient list has a 4096-byte bound; recipient lists have at most 64 entries. JSON state is capped at 32 MiB. | POT-P5; primary must review limits. Saturation reduces suggestion availability only. |
| AT10 | ADP-9 evidence expires 90 days after its run began. Broker time advances monotonically; delayed observations cannot revive expired evidence. The account/action decline floor survives expiry and reload, even though cohort evidence expires. Daily-cap buckets retain at most 91 UTC dates; ADP-11 counts and edit history do not expire. | POT-P5 bounded retention proposal. Metadata for declined groups remains within the 256-group bound; explicit state management is needed if that bound is exhausted. |
| AT11 | Version 2 migrates only homogeneous, templated ADP-9 legacy evidence; mixed evidence starts empty. It preserves reply counts, the last-30 edit window, approval totals, snooze and account pacing; legacy short IDs are invalidated. Unknown versions, malformed/inconsistent cohorts and oversized state fail closed. | POT-P5 migration/reload regressions. A suggestion ID is only a decline handle; there is no acceptance or grant API. |
| AT12 | `Due` builds and selects snapshots under one lock; returned maps/slices do not alias evidence. Exhausting the fallback 99 IDs leaves existing drafts usable and defers more drafts. Every grant still requires the existing owner-confirmed new-grant flow and gate validation; a cached draft grants nothing. | CAP-6, ADP-9, CH-3. W7 and SR3-2/SR3-3 remain separate prerequisites for live use. |
