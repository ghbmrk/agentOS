# Attention optimizer: assumptions

Built for PLAN P3 ("attention optimizer", CAP-6) against SPEC v0.12, on the grants gate (#27) and the owner channel (P1-5). Ported in MIG-4-untrusted-ui (#2782) onto SPEC v1.0's standing keys (KEY-5): proposals are key caveats from `broker/kernel/key`, no longer `grants.Spec`. Covers `broker/attention`. Each row is a reading of the spec, or a gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| AT1 | **What this package adds.** KEY-5's proposal half: drafting the narrowest standing key from recurring approvals. Pacing the question is the owner channel's (CH-15); making the key is the owner's passkey tap (KEY-4). | KEY-5, CH-15 | — |
| AT2 | **Proposes, never enacts.** The optimizer holds no kernel, key, or owner-channel handle; it imports only `broker/kernel/key`'s types (a test checks its imports). A suggestion is a clerk, a list of caveats and one line of text. Taking it is the owner's passkey tap on the owner page, which signs the key, live after KEY-4's grant hold. Declining is `NO <id>`. | KEY-5, KEY-4 | — |
| AT3 | **What earns a suggestion.** A class is a clerk, a verb, and whether the step is a thread reply (a `send` the clerk marked `Thread`). Its run counts consecutive owner approvals that were verified (every argument shown read by the clerk or fixed by the owner, KEY-2) and not edited. A NO, an UNDO, or an edit (including a later owner "wrong" verdict, OP-7) resets the run. An unverified approval does not count, since a key bounds only clerk- or owner-sourced arguments, but an unverified NO, UNDO, edit or wrong verdict still resets the run (L3 B1); nor does an expired request, since silence is not a judgment (potency PA1). The threshold is 10 for templated keys, where any edit resets the run. **Thread-scoped keys** allow light edits (potency PA2; Mark, 2026-10-05): at least 20 unedited approvals, edited ones never counting, with at most 10% edited among the last 30 answered replies, verified or not (`Config.ReplyEditPercent`, default 10; negative restores the strict run). These are KEY-5's numbers. The edit-rate window survives a reset, so a NO does not erase earlier edits. | KEY-5, KEY-2, OP-7 | Tune `Threshold`. |
| AT4 | **Never suggested.** reveal-or-create-secret (VRB-1 steps keep per-step approval under any key), reversible verbs (which need no approval) and verbs off VRB-2's list; a clerk whose service publishes user content (`Config.UserContent`, required by `New` so a missing check cannot fail open); a run whose content class was empty (free text: no template and no thread scope) or changed; and a run whose other arguments changed. | KEY-5, VRB-1, VRB-2 | — |
| AT5 | **The drafted key.** Caveats, in order: the one verb; the run's content class (the template, or the clerk's thread-scope class, as the clerk names it in `Decision.Content`); each other argument at its one value; the recipients, under the verb's object argument, when every approval had the same set (never for replies, whose recipients are the thread's); for a verb with an `amount` argument, a maximum at the largest verified amount approved; and a daily rate at the median of the run's per-UTC-day counts, so bunching approvals into one day cannot raise it. Old rules' per-record cap and 3-day edited-record hold are not drafted: `broker/kernel/key` has no caveat kind for either (KEY-2's record-edit hold is not yet a kind), so the owner page adds them when the kind exists. Expiry and the daily spend cap every derived key needs (KEY-4) are the owner page's to add when it builds the key. The owner's text is fixed wording within three GSM-7 segments (CH-12, UX-52-2): the evidence, a one-clause summary (daily rate and "no money" or the amount cap), "To set it up, open my Wi-Fi page", and "Reply NO <id>". `Detail` is `Describe`'s fixed wording, one term per caveat, every closed kind worded, for the owner page where the owner confirms. | KEY-5, KEY-2, CH-12 | The owner can narrow any bound on the owner page before confirming. |
| AT6 | **After a NO**, the class is not suggested again until it earns twice the threshold more unedited approvals. `Due` offers a suggestion at most weekly; two unanswered offers count as a NO (UX-52-3). `Suggestions` lists them all for the local page without counting an offer. Short IDs default to `S1` ... `S99`, cycling so a declined ID is not reused at once (at most three characters); the wiring passes the owner channel's allocator (`Config.ShortID`, CH-12). | KEY-5, CH-12 | — |
| AT7 | **A10 split.** Each owner approval counts as avoidable if its class had already earned a suggestion when it arrived (a standing key would have covered it), and as necessary otherwise. Only an eligible, verified, unedited approval can be avoidable; unverified, ineligible and edited approvals are necessary. A wrong verdict is a later judgment of an item already counted, so it is never counted again. | A10 | — |
| AT8 | **Wiring.** The owner side calls `Observe` where an owner decision on a plan step lands (with the clerk's facts from the log) and when an owner edit or UNDO is recorded. The digest carries `Due(now)` (not `Suggestions`, so offers are paced). `NO <id>` maps to `Decline`. State is one JSON file. None of this is wired yet. | KEY-5 | Wiring package. |
