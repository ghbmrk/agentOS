# Backup seal and key-table re-wrap (MIG-4-recovery-a): assumptions

Built for MIG-4-recovery-a (#3185), slice a of #2865, from `briefs/MIG-4-recovery-a.md`. The brief's decisions 1 to 10 are the design; each row below is a reading or a residual risk a reviewer may want to change.

| ID | Assumption | Spec basis | If it changes |
|---|---|---|---|
| MIG-4-recovery-a-1 | **The recovery key bounds the seal.** The card's recovery key is 160 bits, and anyone holding a backup can test guesses offline against the public `Recipient`: 2^160 classically, about 2^80 serial quantum steps under Grover, below ML-KEM-768's category 3. The hybrid stops a break of X25519 alone and a break of ML-KEM alone; it does not raise the recovery key's entropy. | BAK-1, REC-1 | A longer recovery key is a card and SPEC question (REC-4, STO-2). |
| MIG-4-recovery-a-2 | **A destination that keeps old versions keeps the erased subject's key.** Object versioning, a trash folder, or a copy of an older table object is outside what `Target.Tables` lists, so `Rewrap` cannot reach it. Storage adapters should delete all versions, and the erase confirmation (slice d) must promise no more than "re-sealed at this destination". | BAK-1, LOG-4 | Each storage adapter row states how it deletes versions. |
| MIG-4-recovery-a-3 | **Rollback at restore.** Someone who kept an older table generation can hand it to a restore, and it opens. Slice b's hold on erases newer than the backup must cover the restored key table (#3186). | REC-1, LOG-4 | none |
| MIG-4-recovery-a-4 | **A crash between put and delete leaves the older generation until the next `Rewrap`.** The outcome is then `Offline`, `ReadBackMismatch` or `OldNotDeleted`, never `Rewrote`; the next `Rewrap` takes `max(listed)+1` and deletes every other generation (`TestACrashBetweenPutAndDeleteIsFinishedNextTime`). | D-168 | none |
| MIG-4-recovery-a-5 | **Only a listed key can be found missing.** `Write` reads `Keys.List()` and refuses a live subject whose `Get` then reports it missing, but a live subject absent from `List` is not seen: the package reads liveness only through `Recall(subject)` and has no list of the log's subjects. That case already fails on the live box (`OpenContent` reports it in `Missing`), so the backup loses nothing the box still had. | BAK-1, LOG-4 | If `kernel.State` gains a live-subject list on its public face, `Write` checks it too. |
| MIG-4-recovery-a-6 | **A section is checked as it ends.** The STREAM chunks stop any change, cut or reorder of the object, but a reader that acts on a section's bytes before `Next` (or the reader's last `Read`) returns acts on bytes whose length and sum are not yet checked. Restore (slice b) writes sections to a staging path and uses them only after `Next` returns `io.EOF`. | BAK-1 | none |
| MIG-4-recovery-a-7 | **`Write` opens each section twice** (once to hash it for the manifest, once to copy it) and refuses one that changed between (`ErrChanged`). The caller (slice e, #3191) gives it a log and store snapshot that does not change while it runs. | BAK-1 | If a snapshot is not available, the manifest moves to a trailer. |
| MIG-4-recovery-a-8 | **`Outcome` is one `Result` and an error**, not one bool per result as the brief's `Outcome{Unchanged: true}` reads, so two results can never both be set. A live key that `Get` reports missing or cannot read is `LiveKeyMissing`, with the error. | D-168 | none |
