# Backup seal and key-table re-wrap (MIG-4-recovery-a): assumptions

Built for MIG-4-recovery-a (#3185), slice a of #2865, from `briefs/MIG-4-recovery-a.md`. The brief's decisions 1 to 10 are the design; each row below is a reading or a residual risk a reviewer may want to change.

| ID | Assumption | Spec basis | If it changes |
|---|---|---|---|
| MIG-4-recovery-a-1 | **The recovery key bounds the seal.** The card's recovery key is 160 bits, and anyone holding a backup can test guesses offline against the public `Recipient`: 2^160 classically, about 2^80 serial quantum steps under Grover, below ML-KEM-768's category 3. The hybrid stops a break of X25519 alone and a break of ML-KEM alone; it does not raise the recovery key's entropy. | BAK-1, REC-1 | A longer recovery key is a card and SPEC question (REC-4, STO-2). |
| MIG-4-recovery-a-2 | **A destination that keeps old versions keeps the erased subject's key.** Object versioning, a trash folder, or a copy of an older table object is outside what `Target.Tables` lists, so `Rewrap` cannot reach it. Storage adapters should delete all versions, and the erase confirmation (slice d) must promise no more than "re-sealed at this destination". | BAK-1, LOG-4 | Each storage adapter row states how it deletes versions. |
| MIG-4-recovery-a-3 | **Rollback at restore.** Someone who kept an older table generation can hand it to a restore, and it opens. Slice b's hold on erases newer than the backup must cover the restored key table (#3186). | REC-1, LOG-4 | none |
| MIG-4-recovery-a-4 | **A crash between put and delete leaves the older generation until the next `Rewrap`.** The outcome is then `Offline`, `ReadBackMismatch` or `OldNotDeleted`, never `Rewrote`; the next `Rewrap` takes `max(listed)+1` and deletes every other generation (`TestACrashBetweenPutAndDeleteIsFinishedNextTime`). | D-168 | none |
| MIG-4-recovery-a-5 | **Only a listed key can be found missing.** `Write` reads `Keys.List()` and refuses a live subject whose `Get` then reports it missing, but a live subject absent from `List` is not seen: the package reads liveness only through `Recall(subject)` and has no list of the log's subjects. That case already fails on the live box (`OpenContent` reports it in `Missing`), so the backup loses nothing the box still had. | BAK-1, LOG-4 | If `kernel.State` gains a live-subject list on its public face, `Write` checks it too. |
| MIG-4-recovery-a-6 | **A section is checked as it ends.** The STREAM chunks stop any change, cut or reorder of the object, but a reader that acts on a section's bytes before `Next` (or the reader's last `Read`) returns acts on bytes whose length and sum are not yet checked. Restore (slice b) writes sections to a staging path and uses them only after `Next` returns `io.EOF`. The first error sticks: every later `Read` and `Next` returns it, so a caller that drops one never reaches `io.EOF` (`TestASectionErrorSticks`). | BAK-1 | none |
| MIG-4-recovery-a-7 | **`Write` opens each section twice** (once to hash it for the manifest, once to copy it) and refuses one that changed between (`ErrChanged`). The caller (slice e, #3191) gives it a log and store snapshot that does not change while it runs. | BAK-1 | If a snapshot is not available, the manifest moves to a trailer. |
| MIG-4-recovery-a-8 | **`Outcome` is one `Result` and an error**, not one bool per result as the brief's `Outcome{Unchanged: true}` reads, so two results can never both be set. A live key that `Get` reports missing or cannot read is `LiveKeyMissing`, with the error. | D-168 | none |
| MIG-4-recovery-a-9 | **The seal does not show who made an object.** It gives confidentiality and integrity under the recovery key, not origin: anyone holding the public `Recipient` can build a content or key-table object that the recovery key opens. Restore (slice b, #3186) trusts a backup's log only through the anchors' signed heads, never because the object opened. | BAK-1, STO-1, KEY-7 | If restore must trust an object before checking the log against the anchors, the box signs objects too. |
| MIG-4-recovery-a-10 | **Section names follow the kernel's store names.** `content/<store>` takes any name `kernel.ValidStore` takes (printable, at most 64 bytes, never the key table), so no store makes `Write` refuse a backup (`TestSectionNamesMatchTheKernelsStoreNames`). Such a name can hold `/` or `..`, so a section name is a label: restore never joins it to a file path. | BAK-1 | If the kernel narrows its store names, sections narrow with it. |
| MIG-4-recovery-a-11 | **A spent generation refuses.** If `rec.Generation` or a listed generation is the last `uint64`, `Rewrap` writes nothing and returns `GenerationSpent`, which, like the other results after `Rewrote`, means the backup may still hold an erased subject's key. Only a target that lists a forged generation reaches it. | D-168 | none |
| MIG-4-recovery-d-1 | **`Set` is the kernel's `Backups`** (#3188, D-168). It names each backup by its `BackupID` and saves every Record `Rewrap` returns before it uses it; a Record that does not save is not used, so the next re-seal rewraps again and drops the table it put. `Prepare` takes, under the kernel's lock, the live keys and the erased subjects (`snapshot`); the I/O at the target runs without it, and the commit, under the lock again, saves and uses the Record (KRN-7, #3317). A re-seal's error is the `Result` word and its cause, which the kernel shows as `StillHeld`'s why. On `OldNotDeleted` the saved Record's `Subjects` keeps the older table's subjects as well as the new one's, so `Subjects` reads "every subject a listed table may give": the erased subject still reads as given and the next re-seal, after a restart too, writes a fresh generation and drops every other (`TestAnOldTableLeftKeepsTheBackupOwing`). Who loads the Records and targets at start is slice e (#3191). | D-168, LOG-4 | none |
| MIG-4-recovery-f1-6 | **The manifest drops the edge fields (version 2).** The edge key and its revocations are kernel log entries when the core side of the edge link is built, so the log section carries them (HW-15, KRN-1; brief decision 4); the manifest has no second copy that could disagree. `Open` reads version 2 with only its own fields and version 1 with its edge fields, which it drops unread; any other version or field refuses. The object header's `version` is unchanged. `Record.PageCA` is the page authority's fingerprint, given by the caller (`Input.PageCAFingerprint`) beside the opaque `Input.PageCA`, since this package links no x509 parser. | BAK-1, HW-15, CH-9 | If the edge link's core side keeps edge keys outside the log, it brings its own section, never these fields back. |
