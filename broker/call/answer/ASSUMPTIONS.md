# Call answerer: assumptions

Built for VOICE-ro-c-p0 (#4948, part of VOICE-ro-c in briefs/VOICE-ro.md) against SPEC CH-5, CH-17 and PLN-3 and the brief's rule 4. Covers `broker/call/answer`.

| # | Assumption | Basis | If it changes |
|---|---|---|---|
| VOICE-ro-c-p0-1 | **Labels decide what a call hears, not the prompt.** `Answer` reads, then `admit` keeps the facts the ask's rung, `a.Rung()`, may hear, and the writer (the model that words the answer) is given only those. At P2 (the token call) every fact passes. Every other rung, P1 and any rung `call` adds later included, gets only facts whose every label is `status`; a fact with no label is private (PLN-3), and one that mixes `status` with any other label is private, since labels only accumulate. So a spoofed caller ID that asks for mail, or says it is the owner, hears the box's status and nothing private: the writer never had the rest. `admit` is unexported and named once, in `Answer`, with `a.Rung()` (`TestTheRungIsTheAsks`, #5232), so no code in the package picks a rung of its own. | Brief rule 4; PLN-3; Security on #4944 | A rung between P0 and P2 that may hear more (P1 after a reply to the box's text) is a new rule here with its own test. |
| VOICE-ro-c-p0-2 | **The read side sets the labels.** `Reads` returns each fact with the labels the kernel gave its value (PLN-3); only facts about the box itself (STATUS, what is due on the box), read from no account, carry `status` alone. Neither the transcript nor the writer sets a label. A fact the read side labels `status` while it holds account data is a defect there, outside this gate. | PLN-3; brief rule 2 | When the planner's read path lands (the rest of VOICE-ro-c), its labelling of STATUS lines is reviewed against this rule. |
| VOICE-ro-c-p0-3 | **The writer knows only what it is given.** The writer is a model call with no tools, no keys and no memory of earlier calls beyond this call's asks, like a PLN-2 reader: what it may word is the ask and the admitted facts. A writer wired to a session that holds private context would bypass the gate. | PLN-2, PLN-3 | A writer with its own context needs that context admitted through `admit` too. |
| VOICE-ro-c-p0-4 | **The reads see the rung.** `Reads.Read` gets the whole `call.Ask`, rung included, so it may skip a private read the call cannot hear; the gate holds whether it does or not (`TestP0AskForMailOrCalendarGetsNoPrivateContent` gives every fact at every rung). A failed read fails the turn, so the loop plays its failed clip (VOICE-ro-a-C8). | Brief rule 5 | none |
