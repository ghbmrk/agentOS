# Journal and intent engine: assumptions

Built against SPEC v0.11 §9 (OP-1 to OP-7) before v0.12 was approved. These are
the readings of the spec this package relies on. Each one is a place a later
spec version could force a change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| A1 | Intents carry an `account` field. The §9 intent sketch has no account, but OP-4 fences "that account", so the engine needs one. Broker-state changes use account `broker`. An effect that spans several accounts fences only the one it names; the broker should split such effects into one intent per account. | OP-4 | Rename or derive it from `executor` + `grant_ref`, or allow a set of accounts. Small. |
| A2 | The fence after a restart covers only intents left unresolved at that restart. During normal running, an `outcome_unknown` intent blocks its own retry (OP-2), and any intent with the **same effect** (same account, action, params, recipients, visibility, executor) under a different ID, but not unrelated intents on the same account. A held duplicate stays `authorized`, `Dispatch` returns a `HeldError` naming the intent it waits behind, and `Waiting()` lists every held intent with its blockers, so the broker can show the owner a waiting retry rather than lose it. | OP-4 says "Restart = replay ... before new dispatch on that account"; OP-2 | A stricter rule (any unknown fences its account) is a few lines in `dispatchable`. It costs potency: one lost acknowledgment would stall every other task on that account until reconciled. |
| A3 | A failed recheck before dispatch ends the intent as `denied` (phase `dispatch`). A caller who wants to try again submits a new intent. | OP-3 | Could instead return to `authorized` and wait. Small. |
| A4 | STOP holds authorized-but-undispatched intents rather than cancelling them. RESUME releases them. STOP is journaled, so it survives a restart. Held intents still pass the OP-3 recheck before they run, so a stale approval (expired CH-10 code) after a long STOP fails there; checking approval freshness is the Policy's job. | OP-6, CH-11 ("RESUME restarts"), CH-10 | If STOP must cancel held work, add a `cancelled` state. Small. |
| A5 | Goal quality is a verdict (`good` / `wrong`) with a source and note, recordable on any intent at any time and replaceable by a later verdict. | OP-7 | A richer grading model (scores, graders per CHG-1) would extend `Quality`. |
| A6 | Recipients are compared in order for OP-1. The same recipients in a different order count as different parameters, which is the conservative reading of "exact params/recipients". | §9, OP-1 | Sort before fingerprinting. Small. |
| A7 | Authentication of the origin, of RESUME, and of owner-supplied evidence (`Resolve`) is the broker's job. The engine records the source string it is given. | CH-10, CH-11 | None here; the broker skeleton (P1-2) does it. |
| A8 | Intent params carry vault references, never secret values, and executors never return secrets as evidence. As defence in depth, a mandatory `Redactor` (supplied by the broker: CRED-7 vault values plus CH-19 secret patterns) runs over every free-text field before it is journaled, and `Open` refuses a nil one. Identifiers are not redacted. The redacted form is what the engine keeps and replays, so an executor never sees a value the redactor removed. | CRED-1, CRED-7, CH-19 | None expected. |
| A9 | Authority-narrowing broker-state intents (`meta.grant.revoke`, `meta.grant.pause`, `meta.budget.lower`, and the change pipeline's `meta.change.revert` and `meta.change.policy.off`, on account `broker`) are exempt from STOP holds and restart fences, so pausing or revoking always works. They still pass the policy check and are journaled. | ADP-9, OP-6 | Add actions to the narrowing list as new pause/revoke commands appear. |
| A10 | `Policy.Check` runs outside the engine lock. A decision is committed only if no journal record was written during the check; otherwise the check runs again (up to 16 times, then `ErrBusy`). Policy inputs that change outside the engine must be read inside `Check`. | OP-3, CH-2 | None expected. |
| A11 | A complete record with a bad checksum stops `Open` (`ErrCorrupt`). There is no automatic recovery: dropping a durable `dispatched` record could duplicate an effect. P1-2 must still answer STOP and STATUS without the journal in that case (CH-2, restricted mode), and a recovery path (quarantine the tail, fence every account) is future work. | DEP-1, CH-2 | Add a recovery open. Medium. |
| A12 | **Erasure (CAP-3).** `Erase` removes an intent's parameters, preconditions, executor evidence and cancel details, in memory and in the file: an `erased` record, then the journal is rewritten (tmp file, locked, renamed) so no live copy remains; `Open` finishes a rewrite a crash cut short. Kept for the audit trail (OP-5): who asked, account, action, recipients, executor, decisions, results, and the idempotency fingerprints. Only finished intents are erased; a pending one is denied first, an authorized one fails its recheck first, so nothing runs on erased parameters; one in flight or unresolved is held and erased once it settles. The caller is recall's deletion reach: the intents a fork lineage submitted from the time it was given a deleted record until its reset (`Between`). The kept fingerprints are unkeyed SHA-256 of the parameters, so they can confirm a guess of low-entropy erased parameters (#59 L3); keying them with the vault is carried forward (BOARD P3-3b). Old copies in backups and freed disk blocks are outside this: a backup taken before an erase still holds the erased parameters, so a restore must replay recall's tombstones through its deletion reach (recalltool W9) before agents run. | CAP-3, OP-5 | Restore package: replay tombstones on restore. |
| A13 | **Sleep records (PE7).** `RecordSleep` appends a `sleep` record naming the machine, the event (`asleep`, `sleep_failed`, `awake`), the wake cause and, for a cold wake, its reason, all short fixed codes; it touches no intent. It is the journal line PE7 condition 12 and potency R1 on #147 ask for, so a box that keeps waking cold can be seen. | RES-1, REV-1 | If sleeps need replaying at `Open`, give them state |
| A14 | **A refusal's guest text (SR2-3j).** A policy refusal whose error has its own `GuestText() string` method (guesterr.Safe, matched structurally so journal imports no broker package) is journaled as the record's `guest` and replayed as `Permission.GuestReason`; a wrapped one is not. `Reason` stays the owner's full text. Journals written before SR2-3j have no `guest`, so their denials show the guest a ref. |
| A15 | **Places in use (SR3-2).** `InUse(account, action, since)` lists the intents that hold a place in a rate window starting at `since`: an `authorized` intent not yet dispatched (a reservation, any age, `Started` false); an `in_flight` or `outcome_unknown` one (started, any age, until `Resolve` settles it, OP-2); and a `succeeded` one whose latest `dispatched` record is at or after `since` (started). `not_applied` and `denied` hold none, and a retry is charged from its own dispatch. The dispatch time is replayed from the journal, so places survive a restart (OP-4). `AuthorizedSince` stays for `broker/mail`, which still counts by authorization time (SR3-2 finding, release). | ADP-9, OP-2, OP-3, OP-4 | Charge by authorization time again only if queues cannot outlive a window. |
| A16 | **An erased use is marked (SR3-2-f3).** `Use.Erased` is set for a `succeeded` intent erased under CAP-3 (A12), from the entry's erased flag, which the `erased` record sets on apply and replay (and the rewritten journal keeps), so it survives `Open` and the erase rewrite. Only `succeeded` uses can carry it: `Erase` takes only finished intents, and `denied` holds no place. The flag is additive; callers that ignore it (broker/mail) see the same uses as before. The record key is not kept among the fields erasure keeps: it names a record of the deleted source, which CAP-3 removes, so the gate counts an erased use against every record instead (grants GR33). | CAP-3, ADP-9, OP-4 | Keep `ParamRecord` after erasure only if a record key is shown not to be content under CAP-3. |
| A17 | **The tail for projections (SIM-proj).** `RecordsAfter(seq)` returns the records with a sequence number above `seq`, or the error reading the journal. Like `Trail` (since SIM-bound, #720) it decodes the journal afresh, so a caller that changes a returned record in place cannot change what is dispatched (L3 on #722). Records are numbered from 1 with no gaps and an erase rewrite keeps every number, so a projection that has applied through `seq` reads exactly its tail. The engine does not call projection code (broker/projection P7). | OP-4 | None expected. |
| A18 | **Startup settles restart fences (JRN-startup-reconcile, #1319; follow-ups #1370 to #1373).** `SettleUnknown(ctx, wait, maxWait)` runs `Reconcile` until no `outcome_unknown` attempt is left or ctx ends; `broker/daemon` starts it in the background at `Run` (agentosd), waiting 2s after the first unresolved round and doubling to 5m, each round bounded by a minute. It only gathers evidence: an executor that answers unknown keeps its account fenced (A2) and is asked again, and nothing is executed again, not even an intent found `not_applied` (daemon `TestOP4StartupReconcileNeverExecutes` stands in a fake for every executor name agentosd registers and fails on any `Execute`; it proves the engine's settle path never executes, not that a real executor's `Reconcile` does not act, which the audit below covers). Every registered `Reconcile` was audited at #1371 and acts only in these ways, all of which repeat harmlessly at each start: follow's `TrustedRoot` finishes or forgets a switch a crash cut short (its own store) and tells the owner again; forget queues the interrupted item and starts the agent's resume (#1370), which runs once: with recall on it waits for recall's open and `Handled` stops a second take-back; with recall off it waits for the boot's own resume, after the gate, the owner channel and the agent are attached, and the queue it drains tells the owner once (`wireResume`, Security S1 on #1382); recall's late mail executor stamps its bookkeeping. The rest read state only (loops, apply, change, mail, recall rollback, grants gate). A new executor whose `Reconcile` sends, pays or deletes would repeat that at every start. Follow answers `not_applied` when the box trusts neither the intent's root nor its source, so an intent a later follow superseded is recorded `not_applied` too, which is harmless because a held root lives in memory only (#1372); a switch that landed and was then rotated by the update client before the first round stays `unknown`, and fenced. A fence evidence cannot lift stays: STATUS names what is unconfirmed after one missed round (`Unconfirmed`, restart-fenced intents only), and a fenced setting says it is on hold; a setting held behind the same change sent this boot (`HeldError`) gets its own reply, which names no restart (#1373). The owner never settles one (D-116, #1373): after `parkAfter` unknown checks the attempt is parked (A19) and goes in the digest; the owner's only path is RETRY, a new attempt (`Retry`). `Resolve` still refuses unknown. | OP-4, OP-2 | Stop retrying an executor that can never tell only if the retry load is shown to matter. |
| A19 | **At-most-once reconcile (D-116, #1373).** An unknown outcome is never executed again on its own. `Reconcile` re-dispatches only when the executor implements `KeyHonouring` and says the service honours the attempt's idempotency key; that retry reuses the same key and attempt (`dispatched` with source `key`), so the service applies it at most once, and only within the key's lifetime from the attempt's first dispatch (`KeyLifetimer`, else `DefaultKeyLifetime`, 24h; the dispatch time is on the attempt, from its first `dispatched` record): past it the effect is checked and parked like any other. The clock measures that lifetime only when it is not behind the attempt's dispatch or the journal's newest record (`newest`, from replay and commits), as maintain's Loop3 distrusts a clock behind its last attempt; otherwise the key retry is refused (`errClockBehind`) and the effect is parked at once. A check that proves `not_applied` dispatches the intent again as a new attempt (`redispatch`, via `Resend`, listed in `ReconcileReport.Redispatched`) under the dispatch recheck (OP-3) and `mayDispatch` (STOP, the account fence, a same-effect intent ahead of it, an executor), which `validate` does not repeat; a refusal journals nothing and leaves the intent `not_applied`, not denied. `NotResent` lists such intents (latest attempt `not_applied` from a `reconcile` source, not erased, not mid-redispatch) for the digest and RETRY, so a refused resend is never dropped silently; `Resend(id, attempt)` is the owner's path for one, refused unless that attempt is the one a check proved not done. One effect-level invariant covers every path to execution (`sameEffect`, checked in `mayDispatch`, which `Dispatch`, `Resend` (redispatch and the owner's RETRY of a not-done effect) and `Retry` all pass under the lock, and again after the policy recheck): intents with the same `effectFingerprint` are rivals once one of them, z, had an attempt proved `not_applied` (by a check or by its executor), when each of the two is z or was submitted after z's first dispatch (`rivals`, from `firstDispatchSeq` and `provedSeq`, set once from the journal, so a restart sees the same rivals; `byEffect` indexes intents by fingerprint, so the check reads only those); a request made before z was first dispatched is a separate send, from z and from z's resubmissions alike. The precedence among rivals is strict, so two never wait for each other (`blocks`): a rival that went holds back only rivals submitted before it went (`wentSeq`, the first record observing a success, set once in `entry.apply`), so a request made after the effect went is a new send, judged as on main (`duplicateOf`, and the rival rules against what was unresolved when it was made); a rival that may have gone or is going (in flight or `outcome_unknown`, parked or `unclear` included) holds back every rival; a rival pending or authorized holds back only a rival whose latest attempt was proved `not_applied` (a resend of a not-done effect, or a guest's repeat of a refused request), not a first dispatch and not the owner's RETRY of a parked rival, which the waiting one is itself held behind (`duplicateOf`; Security R11 on #1433); a rival proved `not_applied` or denied holds nothing back. Whichever dispatches first goes and the rest are refused (`SupersededError`, matching `ErrState`, whose `Rival` says whether the other went, waits to go or may have gone; a fresh intent behind a rival still unknown is held, `HeldError`, and goes if that one is proved not done). `Dispatch` denies an intent a rival that went holds back (`recheck_failed`, fixed guest text), since that is final, even while that rival has a later attempt of its own still open; `Release` dispatches each authorized one so it is answered without the agent asking again (Security R15 on #1433). Intents that only take authority away (`narrowing`: pause, revoke, budget lower, change revert, policy off, loops off, loops budget lower) are exempt from `sameEffect`, as they are from STOP and the fence: applying one again cannot widen anything (ADP-9; Security B8 on #1433), so an owner PAUSE or REVOKE cut off by a restart never stops later ones. A resubmission made after the original went (say, after the owner's RETRY of the not-done original) is a new send here (Security B8 and Potency P6 on #1433); the gate's policy asks the owner to confirm it when it repeats a send known to have gone in the last 24 hours, pre-allowed or not, so it never goes unseen (Mark's confirm repeats, D-116; grants GR35). `InUse` gives the gate what it needs: `Use.Went`, when the attempt that went was dispatched (`entry.wentAt`: a same-key retry's dispatch for the latest attempt, an earlier attempt's own dispatch otherwise), `Use.Known`, the later of that and when the success was recorded (`entry.knownAt`), so a success proved late counts from the proof and `InUse` lists it while either is in the window (Security B11 on #1433), and `Use.Tried`, when the attempt that may still take effect was first dispatched (an unclear intent's parked try, not its refused retry; Security R19). One made before it went, or while it waited, is refused. No time window bounds rivalry. `NotResent` leaves out an intent while a rival blocks it and offers it again once that rival is proved not done or denied, so a resubmission the service refused never hides the original. An authorized rival that hides a not-done effect is dispatched by the settle loop (`Release`, which the daemon runs after each `SettleUnknown` through the gate's `Dispatch`, Security R12 on #1433), so the effect never waits on the agent asking again; refused at the recheck, it is denied and the original is offered again. The state says whether the effect may have gone, not only how the latest attempt ended (`entry.derive`, Security B9 on #1433): a parked attempt whose owner's retry the service refused, or a check proved not done, leaves the intent `outcome_unknown` (`unclear`; `Status.Unclear` names the parked attempt, `Status.Outstanding` the one evidence settles), so every reader that goes by the state treats it as one that may have gone: `Erase` holds it, `InUse` charges its place as started, STOP lists it as unresolved and cancels the parked attempt and every later one still in flight or unknown (Security R18 on #1433), and also an earlier attempt still unknown of an intent a later attempt settled as succeeded, which leaves `open` and is kept in `lingering` so STOP still reads no settled history (Security R22 on #1433), STATUS, recall's work count and the gate's reports read it as may-have-happened, a restart neither fences nor redispatches it, and `validate` refuses a `recheck_failed`, plain `dispatched`, key retry or `parked` record on it. Only the owner's RETRY (`Retry`; `Parked` lists it, with the parked attempt's dispatch time) tries it again, and a check that finds the parked attempt went makes the intent `succeeded`. Likewise an intent one of whose attempts went is `succeeded` once its latest attempt settles, whatever that attempt did (the settle loop's check of a parked attempt racing an owner's retry, R14), and `Parked` no longer offers an intent that went. A key retry repeats an attempt under its own key and is not held back. Repeats of a send nothing proved not applied stay separate sends, as before. A small-scope exhaustive model (`TestOP2SameEffectModel`, `model_test.go`) searches every interleaving of two or three same-effect intents, widening and narrowing, to a bounded depth across submit, approve, deny, dispatch outcomes, restart, checks, parking, the owner's RETRY of parked and not-done intents, `Release`, erase of any intent (as the owner's or a recall reset's), and, in two further configurations, STOP, RESUME and the owner's evidence on any unknown attempt (`Resolve`), and checks after every step that the effect never goes twice through rivals unless the second was requested after the first was known to have gone (and one intent only on the owner's retry), that no attempt starts while another with the effect may still take effect, that a not-done effect is always offered, held behind a live rival, or released, that a request made now is never refused as superseded (nor any narrowing intent), that something waiting can always go, that `Release` answers an authorized request whose effect went as another, and (I5, with a policy that asks as the gate's confirm-repeats rule does and an owner `confirm` step) that a request whose effect is known to have gone as another (erased or not) is dispatched only after the owner's yes given after that success: a `confirm` step, or an `approve` of a request asked after it went; an `approve` is offered before the rival went too, and the policy, as the gate's `decision.covers`, does not take it as a confirmation (Security B10 on #1433). Bounds: two intents to depth 10, three to depth 9, narrowing to depth 10, and the owner configurations to depth 9. The search is sequential, so it is skipped under `-race` and CI's broker job runs it without `-race` at these bounds in a step of its own (Potency P11, L3 L12 on #1433); `MODEL_DEPTH` runs deeper. The match is exact: a resubmission whose params or recipients differ in any byte (an extra param, a recipient's case) has another fingerprint and is not a rival, so both may go; the gate's RETRY line for a not-done effect then warns "may go twice" when a send of the same verified record to the same canonical recipients went, may have gone, or waits for approval or dispatch (`Queued`) since (grants GR35, `sentSince`), so the owner sees the possible duplicate. `Executor.Reconcile` documents that `not_applied` must mean the attempt can never take effect later. The restart fence holds through that redispatch (`redispatching`), so newer work on the account cannot run ahead of it. An executor with neither a useful check nor the key hook gets the default: unknown, then parked after `parkAfter` (10) unknown checks, then the digest, no retry. A `parked` record lifts the account's restart fence (other work resumes) but `duplicateOf` still holds any intent with the same effect, so a resubmission cannot send it twice; settle rounds keep checking parked attempts, and one a check later settles is closed. `Retry(id, attempt)` is the owner's RETRY: it refuses unless the intent is `outcome_unknown`, parked, and its latest attempt is the one named, so an approval of an old request cannot start a second owner retry; it runs a new attempt (source `owner`) under the dispatch recheck (OP-3). The record version is not bumped: an older binary refuses `parked` records and record sources as corrupt (A11) rather than misreading them. | OP-2, OP-4 | Bump the record version if an older binary must read these journals. A key lifetime that some service documents as under 24h needs its executor's `KeyLifetime`. |

## Design notes

- **Write-ahead.** The `dispatched` record is fsynced before the executor runs.
  A crash can therefore make the journal over-report what may have happened
  (replayed as `outcome_unknown`), never under-report it.
- **Torn writes.** Only a final segment without a newline is treated as torn and
  dropped; its `Append` never returned, so nothing acted on it. A complete line
  with a bad checksum is corruption and `Open` fails closed, because silently
  dropping a durable `dispatched` record could let an effect run twice.
- **One transition function.** Live operation and replay share `validate` and
  `apply`, and the live engine applies each record as decoded from the line it
  wrote, so replay reproduces exactly the state the live engine had. The
  property test checks this every fifth step.
- **No external dependencies.** Go standard library only (DEP-1). Property tests
  are seeded random workloads with crash injection, not a third-party framework.
- **Durability of the file itself.** `OpenFile` fsyncs the parent directory, so a
  newly created journal's directory entry survives a crash, and takes an
  exclusive `flock`, so two engines cannot write one journal.
- **Size limits.** Intents over 64 KiB are rejected; free text over 4 KiB is cut
  and tagged with a SHA-256 of the whole.
- **Bounded memory for refusals (SIM-bound).** The engine keeps no per-record
  history in memory: the journal file is the history, and `Trail` reads it.
  Settled denials past the newest `hotDenials` (1024) leave the in-memory
  index. What stays of each is 36 bytes: a 16-byte SHA-256 prefix of
  its id, a 16-byte prefix of its fingerprint, and the index of its shape
  (goal, origin, account, action, executor, refusal texts and phase), each
  distinct shape kept once. `Get`, an OP-1
  resubmission, and a refused `Authorize`, `Dispatch` or `Resolve` of an
  evicted denial answer from that, with no journal read;
  `Get` then omits params, recipients and the other free-form fields, which
  `List`, `Between`, `StatusBetween` and `Trail` still return. Rated denials and ones
  with attempts are not evicted. `List`, `Between`, `StatusBetween`, `Trail`
  and the owner-side rehydration (`RecordQuality`, `Erase`) read the whole
  journal, and the store holds its mutex
  for that read, so a STOP arriving meanwhile waits for it to finish.
- **STOP reads an index.** `open` holds the unsettled intents (pending, held,
  outcome unknown); `Stop`, `Waiting`, `Reconcile` and `GuestActive` walk it,
  so their work does not grow with the settled history.
- **Not yet here:** journal compaction (the file grows without bound and
  `Open` replays all of it), eviction of settled successes, and a hash chain
  for tamper evidence. All can be added without changing the record format's
  meaning.

## Notes for P1-2 (broker skeleton)

From the PR #18 review:
- Put the journal on the encrypted volume. It holds private recipients and
  params (CRED-8).
- Authenticate `Resolve` callers (A7).
- RESUME's confirmation should list the held intents. The outcome-unknown
  question to the owner should make clear that answering NO retries it.
