# Enforcer lock rules: assumptions

Each row is a reading of the spec, or a property the code relies on, that a
reviewer may want to change (briefs/ENF.md slice q, #3675).

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| ENF-q-1 | **The gate is the actuator behind slice s's book, for unlocks and disarms only.** An unlock or disarm already needs the owner's tap at home on an `action.Book` challenge naming the device, the act and a 2-minute window, good once (ENF-s-1 to ENF-s-3). The daemon (slice l) passes `Gate` as the book's actuator for `action.Unlock` and `action.Disarm`, and no other path reaches `Driver.Act`. `Gate.Act` refuses any other act or a route, so wiring it wrong fails closed. | NET-6, NET-2 Channel ("agentOS and its channel never unlock or disarm") | — |
| ENF-q-2 | **The relock interval is one minute** (`RelockAfter`), for every lock, counted from any unlock the enforcer does or sees, whoever unlocked it. NET-6 calls it owner-set, but the signed policy has no field for it yet, and an unsigned setting would be a second rule system (STO-4, P7). Release finding #4285 adds it to the policy. A relock that fails is tried every 5 seconds until one succeeds, logged once. | NET-6 ("the lock relocks automatically after the owner-set interval") | #4285: `Gate` reads each lock's interval from the document in force, which `Tick` already takes. |
| ENF-q-3 | **Unusual means outside 07:00 to 22:00 in the enforcer's zone** (`Unusual`, `Config.Zone`, the zone the page uses, ENF-b-11). NET-6 names no hours. The same release finding (#4285) makes the hours owner-set in the signed policy. Unusual is decided when the act runs, not when the page was drawn, so a challenge drawn at 21:59 and tapped at 22:00 needs the second tap. | NET-6 ("an unlock or disarm through the enforcer at an unusual time needs a second passkey assertion") | #4285. |
| ENF-q-4 | **The second assertion is a challenge of its own** (`Second`, `Confirm`): its own domain (`Domain`), naming the device, the act, "unusual-time", its ID and its expiry, signed by the same passkey with user verification. It is spent on its first try, lasts `action.Window`, and lets one unlock or disarm of that device go ahead until it expires; `Gate.Act` spends it. Neither tap can stand in for the other, and a text reply cannot be one, since only the passkey signs. The page draws both challenges on one screen at an unusual time (`Gate.Unusual`) and posts the second before redeeming the first; that page change is slice l's wiring with the page's own tests. Until it lands, an unusual-time unlock is refused (`ErrSecond`), never let through. | NET-6, NET-4 Passkey rules | — |
| ENF-q-5 | **A visitor's code is a standing rule with action `code`** (`ActionCode`) on a lock. While its window is open, the enforcer sets the code on the lock's own PIN-code schedule with that window (Door Lock cluster, Matter and Zigbee alike, `spikes/ENF-radio/README.md`); outside it the lock holds no such code. `Driver.SetCodes` is declarative: it makes the enforcer's codes on the lock exactly the list, so a code revoked or ended is removed, and the first tick after a restart clears whatever was there. The code comes from the enforcer's device-secret store (`Config.Codes`, slice r) and is never logged; a code that is not 4 to 12 digits is not set. Codes are pushed only when the open set changes. | NET-4 Standing rules ("which the enforcer sets on the lock and removes when the window ends"), NET-6 | Alarm keypad codes would be the same rule on an alarm; no row asks for it yet. |
| ENF-q-6 | **What the radio reports is untrusted** (ENF-k-6, spike risk 4). A report (`Seen`) can only add a log line, a text or an earlier relock. A "locked" report never cancels a relock; a keypad unlock naming a rule that is not an open code rule on that lock relocks at the next tick; a report from a device that cannot make it is dropped. Reports wait for the next `Tick`, so the radio host's read loop never calls back into it, and at most 64 wait (`MaxEvents`); past that they are dropped and every lock relocks at once. | NET-2 Confined radio stacks, NET-6 | — |
| ENF-q-7 | **Every unlock or disarm is logged; one at an unusual time is texted**, whether the enforcer did it or only saw it (a key, a keypad, the vendor's app). A visitor's code inside its window needs no ask but is still texted at an unusual time, since NET-6 texts "any unusual-time unlock or disarm the enforcer sees". The enforcer's own act is told once: the lock's report of it within 15 seconds is not told again. A routine disarm has no alert kind, so it goes to the enforcer's log line (`Config.Log`). | NET-2 Texts and calls, NET-6, NET-4 Standing rules ("logs each use it sees") | — |
| ENF-q-8 | **`Act` takes no lock the page holds.** The page holds the policy lock while `Book.Redeem` runs; `Act` reads no policy, takes only the gate's own mutex, and calls the driver and the alert log outside it. The relock is due before the unlock is sent, so an unlock whose answer never comes is still relocked. | ENF-s-8, NET-6 | — |
| ENF-q-9 | **A frozen lock is isolated by the firewall, not here.** `policy.Linked` and `broker/enforcer/nft` already cut a frozen device's pairs and keep its outbound to its allow list (ENF-i); `TestFrozenDeviceIsolated` holds that for a Wi-Fi lock, and shows the enforcer still relocks it. A Thread or Zigbee lock has no IP path at all. | NET-7 Freeze, A18 Locks | — |
| ENF-q-10 | **`Driver` is the lock's stack, behind slice k's radio interface.** Slice t's Matter and Zigbee adapters build it over `radio.Host` and declare its ops (unlock, disarm, lock and the PIN-code schedule) for their stacks; slice q stays stack-independent and is tested against a fake radio modelling the Door Lock cluster. | Brief decision 6, slice t | — |
