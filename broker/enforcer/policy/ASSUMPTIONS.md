# Enforcer policy: assumptions

Each row is a reading of the spec, or a property the code relies on, that a
reviewer may want to change (briefs/ENF.md slice a, #3658).

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| ENF-a-1 | **The library check is `PublicKey.Verify` over `key.RootMsg`, not `key.Chain`.** A version is the brief's `key.Root{Clerk: "enforcer", Serial: "policy/<version>/<doc hash>/<diff hash>"}` with no verbs. `key.Chain` refuses a root with no verbs, and no verb on the closed list (VRB-2) names a policy change, so `Verify` and `Check` call `owner.Verify(key.RootMsg(root), sig)`. That is the same function `key.Chain` calls on a root, and it also takes only the assertion's one canonical encoding (low S, exact JSON), so a version's key ID is unique. No verb or caveat kind was added (brief decision 2). | STO-4, KEY-1 | If the enforcer's keys are ever derived or narrowed (links), they need a verb and `key.Chain`. That is a change to `broker/kernel/key` and goes to the kernel's issue first. |
| ENF-a-2 | **The owner is one ES256 credential on the enforcer's own RP ID**, passed to `Open`. Ed25519 owners, the kernel tests' fake authenticator, are refused. Enrolling, replacing and revoking the passkey is slice c, which re-opens the engine with the new key. The stored versions must still verify under it, so slice c either keeps the old public key for checking stored versions or re-signs them at enrolment. | NET-4 Passkey rules, Enrolment and recovery | — |
| ENF-a-3 | **Every tightening of a safety-list device other than lock and relock needs the passkey, standing rules included.** NET-4 is read literally: narrowing or revoking a rule on a safety-list device, such as a lock's visitor code, is an asserted tightening (`Class.Owner`). It applies at once, but only through `Propose`. Revoking a code can lock out a carer, which relocking cannot, and a rule's action is free-form, so revoking a disarm window could arm an alarm while people are home. Rules on off-list devices narrow and revoke from the channel. An op that isolates or removes a device also counts as touching every safety-list device paired with it, because it cuts that pair. Decided by the L3 and Security fix-lists on #3697. | NET-4 Tightening, Standing rules | Texting "revoke the plumber's code" becomes a link to the page (slice s), not an action. |
| ENF-a-4 | **The tightening limit is 6 per device per hour** (`TightenLimit`, `TightenWindow`). It counts unsigned tightenings and secure-direction commands, and is held in memory, so a restart resets it. NET-4 asks for a limit but gives no number. | NET-4 Tightening ("rate-limits tightenings") | Slice d measures the channel's real rate and may change the numbers. Persisting the counts would need the store on every relock. |
| ENF-a-5 | **Restoring an older document is classified by what it changes.** NET-2 Recovery makes a restore a loosening. A restored document is a new, higher version with a fresh assertion and goes through `Classify` like any other: if it widens anything, it waits 10 minutes. A restore that only differs by one closed-list tightening applies at once, because that is all it does. | NET-2 Recovery, NET-4 Loosening | A rule that every restore waits would need a restore flag on the proposal, which the page (slice b) would set. |
| ENF-a-6 | **Tightenings are steps on top of the base version, and only one loosening waits at a time.** The base is the last signed loosening applied. Every tightening after it is a step, whether it came unsigned from the channel or was signed by the owner (asserted, or approved on the page). A signed step keeps its key and the document it tightened (`Prev`), so a restart can check that the owner signed exactly that op. While a loosening waits, a step is taken only if it would carry over when the loosening lands. It must apply to the loosening's document with the earlier steps re-applied, and, if unsigned, must not touch a safety-list device there. Otherwise it is refused at once with `ErrPending` or `ErrNeedsOwner`, which the page or text can show. The loosening then lands with every step re-applied: no tightening reported as applied is undone, and no signed loosening is dropped. `Open` refuses a state whose pending loosening could not carry its steps. A second loosening is refused while one waits, because it was drawn against the policy without the first. `Spent` is the highest version ever verified, including versions that were cancelled or refused, and it only rises, so each assertion is good once. | NET-2 Recovery ("version number that only rises"), NET-4 Loosening and Tightening | Queueing loosenings needs each one rendered against the policy with the earlier ones applied, which is the page's work (slice b). |
| ENF-a-7 | **The store is part of the trusted base.** `Open` re-verifies every stored signed version and replays every step through `Apply` and `Classify`. A store edited by someone else can still drop state (roll back to an older signed version), as in DRONE-sim-13. Slice l puts it on the enforcer's sealed store. | STO-4, P5 | — |
| ENF-a-8 | **The document's fields** follow brief decision 2. Segments are the six fixed NET-2 networks, not a list. A standing rule names its action, not its secret: a keypad code is a device secret, held beside the policy (slice r). The drone limits are referenced by hash to `broker/drone`'s signed policy. A device's Wi-Fi identity is a string, the VLAN tag, until question 2 on #3662 is decided. Its meaning is not used here, and changing it is a loosening either way. | NET-2, NET-4 | A later slice that adds a field must add a row to `TestClassifyClosedList` (the field check fails until it does). |
| ENF-a-9 | **Safety-list membership is its own field, and the default is on the list.** `Device.Everyday` takes a device off the list. Its zero value is on, so a device nobody classified fails safe (NET-2: "a device of unknown type or on no list counts as safety"). Setting it is a loosening. `Secure` only names the one secure-direction command, is valid only on a safety-list device, and may be empty, as for a camera. The class lists (camera, plug, heater and the rest) belong to the device-naming slices, which must never set `Everyday` on a listed class. | NET-2 Safety devices, NET-4 | — |
| ENF-a-10 | **The export for the core's backup** is the base version and every step since (`Export`). `ReadExport` rebuilds the policy from it the way `Open` does: it checks the base against the owner and replays each step, accepting an asserted step only with the owner's signature over it. So what it returns is derived from what it verified, and a core serving the backup cannot change it. It restores only through `Propose`: the owner signs the result as a new, higher version. It holds no secret, because neither a document nor an op has a field for one. `TestExportRestoresAndHoldsNoSecret` fixes the set of keys, so a field that could hold a secret fails there. | NET-2 Recovery, BAK-1, STO-4 | — |
| ENF-a-11 | **A device's NET-1 label is a policy field** (`Device.Label`, added by slice b, #3659): `contained`, `contained-except-radio`, or empty for not containable, so an unlabelled device promises nothing. The page shows it; the device never sets it. Changing it is a loosening (`TestClassifyClosedList` row "relabel"), so only the owner can raise or lower a label. | NET-1 ("from qualification and the enforcer's observation, never from what the device reports") | If qualification writes labels outside the owner's tap, the label moves beside the policy, as device secrets do. |
