# Enforcer mDNS pair relay: assumptions

Each row is a reading of the spec, or a property the code relies on, that a
reviewer may want to change (briefs/ENF.md slice f, #3664; #4069, #4081).

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| ENF-f-m1 | **The relay's pairs are the ruleset's.** `NewPlan` takes `nft.Paths` (and `nft.Announces`, ENF-f-m7), so the relay passes records on exactly the paths the firewall opens: an isolated or VLAN-less device's pair passes nothing, and Owner and Household are each one network (ENF-e-4). | NET-3 Casting | — |
| ENF-f-m2 | **One direction pair per pair.** From a person's network to a device, the network's queries go to the device and the device's responses come back; the device's own queries and the network's announcements are not passed. Between two devices both kinds pass both ways. A packet's side is the interface it arrived on (one socket per interface and family, `SO_BINDTODEVICE`, `IP_MULTICAST_ALL`/`IPV6_MULTICAST_ALL` off, own sends not looped back), never an address or a record in it. | NET-3 ("that device's mDNS records passed only across that pair") | A home device that must discover a person's device (AirPlay to a laptop) needs the other direction signed as its own pair. |
| ENF-f-m3 | **Only the sender's own records pass (#4069).** Every packet is parsed whole (a malformed one is dropped) and rebuilt. A response keeps only A/AAAA records of a `<host>.local` name whose address is in a prefix of the enforcer's own address on the sender's interface (not the enforcer's address, not link-local), SRV records of `<instance>.<_svc>.<_tcp\|_udp>.local` names on such hosts, those instances' TXT records, PTR records from the instance's type or a subtype to the instance, and the service-type enumeration for those types. Everything else (other types, reverse names, non-`.local` names, names with a label a person cannot read as it is (blank, control, bidi, zero-width, tag or filler characters, the hostile-text corpus), questions and authority records in a response) is dropped. A host or instance once proved stays the sender's until its TTL, at most 4500 s, or a goodbye. | NET-3 ("there is no general mDNS reflector, so an infected device cannot advertise onto the Owner network") | Passing a further record type needs its own ownership rule here. |
| ENF-f-m4 | **Names are held by where they are heard.** A name that any other relayed interface claims (a response record's name, a PTR's instance, a probe's proposed record) is never a sender's own, for a day after it was last heard, whatever its TTL or a goodbye says. So a paired device cannot take over a name of its paired network or of another device, and two devices announcing one name are both unseen across the relay. The relay holds this in memory only, so a name not heard on its own network since the relay started is not yet held; the pins (ENF-f-m7) stop a paired device taking such a name anyway. At most 1024 names per interface and table are kept; a full table drops its expired names, then the ones whose holds end soonest until an eighth of it is free, so learning a name costs a bounded amount on average. An index from each name to the interfaces claiming it makes "claimed elsewhere" one lookup however many interfaces there are, and a packet decides each service type once, so a response costs at most a few lookups per record plus one per sender instance when it enumerates types. On a link that hears more than 1024 names a day, the stalest holds go first, and those may be hosts that sleep, which the pins (ENF-f-m7) make harmless: a device can take only a name it pinned, and no other device pins it. Only the hosts on an interface fill its table, so a flood there can loosen only that link's own claims, never stop the relay for every other pair. | NET-3 | — |
| ENF-f-m5 | **A query carries only its questions.** A relayed query keeps its `.local` questions of class IN and loses its known answers, probe records and TC bit, so the receiving side learns nothing of the asker's records; responders then answer without known-answer suppression, within the rate limit. Unicast-response (QU) queries get their answer only if the querier re-asks by multicast, and legacy one-shot queries (not from port 5353) are not passed. | NET-3 | — |
| ENF-f-m6 | **IPv4 and IPv6 alike (#4081).** Each interface has a socket for 224.0.0.251 and one for ff02::fb; a packet leaves in the family it came in, under one rate limit per interface for both: at most 40 packets in a burst and 20 a second. Every packet heard is parsed for its claims, so reading has its own limit per interface, taken before parsing (100 in a burst, 50 a second), and parse refuses a message of more than 64 questions or 128 records before reading any, and one whose names take more than 4096 labels and pointers together (a label counts each time a pointer reaches it, and a name follows at most 16 pointers), which bounds the work a crafted packet buys, in reading it and in learning its names. On a kernel without IPv6 the relay runs on IPv4 alone. | NET-3 | — |
| ENF-f-m7 | **A response passes only its device's pinned names (#4144).** `NewPlan` takes `nft.Announces`: per device interface, the mDNS host and instance names the device pinned in the signed policy (`policy.Device.MDNS`). Before the record filter runs, a response keeps only address records of a pinned host, TXT records of a pinned instance, SRV records of a pinned instance on a pinned host, PTRs to a pinned instance, and service type enumeration PTRs to a pinned instance's type; an interface with no pins passes no records. Pins are signed and never learned, so a restart or a full name table never widens what a paired device announces, and a name the device starts announcing later needs a new signature. The record filter (ENF-f-m3, m4) still runs after, so a pinned name passes only on the device's own address and while no other interface claims it. Queries are not bounded by pins. | NET-3 | A pin per pair rather than per device would need the relay to rebuild a response for each interface it leaves on. |
