# Change pipeline: assumptions

Built for PLAN P3 ("change pipeline with held-out suites") against SPEC v0.12: CHG-1 to CHG-6, and ADP-4 for the routing rule candidates of P2-7's router (`broker/route`). Covers `broker/change`. Each row is a reading of the spec, or a gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| C1 | **One tree.** Everything adoptable is a file in one managed tree, and a candidate is a set of file writes and deletes. The pipeline computes the diff itself against the active tree. Each path's first segment decides its class: `procedures`, `skills`, `routing`, `context` (authority-neutral); `config`, `guest-image`, `host-image` (behavior changes); `grants`, `verbs`, `custody`, `checks`, `egress`, `dataflow`, `labels` (authority); `suites`, `graders`, `policy`, `security`, `budget` (governance). Any other namespace is unknown. A candidate's `Claim` is never read by a decision and never shown to the owner. | CHG-6, ARC-2 | Add a namespace in `tree.go`; each new one is reviewed with its class. |
| C2 | **What no candidate may change.** A candidate that edits an authority, governance, or unknown path fails qualification outright, whatever its source and even if the owner would approve: a fix that widens authority or reduces security coverage must fail (LOOP-10), and suites, graders, adoption policy, and Loop 1's budget change only by an owner-approved intent that the change cannot validate (CHG-2, LOOP-6). Those changes are separate intents (`SetAutoAdopt`, `SetSharing`, `RemoveCase`) or, for grants and verbs, the grants package. | CHG-2, LOOP-6, LOOP-10 | — |
| C3 | **Cases.** A task case names a journal intent whose quality verdict (OP-7) has source `owner` and agrees with the stated outcome: accepted needs `good`; corrected and rejected need `wrong`. A verdict from any other source makes no case, so content the agent read cannot plant evidence (CAP-3). Cases arriving from owner outcomes are the suite's defined input and need no approval; removing a case or a security fixture is an owner-approved intent. Security fixtures are added by broker code (Loop 2 regressions, LOOP-9) and only grow. | CHG-1, CHG-2, LOOP-10, CAP-3 | — |
| C4 | **Split.** A keyed HMAC, with a key generated on first start and held in the pipeline's state, puts 30% of cases in the dev split. It hashes `goal:` plus the case's goal, so every case of one goal lands on the same side (P3-1c). `AddTaskCase` takes the goal from the journal intent's `GoalID`, never from the caller, and refuses a case ID starting with `goal:`. A case with no goal hashes on its bare ID. That covers cases saved before goals were stamped (#55), which keep the side they had, and tasks whose intent has no goal; the loops harvester holds a held-out case's origin for those (#55 B2). `Dev` returns only dev cases, and only those may be given to whatever builds a candidate. Held-out and security cases never leave the pipeline except as counts. | CHG-1 | Tune `DevPercent`. |
| C5 | **Evaluation.** At proposal, the held-out cases relevant to the candidate's classes (every held-out case for an image) and every security fixture are frozen. Each held-out case runs against the active tree and the candidate tree through the `Evaluator`, which receives only a `Probe` (a probe ID derived from a fresh per-evaluation nonce, and the input). Both sides run in one shuffled order under the same probe ID, so the evaluator cannot tell baseline from candidate or link probes across evaluations and never the expected output, the owner's outcome, or whether it is a security fixture; the broker grades. An evaluator that cannot exercise a tree on this box (replay does not boot a changed image or config) returns `ErrNotEvaluated`, wrapped or not. That counts as not evaluated, never a pass or a fail and never `BasisStanding`, only where the evaluator legitimately cannot test: held-out cases on image, config, and routing candidates (routing while replay has no model, #37), and security fixtures on upstream releases. Anywhere else, including every shared package and every security fixture on a local or shared candidate, a case the baseline evaluates but the candidate tree does not is a fail, in proposal and in `Recheck` (#34 third review). So a local config change cannot adopt until the evaluator can run fixtures on it. The owner's line says "Not tested on this box". An attested security release that cannot be evaluated rests on its signatures and attestation (UPD-8), as Mark decided for updates. `ProbeTask` maps a probe ID back to its task intent only while that evaluation runs, so replay can find recordings; because its ok=false marks fixtures, only the trusted replay layer calls it, and nothing it returns reaches the tree under test; security fixtures map to nothing, which the agent-machine layer implements as counterfactual replay (LOOP-5); an evaluator error fails that side. A regression is a case the baseline passes and the candidate fails, or fewer passes overall; either rejects. Every security fixture must pass, for every adoption, not only automatic ones. Nothing adopts, with or without the owner, with fewer than `MinSecurity` evaluated fixtures or with zero held-out passes on both sides when relevant cases exist: an evaluator that cannot run (no model access) fails every case on both sides, which would otherwise read as no regression. When no relevant held-out case exists at all (a config change on a fresh box), the change can still go to the owner with its counts, and the passing fixture shows the evaluator ran. Graders are broker code per class; the default compares with the owner's accepted or corrected output and, for a rejected outcome, passes anything but the rejected output. No evaluator exists yet: the VM layer supplies one when Loop 1 lands. | CHG-1, LOOP-5, LOOP-10 | — |
| C6 | **CHG-6 basis.** A local candidate adopts without a prompt when it edits only authority-neutral paths, passes with no regression on at least `MinHeldOut` (5) relevant held-out cases, passes at least `MinSecurity` (1) security fixtures, and the standing grant is on. With fewer cases it goes to the owner with its counts rather than adopting on no evidence. Routing is neutral only when it keeps the same task classes and chooses among routes the active rule already has; a new route or class asks the owner, and a provider `RouteGranted` does not report fails outright (ADP-4, CAP-9). A skill or procedure that adds an external identifier (a URL, email address, or phone number in international or (NNN) NNN-NNNN form) found nowhere in the active tree asks the owner. This check is a heuristic, not a boundary: it misses JSON-escaped URLs, bare domains, and dashed national numbers; the egress and data-flow checks are what stop an exfiltration. A routing rule with no task classes fails. A context rule (`context/<machine>.json`, `{"select": [...]}`) is neutral only when it selects among what `Receives(machine)` lists; one that selects anything else is data flow and fails. | CHG-6, ADP-4, CAP-9, REV-5 | — |
| C7 | **Upstream and CHG-3.** Upstream candidates come only from `ProposeRelease(update.Verified)`. A `Verified` value can only be built by `update.Verify`, after a threshold of distinct root keys has signed the exact metadata, and it counts as a security release only with at least one independent attestation (UPD-8). The candidate is built from the signed image digests, so what is staged is what was signed. Upstream may edit only `guest-image/` and `host-image/`, and local and shared candidates may not edit those. `Propose` takes local candidates only. Config changes, images, and shared packages go to the owner, except an attested security release under the standing `SecurityAutoStage` policy that does not regress. A security release that regresses is held for the owner, never auto-applied and never rejected outright, so the box is not left on the vulnerable image (arbitrator R2). `Ask` gives the one plain line the wiring sends through CH-15 coalescing: the version, how many past tasks did worse with one example (class and date), then "Approve or decline?". A decline is recorded only when the owner denies an owner-basis request, once per namespace (**wired, P3-1b:** a request that closes without the owner's answer, whether expired, voided by wrong codes, left out of a partial YES, or dropped by a restart, makes `Decided` drop the proposal, and the gate then closes the intent as "lapsed, not declined" (arbitrator Q3 on #48), so it is never recorded as a decline. Only the owner's NO is a decline, and only that is recorded as a decline (`Decided`'s `declined`): a denial at the dispatch recheck, such as a stale approval, drops the proposal without one), and is repeated in every digest until a later release touching that namespace is adopted. The first image release cannot be undone, since that would leave the slot with nothing to boot; its digest line offers MORE but no UNDO, and a concern on it says it stays until a newer update is installed. Other namespaces may be emptied by an undo. A security-suite failure still rejects it. An image adoption is recorded as **staged** (the target writes the inactive slot, UPD-1); `ConfirmStaged` after a healthy boot marks it installed, and `StageFailed` reverts it after a boot-count fallback. `update.Verify` is a stand-in for full TUF (freshness, rotation, rollback protection), which P4 builds on a maintained implementation and which constructs `Verified` the same way. | CHG-3, UPD-1, UPD-8 | — |
| C8 | **Journal.** Every adoption, revert, policy change, and suite change is a `meta.change.*` intent on the broker account with executor `change`, which is the pipeline. Decisions read only the intent ID (`chg:<id>:adopt`, `chg:<id>:revert:<n>:<why>`, `chg:policy:<n>:<setting>:<on/off>`, `chg:suite:<n>:remove:<case>`) and grant reference (`CHG-6`, `CHG-3`, or empty), which the journal never redacts; params carry the same facts (`adoption`/`why`, `setting`/`value`, `case`) so distinct intents never share an effect fingerprint, and are otherwise audit only. `Check` runs at authorize and before dispatch, and refuses an adoption whose base is no longer the active tree, so a stale evaluation never adopts. **Wired (P3-1b, grants GR17):** the grants gate delegates `meta.change.*` intents to `Check`, turns `ErrNeedsOwner` into an owner request whose item comes from `Line`. The item carries a verb, an object of at most 40 characters built from broker-known fields, the test result in `owner.Item.Detail` so the object cap never cuts it (UX-48-1), and how the owner can reverse it (`UndoBy`). **Tier (arbitrator ruling on #48):** a local learned skill or procedure that was tested on past tasks and that UNDO can reverse is an ordinary item, so it is low tier. Everything else (images, config, routing, context, shared packages, untested changes, policy and suite changes) is `GrantChange`, which is always high tier. The ruling asked for a plain `YES <id>` reply. SPEC CH-10 has exactly two tiers, so the low tier here is CH-10's texted code from that request: a bare YES does not count, and a wrong code neither approves nor declines. Three wrong codes void the request, which lapses without a decline (C7). A code-free reply tier would be a spec change for Mark., calls `Decided` once the request closes, and keeps denying `meta.*` from guests (GR14). The gate reaches the pipeline only through the `grants.Changes` interface and spots `ErrNeedsOwner` by its `NeedsOwner()` method, because this package cannot be linked into the control path (ARC-2: `route` brings in `net/http`). Since W3 the pipeline's types come from dependency-free packages (`routerule`), so `agentosd` holds the pipeline in-process as the gate's `Changes` and the `change` executor (daemon B13, loops L16), with only builders' model calls out of process; `daemon/inference_test.go` keeps inference out of what it links. Re-enabling CHG-6 auto-adoption needs only the code-generator code, with no local page: it restores the default, and CHG-6 covers only authority-neutral changes, so it is not a new grant under CH-3 (arbitrator Q2 on #48; a one-line CH-3/CHG-6 note goes in the next spec-diff PR). Origin authentication (`owner`, `change`) is the broker's, as for other intents (journal A7). | OP-3, OP-5, CHG-2 | — |
| C9 | **State.** The active tree, adoptions with their edits (the rollback points), cases, the split key, and the two policy flags are saved atomically in one file (`FileStore`) after each effect. On start the active tree is re-applied to every target, so the router gets the adopted rule back. `Reconcile` answers from the saved state: an effect not saved was not applied, since restart re-applied the old tree. Proposals waiting for the owner are in memory only; after a restart their intents are refused at `Check` and Loop 1 proposes again. | OP-2, OP-4 | Persist proposals if re-evaluation costs real work. |
| C10 | **Revert.** `Revert` takes an adoption's ID or owner-facing short ID. It restores the files the adoption changed only if each still holds what the adoption wrote. Otherwise it refuses with the owner-facing text `Can't undo K3 alone: K5 changed the same thing later. Reply UNDO K5 K3 to undo both.` Every attempt is its own intent (`chg:<id>:revert:<n>:<why>`), so a refused or foreign attempt never blocks a later UNDO. An owner revert (`meta.change.revert`, origin owner) and turning a setting off are authority-narrowing in the journal (A9, DECISIONS 2026-10-05), so they work during STOP; a pipeline revert is `meta.change.revert.auto`, which is not narrowing and so holds during STOP. A revert never leaves an image slot empty. A revert that fails inside `Recheck` is returned in the joined error and the pass goes on to older adoptions; only STOP ends it. After `OutageAlert` (3) passes in a row that hit an evaluator outage, the digest says once that the box could not re-test its learned changes. `Recheck` re-evaluates active adoptions, newest first, on the grown held-out and security suites against the tree without them, and reverts any that now regress or fail a fixture the baseline passes (ADP-4, LOOP-10). A recheck in which the evaluator fails every case on both sides is an outage and reverts nothing. An image the owner approved or that is an attested security release is never auto-reverted: a regression gives it a concern line in the digest, `... now does worse on N of M newer tasks. Reply UNDO S to go back to the previous version, or nothing to keep it.` The Loop 1 scheduler decides when to call it. | CHG-6, ADP-4, CH-16, OP-6 | — |
| C11 | **Owner text.** Each adoption gets a short ID of at most 3 characters (CH-12) from `Config.ShortID`, which the wiring sets to the owner channel's allocator so IDs never clash with open requests; the default is the pipeline's own letter-and-digits sequence, and any ID must start with one of the owner-safe letters. `Digest` returns one fixed-template line per adoption and per revert, built only from broker-known fields (class, owner-configured task class names, machine names, the signed release version): for example `Learned a new way to do a task. Tested on 7 of your past tasks, none worse. UNDO K3 / MORE K3`, `Changed which AI handles calendar tasks...`, and for a reorder that changes a class's first provider or drops the local fallback (`Config.LocalProvider`), `Changed AI routing: chat tasks now go first to anthropic instead of openai` / `... no longer fall back to the local model`, with its UNDO (arbitrator R1; no owner ask), `Undid K3: it did worse on newer tasks.` `More` lists the changed paths, reduced to a fixed alphabet, and the counts; the diff itself stays on the local page. **Wiring (owner channel and control package, with the Loop 1 scheduler):** map `UNDO`/`MORE <id>` to `Revert`/`More`. Map `LEARN OFF`/`LEARN ON` to `SetAutoAdopt` and list them in HELP (LOOP-0). A stale YES gets `That change is out of date. The box will re-test it and ask again if it still helps.`, which is not a wrong code. An owner request for a BasisOwner change shows a broker-rendered summary: paths, routes or providers, config keys with old and new values, and the image version and signers. | CHG-6, LOOP-0, CH-11, CH-12 | — |
| C12 | **Sharing.** Off by default; turning it on is owner-approved. `Export` packages one active adoption only if it was built from public inputs (`Candidate.Public`), changes only procedures and skills with no deletions, and no path or file trips the `Private` check (vault values, canaries); with no check configured nothing is exported. A package carries files plus counts from public held-out cases and fixtures, and no case content, IDs, journal data, identity, or authority. `Import` decodes strictly (any other field refuses the package), admits only procedure and skill paths, ignores the sender's evidence for decisions, and re-qualifies on the recipient's own suites as a shared candidate, which the owner approves or rejects. The bytes travel over whatever git-like channel the owner picks; there is no registry. | CHG-4, CHG-5, OSS-9 | — |
| C13 | **Router.** `RoutingTarget` is the only caller of `Router.SetRule` once wired; `ProposeRouting` turns `Router.Candidate()` into a local candidate. Owner acceptance and cost are not in the router's scores yet (route R10); the held-out routing cases are where owner outcomes enter. | ADP-4, CAP-9 | Feed outcomes into the router's scores when Loop 1 lands. |
| C14 | **Open, for the Loop 1 scheduler (#34 review).** (a) Record ordinary owner actions as OP-7 owner verdicts: YES on an unedited item is good, an owner edit is wrong with the edit as the reference, NO or UNDO is wrong. (b) Hold under-evidenced local candidates and show "waiting for evidence (n/5)" in the digest instead of asking. (c) Count a held-out regression only if it reproduces in 2 of 3 re-runs; security fixtures stay strict. (d) `Report` gives the caller exact held-out counts; consider giving Loop 1 accept or reject only, to limit overfitting to the hidden suite. (e) Done in P3-1b: `grants/change_test.go`. (g) **Before Loop 1 emits (arbitrator PL1 on #48):** when a proposal lapses, back off before proposing the same candidate again. The backoff starts at the next digest and doubles each time. After 2 lapses, list it in the digest ("waiting: adopt <x>, YES <id>") instead of texting it. Security releases keep their path. (h) **Potency condition PL2 on #48:** (b) is a condition before Loop 1 emits anything, so the box never sends a high-tier ask for an untested change. (f) The arbitrator may rule on a private task class whose first route moves from local to remote. **Status (P3-2, `broker/loops`):** (a) is `loops.Harvester` (L6), with harvested cases in `ClassTask`, relevant to every task class (L7); (b) and (h) are Loop 1's evidence hold (L9); (d) holds: only the scheduler reads reports, never a builder (L8); (g) is L18; the recheck cadence is L13; (c) and (f) stay open (L17). | CHG-1, CHG-6, OP-7 | — |
| C15 | **Preempted evaluations (PE1, potency on #62).** When the evaluation's context ends part way (the loop scheduler's `Preempt`, LOOP-1, RES-1), or the evaluator returns an error wrapping `ErrInterrupted` (admission refused or preempted a replay machine, replay R6, PE3), `evaluate` stops at once and returns `ErrInterrupted` (wrapping the context's error) instead of a score (or the evaluator's own interruption error), so `Propose`, `ProposeRelease`, `Import`, `Export` and `Recheck` report no verdict: nothing is submitted, reverted, or counted as an outage. The run in flight is discarded, since a preempted run may have failed because of the preemption. Every side that finished is kept, in memory only, as booleans keyed by SHA-256 of the evaluator's identity (`Config.EvaluatorID`, security R1 on #103), the base tree's hash, the candidate tree's hash and the case's full JSON, so a changed case, another candidate, a moved base or a reconfigured evaluator runs afresh. A side once seen is never run again. The next evaluation of the same trees runs only the missing sides, with a fresh nonce and probe IDs as always (CHG-1), and uses up what was kept; a finished evaluation never feeds a later one, so a Recheck still re-runs every case. **Forced preemptions (security F1 on #103):** a candidate can drive host memory pressure, and so `Busy`, by thrashing in its machine; each candidate-side run cut short is counted per case, and after `MaxInterruptions` (2) the candidate fails that case without another run. Only cuts a candidate could cause count; the owner's are exempt, up to `MaxExemptPerCase` per case (C21, PE5, PE5b). The counts are saved, so a restart does not reset them. A baseline side the evaluator errored on (a model outage or rate limit, not a grader's fail) is not kept, so it cannot sit as a fail and hide a regression; it runs again on resume. A candidate side's error is kept as a fail, since the candidate may cause it (L3 on #103). Kept entries expire after `ResumeFor` (12 h) and are capped at `MaxKeptPairs` (4096), oldest dropped first in amortized constant time; a restart drops them. | LOOP-1, RES-1, CHG-1, LOOP-10 | Persist kept results if restarts mid-evaluation turn out common. |
| C16 | **Broker notices in the digest (W3-route, UX-108-1 on #108).** `Notice(key, line)` queues one fixed broker line for `Digest`, once per key: a key already kept, listed or not, adds nothing, across restarts (state `notices`). It is for what CH-15 does not count as urgent, so it waits for the digest instead of a text. Callers pass fixed broker wording only, never candidate or agent text (CH-12). At most `MaxNotices` (32) keys are kept, the oldest listed one dropped first, so a dropped key could be noticed again only after 32 newer ones. First user: `agentosd`'s routing, when the owner's `-rule` stands in for a refused adopted rule (loops L16). **Superseded (W3-route-a, L3 MUST-1 on #110).** When a target could no longer take a namespace's adopted state because the owner changed the configuration it reorders, `Superseded(ns, was)` records the owner's configuration (the empty tree) as active, if the namespace still holds `was`, and marks each active adoption that edited it undone with `WhySettings`, with no line or UNDO of its own (the caller's notice tells the owner). It calls no target, which already runs the owner's configuration, and is no intent: it records what runs rather than changing it (CHG-2), so later evaluations compare against what the owner actually has. It is only for a namespace whose empty tree means the owner's own configuration, which today is `routing` alone (security R3 on #110). (C15 is PE1's, #103.) | CH-15, CH-12, CHG-2, CHG-6 | — |
| C17 | **Implicit cases (W3 PW3 part B; potency PK2, security B1, potency C1 and C3 on #90).** A task case whose journal verdict source is the owner's source plus `-implicit` (loops L6) is implicit, whatever the caller says, and is only ever accepted. Implicit cases are held-out evidence like any other, and a candidate must not regress on them, but they never anchor an auto-adoption: a local, authority-neutral candidate qualifies on its own only if it passed at least one explicit case whose reference the owner approved or wrote (`EndorsedPassed`, an accepted or corrected item; not repeating a refused item is weaker, L3 SHOULD-5 on #109), and toward `MinHeldOut` an implicit case counts half (`weighed`). One that would otherwise have adopted goes to the owner instead with `NeedsExplicit`, at the tier `Line` gives it: a local, tested, undoable skill or procedure is an ordinary low-tier item (potency C1, the arbitrator on #48). An implicit case is never an owner-facing example (B1(b)), and `Dev` returns one without its input or reply, so its content never reaches a builder (L3 MUST-3 on #109; the arbitrator's "count, not content"). `Score` gives the implicit part of each count. | CHG-1, CHG-6, OP-7 | Let 3 or more implicit cases anchor local, undoable skill and procedure adoptions if the anchor is the main blocker in real use (potency). |
| C18 | **Forgetting a task (W3-tasks part 1).** `ForgetGoal` removes every task case harvested from one goal and saves the suite without them. It is the owner's deletion (CAP-3), called only by the broker's handling of an authenticated owner forget (none exists yet), never by a candidate or a loop, so it takes no second approval: CHG-2 guards the suite against changes the owner did not make. `TestOnlyTheDaemonForgets` fails any package but `cmd/agentosd` that calls `ForgetGoal` or the harvester's `ForgetCases`, which drops the harvest records of the forgotten cases so held-out evidence stops counting them. A retried forget after a failed save saves again (security R1 on #123). The journal keeps a forgotten goal's intents, so the daemon tombstones the goal ID (`forgotten.json`, IDs only, before any deletion): Loop 1's mining and the compiler read the journal without its intents, and no text, values or case is kept for it again (security F1 on #123). Security fixtures carry no goal and never go. **Not yet (the cascade, security C1 on #120):** adoptions whose evidence included the forgotten cases stay active, and their reports and history keep the case IDs, until the forget action removes or rebuilds them. **Never caught by a broker forget:** a guest serving task B can copy task A's content into a request it makes for B, and that copy is B's from then on. | CAP-3, CHG-2 | The cascade, before the first owner-facing forget action. |
| C19 | **Deletion (CAP-3).** `ForgetTasks` removes the task cases built on journal intents that recall's deletion reach erased: their input and expected output may hold the deleted record. It is erasure, not a suite change, so it needs no owner intent (unlike CHG-2 removal); security fixtures have no task and are never removed this way. Threat: an agent able to delete sources could shrink the held-out set. It fails closed, since below `MinHeldOut` no candidate qualifies, and `state.Forgotten` counts the removals for the digest. In `agentosd` recall's `ServiceConfig.Cases` is the learning plane's `ForgetTasks`, one method so the parts cannot be wired apart (security F1 on #59): the harvester's tombstone first (`loops.Harvester.ForgetIntents`: `Harvest` refuses the intent from then on, so one still in flight cannot settle into a case; its `Added` mark goes, so evidence stops counting it; `Tasks` and `Origins` stay, so mining still skips it), then these cases, then the task values kept from the intents' params (an intent still queued for values when the forget runs is refused when it is drained, security F2 on #59). The reach runs it before the journal erases the intents and again after, and on every retry. **Who may delete (security A1 on #59):** the first production caller of `recall.Index.Delete` must be an authenticated owner deletion or a source deletion the owner confirmed, never an agent's request or a source-side sync an agent can trigger; otherwise an agent could erase its own lineage's Rejected cases. | CAP-3, CHG-1, CHG-2 | Show `Forgotten` in the digest. |
| C20 | **New identifiers in context rules (W3-builder, security C-3c-4).** C6's new-identifier check also covers context rules, so it covers every text file a Loop 1 builder may write (procedures, skills, context). A context rule naming an address the active tree never used asks the owner. Its select list is already limited to sources the machine receives. | CHG-6 | — |
| C21 | **Which interruptions count (PE5; arbitrator, with security F1 on #103 and P1 to P5).** Only a cut a candidate could have caused counts toward `MaxInterruptions` (still 2). The host marks the rest with errors wrapping `ErrOwnerPreempt`, each logged by a fixed class: `ErrOwnerStop` (STOP, LOOPS OFF, pausing the running loop; `owner-stop`); `ErrOwnerWork` (the owner's accepted work, `admission.Request.Owner`, while memory pressure is within its limit; `owner-work`); `ErrNoRoomPreempt` (admission has no room for the replay machine's fixed declared budget, while no other replay machine and no other running experiment holds room; `no-room`); `ErrClassRevoke` (admission recorded, when it picked the replay machine as victim, that it was for foreground or the owner's accepted work without pressure; `class-revoke`). Foreground is admitted whatever the pressure, so a revoke for foreground is exempt under pressure too: no candidate can start the owner's foreground work. The scheduler reads busy, owner and pressure in one `admission.BusyCause` call, and pressure wins. Accepted work without the owner mark (a loop's, a replay's, the clean room's) is not the owner's, and experiments cannot carry the mark. Only host code attaches these marks, as error values, never from a machine's, replay's or guest's text, so that text counts like any other. When both the evaluator's interruption and the context's cause are present, the cut is exempt only if both are marked; otherwise the unmarked one counts and is the one logged. Pressure, other revokes and any unknown cause count. A counted cut logs "a candidate run was cut short (`pressure` / `refused or revoked` / `unknown`); counted"; an exempt cut logs "a candidate run was cut short (its class); not counted" (counted per evaluation, whichever side was in flight). **Parking.** A candidate with `MaxExempt` (6) exempt cuts is parked: never struck, and no verdict. It is refused with `ErrParked`, before it spends a proposal ID or a save, unless the scheduler marks the evaluator idle (`WithIdle`, only in a pass where nothing but parked work was offered). Its loop is ordered last, so Loop 3's releases never wait behind it. Parking orders and idles: parking ends the pass, and its exempt count keeps growing. So `MaxExempt` bounds one pass, not one candidate. The count is per process (in memory, bounded to 1,024 candidates) and resets on restart. **Per case (PE5b, security B2 on #127):** an owner's cut of one (candidate, case) pair is exempt `MaxExemptPerCase` (2) times; the next counts under `MaxInterruptions` and logs `(<class>, past its exempt limit); counted`. Both counts per pair are saved in the state (`cuts`: counts and a time under `resumeKey`'s hash, no case content), so a restart resets neither; they expire with `ResumeFor`, are bounded to 1,024 pairs (oldest dropped), and go with the verdict. So owner cuts re-roll a case at most `MaxExemptPerCase` + `MaxInterruptions` times. **Idle turns:** the idle evaluator does not pick a parked candidate straight after its own idle run while another parked candidate has waited since; that one goes first.
