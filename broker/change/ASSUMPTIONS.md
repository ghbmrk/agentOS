# Change pipeline: assumptions

Built for PLAN P3 ("change pipeline with held-out suites") against SPEC v0.12: CHG-1 to CHG-6, and ADP-4 for the routing rule candidates of P2-7's router (`broker/route`). Covers `broker/change`. Each row is a reading of the spec, or a gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| C1 | **One tree.** Everything adoptable is a file in one managed tree, and a candidate is a set of file writes and deletes. The pipeline computes the diff itself against the active tree. Each path's first segment decides its class: `procedures`, `skills`, `routing`, `context` (authority-neutral); `config`, `guest-image`, `host-image` (behavior changes); `grants`, `verbs`, `custody`, `checks`, `egress`, `dataflow`, `labels` (authority); `suites`, `graders`, `policy`, `security`, `budget` (governance). Any other namespace is unknown. A candidate's `Claim` is never read by a decision and never shown to the owner. | CHG-6, ARC-2 | Add a namespace in `tree.go`; each new one is reviewed with its class. |
| C2 | **What no candidate may change.** A candidate that edits an authority, governance, or unknown path fails qualification outright, whatever its source and even if the owner would approve: a fix that widens authority or reduces security coverage must fail (LOOP-10), and suites, graders, adoption policy, and Loop 1's budget change only by an owner-approved intent that the change cannot validate (CHG-2, LOOP-6). Those changes are separate intents (`SetAutoAdopt`, `SetSharing`, `RemoveCase`) or, for grants and verbs, the grants package. | CHG-2, LOOP-6, LOOP-10 | — |
| C3 | **Cases.** A task case names a journal intent whose quality verdict (OP-7) has source `owner` and agrees with the stated outcome: accepted needs `good`; corrected and rejected need `wrong`. A verdict from any other source makes no case, so content the agent read cannot plant evidence (CAP-3). Cases arriving from owner outcomes are the suite's defined input and need no approval; removing a case or a security fixture is an owner-approved intent. Security fixtures are added by broker code (Loop 2 regressions, LOOP-9) and only grow. | CHG-1, CHG-2, LOOP-10, CAP-3 | — |
| C4 | **Split.** A keyed HMAC of the case ID, with a key generated on first start and held in the pipeline's state, puts 30% of cases in the dev split. `Dev` returns only dev cases, and only those may be given to whatever builds a candidate. Held-out and security cases never leave the pipeline except as counts. | CHG-1 | Tune `DevPercent`. |
| C5 | **Evaluation.** At proposal, the held-out cases relevant to the candidate's classes (every held-out case for an image) and every security fixture are frozen. Each held-out case runs against the active tree and the candidate tree through the `Evaluator`, which the agent-machine layer implements as counterfactual replay (LOOP-5); an evaluator error fails that side. A regression is a case the baseline passes and the candidate fails, or fewer passes overall; either rejects. Every security fixture must pass, for every adoption, not only automatic ones. Nothing adopts, with or without the owner, with fewer than `MinSecurity` fixtures or, when relevant held-out cases exist, with zero held-out passes: an evaluator that cannot run (no model access) fails every case on both sides, which would otherwise read as no regression. Graders are broker code per class; the default compares with the owner's accepted or corrected output and, for a rejected outcome, passes anything but the rejected output. No evaluator exists yet: the VM layer supplies one when Loop 1 lands. | CHG-1, LOOP-5, LOOP-10 | — |
| C6 | **CHG-6 basis.** A local candidate adopts without a prompt when it edits only authority-neutral paths, passes with no regression on at least `MinHeldOut` (5) relevant held-out cases, passes at least `MinSecurity` (1) security fixtures, and the standing grant is on. With fewer cases it goes to the owner with its counts rather than adopting on no evidence. Routing is neutral only when it keeps the same task classes and chooses among routes the active rule already has; a new route or class asks the owner, and a provider `RouteGranted` does not report fails outright (ADP-4, CAP-9). A context rule (`context/<machine>.json`, `{"select": [...]}`) is neutral only when it selects among what `Receives(machine)` lists; one that selects anything else is data flow and fails. | CHG-6, ADP-4, CAP-9, REV-5 | — |
| C7 | **CHG-3 basis.** Config changes, upstream images, and shared packages always go to the owner, unless the candidate is an upstream release marked `Security` and the standing `SecurityAutoStage` policy is on. Only the update channel sets `Security`, after UPD-8's signature threshold and attestation check; a local or shared candidate claiming it is refused. For image namespaces, a target's `Apply` stages into the inactive slot (UPD-1); boot counting and fallback stay in the update code. | CHG-3, UPD-1, UPD-8 | — |
| C8 | **Journal.** Every adoption, revert, policy change, and suite change is a `meta.change.*` intent on the broker account with executor `change`, which is the pipeline. Decisions read only the intent ID (`chg:<id>:adopt`, `chg:<id>:revert`, `chg:policy:<n>:<setting>:<on/off>`, `chg:suite:<n>:remove:<case>`) and grant reference (`CHG-6`, `CHG-3`, or empty), which the journal never redacts; params are audit only. `Check` runs at authorize and before dispatch, and refuses an adoption whose base is no longer the active tree, so a stale evaluation never adopts. **Wiring:** the grants gate (#27) must delegate `meta.change.*` intents to `Check`, turn `ErrNeedsOwner` into an owner request, and keep denying `meta.*` from guests (GR14). Origin authentication (`owner`, `change`) is the broker's, as for other intents (journal A7). | OP-3, OP-5, CHG-2 | — |
| C9 | **State.** The active tree, adoptions with their edits (the rollback points), cases, the split key, and the two policy flags are saved atomically in one file (`FileStore`) after each effect. On start the active tree is re-applied to every target, so the router gets the adopted rule back. `Reconcile` answers from the saved state: an effect not saved was not applied, since restart re-applied the old tree. Proposals waiting for the owner are in memory only; after a restart their intents are refused at `Check` and Loop 1 proposes again. | OP-2, OP-4 | Persist proposals if re-evaluation costs real work. |
| C10 | **Revert.** `Revert` restores the files an adoption changed only if each still holds what the adoption wrote; otherwise it is refused naming the path, so undoing an older change never clobbers a newer one. The owner's `UNDO <id>` and the pipeline itself (on regression) may revert. `Recheck` re-evaluates active adoptions, newest first, on the grown held-out suite against the tree without them and reverts any that now regress (ADP-4's roll back on regression). The Loop 1 scheduler decides when to call it. | CHG-6, ADP-4, CH-16 | — |
| C11 | **Owner text.** `Digest` returns one fixed-template line per adoption and per revert, with `UNDO <id>` while active, and no candidate text. Turning CHG-6 off (`SetAutoAdopt(false)`) and stopping sharing need only an owner-origin intent; turning either on is owner-approved. The owner channel maps its texts and the digest's `UNDO` to these calls; that wiring, and HELP's word list, land with the loop scheduler. | CHG-6, LOOP-0, CH-11 | — |
| C12 | **Sharing.** Off by default; turning it on is owner-approved. `Export` packages one active adoption only if it was built from public inputs (`Candidate.Public`), changes only procedures and skills with no deletions, and no path or file trips the `Private` check (vault values, canaries); with no check configured nothing is exported. A package carries files plus counts from public held-out cases and fixtures, and no case content, IDs, journal data, identity, or authority. `Import` decodes strictly (any other field refuses the package), admits only procedure and skill paths, ignores the sender's evidence for decisions, and re-qualifies on the recipient's own suites as a shared candidate, which the owner approves or rejects. The bytes travel over whatever git-like channel the owner picks; there is no registry. | CHG-4, CHG-5, OSS-9 | — |
| C13 | **Router.** `RoutingTarget` is the only caller of `Router.SetRule` once wired; `ProposeRouting` turns `Router.Candidate()` into a local candidate. Owner acceptance and cost are not in the router's scores yet (route R10); the held-out routing cases are where owner outcomes enter. | ADP-4, CAP-9 | Feed outcomes into the router's scores when Loop 1 lands. |
