# Worker machines: assumptions

Built for BOARD CAP-8 (SPEC v0.12 CAP-8; A14 and A15 parts) on the machine
lifecycle (P1-4) and the guest plane (P1-7). Each row is a reading of the
spec, or a gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| K1 | A worker is a machine whose ID starts `wk-`, made only by `vm.CreateWorker`. It runs the configured base image (`-worker-image`, with `-worker-argv` as its idle process) under gVisor like any machine: no network, and **no guest services**: no broker socket, so no tools, owner channel or model egress. A worker therefore spends no frontier budget, and there is nothing for it to reserve beyond memory. | CAP-8, ARC-5, ARC-6 | `vm.startFrom` skips `Services` for workers. |
| K2 | Isolation, custody and reach are inherited by **lineage**: a worker joins its creator's lineage, so its snapshots stay in that lineage's custody, OP-1 treats it as the same requester, and CAP-3 deletion reach (`ForgetSince`) rolls workers back with the agent. A lineage held only by workers cannot make more. | CAP-8, CAP-3, OP-1 | `vm.CreateWorker`, `lineageLive`. |
| K3 | Budget: a worker is admitted on its creator's admission class with the memory it asks for (default 256 MiB, so 8 fit beside the N95's agent; 64 to `-worker-max-mb`), so RES-2 admission decides how many run and preemption treats it like its creator's other work. A lineage holds at most 16 workers at once (A15 needs 8), counted with the IDs being made, which are reserved under one lock before the machine is made and released after, so concurrent creates and forks cannot pass it while a fork waiting on a busy worker holds up no other call (L3 MUST-4 on #146). Reap skips a worker whose lock is held: it is in use. A refusal for want of room says what works: destroy a worker or ask for less memory. | CAP-8, RES-1, RES-2, A15 | `workers` limits. |
| K4 | Labels (REV-5, A14): a worker starts with its creator's label. A command or file write is a write into the worker, so a private machine raises a public worker to private before it acts. A command's output, a file read, a fork (it carries the worker's memory) and a diff are reads: a public machine cannot do them on a private worker or snapshot. Labels never fall; rollback keeps the label. For a command or file transfer, the raise and the read check happen in `vm.Manager.Exec` under the worker's lock (`Command.As`), so another machine's raise cannot land between the check and the command (L3 MUST-2 on #146). | REV-5, A14 | `vm.Manager.Exec`, `readable`. |
| K5 | Naming: the guest names a worker; the broker's ID is `wk-` + 8 hex of the lineage's SHA-256 + `-` + name, and every use checks the manager's record for the caller's lineage. Another lineage's worker answers "no such worker", the same as one that does not exist. Snapshot IDs a tool accepts must be snapshots of the caller's lineage's workers: never the agent's own, nor another lineage's. | CAP-8, REV-5 | `workerID`, `Tools.snapshot`. |
| K6 | Commands run as root in the guest from `/` through `runsc exec`, with the arguments after the container ID so none is read as a runsc flag. At most 64 arguments and 16 KiB of them, 512 KiB of stdin, a 1-minute default and 10-minute maximum timeout; each output stream is capped at 64 KiB and marked truncated. A non-zero exit is a result. The manager holds the worker's lock for the command, so no snapshot or rollback of it interleaves; preemption still does not wait (it kills the sandbox). File read is `tail -c +N --` with the output cap as the length (a file reads in pieces of at most 64 KiB), and write is `tee --`, so the base image needs them (busybox or coreutils). Binary goes both ways as base64 (`stdin_base64`, `output_base64`, `content_base64`, `base64`); a tree moves as a tar archive over exec stdin. | CAP-8, RES-1 | `vm.Manager.Exec`, `gvisor.Runtime.Exec`. |
| K7 | Workers fork into workers only, nothing else forks into a worker, and workers are never merged: a worker's memory never runs with an agent's services, nor an agent's without them. | CAP-8, ARC-6 | `vm.Fork`, `vm.Merge`. |
| K8 | Worker operations are broker state, not effects: nothing leaves the box, so they are not journaled as intents and need no approval. Only machines on the live guest plane get the tools; replay and builder machines never do, and a worker has no socket to ask with. | CAP-8, LOOP-5 | `agentosd` `workerTools`. |
| K9 | **Gap:** CAP-1's measured N (how many forks fit) is not computed here; admission refuses what does not fit, and the guest sees the refusal. CAP-1 builds on these tools. | CAP-1 | CAP-1 row. |
| K10 | Idle workers do not hold memory (UX-146-1): every minute the broker **parks** (checkpoints, memory included, then stops and releases admission) each running worker that no tool has named for an hour, and every worker whose lineage has no running machine other than workers (its creator stopped, slept or was preempted). The parking checkpoint is the worker's newest snapshot; `worker_list` shows it stopped with that snapshot, and `worker_rollback` to it revives the worker as it was. After a broker restart the hour starts afresh. A worker busy with a command is in use: Reap skips it and `Park` refuses it at once (`ErrBusy`) rather than wait. | RES-1, RES-2, CAP-8 | `Tools.Reap`, `vm.Manager.Park`. |
| K11 | Erasure never waits behind a command (security F1 on #146): `ForgetSince`, `Rollback` and `Destroy` take a machine's lock by ending any worker command that holds or takes it meanwhile, so a 10-minute command delays them by milliseconds. The guest sees the command end with an error. | CAP-3, CAP-8 | `vm` `lockEndingExec`. |
| K12 | Ending a command ends it inside the sandbox (L3 MUST-1 on #146): on timeout or cancel, gVisor kills the host `runsc exec` and, by the in-sandbox pid it wrote (`--internal-pid-file`), the command itself (`runsc kill --pid … KILL`, logged on failure, never waited on). `runsc exec` passes its stdio into the sandbox, so a command's children could hold the pipes open; `WaitDelay` (3 s) bounds the wait for them. Above that, `vm.Manager.Exec` stops waiting for a runtime that ignores cancellation `ExecGrace` (15 s) past the timeout, so erasure waits at most that long. A command's own children that escape the kill end with the worker: rollback, erasure and destroy restart or stop it. | CAP-3, RES-1, CAP-8 | `gvisor.Runtime.Exec`, `vm` `awaitExec`. |
| K13 | No goal stamp on workers (P3-7 C3 does not apply): C3 assumed workers would sit outside the creator's lineage and so need its goal carried over. Here a worker joins its creator's lineage (K2) and has no broker socket (K1), so it makes no effect requests and no model calls, the only things a goal ID is stamped on (guest G14). The worker tools are broker state, not intents (K8), so the creator's own requests carry the goal and nothing from a worker can go unattributed. If workers ever get a socket or make model calls, they must take their creator's goal then. | OP-1, OP-7, OP-8 | P3-7 binding (C3); guest G14. |
| K14 | While the owner's STOP holds, no worker command starts, and commands in flight are ended within 5 s (security R2 on #146). Workers keep running and keep their files; snapshots, rollback and destroy still work, since nothing leaves the box. | OP-5, CAP-8 | `Tools.Stopped`, `vm.Manager.EndCommands`. |
| K15 | One worker's files may hold at most `-worker-layer-mb` (default 4096 MiB); over it the worker takes no command and no snapshot until files are deleted or it is rolled back, inside the disk's RES-4 reserve (security R3 on #146). | RES-4, CAP-8 | `vm.Config.WorkerLayerBytes`. |
