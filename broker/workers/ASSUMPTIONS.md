# Worker machines: assumptions

Built for BOARD CAP-8 (SPEC v0.12 CAP-8; A14 and A15 parts) on the machine
lifecycle (P1-4) and the guest plane (P1-7). Each row is a reading of the
spec, or a gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| K1 | A worker is a machine whose ID starts `wk-`, made only by `vm.CreateWorker`. It runs the configured base image (`-worker-image`, with `-worker-argv` as its idle process) under gVisor like any machine: no network, and **no guest services**: no broker socket, so no tools, owner channel or model egress. A worker therefore spends no frontier budget, and there is nothing for it to reserve beyond memory. | CAP-8, ARC-5, ARC-6 | `vm.startFrom` skips `Services` for workers. |
| K2 | Isolation, custody and reach are inherited by **lineage**: a worker joins its creator's lineage, so its snapshots stay in that lineage's custody, OP-1 treats it as the same requester, and CAP-3 deletion reach (`ForgetSince`) rolls workers back with the agent. A lineage held only by workers cannot make more. | CAP-8, CAP-3, OP-1 | `vm.CreateWorker`, `lineageLive`. |
| K3 | Budget: a worker is admitted on its creator's admission class with the memory it asks for (default 512 MiB, 64 to `-worker-max-mb`), so RES-2 admission decides how many run and preemption treats it like its creator's other work. A lineage holds at most 16 workers at once (A15 needs 8). | CAP-8, RES-1, RES-2, A15 | `workers` limits. |
| K4 | Labels (REV-5, A14): a worker starts with its creator's label. A command or file write is a write into the worker, so a private machine raises a public worker to private before it acts. A command's output, a file read, a fork (it carries the worker's memory) and a diff are reads: a public machine cannot do them on a private worker or snapshot. Labels never fall; rollback keeps the label. | REV-5, A14 | `Tools.writing`, `readable`. |
| K5 | Naming: the guest names a worker; the broker's ID is `wk-` + 8 hex of the lineage's SHA-256 + `-` + name, and every use checks the manager's record for the caller's lineage. Another lineage's worker answers "no such worker", the same as one that does not exist. Snapshot IDs a tool accepts must be snapshots of the caller's lineage's workers: never the agent's own, nor another lineage's. | CAP-8, REV-5 | `workerID`, `Tools.snapshot`. |
| K6 | Commands run as root in the guest from `/` through `runsc exec`, with the arguments after the container ID so none is read as a runsc flag. At most 64 arguments and 16 KiB of them, 512 KiB of stdin, a 1-minute default and 10-minute maximum timeout; each output stream is capped at 64 KiB and marked truncated. A non-zero exit is a result. The manager holds the worker's lock for the command, so no snapshot or rollback of it interleaves; preemption still does not wait (it kills the sandbox). File read and write are `cat --` and `tee --` commands, so the base image needs them (busybox or coreutils). | CAP-8, RES-1 | `vm.Manager.Exec`, `gvisor.Runtime.Exec`. |
| K7 | Workers fork into workers only, nothing else forks into a worker, and workers are never merged: a worker's memory never runs with an agent's services, nor an agent's without them. | CAP-8, ARC-6 | `vm.Fork`, `vm.Merge`. |
| K8 | Worker operations are broker state, not effects: nothing leaves the box, so they are not journaled as intents and need no approval. Only machines on the live guest plane get the tools; replay and builder machines never do, and a worker has no socket to ask with. | CAP-8, LOOP-5 | `agentosd` `workerTools`. |
| K9 | **Gap:** CAP-1's measured N (how many forks fit) is not computed here; admission refuses what does not fit, and the guest sees the refusal. CAP-1 builds on these tools. | CAP-1 | CAP-1 row. |
