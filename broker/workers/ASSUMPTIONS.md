# Worker machines: assumptions

Built for BOARD CAP-8 (SPEC v0.12 CAP-8; A14 and A15 parts) on the machine
lifecycle (P1-4) and the guest plane (P1-7). Each row is a reading of the
spec, or a gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| K1 | A worker is a machine whose ID starts `wk-`, made only by `vm.CreateWorker`. It runs the configured base image (`-worker-image`, with `-worker-argv` as its idle process) under gVisor like any machine: no network, and **no guest services**: no broker socket, so no tools, owner channel or model egress. A worker therefore spends no frontier budget, and there is nothing for it to reserve beyond memory. | CAP-8, ARC-5, ARC-6 | `vm.startFrom` skips `Services` for workers. |
| K2 | Isolation, custody and reach are inherited by **lineage**: a worker joins its creator's lineage, so its snapshots stay in that lineage's custody, OP-1 treats it as the same requester, and CAP-3 deletion reach (`ForgetSince`) rolls workers back with the agent. A lineage held only by workers cannot make more. | CAP-8, CAP-3, OP-1 | `vm.CreateWorker`, `lineageLive`. |
| K3 | Budget: a worker is admitted on its creator's admission class, but never above accepted work (a foreground agent's workers run as accepted work, so they yield to memory pressure and never outrank the owner's foreground machines; L3 SHOULD-1 on #158, matching #155's cgroup weight for `wk-`), with the memory it asks for (default 256 MiB, of which 7 fit beside the agent on the floor host (8 at 192 MiB, K16); 64 to `-worker-max-mb`), so RES-2 admission decides how many run and preemption treats it like its creator's other work. A lineage holds at most 16 workers at once (A15 needs 8), counted with the IDs being made, which are reserved under one lock before the machine is made and released after, so concurrent creates and forks cannot pass it while a fork waiting on a busy worker holds up no other call (L3 MUST-4 on #146). Reap skips a worker whose lock is held: it is in use. A refusal for want of room says what works: destroy a worker or ask for less memory. | CAP-8, RES-1, RES-2, A15 | `workers` limits. |
| K4 | Labels (REV-5, A14): a worker starts with its creator's label. A command or file write is a write into the worker, so a private machine raises a public worker to private before it acts. A command's output, a file read, a fork (it carries the worker's memory) and a diff are reads: a public machine cannot do them on a private worker or snapshot. Labels never fall; rollback keeps the label. For a command or file transfer, the raise and the read check happen in `vm.Manager.Exec` under the worker's lock (`Command.As`), so another machine's raise cannot land between the check and the command (L3 MUST-2 on #146). | REV-5, A14 | `vm.Manager.Exec`, `readable`. |
| K5 | Naming: the guest names a worker; the broker's ID is `wk-` + 8 hex of the lineage's SHA-256 + `-` + name, and every use checks the manager's record for the caller's lineage. Another lineage's worker answers "no such worker", the same as one that does not exist. Snapshot IDs a tool accepts must be snapshots of the caller's lineage's workers: never the agent's own, nor another lineage's. | CAP-8, REV-5 | `workerID`, `Tools.snapshot`. |
| K6 | Commands run as root in the guest from `/` through `runsc exec`, with the arguments after the container ID so none is read as a runsc flag. At most 64 arguments and 16 KiB of them, 512 KiB of stdin, a 1-minute default and 10-minute maximum timeout; each output stream is capped at 64 KiB and marked truncated. A non-zero exit is a result. The manager holds the worker's lock for the command, so no snapshot or rollback of it interleaves; preemption still does not wait (it kills the sandbox). File read is `tail -c +N --` with the output cap as the length (a file reads in pieces of at most 64 KiB), and write is `tee --`, so the base image needs them (busybox or coreutils). Binary goes both ways as base64 (`stdin_base64`, `output_base64`, `content_base64`, `base64`); a tree moves as a tar archive over exec stdin. | CAP-8, RES-1 | `vm.Manager.Exec`, `gvisor.Runtime.Exec`. |
| K7 | Workers fork into workers only, nothing else forks into a worker, and workers are never merged: a worker's memory never runs with an agent's services, nor an agent's without them. | CAP-8, ARC-6 | `vm.Fork`, `vm.Merge`. |
| K8 | Worker operations are broker state, not effects: nothing leaves the box, so they are not journaled as intents and need no approval. Only machines on the live guest plane get the tools; replay and builder machines never do, and a worker has no socket to ask with. | CAP-8, LOOP-5 | `agentosd` `workerTools`. |
| K9 | How many forks fit (CAP-1's measured N) is `worker_fit`, K16; admission still refuses what does not fit. | CAP-1 | K16. |
| K10 | Idle workers do not hold memory (UX-146-1): every minute the broker **parks** (checkpoints, memory included, then stops and releases admission) each running worker that no tool has named for an hour, and every worker whose lineage has no running machine other than workers (its creator stopped, slept or was preempted). The parking checkpoint is the worker's newest snapshot; `worker_list` shows it stopped with that snapshot, and `worker_rollback` to it revives the worker as it was. After a broker restart the hour starts afresh. A worker busy with a command is in use: Reap skips it and `Park` refuses it at once (`ErrBusy`) rather than wait. | RES-1, RES-2, CAP-8 | `Tools.Reap`, `vm.Manager.Park`. |
| K11 | Erasure never waits behind a command (security F1 on #146): `ForgetSince`, `Rollback` and `Destroy` take a machine's lock by ending any worker command that holds or takes it meanwhile, so a 10-minute command delays them by milliseconds. The guest sees the command end with an error. | CAP-3, CAP-8 | `vm` `lockEndingExec`. |
| K12 | Ending a command ends it inside the sandbox (L3 MUST-1 on #146): on timeout or cancel, gVisor kills the host `runsc exec` and, by the in-sandbox pid it wrote (`--internal-pid-file`), the command itself (`runsc kill --pid … KILL`, logged on failure, never waited on). `runsc exec` passes its stdio into the sandbox, so a command's children could hold the pipes open; `WaitDelay` (3 s) bounds the wait for them. Above that, `vm.Manager.Exec` stops waiting for a runtime that ignores cancellation `ExecGrace` (15 s) past the timeout, so erasure waits at most that long. A command's own children that escape the kill end with the worker: rollback, erasure and destroy restart or stop it. | CAP-3, RES-1, CAP-8 | `gvisor.Runtime.Exec`, `vm` `awaitExec`. |
| K13 | No goal stamp on workers (P3-7 C3 does not apply): C3 assumed workers would sit outside the creator's lineage and so need its goal carried over. Here a worker joins its creator's lineage (K2) and has no broker socket (K1), so it makes no effect requests and no model calls, the only things a goal ID is stamped on (guest G14). The worker tools are broker state, not intents (K8), so the creator's own requests carry the goal and nothing from a worker can go unattributed. If workers ever get a socket or make model calls, they must take their creator's goal then. | OP-1, OP-7, OP-8 | P3-7 binding (C3); guest G14. |
| K14 | While the owner's STOP holds, no worker command starts, and commands in flight are ended (security R2 on #146). STOP is checked when a command asks and again under the worker's lock once the command can be ended (`Command.Hold`), so one queued behind another cannot start after STOP (L3 MUST-2 on #150). The broker's tick ends commands in flight every 5 s; the command itself then stops within gVisor's 3 s `WaitDelay`, and at worst `ExecGrace` (15 s) later the broker stops waiting for it, so a command outlives STOP by at most about 23 s. Workers keep running and keep their files; snapshots, rollback and destroy still work, since nothing leaves the box. | OP-6, CH-11, CAP-8 | `Tools.Stopped`, `Command.Hold`, `vm.Manager.EndCommands`. |
| K15 | One worker's files may hold at most `-worker-layer-mb` (default 4096 MiB); over it the worker takes no command and no snapshot, so the ways back are `worker_delete` (K20), a rollback to an earlier snapshot, or destroy, inside the disk's RES-4 reserve (security R3 on #146). The refusal (`vm.WorkerFull`) names those ways out (UX-150-1). Reap still parks a full worker: it is stopped without a checkpoint and revives by rollback (L3 MUST-1 on #150). The check walks the layer before each command, skipping files that vanish mid-walk (L3 MUST-3 on #150); its cost is bounded by the layer's inode cap, and caching it is a later optimisation. The way to shrink a full worker in place is `worker_delete` (K20). | RES-4, CAP-8 | `vm.Config.WorkerLayerBytes`, `overlay.Measure`. |
| K16 | **How many fit (CAP-1).** `worker_fit` answers how many more workers of a size the caller can start now: the smaller of measured free memory (`MemAvailable` less admission's headroom) and admission's declared room for the workers' class (K3; a fork is sized for its source worker's class) (free budget, plus running experiments a higher class may preempt; under memory pressure none for experiments, `admission.RoomFor`), capped by what the lineage's 16-worker limit leaves (a worker still being made counts once). If memory cannot be measured, the declared budget alone is used and the answer says so. **What it reveals (security F1 on #158):** free memory tracks the owner's activity and other labels' machines, so the answer carries no memory figure, the room is rounded down to 512 MiB (`FitStepMB`) before use, and one lineage's rounded room for a class is reused for 10 s (`FitFor`; a lineage's workers share one class, so in practice one figure): asking with many sizes inside the window learns one coarse figure, no finer. The rounding costs up to one step of forks. On the floor host (pool 3496 MiB beside a 1552 MiB agent) admission takes 7 workers of the default 256 MiB (`worker_fit`'s rounding reports 6) and 8 at 192 MiB, which a guest asks for when it wants 8. **Smaller fits more (potency on #158):** the default stays 256 MiB, and when a size above 192 MiB (`SmallMemMB`) fits fewer than 192 MiB would, the answer says how many fit at 192 MiB, counted from the same rounded, cached room, so it reveals nothing finer; `worker_create`'s description gives the floor's 7 and 8. At the floor it may be 0, and the answer says to work sequentially in one worker. It is advice: each start is still admitted on its own, so a race between asking and forking ends in admission's refusal, never an overcommit. `worker_fork` with `up_to_fit` forks only that many, in the order named, and lists the rest as skipped. | CAP-1, RES-2, REV-5 | `Tools.fit`, `Tools.room`, `admission.RoomFor`, agentosd `measuredFree`. |
| K17 | **Keep the winner (CAP-1).** `worker_keep` destroys every other worker of the caller's lineage forked from the same snapshot as the named one (`ForkBase`), never the source or other workers. A worker that is not a fork is refused, and so is a keep while any of the lineage's workers is still starting (it has no fork base yet, so it would be missed). It reads lineage and fork base from the machine table alone (`vm.Manager.ForkSiblings`; `ForkBase` is written under the table lock too) and destroys through `Destroy`, which ends commands, so a busy winner, sibling or other worker never holds it up; `worker_destroy` resolves its worker the same way (L3 MUST-1 on #158, K11). The pending check and the sibling read share the lock that reserves new workers. A sibling already gone is skipped; if a destroy fails part way, the error names the siblings already destroyed. Erasure that resets a fork clears its `ForkBase`, so it then counts as unforked. | CAP-1, A15 | `Tools.keep`. |
| K18 | **Frontier spend per fork is zero for workers (CAP-1).** CAP-1 reserves frontier spend per fork. A worker has no broker socket and makes no model calls (K1, K13), so a worker fork reserves none; the guest driving them spends on its own reservation. A fork that held an agent runtime would need its own reservation, and the worker tools cannot make one. | CAP-1, OP-8 | `vm.Fork` (workers fork only into workers, K7). |
| K19 | **Preempted is not failed (CAP-1, potency R1 on #158).** Preempting a worker ends its command in flight at once, and the command reports `vm.ErrPreempted`, never an exit code; the guest sees "preempted, retry: … the command has no result (it did not fail)" with the way back (roll back to a snapshot, or destroy and recreate it, and run it again), so a speculative branch cut short is not read as a failing test and the wrong winner kept. A command on a worker already preempted says the same. | CAP-1, RES-1 | `vm.Manager.Exec`, `vm.Manager.Preempt`, `Tools.run`. |
| K20 | **Delete without running the worker's code (CAP-8c, security ruling R-DEL1 to R-DEL7).** `worker_delete` takes up to 64 absolute guest paths and `recursive`; it is the one change a worker over its layer cap takes. Under the worker's lock, with Exec's label rule (a public caller cannot touch a private worker; a private one raises a public worker) and STOP hold, the broker stops the worker and removes the paths from its upper directory itself (`overlay.Delete`): from a handle on the directory, one component at a time with `O_NOFOLLOW`, refusing a symlinked parent (`symlink_in_path`) and any mount point, by the mount table (which also lists same-file-system bind mounts) backed by a device check (`mount_point`); entries go with `unlinkat`, so a symlink is removed itself; the path is resolved, and the layer it shows from decided, through handles alone, so the cost grows with its depth only and a path past the host's PATH_MAX still resolves (L3 on #166); the walk is relative to directory handles and removes at most 100,000 entries or runs 10 s per call (`more_remains`: ask again; the time limit applies only once the call has removed something, so asking again always ends; security F2, L3 on #166) and descends at most 256 directories below the path asked, holding one handle per level (`too_deep`: delete a deeper path first, or roll the worker back or destroy it; L3 MUST-1). A name the kernel finds too long is `bad_path`. A path that fails part way is `delete_failed`; any other failure answers one fixed text (the deletion could not finish; try again, or roll back or destroy it), the detail going only to the broker's log, so no host path or errno reaches the guest (L3 S1, security F3). STOP and the label rule are checked before a running command is ended, so a refused deletion ends nothing (L3 SHOULD-2). A layer the host cannot measure (deeper than its PATH_MAX) still fails the measurement after a deletion; a handle-based measure is carried to SR2-3i. This is openat2's `RESOLVE_IN_ROOT`, `NO_SYMLINKS`, `NO_MAGICLINKS` and `NO_XDEV` done with the standard library, since ARC-2 keeps `unsafe` and third-party code out of the machine plane; empty directories go through `/proc/self/fd/N/name`, as the standard library has no `unlinkat(AT_REMOVEDIR)`. Nothing is created in the layer, so a path only in the base image is refused (`base_image`) and removing an upper copy can bring the base version back (`removed_base_back`). The answer holds a code per path asked and counts (entries removed, bytes freed, still over the cap, state), never other names; worker operations are not journaled (K8). The layer is then measured again: under the cap the worker starts again on the same layer, spec and label (a worker that was already stopped is admitted afresh, so a full parked worker revives this way too; a preempted one waits for its own resume, security R2 on #166); over it, or if STOP arrived meanwhile (security F1 on #166), it stays stopped with its memory released and the deletion stands. The tool says it stops the worker, ending its background processes (security R1 on #166). Rollback stays allowed over the cap: it replaces the layer with a snapshot taken under the cap, and it is K15's other way out. While STOP holds, `worker_create`, `worker_fork` and `worker_rollback` are refused too (security R1 on #150). | CAP-8, RES-4, REV-5, OP-6 | `overlay.Delete`, `vm.Manager.DeleteFiles`, `Tools.del`. |
