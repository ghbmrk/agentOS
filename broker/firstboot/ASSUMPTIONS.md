# First-boot update before trust: assumptions

Built for UPD-b (BOARD.md) against SPEC UPD-3 (and UPD-8 for drive installs), on the update verifier (`broker/update`) and the applier (`broker/apply`, UPD-a). Covers `broker/firstboot` and the `localui` offline wording. Each row is a reading of the spec, with what changes if the reading is wrong.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| F1 | **Bypasses Loop 3 and the change pipeline.** At first boot there is no owner to approve, no tasks to soak and no held-out cases to evaluate. Waiting for them would leave the box on the shipped image while setup asks for credentials. So the gate checks the mirrors itself and hands the release to `apply.ScheduleFirstBoot`. That call is due at once (no jitter, but still the free-moment rules) and has no adoption: after the restart, `Resume` commits or drops the release in the update store only. TUF verification, rollback floors, threshold floors and the A/B fallback are the same as for every other update. | UPD-3, UPD-1 | If the spec wants the pipeline's evaluation even at first boot, the gate waits for Loop 3's adoption instead. |
| F2 | **Stable only.** The gate always checks `update.ChannelStable`, whatever channel the owner later picks (UPD-c): no owner has picked anything at first boot. | UPD-3 ("latest stable") | — |
| F3 | **When the gate opens.** Only after an online check that verifies (signatures, thresholds, rollback and expiry, so a frozen or replayed mirror fails) finds nothing newer on stable than the installed release, and the installed release's freshness is not pending or failed (a drive install, UPD-8). A scheduled or in-flight release, an unreachable mirror, a check that fails verification, or a release that fell back all keep it held. Mirrors are tried in order; the first verified answer counts. | UPD-3, UPD-8 | — |
| F4 | **Fallback.** A first-boot release that fell back is recorded by the applier (`FellBack`) and never scheduled again. The gate stays held, saying so, until a newer release is out. This favours the invariant (credentials never touch an outdated image) over setup finishing. The owner has no override yet: see the Findings line (release). | UPD-3, UPD-1 | An owner override (accept the shipped image) would be a new row with a security review. |
| F5 | **Sticky trust.** Once open, the gate never closes: a restart, going offline or a newer release later is Loop 3's business (UPD-5). The latch is the only state kept across restarts. If the state file is lost, the gate runs one more check, which only delays setup. | UPD-3 | — |
| F6 | **Offline.** Offline, no mirror is contacted. The box runs the shipped image, and STATUS and the local page say so ("offline (setup can continue)"; the AI step names the shipped version and says it opens once online and updated). The other setup steps continue. | UPD-3 | — |
| F7 | **Not wired.** `agentosd` does not build a gate yet (queued row UPD-b2). Wiring conditions: `Step` runs at start and on each uplink change or every few minutes until `Trusted`. Loop 3 and `Schedule` start only once the gate is open, so `ScheduleFirstBoot` is called only by the gate, before the latch. Every path that connects an AI provider or personal account (local page, owner channel, CLI) calls `Hold()` first and refuses with its text. `Status()` is a STATUS note while held. `localui.Hooks.Progress` maps from `Progress()`, with `Online` from the uplink. The applier's `Resume` runs before the first `Step`. **Clock (L3 on #379, point 1):** a first-boot box has never synced time, and online expiry trusts `Now` (update U4), so a clock near the image build date lets a frozen mirror's metadata pass and would open the gate on an outdated image. `Now` must come from the HOST-1b clock guard's `Latest` (as update WF2 does), and `Step` stays held until the guard reports a synced time; this needs a fallible clock in `Config` (`ClockReady func() bool` or `Now func() (time.Time, error)`) so the gate fails closed. **Acceptance (L3 point 2):** UPD-b2 carries a test that no AI or account connect path skips `Hold()`. | UPD-3, UPD-8 | Security session re-checks the clock condition. |
| F8 | **Image side.** Real activation is the P2-1 activator (systemd-sysupdate and bootctl behind `apply.Activator`, per LATER.md's reuse table). The preloaded image must carry the root metadata (`InitStore`) and the mirror list. Queued as UPD-b3 on P2-1. | UPD-3, UPD-1a | — |
| F9 | **Wording only (L3 on #379, points 3-5).** An unexpected scheduling error reads "could not be started", not "updating"; failures from several mirrors read as mixed when one answer failed verification and another was unreachable; in `fell_back`, `Hold()` and `Status()` say the same wait. The gate's open/held outcomes and returned errors do not change. Every message is pinned in a test and follows CH-21 (first person). | UPD-3, CH-21 | — |
| F10 | **Card step (CTRL-card).** `CardStep` keeps one latch (`card_confirmed`) and nothing else. Until it is set, every start generates a new card from the box's randomness: an unconfirmed card was never provisioned, so it unlocks nothing and is safe to drop. On the confirm, `Provision` runs, then the latch is saved, then the display is erased; if either fails the display stays and `Hold` stays held, and the owner retries with the same card, so `Provision` must accept a retry with the same card. A restart between provisioning and the latch makes a new card while a vault from the old one exists: the start then runs `ResetUnlatched` before `NewCardStep`, which calls the provisioner's reset unless the latch says confirmed; an unreadable latch stops the start and resets nothing (CTRL-card-wire). The vault process's reset then makes a fresh setup vault and opens it (CTRL-setup-open, broker/egress K22), so the new card's step 3 and provision can run; the card's provision is refused (412) and setup's finish sends the owner back to step 3, since the remade vault holds no confirmed code generator; the card step routes the owner to step 3 on that refusal and on the reset's `remade:true` (#1115). | HW-1, ONB step 4 | — |
| F11 | **What "no card text on disk" covers.** The acceptance test scans the whole partition (state, journal, process logs, vault files) for the passphrase, recovery key, setup secret and code, Wi-Fi password and grid seed in every encoding the A8 scanner knows. The vault holds the Wi-Fi password and setup secret encrypted (recovery.Provision), never the passphrase or recovery key. On a real box hostapd's file holds the Wi-Fi password root-only (ARC-1): that one file is the stated exception. | HW-1, ARC-1, CRED-8 | — |
| F12 | **Wired (CTRL-card-wire).** agentosd's setup mode, after the record and owner-state checks (so an owned box never resets), starts the step it is handed (`setupMode.Card`) and its `setup_finish` op answers `card pending` while `Hold()` holds. agentosd imports neither this package nor `card` (ARC-2: `card` serves its page over `net/http`), so whoever builds the step runs `ResetUnlatched` and `NewCardStep` where the page runs; agentosd's tests do so in-process. localui's setup page shows an Owner Card step after approval codes and mounts the display at `/setup/card` behind the Host, claim and pairing checks; its recovery sheet and finish path refuse while `Hold()` holds. Remaining gaps, release findings on the PR: the vault process's provision and reset ops exist (CTRL-card-vaultop, broker/egress K21) but nothing calls them yet (#1115), so agentosd's `main` hands setup mode no step and setup mode refuses to start (the image always passes `-owner`); the display crosses `localui.sock` once agentos-localui serves setup (P2-2w c4). | HW-1, ONB-3, ONB-7 | — |
| F13 | **Card step waits for the claim (CTRL-claim).** On a preloaded box `ClaimedCard` builds the `CardStep` only once `broker/claim` reports the box claimed, so no card randomness is drawn and nothing card-shaped is written before the claim; `Hold` says the box waits to be claimed. A claim whose card step then fails to start keeps the claim and returns the claimant token with the error, and the next start builds the step. See `broker/claim/ASSUMPTIONS.md` K5. | HW-10, HW-1 | — |
| F14 | **How claim wiring slots in (CTRL-claim-wire).** `Begin` keeps `ResetUnlatched` first and builds `NewClaimedCard` in place of `NewCardStep` on a sealed box; the page and the finish op take any value with `Display()` and `Hold()` (`localui.OwnerCard`), and `ClaimedCard.Display()` returns its card step's display, nil before the claim. | HW-10, HW-1 | — |
| F15 | **First boot routes the box (CTRL-claim-wire, R2 and R4).** `Begin` reads the latch first (an unreadable one stops the start and resets nothing), then opens the claim. Claim state present: it saves `preloaded: true` on the latch before anything is shown (a failed save stops the start), runs `ResetUnlatched` and returns `RouteClaim` with `ClaimedCard`. No claim state and no `preloaded` marker: `RouteDownload`, the card step at once (HW-10 acceptance 1 unchanged). No claim state but the marker: `RouteReinstall`, whose claim reports "claimed" with `Reinstall` set (so every setup page says only "already claimed, reinstall me", never "setup continues on the phone that claimed me"), refuses every code and has no claimant, and whose card shows nothing and holds with "reinstall me", so no phone sets up or pairs and the vault is never reset. The card confirm keeps the marker. The brief says "first-boot or card state"; this rests on the marker alone, since a download box also has `card_confirmed` and would otherwise be told to reinstall after any restart. Residual: a disk that loses both `claim.json` and the latch looks like a bare install; both are on the same partition, and losing the latch also loses `card_confirmed`, so the vault is reset first (F10) and nothing from the old owner is reachable. | HW-10 acceptance 1, HW-1 | If another file marks a box as preloaded, `Begin` reads it too. |
| F16 | **Setup network until the confirm (CTRL-claim-ap).** `Begin` reads `BoxConfig.SetupNet` (the seller's file, claim K10) after the latch. `Network()` is what the access point loader asks for the Wi-Fi to serve: the setup network while the card holds (before the claim, and after it until the confirm), then nothing; on the first ask after the confirm it burns the file (`Save(nil)`, an empty file through the store's durable rename) and a failed burn is an error, so the loader keeps the radio down rather than serve a network the owner no longer controls. Safer choices where the spec is silent, noted on the PR: it retires at the confirm, not at setup end, since the card network then exists and the sticker password is on the outside of the box; a confirmed box burns any setup file at `Begin` and a failed burn stops the start; a setup file without claim state routes to reinstall, not the download path (it marks a sealed box as surely as `preloaded`); and a setup file that does not parse or cannot be read stops the start. On the reinstall route the card never confirms, so the setup network stays up and the phone can still reach the "reinstall me" page. Residual: the burn rewrites the file but an SSD may keep the old blocks; the password then reaches only a network the box no longer serves. The loader (P2-1, `agentos-ap`) reads the network through `SetupNetwork`, which reads the latch and the owner state and burns the same way; while it serves, it asks again every few seconds, and at the confirm (or once the box is owned) it brings the live access point down before the burn, then brings it up with the card's network, which the page reported before the confirm latched (#1185, apnet N1), and serves that network at every later start, on an owned box too. The card's page tells the phone, before the confirm, to rejoin with the card's Wi-Fi QR code. `CardConfirmed` reads the same latch for the loader; a latch the page forges serves only the network the page reported (apnet N3). | HW-10, HW-1, CH-7, A1 | If the loader reads the network another way, it must still call `Network()` so the burn happens. |
| F17 | **The download route is opt-in (#1270, CTRL-card-sock s1).** A box without a claim state takes `RouteDownload` only when `BoxConfig.Download` is set, which agentos-localui sets from `-download-box`; unset, it routes to reinstall, so a preloaded box whose claim state is lost, unreadable to the page, or not yet moved into the page's state directory is told to reinstall rather than served setup without the claim gate. The shipped unit does not pass the flag (its test pins that): no download image is built yet, so on today's images the download route is unreachable, the safe side. The page also decides once, before `localui.New`, whether setup is open: agentosd's answer to `setup_progress`, open on an answer and closed on a refusal, asked again on any other error until `agentosdWait` passes, then the page exits for its unit to restart it; a closed decision wraps the hooks so `AlreadySetUp` stays true, and New's own re-ask (`adopt`) can then only close setup, never open it without the first boot (Security S-R3). | HW-10 acceptance 1, HW-1 | A download image must pass `-download-box`; its unit test then pins the flag on that image only. |
| F18 | **The card step reruns under a confirmed latch (#1330).** `FirstBoot.Again` (on the claim route only once claimed; the reinstall route answers its hold) makes the hold refuse at once, runs the vault reset (a no-op on a vault remade empty) and shows a new card whose confirm provisions and latches as before. The disk latch stays confirmed meanwhile: agentos-ap reads it (`CardConfirmed`) to serve the card's network, and the setup network was burned at the first confirm (F16), so clearing it would leave the box with no Wi-Fi for the phone that must see the new card. A restart before the new confirm finds the latch confirmed, finishes, is refused `card pending` again and reruns again. Each rerun moves a generation on, so a confirm of a card shown before it is refused and latches nothing. A failed reset (or a new card that cannot be made) shows no card and keeps the hold, and the finish path stops at that hold, so it never reruns; `RetryRerun` reruns it with the same reset, and the setup page calls it on each page load by the paired phone, which the page sends back to the card step with a message to reload (#2362). Nothing waits for a restart. | HW-1, F10 | If agentos-ap stops reading the latch, the rerun may clear it on disk. |
