# photo: assumptions

What the photo client (`Decode`, CH-23) rests on.

- **P-1. 512 MiB covers the costliest accepted file.** Measured with the decoder's own peak: a 50-megapixel baseline JPEG at 134 MiB, a 50-megapixel 16-bit RGBA PNG at 432 MiB. `MemBytes` is 512 MiB and is the cgroup cap of the whole sandbox, which adds about 18 MiB of its own (gvisor V-photo-1); a progressive or CMYK 50-megapixel JPEG can need 750 to 950 MiB and is refused as `decode` until CH-photo-b revisits the cap; agentos-photo sets Go's soft limit to 448 MiB so the collector works before the cap. A file that needs more is refused as `decode`, not taken.
- **P-2. 80 MiB holds any output.** The re-encoded image is at most 4096 pixels a side; a PNG of noise at that size is about 64 MiB, the thumbnail well under 1 MiB. `MaxOutput` is 80 MiB; a truncated frame is refused as `decode`.
- **P-3. The frame's dimensions are read from the bytes.** The client trusts no field of the header line: it reads each part's width and height from the PNG IHDR or the JPEG SOFn and compares. A decoder that lies is refused (`TestDecodeRejectsLyingHeader`).
- **P-4. A hostile decoder can at most refuse or return a well-formed image.** It runs with no network, a read-only root, no broker state, a memory cap and a deadline (ARC-5); what it returns is a JPEG or PNG within the limits, which downstream code treats as untrusted bytes.

What the HEIC path (CH-photo-heic, #3115) rests on.

- **CH-photo-heic-1. A HEIC run has its own memory cap, so no depth is guessed.** `gen2brain/h265` decodes a HEIC above 8 bits to 16-bit RGBA, and takes the depth from the coded stream, not from any box a check before decoding could read; so every HEIC is held to the same 50 MP as any photo, and its run is given room for the costliest one. The broker caps any ISOBMFF file's run at `HEICMemBytes`, 960 MiB, and agentos-photo sets Go's soft limit to 832 MiB when the file's first 4 KiB name an HEVC brand (P-1's caps and 448 MiB otherwise). Measured on the built binary at 8160x6120 (49.9 MP), peak resident set: cost grows with the coded size, and the costliest case is a high-entropy HEIC above 8 bits, 4:4:4, with an alpha item. At 17.9 MB (under `MaxInput`) it peaks at 819 to 831 MiB; built with `MaxInput` raised so files past 20 MiB decode, 22.5 MB and 26.3 MB files peak at 828 to 841 MiB under either a 768 or an 832 MiB soft limit, since about 745 MiB is live at once and the soft limit cannot hold it (#3124 L3 6400119599). So the worst accepted file stays under about 841 MiB, 859 MiB with the sandbox's own 18 MiB (gvisor V-photo-1), about 100 MiB under the cap. Low-entropy files cost less: 4:4:4 with alpha about 781 MiB, without alpha 673 to 750 MiB, 10-bit 4:2:0 620 to 746 MiB, the higher figures under the higher soft limit. A decode uses at most four goroutines (`heicThreads`), so a wider host decodes no more tiles at once (the same peak at `GOMAXPROCS` 1 and 32). A file that needs more is OOM-killed and refused as `decode`. A file with a top-level `moov` (a picture sequence, which h265 decodes frame by frame when no primary item is usable), or whose top-level boxes do not frame as h265 frames them, is refused before decoding. Decided by Mark (option B on #3124's limit card, 2026-10-25), replacing a 24 MP cap for HEICs above 8 bits whose pre-decode depth check four review rounds bypassed.
- **CH-photo-heic-2. The decoder clamps to the declared size and the frame limit holds the rest.** h265 trims a decoded picture to its `ispe`, and `FrameSizeLimit` (the declared pixels plus one 64-sample coding tree block of padding each way) refuses coded frames larger than the declaration, so a file whose `ispe` lies small fails as `decode` instead of allocating (`TestDecodeHEICOver50MPRefused`). A grid's tiles are bounded by their own size (CH-photo-heic-5). The decoder's own size check after decoding (fits the declaration either way up) is a backstop no test reaches while h265 clamps.
- **CH-photo-heic-3. A HEIC's EXIF orientation is never applied.** The transforms are its `clap`, `irot` and `imir` properties, which h265 applies (`AutoRotate`); HEIF readers ignore the EXIF tag, as the format says. A file whose maker wrote both will not be turned twice.
- **CH-photo-heic-4. The broker sends any ISOBMFF file to the sandbox.** Its pre-check is only `ftyp` at offset 4; the decoder decides which brands are a HEIC (an HEVC brand as major or compatible) and refuses the rest, such as AVIF, as `type`. That costs one sandbox run per non-HEIC ISOBMFF file and keeps the brand list in one place.
- **CH-photo-heic-5. A grid's tiles and an item's later pictures stay within the declared size (#3131).** `broker/go.mod` replaces h265 v0.2.3 with `broker/third_party/h265`, upstream with three edits (its PATCH.md). Each tile of a `grid` decodes under a frame limit of the one size every tile's `ispe` names, plus one 64-sample coding tree block each way, instead of the whole image's; tiles must name one size that covers the output with no row or column of tiles wholly past it, and only as many tiles decode at once as fit the image's own limit together. An item that codes many pictures keeps the first and releases each later one as it comes out. Before, a declared 3456x3456 2x2 grid whose tiles each coded the whole 3456x3456 was accepted at 237 MiB peak; it is now refused as `decode` at 10 MiB (`TestDecodeHEICGridTilesBoundedByCell`), and 64 pictures in one 1024x1024 item took 119 MiB of heap and now stay under 48 MiB (`TestDecodeHEICItemOfManyPicturesHoldsOne`). Tiles overhanging the output so that two would not fit the limit together decode one at a time (`TestDecodeHEICGridTilesShareTheLimit`), and a tile naming no ispe or another size than the rest is refused (`TestDecodeHEICGridTilesNameOneSize`). Honest files decode as before: 512-sample tiles keep four at once, and the 17.9 MB 12-bit 4:4:4 grid with alpha of CH-photo-heic-1 peaks at 825 to 826 MiB, as on main (825 to 831). Rests on: real encoders (Apple's 512-sample tiles, h265's own `Tile`) give every tile one `ispe` and lay out `ceil(size/tile)` tiles, so no tile row or column falls wholly past the output. If wrong: such a file is refused as `decode`.
