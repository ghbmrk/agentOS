# photo: assumptions

What the photo client (`Decode`, CH-23) rests on.

- **P-1. 512 MiB covers the costliest accepted file.** Measured with the decoder's own peak: a 50-megapixel baseline JPEG at 134 MiB, a 50-megapixel 16-bit RGBA PNG at 432 MiB. `MemBytes` is 512 MiB and is the cgroup cap of the whole sandbox, which adds about 18 MiB of its own (gvisor V-photo-1); a progressive or CMYK 50-megapixel JPEG can need 750 to 950 MiB and is refused as `decode` until CH-photo-b revisits the cap; agentos-photo sets Go's soft limit to 448 MiB so the collector works before the cap. A file that needs more is refused as `decode`, not taken.
- **P-2. 80 MiB holds any output.** The re-encoded image is at most 4096 pixels a side; a PNG of noise at that size is about 64 MiB, the thumbnail well under 1 MiB. `MaxOutput` is 80 MiB; a truncated frame is refused as `decode`.
- **P-3. The frame's dimensions are read from the bytes.** The client trusts no field of the header line: it reads each part's width and height from the PNG IHDR or the JPEG SOFn and compares. A decoder that lies is refused (`TestDecodeRejectsLyingHeader`).
- **P-4. A hostile decoder can at most refuse or return a well-formed image.** It runs with no network, a read-only root, no broker state, a memory cap and a deadline (ARC-5); what it returns is a JPEG or PNG within the limits, which downstream code treats as untrusted bytes.

What the photo store (`keep.Store`, CH-photo-b) rests on.

- **P-5. A receipt is a plain journal intent, kind `photo.keep.`, capped in the store.** The brief asked for a registered `journal.Lifecycle` (the brief's fallback is plain records with the cap in the store). `journal.Register`, `Lifecycle.Check` and `Lifecycle.DailyCount` are not opened in `broker/core/core.txt`, so a non-core package may not call them (core `TestNoWritePathOutsideTheCore`), and the irreversible kind gains nothing from registration (only `UndoPlan` reads the registry). The store counts receipts itself from `ReadTrail` with `DailyCount`'s rule: a receipt counts on the box's day of its first dispatch unless every attempt is known not applied, 200 a day per box. A deleted or delivered photo still counts, so deleting frees no place that day. Delivery (`photo.deliver`) and deletion (`photo.delete`) are other actions and do not count.
- **P-6. The listing is a fold of the journal.** No index file exists beside the journal (OP-11); the bytes are content named by hash in `Dir`, and `Open` removes any file no live photo or unsettled receipt names.
- **P-7. The image's rename is the commit.** The thumbnail is renamed first, then the image; a crash before the image lands is reconciled as not applied and the thumbnail removed unless another photo holds the same hash.
- **P-8. Expiry is fixed at receipt.** It is the received time plus the owner's days setting read then; changing the setting later does not move a kept photo's expiry. The received time is the later of the box clock and the clock guard's latest reading, which the guard floors even while unverified, so a box clock behind never fixes an expiry already passed; a box clock ahead can only keep a photo longer.
- **P-9. Nothing expires on an untrusted clock.** The sweep reads the clock's earliest bound, and only when it is verified and not restricted, so no photo goes early (CH-26).
- **P-10. Same bytes are kept once.** Two photos with the same image share one file; a deletion removes the bytes only when no other live photo or unsettled receipt names the hash (decided when the delete runs or is reconciled, from the journal then, never from a value fixed at submit).
- **P-11. Hashes survive the journal's redactor.** A 64-hex-digit SHA-256 is assumed not to match a secret pattern; if a redactor ever scrubbed it, the store could not find a photo's bytes and would list it as corrupt, never serve other bytes.
- **P-12. Photo IDs are never reused.** The next ID is one past the highest ever submitted, erased ones included, since erasure keeps intent IDs.
- **P-13. One stuck deletion holds no other.** The expiry sweep and delete-all try every photo and return the failures together; a sweep also finishes deletions that stopped part way (bytes gone, recall or erase not done). A denied delete is retried: each attempt is its own intent, `photo:delete:P<n>` then `photo:delete:P<n>:<k>`, and the next owner delete or sweep after a denial (at authorization or the dispatch recheck, of a photo expired or not) submits the next one; an attempt pending, authorized, in flight or done is carried on. The view folds every attempt into its photo and the erase covers them all (CH-photo-f, #2320).
- **P-14. The store is its own package, `photo/keep`.** The daemon's ARC-2 test classes `photo` as the decoder client, allowed to import only `vm/gvisor`; the store needs `journal`, `clock` and `recall`, so it sits in `broker/photo/keep` and imports `photo` for the `Photo` type. `durable/stores.txt` lists `photo/keep content`.

What the HEIC path (CH-photo-heic, #3115) rests on.

- **CH-photo-heic-1. A HEIC above 8 bits is capped at 24 MP.** `gen2brain/h265` decodes it to 16-bit RGBA, so its peak live heap is about 10.7 bytes a pixel: 256 MB at 24 MP (6000x4000, 10-bit), against 271 MB for a 50 MP 8-bit HEIC and P-1's 432 MiB PNG; a 50 MP 10-bit file needed 533 MB, past `MemBytes`. So `MaxDeepPixels` refuses it as `pixels` before any decode. The depth is read from every `hvcC` box anywhere in the file, found by its type and size rather than by walking `meta`, so a grid's tiles and an alpha plane count (a grid item has no `hvcC` of its own) and no arrangement of `ipco` boxes hides one; a false match only lowers the limit. A decode that yields 16-bit samples under an 8-bit declaration is refused as `decode`. A file with a top-level `moov` (a picture sequence, which h265 decodes frame by frame when no primary item is usable), or whose top-level boxes do not frame as h265 frames them, is refused before decoding. Measured with `GODEBUG=gctrace=1` on `agentos-photo` with its 448 MiB soft limit; a 50 MP 8-bit file took about 2 s on four cores.
- **CH-photo-heic-2. The decoder clamps to the declared size and the frame limit holds the rest.** h265 trims a decoded picture to its `ispe`, and `FrameSizeLimit` (the declared pixels plus one 64-sample coding tree block of padding each way) refuses coded frames larger than the declaration, so a file whose `ispe` lies small fails as `decode` instead of allocating (`TestDecodeHEICOver50MPRefused`). The decoder's own size check after decoding (fits the declaration either way up) is a backstop no test reaches while h265 clamps.
- **CH-photo-heic-3. A HEIC's EXIF orientation is never applied.** The transforms are its `clap`, `irot` and `imir` properties, which h265 applies (`AutoRotate`); HEIF readers ignore the EXIF tag, as the format says. A file whose maker wrote both will not be turned twice.
- **CH-photo-heic-4. The broker sends any ISOBMFF file to the sandbox.** Its pre-check is only `ftyp` at offset 4; the decoder decides which brands are a HEIC (an HEVC brand as major or compatible) and refuses the rest, such as AVIF, as `type`. That costs one sandbox run per non-HEIC ISOBMFF file and keeps the brand list in one place.
