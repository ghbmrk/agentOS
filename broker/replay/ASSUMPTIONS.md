# Replay evaluator: assumptions

Built for the change pipeline's `Evaluator` (P3-1, `broker/change`
ASSUMPTIONS C5) on the VM lifecycle (P1-4) and the guest plane (P1-7).
Each row is a reading of the spec, or a gap left for a later package, that
a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| R1 | A replay runs in a fresh experiment-class machine from the guest image, labelled private, seeded with the tree under evaluation, not in a fork of the live guest. Both sides of a comparison start from the same state, and the live guest's memory never enters an evaluation. The machine is destroyed when the run ends. It takes no per-step snapshots. | LOOP-5, RES-1, REV-5 | Fork a warm template checkpoint per image when cold starts are too slow (S3: 2-4.5 s against 56 s). |
| R2 | Model access stays off until three conditions from the #37 review hold: K1, the handler is a router whose grants, data labels (`Label=private`), source-machine grants, and per-call PrivateOK check come from broker configuration; only the order among those granted routes (the routing rule) comes from the tree under test, which is the candidate being measured; with refusal tests for a private case to a provider not marked PrivateOK and for an ungranted provider. K2, a dedicated evaluation `Meter` with its own overall cap (the evaluation budget), not the guests' meter (keyed per random `eval-` ID it would give each run a fresh machine cap), plus the digest line "Self-tests: N model calls". K3, the builder cannot read evaluation model-call records (the replay plane already has its own `Dir`). Live model calls on a separate capped evaluation budget are Mark's decision (2026-10-05), recorded in SPEC LOOP-5 by this PR. Until K1-K3 hold, `Model` is nil, replay is fully offline, model calls answer 503, and a tree that changes `routing/` is not evaluated, since both sides would give the same output. Effects are what "recorded external responses" covers: they are replayed and fail closed. | LOOP-5, ADP-4, OP-8, CAP-9, CHG-1 | Wiring package, once K1-K3 hold. |
| R3 | An effect request is answered from the case's recorded effects: same account, action, params, and recipients (compared as JSON). Each recording answers one request (a repeated `request_id` is the same request, OP-1). The guest gets the recorded permission decision and final state; nothing reaches the journal or an executor. Any other request fails the run with `ErrUnrecorded`, even if the guest goes on to answer. Params are compared as journaled, so an effect whose params the redactor changed never matches and fails closed. | LOOP-5, OP-1, CRED-7 | — |
| R4 | The evaluator sees only a probe: an opaque ID and the input (change pipeline). Which task a probe came from is the broker's lookup: `JournalRecordings.Task` maps a probe ID to the journal intent its case was recorded on, supplied by `Pipeline.ProbeTask`. A probe with no task (a security fixture) has no recordings, so any effect it asks for fails closed. A task is the intents sharing that intent's goal ID, or, when it has none, its origin. Guest intents carry the goal ID of the owner message they serve (guest G14), so a task is one owner request; intents journaled before that, or with no attributable message, fall back to the whole guest lineage, which is broader but still has no live effect. Broker-state intents are never recordings. | LOOP-5, OP-1, CHG-1 | — |
| R5 | The guest reads the tree's `procedures/`, `skills/`, and `context/` files under `/etc/agentos/tree`. `routing/` is applied broker-side through `Config.Model`, and is not evaluated without it (R2). Authority and governance namespaces never reach a guest. A tree whose `config/`, `guest-image/`, or `host-image/` files differ from the active tree's (`Config.Active`, the pipeline's `Files`) is not run: `Run` returns `ErrNotEvaluated`, wrapping `change.ErrNotEvaluated`, which the pipeline counts as not evaluated ("Not tested on this box"), never a pass. The seeded files are root-owned 0644, but the guest runs as root inside its sandbox, so read-only modes would not bind it; the seed is a copy, and what the guest does to it is the output under test. | LOOP-5, CHG-1, CHG-3, LOOP-10 | Resolve the image and guest configuration from the tree when those classes get an adopter. |
| R6 | A run that cannot finish (admission refuses the machine, it is preempted, the guest does not answer within `Timeout`, default 10 min) is an evaluator error, which the pipeline counts as a failure on that side. A failure on the candidate side only can therefore reject a good candidate; it never adopts a bad one. | CHG-1, RES-1 | Retry once before failing. |
| R7 | Replay machines are told apart by their ID prefix `eval-` (`vm.EvalPrefix`): `Services` routes them to the replay plane and every other machine to the live plane. The machine manager keeps the prefix for replay: `Create` refuses it, and `Fork` neither forks a replay machine nor makes one. Replay machines left by an earlier broker run are destroyed when the evaluator starts, and each run's destroy is bounded (2 min). The seed is admitted against the disk budget like a layer copy (vm V24). | ARC-6, RES-4 | — |
| R8 | Not wired into `agentosd` yet: the change pipeline is not wired either. The wiring is to set `vm.Config.Services` to `replay.Services{Live: plane, Replay: evaluator}` and the pipeline's `Evaluator` to the evaluator. | — | Wiring package. |
| R9 | There is one `Evaluator` per machine manager: at start it destroys every `eval-` machine, which would include another evaluator's runs. Replay machines are never forked, rolled back, or merged (vm V24). | LOOP-5 | — |
