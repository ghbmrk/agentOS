# localsrv: assumptions

Started for ONB-private-save-fail l2 (#1623) against ONB-3 and CAP-9. Each row is a reading a later change could overturn.

| # | Assumption | Basis | If it changes |
|---|---|---|---|
| LS1 | The vault's provider list answers `EnrollClosed` only once setup's seal is written (egress K17), and only setup's own finish seals, after it found no listed provider owed an answer. So a sealed vault took no answer since the check, and finish's owed check and `privateOK` treat `EnrollClosed` as listing nothing: the answer is not owed, and finish can record after a seal whose finished record failed to save. Every other list failure, `EnrollNotOpen` included, still owes. | ONB-3, CAP-9 | If anything else can seal the vault, or a sealed vault can take answers, an owed answer could be dropped with the vault keeping an older yes; finish must then owe on `EnrollClosed` again. |
| LS2 | **Setup's device-code op relays and keeps nothing (#1264 c4e2b; ONB-3, CRED-5).** `OpSetupDeviceCode` answers only for a provider the vault lists as signing in by device code and that `SignIn.Ready` says can start now; it returns the https page, the code and the issuer name, each shape-checked, and logs none of them. A provider whose last sign-in still waits answers `ErrSignInBusy`, so the page says to wait rather than that it failed. Rate: 4 starts a minute, 90 s each. | ONB-3, CRED-5 | A provider that signs in by redirect, not code, needs another op. |
| LS3 | **The plan's sign-in after setup always takes a code (#1264; ONB-3, ONB-9, CRED-5).** `OpPlanSignIn` starts the sign-in that `PlanSignIn.Ready` says is open, for a live session, and only with a code-generator code or grid cell checked as `OpSIM` checks one (the try counts toward the socket's limit and the day's tries; an unlock proof is refused). Whoever approves the provider's code becomes the plan's login, so a stolen session alone must not be able to point the plan's work at another account. It relays the link, the code and the issuer, shape-checked as setup's are (`issued`), and logs none of them. While a sign-in it started waits (`PlanSignIn.Waiting`), it keeps the link, code and issuer in memory with the token digest of the session that last proved the owner for them (#1945): that session gets them back with no code and no start, from `OpPlanSignIn` or `OpPlanSignInReady`; another session gets them only after a good code, which moves them to it. Nothing is kept once the sign-in stops waiting, and nothing survives a restart (the runner's wait ends with agentosd too). A busy sign-in the server does not hold (setup's, or one whose link failed `issued`) answers `ErrSignInBusy`, and starts are bounded at `DeviceCodesPerMinute` a minute on the socket; both are refused before the code is checked, so no code is spent on them, and a start the provider refused as busy is not counted. One start runs at a time (`planMu`). Residual: a sign-in that a setup-mode runner starts between the busy check and the provider's start would still spend the code; after setup no other runner starts one. `OpPlanSignInReady` takes a token only. | ONB-3, ONB-9, CRED-5 | If the plan signs in by redirect, not by code, it needs another op. If more than one plan can sign in here, the op needs a provider argument and a kept code per provider. |
| LS4 | **A lock between adopt-SIM's token check and its code kills the session (#927, M14; SR3-1).** `adoptSIM` compares the lock generation `LocalSignIn` returns with the session's: a lock in between answers `ErrUnauthorized`, drops the token, and calls `AdoptSIM` zero times; the good code alone does not revive the session, as in RESUME. | CH-7, CH-19 | If a code alone could re-establish a session (a sign-in that issues a new token in the same call), adopt-SIM could then proceed on that new session; the test and this row would need the new token's generation. |
| TN-gmail-connect-LS5 | **Connecting an account needs a session and no code (#3006; §12.1 step 7, CLK-9, CLK-1, D-154).** `OpAccountBegin` and `OpAccountFinish` answer only a live session, check every field again (an account in `Config.Accounts`, a plain use ID within `MaxID`, a client ID and secret within `MaxClientField`, a paste within `MaxPasted`, no unknown field) and only then call the account's `AccountSignIn`; a failed call is `ErrFailed`, never its text. No code is asked: §12.1 step 7 makes the sign-in a tap, Google's warning and a paste, and the grant is the owner's own Google consent. `localsrv/accountsock` is the mail clerk's client: one call per connection on the proc wire, only to a peer under `-mail-uid`, answers bounded at 64 KiB. | SPEC §12.1 step 7; D-154 rule 1 | If connecting an account must take a code (as `OpPlanSignIn` does under CRED-5), add it to both ops and the Connect form. If the mail process's owner wire changes, `TestGmailSpeaksTheMailProcesssWire` fails. |
| OWN-https-LS6 | **The page authority is the kernel's; agentosd forwards certify, and certify needs no session (OWN-page-https slice a, #3153; MIG-4-recovery-f2, #3289; CH-9, HW-1).** `Config.Certify` is the kernel's certify (`kernelsock.Owner.Certify`, wrapped in `cmd/agentosd/pagecertify.go`); agentosd holds no authority, no sealer and no file for one. Empty or oversized keys refuse here, before the kernel. The kernel's refusals reach the page only as `ErrNoAuthority`, `ErrRestore` or `ErrBadArgs` (a key that is not P-256); anything else, its text included, is `ErrFailed`. `Config.Certify` nil (no `-kernel-owner`) answers `ErrNoAuthority`, logged once. `OpCertify` answers only the leaf and the authority's certificate; it takes a token from no one, since the page asks at start before any sign-in and the leaf can name only the page, for a P-256 key the page holds. A compromised page can get leaves for keys it chose, which gains it nothing it does not already have by serving the page; the socket admits only the page's uid. | CH-9, HW-1, D-186 | If any other client may reach localui.sock, certify needs a bound; `localsrv/certify.go`. |
| MIG-4-reconnect-a-LS7 | **The passkey ops exist only with agentosd's `-passkey-rp-id`, need a session, and refuse with a closed set (#2779a; KEY-4, CH-7).** `Config.Passkeys` nil leaves `OpPasskeys`, `OpPasskeyBegin`, `OpPasskeyFinish` and `OpPasskeyCutOff` unregistered (`localapi.PasskeyOps`, apart from `localapi.Ops`). Each answers only a live session; the frames are bounded again here (a point exactly 65 bytes, each assertion part 1 to `MaxPasskeyAssertion` (2 KiB), an ID 64 lowercase hex), and begins are bounded per minute (`PasskeyBeginsPerMinute`, as setup's `EnrollsPerMinute`). The owner side is given the session's token digest, never the token, and its answer passes only as one of `localapi.PasskeyCodes` or `ErrBadArgs`: any other error, its text included, is `ErrPasskeyUnavailable`. The interface is raw bytes, so localsrv links no `kernel/key`. | #2779a, KEY-4, CH-7 | — |
| TN-account-plan-LS8 | **agentosd relays the account plan from the one account clerk that prepares it (TN-account-plan slice b, #3189).** `OpAccountPlan` needs a session and names no clerk: the plan comes from the one `Config.Accounts` entry that is also an `AccountPlanner` (the mail clerk's `accountsock.Gmail`); none or two answer `ErrFailed`. The answer is bounded again before the page sees it (`planBounded`: at most `MaxPlanItems` items, plain IDs and tags, each string under `MaxPlanText`, valid UTF-8 and on one line, a reason only with no items, and only as a plain ID) and agentosd keeps nothing of it. The wiring is `pageAccounts`' as it is, so `cmd/agentosd` is unchanged. | §12.1 step 7, D-154, DEV-8 | A second clerk with a plan of its own needs the op to name the clerk. |
