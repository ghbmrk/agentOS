# Capability kernel: assumptions

Built for MIG-2 (#2525, D-139 step 2). Covers `broker/kernel`, `broker/kernel/key` and `broker/clerk`. Each row is a reading a reviewer may want to change.

| ID | Assumption | Spec basis | If it changes |
|---|---|---|---|
| MIG-2-a | **A passkey is a `key.PublicKey` naming its algorithm** (#3116). A real one is a WebAuthn ES256 credential bound to its RP ID, its P-256 point stored raw at enrolment (no CBOR); its signature over a message is the get() assertion, which verifies only if `type` is `webauthn.get`, the challenge is SHA-256 of the domain-separated message, the RP ID hash is the credential's, UP and UV are both set, and the ECDSA signature is over authenticatorData ‖ SHA-256(clientDataJSON). The client data must also name the origin `https://<RP ID>` and not be cross-origin, so the RP ID must be a host that serves only the owner page; a browser would otherwise let any subdomain of it ask for the tap. The sign count is not checked (synced passkeys report 0). A key's ID hashes its signatures, so an ES256 signature has one accepted encoding (`AssertionSig`: the assertion's JSON with its ECDSA signature in DER at low S); an authenticator's high S is turned into it before attach, and any other spelling verifies nothing, so a revoked grant cannot come back under a new ID. Ed25519 passkeys stay for the simulator's fake authenticator and tests (EVL-1); an Ed25519 key's JSON and the root, link, use, enrolment and cosign bytes it signs are unchanged, so old logs and keycheck still read them; the setup message now length-prefixes each anchor. The owner side signs in two steps: export the message (`RootMsg`, `LinkMsg`, `EnrollMsg`, `CosignMsg`, `UseMsg`, `kernel.PlanMsg`, `SetupMsg`), hand the page `Challenge(msg)`, attach what comes back. Holders (clerks, the planner, guests) stay Ed25519. The unlock handoff still carries anchors as Ed25519 keys. | KEY-4, CLK-1 | An ES256 anchor needs the handoff to carry typed keys; another algorithm is a new `Alg` case in `PublicKey.Verify`. |
| MIG-2-b | **Owner-channel authentication is outside the kernel.** `Issue`, `Revoke`, `Pause`, `Stop`, `Resume`, `Cancel`, `Undo`, `Retry` record owner events as given; the daemon authenticates the owner before calling them. Owner-issued roots count only once they are in the log. | KEY-4 | A kernel that verifies owner events needs a signed event envelope. |
| MIG-2-c | **Verb tiers are a closed table of 16 verbs** in `key/verbs.go`; each is reversible or irreversible. Only irreversible verbs are held. | KRN-4 | A new verb is a new table row and a test. |
| MIG-2-d | **The hold window is whatever the key sets.** A key with no hold caveat has no hold; the kernel adds no floor. The first approval tap issues the standing key, so the owner's choice is the policy. | KEY-8 | A floor would be one clamp in `Limits.Window`. |
| MIG-2-e | **Novelty is the shape of a step**: verb, clerk, recipient, content class and sorted labels. A shape completed once under a root is no longer novel under it. | KEY-8 | Drop the recipient from `Shape` for a looser rule. |
| MIG-2-f | **A duplicate fingerprint (irreversible verb) within 24 hours under one root is refused.** The fingerprint is the verb, clerk and the verb's declared arguments, so it cannot be moved by an extra or renamed one; each name and value is length-prefixed, so no value can imitate a boundary. Undoing a step does not clear it for an irreversible verb: the effect stays done. The `amount` has one canonical spelling (`10`, never `010` or `+10`); any other is refused, so equal amounts have equal fingerprints. Other values are not canonicalized here; that is the real clerk's job (#2551). | KRN-8 | The window is one constant. |
| MIG-2-g | **A plan is checked whole at accept, cumulatively, and each step again at dispatch.** Uses are charged at the first dispatch attempt only, so a redo is not charged twice and an accepted step the cap later refuses is cancelled. | KRN-5, KEY-2 | Charging at accept would reserve budget for steps that never run. |
| MIG-2-h | **Pause waits; any other refusal, including STOP, cancels the step.** | KRN-7 | none |
| MIG-2-i | **An unknown result is probed every 60 s, up to 10 checks, then parked.** At boot, a step in flight becomes `unknown` ("restart"), so nothing repeats on a guess. `State.Status` lists every unknown and parked step with the clerk's last detail, for STATUS, and with what the owner's RETRY tier is judged on, from the plan's own step: its amount, whether its verb moves money (always the high tier, CH-11) and its recipient; and with its plan's status and cancel reason, so a cancelled plan's step reads as having no next step. A clerk's probe answers a `kernel.Result`: a probe that finds a covered submit done carries its STATUS line (`step.probed` `covered`, bounded by `shown` before it is logged and when folded), so a submit whose answer was lost is still listed (CLK-3, #2727). `shown` refuses controls, line and paragraph separators, and every format character except the two joiners (U+200C, U+200D). So a label holding a joined emoji is still listed, while a bidi control, an invisible space (U+200B, U+2060) or a tag character (which can hide text from the owner) keeps the line out (#2740). Its line is logged only on `done`, and its STATUS window runs from the probe, up to `MaxChecks`×`ProbeEvery` after the send; the line's text keeps the clerk's send time. The owner's RETRY (`Kernel.Retry`) is the only way out of parked: it applies only to a parked step of an active plan (a cancelled plan keeps its cancel), and is refused (`ErrRetryRefused`, no entry) while the redo's key checks would refuse it (a STOP, a revoke, an expiry, a limit) or its clerk is not booted, so the step stays parked rather than its plan being cancelled (a pause only delays the redo); a parked step of a cancelled plan stays listed, not retryable; resets the check count, and sends the step again under its own idempotency key after Next's full check (key, revocation, pause, STOP, limits as of the first dispatch). A redo that answers `failed`, even one that sent nothing (`too-large`), parks the step again, charged and listed, since the send before it may have acted; only a first send's `failed` fails the plan (#2742 item 8). RETRY is a widening, so it anchors and an unconfirmed one is dropped at open; the warning that the effect may happen twice is owner text, not the kernel's. The sim does not inject RETRY: parking needs ten lost probes, which its fault rates almost never reach, so the unit tests carry it. | KRN-8, CH-11, OWN-16 | The probe interval and limit are constants. |
| MIG-2-j | **The unconfirmed tail is only widening entries.** At open, trailing `resume`, `key.issued`, `key.resumed` and `step.retried` entries no anchor covers are dropped; dispatch, result and narrowing entries are always kept. Every owner action (`Issue`, `Revoke`, `Pause`, `Unpause`, `Stop`, `Resume`, `Retry`) anchors the head itself and returns the anchor's error, so a widening that returned nil survives a restart. When the anchor fails after a widening, the entry is already in live state, so the log is marked broken (as a failed write does) and refuses everything until reopened, when Open drops the entry. A failed narrowing (`Revoke`, `Pause`, `Stop`) stays in force and the log stays usable, since Open keeps it. | LOG-2, KRN-7 | An anchor that lags a narrowing is harmless; one that lags a dispatch would repeat an effect. |
| MIG-2-k | **Erase and per-subject keys are in `erase.go`** (KRN-erase rows below). The log stays one AES-256-GCM key; content is sealed per subject outside it. | LOG-1, LOG-4 | none |
| MIG-2-l | **`Undo` marks only.** It records that a reversible step should be reversed; the clerk reverses it as a new step the key must allow. | KRN-5 | none |
| MIG-2-m | **The plan format is frozen as `Plan{ID, Key, Steps, Sig}`** (`Sig` added by KRN-possession inside v1, since no log has been deployed), a thin typed list (max 64 steps), per Mark's PLN-5 approval. Each step carries only what the planner can claim: `verb`, `clerk`, `args` (name to value), `content` and `labels`. Source, task, recipient and amount are derived at accept, never read from the planner. | PLN-5 | A new field is a new entry version. |
| MIG-2-n | **`key` is a pure value library, not a core package.** It holds no state and writes nothing; `kernel` and `clerk` are core. | CLK-2 | none |
| MIG-2-o | **The mail clerk is a synthetic mailbox.** No real account is touched; the real Gmail clerk is the slice (#2526). | CLK-2 | none |
| MIG-2-p | **Every step is normalized from the planner's fields.** Argument sources are planner, the task is the one the key serves (`Plan.Task`, `key.ChargeTask`, KRN-5), else the plan id under `key.PlanPrefix`, a prefix no task opens under, so a plan the planner names like a task is never charged as it, and a per-task cap spans a task's re-plans and `Authorize` and `Spend` refuse a step or call for another task (#2902), the recipient is the first declared argument of the verb and the amount the `amount` argument (non-numeric or negative becomes -1). Content and labels stay claims. | KEY-2, CLK-2 | A planner step cannot attest its own provenance. |
| MIG-2-q | **Every clerk judges claims with its own `Facts`; `Check` refuses every step at a clerk without them** (`claim`). The fake mail clerk reads every step as its declared `Content` and `Labels`, and the amount argument in its one canonical spelling, the same reading as the exit's. | KEY-2, CLK-2 | A clerk whose facts are wrong refuses honest steps; it never passes a lie it did not compute. |
| MIG-2-r | **A key with bounded arguments refuses planner steps by construction**, since every normalized argument is planner-sourced. An owner or clerk sourcing path is a later row. | KEY-2 | A bounded-arg key cannot yet be used until that path exists. |
| MIG-2-s | **A cancelled plan keeps probing an unknown step, and `repeats` counts in-flight, unknown and parked steps of any plan**, so a cancel cannot hide an effect that may have happened. | KRN-8 | none |
| MIG-2-t | **Each verb has a fixed argument list** (`key/verbs.go`); a step with an extra, renamed or missing argument is refused by `Authorize`, in the kernel, the clerk and a replay. The first declared argument is the recipient. A declared argument with an empty value is refused too: it names nothing to act on. | KRN-8, KEY-2, KEY-8 | A clerk needing another argument gets a table row and a test. |
| MIG-2-u | **The simulator lives at `broker/kernel/sim`**, as EVL-1 now says (SPEC v1.0). | EVL-1 | none |
| MIG-2-v | **The simulator's faults are crash, lost ack, double and stale redelivery, a full disk, a clock that jumps back and a kernel clock that runs ahead of the clerk's.** Each fault is counted where it took effect (a refused append, a clock behind the log's last entry, a stale request the clerk turned away, a failed anchor write), and a test fails if any counter stays zero. A hostile planner also submits plans under a key stripped to its root, a link it forged, or a stranger's signature; each must be refused and is counted, and one that is admitted fails the sweep. A failed anchor after a widening is injected, and the world flags any effect while that widening is unconfirmed. The clerk keeps the true time, and a hostile kernel clock (on from the start in half the seeds, toggled by a fault) jumps past every held step's window at each tick; the clerk's refusals of those steps are counted. | EVL-1, CLK-2 | none |
| KRN-possession | **Using a key needs the signature of its last holder.** Every link already names a holder and is signed by the previous one (KEY-1), but the full root travels inside every derived key, so a key's chain proves only what was granted, not who presents it: `Key{Root: k.Root}` recovered the unnarrowed root. `key.Verify` is now the only way to a `Verified` key, and it requires an ed25519 signature by the tip's holder over `agentos.key.use.v1 || tip ID || use`; for a plan, the use is the JSON of its ID and steps, so the signature also pins what runs, and the clerk takes the step from the signed plan (`Request.Step()`), never from the kernel or the transport. A stripped key's holder is the root's holder, which is its passkey (D-146), so the planner and the home clerk alike can sign nothing under it; a re-derived or rewritten link fails its parent's signature. Chosen over macaroon MACs because a MAC chain needs the root secret at every checker, so any clerk could mint keys, and the root is a phone passkey, which signs and cannot MAC. No new component: the KEY-1 chain and its ed25519 keys are reused. Plan text must be valid UTF-8 (`ErrNotText`), since JSON writes invalid bytes as U+FFFD and two plans could share one signature. A signed plan is not bound to one log: replay is stopped by plan IDs, rebuilt from the log; a restore brings back the same log, so a log ID would not change; and a holder whose key is issued into a second log can sign there anyway. | KEY-1, KEY-3, D-139, D-142 | A holder whose secret leaks can use only what its own key allows; revoke that key. |
| MIG-2-rel-a | **A request names a step and nothing else** (`Request{Plan, Index}`; the idempotency key is derived). The clerk reads the time from its own `Clock` and the step's first dispatch and hold from the log (`View.Dispatched`), which answers only for a step in flight and only when the request's plan equals the logged plan exactly (`reflect.DeepEqual` over id, key, steps and signature), so a request carrying any other plan is refused (`dispatch`). A signature compare alone would not do: the holder can sign another plan under a logged id. So no request can claim a dispatch sequence that undercounts the key's uses, a hold, an hour, or a step the kernel is not running, and a stale or duplicated delivery after the result is turned away. | CLK-2, KRN-8 | An out-of-process clerk reads the same facts from its own copy of the log. |
| MIG-2-rel-b | **The hold start is the log's stamp of the hold entry**, taken on the kernel's clock; the clerk judges the window's end on its own. A kernel clock that runs ahead at release is caught; one that was behind when it stamped the hold is not, since both clocks then agree the window is over. CLK-2 asks the clerk to time the hold-start entry from when it saw it, which needs the clerk to follow the log as it grows: it comes with the out-of-process clerk (#2551). | CLK-2, KEY-8 | The clerk records its own time for each hold entry it sees. |
| KRN-root-limit | **Every key derived from the root is a clerk key that lapses and is capped** (D-145, D-146): the chain check refuses a first link without an expiry and a daily spend cap (`ErrUncaveated`), so `Derive`, `Verify`, `Chain` and through them the kernel, the clerks and a replay all refuse it. The grant decision also caps the life: a first link's earliest expiry is at most `ClerkLife` past the time it goes live (`ErrLife`, #2670), so a tap cannot sign a key that runs for years; `key.ClerkKey` sets that default (30 days). A history longer than that is covered by same-limit renewals, as the slice runner does. A renewal whose limits are within the old key's (`key.Limits.Within`: every limit the old link sets, set at least as tightly, expiry aside) is live at once like a same-limit one, since it gives no more power (#2670 item 5); one that drops or loosens a limit waits the hold. Keys below the first link inherit its limits and need add none. A first link's caps count against the clerk's account under the root (`account`, in `Verified.Scopes`), so a renewal or a second first link to the same holder starts no fresh budget. The root's holder is its passkeys: any enrolled passkey signs a first link off it or a one-off under it, and the home clerk's signature confers nothing; the passkey's own signature under the bare root is a one-off over the clerk's limits. | KEY-3, D-145, D-146 | A clerk that never spends still carries a cap, of 0. |
| KRN-grant | **Roots and first links are grants in the log, live after `GrantHold`** (D-146, KEY-1). `Kernel.Issue` takes one batch, one entry and one hold; a first link's root must be granted already or earlier in the batch, and a first link is never live before its root. `kernel.Live` refuses a key whose root or first link is not granted (`not-granted`) or still in its hold (`grant-held`), in `Admit`, in spend funding and extensions, and in `clerk.Check` on the clerk's own clock. A revoke cancels a pending grant, and so does revoking the passkey that signed it; `State.Pending` lists the rest, none under a revoked root, for the owner's notice. Same-limit or narrower renewal: a first link to the same holder under the same root, with caveats within the old link's (`Limits.Within`, KRN-root-limit) and a later expiry within `ClerkLife` of the entry, renewing a grant that is live, not lapsed, not paused and not revoked, is live at once. `Issue` and the fold share one decision (`State.grants`), so `Issue` logs only what the fold grants. The hold starts at the entry's stamp on the kernel's clock, as a step hold does (MIG-2-rel-b). | KEY-1, KEY-4, KEY-6, D-146 | A notice is the owner channel's (#2643): `Pending` is what it reads. |
| KRN-passkeys | **The anchors are the owner's hardware keys, given at boot; a phone passkey is enrolled by an anchor's signature** (`key.Enroll`, `Kernel.Enroll`, a widening that anchors and is live at once) and revoked by an owner action (`Kernel.Unenroll`, a narrowing). An anchor is never cut off that way: `Unenroll` refuses one (`ErrAnchor`) and the fold ignores a logged one, so one forged owner message cannot lock the owner out; replacing a hardware key is recovery's (REC-3, #2670 item 3). `key.Passkeys` rebuilds the set from the anchors and the signed list, so a clerk checks it with its own anchors and trusts the list keeper for revokes only, as it already does for key revokes. A revoked passkey never comes back. A grant is verified against the set at its entry, so a cut-off phone grants nothing; a key derived from its earlier grants runs until it lapses or is revoked; its one-off under a bare root is refused (`PlanOwners`). Any passkey in the set signs a first link, so a phone renews the clerk key of a root a hardware key granted. For a key derived from a granted root, `PlanOwners` still requires the root's passkey to be an anchor or one an anchor enrolled, cut off since or not, checked with the checker's own anchors, so a view that lies about a grant cannot vouch for a root no owner passkey signed. Anchors are not revoked here: losing one is REC-3's re-root. | ID-1, KEY-4, REC-3, D-146 | Revoking an anchor would be one more owner action and a `Passkeys` rule. |
| KRN-cosign | **A big change needs two passkeys, one an anchor** (D-146 item 5, `broker/kernel/cosign.go`). Power is per clerk and holder: the verbs its grants reach, narrowed by their links (`key.Reach`), and its daily budget, the sum over roots of each root's largest daily cap, since each root is its own account; the passkeys' own one-offs are a holder too. A batch is big when, against the live grants, the live and pending grants with the batch give any holder a verb it lacked or a budget past the owner's line (`State.Line`, default 200%, never under 100%), so a first key to a new holder, setup included, is big, and a same-limit renewal or a raise to double is not. Counting pending grants on that side means raises in one hold cannot each pass as small: a renewal's cap replaces its root's, a new root's adds. Lapsed, revoked and paused grants are none. The line bounds each step, not a chain: X, then 2X, then 4X on later days each pass with a hold and a notice but no hardware key. A big batch is granted whole or not at all: its co-signers (`key.Cosign` over `BatchHash`) must be two passkeys of the set, one an anchor (`key.Approved`). The keys' own signatures count for nothing, since a batch can carry a key a hardware key signed long ago. A one-off under a bare root may spend up to the line times the largest live daily cap of a clerk key under that root (`OneOffLine`); past it the plan carries a co-signature over `PlanHash`, checked in `Admit` and again in `clerk.Check` with the clerk's own anchors (`OneOff`). Raising the line is big (`SetLine`, co-signed over `LineHash`, which names the count of changes so far, so an old approval cannot replay); lowering it narrows. Other caveats (uses, rates, content) do not count toward big: a renewal that drops one still waits the hold. | KEY-4, KEY-6, ID-1, D-146 | A clerk takes `OneOffLine` from the log's view, as it takes grants; a view that lies about it is the trusted base's (MIG-2-rel). The ceremony that collects the hardware key's tap is #2643's. |
| KRN-ownerlink | **A passkey may narrow a clerk key for the clerk itself** (`key.Narrow`). A link after the first is signed by its parent's holder, or by a passkey of the set when the link keeps that holder; `Verified.ByOwner` marks such a tip and `Verified.Narrowers` lists the passkeys. It is the owner's approval of exactly those caveats (OWN-9): no grant, so it waits no hold, since the holder could derive the same key itself, and its caps count against the link alone, so a uses cap counts the approval. A link to any other holder is a grant and still needs one. `Live`, shared by `Admit` and `clerk.Check`, refuses a key a cut-off passkey narrowed (`CCutOff`). A clerk that asks more of the key reads the chain `clerk.Verify` checked, never a second verification of its own. | KEY-3, OWN-9, CLK-2, D-146 | A stolen phone still approves until it is cut off, as a tap does today; the browser gate's use of it is #2675. |
| KRN-task | **A task is a log entry, and a key serves one task through its task caveat** (KRN-5, CLK-3, D-147; `broker/kernel/task.go`). `OpenTask` logs `task.opened`; the fold sets its time and its timeout, `TaskTimeout` (24 hours) later. The owner's setting of the timeout (lowering by text, raising as a KEY-4 widening) is a later row. `key.LimitTask` binds a key to one task, and a key moves to no other: a second task caveat is `ErrLoosens`. `Admit` refuses a plan whose key's task is not live (`task`). A task ends at `EndTask`, at STOP and at its timeout, and an ended task never comes back. A rejected plan, a failed step, a cancel or a revoke does not end it, and an admitted plan's steps and their reconciliation outlive it. A task approval (`ApproveTask`, an enrolled passkey's `key.Approve` over `TaskHash` of the task, the approval's place `N` among the task's approvals, the site and the held request) lives inside the task. `N` must equal the task's `Taps`, the count of approvals it has logged, so every tap signs anew and a seen co-signature can never be logged again: a task holds one per site, a later one for the same site replaces it (as when the clerk asks again after a card fill), it ends with the task, and cutting off its passkey ends it at once. A clerk reads the one for the request's site, as the clerk reads it from the request, through `TaskApproved`, live on its own clock and signed by a passkey from its own anchors; the approval's `At` is the fold's, the log's time of the tap, for the clerk to order its own fills against. The clerk process's view (`broker/clerk/run`) carries the chain's task as of the call. | KRN-5, CLK-3, KEY-3, D-147 | KEY-3 has the kernel add the task caveat with its narrow-only sub-key, in the narrowing that binds a key to its plan. Until that sub-key exists, the host that hands a planner its key adds the caveat, and a planner must hold only task-bound keys: a caveat narrows, so a planner given an unbound key could bind it to any live task. |
| KRN-calls | **The kernel logs a clerk call and its answer in two steps** (#2700, KRN-7, OWN-17, OWN-18). `Kernel.Calls` runs every plan as far as the clock allows and returns the calls due, each dispatch already logged; `Kernel.Answer` logs the answer. A call is handed out once until answered; a restart marks dispatches in flight unknown and probes them (Boot), so that hand-out record is not state. `Kernel.Send` is the last check before each dispatch goes out, under the lock its view is taken under: a STOP, revoke or cancel logged since `Calls` cancels the step unsent, and a pause leaves it unsent until the key resumes, so nothing reaches a clerk after "Stopped." `Tick` is the same steps over the in-process clerks. A dispatch that reached no clerk is `unsent`: STATUS lists it with its clerk, and it is sent again under the same idempotency key, charged once, after `UnsentWait`, doubling at each attempt up to `MaxUnsentWait` (16 minutes). A step whose clerk the kernel was not booted with is never sent: its plan is cancelled (`no-clerk`, naming the clerk) before any dispatch is logged, so nothing is charged. A cancelled plan keeps its cancel's code and detail (`PlanState.Cancel`, `CancelDetail`) for STATUS. A step cancelled while known not to have acted (queued, unsent, or proved not done by a probe) gives its dispatch's charge back, so a cancel leaves no cap spent on an effect that never happened; a step that may have acted keeps it, and a step RETRY sent again goes back to parked, charged and listed, until a probe finds it not done (#2707 item 5). A probe that reached no clerk is `unreached` and counts none of the ten checks, so a clerk that is down never parks a step. | KRN-7, KRN-8, OWN-17, OWN-18 | A clerk that answers `unsent` when bytes did reach it would run a step twice; only the transport, which knows no byte was written, says it. The same false `unsent`, or a false `notdone` from a probe, after a cancel also gives the step's charge back. `unsent` comes only from the transport (`clerk/run` passes none from a clerk), but `notdone` is the clerk's word: a lying clerk can free a use on a key other clerks share, one step per cancelled plan. |
| REPLAY-1 | **A log prefix reproduces every kernel decision in it** (`kernel.Rederive`, #2934, change 4 slice 1). Inputs (owner actions, plans, clerk answers and probes, metered usage, pool readings, tasks) are folded as given, since the log is where they enter; each decision (`plan.accepted`, `plan.rejected`, `step.held`, `step.dispatched`, a non-owner `plan.cancelled`, `pool.reset`) is derived again before it is folded, with the live kernel's own pure functions at the entry's own `At`, and must equal the logged bytes. The send check is one function (`sendCheck`) shared by `Send`, `Retry` and the checker. The only random draws come from `Config.Rand`: log and content nonces, and subject IDs and data keys; none changes a decision, since the log records each ID and key ID as given. Production (`proc`) pins `Config.Rand` to crypto/rand; tests, the sim and eval runs seed it. Every kernel test's `replays()` and every sim check run it. Not seen: a decision the kernel should have logged and did not, since a tick that logs nothing leaves no entry (a logged tick is a LOG-5 change); whether a `no-clerk` cancel's clerk was really absent, since the log does not name the booted clerks; and `model.reserved`, which depends on the log's broken flag rather than state. A new entry type is a decision with no derivation until it is listed, so none is folded unchecked by default. The periphery's clock, randomness and network reads enter as events once agentosd starts the kernel (#2682). | KRN-1, EVL-1 | A tick entry would let the checker also find omissions. |

"Only from the paired phone" is the owner channel's authentication, as for every owner action (MIG-2-b): the setup page binds the call to the phone the claim sticker or flasher paired.
