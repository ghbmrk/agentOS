# Kernel channel check: assumptions

Each row is a reading of the spec, or a property the code relies on, that a
reviewer may want to change (issue #4373, KRN-cap-first-b; D-255, NET-2 The
channel).

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| KRN-chan-1 | **The kernel checks a token at the send and spends it at the answer.** The enforcer counts a message once, somewhere between the kernel's write and the kernel's read of its answer (every request gets a `Result` or `ReadReply`; the hello, the enforcer's hello). Its bucket (`wire.Bucket`, the cell rate algorithm) leaves a message counted later no fuller and finds one checked later no emptier (`TestBucketLaterIsSafer`), so a kernel that checks at the earliest moment and spends at the latest holds a bucket never fuller than the enforcer's. To know the latest moment, one message of each kind is unanswered at a time (`ErrWait`); a head and an entry share one kind, as the enforcer counts them (`wire.RateKindOf`). | NET-2 The channel ("which the kernel checks each message against before sending it"), D-255 item 2 | Several unanswered per kind would need each spent at its own answer, in order; the bound is the same. |
| KRN-chan-2 | **A request whose answer never came is spent when the next hello is answered.** The enforcer counts only the connection whose hello it accepted last, and makes a connection that one before it writes its hello (`broker/enforcer/channel` ENF-d-9). So once the kernel reads the next connection's enforcer hello, no frame of an earlier connection is counted after that moment: the request is spent then. Until then nothing but the hello is sent (`ErrOrder`). | NET-2 The channel | Without ENF-d-9 a late frame could be counted at any time, and only a time bound (as for the hello, KRN-chan-3) would hold it. |
| KRN-chan-3 | **A hello whose answer never came is counted by `MaxLate` (two minutes) after the kernel gives up on its connection.** Hellos arrive on their own connections, so ENF-d-9 does not order them, and `Lost` spends such a hello at the loss plus `MaxLate`. This rests on the kernel's client aborting a connection it gives up on, so its stack sends nothing more, on a frame already sent being read within two minutes on the home's wire, and on the enforcer counting a hello as it reads it: it does so under a lock no request holds across a radio or policy call (`broker/enforcer/channel` ENF-d-7, #4508), so no blocked call there delays the count. A late hello only matters if the kernel also opens connections at the full hello rate then; the burst's tolerance is nine minutes. | NET-2 The channel | A hello carrying a sequence number the enforcer checks would bound it without time. |
| KRN-chan-4 | **The check's clock runs one part in `Margin` (64) slow.** The kernel and the enforcer read different clocks; the check runs on `time.Now`'s monotonic reading, which never steps, and slows it by 1/64, so its intervals are no shorter than the enforcer's while the two clocks' rates differ by less than about 1.5% (a free-running crystal is within 0.01%, an NTP slew within 0.05%). A kernel at the exact edge of the rate trips on any faster drift, which `TestHonestKernelNeverTrips` shows (with no margin it trips at the first seed). The caller passes `time.Now`; a wall clock stepped forward would look like a refill. The enforcer's side rests on its own rate clock never stepping back and counting through suspend (`broker/enforcer/channel` ENF-d-10, #4507). | NET-2 The channel; D-255 item 3 (no clock difference trips) | The cost is the kernel's pace: 1.5% under the enforcer's rate. |
| KRN-chan-5 | **A new run assumes the last one spent a full burst of every kind just before it.** The kernel keeps no rate state across a restart, so `New` spends a full hello burst at its start and each request kind's full burst when its first hello is answered (KRN-chan-2's moment). An earlier run's hello unanswered at its end may still arrive within `MaxLate`, but the earlier run's own check kept every hello within a burst of its end while `MaxLate` is within the hello burst's tolerance (`TestMaxLateInsideHelloBurst`), so the full burst covers it. The first hello passes a slowed minute after start and each request kind one interval after that (a proposal link ten minutes). | NET-2 The channel | Persisting the buckets would remove the wait. |
| KRN-chan-6 | **The format check is the enforcer's read path over the bytes the kernel writes.** `Frame` encodes the message, writes it with `wire.WriteFrame` and reads it back with `wire.ReadFrame` and `wire.Decode` on the enforcer's direction, and returns those exact bytes; anything the enforcer would trip on as outside the format (`ErrType`, `ErrLength`, `ErrPayload`), a type the core does not send, or a second hello on a connection is refused before a byte is written. | NET-2 The channel ("one fixed format definition"), D-255 item 3 | — |
| KRN-chan-7 | **This package is the check only.** The kernel's channel client (ENF slice o) writes exactly `Frame`'s bytes, calls `Answered` on each answer and `Lost` when a connection ends or it gives up on one; it times out a request whose answer does not come and calls `Lost`. Until it lands nothing links the gate, so it adds no trusted-core lines. | #4373 | Wiring it into the kernel grows the trusted core and needs its D-159 row. |
