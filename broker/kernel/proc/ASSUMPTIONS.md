# The kernel's process: assumptions

`broker/kernel/proc` is the kernel's half of `broker/clerk/run`, split out by KRN-2 split (#2892). Its earlier rows (MIG-4-run a to d, h, i, m, o; STO-2b-1 z, aa; LOG-anchor-tpm a, b) stay in `broker/clerk/run/ASSUMPTIONS.md`, where both processes were built. Each row is a reading a reviewer may want to change.

| ID | Assumption | Spec basis | If it changes |
|---|---|---|---|
| KRN-2-split | **The kernel's process links no clerk's code; the wire lives on the kernel's side.** `kernel/proc` holds the kernel process (`OpenKernel`, `Tick`, `RunKernel`, the owner and meter sockets and their clients), the log file and its anchor, and the wire both sides speak (the call, the view, `Remote`, `ServeClerk`, `Conn`, `ServeConns`, `ServeOne`). `broker/clerk/run` keeps the clerks' processes and imports it, so a clerk's process links the kernel process's code but not the reverse: no clerk binary exists yet, and the code it gains holds no parser of outside bytes the clerk does not already read. The clerks' own errors cross a socket by their text through `WireErrors`, called from `clerk/run`'s init, since this package cannot name them. A process's private-file checks and atomic write moved to `broker/kernel/privfile`, which both use. `TestTheKernelProcessLinksNoClerkCode` holds the split: of `broker/clerk` the kernel links only `clerk/handoff`. Measured at the build: own lines 143,042 to 131,451, dependency lines 303,277 to 282,015, parsers 122 to 118. | SPEC KRN-2 | When a clerk ships as its own binary, it may want the wire in a package of its own, so it links no log or anchor code. |
| STO-2c-restart | **A kernel that came up and then failed reboots the box; one refused at its start does not** (#2998). After the unlock cap (#2977, tpmseal STO-2c-cap) no restart in the same boot unlocks, so `Restart=on-failure` cannot bring the kernel back. `RunKernel` makes `MainConfig.Up` (`-up`, empty, `O_EXCL` and no link followed) once both sockets listen, after every start check (the log key, the anchor, the owner's hardware keys in the unlock step). `agentos-keeper-kernel.service` makes it in `/run/agentos-kernel`, which outlives a stop (#3073) and a reboot empties: each start first removes the last start's file (`ExecStartPre=` `KERNEL_UP_CLEAR`, which `mkosi.finalize` requires beside the reboot line), so a start refused after a good one reads as refused, and its `ExecStopPost=` asks for a reboot only when the kernel made it and the unit's result is not success: `systemd-run --on-boot=30min`, so the reboot comes no sooner than 30 minutes into the boot (a boot timer past its time elapses at once). A refusal at the start repeats on every boot, so it stays down as before; a kernel that comes up and fails on every boot reboots the box at most twice an hour, spending at most four of the counter's increments an hour (#2897). `mkosi.finalize` admits only that one reboot line in the unlock unit (`KERNEL_REBOOT`), and no `OnFailure=` or `OnSuccess=`. A failure to make the file is said on stderr and the kernel runs on: the file only lets a later failure reboot the box. **Limits:** a failure after the cap but before the sockets that a reboot would cure (a TPM glitch at the anchor) stays down until the weekly reboot (UPD-10); the reboot does not wait out a call (UPD-6), since nothing reaches the kernel while it is down; the kernel's uid can make or remove the file, which lets a compromised kernel only reboot or keep down its own box, a denial of service it already has. | STO-2, CLK-1 | If the kernel ever survives its own crash without a second unlock (#2998 option 2), this reboot goes. |
| MIG-4-run-keys | **The kernel process opens its subject-key table at start** (#2682, KRN-erase). `RunKernel` refuses an empty `KeyDir` (`ErrNoKeyTable`, `-keys-dir`, `/var/lib/agentos-kernel/keys` in `agentos-keeper-kernel.service`), and `OpenKernel` opens `FileKeys` there under the log key and calls `OpenContent` before any socket listens, so content opens in the real process and every logged erase deletes its key again at each start. The table is keeper-side: it sits in the kernel's own 0700 state directory, which the main side's units cannot reach (D-154, `InaccessiblePaths=/var/lib/agentos-kernel`), and it crosses no boundary. A table open to another uid, or a key file that does not open as its subject's, stops the start (refused at start, so no reboot, STO-2c-restart). No content store exists yet, so the stores map is empty: an erase's store entries stay unconfirmed and back off until a store is wired. The start's `ContentReport` goes to stderr as two counts, no subject IDs; no owner call reports it yet. `KeyDir` empty in `OpenKernel` keeps content closed, for tests only. | LOG-4, KRN-erase, D-154 | When content stores land, they join the map here; when STATUS carries the report, the stderr line can go. |
| MIG-4-guest-plan-results | **The owner seam's plan read is the kernel's `PlanView`** (#3086, PLN-4, PLN-5 (b)). `plan` answers `kernel.State.PlanView`: the status, a rejected plan's refusal code (`PlanState.Reject`, folded from the `plan.rejected` entry, so a rebuild reads the same), and each step's phase, its clerk's last answer (`StepState.Detail`, which `detail` already bounds for STATUS) and whether it was undone. The refusal's detail is not carried: it can name values, and PLN-4 gives the guest only the check. The owner side reads it whole; the guest plane narrows it (guest ASSUMPTIONS MIG-4-guest-plan-a). | PLN-4, PLN-5, KRN-1 | A step's handles join `StepView` when the log keeps reader values behind them (PLN-1, PLN-2). |
| MIG-4-recovery-e3-a | **The kernel writes, reads back and marks each backup itself** (#3251, BAK-1). `Kernel.Backup` takes, under the lock, the log's length (`FileStore.Size`), a copy of every live subject's key and the live set (`backupSnap`), then writes outside the lock, so STOP never waits on a backup's write. Nor does STOP wait on a backup's re-seal (#3317, Security finding 2 on #3311): `reseal` takes the re-seals due under the lock (`kernel.Reseals`), runs each one's I/O on its own goroutine without it, and commits it under the lock. Tick starts them and does not wait; `Erase` and `Backup` wait for theirs, so a hung target delays their reply, never STOP. Each current target gets its own `backup.Write`: the content object goes to `<backup id>.content` (a synced temporary linked into place, never over an existing file) beside the target's key tables, and is read back with the table; only when both sums match is the `Kept` verified. No key table goes out before its `Record` is kept: the target `backup.Write` puts to (`pendingPut`) first saves the backup as `Pending` in `records`, under the lock, and adds it to the `Set`, and sends nothing if that save fails (Security fix-list 1 on #3311). The pending `Record` lacks only the content and table sums, which an erase does not use; a finished backup replaces them and clears `Pending`. While its first table is on its way the `Set` holds the backup behind a target that refuses every call (`inFlight`), so an erase then names it held (`ErrInFlight`) instead of re-sealing a table not yet there, which the put would land beside still giving the erased key; once the put is over its backoff is dropped (`RetryBackup`) and `Backup` re-seals it at once if a subject it gives was erased meanwhile, and the kernel process's Tick retries that, with its backoff, if it fails (#3311 L3 and Security on 6ef6bef, L3 on 6e14b28). One that never finished (the kernel stopped, the put reported a failure after the table landed, or the finish could not be saved) stays pending and unverified, in the `Set`, so an erase re-seals its table or names it held. Pending entries are kept at start as they are: an empty folder cannot tell a table never written from a drive not mounted, so none is dropped, and an erase over a table that never landed writes one holding only live keys. After the adds `Backup` re-seals what is due, so a subject erased between the snapshot and the add is re-sealed at once. One backup runs at a time; a target whose last backup at this recipient is verified and under `BackupEvery` (ten minutes) old returns it (`Reused`), read from the kept records, so the wait survives a restart; a changed recipient, an unverified last backup or a clock run backwards writes again. | BAK-1, LOG-4, KRN-7 | When a content store lands, its `content/<store>` section joins the same snapshot. If a write ever takes long enough to matter for the owner's call timeout (one minute), e4 sets a longer one. |
| MIG-4-recovery-e3-b | **The backup records are one file, sealed under the log key, required at start** (`-backup-dir`, `/var/lib/agentos-kernel/backups`). `records` holds every `Kept` (target name, verified mark, `Record`), AES-256-GCM under the log key with its own AAD, written atomically (`privfile.WriteAtomic`); the `Set`'s save rewrites it before a re-sealed `Record` is used. A file that does not open, or names a target the log never added, stops the start (`ErrRecordsFile`, refused at start, so no reboot). `RunKernel` refuses an empty backup directory (`ErrNoBackupDir`), since an erase must reach every backup taken before. **Limits:** the seal gives integrity, not freshness: a writer of the drive can put back an older sealed `records`, dropping a later backup from the `Set`, so an erase would not re-seal it (that backup still opens only with the recovery key). The file has no retention yet and is capped at 16 MiB (some ten years of daily backups to two targets); the `backups` answer's 4 MiB frame bounds the list sooner. | BAK-1, LOG-4, D-168 | A rollback check would log each backup (a `backup.taken` entry) so the log, which the anchor protects, names every `Record`; retention is its own row. |
| MIG-4-recovery-e3-c | **A dir target is never the kernel's own data** (#3251 review note 1). The kernel resolves the log's folder, the key table's and the backups' at start; `backuptarget` and every later use of a target (write, read-back, re-seal) resolve its locator through links and refuse one that is, or is inside, any of them (`ErrTargetInKernel`), or is not a reachable directory (`ErrTargetNotDir`). A link swapped in between a check and the write it guards is not caught, but a dir target only ever writes `<hex id>.table.<n>` and `<hex id>.content` under fresh names, so it cannot replace the log, a key file or the records. A target logged append-only is never asked to delete, and `backups` reports it as not rewritable, so an erase there leaves a held backup with its reason. | HW-16, HW-17, D-168 | The storage adapter row adds its own kind and constructor here. |
| MIG-4-recovery-e3-d | **`broker/backup`'s tests no longer link `kernel/proc`**, since `kernel/proc` now links `broker/backup` and Go refuses the cycle. The two checks that used a real `FileKeys` moved here: `TestABackupTableIsNoKeyFile` (a table written as a key file does not open) and `TestARestoreUnwrapsIntoFreshFileKeys` (REC-1: unwrap into a fresh `FileKeys`, then a start on the log with a later erase deletes that key); `broker/backup` keeps its own versions over `kernel.MemKeys` and the log-key AEAD. | BAK-1, REC-1 | none |
| MIG-4-recovery-f1-4 | **The kernel holds the page authority and certifies the page's key.** `KernelConfig.PageCA` is opened once by `OpenKernel` (a value that does not open starts no kernel) and never changes, so `certify` reads it without the lock. `certify` is a `procOp` that takes the lock only to read whether setup has logged anchors; it is served while setup is open, since setup's passkeys are made on the page. With no authority it answers `ErrNoAuthority` before setup and `ErrPageRestore` once claimed, never a new authority. Keys over 128 bytes or not P-256 PKIX DER answer `pageca.ErrKey`. The leaf comes from `pageca.Authority.Issue` unchanged, at the kernel's clock. `kernel/proc/kernel.go` gained the config and struct fields, a file the brief's scope did not list. | CH-9, KRN-7, D-186 | If leaves must be revocable or shorter-lived, that is the brief's residual risk 2, a later choice. |
| MIG-4-recovery-f1-5 | **Every backup carries the authority and its Record names it.** `writeOne` passes `pageca.Marshal`'s form as the manifest's opaque `PageCA` and the fingerprint (the Owner Card's form) as the Record's `PageCA`, which `Rewrap` carries unchanged and the records file keeps across a restart. A kernel with no authority writes and names none. Restore (#3186) compares the two. | CH-9, BAK-1, D-186 | none |
| EDGE-link-core-b-4 | **Setup logs the handed first edge key; a start not by the tpm slot cuts the edge.** `KernelConfig.FirstEdge` reaches `kernel.SetupWithEdge` through the `setup` call, now a `procOp` (`Kernel.Setup`), so the key lands at sequence 2. When the hand-off's slot is not `tpm`, `RunKernel` hands no first key and calls `EdgeCut` naming the slot before serving; a failed cut starts no kernel. `KernelConfig.LinkKey` is held and read by nothing yet (c2's `linksign`); no backup writes it (`TestBackupHoldsNoLinkKey`). The tests that run `RunKernel` skip as root, since the kernel refuses root; CI runs them as a plain user. | HW-15, REC-2, BAK-1 | If setup moves off the owner socket, the first key moves with it. |
