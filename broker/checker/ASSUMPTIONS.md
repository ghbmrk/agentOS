# checker: assumptions

What `checker` and `cmd/agentos-checker` rest on (SIM-split, briefs/SIM.md; OPERATING §5).

| ID | Assumption | Source | Held by |
|---|---|---|---|
| C-1 | The checker process holds the CH-4 seed and nothing else, apart from the broker, the vault process and every key holder. The unlock step hands it over `hand.sock` with the holders' protocol (`GET /state`, `PUT /secret`, so `holder.Keeper` serves unchanged); no socket reads it back, and the state file holds only the last spent step. This PR builds the process; moving the seed and the pending enrol seed out of egress custody, and routing the broker's verify here, is the wiring row's. | CH-4, ARC-1, SIM-split | `TestHandlersServeClosedSets`, `TestSpentStepSurvivesRestart`; wiring BOARD row |
| C-2 | A code verifies as egress custody's does: the current or previous 30-second step, after both the caller's `after` and the durable last step, with counted and silent wrong-code buckets (20 and 10 per 10 minutes) that pause per bucket. The step is on disk before the answer. The checker does not accept the unlock proof (`unlock:` prefix); until wiring joins the two, the unlock's last step (custody) and the checker's are separate stores, so one code could pass both once. | CH-4, O6 | `TestVerifiedCodeApprovesEachActOnce`, `TestWrongCodesApproveNothingAndPause`, `TestVerifyHonoursAfter`; wiring BOARD row |
| C-3 | A verified code records one approval per act it was given (at most 64), each redeemable once within 15 minutes (the CH-10 code lifetime). Approvals live in memory only: a restart drops them and the owner approves again. | CH-10 | `TestVerifiedCodeApprovesEachActOnce`, `TestApprovalExpires`, `TestSpentStepSurvivesRestart`, `TestClientReportsRefusals` |
| C-4 | An act is the SHA-256 of the length-prefixed account (the credential name), host, method, wire path and body, so it binds the whole request a holder sends and the login that sends it (#1057 S1). The broker must compute it over the exact bytes the holder sends: the body rule's encoding, which equals what egress forwards because the rule is idempotent; that binding is the wiring row's. Every holder uid shares `redeem.sock` and the checker does not map uid to account, so a compromised holder can spend, and so deny, another account's approval, but never use it with that account's login. | CH-10, ADP-10 | `TestActBindsTheWholeRequest`, `TestHighRiskActNeedsACheckerVerifiedCode`, `TestApprovalIsBoundToTheAccount`; LATER line |
| C-5 | Known gap: a code-generator code is bound to time, not content. A compromised broker that receives a fresh owner code can ask the checker to approve acts other than the ones the owner was shown, within the code's 30-second window. The checker stops a compromised holder or egress from acting without any code, not a compromised broker from substituting content. Paper-grid cells (CH-10) do not have this gap. | CH-4, CH-10 | stated in the PR; SIM-check predicate row |
| C-6 | Linux unix sockets and `SO_PEERCRED`: `hand.sock` admits the unlock uid, `verify.sock` the broker uid, `redeem.sock` the holder uids, through `sockets.ListenPeers`. The binary refuses one uid on two sides, running as any peer uid, and a run directory not 0711 or not owned by its uid, and makes itself non-dumpable. | ARC-1 | `TestServeOverSockets`, `TestParseKeepsEachSideApart`, `TestRunRefusesItsPeerUID`, `TestIsolateRefusesItsPeerUIDAndDropsDumpable` |
| C-7 | An act may carry a wait (whole seconds, at most `MaxWait`, 7 days): its approval opens at verify time plus the wait and stays redeemable for the 15-minute TTL after that; a wait over `MaxWait` refuses the verify. `POST /revoke` on `verify.sock` withdraws up to 64 acts' approvals and can only deny, so the broker uid gains no new power from it. | CH-4, CH-10, REV-3 | `TestAHeldActWaitsOutItsUndoWindow`, `TestRevokeWithdrawsAnApproval` |
