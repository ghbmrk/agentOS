# Attestation schema: assumptions

Built for P4-4 (BOARD.md) against SPEC v0.12 OSS-4, for the attestations
P4-3 (`broker/update`) signs and checks under OSS-8 and D6. Hardware-database
entries (OSS-4's other half) and attestations of public candidates other than
releases are later packages. Each row is a reading of the spec, or a gap left
for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| A1 | The public schema is `schema.json`, embedded in the build and published with the repository. A schema change is a reviewed code change that reaches boxes with a release, so nothing on a box can add a value at runtime. Recommended (potency PR1 on #73), with the hardware-database package: publish the schema as a signed TUF target so new hardware is listed without a release. | OSS-4, OSS-11 | Medium: the signed target replaces the embedded copy. |
| A2 | **Every statement field is closed.** `result` and `channel` are listed values (`pass`/`fail`, `stable`/`fast`, also checked against `update`'s constants); `hardware` is exactly `{vendor, model, firmware}`, each listed under the one above; `versions` maps listed components to listed versions; `operator` is empty or `maintainer`. `release` must be `ReleasePath(n)` exactly and `manifest_sha256` 64 lower-case hex digits; both name public signed bytes and must match the verified release to count. The statement has no time field at all (OSS-4 allows a day; nothing needs one). Unknown, repeated and case-variant keys are refused, including inside `hardware`. | OSS-4, OSS-8 | — |
| A3 | **`unlisted` for what the schema does not know yet.** Hardware or a version missing from the schema is attested as `unlisted`, and once a hardware level is `unlisted` every level below it must be too. So a box on new hardware can still attest (and an outside attestor still counts for D6) while saying nothing beyond "not listed". `unlisted` is never listed itself. A model may be listed before any of its firmware versions (only `unlisted` firmware then); the floor reference PC (HW-4, GEEKOM Air12 Lite) is listed that way until A1 runs record its firmware. | OSS-4, HW-4 | Low: drop `unlisted` and refuse unknown hardware, at the cost of attestations from new PCs. |
| A4 | **Listed values are tokens:** lower-case letters, digits, and inner `.`, `_`, `-`, at most 32 characters. Listing is what bounds a value; the shape only keeps listed values plain and lets version strings like `2026.9.8` in. There is no per-statement bit cap (unlike hints, H2): every field is public data about public software and the PC class, and the list grows with real hardware. | OSS-4 | Add a cap if a later field could carry owner-derived choices. |
| A5 | **Strict to sign, tolerant to read (potency PB1 on #73).** `update.Attest` refuses to sign a statement outside the box's schema. `update.ParseAttestation` accepts hardware and versions of the token shape (A4) with A3's structure, and maps what the box's schema does not list onto it: an unknown hardware level becomes `unlisted` with every level below it, an unknown version becomes `unlisted`, an unknown component is dropped. So a box on release N counts an attestor's statement about N+1 that names N+1's new versions (D6 would otherwise never auto-stage such a release), and only values the box lists reach its digest. Bad shapes, unknown or case-variant keys, and a level listed under an unlisted one are still refused. | OSS-4, OSS-9, UPD-8 | — |
| A6 | **Residual channel: keys and signatures.** The attestor's Ed25519 key and the signature are high-entropy bytes the attesting code chooses. They carry nothing private only if the key is generated by broker code, never chosen by an agent or derived from owner data. That is the publication package's to keep (OSS-6 pseudonymous, rotated key). | OSS-4, OSS-6 | The publication package records where the key comes from. |
| A7 | Wire change: `hardware_class` (a free string) is replaced by `hardware`. No attestation has been published (no release keys until K3/q6), so there is no compatibility path. | OSS-4 | — |
