# Owner Card: assumptions

Built for PLAN P2-2 against SPEC v0.12 (§3.1, ONB-7, CH-4, CRED-8). Each row is a
reading of the spec, or a gap left for a later package, that a reviewer may want
to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| C1 | Typed values use one 32-symbol alphabet with no I, O, 0 or 1 (5 bits each), grouped in fours: setup secret 26 (130 bits), recovery key 160 bits, printed in broker/recovery's format (P2-8): eight groups of four key symbols, each followed by a GF(32) check symbol, 40 symbols, so a typo names its group (`recoverykey.go`, pinned to recovery's output by test vectors). Under the grid the card prints a four-symbol grid check code (`GridCheck`, HKDF of the seed), which recovery asks for to confirm a grid-only rotation. The vault passphrase is 7 words from EFF's large list (90.3 bits; §3.1 asks at least 80). The grid seed is 32 random bytes. | §3.1, CRED-8 | Constants in `card.go`. The card has no Wi-Fi (WIFI-del-e, #3365, D-178): the core serves none and only the enforcer holds the Owner network's password; `WiFiQR` stays for the claim sticker's enforcer setup network. |
| C2 | The setup code is 8 symbols (40 bits) derived from the setup secret by HMAC-SHA-256, so the card prints "the setup secret and its short setup code". It only pairs the owner's number (localui, rate-limited) and never unlocks anything. P2-2 uses the setup secret only through its code; ID-1's other use of it (re-running setup after a reset) belongs to recovery (P2-8), so it is printed as the **reset secret** on the recovery sheet, not on the card. | §3.1, ID-1, CRED-8, ONB-6 | `SetupCodeFor`. |
| C3 | The vault passphrase QR code holds the passphrase text itself, and `NormalizePassphrase` (lower case, single spaces) is the form the passphrase slot (P2-4) derives from. **For P2-4:** a page served over plain HTTP is not a secure context, so browsers deny it the camera; scanning "on the local page" needs a photo upload (`<input type=file capture>`) decoded on the box, or the phone camera app. A QR holding a URL with the passphrase would leave it in browser history and its cloud sync, so this package does not do that. The card tells the owner the path that works today: scan with the phone's camera app, tap Copy, paste on the Wi-Fi page. Conditions for P2-4: decoding photos is parsing untrusted images, so it runs in a sandboxed, no-network, short-lived process, never in the vault or broker; it needs a decoder (`rsc.io/qr` only encodes); typing stays first-class. | CRED-8, CH-6 | Payload format in `render.go`. |
| C4 | The paper grid is printed from `owner.GridCell` and `owner.GridLabels` (10x10, 6 digits, O6), so the card and the channel cannot disagree. | CH-4, CH-18 | Owner channel's grid constants. |
| C5 | `WaitMinutes` (3) is provisional until S1 measures power-on to the enforcer's setup page on real PCs and ONB-4's target is frozen. The quick-start starts from the enforcer's setup network and claims on the Owner network (§12.1 steps 1 and 4, WIFI-del-e). | ONB-4, ONB-7 | One constant; the quick-start reads it. |
| C6 | Boot keys are vendor documentation, not yet checked on hardware [Inference]; S1's checklist confirms them. | ONB-7, HW-6 | `BootKeys`. |
| C10 | The card prints the Wi-Fi page, the local page's one name in owner texts (CH-12, WIFI-del-f) (`BoxPage`, `https://agentos.internal/`, the page's name over HTTPS, WIFI-del-c) on its front and on the "Nothing happened?" side ("Wi-Fi joined but no page?"), so the owner can always get back to status, STOP, RESUME and sign-in. The core has no access point address (D-178). HTTPS, not plain HTTP: the enforcer installs the core's authority before the claim (§12.1 step 4), and the plain listener's redirect keeps only the path. The grid sheet says to keep it apart from the box and the card. | CH-9, ONB-7, HW-1 | `PageName`, `localui.DefaultPageName` and `pageca.DefaultName` must match (a test checks). |
| C7 | The card says, beside the passphrase, "If this drive was out of your hands, unlock it only on your trusted PC" (HW-5a's point-of-use text), and to keep the card apart from the drive (risk 10). | HW-5a, CRED-8 | Text only. |
| C8 | Out of scope for P2-2: provisioning a drive from a card (vault slots, grid seed into the vault: P2-4, P2-8), the DIY first-boot card (HW-1, §8.4), and rotating card secrets from the local UI (REC-4). `Generate` and `HTML` are what those packages call. CTRL-card adds the first-boot display and confirm (`display.go`, C12-C16). | HW-1, REC-4 | Later packages. |
| C9 | Reuse: QR encoding is `rsc.io/qr` v0.2.0 (BSD-3, encode only, no dependencies of its own, Go authors' encoder), vendored under `broker/vendor` so builds work offline (DEP-1) and recorded in DECISIONS. Its PNG writer's metadata URL is listed as an inert literal for the A9 static scan. The Wi-Fi QR uses `T:WPA`, which current phones use for WPA3 too; S1 checks that Android joins an SAE-only access point from it [Risk]. the word list is EFF's file embedded byte for byte, pinned by SHA-256 in a test. Output was checked to decode with OpenCV's QR reader during development. | — | — |
| C11 | The box keeps neither the recovery key nor the vault passphrase (P2-8, #35), so it cannot reprint them; the recovery sheet and the passphrase block each say so in plain words (arbitrator ruling on #35: no rewrap, a plain-words line). | REC-4, CRED-8 | `render.go`. |
| C12 | **Where the display lives (CTRL-card).** The brief names `broker/ownercard/` or a successor under `broker/localui/`; neither exists, and `broker/card` is the Owner Card package and already tier A in `tools/risk_tier.py`, so `Display` lives here. The local UI mounts `Display.Handler` behind its own address and pairing checks; wiring it into the setup page and agentosd is a release finding on the PR. | HW-1, ONB-7 | Move the file; the API does not change. |
| C13 | **Erase is best effort in memory, exact on disk.** Nothing of the card is written before the confirm; after it the display zeroes every byte value it holds (rendered sheet, grid seed, typed answers) and drops the card. Go strings (passphrase, recovery key, Wi-Fi and setup values) cannot be zeroed and stay in freed heap until reused. This holds only if the box has no swap or encrypted swap and no core dumps; the image must keep both off (a condition on the image, CTRL-uki). | HW-1 | An mlocked byte-only card type. |
| C14 | **Shown until confirmed, to the paired phone only.** "Show once" is read as: the page goes only to the phone that paired (Handler's `paired`), never cached (`no-store`), and is re-shown on reload until the confirm, since a reload would otherwise lose a card nobody holds yet. Wrong answers have no attempt limit: whoever can answer can already read the card. A cross-site POST (Origin of another host, or `Sec-Fetch-Site: cross-site`) is refused. | HW-1, CH-7 | A one-shot view would need a re-generate path instead. |
| C15 | **Confirm values.** One passphrase word and one recovery key group, positions drawn from the box's randomness, compared in constant time after the card's normalisation (case, spaces and dashes forgiven). Two values from different sheets prove the owner holds both the passphrase and the recovery sheet. | HW-1 | `Display.Confirm`. |
| C16 | **The page.** Print is offered first, then save as a file (the bare sheet, `Content-Disposition: attachment`), with a warning not to take a screenshot or photo (phone cloud sync). The controls are hidden in print. After the confirm every request gets 410 saying no copy is kept and that a new card comes from rotation (REC-4). Journal events are fixed strings; `Card` and `Display` format as placeholders, so no stray log line carries card text. | HW-1, ONB-7, REC-4 | `display.go`. |
| C17 | **Rotation mode (CTRL-card-rot).** `DisplayConfig.Rotate` makes the display show only the rotated parts (the rest blanked before rendering), titled as a rotation with "Until you confirm, your current card keeps working" and a cancel. The confirm asks a passphrase word and/or recovery key group of the new parts, or else one check value (setup code, grid check). `Discard` erases a waiting display for cancel or lapse (`ErrDiscard` from `Provision` does the same); once `Provision` reports `ErrInEffect` (part of the new card already written), the owner has just typed values back from their copy and the rotation is used up, so the display erases its copy as after a full confirm (`Confirmed` stays false), `Discard` returns `ErrInEffect`, and every later request gets 410 with the one step that finishes: keep the new card and the current one, and start a new card from the Wi-Fi page with the passphrase or recovery key from whichever card works. Not every part of the new card need be in effect (the setup secret and grid are stored after the slots, and a failed recovery-key write leaves the old key in effect), so the text never says to use the new card alone; the next rotation must replace every part this one rotated (recovery R14) (CH-12; #1090 review F1, F3). | REC-4, HW-1 | `display.go`, `render.go`. |
| C18 | **The discard hook (CTRL-card-rot-wire; #1090 security review R2).** `DisplayConfig.Discarded` runs once when a waiting display erases its card for any reason but a confirm or a card in effect: `Discard`, the page's cancel, a lapse, or `ErrDiscard` from `Provision`. It runs with the display locked, so it must not call back into the display; the box's page uses it to drop the vault process's pending rotation and the passphrase it holds. | REC-4, CRED-1 | `display.go`. |
| C19 | **The page authority on every card (OWN-card-ca, #3167).** `DisplayConfig.Authority` is the page authority's certificate (DER, public). `NewDisplay` refuses with `ErrNoAuthority`, before drawing any randomness, unless `CheckAuthority` reads it as the page's authority: a CA (`BasicConstraintsValid`, `IsCA`, `MaxPathLenZero`) under a critical name constraint permitting exactly `PageName`, as `pageca` makes it. That reading does not replace the phone's or `pageca`'s; it keeps the card from printing a stranger's fingerprint. The full card's front and every rotation sheet, whatever its parts, print the Wi-Fi page's name, its authority's fingerprint (`Fingerprint`: SHA-256 of the DER, upper-case hex in groups of four, two lines of eight; a test holds it equal to `pageca.Fingerprint`), the address-bar line and the trust line. The fingerprint comes from the display, not `Card`, so `Card` stays the secrets `wipeCard` clears; `card` imports no `pageca`. | HW-1, CH-9, REC-4 | `authority.go`, `render.go`. |
