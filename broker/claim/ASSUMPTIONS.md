# Box claim: assumptions

Built for CTRL-claim (BOARD.md) against SPEC HW-10 and HW-1 (D-102). Covers `broker/claim`, the claim gate in `broker/firstboot` (`ClaimedCard`) and the claim screen in `broker/localui`. Each row is a reading of the spec, with what changes if the reading is wrong.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| K1 | **Code format.** The sticker code is 16 symbols from the Owner Card's alphabet (no I, O, 0 or 1), 80 bits, printed `XXXX-XXXX-XXXX-XXXX`. Typing ignores case, spaces and dashes. The seller makes it with `NewCode` and seals it with `Seal` when preloading the box; the sticker's QR may be a link to `/claim?code=…`, which only fills in the form. | HW-10 | A different sticker format changes `NewCode`, `Normalize` and the screen's placeholder only. |
| K2 | **The box keeps no code.** The disk holds the code's salt, its cost (`KDF`) and two Argon2id verifiers, never the code: one of the whole code (domain "agentos claim v2") and one of its first 8 symbols (K9), both 32 bytes. The claim removes both and stores only a SHA-256 hash of the claimant token, so the sticker "unlocks nothing and dies at first claim". Online, 80 bits under a 5-try lock make guessing hopeless. Offline, a disk read is weaker than 80 bits: the prefix verifier lets the code be searched in two 40-bit halves, about 2^40 Argon2id evaluations each (2^41 in all, about 2^40 expected). At the production cost (`productionKDF`: 64 MiB, 3 passes, 4 lanes, about 50 to 100 ms each on the controller) that is about 2,400 controller-years, or on the order of a hundred GPU-years, since each guess needs its own 64 MiB. Who can read the disk: the seller, who knows the code anyway, or whoever obtains a leaked provisioning state and then claims the box over its Wi-Fi before the buyer. `Open` refuses a state whose cost is below `productionKDF` or above `kdfCeiling` (1 GiB, 16 passes), or that has no cost at all (a state from before the KDF), so a state cannot make guessing cheap or a single try ruinous; such a box is reinstalled and resealed. | HW-10 | A different cost changes the offline figure in proportion; a cost below the floor needs a new floor and a new figure here. |
| K3 | **Lockout survives restarts of the software, not of the box.** Every wrong code is saved before the answer goes out. After `MaxWrong` (5) the screen locks and records the kernel boot ID; only a new boot ID (the owner restarts the box) lifts it. Each lock halves the next boot's allowance (5, 2, then 1 per boot), so a thief who power-cycles gets at most a handful of guesses per restart. A save that fails locks the screen in memory (fail closed). This is the #1056 hint: the backoff is persisted. The sticker holder's reserve (K9) sits beside this count and never touches it. | HW-10 acceptance 3 | If the spec wants a time-based lock instead, `allowed` and the boot check change; the persisted counter stays. |
| K4 | **No claim state means the download path.** `Open` returns `ErrNoCode` when the box was never sealed: a box installed from the GitHub flasher pairs by the flasher's one-time QR instead (FLASH-1). `Seal` refuses a box that already holds state, so a seller cannot reseal a claimed box without reinstalling. | HW-10 | — |
| K5 | **No secret before the claim.** `firstboot.ClaimedCard` builds the card step (and so draws randomness for the Owner Card) only after the claim succeeds. Before it, `Hold` says the box waits to be claimed. The acceptance test scans a copy of the partition after a wrong code and a restart for anything drawn from a canary randomness stream, and checks none was drawn, and that no vault, setup key (`setup.key`) or unlock state exists. The vault process's `init -setup` makes the setup vault and its key only once `Claimed` reports the box claimed (egress K22). | HW-10, HW-1 | — |
| K6 | **Setup belongs to the claimant.** The claim sets an HttpOnly, SameSite=Strict cookie with the claimant token for the setup cookie's lifetime (7 days). While a claim is configured, `/`, `/setup` and every setup step redirect to `/claim` before the claim and refuse any phone without the token after it. A claimant who loses that phone before the card exists reinstalls (the "already claimed" path). | HW-10 | A recovery path for a lost claimant phone would be a new row. |
| K7 | **The journal gets counts only.** Claim events are fixed strings plus try counts; a typed code never reaches the journal or logs. | HW-10, CRED-8 | — |
| K8 | **Wired (CTRL-claim-wire).** `firstboot.Begin` opens the claim and routes the box (firstboot F15): a sealed box gets `ClaimedCard`, which the page hands `localui.Config.Claim` and `Config.Card`, so `/claim` and the card display sit behind localui's subnet, Host, same-origin and claimant checks (localui L35). `main` still hands setup mode no step (agentosd OC1), so the image path is unchanged until the page's process builds it. | HW-10, HW-1 | — |
| K9 | **The sticker holder always beats a lockout burner (R3).** `Seal` also stores a full-length (32-byte) Argon2id verifier of the code's first `PrefixSymbols` (8) symbols, under the same salt and cost as the code's verifier (K2), in its own domain. Each boot keeps a reserve of `ReserveTries` (3) for codes that start with those symbols: such a code is tried even while the shared count is locked, a right one claims, and a wrong one spends the reserve, saved before the answer (an unsavable count locks, fail closed), never the shared count. Every other code goes to the shared count as before. So another client on the Wi-Fi that posts a wrong code after every restart can lock the shared count but never the reserve, and the owner reading the sticker claims on the same boot. Chosen over limiting who reaches `/claim` because before the claim no phone is told apart from another. **Why a full-length, memory-hard prefix verifier (option (a) of the #1080 delta review, N1; coordinator's choice).** A short tag of t bits lets a burner find a reserve-spending prefix online in about 2^t free posts at a locked screen (the 16-bit tag fell in 44,913 posts), while any stored prefix data lets a disk read search the code in halves offline; no tag length makes both costs large, so the prefix verifier is full length and both verifiers are Argon2id. Online: while the reserve has tries, each post costs one Argon2id derivation (about 50 to 100 ms at 64 MiB, one at a time under the claim's lock), and a code without the sticker's first groups meets the reserve once in 2^40, so a burner needs about 2^39 posts, over a thousand years, to spend one reserve try; once the reserve is spent a locked screen answers without a derivation. Offline: the figures are K2's, about 2^40 Argon2id evaluations per half; that is an offline cost against the disk's verifiers, not an online one. The reserve-miss (423, locked) and reserve-hit (422) answers differ, which tells a client only whether it matched the 40-bit prefix, the same fact the reserve count shows. `TestALockedOutSprayNeverReachesTheReserve` sprays 2^20 codes at a locked screen (with the KDF swapped for a hash so it runs in seconds) and the owner still claims on the next boot; `TestProductionKDF` pins the production cost. Residual: each post while the reserve has tries costs the box one 64 MiB derivation, serialized, so a flood of posts slows every answer, the owner's included, but takes no try from the owner. A state sealed before the reserve has no prefix and no reserve. | HW-10 acceptance 3 | A per-boot reserve larger than 3, a different prefix length or a different cost changes the residual figures; any short prefix tag brings back the online burner. |
