# Agent-machine lifecycle: assumptions

Built for PLAN P1-4 against SPEC v0.12 (PR #15) on the broker skeleton
(PR #19). Each row is a reading of the spec, or a gap left for a later
package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| V1 | A machine is a read-only image plus a host overlayfs upper layer, served to gVisor with gVisor's own overlay off (`--overlay2=none`). gVisor's internal overlay keeps writes in an opaque file, so the broker could not snapshot files without a full checkpoint. | REV-1, ARC-5, S3 | Firecracker (if it wins on the N95) needs a block-device layer instead; only `vm/gvisor` and `vm/overlay` change. |
| V2 | Per-step snapshot = pause, copy the upper layer (reflink where the file system has it, otherwise extent by extent so holes stay holes, hardlinks kept), resume. Full checkpoint = the same plus `runsc checkpoint` while paused, so files and memory match. `runsc pause` does not flush the sentry's dirty pages of files the guest has mmapped, so a file-system snapshot can miss mmapped writes not yet synced; a full checkpoint holds them in memory. | REV-1 | Sync before copying if a guest workload depends on it. |
| V3 | "Step" is whatever calls `Manager.Step`. The guest plane (P1-7) calls it after each broker tool call, on the machine that made it; a failed Step is logged and does not fail the tool call (G4). | REV-1 | — |
| V4 | Rollback is allowed to the machine's own snapshots and to the snapshot it was forked from, nothing else, so a machine cannot load another machine's data. | REV-4, REV-5 | `inLineage`. |
| V5 | `fork(n)` is all or nothing: every fork is admitted on its own full budget (forks share no memory, S3) before the source is checkpointed. Forks keep the source's class. | REV-4, CAP-1, RES-2 | `Manager.Fork`. |
| V6 | `merge` is a three-way file merge of a fork back into the machine it came from, against the fork point. Any path both sides changed differently is a conflict and nothing merges. A directory one side removed or retyped while the other side changed something beneath it is a conflict too. Before merging, the destination gets a full checkpoint, so the owner can undo the merge with memory intact. Ownership and guest xattrs (e.g. file capabilities) count as changes. The merged machine restarts on the merged files (a file-system rollback), so its memory is not kept. Keep-the-winner (CAP-1) needs no merge: keep the fork, destroy the rest. | REV-4 | A live in-guest merge would need guest cooperation (P1-7). |
| V7 | Data labels (REV-5) are tracked here because snapshots carry data: a label only rises; rollback, rebuild and merge never lower it; forks inherit it; reading a diff raises the reader to the snapshots' label. Egress enforcement is not here. | REV-5 | REV-5 package. |
| V8 | Preemption (RES-1) pauses the guest, kills it, and returns once its cgroup is empty, which is what `admission.Preempter` requires (memory released). Nothing is copied on that path, so its time does not depend on what the guest wrote. The machine's layer stays on disk and `Resume` restarts the machine on it (cold). In-memory state since the last full checkpoint is lost. Checkpointing memory first would cost 2–4.5 s for an OpenClaw-sized guest (S3), too slow for a call. A kill that fails leaves the machine Running and still counted (disk and admission): preemption returns the error, and a retry kills again rather than reading it as stopped; a rollback, rebuild or resume that cannot kill keeps the machine's admission. A preemption that killed the guest without its lock records it Preempted even if the runtime cleanup then fails, since admission has already let its memory go (P1-4-killfail). The same holds for a failed start's cleanup: when `startFrom` was tried and the kill after it fails, the guest is recorded Running even if it failed before Running, so a failed `Create`, `Fork`, rollback, rebuild, resume or merge keeps its admission, and a failed `Create` or `Fork` also keeps the machine's record, so `Preempt` or `Destroy` can kill it again and its ID is not reused meanwhile. A fork undo whose `Destroy` fails keeps that fork the same way. A guest whose kill failed for a reason other than being alive (say a cgroup removal) thus holds its admission until a later kill succeeds: over-counting is the safe side of RES-2 (P1-4-killfail-create). Preemption does not wait for an operation holding the machine; target and measurement: P2-5 (budget/ASSUMPTIONS.md R5, R6). | RES-1, LOOP-1 | Checkpoint-then-kill as an option once the target is frozen. |
| V9 | A preemption that lands between a machine's admission and its start withdraws the admission; the machine does not start (`ErrRevoked`). | RES-1 | — |
| V10 | Every machine runs in its own cgroup v2 group: `memory.max` is the declared budget, `memory.high` is 1/16 below it (throttle before the stall S3 measured), swap is 0. The manager refuses to open without a cgroup parent unless told it is a test. | RES-2 | `cgroup.Child`. The 1/16 margin is unmeasured. |
| V11 | PSI comes from the machine parent group's `memory.pressure` (else `/proc/pressure/memory`). If PSI worked and then fails, it reads as +Inf, so only foreground is admitted. A host with no PSI at start-up admits on the budget alone. `-max-pressure` defaults to 10 % (unmeasured; size on the N95). | RES-2 | Flag. |
| V12 | ARC-2: the control-path packages still cannot start processes. `agentosd` (the composition root) opens the machine plane and hands it to admission as a `Preempter`. Only `vm/gvisor` starts a process, and only the configured runsc (`TestOnlyRunscIsExecuted`). | ARC-2 | `daemon/arc2_test.go`. |
| V13 | Broker restart: machines come back `stopped` with layers and snapshots intact; leftover sandboxes are killed. `Resume` restarts from the newest snapshot. | ARC-4 | — |
| V14 | Destroy keeps a machine's snapshots until pruned by policy (`prune.go`, budget R10). | RES-4 | `PrunePolicy`. |
| V15 | Each machine gets its own broker services directory, `Config.Services`, mounted read-only at `/run/agentos` with gVisor's `--host-uds=open`; the sandbox has no other network. The directory is opened before every start or restore and closed on destroy. A fork gets its own directory; a connection it inherits from its source reads EOF after restore and never speaks for the source (integration tests). `--host-uds=open` is sandbox-wide, but a host socket file planted in the image is not reachable from the guest (`TestIntegrationHostSocketInImageIsUnreachable`). What bounds it is the set of host paths in the bundle: the bundle tests count a mount as a bind when its type is `bind` or an option is `bind` or `rbind` (whatever its type), allow only the services directory at its mount point, and pin `--host-uds` to `open` in every flag form (A14-r1); P2-1's image build should still assert the image holds no socket files. Each machine's lineage (OP-1) is its root's ID plus a creation nonce, so a reused ID gets a new one; `DataLabel` gives egress a fail-closed label. | ARC-6, REV-5, OP-1 | — |
| V16 | Layer paths are resolved beneath the layer root without following any symlink; a path under a symlink or other non-directory is absent, as for the kernel overlay. An image symlink to a host path (Debian's `/var/run -> /run`) never leads a diff, merge, or copy into the host. | REV-1, REV-4 | — |
| V17 | Layer copies keep only regular files, directories, symlinks, and 0/0 whiteouts; anything else (device nodes, FIFOs, sockets) fails the snapshot with the path named. Of overlayfs's xattrs only a valid opaque marker is kept; redirect, metacopy, and origin are dropped, and machine roots mount with `redirect_dir=off,metacopy=off,index=off`. Setuid bits and owners are kept because guests need them (REV-1), and are inert on the host because of V18. | REV-1, ARC-5 | — |
| V18 | Machine roots mount `nosuid,nodev` and are made private right after mounting. That cannot stop the mount event itself from reaching peers when the state directory sits on a shared mount, so `agentosd` must run in its own mount namespace (systemd `PrivateMounts=yes`), where mounts do not propagate to the host. The broker's state directory (layers and snapshots) must be on a file system mounted `nosuid,nodev` (P2 image build). | ARC-5, CRED-2 | P2 host image: unit file. |
| V19 | Snapshots are admitted against measured disk, as memory is (arbitrator ruling on #23): a snapshot is taken only if copying the machine's layer (allocated bytes; holes and hardlinks cost nothing extra) leaves the state disk's RES-4 reserve free (`-disk-reserve-mb`, default 2 GiB, unmeasured), with a per-machine byte cap (default: the machine disk budget, V30) and a 200,000-inode cap. Otherwise the step is refused with a "disk budget" error the guest can act on (delete files, roll back) and nothing is truncated or dropped. The guest's own writes are stopped by its quota (V30). | RES-4, REV-1 | Size the reserve on the N95 (P2). |
| V19a | Every copy is reserved against the same budget before it starts, not only snapshots: a full checkpoint counts its layer plus the machine's whole memory budget; fork(n) reserves n copies of the layer before checkpointing and holds them until every fork has started; a merge reserves the merged layer and dst's restart before checkpointing dst; a rollback reserves its restore before stopping the machine. Reservations are serialized and held ones count against later checks, so concurrent copies cannot together eat the reserve. A refusal leaves machines running as they were. While a copy runs its bytes count twice (used and held), an overestimate. | RES-4 | — |
| V20 | CI's gVisor is pinned by SHA-512, trust on first use from the same origin; it is not a signature check. | DEP-1 | Verify the release signature when the P2 image vendors runsc. |
| V21 | Known gaps: a `Preempt` whose kill fails leaves the machine stopped while admission still counts it, until it is destroyed; `Manager.Diff` with an empty requester (broker or owner callers only) raises no label. | RES-1, REV-5 | Small. |
| V22 | Every machine's cgroup has `memory.oom.group=1`: an OOM kill takes the whole machine, never part of it. | RES-2 | — |
| V23 | A machine's console reaches `console.log` through a pipe the broker reads (`gvisor.keepConsole`): at 4 MiB the log becomes `console.log.1`, replacing the older one, so a machine keeps at most `vm.ConsoleMaxBytes` (8 MiB) of console whatever its guest prints. A broker restart kills running sandboxes (V13), so no guest outlives its reader. | RES-4 | — |
| V24 | `CreateSeeded` writes broker-chosen files into a fresh machine's layer before its guest first runs (root-owned 0644, local clean paths only), admitted against the disk budget and the layer byte cap like any copy. This is how a replay hands its guest the tree under evaluation. The seed is held in memory: a rebuild writes it again, but a broker restart forgets it. IDs starting `eval-` are kept for replay machines: `Create` refuses them, `Fork` neither forks nor makes one, and `Rollback` and `Merge` refuse them. Every write of a seed (create, rebuild) reserves the disk first. A non-empty seed needs a private machine (`ErrSeedLabel`): the managed tree is derived from owner tasks and no file carries a public mark yet (compile K7); forks inherit the label. | LOOP-5, RES-4, ARC-6, REV-5 | A public mark on seed files lets a public machine take a seed whose every file came from a public candidate. |
| V25 | A snapshot taken while a preemption begins is discarded with `ErrPreempted`: Preempt marks the machine before it kills the sandbox, and `capture` checks the mark after the copy and checkpoint return, before it writes `meta.json`. A runtime that reports success on a killed sandbox therefore never publishes a truncated image, and a mark not seen means the kill came after the image was whole (Security R2 on #124). A snapshot whose resume then fails is withdrawn as well, so a snapshot operation that returns an error never leaves a published snapshot (#134 CI). | RES-1, REV-4 | `Manager.capture`, `takeLocked`. |
| V26 | **Deletion reach (CAP-3).** `ForgetSince(lineage, T)` takes back from a fork lineage what it may hold since T: each machine goes back to its newest usable snapshot taken before T (memory too from a full checkpoint; a stopped or preempted machine gets the layer on disk and stays stopped), or to a fresh layer from its image when none exists; then every snapshot of the lineage taken at or after T is deleted, those of destroyed machines and fork points included (metadata first, so a crash part-way leaves an unpublished directory `Open` drops). Snapshots now record their lineage; an older one whose machine is gone is deleted when taken at or after T, whatever its lineage, and an older one is also of the lineage named by its machine ID (the lineage load gives a pre-lineage machine), so a forget of that lineage reaches it after its ID was taken by a machine of another lineage (#1660). Labels do not fall. Known gap: a machine of another lineage that read a lineage snapshot through `Diff` is not reached. A repeat after success rolls back work done since; recall's reach records the reset and does not repeat it. A snapshot is dated when its capture completes, not when it starts, so a record handed to the machine during the capture cannot land in a snapshot dated before it (#59 L3 3). `ResetPlan` measures, without changing anything, the oldest restore point and the files changed since it (overlay `Diff`; memory not measured), which recall counts as work to ask about (recalltool W10). A running machine restarts on reset, opening its services again, so its unanswered owner messages are handed out again (guest G5). While `Config.Contained` reports a lineage (it holds a record the owner deleted, asked or unanswered), its machines are not forked or merged (`ErrContained`). | CAP-3, REV-4, REV-5 | — |
| V27 | **Sleep checkpoints (PE7 part 1).** `CheckpointAndStop` pauses a running machine and takes a full checkpoint marked `Sleep`. That checkpoint records the machine's start count and a SHA-256 over its files and memory image (`treeHash`). The machine is then stopped while still paused, so nothing runs after the checkpoint, and its memory goes back to admission. A sleep that fails (the checkpoint, the machine record's save, or the stop) withdraws its checkpoint, as `takeLocked` does (#137), so an error never leaves one a wake could restore; a guest not yet stopped runs on. `ResumeFromCheckpoint` restores only that machine's own sleep checkpoint, and only when it is still the newest snapshot, the machine has not started since (any start, including a fork restart or merge, raises the count), and the hash matches. Otherwise, or if the restore fails, the machine resumes cold on its layer, on a context of its own bounded by `ColdResumeFor` (1 minute) so a restore that ran out the caller's still starts it (L3 on #149), and the result names the reason by a fixed class (`ColdNotSleep`, `ColdNewer`, `ColdStarted`, `ColdChanged`, `ColdFailed`) for the sleeper's wake journal line (potency R1 on #147). The sleep checkpoint is deleted after one attempt either way. The owner's own checkpoints and steps are never restored or deleted by it, and the label never falls. The hash sits in the snapshot's `meta.json`, on the same broker-only 0700 store as the checkpoint, so it catches corruption and any writer without broker rights, but not one that can rewrite the store. | REV-1, REV-5, RES-1 | A signed or keyed hash if the snapshot store's trust changes. |
| V28 | Worker machines (`wk-`, CAP-8) are made only by `CreateWorker`, in a live non-worker machine's lineage; they get no guest services; they fork into workers only and are never merged; `Exec` runs a command only in a worker, holding its lock, through a runtime that implements `Execer` (gVisor: `runsc exec`), after raising the worker to the caller's label and refusing a caller labelled below it (`Command.As`); it waits at most `ExecGrace` past the timeout for a runtime that ignores cancellation. See workers/ASSUMPTIONS.md. | CAP-8 | `vm/worker.go`. |
| V29 | **CPU, I/O and process limits per machine (SR2-4).** Every machine kind, `wk-` workers included, gets `cpu.weight` and `io.weight` by admission class (foreground 1000, accepted 100, experiment 1, an unknown class the least; a `wk-` worker never more than accepted, so a foreground agent's builds cannot crowd out the agent itself) and `pids.max` 4096 (`MachineLimits`); `Child` refuses a machine without a process cap and both weights. Weights compare machines inside the pool; the pool as a whole weighs 100 against the broker's 1000 (budget R12), and its own `pids.max` bounds all machines together (budget R14). A class is fixed at creation, so a machine keeps its weights until it is next started. 4096 tasks is a judgment, unmeasured: a gVisor sandbox's host tasks are the sentry's threads plus systrap stub threads for the guest's, so it bounds a fork bomb well below `memory.max` while leaving room for a parallel build in a worker. CI's integration job shows the kernel refusing a fork past the cap. Check the cap against a worker build and OpenClaw's thread count on the N95 run (A2). | RES-1, RES-2, CAP-8 | `vm.MachineLimits`, `vm.MachinePids`. |
| V30 | **Per-machine disk quotas (SR2-3).** Every machine, workers (`wk-`), builders (`lb-`), replay machines and forks alike, writes under its own Linux project quota: its layer and overlay work directory live in `machines/<id>/disk`, tagged with a project of its own (persisted in its record, `Machine.Project`) before any layer is written, with hard limits `MachineDiskBytes` (`-machine-disk-mb`, default 8 GiB, unmeasured) and `MaxLayerInodes`. The machine's record, runtime files and console stay outside it, so a full quota cannot stop the broker recording the machine. The overlay is mounted without `CAP_SYS_RESOURCE` (`quota.Enforced`), because overlayfs writes its upper layer with its mounter's credentials and ext4 lets that capability past a hard limit; the broker's own copies (restores, merges, seeds) are made with it and are admitted by V19a instead. A write past the limit fails in the guest with EDQUOT on ext4 and ENOSPC on XFS, which uses a full disk's errno for project quotas; nothing in the broker infers "quota reached" from an errno, and a test that does pairs it with the project's usage (`quota` tests). Destroy clears the project's limits. Every resume on the layer it has tags the whole layer again (`quota.FS.Tag`), since a layer written with quotas off, or copied or restored with its tags lost, would otherwise pass project 0, which no limit covers, to what the guest writes in its directories. A restart never gives a new machine the project of a directory left by a creation cut short. Layers from before this layout are not migrated (pre-release). The broker measures a layer (`overlay.Measure`, for its caps and snapshot, fork and merge reservations) through directory handles, never host paths, so how long a layer's paths are never makes the measure fail; it does not cross into another file system mounted inside the layer. A layer the broker cannot copy, because the copy walks host paths (`overlay.Copy`), is over the cap: nested more than 256 directories deep (`overlay.MaxTreeDepth`, CAP-8c's depth), or with a path that would reach the host's path limit (4096 bytes) under the longest root any copy of it can have (the layer of a machine with a 40-character ID, or a snapshot's), so a layer one snapshot accepts no later restore or fork refuses (L3 MUST-A on #174). It is refused with `ErrQuota` in text that names no host path, and the machine keeps running (security R4 on #166, L3 MUST-1 on #174). What must checkpoint first (a step, a fork, PE7 sleep, a merge) is then refused, never run unchecked; rollback, erasure and destroy never measure the live layer, so such a machine can always be undone; such a worker parks as one over its cap does, stopped without a snapshot, as does a worker whose snapshot fails for any other reason (logged), so a park always gives its memory back; and a deletion in it stands with the worker stopped until a deletion flattens it (security M4 on SR2-3i). With `-disk-quota=off`, or on without quotas (no machine starts), STATUS says so (security R2 on #152). Known gap: tagging a layer on resume (`quota.FS.Tag`) still walks host paths, so a layer with a path past the host's limit does not start on its own layer, and that failure's text names a host path; the worker tools answer it as a ref with the detail in the broker's log (SR2-3f, workers K21); other tool families are row SR2-3g. Rollback restores a layer that does start. | RES-4, REV-1 | `quota`, `Manager.limitDisk`. |
| V31 | **The reserve holds against running guests (SR2-3).** What running guests may still write, each one's budget less its quota use plus its console allowance, is counted like a held copy: a machine starts (create, fork, resume, rollback, rebuild) only if its own fits above the reserve beside the others (`ErrDiskFull`), and every copy is admitted only above all of it. A stopped machine writes nothing and is not counted; one whose kill failed, at a stop, a failed creation or a broker restart, stays counted until a kill succeeds (security F1 and L3 on #152); the count is by project, so reusing the machine ID does not drop it. The state file system must have project quotas (ext4 or XFS, `prjquota`); `agentosd` refuses to run machines without them unless started with `-disk-quota=off`, which it logs, and where guests can fill the disk. The broker's own copies into the snapshot store are admitted by V19a rather than limited by the file system; a separate machines volume (P2-1, SR2-3i) also takes them off the journal's disk. | RES-4 | P2-1 image: state file system with `prjquota`, or a machines volume. |
| V32 | **runsc's own messages never reach the guest (SR2-3h, SR2-3m, SR2-3n).** In runsc release-20260928.0, `util.Errorf` (and `Fatalf`, exit 128) always writes its message to stderr and, when `--log` is set, a JSON error line to that file; info lines go only to `--debug-log` (else discarded); the guest's in-sandbox pid is written to `--internal-pid-file` only after the command starts (read from `runsc/cmd/util/util.go`, `runsc/cli/cli.go`, `runsc/cmd/exec.go` at that tag). `runsc exec`'s stderr is the guest command's too, so `--log` alone cannot keep runsc's text off it. `gvisor.Exec` gives each exec its own `--log` and `--debug-log` files (0600, removed after) and treats the exec as runsc's failure when that `--log` is non-empty or the pid file is empty: it answers an error and no output (not a result, so the guest's exit code and stderr are never runsc's), and the worker tools turn that error into a ref (workers K21). The failure's messages (error log, debug log, stderr, each clipped to 16 KiB) go to `exec.log` in the runsc state directory (broker-held, 0700), 0600, rotated at 1 MiB to `exec.log.1` through `keepConsole`, so the two stay within 2 MiB plus one entry. A successful exec logs nothing. A Go runtime panic, fatal error or fatal signal (`SIGxxx:` and `PC=`) in runsc after the guest started writes its trace to runsc's fd 2 with no `--log` line (runsc's `--panic-log-fd` is refused for non-internal commands) and exits 2. So the guest's stderr is not runsc's fd 2 (SR2-3n): `gvisor.Exec` passes a pipe of its own as runsc's fd 3 with `exec --pass-fd 3:2`, which in that release sets the guest's fd 2 to the host fd 3 over the default `os.Stderr` (`fdMap[mapping.Guest] = file` in `runsc/cmd/exec.go`; `FDMappings.Set` in `runsc/cmd/sandboxsetup/fdmappings.go` refuses only negative numbers), and reads runsc's own fd 2, clipped to 16 KiB, apart. No guest write can then split, mimic or crowd out runsc's trace, and none of runsc's stderr reaches the guest; Exec treats as runsc's failure any failed exec with anything on runsc's own stderr (any non-zero exit, a kill, or `ErrWaitDelay`), read before or after its context ended (Security S1 on #391, V34, P1-4-flake-crashed); an exit 0 with text stays a result, and logs that stream's first 16 KiB. A guest that exits 2 keeps its output whatever it wrote, a Go program's own panic included. The guest's stderr pipe is read to its end but no longer than `ExecWaitDelay` past the context's end or runsc's exit, as os/exec bounds stdout. Known gaps: a guest command that cannot start (a missing program) reads as fixed text, not runsc's (V33, SR2-3p); and runsc verbs other than `exec` still put stderr in their errors, which reach the guest only as refs (SR2-3g's filter, workers K21). | RES-4, CAP-8 | A fixed-text sentinel for a command that did not start; re-read the four files when the pinned runsc changes (V20); a runsc that ignored `--pass-fd 3:2` would put the guest's stderr on runsc's stream, which Exec never answers, so it would withhold output, not leak runsc's text; CI's `TestIntegrationWorkerExec` runs the pinned runsc and fails if the guest's stderr does not arrive through Exec's pipe. | V34 | **A deadline answers partial output unless runsc wrote (P1-4-flake).** When Exec's context ends while runsc still runs, Exec kills it, so its exit is the kill's (-1), never 2. | V35 | **runsc's exit 128 is runsc's fatal, not the guest's (P1-4-flake-exit128).** In runsc release-20260928.0, `runsc exec` reaches `util.Fatalf` (exit 128, its message on stderr and as a `--log` JSON line) on three paths: `loading container failed: `, `parsing process spec: ` and `failure to start child exec process`; its ordinary failures are `util.Errorf` (exit 1). Each of these runs before runsc writes the pid file (V32, SR2-3q); the third is the detached exec's path, which neither `Exec` nor the corpus replay takes.
