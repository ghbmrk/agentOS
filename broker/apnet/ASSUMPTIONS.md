# apnet: assumptions

Built for CTRL-claim-ap u1 (#1185) against HW-1, CH-7, HW-10 and ARC-1. `broker/apnet` is the card's Wi-Fi network as the page reports it and as agentos-ap serves it. It imports only the standard library, so agentosd can take it without linking the card or the claim (ARC-2). Each row is a reading a later change could overturn.

| # | Assumption | Basis | If it changes |
|---|---|---|---|
| N1 | **The page reports the card's network before the confirm latches.** The card step's provision (`localui.ServeCardNet`) first sends the card's Wi-Fi name and password to agentosd (`page_setup_ap_net`), which writes them root-only (0600, durable rename) to `/var/lib/agentos/ap-net.json`; only then does it provision, and the latch saves after that. So agentos-ap, which serves this file once it sees the latch or the owner state, always has the network when the confirm appears. A report that fails fails the provision: nothing latches and the card stays shown for a retry. A later report replaces the last, since a reset card is a new card. The op is served for the whole setup session until finish, whenever the page runs the card step, not only while the card is shown; a report after the confirm replaces the network, and agentos-ap serves the new one (Down then Up). | HW-1, CH-7, ARC-1 | If the confirm moves out of the page, whatever confirms must write the file first. |
| N2 | **Only a network a card prints is taken.** `Validate` accepts exactly `AgentOS-` plus four card symbols and a password of 16 card symbols in four groups, the shape `card.Generate` makes; `Parse` also refuses unknown fields and trailing data. So the page cannot make the root loader serve the setup network's name, an open network, or anything hostapd would read as more than a name and a key. The alphabet is a copy of `card.Alphabet`, pinned by a test. | CH-7, ARC-2 | A new card format changes `Validate` and its test together. |
| N3 | **A forged latch serves only the page's own network.** The latch is the page's file, so a compromised page can mark the card confirmed early. agentos-ap then burns the setup network and serves the network the page itself reported; it gains nothing it could not get by confirming, and the claim code still guards the claim. This does not widen #1385 (the page can forge "claimed"), which stays open as filed. | HW-10, HW-1 | If the latch moves to a root-owned file, the loader can trust it and this row goes. |
| N5 | **A Wi-Fi rotation rewrites the file (REC-4, #1191; replaces N4).** Once the vault process commits a card with a new Wi-Fi password, or may have (409, or no answer: the owner keeps the new card), the page hands its network to agentosd (`page_rotate_ap_net`, the confirming session's token). agentosd takes only a network `Validate` accepts with the file's current SSID, only when the file exists, and replaces it durably (0600, rename); it logs no password. agentos-ap sees the change at its next poll (2 s) and brings the access point Down then Up, so the old password is off the air from then on, including after restarts. A failed hand-off leaves the old password served and the done page says so. `APLoader.Rekey` stays unwired. Residual: a compromised page with a live session can write any card-shaped password under the same SSID (availability only; release finding on the PR). | REC-4, CH-7, ARC-1 | If agentosd learns the committed card's Wi-Fi from the vault process, the hand-off binds to the commit instead of the page. |
