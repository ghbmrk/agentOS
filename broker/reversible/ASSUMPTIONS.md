# Reversible conversions (REV-3): assumptions

Built for package P2-rev3 against SPEC v0.12, on the grants gate (P2-grants), the owner channel (P1-5) and the journal (P1-1). Each row is a reading of the spec, or a gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| RV1 | **What is built.** Two of REV-3's four conversions are built. The first is a *delay*: an approved effect is held for an undo window, and UNDO cancels it. The second is a *stage*: an approved effect is first made as a reversible copy (a draft, a scheduled send in the owner's account, a staging copy), the effect itself runs when the window ends, and UNDO cancels the effect and runs the stage's inverse. "Drafts instead of sends" is a stage whose operation is a draft. *Shadow runs* are not built for effects, because no adapter offers a sandbox to shadow against. For learned changes, the replay evaluator (P3-1a) is already the shadow run. | REV-3 | An adapter with a sandbox adds a third form. |
| RV2 | **Only owner-approved effects are converted.** A pre-allowed effect still runs at once, because ADP-9 says pre-allowed effects run "without approval and without notification", and an undo window nobody hears about undoes nothing. ADP-11 replies keep their own queued window. Secrets (CRED-6) are never held: `Check` refuses a form on a secret operation, and the gate applies a form only while the granted verb is in the irreversible class. | REV-3, ADP-9, ADP-11, CRED-6 | Converting pre-allowed effects needs a digest-only UNDO, which comes with CH-15's digest. |
| RV3 | **Forms are declared by the adapter, next to its verbs.** `grants.Config.Forms` maps executor → operation → `reversible.Form`. `New` keeps only the forms `reversible.Check` accepts against `Config.Declared`, and logs and drops the rest, so an operation with a bad form is asked with no undo window, as before. Check's rules: the operation is declared, in the irreversible class and not a secret; a stage and an inverse come together, differ, and are declared on the same executor at a reversible verb (so running them without asking is what ADP-2 already allows); the window is 1 min to 24 h, with 10 min (the ADP-11 window) as the default. A form never adds an operation an agent can request. | ADP-1, ADP-2, REV-3 | `reversible.Check`. |
| RV4 | **The undo window is the broker's to promise.** The gate sets the approval item's `UndoWindow` from the form, or to zero, and ignores any window a `Verifier` reports, so the CH-12 line "undo within 10 min" holds only where the gate actually holds the effect. The window is part of the line the recheck compares (GR8). | CH-12, OP-3 | — |
| RV5 | **The owner channel holds, the gate waits.** When the owner approves an item with an undo window, the channel queues it under its own UNDO ID, records it for a restart (`QueuedRef.Held`), and returns the approval with `Decision.Hold` and `Until`. The confirmation reply carries the run time and the ID (CH-16): `Approved A. It runs at 12:10 unless you reply UNDO K7.`. A batch reply gives one ID per held item and the earliest run time, and stays within three segments at 20 items. The gate keeps the intent pending ("approved; held for the owner's undo window until 12:10 UTC") until `DueAutoReplies` releases it; it then records the approval and dispatches. An item that cannot be held (no free ID, or the restart record cannot be saved) is denied (`Why` "not held") and the reply says so, so nothing runs without the undo its request promised. Holds count toward `MaxOpen` while they wait. | CH-12, CH-16, OP-3 | `owner.holdLocked`, `grants.hold`. |
| RV6 | **UNDO, STOP and restart.** `UNDO <id>` inside the window denies the intent (`Why` "undo"), with the reply `Cancelled K7. It did not run.`. STOP keeps a held effect from being released, the same as an ADP-11 reply, so its window can pass during the STOP and UNDO then reports it is past its window. A restart cancels every held effect (`Why` "restart"), and the boot text lists them as `Approved actions not run: K7`. Held approvals are not carried over a restart, because the approval itself is in memory (GR8). The recheck's freshness (`Fresh`, GR8) counts from the release, not from the owner's YES. | CH-16, OP-3, OP-4 | Persist held approvals if restarts during a window cost real work. |
| RV7 | **Stage semantics.** The stage runs as soon as the owner approves, as `<id>/stage`, with the effect's params plus `reversible_parent`. A stage that fails does not cancel the effect: it still runs after the window, as approved. So the adapter's own operation must work whether or not its staged copy exists, and must complete that copy when it does exist (sending the draft, or confirming the scheduled send), found by the stage intent's ID. On a cancel (UNDO or restart), the gate waits for any stage attempt in flight. If the stage succeeded, the gate runs the inverse as `<id>/unstage` with the stage's evidence in `reversible_staged`. Following #69's organize undo, the adapter applies the inverse only if the staged copy is still what the stage made, and otherwise returns not-applied. The copy is then left alone, and the owner gets a fixed line: `UNDO K7: it did not run, but its draft or staged copy could not be removed, so it was left as is.`. | REV-3, ADP-2 | Adapters (P2-6) implement stage, inverse and completion. |
| RV8 | **Derived intents come only from the gate.** A stage or inverse is journaled like any effect (REV-2). It carries origin `broker:reversible`, and the gate allows it only if the gate itself submitted it (an in-memory set), its operation is the one the form names, and the parent is in the right state: held, for a stage, or denied, for an inverse. Any other intent with that origin is denied, whatever its params name. Neither operation needs a grant of its own, because the owner approved the effect they belong to. Both do need the account's adapter grant to be live: after a PAUSE or REVOKE the inverse is refused, and the owner gets the RV7 line. | REV-2, ADP-1, OP-1 | — |
| RV9 | **Reuse.** `reversible` is pure data and validation. It imports only `journal` and `verb` and is on the ARC-2 control path's allowed list. The hold reuses the owner channel's ADP-11 queue (IDs, restart record, STOP rule, UNDO parsing) rather than adding a second one. #69's organize undo is a different shape: it restores, after the fact, effects that already ran, using their journaled prior state. Nothing here depends on it, and organize operations are reversible, so `Check` gives them no form. Its "only if unchanged" rule is the one RV7 asks of inverses. | ARC-2, ADP-2 | — |
| RV10 | **Not covered here.** UNDO for effects that already ran is not covered; it comes with the digest (CH-16 via ADP-2's organize line, #69). Neither is the local page's view of held effects (P2-2), or wiring `Config.Forms` from real adapters' declarations (P2-6/P2-7). No adapter on main declares a form yet, so nothing on the box is held until one does. | CH-16, ADP-2 | Later packages. |
