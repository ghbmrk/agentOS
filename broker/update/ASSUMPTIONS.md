# Release signing and update verification: assumptions

Built for P4-3 (BOARD.md) against SPEC v0.12. Covers `broker/update` and
`cmd/agentos-release`. Each row is a reading of the spec, or a gap left for a
later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| U1 | TUF is go-tuf v2.4.2, the reference Go implementation, vendored and hash-pinned. Versions before 2.3.1 accept a role threshold of 0 (GHSA-fphv-w9fq-2525) and panic on malformed metadata (GHSA-846p-jg2w-w324), and 2.3.1 needs Go 1.25, so the broker module moved from go 1.22 (out of support) to `go 1.25.0` with `toolchain go1.26.8`. go-tuf brings sigstore's signature package, go-securesystemslib's canonical JSON, and protobuf; none runs at boot or contacts anything (A9 static scan passes; the vendored doc-comment and error-message URLs are listed in `inert_literals`). Only `update` and `cmd/agentos-release` import it; `agentosd` stays third-party-free (ARC-2). | UPD-8, DEP-1, ARC-2 | Bump go-tuf with each advisory. |
| U2 | Roles: root and targets are offline, held by maintainers, each with a k-of-n threshold; snapshot and timestamp are single online keys used by a scheduled `refresh`, which cannot add or change a release. Defaults: root and targets expire after 365 days, snapshot 7 days, timestamp 1 day. Root rotation needs the old root threshold and the new one. A check that accepts a rotation reports the new root version (`Result.RootRotatedTo`) so the digest can log it (Security R3). All keys are Ed25519. | UPD-2, UPD-8 | Expiries are constants in `repo.go`. |
| U3 | The box refuses a root or targets threshold below 2 (`Options.MinThreshold`; a lower setting counts as 2), so one stolen key cannot sign a release even if a root said 1. One key listed under two key IDs counts once, and a threshold of 0 for any role is refused (both go-tuf behaviour, pinned by tests). Every root in the rotation chain must meet it, and the box saves no root past a weak one. A single maintainer meets this with several keys held apart (SPEC open question 6, key custody, is still open). | UPD-8, §16 q6 | Mark decides custody. |
| U4 | Offline (`Options.Offline`, a drive): signatures, thresholds, root rotation, metadata version rollback, and "newer than installed" are all checked; no expiry is, including root and targets, since a drive can be months old. The release is `Fresh() == false`; `Commit` records the manifest path and SHA-256 and leaves the freshness check pending, and the owner sees `OfflineNotice`. The next online `Check` settles it only after the whole check succeeds: `FreshnessConfirmed` if the fresh targets list that exact manifest, otherwise `FreshnessFailed` (the check stays pending; the owner sees `NotConfirmedNotice`). Online, expired timestamp, snapshot, targets or root metadata is refused. **Limits.** Offline, a revoked key stays usable for drives signed before its revocation until the box next sees a newer root: a drive carries its own metadata, and nothing offline says the key was revoked. A box's local saved metadata blocks rollback below what it has seen, but a box restored from an older disk image loses that; P2-4b's TPM NV monotonic counter (egress V6) is the anchor the updater should bind the installed version to. Offline, a drive whose newest root expired more than 180 days ago (`MaxOfflineRootAge`, by the box's clock) is refused with `ErrDriveTooOld` and `DriveTooOldNotice` unless `Options.AllowOldDrive` carries the owner's tier-4 override (Mark, 2026-10-05): the updater sets it only after the owner approves at tier 4 (code-generator code plus local confirmation) for that drive and that check, never from configuration or a lower tier. **Clock.** Online expiry trusts the box's clock (`Options.Now`); a clock set back lets a frozen mirror's expired metadata pass. A floor (never earlier than the newest accepted timestamp's signing time, or a TPM-backed time) belongs to the updater. A clock far in the future refuses everything as expired (tested). | UPD-8, DEP-4, A14, HW-5a | Checking root or targets expiry offline would refuse old drives. |
| U5 | A release is one target, `releases/<version>.json`, holding the `/usr` verity root hash and the target paths of its boot files and images; every named file must be a signed target or the box refuses the release. Versions are positive integers and only go up, in the tool and on the box. `*Verified` is only made by `Check` (sealed; a zero or hand-built value is refused by every method with `ErrNotChecked`), so activation and the PCR-policy signing in P2-4b (its T4) can require one. `Fetch` writes a file only after its signed length and SHA-256 match, and syncs the file and its directory, as every metadata write does. | UPD-1a, UPD-8, HW-5a | — |
| U11 | One type: `change.Pipeline.ProposeRelease` takes the `*update.Verified` that `Store.Check` makes, and refuses nil or a zero value. `Version()` is the version as a decimal string and `Images()` every release file with its signed SHA-256, so release files live under `host-image/` or `guest-image/`, the pipeline's namespaces. `Security()` is false unless `WithAttestations(atts, own)` found `SecurityAutoStage` satisfied; the manifest flag alone never sets it. #34's stand-in `Verify` is gone; its tests are ported (threshold, images only, one key once, strict decoding). | CHG-3, UPD-8 | — |
| U6 | Channels: a stable box takes only stable releases, a fast box takes both, a pinned box does not check for automatic updates. Soak and cadence (UPD-5), quiet windows (UPD-6) and the journaled update intent belong to the updater, not here. | UPD-4 | The updater package. |
| U7 | Attestations are DSSE v1 envelopes (written out in `attest.go`; the go-securesystemslib `dsse` package would also vendor `x/crypto/ssh`) over a statement naming the release's manifest path and SHA-256, the result, channel, hardware (vendor, model, firmware) and versions, each a value the public attestation schema lists (`broker/attest`, OSS-4, P4-4), the attestor's Ed25519 key, and an optional operator label. **D6, as the arbitrator corrected it:** a security fix auto-stages only with one valid passing fast-channel attestation from an attestor on the box's allow-list (`Options.Attestors`), because anyone can mint a key, a compromised signing quorum included. The list is the keys pinned in the image plus those the owner adds (CH-3 new grant: code-generator code plus local confirmation); it changes otherwise only through an update the current list attested, which is the updater's to enforce. Adding an owner attestor widens what can auto-stage, so it is an authority change at the high tier (code-generator code plus the local page, like a grant), never a texted code; removing one narrows and takes effect at once; the image-pinned part changes only through an installed release (security lens condition on the wiring). It starts empty, so until it has entries every security fix takes the owner's CH-3 install path. An allow-listed key still does not count if any root this box accepted listed it (`seen_keys.json`), if it is in the signed maintainer-operated list (`attestors/maintainer.json`, staged with `agentos-release attestors`) or self-labelled `operator: maintainer`, or if it is the box's own. A maintainer-run attestor (the project's test box) runs from day one and is evidence (`MaintainerPasses`). **Interim (Mark, 2026-10-05, "Project test box"):** the image pins the test box's key in `Options.InterimAttestors`. An allow-listed pinned key counts as the check while every allow-listed key is pinned and no outside attestor has ever been listed on this box (`InterimAttestation()` says so, for the digest). Only box-held data decides this: the signed maintainer list can narrow, never make a key count, so a compromised quorum cannot revive the interim rule (L3 round 3, B1). The Store records the first outside listing in `outside_attestor_listed` and never clears it, so removing the outside attestor later does not widen what auto-stages (B2); deleting the store directory or restoring an old image clears the flag and revives the interim rule, the same rollback class as U4, so the flag is to be bound to P2-4b's TPM NV anchor with the installed version; the updater calls `Store.NoteAttestors` on every owner change to the list, and `Check` records it too. A key that merely labels itself `operator: maintainer` never rides this rule. Weighting by reproducibility (OSS-9), where the box's attestation key lives, and how attestations are fetched are later. | OSS-8, OSS-9, UPD-8, CH-3 | — |
| U12 | `Check` and `Commit` hold an exclusive `flock` on `<Dir>/.lock`, so two checks (two mirrors, or the updater beside Loop 3) cannot interleave saved metadata and lower the rollback floor (security lens C3). `Result.SecurityFix` names the highest release above the installed one on the box's channel marked as a security fix, so a newer ordinary release does not hide it (C2). | UPD-5, UPD-8 | — |
| U8 | `DirSource` reads a repository directory (a drive or a synced mirror) and refuses any path with `..`, empty or hidden segments. An HTTP mirror source, with owner-configured mirrors declared as endpoints, is the updater's. Metadata reads are capped at 4 MiB and manifests at 64 KiB. Metadata holding a JSON `null` anywhere is refused before go-tuf parses it, and any other panic during `Check` fails closed as `ErrBadRepository`: go-tuf 2.4.2 dereferences a null targets entry while parsing, after the snapshot's hash check but before signatures, so a thief with only the online snapshot and timestamp keys could otherwise crash every checking box (`TestOnlineKeysCannotServeNullTargets`; worth reporting upstream). Manifests, the attestor list and attestations decode strictly: no unknown, duplicate or case-variant key, nothing trailing. | DEP-4, UPD-2 | The updater package. |
| U9 | Private key files are plain PKCS #8 PEM, mode 0600, meant for offline media; `LoadPrivateKey` refuses a file its group or others can read or write, and `keygen` prints an offline-media reminder. No real keys exist yet (K3). The custody and rotation procedure, any passphrase or hardware-token storage, and the scheduled `refresh` job on the publication repository (OSS-11; it needs the online keys as secrets) wait on Mark's key-custody decision. | UPD-2, §16 q6 | — |
| U10 | Moving to Go 1.26 changed three things outside this package: `e2e/a14_test.go` records the guest socket's redirect of an unclean path as 300 (Go now answers 307 where it answered 301; the path is never served either way); CI's format check skips `vendor/` (go-digest's upstream files are not gofmt-clean); the A9 audit job installs the module's Go before its offline build. Every CI job, the root-run test steps, and `broker/test/a9-scenario.sh` set `GOTOOLCHAIN=local`, so no build downloads a toolchain; box image builds must do the same (lens condition). | A14, A9 | — |
| U15 | **Staged releases (UPD-a).** `Stage` records a sealed release newer than the installed one in `staged.json` (version, `/usr` root hash, manifest path and hash, freshness). The box can then commit it after the restart, from a process that no longer holds the `*Verified`. `CommitStaged` commits only the staged version, and only if it is newer than the installed one, under the store lock. `Stage` takes only a release this store checked, and only while the store's root and targets versions are the ones it was checked under (`ErrTrustMoved`; L3 on #133), so a key rotation or newer targets after the check mean checking again. `DropStaged` changes nothing else: a fallback never rewinds the installed record, root metadata or seen keys (UPD-1). | UPD-1, UPD-8 | — |
| U13 | **Following a fork (OSS-10, OSS-9 B1/B2/B4; Security C1–C8 at the strongest tier).** Only `FollowRoot(root, digest, name, opts)` changes which chain the box trusts; `Check` never does, and a root that does not chain from the trusted one (not signed by its root threshold) is refused there with nothing saved (C7). **Verification (C3):** the root must pass its own root-role threshold (`VerifyDelegate`), the same `floor()` as `Check` (root and targets at least `MinThreshold`, never below 2, no override), a threshold of at least 1 that fits its keys for every role, and be unexpired by `Options.Now`. **Approval (C6):** `DescribeRoot` returns what the page shows (version, each role's key fingerprints and threshold, expiry, the root's SHA-256) and a `Digest` over all of it; `FollowRoot` refuses any other digest (`ErrFollowNotApproved`), so the owner's code approves exactly the root shown. **Keys (C2, C8):** every key of the current root and the new one, in every role, joins `seen_keys.json` before anything else changes and never leaves, so a fork maintainer's key, a former root's key, or (as before) a self-labelled maintainer key never counts as an independent attestor, allow-listed or not, on either chain or after switching back. **Interim (C1, B2):** the switch writes the sticky `outside_attestor_listed` flag, so the project's test box stops counting for good, switching back included; it is the same flag U7 binds to P2-4b's TPM NV anchor carry, so binding that one file covers both. Image-pinned outside attestors and owner-added ones stay listed (Q-B): the allow-list is the caller's and unchanged. **Anti-rollback (C5):** `installed.json` is kept, so a fork must release above the installed version; Loop 3 says "<name> has no release newer than yours yet". **Crash safety (C4):** under the store lock the writes go seen keys, interim flag, the project record (below), a `following` marker (the new root's digest and the source record), `root.json` (atomic), then remove `timestamp.json`, `snapshot.json` and `staged.json`, write or remove `source.json`, then remove the marker. `Check`, `CommitStaged` and `FollowRoot` first settle a marker left by a crash: if `root.json` is the marked root the switch is finished, otherwise the marker is dropped and the old chain stands (what was already written only narrows). A release checked under the old root never stages: `Stage` now compares the trusted root's digest as well as its version, since two chains can share version numbers. Tested with a crash injected before every step. **Source record:** `source.json` holds the owner's name for the fork, when it was chosen, the root's digest and its first root-role key fingerprint (sorted), for STATUS, the digest and the audit; an empty name means the root is the project's own, which the caller knows from the root its image ships, and removes the record. **Same-chain rollback (Security R2 on #180):** a root whose root-role keys all lie within the trusted root's and whose version is not newer is the same chain going back, not a fork, and is refused (`ErrRollback`) before anything is written; only the trusted root itself, byte for byte, may be followed again (it re-trusts nothing and only renames the source). **Project record (OSS-10w-r):** a named follow that leaves the project's chain (no `source.json`) first saves the root it leaves as `project_root.json` (a narrowing write: it only raises the bar for switching back); leaving one fork for another keeps it. `Store.ProjectRoot` returns the anchor under the store lock, after settling: the trusted root while the box is on the project chain (no `source.json`: after a switch back, or a rotation `Check` verified), else this record (Security F1 on #476: a stale record or the shipped root would admit a project root the box had seen rotated out). **Wiring (WF1', WF2):** an empty name is passed only for a root `ProjectRoot(anchor, root, links, opts)` admits, where the anchor is `Store.ProjectRoot` or, without one, the root the image ships: the root has the anchor's root-role keys (by key material) at a version not below the anchor's and is signed by the anchor's root threshold (same keys are no shortcut past TUF's old-threshold rule, L3 on #476), or the owner's root files walk from the anchor to exactly it, each link through go-tuf's `trustedmetadata.UpdateRoot` (the old root's threshold, its own, version exactly +1) and the same `floor()`; links at or below the anchor's version are skipped, at most `MaxRootRotations` links are taken. `Options.Now` is the HOST-1b clock guard's `Latest`. `TrustedRoot` returns the trusted root after settling any interrupted switch, so the executor (`broker/follow`, OSS-10w) can reconcile. **Limits:** (a) following an older, unexpired root of another chain whose later roots revoked keys re-trusts those keys until the box sees the later roots; the page shows the root version and expiry, and the owner is asked for the fork's current root. (b) Switching back needs a current project root and, after a project root-key rotation, the project's root files from the anchor onward; the image's own root may have expired, and the owner brings the project's newest root files, which pass the same checks. (c) Against an older but unexpired project root, a box that left the project after trusting a newer one is protected by the anchor; one that never trusted a project root newer than the image's rests on root expiry alone (TUF's freeze limit). Holders of a threshold of rotated-out project root keys can forge a branch from an anchor at or below their rotation, which TUF accepts by design for clients that have not seen it. | OSS-10, OSS-9, UPD-8 | Security re-check if any step order or check changes. |
| U14 | **Evidence, weighted, never authority (OSS-9 A2, Q-A).** `Verified.Evidence` counts listed independent attestors (`IndependentPasses`) and maintainer-operated keys that the signed list or the image names; it decides nothing. A key that only labels itself maintainer-operated, and every other unlisted key, is not counted or mentioned (Q-A: unlisted reports are omitted from the owner's text entirely). Pinned tests show any number of unlisted reports never stage a security fix or end a soak (`oss9_test.go`, maintain). Reproduction on this box (CHG-4 requalification) has no source yet, so Loop 3 passes "not rebuilt" until one exists. | OSS-9, OSS-8 | Weighting changes only the owner's text. |
| U16 | **Attestation authority is bound to the attestor policy (SR3-6, review F6; amends U7).** Each `Verified` records the store's attestor-policy digest at its check: a digest of the allow-list and interim keys last noted (`attestor_policy`, written by `NoteAttestors` and `Check`) plus whether `outside_attestor_listed` exists. `Security()`, `SecurityAutoStage` and `InterimAttestation()` re-read it and hold only while it is unchanged (`ErrPolicyMoved` otherwise; an unreadable store fails closed, pinned by `TestUnreadablePolicyFailsClosed`, SR3-6f-1c), and `Stage` checks it under the store lock, the lock `NoteAttestors` takes, for a release carrying attestation authority, alongside the TUF root/targets check (`trustUnchanged`). Any change retires it, widening included (one recheck); the sticky flag is part of the digest, so removing the outside attestor or reopening the store never restores the interim policy, and a fork switch (U13) retires it too. A release without attestation authority (the owner's path) is unaffected. **Ordinary releases too (SR3-6f-4):** `IndependentPasses` is 0 once the policy moved, as for `SecurityAutoStage`, so a removed attestor's pass no longer counts toward an ordinary release's `MinPasses` (UPD-5); `WithAttestations` marks a release whose admission counted an independent pass, and `Stage` checks the policy for it as for a security fix. A release admitted on no pass (no attestor listed, or the owner's path) still stages after a policy change. The policy is state, not a counter: returning to the identical list is the same policy, which grants nothing it did not. **Anchored (SR3-6f-2).** `Store.Anchor` is a monotonic counter read with the policy: an outside listing (`NoteAttestors`, `FollowRoot`) raises it before writing `outside_attestor_listed` (a failed raise still writes the file and returns the error), a record found with the counter at 0 is carried into it, and the policy reads `listed` while either says so, so deleting the record or the whole store directory no longer revives the interim rule. On the box the counter is a TPM NV counter the vault process keeps (`cmd/agentos-egress`, the only `tpmseal` importer), served read and raise only on the broker-only verify socket (`anchorsock.NewSocketAnchor`, a subpackage so agentosd links no HTTP client before W5b); only the vault process picks its id, and its id, ref, auth and base are a vault entry agentosd cannot write. It is defined at the first read under a fixed first id, which stays defined, so a fresh PC and a cleared one never look alike. An unreadable anchor fails closed (`policy()` errors: no attestation authority, `Stage` refuses). A counter the vault recorded and this PC no longer has (TPM cleared, or the vault moved to another PC) answers "anchor missing", never 0 or "no anchor", and the owner gets the counter-reset notice. So does a counter this PC has that the vault holds no working auth for: a crash between the define and the vault write, a vault restored onto this PC, or the index redefined under another auth (#600 review). A vault that recorded a counter, on a PC whose TPM is absent at start, answers 409 too, never "no anchor". The owner's re-trust of the PC defines a new counter already at 1, so the interim rule ends there (it only narrows); while the first counter is still there it does so under a new random id beside it, since `DefineCounter` hands back an existing counter without its auth. A compromised agentosd can only raise it, which only retires interim authority. **Residuals:** a crash during the very first define also needs the owner's re-trust, since it cannot be told from a restore; each re-anchor beside the first counter keeps one more NV index, one per owner re-trust (and one per re-anchor stopped by a crash, which raises before it records, so a crash never leaves a record of a counter at 0). After a re-anchor the first index stays defined and authenticates: a vault rollback or an older REC-1 copy holding its record, plus deleting the store flag, reads 0 from it (the V6 class). On a PC with no TPM a vault that never recorded a counter answers `ErrNoAnchor`, the store behaves as before (deleting the store directory revives the interim rule, the U7 rollback class), and STATUS says interim attestation is not anchored (W5b condition); root on the box that rolls back the vault file and undefines the counter is the V6 case, which the owner sees through CRED-8's counter-reset notice. Wiring the client is W5b. | UPD-8, OSS-8 | Security re-check if the digest's inputs, the Stage check or the anchor's answers change. |
| U17 | **Committing exactly the staged release (SR3-4).** `CommitRelease(Ref)` commits only a staged release whose version, `/usr` root hash and manifest digest all equal the `Ref`, writes the root hash into `installed.json` with the rest, and only then removes `staged.json` and syncs the directory. Called again for a release that is already installed, it only finishes removing a matching `staged.json` and returns nil, so the applier can retry until it has recorded the result. A different release with the same version is refused whether it is staged or installed. `CommitStaged(version)` stays for `broker/firstboot`'s tests, which commit by version on a box they built. | UPD-1, UPD-1a, OP-4 | — |
