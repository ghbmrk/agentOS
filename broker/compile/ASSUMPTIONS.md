# Compiled skills: assumptions

Built for PLAN P3 ("compiled skills", CAP-5) against SPEC v0.12, on the change pipeline (#34), the replay evaluator (#37) and the guest plane (P1-7). Covers `broker/compile` (broker side: trajectories, compiler, A10 measure) and `broker/skill` (the file format and the guest-side runner). Each row is a reading of the spec, or a gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| K1 | **Where a skill runs.** In the guest, not the broker. `agentos-guest-bridge` serves each valid file under the tree's `skills/` and `procedures/` as an MCP tool `skill_<id>` on `/skills/mcp`, and runs it by sending each step to the broker's own `effect_request`. A skill therefore holds no authority of its own: every step is journaled, rate-limited, routed, label-stamped, checked against grants and approved exactly as a request the model made (ARC-7), and the broker never interprets a skill (ARC-2). The guest is root and can change or ignore the runner; nothing in the broker trusts it. The same holds in replay, which seeds the tree into the replay machine, so held-out evaluation exercises the skill as it would run live. | CAP-5, ARC-2, ARC-7, LOOP-5 | — |
| K2 | **Where the model is consulted.** Once, to fill the skill's inputs; then only where an assumption fails. The assumptions are: every input is present, of its slot's type (text, email, number, bool, list or object), and no longer than twice the longest value any source run used (at least 64 bytes); and every step succeeds. A failed input stops the run before any effect. A step in any state but `succeeded` (waiting for the owner, denied, held, refused) stops it there, and the tool returns the remaining steps with their bound values for the model to finish. The runner never retries, skips or reorders a step. Step request IDs are `skill-<id>-<run_id>-<n>`, so a retried run repeats its requests and each effect runs at most once (OP-1). | CAP-5, OP-1 | Add value assumptions (enumerations, patterns) when Loop 1 data shows inputs that pass the type check but fail the step. |
| K3 | **Trajectory.** A task's effects are the intents sharing its goal ID, in submission order, with broker-state intents left out. It is successful when every effect succeeded, an owner verdict (OP-7, source `owner`) says good, and no verdict from any source says wrong. Its span runs from the first submit to the last outcome in the journal. **Wiring:** guest intents carry no goal ID yet (replay R4 has the same gap), so on the box no trajectory forms until the guest plane stamps each effect with the owner message it serves. `Config.Group` is the seam. Because the goal ID is part of an intent's identity (OP-1), the stamp must be fixed per request ID, not per moment. | CAP-5, OP-7 | — |
| K4 | **Builder sees only the dev split.** The compiler reads only tasks behind a dev case of class `skill` or `procedure` (`Pipeline.Dev`), so a skill is never built from a case that will judge it (CHG-1). It needs no access to held-out membership. `CaseClass` tells the harvester to file a task with at least `MinSteps` effects as a `skill` case; skill candidates are evaluated on held-out cases of that class (change C5). A task first used to build a skill and later filed as a held-out case would judge a skill it helped build; the harvester should file cases before the compiler runs. With a 30% dev split, a shape needs about ten accepted runs before three reach the compiler. | CHG-1, CAP-5 | Raise the dev share for the `skill` class if skills arrive too slowly. |
| K5 | **Procedure, then skill.** A shape (accounts and actions in order, every value's position and JSON kind) seen fewer than `MinRuns` times becomes a procedure `procedures/p<shape>.json`: its steps with every value an input, so it carries no recorded value. At `MinRuns` (3) runs it compiles into `skills/k<shape>.json`: a value equal in every run is a literal, any other an input, and values that move together run for run share one input. The skill's candidate deletes that shape's procedure. A one-effect task is neither (`MinSteps` 2): it is already one `effect_request`. More runs alone make no new candidate; a literal that later varies does (the skill is regeneralized). A trajectory containing a value the journal redacted (`Config.Redacted`) is never compiled, so a redaction marker is never replayed as a literal. | CAP-5 | Tune `MinRuns`, `MinSteps`. |
| K6 | **Through §11 only.** The compiler only returns candidates (`Source` local, `Origin` "compile"); the Loop 1 scheduler decides when to call `Candidates` and proposes each to the pipeline. Skills and procedures are authority-neutral by namespace (CHG-6), so an adoption with enough held-out evidence and no regression is unprompted and reverts by `UNDO`. A skill whose literal is a URL, address or phone number found nowhere in the active tree (a task that always goes to one person) goes to the owner (change C6). Per the arbitrator, such a local, undoable skill adoption with held-out evidence (`HeldOut > 0`) uses the plain-reply owner tier with an echoed short ID ("YES K7"); that tier is the owner-channel wiring's (#48). | CHG-6, §11, OP-5 | — |
| K7 | **Private by default.** Skills and procedures are built from owner task data, so a candidate is `Public` only when every source intent came from a public machine (REV-5); sharing needs `Public` (change C12) and private-derived skills are never published (OSS-3). Literals are values that recurred in every run; inputs are not stored. **Wiring:** the tree under `skills/` and `procedures/` is private-derived; a machine that reads it must be labelled private unless every file it reads came from a public candidate. | REV-5, CHG-5, OSS-3 | — |
| K8 | **A10 second-run speedup.** `Measure` reports, per active skill, the median span of owner-accepted model runs of its shape (no skill step in them) against the median span of complete skill runs (grouped by request ID, so no goal ID is needed), the ratio, and how many skill runs stopped for the model. Spans cover first effect to last outcome, so they omit the model's planning before the first effect; the measured ratio is therefore conservative for the model side [Inference]. Request IDs are guest-chosen, so a guest could mislabel runs; that affects only the metric, never authority. | A10, CAP-5 | Add model-call counts per task once the meter keys usage by goal. |
| K9 | **Format.** Skill files are decoded strictly: unknown fields, trailing data, an ID that is not `k`/`p` plus 12 hex of the shape or not the file's name, more than 32 steps or slots, an unused or unknown slot, a node that is not exactly one of literal, slot or object, a procedure with a literal, the `broker` account, or a `meta.*` action each refuse the file, and the bridge does not offer it. Account and action names follow the guest plane's lowercase rule. | CAP-5, OP-5 | — |
