# Loop scheduler and Loop 1: assumptions

Built for PLAN P3 ("Loops 1–3") against SPEC v0.12 §11A: LOOP-0 to LOOP-3 (the scheduler shared by all three loops) and LOOP-4 to LOOP-6 (Loop 1). It closes the change pipeline's open items for the Loop 1 scheduler (`broker/change` ASSUMPTIONS C10, C14 (a), (b), (d)) and replay's model-access conditions K1–K3 (`broker/replay` ASSUMPTIONS R2). Covers `broker/loops`, plus `meter.Overall`/`SetOverallCap`, the two `meta.loops` narrowing actions in `journal`, and `change.ClassTask`. Each row is a reading of the spec, or a gap left for a later package, that a reviewer may want to change.

|---|---|---|---|
| L1 | **Scope.** One scheduler for all three loops; each loop is a `Source` that offers `Job`s. Loop 1 (`Learn`) is built here. Loop 2 (LOOP-7 to LOOP-10) and Loop 3 (LOOP-11) are separate packages (P3-4, P3-5) that plug in as Sources; their value is findings and qualified updates per unit of cost. | §11A | — |
| L2 | **Settings by text.** On by default. The whole message, ignoring case and punctuation (as CH-11), is one of `LOOPS OFF/ON`, `LOOP n OFF/ON`, `SPARE BUDGET n` (model calls a day, at most 5000 by text), `STOP SHARING`/`START SHARING` (the pipeline's `SetSharing`), and word names for one loop: `LEARNING`, `SECURITY TESTS`, `UPDATE CHECKS` + `OFF`/`ON` (UX-49-2). `HELP LOOPS` returns `HelpText` (one segment); HELP itself carries only `HelpLine`, so the whole HELP stays within three segments (UX-49-1, tested in `control`). `Confirm` is the one-line reply, saying what stops, and on turning work back on, "Reply LOOPS OFF if this wasn't you." (UX-49-3, security C1). `BudgetAsk` renders a raise's approval with old and new calls from broker state (security C2). `LOOP n ON` after `LOOPS OFF` turns on that loop only. Each setting is a broker-state intent (`loops:n<seq>:<verb>:<arg>`, executor `loops`, OP-5) that only origin `owner` may make: no loop, the pipeline, or a guest can change a setting or the budget (LOOP-6, CHG-2). Turning loops off and lowering the budget are authority-narrowing (journal A9), so they work during STOP. Turning loops on needs only the owner's text, since it spends only the budget the owner already set; raising the budget spends the owner's quota, so it returns `ErrNeedsOwner` and needs an approved owner request (CH-10). `DefaultsLine` is onboarding's one line. **Wiring.** The grants gate delegates `meta.loops.*` to `Scheduler.Check` (grants GR18). `ErrNeedsOwner` reports `NeedsOwner()`, and a budget raise becomes a request from `Scheduler.Line`: low tier only for a small step (at most twice the budget and at most 500 calls a day), high tier otherwise, since spare calls are paid AI use (grants GR18). The owner channel's handler (`control.Handler.Settings`) passes whole messages that are not control words to `Scheduler.Text` before the agent. In a locked session `Text` takes only settings whose worst case is a pause (anything OFF, STOP SHARING, a budget no higher than now, HELP LOOPS), like CH-11's pause words; turning work on and raising the budget get the unlock prompt (UX-57-1). A failed setting says why when the box knows: the 5000 limit, a refusal's reason, sharing not available, or else that the box could not save it (UX-57-2). `Text` runs `ParseText`, `Set` and `Confirm`. `HelpExtra` carries `HelpLine` into HELP. The two processes are joined in the wiring package (L16). `LEARNING OFF` pauses Loop 1, so nothing new is learned. It is separate from the change pipeline's `LEARN OFF`, which stops adopting changes without asking: changes are still learned and proposed for approval. Applied settings are kept for Reconcile, the last 256 by apply order (`Order`), so a raise approved after many newer settings is still kept (security R2; L3 R2 on #49). | LOOP-0, CH-10, CH-11, OP-5 | Ask for a texted code on `LOOPS ON` if the security lens wants it. |
| L3 | **Spare budget (UX-43-1, K2).** One meter of its own (`Config.Spare`), never the guests', for every loop model call: replay (`replay.Config.Meter`), the clean-room builder, and Loop 1's builder. Its overall cap is the owner's setting (`SpareLimits`: calls, and 10 000 tokens a call); the per-machine cap is fixed broker configuration, and since every replay machine has a fresh ID, the overall cap is what bounds evaluation. A zero budget is a cap no real call fits under. The meter refuses calls past the cap whoever makes them, so the budget is never exceeded; the scheduler also offers no `UsesModel` work while it has no room. The digest says `Spare-time AI use, last 24 hours: N of M calls (self-tests and learning).` once any call was made (UX-49-4; the meter's window is assumed to be 24 h). **Conditions (lens gate on #49):** the wiring opens the spare meter with the minimal cap so nothing runs before `New` applies the setting, and asserts replay uses it (security C4); the clean room gets a meter share with a `Max` (below), so its own run loop cannot spend the whole budget (potency PS2, arbitrator); A11 measures calls and tokens per evaluation and `DefaultSpareCalls` is set from it, with the owner shown an estimated daily cost (potency PS3).  **Evaluation reserve (LOOP-5, arbitrator ruling on #49).** The spare meter has shares by machine-ID prefix (`meter.Share`, one mechanism for every split): `Scheduler.EvalShare()` keeps 30% (`EvalReserve`) for replay machines (`eval-`) while the scheduler runs a unit marked `Evaluates` (Loop 1's recheck, routing, and candidate units), and lends it to other users otherwise; a borrower hands it back for its next calls once evaluation runs again, but spend already made in the 24 h window stays spent. A candidate's builder runs inside an evaluating unit, so it never borrows the reserve; the clean room and non-evaluating loop work do. The clean room's share sets `Max` instead (its sub-cap, PS2). No new owner setting: both are fractions of the owner's spare budget. The wiring calls `Spare.SetShares([EvalShare(), {Prefix: <clean room's machine prefix>, Max: <fraction>}])`. | LOOP-2, LOOP-5, OP-8 | Tune the fractions from A11. |
| L4 | **Spare compute.** One unit of loop work at a time. None starts while `Busy` (foreground or accepted work, from admission) or `Stopped` (STOP). While work runs, `Busy` and `Stopped` are polled every 250 ms and the work is cancelled at once; `Preempt` does the same on demand and waits at most `YieldTarget` (default 2 s until RES-1's target is frozen), returning `ErrSlowYield` past it. The machines it runs are experiments and are frozen by admission independently (RES-1). A preempted or switched-off unit is not measured and is offered again later; this re-admits preempted loop work (P1-4 follow-up), but by re-running it in a fresh machine rather than `Manager.Resume`, since replay machines are thrown away (replay R1). | LOOP-1, RES-1 | Resume preempted machines once long jobs exist. |
| L5 | **Measured return.** A job reports its value; the scheduler measures its cost: spare-meter tokens used while it ran plus 50 tokens per second of compute. Each loop keeps moving averages (weight 0.3) of value and cost per run, and recent spend decayed with a 24 h half-life. Its share is its return (value/cost) relative to the best loop's, at least 5%; an unmeasured loop gets a full share. Loops are tried in order of share over (1 + recent spend). A loop with 3 runs in a row of no value is parked for 24 h, unless its source reports `Urgent()` (Loop 3 with a security fix or a retry due, or back online; arbitrator ruling on #53), and `Wake` unparks every loop. When no loop offers work, the scheduler sleeps (1 h, or until `Wake`). Measurements are in memory: after a restart every loop earns its share again. Values are in each loop's own units (gain, findings, updates); a common scale or normalizing each loop against its own history, and persisting the averages, are open (potency PR1, PR2). | LOOP-3 | Tune the constants from A11 runs. |
| L6 | **Owner outcomes (C14 (a)).** `Harvester.Harvest` turns an authenticated owner action into an OP-7 verdict with source `owner` and one task case: YES on an unedited item is good with the item as the reference; an edit is wrong with the edit as the reference; NO and UNDO are wrong and the item must not be reproduced. The case input is the owner's task message. The case is public only if the caller says so and the journal's REV-5 label on the intent is public: the label can only narrow it (security B1). Only the first action on an intent makes a case (UNDO after YES keeps the accepted case; the journal has both verdicts), since removing a case is an owner-approved intent (CHG-2). Crash safety: the task is saved as harvested (and so held out of mining, L8) before the pipeline adds its case, and marked added after; a retry after a failure in between records the same verdict again in the journal and adds the case once (a duplicate add is ignored), and until then the task is held out of mining but not counted as evidence. **Wiring:** call `Harvest` where the owner's YES, edit, NO, or UNDO on an agent item is applied (wiring package, L16). **Open:** one case per goal (security C1 on #52); guest intents now carry goal IDs (P3-7, #55), so a task key is one owner request, not a whole lineage; implicit acceptance as a weaker good verdict (potency PK2) needs a verdict strength the pipeline does not have. | OP-7, CHG-1, CAP-3 | Let a later owner action replace the case. |
| L7 | **Task cases.** A harvested case has class `change.ClassTask`, which the pipeline treats as evidence for every change to how tasks are done (procedures, skills, routing, context, config, and images), so one task counts once in every class's suite and in the owner's "N of M tasks" line. | CHG-1 | — |
| L8 | **Nothing held out reaches a builder.** A builder gets a `Brief`: the hypothesis and the dev split (`Dev(ClassTask)`). Mining skips every task with a held-out case, at the level of its task key (goal ID, or the origin for intents without one, as replay R4). Guest intents carry the goal ID of the owner message they serve (guest G14), so a held-out case excludes its goal's task, its lineage's unstamped bucket (`origin:guest:<lineage>`, recorded per case as `Origins`), every other goal of its lineage with an intent inside the held goal's span (first to last intent), and the first goal the lineage started after that span (`heldWithNext`): a guest's held-out work may land unstamped (two messages open, one delivered but not fetched, past the quiet window), under a goal that ran alongside it, or, if it was still finishing when handed the next message, under that next goal (#55 review B2; arbitrator ruling, which accepted this over whole-lineage exclusion because that zeroes mining on a one-guest box). A held case with no goal is a span of its one intent, and also holds the nearest goal stamped before it. Each held case holds its own neighbours, so several held goals each exclude theirs. Spans are per lineage, so a held goal whose work reached another lineage (a CAP-8 worker stamped with its creator's goal) holds its neighbours there too. Cost: held cases times journal intents per mining pass. Trailing held work that lands past the next goal (held A, then B, then C: C) is still mined; that needs a guest working on A after B was answered. Later goals of the lineage are still mined, so one held-out case does not stop Loop 1 on a one-guest box; in the test rig's split (about 2 in 3 cases held out) this mines about a third as many tasks as goal-only exclusion. Cases harvested before `Origins` existed do not hold their unstamped bucket. No evaluation count, report, or model-call record reaches a builder (C14 (d), K3); the scheduler alone reads reports, to measure return. | CHG-1, LOOP-4 | — |
| L9 | **Evidence hold (C14 (b)).** Loop 1 proposes nothing until there are `MinHeldOut` (5, set to the pipeline's) held-out task cases, so the owner is never asked about an under-evidenced change (arbitrator PL2, change C14 (b)); the digest says `Learning: N ideas are waiting until there are 5 past tasks to test them on (n so far).` | CHG-6, CHG-1 | — |
| L10 | **Signals (LOOP-4).** From the journal, ignoring broker-state intents: failures (not applied or unknown) and owner corrections (wrong verdict, owner source) ask for a procedure; steps that took over 2 minutes from dispatch to outcome, twice or more, and the same action sequence in 3 or more tasks ask for a compiled skill; tasks costing over 3 times the median ask for a narrower context. The expensive signal needs `Cost` (per-task tokens); the meter does not expose task usage yet, so it is off until wired. A hypothesis's key names accounts and actions only, but what a builder sees is not abstract: `Hypothesis.Evidence` carries each supporting step's full journal record (status and params), and `Brief.Dev` carries each dev case's input, the owner's task text. Both are owner data, so a builder is private-labelled (L11). Most-evidenced first; a hypothesis is retried only when more tasks support it. | LOOP-4 | — |
| L11 | **Candidates (LOOP-6).** A builder's candidate may write only the namespace of its hypothesis's class (`procedures`, `skills`, or `context`); anything else is dropped before the pipeline (`ErrOutOfClass`). Source, origin (`loop1`), and the public mark (every input labelled public, REV-5) are set by Loop 1, never by the builder. Proposing is Loop 1's only path to a change; the pipeline decides everything else. `BySignal` routes each signal to its own builder (the compiled-skill compiler, CAP-5, for repeated trajectories; a model-backed agent in an experiment machine on the spare meter for the rest, a later package). Since a brief carries owner data (L10), every builder that calls a model does so through the model router with the label private, so only providers marked PrivateOK see it (security C3). Loop 1 offers a builder only the signals it handles. Until builders are wired, Loop 1 proposes routing rules and rechecks. | LOOP-6, CHG-5, CHG-6 | — |
| L12 | **Routing candidates.** `Router.Candidate()` is proposed only when replay has model access (`ModelWired`), since offline both sides answer alike (replay R2), and only with enough evidence; it is retried when held-out evidence grows. | ADP-4 | — |
| L13 | **Recheck cadence (C10).** `Recheck` runs when 5 held-out cases arrived since the last one, or a week passed and any arrived, and only while some adoption is active. Its value is the number of changes it reverted. | ADP-4, LOOP-10 | — |
| L14 | **Value.** A proposal's value is its held-out gain (passed minus baseline passed): plus 0.25 when adopted with no gain, half when waiting on the owner, none when rejected. | LOOP-3 | — |
| L15 | **Replay model access (K1, K3).** Rule models are free text; a per-provider allowed-model list is a possible hardening (security R3). `EvalModel.Handler(tree)` builds a fresh model router per replay: providers, grants (`Granted`, the owner's grants for the guest's model calls), and `PrivateOK` are broker configuration; the label is always private; only the rule comes from the tree (or the active rule). An unreadable rule or an undeclared provider refuses every call, so the candidate fails. Decisions go only to `CallCount`, which keeps counts. With this, R2's K1-K3 hold; replay's `Model` stays nil until the wiring sets it. | LOOP-5, ADP-4, CAP-9 | — |
| L16 | **Not wired yet** (the change pipeline is not wired either, replay R8). Like `change` (#48), this package imports `net/http` through `route` and `meter`, which ARC-2 keeps out of `agentosd`'s control path, so the scheduler runs in the pipeline's own process, reaching the daemon's journal over its socket. Wiring: open the spare meter; `replay.Config{Model: EvalModel{...}.Handler, Meter: spare}`; `Scheduler` with `Sources: [Learn]`, `Busy` from admission, `Stopped` from the engine, registered as executor `loops`; `Harvester` with the engine and pipeline; `Scheduler.Run` in its own goroutine. | — | Wiring package. |
| L17 | **Open from C14.** (c) counting a held-out regression only when it reproduces in 2 of 3 re-runs needs a pipeline change and stays open; (e) is done (P3-1b, `grants/change_test.go`); (f) is for the arbitrator. | CHG-1 | — |
| L18 | **Lapsed owner requests (change C14 (g), arbitrator PL1).** When a Loop 1 proposal waits on the owner, the same hypothesis or routing rule is not proposed again until a backoff passes: 24 h (the next digest), doubling each time. ## Loop 2 (P3-4): passive checks and findings

Built for P3-4 against SPEC v0.12 LOOP-8 to LOOP-10, in `secure.go` (`Guard`, Loop 2's `Source`). Narrow scope (2026-10-05): after a safety check paused the session, Mark restarted the work on the recommended narrow option: LOOP-7, active testing from inside the sandbox, is not built here.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| S1 | **Scope.** Passive checks (LOOP-8), finding handling (LOOP-9), and the suite-only-grows rule (LOOP-10). LOOP-7 is out of scope and still open, so A11's "loop 2 finds a seeded vulnerability" is not met by this package. | LOOP-7 to LOOP-10, A11 | A later package builds LOOP-7 as another `Guard` input. |
| S2 | **Passive checks.** One pass runs four checks over a `Box` the wiring supplies: every listed artifact's measured digest against the signed release (`update.Verified.Images` plus dependency digests); installed packages against the last advisory snapshot, offline included; config files in force against the change pipeline's active tree; vault items' expiry (names and dates only, never values). An artifact the release does not name or that cannot be measured is a finding: fail closed. A package version that cannot be compared with an advisory's fixed version is neither assumed fixed nor assumed vulnerable: it is one Low finding per package and version in the digest ("Could not check X version V against known vulnerabilities. Check it on the box page.") with no pause and no fixture, texted once if it stays so for 7 days (L3 review blocker 2; arbitrator ruling 1 on #54). When only an advisory's fixed version does not parse, the finding names that advisory instead ("Could not read the fixed version in advisory A for X."), one per advisory, under the same 7-day rule. Versions order as dpkg does (epoch, upstream, revision, `~` before anything) unless a package names `semver` (`version.go`; security lens C1). A check that is not wired is named in the digest as not run, never counted as passed. A snapshot older than 7 days, or never fetched, gives a digest line that the known-vulnerability checks are not current. | LOOP-8, DEP-4, LOOP-11 | — |
| S3 | **Cadence and value.** A pass is due every 6 h, or at once after `Trigger` (a new release or snapshot; pair with `Scheduler.Wake`). It makes no model calls, so it runs even with no spare budget. Its value is the number of new findings; three clean passes in a row park Loop 2 for 24 h under L5, so in steady state the checks run at least daily. **Follow-up for the scheduler (potency lens on #54):** exempt the passive pass from L5 parking, since it makes no model calls and costs little compute, so the 6 h cadence holds; that is a `scheduler.go` change, left to its owner. | LOOP-3 | — |
| S4 | **Finding handling.** Per new finding, in order: contain (pause the `Contain` target the wiring named for that artifact or package; drift and expiry name none); preserve evidence (the finding and its SHA-256, saved before anything slower runs, kept forever); add a regression fixture; propose a fix if a `Fixer` exists; tell the owner. A finding is handled once while it persists, again if it reappears after clearing. Evidence keeps one record per finding digest with an appearance count and last time; a finding that clears and returns is contained and recorded again, but texted again only if it stayed clear for 24 h; sooner, the digest marks it "Again:". A pause stays listed in the digest after its finding clears  until the wiring calls `Resumed` (security lens R1, R2). Evidence is unbounded for now: passive findings are few and deduplicated; bound it when LOOP-7 adds high-volume findings (R3). High findings (hash, drift, expired credential, advisory rated high or critical) are texted in fixed wording, one text per pass within three segments, with the rest on MORE (`More`); Low ones (other advisories, expiry within 14 days) appear only in the digest. Owner text never says grant or executor: the wiring gives each target a `Label` ("pre-allowance P4", "the network gateway"). A pause says "It stays paused until you turn it back on.", since Loop 2 cannot resume anything; when a paused finding clears, the owner is texted "Cleared: X. <label> is still paused; ask your agent to turn it back on." if the finding was texted, and the digest keeps that line until the wiring calls `Resumed`. Each line ends with the next step where there is one ("Replace it on the box page."). The digest shows at most 3 findings (High first, advisories grouped per package with the highest fixed version) and "And N more". Text is marked urgent unless it is only about credential expiry (UX lens on #54). A failed containment is recorded, returned as an error, and said in the text ("Could not pause it. STOP pauses everything."). New findings are handled most serious first (High before Low; hash, then drift, advisory, expiry), so the pause cap and the text go to tampering before anything a noisy feed produces, and new findings lead the text ahead of cleared and uncomparable lines (L3 round 2, F1 and F3). Version strings in owner text keep `~` and `+`. At most `MaxPauses` (3) automatic pauses per pass, so a bad advisory feed cannot pause a whole grant set; each finding past the cap is texted with how to pause it (PAUSE for a grant, else STOP) (potency lens on #54). | LOOP-9 | — |
| S5 | **Minimized regression case.** A passive finding is already minimal: one subject and one condition (`FixtureRule`: the first fixed version for an advisory). Only advisories make a fixture, and it passes when the tree under test has the package at or above the fixed version, or does not have it at all. Hash, drift and expiry findings make none: a hash fixture would pin today's digest and fail every later release that changes the artifact (security lens B1); tampering is caught by this check and UPD-8 signatures, not by the suite. The fixture ID is `loop2/<finding ID>`, so a repeat is `ErrDuplicate`, which is not an error. | LOOP-9 | LOOP-7 adds input minimization for active findings. |
| S6 | **Fixes and LOOP-10.** A fixer's candidate gets source `local`, origin `loop2`, and public false from Loop 2, never from the fixer, and goes through `Propose` like any candidate. The pipeline already fails a candidate that edits `checks/`, `grants/` or another authority path (LOOP-10), or `security/`/`suites/` (CHG-2), and rejects any candidate that fails a security fixture; tests show a Loop 2 fix meets each of those. `SuitePipeline` has no remove: Loop 2 can only add fixtures. No fixer exists yet (it is a model-backed builder, like Loop 1's); until then findings wait for an update. | LOOP-10, CHG-2 | — |
| S7 | **Fixture answers (wiring condition K-S1).** The replay evaluator must answer a probe whose input is a `FixtureRule` with `AnswerFixture(input, Facts)`, where `Facts` are the digests and package versions the tree under test would install. Until it does, every Loop 2 fixture fails on both sides, and since every fixture must pass for every adoption (change C5), **no change adopts after Loop 2's first fixture**. `GuardConfig.FixturesLive` is off by default: each fixture is then recorded as `deferred` and the suite does not grow, while detection, containment, evidence and notice still run (L3 review R5). Turned on without these conditions, an unanswered fixture fails closed but stops Loop 1 and also blocks every update, attested security releases included (change C7 rejects any release that fails a security fixture), so wire this before turning Loop 2's fixtures on in `agentosd`. **K-S1 alone is not enough (potency lens PS1 on #54):** a fixture encodes a finding the active tree has now, so the baseline fails it by construction, and every candidate that does not fix that subject fails too; one open advisory with no upstream fix would freeze all learning. **Rule, owned by the change pipeline's C5 grading:** a `loop2/` fixture counts as "must not regress against the baseline" while the active tree fails it, and as "must pass" for good once the active tree has passed it. The suite still only grows (LOOP-10). Both conditions hold before fixtures go live. | LOOP-10, CHG-1 | — |
| S8 | **Containment (wiring condition K-S2).** `Containment` is implemented by the wiring: pausing a grant is `meta.grant.pause`, narrowing and exempt from STOP (journal A9). The grants gate allows that only from origin `owner` today, so the wiring needs the gate (`evaluateBroker`) to accept it from origin `loop2` too (pause only, never revoke or resume), as its own small grants PR with a threat check, not in #48. GR12 lets only the owner's number pause, so `loop2` must be an origin the broker authenticates itself (journal A7), never one a guest can claim; a test must show a guest-claimed `loop2` pause is refused (security lens C2). Executors have no pause intent yet. Worst case of a false finding is a paused grant or executor and a text to the owner, never wider authority. Advisory snapshots must be signed and verified, like updates (DEP-4), before `Box.Advisories` is wired, since a High advisory pauses things (security lens C3). | LOOP-9, ADP-9, OP-5 | — |
| S9 | **Inputs and wiring.** `Box` should take verified types (a snapshot only an advisory verifier can build, and `*update.Verified`) once they exist in a dependency-free package (P3-1b's recommendation); until then the wiring must pass only verified data (S8, C3). `Pass` runs serially, as the scheduler runs one job at a time. **Not wired yet**, like L16 (it runs beside the scheduler, outside `agentosd`'s control path). Wiring: `NewGuard` with a `Box` from the update store, the dependency manifest (`assurance/dependencies.json`), the change pipeline's tree, and vault metadata; add it to the scheduler's `Sources`; Notify through the owner channel's CH-15 coalescing, with `urgent` mapped to CH-15's urgent class and everything else held for quiet hours (arbitrator ruling 4: urgency follows the owner's CH-15 classes with High as the default, and a hash mismatch is always urgent, which the owner cannot turn off; `urgent` is false only for a text about expiry, clearing, or an uncomparable version); map MORE to `More` while Loop 2's text is the latest; set each `Target.Label`; call `Resumed` when the owner resumes a paused target; K-S1 and K-S2. Advisory hints for P4-1's `vuln` category are left to the wiring. | — | Wiring package. |
