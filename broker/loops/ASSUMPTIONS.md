# Loop scheduler and Loop 1: assumptions

Built for PLAN P3 ("Loops 1–3") against SPEC v0.12 §11A: LOOP-0 to LOOP-3 (the scheduler shared by all three loops) and LOOP-4 to LOOP-6 (Loop 1). It closes the change pipeline's open items for the Loop 1 scheduler (`broker/change` ASSUMPTIONS C10, C14 (a), (b), (d)) and replay's model-access conditions K1–K3 (`broker/replay` ASSUMPTIONS R2). Covers `broker/loops`, plus `meter.Overall`/`SetOverallCap`, the two `meta.loops` narrowing actions in `journal`, and `change.ClassTask`. Each row is a reading of the spec, or a gap left for a later package, that a reviewer may want to change.

| L2 | **Settings by text.** On by default. The whole message, ignoring case and punctuation (as CH-11), is one of `LOOPS OFF/ON`, `LOOP n OFF/ON`, `SPARE BUDGET n` (model calls a day, at most 5000 by text), `STOP SHARING`/`START SHARING` (the pipeline's `SetSharing`), and word names for one loop: `LEARNING`, `SECURITY TESTS`, `UPDATE CHECKS` + `OFF`/`ON` (UX-49-2). `HELP LOOPS` returns `HelpText` (one segment); HELP itself carries only `HelpLine`, so the whole HELP stays within three segments (UX-49-1, tested in `control`). `Confirm` is the one-line reply, saying what stops, and on turning work back on, "Reply LOOPS OFF if this wasn't you." (UX-49-3, security C1). `BudgetAsk` renders a raise's approval with old and new calls from broker state (security C2). `LOOP n ON` after `LOOPS OFF` turns on that loop only. Each setting is a broker-state intent (`loops:n<seq>:<verb>:<arg>`, executor `loops`, OP-5) that only origin `owner` may make: no loop, the pipeline, or a guest can change a setting or the budget (LOOP-6, CHG-2). Turning loops off and lowering the budget are authority-narrowing (journal A9), so they work during STOP. Turning loops on needs only the owner's text, since it spends only the budget the owner already set; raising the budget spends the owner's quota, so it returns `ErrNeedsOwner` and needs an approved owner request (CH-10). `DefaultsLine` is onboarding's one line. **Wiring.** The grants gate delegates `meta.loops.*` to `Scheduler.Check` (grants GR18). `ErrNeedsOwner` reports `NeedsOwner()`, and a budget raise becomes a request from `Scheduler.Line`: low tier only for a small step (at most twice the budget and at most 500 calls a day), high tier otherwise, since spare calls are paid AI use (grants GR18). The owner channel's handler (`control.Handler.Settings`) passes whole messages that are not control words to `Scheduler.Text` before the agent. In a locked session `Text` takes only settings whose worst case is a pause (anything OFF, STOP SHARING, a budget no higher than now, HELP LOOPS), like CH-11's pause words; turning work on and raising the budget get the unlock prompt (UX-57-1). The two processes are joined in the wiring package (L16). `LEARNING OFF` pauses Loop 1, so nothing new is learned. It is separate from the change pipeline's `LEARN OFF`, which stops adopting changes without asking: changes are still learned and proposed for approval. | L3 | **Spare budget (UX-43-1, K2).** One meter of its own (`Config.Spare`), never the guests', for every loop model call: replay (`replay.Config.Meter`), the clean-room builder, and Loop 1's builder. Its overall cap is the owner's setting (`SpareLimits`: calls, and 10 000 tokens a call); the per-machine cap is fixed broker configuration, and since every replay machine has a fresh ID, the overall cap is what bounds evaluation. A zero budget is a cap no real call fits under. The meter refuses calls past the cap whoever makes them, so the budget is never exceeded; the scheduler also offers no `UsesModel` work while it has no room. The digest says `Spare-time AI use, last 24 hours: N of M calls (self-tests and learning).` once any call was made (UX-49-4; the meter's window is assumed to be 24 h). **Conditions (lens gate on #49):** the wiring opens the spare meter with the minimal cap so nothing runs before `New` applies the setting, and asserts replay uses it (security C4); the clean room gets a meter share with a `Max` (below), so its own run loop cannot spend the whole budget (potency PS2, arbitrator); A11 measures calls and tokens per evaluation and `DefaultSpareCalls` is set from it, with the owner shown an estimated daily cost (potency PS3).  **Evaluation reserve (LOOP-5, arbitrator ruling on #49).** The spare meter has shares by machine-ID prefix (`meter.Share`, one mechanism for every split): `Scheduler.EvalShare()` keeps 30% (`EvalReserve`) for replay machines (`eval-`) while the scheduler runs a unit marked `Evaluates` (Loop 1's recheck, routing, and candidate units), and lends it to other users otherwise; a borrower hands it back for its next calls once evaluation runs again, but spend already made in the 24 h window stays spent. A candidate's builder runs inside an evaluating unit, so it never borrows the reserve; the clean room and non-evaluating loop work do. The clean room's share sets `Max` instead (its sub-cap, PS2). No new owner setting: both are fractions of the owner's spare budget. The wiring calls `Spare.SetShares([EvalShare(), {Prefix: <clean room's machine prefix>, Max: <fraction>}])`. | LOOP-2, LOOP-5, OP-8 | Tune the fractions from A11. |
| L4 | **Spare compute.** One unit of loop work at a time. None starts while `Busy` (foreground or accepted work, from admission) or `Stopped` (STOP). While work runs, `Busy` and `Stopped` are polled every 250 ms and the work is cancelled at once; `Preempt` does the same on demand and waits at most `YieldTarget` (default 2 s until RES-1's target is frozen), returning `ErrSlowYield` past it. The machines it runs are experiments and are frozen by admission independently (RES-1). Each cancellation carries a cause for the change pipeline (PE5, change C21): `change.ErrOwnerStop` for STOP, LOOPS OFF or pausing the running loop, `change.ErrOwnerWork` for the owner's accepted work without pressure, `change.ErrPressurePreempt` under pressure (which wins), read in one `BusyCause` call; with only `Busy` configured, only STOP while not busy is the owner's. A preempted or switched-off unit is not measured and is offered again later; this re-admits preempted loop work (P1-4 follow-up), but by re-running it in a fresh machine rather than `Manager.Resume`, since replay machines are thrown away (replay R1). | LOOP-1, RES-1 | Resume preempted machines once long jobs exist. |
| L5 | **Measured return.** A job reports its value; the scheduler measures its cost: spare-meter tokens used while it ran plus 50 tokens per second of compute. Each loop keeps moving averages (weight 0.3) of value and cost per run, and recent spend decayed with a 24 h half-life. Its share is its return (value/cost) relative to the best loop's, at least 5%; an unmeasured loop gets a full share. Loops are tried in order of share over (1 + recent spend). A loop with 3 runs in a row of no value is parked for 24 h, unless its source reports `Urgent()` (Loop 3 with a security fix or a retry due, or back online; arbitrator ruling on #53), and `Wake` unparks every loop. When no loop offers work, the scheduler sleeps (1 h, or until `Wake`). Measurements are in memory: after a restart every loop earns its share again. Values are in each loop's own units (gain, findings, updates); a common scale or normalizing each loop against its own history, and persisting the averages, are open (potency PR1, PR2). | LOOP-3 | Tune the constants from A11 runs. |
| L6 | **Owner outcomes (C14 (a)).** `Harvester.Harvest` turns an authenticated owner action into an OP-7 verdict with source `owner` and one task case: YES on an unedited item is good with the item as the reference; an edit is wrong with the edit as the reference; NO and UNDO are wrong and the item must not be reproduced. The case input is the owner's task message. The case is public only if the caller says so and the journal's REV-5 label on the intent is public: the label can only narrow it (security B1). Only the first action on an intent makes a case (UNDO after YES keeps the accepted case; the journal has both verdicts), since removing a case is an owner-approved intent (CHG-2). Crash safety: the task is saved as harvested (and so held out of mining, L8) before the pipeline adds its case, and marked added after; a retry after a failure in between records the same verdict again in the journal and adds the case once (a duplicate add is ignored), and until then the task is held out of mining but not counted as evidence. **Implicit acceptance (PW3 part B; potency PK2, security B1, potency C1 and C3 on #90):** an auto-reply the owner let go unanswered through an undo window that ran out on time (owner O18, grants GR20) is `Implicit`: an OP-7 good verdict with source `owner-implicit`, never `owner`, and an accepted case the pipeline marks implicit from that source (change C17). At most `MaxImplicitPerDay` (5) a day per guest lineage, and `MaxImplicitBoxPerDay` (10) a day across all, become cases (`ErrImplicitCap`), so one burst an injected guest wrote cannot flood the suite, nor a recreated machine reset its lineage's cap (B1(c); L3 MUST-2 on #109). The slot is taken under the same lock as the check, before the verdict is recorded, and given back if the case is not kept (L3 MUST-1); counts from earlier days are dropped. A builder's `Evidence.Dev` never holds an implicit case (change C17). An implicit case counts half toward the evidence hold (L9: `Evidence.HeldOut` is explicit cases plus half the implicit ones, rounded down; `Explicit` counts the explicit ones) and toward a proposal's value (L14). Compiled skills count implicit runs toward `MinRuns` only beside an explicit-good run of the same shape and never take content from them (compile K3; arbitrator ruling on B1(b) vs potency C3(b), "count, not content"). **Wiring (L16):** agentosd calls `Harvest` from the gate's owner verdicts (grants GR20) for YES, NO, UNDO and implicit acceptances, with the owner's task text kept by goal ID (guest G16); an edit has no correction text yet. **Open:** one case per goal (security C1 on #52); guest intents now carry goal IDs (P3-7, #55), so a task key is one owner request, not a whole lineage; implicit acceptance of other shown, unrefused guest effects (potency C2, BOARD W3-implicit). | OP-7, CHG-1, CAP-3 | Let a later owner action replace the case. |
| L7 | **Task cases.** A harvested case has class `change.ClassTask`, which the pipeline treats as evidence for every change to how tasks are done (procedures, skills, routing, context, config, and images), so one task counts once in every class's suite and in the owner's "N of M tasks" line. | CHG-1 | — |
| L8 | **Nothing held out reaches a builder.** A builder gets a `Brief`: the hypothesis and the dev split (`Dev(ClassTask)`). Mining skips every task with a held-out case, at the level of its task key (goal ID, or the origin for intents without one, as replay R4). Guest intents carry the goal ID of the owner message they serve (guest G14), so a held-out case excludes its goal's task, its lineage's unstamped bucket (`origin:guest:<lineage>`, recorded per case as `Origins`), every other goal of its lineage with an intent inside the held goal's span (first to last intent), and the first goal the lineage started after that span (`heldWithNext`): a guest's held-out work may land unstamped (two messages open, one delivered but not fetched, past the quiet window), under a goal that ran alongside it, or, if it was still finishing when handed the next message, under that next goal (#55 review B2; arbitrator ruling, which accepted this over whole-lineage exclusion because that zeroes mining on a one-guest box). A held case with no goal is a span of its one intent, and also holds the nearest goal stamped before it. Each held case holds its own neighbours, so several held goals each exclude theirs. Spans are per lineage, so a held goal whose work reached another lineage (a CAP-8 worker stamped with its creator's goal) holds its neighbours there too. Cost: held cases times journal intents per mining pass. Trailing held work that lands past the next goal (held A, then B, then C: C) is still mined; that needs a guest working on A after B was answered. Later goals of the lineage are still mined, so one held-out case does not stop Loop 1 on a one-guest box; in the test rig's split (about 2 in 3 cases held out) this mines about a third as many tasks as goal-only exclusion. Cases harvested before `Origins` existed do not hold their unstamped bucket. No evaluation count, report, or model-call record reaches a builder (C14 (d), K3); the scheduler alone reads reports, to measure return. | CHG-1, LOOP-4 | — |
| L9 | **Evidence hold (C14 (b)).** Loop 1 proposes nothing until there are `MinHeldOut` (5, set to the pipeline's) held-out task cases, so the owner is never asked about an under-evidenced change (arbitrator PL2, change C14 (b)); the digest says `Learning: N ideas are waiting until there are 5 past tasks to test them on (n so far).` Implicit cases count half toward it (L6). | L10 | **Signals (LOOP-4).** From the journal, ignoring broker-state intents: failures (not applied or unknown) and owner corrections (wrong verdict, owner source) ask for a procedure; steps that took over 2 minutes from dispatch to outcome, twice or more, and the same action sequence in 3 or more tasks ask for a compiled skill; tasks costing over 3 times the median ask for a narrower context. Both are owner data, so a builder is private-labelled (L11). Most-evidenced first; a hypothesis is retried only when more tasks support it. | LOOP-4 | — |

| L16 | **Process boundary (W3; arbitrator, adopting potency PW1 on #56).** The scheduler, Loop 1's `Learn`, and the change pipeline are deterministic and link into `agentosd` in-process; this package imports no router, provider adapter, or HTTP client (routing rules come from `routerule`), and `daemon/inference_test.go` holds that for `agentosd` and every package W3 links into it. On first start the pipeline records the vault process's rule, or, with the vault process down, the owner's, pushed once it is up (potency PW6). On a restart the restored rule is pushed, retried every 30 seconds until the vault process is up; one it refuses (the owner changed `-rule`) gives way to the owner's rule and stands for it from then on, so a revert to it is not refused (security R1). After start an adoption or revert the vault process does not take fails, so the pipeline never records a rule the router does not route by. Every write to the vault process (and the reads it decides on) holds one lock; Loop 1's `state()` reads and the digest's read of the owner's rule do not (security R2 on #110), so a delayed push never lands after a newer adoption (L3 M2 on #96). Every 30 seconds agentosd checks that the vault process routes by the pipeline's active rule and sets it if not (a vault process restarted without it); a rule it then refuses (the owner changed `-rule` while agentosd ran) gives way to the owner's rule the same way. When the owner's rule stands in for a refused rule, the owner's digest says so in one fixed line (`routingStandsInText`, one GSM-7 segment; W3-route, L3 S1 on #96): "Your AI model settings changed, so the box uses your order of models. The line is queued with `change.Pipeline.Notice`, keyed by the refused rule, so one refused rule gives one line, across restarts; a line that could not be queued is tried again at the next 30-second check. The digest is rendered once W5 wires `Pipeline.Digest`. **Projection (W3-route-a, potency PR1 on #108).** When the owner's rule stands in, the pipeline records it as its routing state (`change.Pipeline.Superseded`, change C16: the empty tree for `-rule`, the refused adoption marked undone by the owner's settings), so the next evaluation's base is what the router actually runs (L3 MUST-1 on #110). The refused order is kept in the learn directory (`routing-learned.json`) until the pipeline adopts anything. While the pipeline holds the owner's rule and the vault process has measured nothing new on it (its candidate equals its rule), Loop 1's routing candidate (`routerOf.Candidate`) is the refused order projected onto the owner's rule (`project`): in each of the owner's classes, routes the learned order had keep their learned relative order, routes new to the owner's rule keep the owner's places, and routes the owner dropped are gone. The projection is always a reordering of `-rule`, so egress K12 takes it, and it goes through `ProposeRouting` like any routing proposal: evaluated and decided by the pipeline (CHG-6), never applied directly. It gives way to the router's own measurement once there is one, and ends once the pipeline adopts anything, the projection included. When part of the learned order survives, the digest line is `routingProjectedText` instead: "Your AI model settings changed, so the box uses your order of models. While learning is on, it will check whether its learned order still helps." Loop 1's `Router` reads the vault process's measured proposal, or, with the vault process down or proposing the rule it already routes by, the pipeline's active rule, so nothing is proposed; its `SetRule` goes through the routing target; an empty proposal is none (`change.ProposeRouting`). With `-routing` empty, routing adoptions are refused (`heldRouting`). **Owner outcomes (potency PW3 on #90):** the gate's final owner verdicts (grants GR20) are harvested (`harvestOutcome`): YES as approved, NO as denied, UNDO as undone, each with the owner's task text as input and the effect's parameters as the item, public only if the owner marked the task PUBLIC (L6 narrows by the journal's label). The task texts are the owner's chat to the agent machine (guest G16), kept in the learn directory (`tasks.json`, broker only): at most 512, none past 30 days. A verdict whose task text is not kept is skipped. An effect is matched to its task by goal ID, so work the agent does within the guest's 30-minute carry-over (guest G14) takes the last task's text as its input even if unrelated: a quality cost, not a leak, since both labels still narrow it (L3 N2 on #101). Verdicts wait in a queue of 256, harvested on their own goroutine; more are dropped with a fixed log line, so a slow learning plane never holds the gate (security A2). Expired texts are swept at start too. The PUBLIC mark is the broker's own parse of the owner's message (control). **At rest (security A3):** `tasks.json` is plaintext owner data on the drive, as the pipeline's cases (`change.json`, `harvest.json`) already are; only the vault is encrypted. Open: delete a task's text when the owner forgets that task (no such owner action exists yet), and add the learn directory to the at-rest inventory the A8 checks cover. Only fixed classes are logged.
