# Loop scheduler and Loop 1: assumptions

Built for PLAN P3 ("Loops 1–3") against SPEC v0.12 §11A: LOOP-0 to LOOP-3 (the scheduler shared by all three loops) and LOOP-4 to LOOP-6 (Loop 1). It closes the change pipeline's open items for the Loop 1 scheduler (`broker/change` ASSUMPTIONS C10, C14 (a), (b), (d)) and replay's model-access conditions K1–K3 (`broker/replay` ASSUMPTIONS R2). Covers `broker/loops`, plus `meter.Overall`/`SetOverallCap`, the two `meta.loops` narrowing actions in `journal`, and `change.ClassTask`. Each row is a reading of the spec, or a gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| L1 | **Scope.** One scheduler for all three loops; each loop is a `Source` that offers `Job`s. Loop 1 (`Learn`) is built here. Loop 2 (LOOP-7 to LOOP-10) and Loop 3 (LOOP-11) are separate packages (P3-4, P3-5) that plug in as Sources; their value is findings and qualified updates per unit of cost. | §11A | — |
| L2 | **Settings by text.** On by default. The whole message, ignoring case and punctuation (as CH-11), is one of `LOOPS OFF/ON`, `LOOP n OFF/ON`, `SPARE BUDGET n` (model calls a day, at most 5000 by text), `STOP SHARING`/`START SHARING` (the pipeline's `SetSharing`), and word names for one loop: `LEARNING`, `SECURITY TESTS`, `UPDATE CHECKS` + `OFF`/`ON` (UX-49-2). `HELP LOOPS` returns `HelpText` (one segment); HELP itself carries only `HelpLine`, so the whole HELP stays within three segments (UX-49-1, tested in `control`). `Confirm` is the one-line reply, saying what stops, and on turning work back on, "Reply LOOPS OFF if this wasn't you." (UX-49-3, security C1). `BudgetAsk` renders a raise's approval with old and new calls from broker state (security C2). `LOOP n ON` after `LOOPS OFF` turns on that loop only. Each setting is a broker-state intent (`loops:n<seq>:<verb>:<arg>`, executor `loops`, OP-5) that only origin `owner` may make: no loop, the pipeline, or a guest can change a setting or the budget (LOOP-6, CHG-2). Turning loops off and lowering the budget are authority-narrowing (journal A9), so they work during STOP. Turning loops on needs only the owner's text, since it spends only the budget the owner already set; raising the budget spends the owner's quota, so it returns `ErrNeedsOwner` and needs an approved owner request (CH-10). `DefaultsLine` is onboarding's one line. **Wiring (C8/C7 grants thread):** the gate delegates `meta.loops.*` to `Scheduler.Check` and turns `ErrNeedsOwner` into an owner request; the owner channel tries `ParseText` on whole messages before handing them to the agent, adds `HelpLine` to HELP, and replies with `Confirm`. Settings already applied are kept for Reconcile only for the last 256 (security R2). | LOOP-0, CH-10, CH-11, OP-5 | Ask for a texted code on `LOOPS ON` if the security lens wants it. |
| L3 | **Spare budget (UX-43-1, K2).** One meter of its own (`Config.Spare`), never the guests', for every loop model call: replay (`replay.Config.Meter`), the clean-room builder, and Loop 1's builder. Its overall cap is the owner's setting (`SpareLimits`: calls, and 10 000 tokens a call); the per-machine cap is fixed broker configuration, and since every replay machine has a fresh ID, the overall cap is what bounds evaluation. A zero budget is a cap no real call fits under. The meter refuses calls past the cap whoever makes them, so the budget is never exceeded; the scheduler also offers no `UsesModel` work while it has no room. The digest says `Spare-time AI use, last 24 hours: N of M calls (self-tests and learning).` once any call was made (UX-49-4; the meter's window is assumed to be 24 h). **Conditions (lens gate on #49):** the wiring opens the spare meter with the minimal cap so nothing runs before `New` applies the setting, and asserts replay uses it (security C4); the clean room either becomes a scheduler Source or gets a fixed sub-cap, so its own run loop cannot spend the whole budget (potency PS2); A11 measures calls and tokens per evaluation and `DefaultSpareCalls` is set from it, with the owner shown an estimated daily cost (potency PS3). | LOOP-2, OP-8 | Split replay and builder spend into two meters if one starves the other. |
| L4 | **Spare compute.** One unit of loop work at a time. None starts while `Busy` (foreground or accepted work, from admission) or `Stopped` (STOP). While work runs, `Busy` and `Stopped` are polled every 250 ms and the work is cancelled at once; `Preempt` does the same on demand and waits at most `YieldTarget` (default 2 s until RES-1's target is frozen), returning `ErrSlowYield` past it. The machines it runs are experiments and are frozen by admission independently (RES-1). A preempted or switched-off unit is not measured and is offered again later; this re-admits preempted loop work (P1-4 follow-up), but by re-running it in a fresh machine rather than `Manager.Resume`, since replay machines are thrown away (replay R1). | LOOP-1, RES-1 | Resume preempted machines once long jobs exist. |
| L5 | **Measured return.** A job reports its value; the scheduler measures its cost: spare-meter tokens used while it ran plus 50 tokens per second of compute. Each loop keeps moving averages (weight 0.3) of value and cost per run, and recent spend decayed with a 24 h half-life. Its share is its return (value/cost) relative to the best loop's, at least 5%; an unmeasured loop gets a full share. Loops are tried in order of share over (1 + recent spend). A loop with 3 runs in a row of no value is parked for 24 h. When no loop offers work, the scheduler sleeps (1 h, or until `Wake`). Measurements are in memory: after a restart every loop earns its share again. Values are in each loop's own units (gain, findings, updates); a common scale or normalizing each loop against its own history, and persisting the averages, are open (potency PR1, PR2). | LOOP-3 | Tune the constants from A11 runs. |
| L6 | **Owner outcomes (C14 (a)).** `Harvester.Harvest` turns an authenticated owner action into an OP-7 verdict with source `owner` and one task case: YES on an unedited item is good with the item as the reference; an edit is wrong with the edit as the reference; NO and UNDO are wrong and the item must not be reproduced. The case input is the owner's task message. The case is public only if the caller says so and the journal's REV-5 label on the intent is public: the label can only narrow it (security B1). Only the first action on an intent makes a case (UNDO after YES keeps the accepted case; the journal has both verdicts), since removing a case is an owner-approved intent (CHG-2). Crash safety: the task is saved as harvested (and so held out of mining, L8) before the pipeline adds its case, and marked added after; a retry after a failure in between records the same verdict again in the journal and adds the case once (a duplicate add is ignored), and until then the task is held out of mining but not counted as evidence. **Wiring (C8/C7 grants thread):** call `Harvest` where the owner's YES, edit, NO, or UNDO on an agent item is applied. | OP-7, CHG-1, CAP-3 | Let a later owner action replace the case. |
| L7 | **Task cases.** A harvested case has class `change.ClassTask`, which the pipeline treats as evidence for every change to how tasks are done (procedures, skills, routing, context, config, and images), so one task counts once in every class's suite and in the owner's "N of M tasks" line. | CHG-1 | — |
| L8 | **Nothing held out reaches a builder.** A builder gets a `Brief`: the hypothesis and the dev split (`Dev(ClassTask)`). Mining skips every task with a held-out case, at the level of its task key (goal ID, or the origin for intents without one, as replay R4). Guest intents carry no goal ID yet, so a guest's whole lineage is one task: once it has any held-out case, Loop 1 mines nothing from that guest. This is the safe direction, but plainly: on a one-guest box the procedure and skill path is inert, since mining stops at the first held-out case while L9 waits for 5. Guest task or goal IDs must land before the builder package (potency PS1, security R1; follow-up with replay R4). No evaluation count, report, or model-call record reaches a builder (C14 (d), K3); the scheduler alone reads reports, to measure return. | CHG-1, LOOP-4 | Narrow to per-task once guest intents carry a goal ID. |
| L9 | **Evidence hold (C14 (b)).** Loop 1 proposes nothing until there are `MinHeldOut` (5, set to the pipeline's) held-out task cases, so the owner is never asked about an under-evidenced change (arbitrator PL2, change C14 (b)); the digest says `Learning: N ideas are waiting for more of your past tasks to test against (n/5).` | CHG-6, CHG-1 | — |
| L10 | **Signals (LOOP-4).** From the journal, ignoring broker-state intents: failures (not applied or unknown) and owner corrections (wrong verdict, owner source) ask for a procedure; steps that took over 2 minutes from dispatch to outcome, twice or more, and the same action sequence in 3 or more tasks ask for a compiled skill; tasks costing over 3 times the median ask for a narrower context. The expensive signal needs `Cost` (per-task tokens); the meter does not expose task usage yet, so it is off until wired. A hypothesis's key names accounts and actions only, but what a builder sees is not abstract: `Hypothesis.Evidence` carries each supporting step's full journal record (status and params), and `Brief.Dev` carries each dev case's input, the owner's task text. Both are owner data, so a builder is private-labelled (L11). Most-evidenced first; a hypothesis is retried only when more tasks support it. | LOOP-4 | — |
| L11 | **Candidates (LOOP-6).** A builder's candidate may write only the namespace of its hypothesis's class (`procedures`, `skills`, or `context`); anything else is dropped before the pipeline (`ErrOutOfClass`). Source, origin (`loop1`), and the public mark (every input labelled public, REV-5) are set by Loop 1, never by the builder. Proposing is Loop 1's only path to a change; the pipeline decides everything else. `BySignal` routes each signal to its own builder (the compiled-skill compiler, CAP-5, for repeated trajectories; a model-backed agent in an experiment machine on the spare meter for the rest, a later package). Since a brief carries owner data (L10), every builder that calls a model does so through the model router with the label private, so only providers marked PrivateOK see it (security C3). Loop 1 offers a builder only the signals it handles. Until builders are wired, Loop 1 proposes routing rules and rechecks. | LOOP-6, CHG-5, CHG-6 | — |
| L12 | **Routing candidates.** `Router.Candidate()` is proposed only when replay has model access (`ModelWired`), since offline both sides answer alike (replay R2), and only with enough evidence; it is retried when held-out evidence grows. | ADP-4 | — |
| L13 | **Recheck cadence (C10).** `Recheck` runs when 5 held-out cases arrived since the last one, or a week passed and any arrived, and only while some adoption is active. Its value is the number of changes it reverted. | ADP-4, LOOP-10 | — |
| L14 | **Value.** A proposal's value is its held-out gain (passed minus baseline passed): plus 0.25 when adopted with no gain, half when waiting on the owner, none when rejected. | LOOP-3 | — |
| L15 | **Replay model access (K1, K3).** Rule models are free text; a per-provider allowed-model list is a possible hardening (security R3). `EvalModel.Handler(tree)` builds a fresh model router per replay: providers, grants (`Granted`, the owner's grants for the guest's model calls), and `PrivateOK` are broker configuration; the label is always private; only the rule comes from the tree (or the active rule). An unreadable rule or an undeclared provider refuses every call, so the candidate fails. Decisions go only to `CallCount`, which keeps counts. With this, R2's K1-K3 hold; replay's `Model` stays nil until the wiring sets it. | LOOP-5, ADP-4, CAP-9 | — |
| L16 | **Not wired yet** (the change pipeline is not wired either, replay R8). Like `change` (#48), this package imports `net/http` through `route` and `meter`, which ARC-2 keeps out of `agentosd`'s control path, so the scheduler runs in the pipeline's own process, reaching the daemon's journal over its socket. Wiring: open the spare meter; `replay.Config{Model: EvalModel{...}.Handler, Meter: spare}`; `Scheduler` with `Sources: [Learn]`, `Busy` from admission, `Stopped` from the engine, registered as executor `loops`; `Harvester` with the engine and pipeline; `Scheduler.Run` in its own goroutine. | — | Wiring package. |
| L17 | **Open from C14.** (c) counting a held-out regression only when it reproduces in 2 of 3 re-runs needs a pipeline change and stays open; (e) the gate-level delegation test is the C8/C7 grants thread's; (f) is for the arbitrator. | CHG-1 | — |
| L18 | **Lapsed owner requests (change C14 (g), arbitrator PL1).** When a Loop 1 proposal waits on the owner, the same hypothesis or routing rule is not proposed again until a backoff passes: 24 h (the next digest), doubling each time. After 2 such proposals Loop 1 stops proposing it; the owner channel lists it in the digest instead of texting (#48). Backoff is in memory, so a restart may ask once more. Security releases are Loop 3's and keep their own path. | CHG-6, CH-15 | — |
