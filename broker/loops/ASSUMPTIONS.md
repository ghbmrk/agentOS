## Loop 2 probes (P3-4b-4a, P3-4b-4b, P3-4b-3c)

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| S26 | **Command probes fail closed.** `CommandProbe` runs a harness with `--out <file>`, discards its stdout and stderr, caps the output at 1 MiB, and parses it strictly. A nonzero exit, a timeout, a missing, oversized or malformed output, an output of another check, or an `errors` line is an error, never a clean run. It lives in `probecmd`, not `loops`, because it starts a child process and the learning plane may not (ARC-2; daemon `TestARC2ControlPathCannotReachInference`). `canary.py round` runs its controls first and skips product targets if any fails, and withholds its own output if it would carry a canary value. | LOOP-7, A5, CRED-7 | — |
| S27 | **Corpus replay.** Each published item carries each closed check's fixed synthetic payload in the item's own slot (`{REPLACE_rogue_string}`) or after its text, and the check must still hit; the label check takes the item itself as a label name and must refuse it. A check that misses its bare payload makes the run an error. The finding names the item and check, never the attack text. A run lists in `Checked` one `CorpusKey` per (item, check) it took, and `runProbe` closes a corpus finding only on its own item and check (#515 L3), so a check dropped from `Checks`, or not run by this process (S28), never closes what it found. The broker replays the corpus built into its binary (`broker/corpus` C1), never a drive file. Replay is direct, through the checks' functions, or through a guest plane (S42). | LOOP-7, LOOP-9, CH-19, ARC-2 | If a finding ever names a check by something other than its `Name`, key the close on the finding's ID instead. |
| S33 | **Tamper verdict broker-side (P3-4b-4b; P3-4b-4c-tamper).** `TamperProbe` digests each broker-held target (names, types, modes and contents, links not followed) and, for a file target, the `.agentos-tamper-*` names in its parent directory (other names there may be the broker's own writes, which `Quiesce` does not hold; #584 L3 1), before and after the guest's scripted writes; a changed or removed target is a High `tamper` finding named by its owner word, an unchanged one a refusal. The guest's own count of accepted writes is logged by the runner, never used. Each round the broker draws a fresh random nonce, and the fixed script only creates a new sibling named by it (`machprobe.Sibling`, `O_EXCL`) beside a file target or inside a directory one, so a write that lands always changes its target, also on a later round (L3 #548 point 1), and never damages it: a writable grader keeps its bytes (P3-4b-4c-restore). A writable parent directory counts as a writable file target, since it lets a guest replace the file. The broker removes the round's siblings after the verdict; a found target may still need restoring from the broker's copy if something other than the fixed script wrote it. Each target is tried at its host path, under `/proc/self/root` and `/proc/1/root`, and at any `Guest` path where the deployment shows it inside a machine (a read-only mount). **Positive control (P3-4b-4c-fresh):** `Control` is a broker-made directory the wiring mounts writable into the probe machine; its paths are tried the same ways and shuffled in with the targets' by `crypto/rand`, and if it is unchanged after the round, cannot be read, or is missing, the round fails (an error), journaling and closing nothing. A missing control fails, where a missing target is changed: the guest can remove a target it can write, but a teardown or a cleaner on the host can also remove the control, so its absence is no proof the script ran (P3-4b-4c-symlink). The control catches a round whose writes did not run; it does not stop a guest that can tell it apart (by name, type, contents, times or mount) and writes only it. The shuffle hides position only; a selective guest is stopped by the fresh signed-image machine and the fixed script, and the wiring's control should look like a target (P3-4b-4c-control). **Fresh machine:** `Attempt` names the machine that ran the writes, and a round fails if it names none or the previous round's (`lastMachine.fresh`, shared with the exhaustion probe); it checks the last round only, and producing a machine from the signed image each round is P3-4b-4c's wiring. **Broker writes (P3-4b-4c-attrib):** `Quiesce`, when set, holds the broker's writers of the targets (checkpoints into `snapshots`) from the first digest to the last; its error fails the round and its `resume` runs on every path. Chosen over attributing changes by the nonce, which misses removals and mode changes. **Host-side reads (P3-4b-4c-nofollow, -symlink; #635 L3 and Security 4a):** the digest follows no link at any depth. It opens each regular file and each directory it walks with `O_NOFOLLOW|O_NONBLOCK` (`os.OpenFile` adds `O_CLOEXEC`) and requires, by `Fstat`, the type, device and inode the walk's `Lstat` saw. It reads a directory through that handle and reaches its entries through the handle too (`/proc/self/fd/N/<name>`), never by a path whose components a guest could have swapped for a link since the check; after reading a directory, its path must still name it. A file is read up to the size the walk saw, in chunks, checking the round's ctx between chunks and between entries; the walk stops at 64 levels. A swap under the walk (a FIFO, a link, a device or another file or directory, at the entry or above it), a tree deeper than 64 levels, or a cancelled ctx fails the round and never passes it. So a guest can neither wedge the round with `Quiesce` held nor steer the read outside a target. What does not hold: a directory swapped out and back while the walk is inside it is not seen, but the walk reads the original through its handle, so nothing outside the target is read. The walk needs `/proc` mounted; without it every round fails. A target's or the control's `Path` that is a symbolic link by `Lstat` is refused before `Quiesce`, naming which, with nothing journaled or written; resolving links in the wiring (`EvalSymlinks`) was the other route, and refusal is chosen because it fails closed if the wiring changes. Only the last component is checked: a Path's parent directories are the wiring's and never guest-writable. `targetDigest` and `removeSiblings` choose a directory by `Lstat`, so neither acts through a link that appears mid-round; a target that became a link is reported changed, the round fails, and `removeSiblings` removes nothing for it. **`Attempt`'s contract:** whoever wires `Attempt` makes it return only after the round's machine has stopped, so no guest write lands during the after-digest (box row P3-4b-4c carries the wiring). `Run` rests on it for the verdict only (a write that lands after the after-digest is missed), not for liveness: the bounds above hold while a guest still runs. | LOOP-7, LOOP-9 | If a target is reachable in a way the broker cannot digest (a device, a remote store), give it a digest function. If the wiring cannot hold a writer, take a target it does not write during a round instead. |
| S35 | **Exhaustion targets (P3-4b-4b; P3-4b-4c-exhaust).** `ExhaustProbe` starts a machine (`Machine`), which must not be the last round's (the tamper probe's `lastMachine` check), reads its counters, has its guest press CPU, memory, disk and processes (`Press`) for `Hold`, pings the broker meanwhile, reads the counters again and times the machine's preemption. The counters are read broker-side: `cpu.stat` `usage_usec`, `memory.stat` `shmem` and the disk quota's usage (`PressedMachine.DiskUsed`, which reads the quota's counter, never the guest's tree, which a guest could make slow to walk). Each must rise over the hold by a minimum, or the guest did not press and the run fails, reporting what it found and closing nothing. The minimums are: memory and disk half of what the fixed script holds (`Script`: `machprobe.Options` `MemMB` and `DiskMB` in bytes, which the wiring passes as the same values it ships to the guest, and which must lie within `Budget`. a `Script` under `scriptFloor`, 24 MiB of memory and 1 MiB of disk, fails the probe before a machine starts, since half of each is over twice the largest rise presses that exited at once left (shmem 5.1 MiB, disk 4 KiB, below), so `Script{2, 2}`'s 1-byte minimums are refused (P3-4b-4c-bounds); that the wiring passes the very options it ships stays BOARD P3-4b-4c's check; the test guest's 48 and 32 MiB give 24 and 16 MiB); CPU time half of `Hold` on every CPU the machine may run on, counted broker-side from `cpuset.cpus.effective` (the machine's group, or its nearest ancestor's, since machine groups do not enable cpuset; unreadable fails the round, as does a count over `maxCPUs`, 1<<16, which no kernel writes: it is checked while summing, so four `0-4611686018427387903` ranges no longer wrap to a small count; #599 Security L1), because the script spins on every CPU for longer than the hold. A CPU minimum under 1 s of CPU time (`cpuFloor`: too short a `Hold` for the CPU count, a sub-microsecond `Hold` included), or a `Hold` so long that `Hold` × CPUs would overflow, fails the round before the press. A negative counter or disk usage, which the kernel never writes, fails the round: a negative baseline would inflate the rise (#599 Security L2). Memory is `shmem`, not `memory.current`: gVisor backs guest memory with a memfd, which the host counts as shmem, while `memory.current` also counts the file cache the disk press leaves (a control whose memory press exited at once still rose 49 MiB there). Basis, from CI on #599 (`machines`, four CPUs; `Hold` 3 s for the clean round, 1 s for the controls; minimums CPU 6 s and 2 s, memory 24 MiB, disk 16 MiB): the clean round rose CPU 10.3 s (1.7 times), shmem 73 MiB (3.1 times), disk 32 MiB; a press whose four `runsc exec`s all exit at once rose CPU 0.45 s, shmem 1.7 MiB, disk 4 KiB; with only the CPU press exiting at once, CPU 0.48 s (shmem 72 MiB, file 112 MiB); with only the memory and process presses exiting at once, shmem 5.1 MiB (file 37 MiB, CPU 6.1 s). The floor is 2.1 times the largest CPU overhead measured (0.48 s). The halves leave room for reclaim, block rounding and the machine's low `cpu.weight` while the broker answers. What passes is "held at least half the script's memory and disk at the end of the hold, and used at least half the hold's CPU time on every CPU": a guest that bursts every CPU for half the hold and idles the rest still passes, so a round shows the guest pressed for at least half the hold, not that it pressed throughout. The memory minimum is met by memory held by any of the guest's presses, not only the memory press: the process press's children hold about 23 MiB (estimated from the memdrop run as 73.5 MiB total less the 48 MiB memory press and about 2 MiB of overhead, so within a couple of MiB of the 24 MiB minimum), and the memdrop control cuts both presses, so whether a guest that runs only the process press passes the memory gate is not established: it is at the edge, not clearly over or under; the claim is "guest memory was held", not "the memory press ran" (Security R2 on #599, comment 6081667338; a control that cuts only the memory press would isolate it). Processes are not gated, nor claimed: under gVisor a guest process is a task inside the sentry, not a host task, so `pids.current` does not count them and the machine cgroup's `pids.max` bounds the sandbox's host threads, not guest processes. So `pids.max` is checked under the subject `sandbox threads` (RES-2: the process cap), a clean round lists that and never `processes` in `Checked`, and an open `processes` finding stays open with nothing to close it until a guest task limit exists (BOARD P3-4b-4c-pids-r1; P3-4b-4c-pids). The guest still presses processes; `Press`'s result is logged (machprobe M1), never a verdict. The baseline is read before the guest presses, since memory and disk pressure reach their level early in the hold and then stay flat. A limit unset ("max" or missing) or above the configured per-machine budget (`Budget`: the `memory.max`, `pids.max` and disk quota the broker writes for the machine), a `cpu.weight` at or above the broker's, or no disk budget is a High "above budget" finding (`pids.max`'s on `sandbox threads`, worded as sandbox threads over budget); a probe without a budget fails closed. Each parser and guard here has a table-driven fail-closed test (`TestEachExhaustionParserAndGuardFailsClosed`; Security README). An answer over `ResponseTarget` (a ping over four targets ends the timing) or a preemption over `PreemptTarget` is a High "slow" one. The claim is "limits set at or under the configured budget (guest processes not checked yet), the guest pressed (as above), the broker answered, the machine was preempted in time", not "pressure cannot starve the broker" (S36). The preemption target is the frozen yield target (2 s, LOOP-1); SPEC freezes no broker response figure, so the 1 s the gVisor rig uses, and any wiring sets, is a stand-in until it does (RES-1). | LOOP-7, RES-1, RES-2, LOOP-1 | When SPEC freezes a response target, use it. When the wiring creates the probe machine (P3-4b-4c), pass it the same budget it writes, and as `Script` the options it ships to the guest. When a guest task limit exists (P3-4b-4c-pids-r1), check it and restore `processes` to `Checked`. |
| S36 | **Bounded pressure.** The guest's memory and disk pressure stays under the machine's limits, so a round measures the broker rather than an OOM kill; the limits and counters themselves are read broker-side from the cgroup and the quota, never asked of the guest. So a round shows a limit is set at or under the budget, not that the sandbox enforces it once reached (#548 Potency 2). | LOOP-7, RES-2, RES-4 | A round that exceeds a limit and expects the cgroup to act inside the machine only. |
| S37 | **No containment yet.** Machine-probe findings carry no `Contain` target: whether a probe finding pauses grants is open (P3-4b-3b), so they are reported and noticed only: their line says nothing is paused and nothing is needed (S38), and an "above budget" line names the resource and that the machine is over its budget (P3-4b-4c-step). Corpus replay through a real guest channel is a separate package (P3-4b-4d). | LOOP-7, A-6 | When P3-4b-3b decides, set `Contain`. |
| S41 | **Plain names are the only source of LOOP-7 subject names.** `plainname.go` maps each fuzz target (`<package>.<func>`), the socket probe (`socket.*`), each canary registry target and each closed corpus check to owner words; a subject without an entry falls back to "one of my internal checks", and `TestThePlainNameMapCoversEveryLoop7Subject` fails until the new target has an entry. ## Corpus replay through a guest (P3-4b-4d)

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| S42 | **Verdict from the broker's side of the path.** A delivered check hands the replayed text to a guest as untrusted input over its guest plane and takes the verdict from what the broker then saw: the text the owner channel put on the owner's line (code filter; caught if the payload's code is absent), whether the mailbox message gained a label (label check), whether a planted message left the inbox (alert patterns). The guest's own answer is never read as a verdict. A route also checks, from the plane's `OwnerReply` and the journal, that the guest carried the very text down it; otherwise it errors and the run fails, so a guest that drops a text cannot pass as a caught one. Findings carry the item ID and the check name only. | LOOP-7, ARC-6, CH-19, ADP-2 | — |
| S43 | **Commitment filter replayed through the plane, and kept in-process (P3-4b-4e).** `PlaneChecks` takes the commitment filter by the only route a guest has to it: the guest composes the replayed text over MCP as an ADP-11 auto-reply (`mail.reply`) in a thread the owner pre-allowed, and the verdict is what the owner channel answered the gate's `QueueAutoReply` with: queued means the filter missed, a normal approval request means it caught the text. A reply the gate never handed the channel as an auto-reply (cold thread, a machine that is not a composer, no matching rule), one the channel refused, one the journal shows not carrying the text, or one not left pending is an error that fails the run, never a caught. `Checks` keeps its in-process copy of the filter as a second probe: the plane copy needs a guest machine, and runsc in a box, so the in-process copy covers a box that runs without them. | LOOP-7, ADP-11 | If a guest gains another route to the filter, add it to `PlaneChecks`. |
| S44 | **The rig's approvals.** The replay rig grants mail through the real grants gate, with approval requests recorded instead of texted (`gateOwner`); an alert archive the gate asks about is never answered, so it stays pending and the message stays in the inbox, which is the check catching it. The guest stand-in obeys its input, the worst case for an injection. A host-run copy of the same replay runs everywhere; the gVisor one runs in the CI machines job. For the commitment filter (P3-4b-4e) the rig earns and verifies, never bypasses: the thread's starter is the owner's copy in Sent, as `threadVerified` reads it; the gate's `Config.Isolated` counts the replay machine as a reply composer (no production code sets it yet, BOARD P3-4b-4e-composer); the reply rule (`Rule.Reply`, 40 per record and per day) is granted down the same owner path as the mail grant, approved then confirmed on the local page. The gate asks for no CAP-6 earned run when a reply rule is granted (BOARD P3-4b-4e-earned), so the rig has none to earn. The undo window is 1 ms: the rig has the owner UNDO each queued reply and checks the journal denied it, and the control's stand-in queue holds its replies without sending; the replay then ticks the gate past the window and checks nothing is queued and the mail server took no submission. | LOOP-7, ADP-2, ADP-11, A-6 | — |
| S45 | **One owner text, bounded routes.** The code filter's verdict holds only when the replayed text fits one owner text (`AgentPrefix` plus the text within `control.MaxText`, where `control.Fit` clips), so a longer text fails the run before the guest is asked instead of reading as caught because the clip cut the code. The archive route reads the mailbox only after its own intent settles (done, denied, or pending with the owner asked), and the control approves only that intent's own request item; an intent still authorized or in flight at the deadline is an error, never caught. | LOOP-7 | If the owner line's clip or segment rule changes, move the bound with it; P3-4b-4c's production `Relay` takes the same deadline. |
| S52 | **Canary targets run apart from the harness's environment, and a leak survives an error.** `canary.py` gives each target `PATH` (the parent's), `HOME` and `TMPDIR` set to a scratch directory removed after the round, the `CANARY_*` variables, the parent's value of each name its registry entry lists under `env`, only from `TARGET_ENV_ALLOWED` (`GOFLAGS` alone; any other name, `GOTOOLCHAIN` and `GOCACHE` included, is refused at load: P3-4b-4c-canary-env-r1), and `GOTOOLCHAIN=local`, set after all of those, so no entry can make a round download a toolchain even past the allow-list (`test_gotoolchain_stays_local_past_the_allow_list`). The shipped targets name no variable: `broker/vendor` holds every module, so `go test` reads no module cache, and they take no `GOCACHE` because `CommandProbe` runs the harness with `GOCACHE=off`, under which `go test` refuses to build (Security 4a on #583), so each round builds cold in its scratch `HOME` (about 20 s per target here). The host's Go must be at least the version `go.mod`'s `go` line names (`GOTOOLCHAIN=local` fetches no other; CI pins the toolchain line). **A target, and each control, runs as another uid** (P3-4b-4c-canary-uid): `run_confined` starts `canary.py _confine` under depaudit's `_unshare_flags(own_network=False)` (a user namespace mapping the harness's uid to 0 and the first id of its subordinate range to 1000, plus mount and PID namespaces with a fresh `/proc`; no network namespace, so a target keeps the host's network), and `_confine`, the namespace's init, chowns the round's plant, surface and scratch directories to 1000, runs the target through depaudit's `AS_SCENARIO` (uid and gid 1000, no groups, no_new_privs), and after it exits or times out ends the namespace and chowns them back (`_hand_back`), then writes the exit status to a file in a directory only the harness's uid reaches. Before that, `_reach_root` covers the topmost ancestor of `ROOT` that others cannot search (CI's `/home/runner` is 0750) with a 0755 tmpfs in the target's mount namespace and binds `ROOT` back at its own path, so the target reaches the repository and the rest of that ancestor (on CI, the harness's `HOME`) is hidden from it. The round's directories and the status directory are made in `/tmp` (`ROUND_DIR`), not the harness's `TMPDIR`: probecmd's harness gets a `TMPDIR` the target's uid cannot search (a Go test's 0700 `t.TempDir`). So the target cannot name the harness's `/proc` entries (another PID namespace), cannot read `/proc/1/environ` of `_confine` (another uid; `_confine` runs with the target's own environment anyway), and gets EACCES on any file of the harness's that is not world-readable, a 0600 file or anything under a 0700 `HOME` (`ConfinementTest`, run in the `dependency-audit` job; `control-confined` checks the uid and the parent's environment on every pass). It fails closed: no usable range, an unshare that fails, or no status file makes the round an error and the target never runs or its result is not used. **Limits left:** a target still reads what any uid on the host can: world-readable files, the repository at `cwd=ROOT` (it must, to run), and any secret the box leaves in a world-readable place; it can still use the network. The harness's environment is out of its reach, but a world-readable file is not. CI's `canary` job grants the runner a subordinate range as `dependency-audit` does (`usermod`, and the AppArmor userns sysctl on Ubuntu 24.04). A round whose target leaked and errored writes the finding and the error and leaves the target out of `checked`, so it closes nothing (`runProbe` reports findings from a failed run).
