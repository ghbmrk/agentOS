# notice: assumptions

Built for P2-2w c4e4 s2a and s2b (#1421) against OP-9, CH-3 and CAP-9. `broker/owner/notice` is the vault process's owner notices as data: codes, the owner texts rendered from them, and the map from the vault process's notice lines to codes. The vault process (agentos-egress) queues them and serves them on `notice.sock`; agentosd's `noticePuller` (cmd/agentosd/noticepull.go, s2b) pulls them and sends each through `owner.Channel.Inform`. Each row is a reading a later change could overturn.

| # | Assumption | Basis | If it changes |
|---|---|---|---|
| N1 | **Only codes cross to agentosd, never text.** The vault process sends a code and, for a provider notice, a name that must match `^[A-Za-z0-9][A-Za-z0-9 -]{0,31}$` (no dot, so a name never reads as a web address); for a wrong code, the name must be one of five fixed "what" keys. `Text` renders the owner's text from one table and refuses anything else, so a vault process (or anything that reaches agentosd as it) can choose which fixed text the owner gets and a provider name of that shape, but cannot write a link or a domain, a number or free words into an owner text. Provider names come from `providerNames` or a provider id (`^[a-z][a-z0-9-]{0,31}$`), both of that shape; a test names every built-in one. | CH-3, CAP-9 | A notice that needs more than a name gets its own code and field check. |
| N2 | **The notices are the vault process's existing lines, matched exactly.** `custody.notify` still logs every line; `FromLog` maps the mail, second-line calling and texting account lines, the missed-texts line, the private-data allow and withdraw lines, every "wrong code for …" line and the too-many-wrong-codes unlock line. Every other line (unlock, trusted host, card rotation, pins) stays log-only until a row routes it. A test in agentos-egress maps each of its constants and runs the real custody through a wrong code and an allow, so a reworded line fails there rather than going quiet. | OP-9, CH-3 | A new owner-facing line needs a code here and a case in that test. |
| N3 | **The queue is memory-only, bounded and at-least-once.** The vault process keeps the last 64 notices, numbered, under a random boot id; `GET /notices?boot=B&after=N` drops numbers up to N for the same boot and answers the rest, or waits up to 25 s. A restart of the vault process loses unsent notices (and a new boot id makes agentosd start over); a full queue drops the oldest and reports `missed` until the caller has seen past it. Pushing never blocks and never calls back into custody, since `notify` runs under `custody.mu`. Only agentosd's uid reaches the socket (the vault process's peer listener). A process running as agentosd's uid can drain notices unsent; that is the same trust the model and verify sockets already give that uid (#1426). | OP-9, CH-3 | If notices must survive a restart, the queue moves to a file beside the unlock state. |
