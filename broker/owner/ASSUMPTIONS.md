# Owner channel: assumptions

Built for PLAN P1-5 against SPEC v0.12 (PR #15; §6 is unchanged from v0.11) on
top of the broker skeleton (PR #19). Each row is a reading of the spec, or a gap
left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| O1 | `Channel` sits in front of `control.Handler` and is its `control.Auth`. It owns every word that carries or checks a code (RESUME, YES, NO, UNDO, MORE, RUN, session unlock) and passes STOP, STATUS, HELP, unclear code-like messages and chat through. The control package is unchanged. Wiring `Channel` into `daemon.Run` needs the vault's `Secrets` (P1-3) and a state path, so it lands with integration (P1-7); a daemon embedding it must call `Boot` (or `Run`, which does). | CH-3, CH-11 | Small: `daemon.Run`. |
| O2 | Request IDs are a letter (no I or O) and a digit, or a letter and two digits when those run out, unique among open requests, queued replies, the restart record, and IDs closed in the last 24 h, so a late reply never lands on a new request with a reused ID. The search is bounded and fails with an error. With one request open, a low-tier `YES <code>` may omit the ID, and a texted code names its own request; a code-generator code always needs the ID, because it proves the owner but not which request they read. A code that names no request counts as a wrong code. | CH-12, CH-13, CH-18 | Small: `parseReply`, `findLocked`, `newIDLocked`. |
| O3 | A partial `YES K3 1 3 <code>` approves the listed items and denies the rest of that batch, so the single-use code never leaves part of a batch open; the request text says "the rest are denied". `NO 2` denies one item and leaves the rest open. Unanswered items expire as denied and are kept for the digest (`TakeExpired`, capped at 200 with a count of the rest). | CH-13, CH-18 | Keeping the rest open would need a fresh code per remainder. |
| O4 | Code hygiene: 3 wrong replies void a request or RESUME code. 5 wrong codes of any kind since the last code-generator unlock, within 24 h, lock the low tier and end the session unlock, and the owner is told; a code-generator code or grid cell lifts the lock but does not forgive the wrong codes, which age out. **Added:** 10 wrong codes in 24 h pause code checks by text until the oldest ages out (the reply names the time). CH-18 bounds texted codes but not guesses at the 6-digit high-tier codes. **Held for the arbitrator** (PR #22 review): UX proposed throttling to 1 attempt per 30 min instead, and Potency/L3 noted the window slides, so a spoofer can keep it armed; P2-2's local UI must offer RESUME and an unlock that clears the pause before the channel goes live. | CH-18 | Arbitrator ruling pending. |
| O5 | While locked, a code is the whole message or a separate trailing token of exactly 6 digits; it is checked and counts as wrong if it fails. A message sent with its code runs. A message sent without one is held (one at a time, 15 min); a later code-only unlock shows its first 40 characters and runs it only on `RUN`, because the code proves the unlock, not who wrote the held text. A second locked message or a wrong code drops what is held. `RUN` is an addition to CH-11's word list (needs a spec diff). While unlocked, a code in chat is checked silently: a match is spent and stripped before the agent sees it, but it never extends the unlock and a miss is not counted, so a spoofer gains nothing by guessing. | CH-11, CH-14 | Small: `routeLocked`. |
| O6 | A code-generator code is RFC 6238 (SHA-1, 30 s, 6 digits), accepted for the current step or the one before (texts arrive late, never early), never at or before the last step accepted, so each code works once. The paper grid is 10x10 cells (A1 to J10) of 6 digits derived from a seed; the box asks for one random unused cell, and only that cell is accepted. Seeds come from the vault (P1-3) through `Secrets`; nothing here stores them. | CH-4, CH-18, CRED-8 | Grid size and cell length are for the Owner Card design (P2-2). |
| O7 | Durable state (unlock expiry, last generator step, spent grid cells, recent wrong codes, low-tier lock, retired IDs, and the IDs and refs of open requests and queued replies, never codes or reply text) is one JSON file replaced atomically. Every change is made to a copy, saved, then made current, so a failed save leaves nothing live in memory; only wrong-code counts and locks are kept in memory regardless, since they only restrict. After a restart `Boot` decides every item of a request that was open as denied (`Why: restart`), lists them for the digest, and texts the owner which requests were cancelled and which auto-replies were not sent. Intents that were awaiting approval without a request reaching this channel are the caller's to close (P1-7). | CH-13, CH-18, OP-4 | Persisting open requests would mean persisting their codes, which the review ruled out. |
| O8 | Tiering takes `Facts` the caller says the broker verified. Unverified or missing facts are high risk. An amount at or above the owner's limit is high risk, and a zero limit makes every amount high risk. Grant, CRED-6, recovery and tier-change kinds are always high. | CH-10 | `Classify`. |
| O9 | Approval texts render only verified fields through a fixed alphabet: look-alikes folded (a table for Cyrillic, Greek, accented Latin, fullwidth forms), line breaks removed, GSM-7 extension characters dropped, each field capped, and secret-shaped fields shown as `[hidden]`. A batch lists as many items as fit in three segments and points to `MORE <id>`. | CH-10, CH-12, CH-19 | `render.go`. |
| O10 | The CH-19 filter is fixed patterns on folded text (fullwidth forms, every Unicode digit, look-alike letters, combining and format characters): known token formats (AWS, GitHub, Slack, OpenAI/Anthropic-style `sk-`, Stripe, Google API keys, JWTs, private-key headers, `otpauth://`) and a 4-10 character token containing a digit within 4 words of a code word (code, OTP, verification, PIN, passcode, password, pass, key, sign-in, 2FA, MFA, security, login, token). Adjacent digit groups are joined, so "482 913" counts. A hit replaces the whole text with a pointer to the local UI. The 4-word reach is a tradeoff: sentence scope would catch more and hide more ordinary texts. | CH-19 | Pattern list grows through Loop 2 (LOOP-10). |
| O11 | ADP-11 auto-replies: the commitment filter runs on folded text and checks secret-shaped content, amounts (leading or trailing currency symbols, ISO codes, currency words), dates (a month next to a day number, full weekday names, numeric dates with `/` or `-` only, ISO dates, times, deadline words, and `due` only as a deadline), and the owner's phrase list matched as whole words (default: the ADP-11 phrases with their inflections, plus promise and guarantee). A pass-corpus test pins routine replies that must stay auto-replies. Bare affirmatives (yes, ok, sure, deal) are **not** included: they appear in most routine replies, so they would turn nearly every auto-reply into an approval and remove ADP-11's value; the alert and undo window cover that residual. A match becomes a normal approval request; otherwise the owner gets the first line and `UNDO <id>`, and `DueAutoReplies` releases it after the undo window (default 10 min), never while STOPped. If the alert cannot be sent, the reply is dropped. | ADP-11, CH-16 | `commit.go`, `autoreply.go`. |
| O13 | One CH-15 limit (default 6 per hour) covers every reply to a message that proves only the owner's number: unlock prompts, held-message and wrong-code replies, usage replies, HELP, "not understood", RESUME code texts (also capped at 3 per hour and re-sending the live code). STOP replies, replies confirming an accepted code, and replies inside an unlocked session are not counted. Beyond the limit the box is silent. `Run` makes the channel's own decisions in arrival order and runs the control handler's part on its own goroutine, so a slow agent never delays a STOP (B11). | CH-2, CH-15 | Owner-set limit later. |
| O14 | Open requests plus queued replies are capped at 50 (`ErrFull`), so nothing grows until the channel stalls; STOP always answers. Rendered fields cut digit runs of 6 or more to their last 4 so no field reads like a code, and the verb shown is the one `Classify` judged (`Facts.Verb`; excluded verbs match case-insensitively). | CH-2, CH-10, CH-12 | Small. |
| O12 | Out of scope here: voice and DTMF (CH-5, CH-17, P2-3), pacing, quiet hours and the digest (CH-15), evidence delivery (CH-20), UNDO for executed effects other than queued replies (CH-16 with REV-3), and unknown-host vault unlock (CRED-8, P2-4). `RequireUnlock` is the hook for the unknown-host boot. | — | Later packages. |
