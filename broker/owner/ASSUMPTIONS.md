# Owner channel: assumptions

Built for PLAN P1-5 against SPEC v0.12 (PR #15; §6 is unchanged from v0.11) on
top of the broker skeleton (PR #19). Each row is a reading of the spec, or a gap
left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| O1 | `Channel` sits in front of `control.Handler` and is its `control.Auth`. It owns every word that carries or checks a code (RESUME, YES, NO, UNDO, MORE, RUN, session unlock) and passes STOP, STATUS, HELP, unclear code-like messages and chat through. The control package is unchanged. `daemon.Run` builds it when `OwnerState` is set (P1-7) and calls `Run` with a modem or `Boot` and a minute `Tick` without one; owner chat goes to the guest plane's inbox for the agent machine, and the guest's answers go out through `Notify`. `Secrets` stay empty until the vault can be unlocked (P2-4), so high-tier codes are refused until then. | CH-3, CH-11 | — |
| O2 | Request IDs are a letter (no I or O) and a digit, or a letter and two digits when those run out, unique among open requests, queued replies, the restart record, and IDs closed in the last 24 h, so a late reply never lands on a new request with a reused ID. The search is bounded and fails with an error. With one request open, a low-tier `YES <code>` may omit the ID, and a texted code names its own request; a code-generator code always needs the ID, because it proves the owner but not which request they read. A code that names no request counts as a wrong code. | CH-12, CH-13, CH-18 | Small: `parseReply`, `findLocked`, `newIDLocked`. |
| O3 | A partial `YES K3 1 3 <code>` approves the listed items and denies the rest of that batch, so the single-use code never leaves part of a batch open; the request text says "the rest are denied". `NO 2` denies one item and leaves the rest open. Unanswered items expire as denied and are kept for the digest (`TakeExpired`, capped at 200 with a count of the rest). | CH-13, CH-18 | Keeping the rest open would need a fresh code per remainder. |
| O4 | Code hygiene: 3 wrong replies void a request or RESUME code. 5 wrong codes of any kind since the last code-generator unlock, within 24 h, lock the low tier and end the session unlock, and the owner is told; a code-generator code or grid cell lifts the lock but does not forgive the wrong codes, which age out. **Challenge mode (arbitrator ruling on PR #22):** 10 wrong codes since the last unlock, within 24 h, stop bare codes. The owner is texted a one-time challenge (4 characters, about 20 bits) and unlocks with `UNLOCK <challenge> <code>` (a CH-11 addition, pending the same spec diff as `RUN`), or `RESUME <challenge> <code>` while stopped. The challenge is single use and replaced after each attempt, after 30 min, or after 3 messages naming a wrong challenge (so guessing it is not free; a spoofer can make the owner ask again). A bare `UNLOCK` or `RESUME` re-sends the live one. Challenge texts have their own limit of 4 per hour, apart from the shared CH-15 budget. Any other message carrying a code is dropped silently: not counted, nothing consumed, no reply, so spoofed codes cannot re-arm the lock. Attempts that carry the challenge are capped at 48 per fixed 24-hour window that starts at its first attempt and does not slide. Alerts about ignored codes go out at most once an hour (the entry text counts), and the digest gets a count (`TakeDigestNotes`). P2-2's local UI must still offer RESUME and a local unlock, as defense in depth. | CH-18 | Arbitrated; the bound and TTL are constants. |
| O5 | While locked, a code is the whole message or a separate trailing token of exactly 6 digits; it is checked and counts as wrong if it fails. A message sent with its code runs. A message sent without one is held (one at a time, 15 min); a later code-only unlock shows its first 40 characters and runs it only on `RUN`, because the code proves the unlock, not who wrote the held text. A second locked message or a wrong code drops what is held. `RUN` is an addition to CH-11's word list, pending the CH-11 spec diff the reviewer sent to the coordinator. While unlocked, a code in chat is checked silently: a match is spent and stripped before the agent sees it, but it never extends the unlock and a miss is not counted, so a spoofer gains nothing by guessing. | CH-11, CH-14 | Small: `routeLocked`. |
| O6 | A code-generator code is RFC 6238 (SHA-1, 30 s, 6 digits), accepted for the current step or the one before (texts arrive late, never early), never at or before the last step accepted, so each code works once. The paper grid is 10x10 cells (A1 to J10) of 6 digits derived from a seed; the box asks for one random unused cell, and only that cell is accepted. Seeds come from the vault (P1-3) through `Secrets`; nothing here stores them. | CH-4, CH-18, CRED-8 | Grid size and cell length are for the Owner Card design (P2-2). |
| O7 | Durable state (unlock expiry, last generator step, spent grid cells, recent wrong codes, low-tier lock, retired IDs, and the IDs and refs of open requests and queued replies, never codes or reply text) is one JSON file replaced atomically. Every change is made to a copy, saved, then made current, so a failed save leaves nothing live in memory; only wrong-code counts and locks are kept in memory regardless, since they only restrict. Open requests also record when they were first asked, their expiry, and a digest of each item (`ItemSum`), never the item. After a restart `Boot` retires every open request, so every old code dies. With `Config.Reissue` set (the grants gate, GR10), it hands the items of unexpired requests to it to re-send with new codes (`RequestEach`: one request and code per item, in one text when they fit, each line ending "asked HH:MM, re-sent after restart"), and decides items of expired requests as denied (`Why: expired`). Without it, or for a record without an expiry, items are decided as denied (`Why: restart`). Queued auto-replies are decided as denied (`Why: restart`). Decided items are listed for the digest, and the owner is texted what will be re-sent, what was cancelled or expired, and which auto-replies were not sent. | CH-13, CH-18, OP-4 | Persisting open requests would mean persisting their codes, which the review ruled out. |
| O8 | Tiering takes `Facts` the caller says the broker verified. Unverified or missing facts are high risk. An amount at or above the owner's limit is high risk, and a zero limit makes every amount high risk. Grant, CRED-6, recovery and tier-change kinds are always high. | CH-10 | `Classify`. |
| O9 | Approval texts render only verified fields through a fixed alphabet: look-alikes folded (a table for Cyrillic, Greek, accented Latin, fullwidth forms), line breaks removed, GSM-7 extension characters dropped, each field capped, and secret-shaped fields shown as `[hidden]`. A batch lists as many items as fit in three segments and points to `MORE <id>`. | CH-10, CH-12, CH-19 | `render.go`. |
| O10 | The CH-19 filter is fixed patterns on folded text (fullwidth forms, every Unicode digit, superscript and subscript digits, mathematical alphanumeric letters, look-alike letters, curly apostrophes, combining and format characters): known token formats (AWS, GitHub, Slack, OpenAI/Anthropic-style `sk-`, Stripe, Google API keys, JWTs, private-key headers, `otpauth://`) and a 4-10 character token containing a digit within 4 words of a code word (code, OTP, verification, PIN, passcode, password, pass, key, sign-in or sign in, 2FA, MFA, security, login, token). Adjacent digit groups are joined, so "482 913" counts. A hit replaces the whole text with a pointer to the local UI. The 4-word reach is a tradeoff: sentence scope would catch more and hide more ordinary texts. | CH-19 | Pattern list grows through Loop 2 (LOOP-10). |
| O11 | ADP-11 auto-replies follow Mark's approved D2 set (the arbitrator withdrew an earlier narrowing). A reply becomes a normal approval request when it carries: secret-shaped content (CH-19); money (leading or trailing currency symbols, ISO codes, currency words); any date or time reference (weekdays, today, tonight, tomorrow, a month next to a day number, numeric dates with `/` or `-`, ISO dates, clock times, relative days such as next week or in 2 days, deadline words, and `due` as a deadline); or one of ADP-11's six phrases (confirm, agree, will pay, approved, sign, accept) with their inflections, in any person and in questions. Additions beyond Mark's set: look-alike and Unicode-digit folding, the amount patterns, and further commitment verbs (pay, book, order, reserve, promise, commit, guarantee) after a first-person subject. Matching is by whole words, so "significant", "signal" and "acceptable" pass, as does "version 2.1". The owner's lists add to the defaults and never replace them. There is no false-positive target: a false positive costs one approval prompt, which Mark accepted. The pass and fail fixtures in `commit_test.go` pin both sides. Bare affirmatives (yes, ok, sure) are not included, since they appear in most routine replies. Otherwise the owner gets the reply's first line and `UNDO <id>`, and `DueAutoReplies` releases it after the undo window (default 10 min), never while STOPped. If the alert cannot be sent, the reply is dropped. | ADP-11, CH-16 | `commit.go`, `autoreply.go`. |
| O13 | One CH-15 limit (default 6 per hour) covers every reply to a message that proves only the owner's number: unlock prompts, held-message and wrong-code replies, usage replies, HELP, "not understood", RESUME code texts (also capped at 3 per hour and re-sending the live code). STOP replies, replies confirming an accepted code, and replies inside an unlocked session are not counted. Beyond the limit the box is silent. `Run` makes the channel's own decisions in arrival order and runs the control handler's part on its own goroutine, so a slow agent never delays a STOP (B11). | CH-2, CH-15 | Owner-set limit later. |
| O14 | Open requests plus queued replies are capped at 50 (`ErrFull`), so nothing grows until the channel stalls; STOP always answers. Rendered fields cut digit runs of 6 or more to their last 4 so no field reads like a code, and the verb shown is the one `Classify` judged (`Facts.Verb`; excluded verbs match case-insensitively). | CH-2, CH-10, CH-12 | Small. |
| O15 | `PAUSE <grant>` and `REVOKE <grant>` (CH-11's pause and revoke commands for pre-allowances, ADP-9) need only the owner's number, like STOP. The channel parses them (grant IDs are G and 1-4 digits) and hands them to `Config.Narrow`, the grants gate, outside its lock. Their replies count under CH-15. UNDO of a queued auto-reply, and `Boot` dropping one, are reported to `Decide` (Why `undo` or `restart`), so its intent is closed. `Tier` tells a batching caller which tier an item would get, and `Active` whether the owner texted recently. Recipients are rendered in full and never cut, hidden, or digit-collapsed (this overrides O9 and O14 for recipients). An item whose recipients cannot be shown in full (over 100 characters, outside the alphabet, a line break, or secret-shaped) is refused with `ErrLocalOnly` and waits for the local page. Unverified items carry a fixed `UNVERIFIED, details on the Wi-Fi page:` prefix outside the field caps. | ADP-9, ADP-11, CH-11 | Grants package. |
| O16 | The local UI (P2-2) reaches the channel through `LocalStatus`, `LocalGridCell`, `LocalSignIn`, `LocalStop` and `LocalResume` (`local.go`). A local sign-in is the O4 local unlock: a code-generator code or the asked grid cell unlocks the session, clears challenge mode and the low-tier lock, and counts as a wrong code when wrong; local attempts have their own durable fixed 24-hour bound (`LocalBound`, 24). Sign-ins are texted to the owner at most once an hour, listing each (`FlushLocal`, run by `Tick`); untold sign-ins and the last such text are durable (`State.LocalSignIns`, `LocalAlertAt`) and are dropped only after a successful send, so a restart or a failed send never loses one (a repeat is possible if the save after a send fails); a wrong local code is texted on the first of a bound window and when the bound runs out, and all are listed in `TakeDigestNotes`. `State.Locks` counts session locks (wrong codes crossing `WrongToLock`, `RequireUnlock`) and is reported in `LocalStatus`, so the local UI signs out devices signed in under an earlier count even after a later unlock by text. Local RESUME trusts the caller's signed-in device and voids any texted RESUME code. **SR3-1:** `LocalSignIn` returns the `Locks` count it accepted the code under, read in the same critical section as the check, never after its texts go out; `LocalResume` takes that count and refuses with `ErrLocked` if a lock came since, checked under the channel lock where the resume commits. | CH-7, CH-11, CH-18 | `local.go`. |
| O17 | **Settings texts (W3).** A whole message the `Settings` hook takes (the loop scheduler's `Text`: LOOPS OFF/ON, LEARNING OFF/ON, SPARE BUDGET, STOP/START SHARING, HELP LOOPS) is answered by the box and never reaches the agent; HELP carries `HelpExtra`. In a locked session a setting `Narrows` reports (worst case a pause) runs at once like CH-11's pause words, with its reply counted against CH-15's limit; one that widens is held for the unlock like any other message. `Narrows` reads only the scheduler's settings, never the channel. So the owner's number alone, in a locked session, can turn loops or sharing off or lower the spare budget: no more than STOP already allows that adversary (security R2 on #90). When the learning plane could not start, every such setting gets the fixed "not running" reply, and STATUS adds "Spare-time work: not running." through `Notes`, STATUS's exception lines, so the owner learns it without sending a setting first (W3-off, UX R1 on #92). | CH-11, CH-14, LOOP-0 | — |
| O12 | Out of scope here: voice and DTMF (CH-5, CH-17, P2-3), pacing, quiet hours and the digest (CH-15), evidence delivery (CH-20), UNDO for executed effects other than queued replies (CH-16 with REV-3), and unknown-host vault unlock (CRED-8, P2-4). `RequireUnlock` is the hook for the unknown-host boot. | — | Later packages. |
| O18 | **Silence on time (security B1(a) on W3 PW3).** A queued reply released by `DueAutoReplies` is marked `Late` when it is released more than `LateRelease` (2 minutes; the daemon releases every minute) after its window, when its alert's time is unknown, or when the box's line failed any send between its alert and its release (`watchedLine` records failures). A late reply is still sent; only its silence is not read as the owner's (grants GR20). There is no delivery report: an alert the carrier took counts as delivered. Held effects are never marked: the owner said YES. `Queued.Alerted` is the alert's time, so the gate also reads silence whose alert or release fell in the owner's quiet hours as not the owner's (grants GR20, security F1 on #109). An UNDO for a reply already released is kept with its release (`UndoneAfterRelease`, for `RetireFor`): too late to stop the reply, but it was not let go, so the gate reports no acceptance for it (L3 MUST-4 on #109). | ADP-11, CH-16, OP-7 | Use delivery reports once the modem gives them. |
| O19 | **Canonical recipients only (security review 2, finding 1, #143; SR2-1).** An approval text shows recipients only when every one is canonical: a plain email address with no run of 6 or more digits, a full E.164 number (`+`, a country code not starting with 0, 7 to 15 digits), or `acct ...` and 4 digits. The set must already be plain ASCII: a look-alike is no longer shown folded, because the folded form is not where the effect goes. Anything else, including agent-written text that would plant a fake expiry, request ID or code, renders as "N recipients, see the Wi-Fi page" and is `ErrLocalOnly`; the grants gate refuses such an action with a reason saying what to change (`grants.RecipientsNotTextable`), since this build has no local approvals page (P2-2a, UX-144-2), and drops one carried over a restart from its batch so the rest are still asked (UX-144-1). Spaced or dashed numbers are not normalized (UX-144 R1 declined: the shown form must be what the effect uses); national-format numbers go to the same refusal until the item builder normalizes them (potency R1 on #144, carried). A code-like email is refused rather than digit-collapsed, which keeps O15's rule that recipients are never collapsed. This narrows O15. | CH-10, CH-12 | `recipientText`, `canonical`. |
| O20 | **Terms are bound, not texted (SR3-3).** `Item.Terms` is a `TermList`, the canonical JSON of `[]Term`, so `Item` stays comparable. `ItemSum` appends it only when set, after the Detail/UndoBy appendix and with its own `T` tag, so the digest of an item without terms is unchanged and terms never read as a detail. A grant change still open across the upgrade to SR3-3 was summed without its terms, so at re-issue it no longer matches and is closed as changed while the box restarted: the owner asks again (fails safe; L3 point 5 on #433). `line()` ignores terms: an approval text keeps its one short line (CH-12), and only the local page shows them. A `TermList` that does not decode as a non-empty list is shown as an unreadable rule to deny. | CH-12, ADP-9 | `ItemSum`, `TermList.List`. |
| O21 | **Pacing defaults (W5-Dc-r1a, SG-r1-1, SG-r1-2; provisional, for Mark).** `State.Pacing` absent or zero reads as no quiet hours, 3 unsolicited texts an hour, and only `security` urgent, so a state file from main loads unchanged. The classes are a closed set: `security` (always urgent, cannot be cleared), `approval` and `agent` (urgent only if the owner says so), `update` (never urgent). A saved setting outside what the owner could set (an hour outside the day, a rate outside 1 to 20, an unknown or fixed class) is replaced in memory by the defaults on load and logged with a fixed line that names no value: it fails closed to pacing, never to none. | CH-15 | `Pacing.valid`, `checkPacing`. |
| O22 | **One gate, one budget (W5-Dc-r1a QH-2, SG-r1-4; provisional).** Unsolicited texts go through `Post(class, …)`: `Inform` as `update`, `Notify` as `agent`, `NotifyAs` with the caller's class, and `alert` as `security`. The `Boot` text is not paced: it carries the new codes and explains them, so it goes at once and counts toward the hour, and a held copy can never be released after its codes died (round 1 on #617, B4). `alert` and `Boot` are broker templates carrying the broker's own wording, so they skip Disclose as they did before (CH-19); the rest keep it. Approval requests (`sendRequest`) and auto-reply notices (`QueueAutoReply`) are never held here, because grants paces them (W5-Dc-r1b), but each one sent counts toward the hour, so the allowance is one budget. An urgent text counts too. Replies on `Run`'s path (STOP and RESUME confirmations, HELP, STATUS, YES, code texts) are never held or counted: the owner just wrote, so is reachable (SG-r1-4). The count is the send times in the last hour, kept in state; a time after now (the clock stepped back) is not counted and is dropped on the next send, as `Boot` refuses a future `Asked`; a failed save of a count still keeps it in memory. | CH-15, CH-11 | `post`, `countSent`. |
| O23 | **The hold (W5-Dc-r1a QH-3, QH-4, SG-r1-3; provisional).** A non-urgent text is held when it is quiet hours, the hour's allowance is spent, or older texts are already held, so a newer text never goes before an older one. It is saved before `Post` returns nil; a failed save returns the error and nothing is sent or kept. The hold keeps 32 texts, already disclosed and fitted; past that the oldest are dropped and counted, and the next release starts "N earlier texts were dropped while paced." `Release` (and every non-urgent `Post` first) sends the hold oldest first, packed with " / " (GSM-7 has no line break), except that agent text (`Notify`, `NotifyAs`, marked `Agent`) always goes alone so a " / " in it cannot forge a broker segment (CH-19), into texts of at most `control.MaxText`, one per allowance unit. A text leaves the hold only after the modem took it; a send error keeps it. If saving the removal then fails, it is removed in memory anyway, so it is not repeated in this run, but a restart before the next save would send it again: release is at least once across a crash, since a repeat is preferred to a loss. A setting change does not release by itself; the next `Post` or r1b's minute tick does. | CH-15, CH-12, OP-9 | `releasePaced`, `packHeld`. |
| O24 | **Pacing settings (W5-Dc-r1a QH-6, SG-r1-5; provisional).** The `Settings` hook takes whole messages `QUIET <a>-<b>` (box-local whole hours 0 to 23, not equal), `QUIET OFF`, `TEXTS <n>` (1 to 20) and `URGENT APPROVAL|AGENT ON|OFF`, parsed as CH-11 parses (case and punctuation ignored), before the loop settings and the agent. Each needs an unlocked session: locked, the message gets the unlock prompt and is held like other chat, and runs only on `RUN` after the unlock. A message of that shape with a bad value (`QUIET 25-7`, `TEXTS 0`, `URGENT update ON`, `URGENT security OFF`) gets one fixed line naming the forms and changes nothing. A change is saved before its fixed-wording reply, which names what still goes at once; a failed save replies that nothing changed. HELP appends one line naming the forms; with the longest `HelpExtra` on main (learning off) the reply is 444 of 459 characters. | CH-11, CH-14, CH-15 | `pacingSetting`, `pacingShape`. |
| O25 | **The hold and forget (release finding, W5-Dc-r1a).** Held texts are not indexed by forget reference, so a CAP-3 forget does not reach a text held overnight; it is sent when the hold is released. The exposure is at most 32 texts for at most one quiet window, already through Disclose, and they sit in owner state as approval items do today. Nothing in a held text is logged. Raised as **release** (BOARD W5-Dc-r17): a later package gives `HeldText` a reference and lets forget drop it. | CAP-3 | `HeldText`, forget's reach. |
| O26 | **Digest and allowance (SG-r1-6; provisional).** The daily digest is held by quiet hours but neither counts against nor is held by the hourly allowance. Built in W5-Dc-r1b; recorded here because the allowance is owner state. | CH-15 | r1b's digest wiring. |
| O27 | **NAME (CH-11, CH-21; CH-21b).** `NAME` alone replies with the name. `NAME <name> <code-generator code>` renames at once and unlocks. In an unlocked session `NAME <name>` gets a fixed-wording reply with a texted 6-digit code, confirmed by `NAME <code>` within `CodeTTL`; a spoofer never sees it, wrong guesses count toward the lockout and void the request after `WrongPerRequest`. In a locked session `NAME <name>` is held; a code-only unlock turns it into that confirmation, never into RUN. A texted confirmation counts only while unlocked; locked, only a strong code confirms. A name failing `boxname.Check` is refused before any code is checked or held. A message counts as NAME only when its argument is a code or of name shape, else it is chat. The waiting rename is in memory (a restart drops it); the name is durable in `State.Name`. `Config.OwnerName` is "" until the setup row wires it. | CH-11, CH-21, A14 | Persist the waiting rename; require a code-generator code even when unlocked |
| O28 | **A held text is revalidated at send (PACE-1 PC-1 to PC-3).** `PostAbout` posts a text with `Subjects`, the facts it states (loops cleared keys), saved with the hold. Every send path (urgent, send-now, release) asks the `SetCurrent` hook first; a text it rejects is dropped and spends no allowance, and with no hook a text with subjects is dropped (fail closed: the owner stays on the alert). The hook runs without `c.mu` held, under `c.pmu`, so held indexes are stable. A text without subjects is unchanged. The check and the modem send are not atomic: a finding that reopens between them can still meet a sent "Cleared", which the urgent return then follows. | OWN-4, CH-15 | If a held text can state something other than a cleared key, give it its own subject kind and hook. |
