# Owner channel: assumptions

Built for PLAN P1-5 against SPEC v0.12 (PR #15; §6 is unchanged from v0.11) on
top of the broker skeleton (PR #19). Each row is a reading of the spec, or a gap
left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| O1 | `Channel` sits in front of `control.Handler` and is its `control.Auth`. It owns every word that carries or checks a code (RESUME, YES, NO, UNDO, MORE, session unlock) and passes STOP, STATUS, HELP and chat through. The control package is unchanged; wiring `Channel` into the daemon's owner socket replaces one line in `daemon.Run` and is left to integration so this PR does not edit P1-2's files while they are in review. | CH-3, CH-11 | Small: `daemon.Run`. |
| O2 | Request IDs are a letter (no I or O) and a digit, or a letter and two digits when those run out, unique among open requests and queued replies. Starting with a letter keeps `YES K3 1 3 482913` unambiguous: ID, item numbers, code. With one request open the ID may be left out; with several, a texted code names its own request, otherwise the box asks for the ID. | CH-12, CH-13 | Small: `parseReply`, `findLocked`. |
| O3 | A partial `YES K3 1 3 <code>` approves the listed items and denies the rest of that batch, so the single-use code never leaves part of a batch open. `NO 2` denies one item and leaves the rest open. Unanswered items expire as denied and are kept for the digest (`TakeExpired`). | CH-13, CH-18 | Keeping the rest open would need a fresh code per remainder. |
| O4 | Code hygiene: 3 wrong replies void a request or RESUME code; 5 wrong codes of any kind in 24 h lock the low tier and end the session unlock, and the owner is told; a code-generator code or grid cell lifts both. **Added:** 10 wrong codes in 24 h pause code checks by text until the oldest ages out. CH-18 bounds texted codes but not guesses at the 6-digit high-tier codes; without a bound a spoofer of the owner's number could guess indefinitely. The cost is that such a spoofer can also deny the owner unlock-by-text for up to a day; the local UI (P2-2) still unlocks. | CH-18 | Security lens may prefer a different bound. |
| O5 | While a session is unlocked, numbers in chat are chat: they are not checked as codes and not stripped. While locked, a whole-message code or a trailing 6-8 digit code is checked and counts as a wrong code if it fails, and the rest of the message is held for 15 minutes and run after the unlock. This closes free guessing inside an unlock window. | CH-14 | Small: `routeLocked`. |
| O6 | A code-generator code is RFC 6238 (SHA-1, 30 s, 6 digits), accepted one step either side, and never at or before the last step accepted, so each code works once. The paper grid is 10x10 cells (A1 to J10) of 6 digits derived from a seed; the box asks for one random unused cell, and only that cell is accepted. Seeds come from the vault (P1-3) through `Secrets`; nothing here stores them. | CH-4, CH-18, CRED-8 | Grid size and cell length are for the Owner Card design (P2-2). |
| O7 | Durable state (unlock expiry, last generator step, spent grid cells, recent wrong codes, low-tier lock) is one JSON file replaced atomically, so a restart reopens nothing. Open requests and queued auto-replies are in memory: a restart drops them, which leaves their journal intents pending (not approved) and drops unsent replies. | CH-18, OP-4 | Persist them if the lens review wants approvals to survive a reboot. |
| O8 | Tiering takes `Facts` the caller says the broker verified. Unverified or missing facts are high risk. An amount at or above the owner's limit is high risk, and a zero limit makes every amount high risk. Grant, CRED-6, recovery and tier-change kinds are always high. | CH-10 | `Classify`. |
| O9 | Approval texts render only verified fields through a fixed alphabet: look-alikes folded (a table for Cyrillic, Greek, accented Latin, fullwidth forms), line breaks removed, GSM-7 extension characters dropped, each field capped, and secret-shaped fields shown as `[hidden]`. A batch lists as many items as fit in three segments and points to `MORE <id>`. | CH-10, CH-12, CH-19 | `render.go`. |
| O10 | The CH-19 filter is fixed patterns: known token formats (AWS, GitHub, Slack, OpenAI/Anthropic-style `sk-`, Stripe, Google API keys, JWTs, private-key headers, `otpauth://`) and a 4-10 character token containing a digit within 4 words of a code word (code, OTP, verification, PIN, passcode, 2FA, MFA, security, login, token). A hit replaces the whole text with a pointer to the local UI. | CH-19 | Pattern list grows through Loop 2 (LOOP-10). |
| O11 | ADP-11 auto-replies: the commitment filter checks secret-shaped content, amounts and currencies, dates, weekdays, times, deadline words, and the owner's phrase list (default: confirm, agree, will pay, approve, sign, accept, matched at word starts). A match becomes a normal approval request. Otherwise the owner gets the reply's first line and `UNDO <id>`, and the reply is released by `DueAutoReplies` after the undo window (default 10 min). If the alert cannot be sent, the reply is dropped. The other ADP-11 conditions (earned, verified thread starter, composer isolation, native scheduled send) belong to the adapter and composer packages. | ADP-11, CH-16 | `commit.go`, `autoreply.go`. |
| O12 | Out of scope here: voice and DTMF (CH-5, CH-17, P2-3), pacing, quiet hours and the digest (CH-15), evidence delivery (CH-20), UNDO for executed effects other than queued replies (CH-16 with REV-3), and unknown-host vault unlock (CRED-8, P2-4). `RequireUnlock` is the hook for the unknown-host boot. | — | Later packages. |
