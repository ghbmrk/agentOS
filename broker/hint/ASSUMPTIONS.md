# Hint schema and emitter: assumptions

Built for P4-1 (hint schema) against SPEC v0.12 OSS-1, OSS-5, and OSS-7.
The clean-room builder (OSS-2), the leakage audit (A12), attestations
(OSS-4, OSS-8), and publication metadata (OSS-6) are later packages. Each
row is a reading of the spec, or a gap left for a later package, that a
reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| H1 | The public schema is `schema.json`, embedded in the build and published with the repository. A schema change is a code change (§11), so the private side can never add a value at runtime. | OSS-1 | Medium: a signed schema file shipped with updates instead. |
| H2 | **Schema rules (`Parse`), test-enforced on the shipped schema.** Every category, kind, field, and value is a lower-case word of at most 32 characters with inner underscores and no digits, so no value can spell a number, a name, an identifier, or free text. Every field has at least two values (a one-value field carries nothing and only adds surface). Values are unique per field. Every category has at least one kind. Unknown and repeated JSON keys are refused. No kind may carry more than `MaxBitsPerHint` (16) bits, measured as log2 of the number of distinct hints of that kind; the shipped schema's largest kind is about 11.1 bits (`skill_gap`). | OSS-1 | Raise the cap only with a security review. |
| H3 | **Which values are allowed is a review duty the rules cannot check.** The shipped values avoid sensitive life domains (health, religion, government benefits, legal matters), since even a bounded choice would say which of those the owner deals with. `service_class` names service types, never specific services. | OSS-1, OSS-3 | Reviewers check every schema diff for this. |
| H4 | A hint has every field of its kind and nothing else: no optional fields, so presence or absence cannot carry information. | OSS-1 | — |
| H5 | **Only the canonical form crosses.** `Canonical` rebuilds the hint from the validated values in fixed key order with the schema version and the kind's embargo mark, so key order, spacing, escapes, or duplicate keys in what a machine submitted cannot carry information. The strict wire parser (`ParseJSON`) refuses non-string values, nesting, unknown or repeated keys, and trailing data before validation. Validation errors name the field, never the submitted value. | OSS-1 | — |
| H6 | **Embargo is a property of the kind, not a choice of the private side.** `vuln` is marked `embargo` in the schema, and every vuln hint crosses marked for the encrypted private-report path. The private side cannot know whether a finding harms other installations; the clean room decides that after rebuilding the regression. | OSS-5 | The clean-room builder (OSS-2) reads the mark and routes. |
| H7 | **Owner policy per category (OSS-7):** `Automatic` (the zero value, so the spec's default), `Ask`, or `Never`. A policy naming an unknown category or mode is a configuration error at `New`, not a silent default. `Approve` and `Decline` are owner actions only; they are not wired to the local page or an owner-channel command yet. | OSS-7 | The local UI package (P2-2) sets the policy and calls `Approve`/`Decline`. |
| H8 | **Every hint is logged where the owner can read it:** forwarded, asked, approved, declined, withheld, duplicate, over-limit, refused, and failed sends. A refused hint (one that failed the schema) is logged with no kind or fields, since what was submitted may be private text. A record is written before the outbox is called, so nothing crosses unlogged; a failed send is a second record pointing at the first, and does not count. Records keep only the UTC day, nothing finer. The file log is mode 0600 and synced per record. Showing the log to the owner (`Log.List`) on the local page is not built. | OSS-1, OSS-7 | P2-2 shows it. |
| H9 | **Daily bound and dedupe (beyond the spec, added for the covert-channel case).** At most `DailyLimit` hints (default 20) cross or are asked per UTC day, and a hint identical to one already crossed or asked today is logged as a duplicate and does not cross again. Together with H2 this bounds what a compromised private side can signal by its choice of hints to about 20 × (16 + log2 kinds) bits a day. Both survive a restart: today's counts and open asks are rebuilt from the log. Withheld and refused hints are not bounded, so a flooding machine can grow the local log; that is a local resource question, not a leak. | OSS-1 | Tune the default once loops emit real hints. |
| H10 | The day boundary is UTC, not the owner's local time. | OSS-4 (day granularity) | Cosmetic. |
| H11 | Nothing calls the emitter yet. Loop 1 and Loop 2 (P3) emit hints through it; the clean-room builder (OSS-2) implements `Outbox`. The emitter holds no credential, reads no private store, and makes no network call. | OSS-1, OSS-2 | — |
