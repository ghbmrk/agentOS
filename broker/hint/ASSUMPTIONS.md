# Hint schema and emitter: assumptions

Built for P4-1 (hint schema) against SPEC v0.12 OSS-1, OSS-5, and OSS-7.
The clean-room builder (OSS-2), the leakage audit (A12), attestations
(OSS-4, OSS-8), and publication metadata (OSS-6) are later packages. Each
row is a reading of the spec, or a gap left for a later package, that a
reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| H1 | The public schema is `schema.json`, embedded in the build and published with the repository. A schema change is a code change (§11), so the private side can never add a value at runtime. | OSS-1 | Medium: a signed schema file shipped with updates instead. |
| H2 | **Schema rules (`Parse`), test-enforced on the shipped schema.** Every category, kind, field, and value is a lower-case word of at most 32 characters with inner underscores and no digits, so no value can spell a number, a name, an identifier, or free text. Every field has at least two values (a one-value field carries nothing and only adds surface). Values are unique per field. Every category has at least one kind. Unknown and repeated JSON keys are refused. No kind may carry more than `MaxBitsPerHint` (16) bits, measured as log2 of the number of distinct hints of that kind; the shipped schema's largest kind is about 11.1 bits (`skill_gap`). | OSS-1 | Raise the cap only with a security review. |
| H3 | **Which values are allowed is a review duty, with a mechanical backstop.** The shipped values avoid sensitive life domains, since even a bounded choice would say which of those the owner deals with. `Parse` refuses any category, kind, field, or value with a part on a fixed sensitive-word list (health, medical, legal, religious, benefits, immigration, tax, and others; `sensitive` in `schema.go`). The list cannot be complete, so reviewers still check every schema diff for this (Security R2 on #40). `service_class` names service types, never specific services. | OSS-1, OSS-3 | Reviewers check every schema diff. |
| H4 | A hint has every field of its kind and nothing else: no optional fields, so presence or absence cannot carry information. | OSS-1 | — |
| H5 | **Only the canonical form crosses.** `Canonical` rebuilds the hint from the validated values in fixed key order with the schema version and the kind's embargo mark, so key order, spacing, escapes, or duplicate keys in what a machine submitted cannot carry information. The strict wire parser (`ParseJSON`) refuses non-string values, nesting, unknown or repeated keys, and trailing data before validation. Validation errors name the field, never the submitted value. | OSS-1 | — |
| H6 | **Embargo is a property of the kind, not a choice of the private side.** `vuln` is marked `embargo` in the schema, and every vuln hint crosses marked for the encrypted private-report path. The private side cannot know whether a finding harms other installations; the clean room decides that after rebuilding the regression. | OSS-5 | The clean-room builder (OSS-2) reads the mark and routes. |
| H7 | **Owner policy per category (OSS-7):** `Automatic` (the zero value, so the spec's default), `Ask`, or `Never`. A policy naming an unknown category or mode is a configuration error at `New`, not a silent default. An approved hint joins the next batch like any other. `Approve` and `Decline` must be reachable only from an owner action; they are not wired yet. | OSS-7 | The local UI package (P2-2) and the owner channel wire them; see the wiring conditions below. |
| H8 | **Every hint is logged where the owner can read it:** queued, asked, approved, declined, withheld, duplicate, over-limit, refused, forwarded, and failed sends. A refused hint (one that failed the schema) is logged with no kind or fields, since what was submitted may be private text. Forwarded records are written before the outbox is called, so nothing crosses unlogged; a failed send is a record per hint pointing at its Forwarded record, and those hints stay queued. Records keep only the UTC day. The file log is mode 0600 and synced per record. A last line torn by a crash mid-write is removed on open (nothing it described happened, since records precede effects) and `Repaired` reports it; damage elsewhere refuses to start. **OSS-1's "visible to the owner" is only partly met:** `Log.List` exists, but nothing shows it to the owner until P2-2. | OSS-1, OSS-7 | P2-2 shows it (UX 2 below). |
| H9 | **Daily cap, reserve, backlog, dedupe (beyond the spec, for the covert-channel case).** One batch carries at most `DailyLimit` hints (default 20). `EmbargoReserve` slots (default a quarter of the limit) are kept for embargo kinds, and slots one class leaves unused go to the other, so a flood of routine hints cannot starve a `vuln` hint (OSS-5). Hints over the cap wait for later batches, oldest first, in a queue bounded per class by `MaxBacklog` (default 7 × the limit); over that bound a hint is logged over-limit and dropped, and a full routine queue never blocks an embargo hint. A hint identical to one waiting, asked, or queued today is a duplicate. **What the bound is:** with only the set crossing (H12), a day's batch is a choice of at most 20 of the 2,574 distinct hints the shipped schema allows, about log2 C(2574, 20) ≈ 165 bits a day. The limit and dedupe window are held pending the arbitrator's ruling on Security R1 (5 a day, 7-day dedupe, about 50 bits a day). K1 below is the real control on this channel. | OSS-1, OSS-5 | Set from the arbitrator's ruling. |
| H10 | **The day is UTC and only moves forward.** A clock stepped back keeps the latest day seen (rebuilt from the log at start), so it cannot reopen an earlier day's dedupe or batch; a batch waits until the clock reaches the latest day again. | OSS-4 (day granularity) | Cosmetic for the UTC choice. |
| H11 | Nothing calls the emitter yet. Loop 1 and Loop 2 (P3) emit hints through it; a daemon tick calls `Release`; the clean-room builder (OSS-2) implements `Outbox`. The emitter holds no credential, reads no private store, and makes no network call. | OSS-1, OSS-2 | — |
| H12 | **Only the set crosses (Security B1 on #40).** `Emit` never sends. Each UTC day's hints are held and released as one batch by `Release` once the release time (`ReleaseAt`, default 04:00 UTC) has passed on a later day, at most one batch a day, sorted by canonical form. The order hints were emitted in and the time they were emitted do not reach the outbox. A failed send is retried at the next `Release` call. | OSS-1, OSS-6 | — |

## Conditions for wiring (from the #40 review)

These bind whoever connects the emitter to the rest of the box.

- **K1 (Security):** broker code derives every hint from structured, journaled facts. No agent machine ever chooses, words, or picks a hint. This is the real control on the remaining channel (H9).
- **K2 (Security):** vuln hints keep their embargo path (H6). The clean room publishes nothing derived from one until that path clears.
- **UX 1:** state the informed default once, in the §8.1 setup defaults and the first digest: "Shares anonymous fixed-choice hints with AgentOS maintainers (no text, no names); change any time".
- **UX 2:** a weekly digest line, "Shared N anonymous hints this week (MORE H)", plus a local log in broker-rendered words with dates in the owner's local day.
- **UX 3:** in Ask mode, hints go into the CH-13 batch as numbered YES/NO items with no code. Unanswered items expire as declined.
- **UX 4:** owner policy changes are echoed back in fixed wording; "stop sharing hints" works by text through the CH-11 pause and revoke path.
- **Owner-only settlement:** P2-2 restricts `Approve` and `Decline` to an owner action.
