# Guest plane and OpenClaw guest: assumptions

Built for PLAN P1-7 against SPEC v0.12 (PR #15), on the VM lifecycle
(PR #23), the vault and egress proxy (#21), assurance CI (#20), and the
owner channel (#22). Each row is a reading of the spec, or a gap left for
a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| G1 | Each machine gets one Unix socket, `broker.sock`, in its own 0700 directory, mounted into its sandbox (V15). Identity is the socket the request arrived on; nothing the guest sends names a machine. One socket carries every ARC-6 service as HTTP paths: `/model/...` (a), `/mcp` (b), `/owner/next` and `/owner/reply` (c). Anything else is 404. Paths are matched as sent, never cleaned or redirected (Go 1.26's `ServeMux` answers an unclean path with a 307 that keeps the method and body): a `/model/` path goes to the model chain with its escapes and dot segments intact, where the shape check refuses them (on the box the model router in the vault process, which serves only the exact unescaped `/v1/chat/completions` paths; the egress proxy, E1, where a test rig serves it directly), and any other path must match exactly with nothing escaped. One machine holds at most `MaxOpenConns` (default 16) of the broker's connections: past that the broker accepts nothing more from it until one closes, so further connections wait in the kernel and cost the broker no descriptor (CH-2; a 3000-connection flood leaves STOP answering). Idle connections close after 15 s, header reads after 10 s. At most `MaxConns` (default 8) requests run at once; more get 429. | ARC-6, ARC-7, CH-2 | Small: `Plane.Open`. |
| G2 | Broker tools are MCP over streamable HTTP, the subset S4 qualified with OpenClaw 2026.9.8: one JSON-RPC request per POST, one JSON response; no SSE stream (GET is 405), no sessions, no batches, no server-initiated messages. It is stdlib code, not an SDK, because the broker process takes no third-party code (DEP-1) and the server side of this subset is small. | ARC-6, DEP-1 | Add SSE if a qualified guest needs server-initiated messages. |
| G3 | Two tools: `effect_request` (submit, authorize, dispatch an intent) and `effect_status`. Names avoid "intent", which OpenClaw already uses for a built-in (S4 finding 4). OpenClaw defers MCP tools behind its `tool_search` and `tool_call`; the end-to-end run goes through that path. The guest learns only the broker's state, the permission reason, and fixed error strings, never executor evidence or engine errors (those go to the broker log). Account and action must be lowercase ASCII names (`^[a-z0-9][a-z0-9._-]{0,63}$`), so no spacing, invisible, look-alike, or case variant passes for another name. Refused before anything is journaled: the broker's own account (`broker`) and any `meta.*` action, which are the owner's and the broker's (some narrow and so pass STOP, OP-5); params over 16 KiB, more than 50 recipients, or a recipient over 320 bytes; requests past a per-machine token bucket (burst 20, one per 3 s); and an account with no adapter (with no `Route`, as in `agentosd` today, that is every account). | ARC-6, ADP-10, CRED-7, OP-5, CH-2 | Tools grow with adapters. |
| G4 | Intent IDs are `<lineage>/<request_id>` and the origin is `guest:<lineage>`. A lineage is the root machine's ID plus a nonce drawn when it was created, and forks inherit it: forks share their source's memory, so a request a fork repeats from its source's history is the same intent and runs at most once (OP-1), while a machine re-created under an old ID starts a new namespace. Machines outside a lineage cannot read or collide with its requests. Step (REV-1) runs after an `effect_request` the journal took, not after reads, refusals, or malformed calls. Steps are coalesced per machine: at most one per `StepInterval` (2 s), and requests inside the interval share one trailing snapshot, so a looping guest cannot fill the snapshot store that every machine shares (RES-4). A failed Step is logged and does not fail the call, because the effect has already been journaled. | OP-1, REV-1, RES-4 | If a missed Step must block, fail the tool call instead. |
| G5 | Owner messages are delivered at least once. Each is handed to the guest once per incarnation of its machine and again only after the machine restarts (preemption, rebuild, rollback, or a broker restart: the vm manager opens the machine's services again), never because the guest is slow, so long tasks do not get the message twice. A restart from a full checkpoint taken after delivery can still hand it out again; the bridge treats a repeat as a new turn. A reply naming any pending message of the same machine is accepted once. The inbox holds 32 messages and is written through to `InboxPath` (0600, broker-held like the journal; owner text only after the channel has stripped codes), so a broker restart redelivers unanswered chat instead of dropping it; a destroyed machine's messages are dropped. A message not marked public raises the machine to private before the guest can read it (REV-5). Messages loaded from `InboxPath` raise the machine to private before `/owner/next` hands one out, since the store can outlive the machine record and a fresh machine under the same ID starts public (security C1 on #56); a failed raise hands out nothing (503). The raise is not in `Open`, because the machine manager opens services while holding the machine's lock. | ARC-6, REV-5, OP-4 | — |
| G6 | ARC-6 (d), uncredentialed egress by label, is not served: machines have no network but their socket. | ARC-6 | Later package. |
| G7 | Model calls are metered (OP-8) at the socket before any provider sees them. `Start` charges one call, the input estimated from the request's size (bytes/4), and an output reservation. The reservation is also what the provider is sent: every output limit in the body (`max_tokens`, `max_completion_tokens`, `max_output_tokens`; reasoning budgets sit inside them) is clamped to `MaxReserve`, one is inserted at `DefaultReserve` when none is present, and the body is re-encoded so duplicate keys cannot smuggle a second limit; a body that is not one JSON object is refused, and so is any `n` other than 1 (several choices would each run to the limit). The meter sits in front of every model path, router or raw proxy, so this one check covers both. `MaxReserve` defaults to 32000, the router's ceiling (`route.DefaultMaxOutputTokens`, pinned by a test), and `DefaultReserve` to `MaxReserve`. So parallel calls cannot overshoot a cap against a provider that honors its limit. `Done` settles by the arbitrator's rule. A response that completed normally (a parsed JSON body, or a stream that reached `[DONE]`, `message_stop`, or a `message_delta` with a `stop_reason`) and carries provider-reported usage whose output count came after the message started (not only `message_start`'s placeholder) is charged that usage. Behind the model router (`Routed`), the router reports the provider's usage to the meter through the request context (`route.WithUsage`, `meter.Report`), so the meter settles from it even when the guest asked for none; without the router the meter reads OpenAI `usage` (the egress proxy forces `stream_options.include_usage`) and Anthropic `message_start`/`message_delta` from the response. Cached input counts at the provider's cached weight: Anthropic reads 0.1 and writes 1.25; OpenAI 0.5, the smallest discount it offers; an unknown provider's reads in full. Otherwise (no usage, a truncated or unparseable body, a provider answer the router could not use, which it reports by size, a hang-up) output is the content, argument, and reasoning characters counted (the router's count or the meter's, whichever is larger), not framing, and on a response cut off before its end that count is the least output charged; a body that could not be read at all is charged by its size. A call that never reached the vault process (a dial failure) is charged its call and input estimate; one that reached it but got no answer is charged its full output reservation, since the provider may have billed output. The call runs on a context the guest cannot cancel (10 min bound), and keeps reading after the guest hangs up, so hanging up does not shrink the charge. Exhaustion answers 429 in OpenAI's `insufficient_quota` shape and is journaled once per exhausted scope; a task's owner notice is sent once, until the owner extends the task. Default caps (300 calls and 3M tokens per machine per 24 h; 1500 calls and 15M tokens overall; owner extensions up to 300 calls and 3M tokens a day) are placeholders until sized from measured task usage. | OP-8 | Tune in `meter.Default*`. |
| G8 | `agentosd` forwards each machine's model route, after the OP-8 meter, to the vault process `agentos-egress` (P2-4a, egress K4), which holds the unlocked vault and runs the model router and the proxy; `agentosd` links neither. The provider-reported usage of each served call comes back in a trailer that the meter charges (egress K9). Until the owner unlocks the vault (egress K5) model calls answer 503. The same chain (guest socket, meter, router, proxy, provider) is composed in one process through `guest.Routed` in `e2e/routed_test.go`; the proxy layer under it is attacked directly through the guest socket in `e2e/a14_test.go`, the A5 canary target. That harness runs the guest side in-process rather than inside gVisor; the gVisor boundary is proven separately by the vm integration tests and `TestIntegrationOpenClawGuest`. | CRED-1, CRED-5, ARC-6 | — |
| G9 | There is no modem driver before P2-3, so owner texts arrive only through the owner socket and the channel's outbound texts, including guest answers, are not sent on the box. `e2e/owner_test.go` proves the path with the modem simulator. | CH-1, ARC-6 | P2-3. |
| G10 | The guest bridge (`cmd/agentos-guest-bridge`) is guest code: PID 1 inside the machine, root-replaceable, trusted by nothing in the broker. It passes loopback HTTP to the socket and owner messages to OpenClaw's chat-completions API with a random guest-local token. Everything it could do, the guest could do itself through the socket. | ARC-7 | — |
| G11 | The OpenClaw image is a test rig (`guest/openclaw/build-rootfs.sh`): Node and OpenClaw pinned by version and hash, install scripts off, the S4 profile, and the host's shell and a few tools for OpenClaw's exec tool. The box's real image comes from P2-1. The guest profile is defense in depth only (ARC-7): containment, custody, and spend do not depend on it. | ARC-3, ARC-7, DEP-1 | P2-1. |
| G12 | Grants and the approval policy are wired by the grants package ([assumptions](../grants/ASSUMPTIONS.md)): `daemon.Run` uses `grants.Gate` as the policy, and `agentosd` passes it to this plane as `Effects` and `Route`, so only accounts a grant connects route, and every irreversible effect waits on the owner or an exactly matching pre-allowance. Intents left pending by a restart, including a crash between submit and authorize, are re-issued to the owner or denied with a reason (GR10); `effect_status` says the owner will be asked again while they are held. Each intent records the submitting machine and its label (`Config.Label`; unknown means private). Requests are partitioned by label (`<lineage>/private/<request_id>` for private machines), so a private fork cannot pass anything to its public parent through request IDs, states, or reasons. A private repeat of a public-era request reads it without driving it (grants GR13). `broker` and `meta.*` are refused before routing, unjournaled (GR14). `Boot` runs on every start. | OP-4, OP-5, CH-13, REV-5 | Grants package. |
| G13 | Guest answers reach the owner through `owner.Channel.Notify`, which always starts them with `Agent: ` so agent text cannot pass for a broker template (an approval request, a code prompt), and replaces secret-shaped text with a pointer (CH-19). They are not yet paced or held for quiet hours (CH-15). | CH-15, CH-19 | Put agent replies under CH-15 pacing with the digest. |
| G14 | **Goal IDs (P3-7).** Each effect request is stamped with a goal ID, `owner:<message id>`, naming the owner message its lineage serves, so a task is one owner request rather than the whole guest lineage (compiled skills K3, Loop 1 L8 and L10, replay R4 all group by it). The broker chooses it; nothing the guest sends names a goal. The goal is the one owner message the lineage's guests hold handed-out and unanswered; with none, the last one the lineage was handed, since work that goes on after the answer still serves it, until another message is delivered to the lineage or `GoalQuiet` (30 min) has passed since that message was handed out (only the owner's side moves the window; guest requests and model calls never extend it, arbitrator on #55), after which requests go unattributed (potency PG1: recurring work does not merge into an unrelated owner task); with several open at once (the shipped bridge takes one at a time, so only a modified guest does this), none, because the broker cannot tell which one a request serves and does not guess. A message delivered but not yet fetched is not served. Because the goal is part of an intent's identity (OP-1), it is fixed by the request's first submission: a repeat, from the machine or a fork, keeps the journaled goal whatever the lineage serves by then, and a concurrent first submission that lost to another goal takes the winner's. Intents journaled before this change keep their empty goal. The last handed-out message per lineage is kept with the inbox (`InboxPath`), so work after a broker restart still names its goal, and is dropped when the lineage's last open machine is destroyed. Model calls also count against the goal (`meter.WithGoal`, `meter.GoalUsage`), for accounting only: caps stay per machine, task, and box (OP-8). Goal usage is kept until a goal has been idle a week. **Limits:** a guest that fetches two messages at once leaves its requests unattributed, which groups them by origin (Loop 1 holds a held-out goal's origin bucket and the lineage's next goal too, loops L8, so neither is mined into a builder's brief); a guest that answers one message and works on another's request while holding none open attributes it to the last one, which affects grouping and metrics only, never authority. Work started by events (timers, mail) must never inherit the last owner goal (arbitrator on #55): the event-bus wiring ends it on an event delivery and gives such work its own goal or none. Worker machines built from a base image (CAP-8) are not in the creator's lineage; the worker tool must carry the creator's goal. Message timing affects grouping only, never authority; the guards below keep a guest from using it to persist its own steps. | OP-1, OP-7, OP-8 | Conditions from the lens gate on #55, binding later packages: (a) before the event bus feeds guests, an event delivery ends the last owner goal and event-triggered work gets its own goal (`event:<id>`) or none (security C2, potency PG1); (b) the CAP-8 worker tool stamps the creator's goal at creation (security C3); (c) compiled skills record their source lineages, and a guest reset for suspected compromise or a Loop 2 finding on it reverts skills compiled from that lineage (security C1); (d) no owner-facing usage line uses `GoalUsage` before (a) and (b) land (UX); (e) if L10 needs totals past the 7-day idle window, persist them elsewhere (security R1). |
| G15 | Further broker tools (`Config.Tools`) are listed after the effect tools and called with the machine and lineage the socket fixes; `agentosd` serves the owner-question tools there (`question.GuestTools`, CAP-10; W9) and the recall tools (CAP-3; W2). They are not effects: nothing is journaled and no step snapshot is taken. | ARC-6, CAP-3, CAP-10 | — |
| G16 | **Delivered tasks (W3; potency PW3 on #90).** `OwnerAgent.Delivered`, if set, is told each owner message delivered to the agent machine as its goal ID (`GoalID`), text, and PUBLIC mark, so agentosd can keep the task text a harvested case needs (loops L6). Replay deliveries never report one. | OP-7 | — |
