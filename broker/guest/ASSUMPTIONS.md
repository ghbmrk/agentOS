# Guest plane and OpenClaw guest: assumptions

Built for PLAN P1-7 against SPEC v0.12 (PR #15), on the VM lifecycle
(PR #23), the vault and egress proxy (#21), assurance CI (#20), and the
owner channel (#22). Each row is a reading of the spec, or a gap left for
a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| G1 | Each machine gets one Unix socket, `broker.sock`, in its own 0700 directory, mounted into its sandbox (V15). Identity is the socket the request arrived on; nothing the guest sends names a machine. One socket carries every ARC-6 service as HTTP paths: `/model/...` (a), `/mcp` (b), `/owner/next` and `/owner/reply` (c). Anything else is 404. Each machine has at most `MaxConns` (default 8) requests in flight; more get 429. | ARC-6, ARC-7 | Small: `Plane.handler`. |
| G2 | Broker tools are MCP over streamable HTTP, the subset S4 qualified with OpenClaw 2026.9.8: one JSON-RPC request per POST, one JSON response; no SSE stream (GET is 405), no sessions, no batches, no server-initiated messages. It is stdlib code, not an SDK, because the broker process takes no third-party code (DEP-1) and the server side of this subset is small. | ARC-6, DEP-1 | Add SSE if a qualified guest needs server-initiated messages. |
| G3 | Two tools: `effect_request` (submit, authorize, dispatch an intent) and `effect_status`. Names avoid "intent", which OpenClaw already uses for a built-in (S4 finding 4). OpenClaw defers MCP tools behind its `tool_search` and `tool_call`; the end-to-end run goes through that path. The guest learns only the broker's state and permission reason, never executor evidence. An account with no adapter is refused with no intent journaled. | ARC-6, ADP-10, CRED-7 | Tools grow with adapters. |
| G4 | Intent IDs are `<lineage>/<request_id>` and the origin is `guest:<lineage>`, where lineage is the machine a fork descends from. Forks share their source's memory, so a request a fork repeats from history is the same intent and runs at most once (OP-1). Machines outside a lineage cannot read or collide with its requests. Step (REV-1) runs after every `tools/call`, on the calling machine, with a 30 s bound; a failed Step is logged and does not fail the call, because the effect has already been journaled. | OP-1, REV-1 | If a missed Step must block, fail the tool call instead. |
| G5 | Owner messages are delivered at least once: each is leased to the guest for 15 min and handed out again if no reply arrives; replies must name a pending message of the same machine. The inbox holds 32 messages, in memory: a broker restart drops unanswered chat. A message not marked public raises the machine to private before the guest can read it (REV-5). | ARC-6, REV-5 | Persist the inbox if dropped chat proves costly. |
| G6 | ARC-6 (d), uncredentialed egress by label, is not served: machines have no network but their socket. | ARC-6 | Later package. |
| G7 | Model calls are metered (OP-8) at the socket before any provider sees them: one call and the request's estimated input tokens are charged up front, output tokens after. Tokens are estimated as bytes/4, since the broker counts only what it observes and does not parse every provider's usage field. Exhaustion answers 429 in OpenAI's `insufficient_quota` shape (how OpenClaw retries it is not yet measured) and is journaled once per exhausted scope. Default caps (300 calls and 3M tokens per machine per 24 h; 1500 calls and 15M tokens overall; owner extensions up to 300 calls and 3M tokens a day) are placeholders pending the budget re-estimate. | OP-8 | Tune in `meter.Default*`. |
| G8 | `agentosd` forwards each machine's model route, after the OP-8 meter, to the vault process `agentos-egress` (P2-4a, egress K4), which holds the unlocked vault and runs the proxy; `agentosd` links neither. Until the owner unlocks the vault (egress K5) model calls answer 503. The chain is also composed in one process in `e2e/a14_test.go`, the A5 canary target. That harness runs the guest side in-process rather than inside gVisor; the gVisor boundary is proven separately by the vm integration tests and `TestIntegrationOpenClawGuest`. | CRED-1, CRED-5, ARC-6 | — |
| G9 | There is no modem driver before P2-3, so owner texts arrive only through the owner socket and the channel's outbound texts, including guest answers, are not sent on the box. `e2e/owner_test.go` proves the path with the modem simulator. | CH-1, ARC-6 | P2-3. |
| G10 | The guest bridge (`cmd/agentos-guest-bridge`) is guest code: PID 1 inside the machine, root-replaceable, trusted by nothing in the broker. It passes loopback HTTP to the socket and owner messages to OpenClaw's chat-completions API with a random guest-local token. Everything it could do, the guest could do itself through the socket. | ARC-7 | — |
| G11 | The OpenClaw image is a test rig (`guest/openclaw/build-rootfs.sh`): Node and OpenClaw pinned by version and hash, install scripts off, the S4 profile, and the host's shell and a few tools for OpenClaw's exec tool. The box's real image comes from P2-1. The guest profile is defense in depth only (ARC-7): containment, custody, and spend do not depend on it. | ARC-3, ARC-7, DEP-1 | P2-1. |
| G12 | No grants or approval policy are wired on the box yet: `daemon.Run` keeps its deny-all policy, so every `effect_request` from a guest is journaled and denied until grants (OP-5) and the policy that opens owner approval requests (`owner.Channel.Request`) land. The end-to-end tests use an allow-all policy to prove the path. So no intent can be waiting on owner approval yet, and P1-5's carry-forward (close approval-pending intents that have no live request after a restart) has nothing to close; it moves to the package that connects policy to `Channel.Request`. An intent left `pending` by a crash between submit and authorize is finished when the guest retries the same `request_id`. `Boot` runs on every start. | OP-4, OP-5, CH-13 | Grants and approval policy package. |
