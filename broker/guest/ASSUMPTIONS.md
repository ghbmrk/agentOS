# Guest plane and OpenClaw guest: assumptions

Built for PLAN P1-7 against SPEC v0.12 (PR #15), on the VM lifecycle
(PR #23), the vault and egress proxy (#21), assurance CI (#20), and the
owner channel (#22). Each row is a reading of the spec, or a gap left for
a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| G1 | Each machine gets one Unix socket, `broker.sock`, in its own 0700 directory, mounted into its sandbox (V15). Identity is the socket the request arrived on; nothing the guest sends names a machine. One socket carries every ARC-6 service as HTTP paths: `/model/...` (a), `/mcp` (b), `/owner/next` and `/owner/reply` (c). Anything else is 404. One machine holds at most `MaxOpenConns` (default 16) of the broker's connections: past that the broker accepts nothing more from it until one closes, so further connections wait in the kernel and cost the broker no descriptor (CH-2; a 3000-connection flood leaves STOP answering). Idle connections close after 15 s, header reads after 10 s. At most `MaxConns` (default 8) requests run at once; more get 429. | ARC-6, ARC-7, CH-2 | Small: `Plane.Open`. |
| G2 | Broker tools are MCP over streamable HTTP, the subset S4 qualified with OpenClaw 2026.9.8: one JSON-RPC request per POST, one JSON response; no SSE stream (GET is 405), no sessions, no batches, no server-initiated messages. It is stdlib code, not an SDK, because the broker process takes no third-party code (DEP-1) and the server side of this subset is small. | ARC-6, DEP-1 | Add SSE if a qualified guest needs server-initiated messages. |
| G3 | Two tools: `effect_request` (submit, authorize, dispatch an intent) and `effect_status`. Names avoid "intent", which OpenClaw already uses for a built-in (S4 finding 4). OpenClaw defers MCP tools behind its `tool_search` and `tool_call`; the end-to-end run goes through that path. The guest learns only the broker's state, the permission reason, and fixed error strings, never executor evidence or engine errors (those go to the broker log). Refused before anything is journaled: the broker's own account (`broker`) and any `meta.*` action, which are the owner's and the broker's (some narrow and so pass STOP, OP-5); params over 16 KiB, more than 50 recipients, or a recipient over 320 bytes; requests past a per-machine token bucket (burst 20, one per 3 s); and an account with no adapter (with no `Route`, as in `agentosd` today, that is every account). | ARC-6, ADP-10, CRED-7, OP-5, CH-2 | Tools grow with adapters. |
| G4 | Intent IDs are `<lineage>/<request_id>` and the origin is `guest:<lineage>`. A lineage is the root machine's ID plus a nonce drawn when it was created, and forks inherit it: forks share their source's memory, so a request a fork repeats from its source's history is the same intent and runs at most once (OP-1), while a machine re-created under an old ID starts a new namespace. Machines outside a lineage cannot read or collide with its requests. Step (REV-1) runs after an `effect_request` the journal took, not after reads, refusals, or malformed calls. Steps are coalesced per machine: at most one per `StepInterval` (2 s), and requests inside the interval share one trailing snapshot, so a looping guest cannot fill the snapshot store that every machine shares (RES-4). A failed Step is logged and does not fail the call, because the effect has already been journaled. | OP-1, REV-1, RES-4 | If a missed Step must block, fail the tool call instead. |
| G5 | Owner messages are delivered at least once. Each is handed to the guest once per incarnation of its machine and again only after the machine restarts (preemption, rebuild, rollback, or a broker restart: the vm manager opens the machine's services again), never because the guest is slow, so long tasks do not get the message twice. A restart from a full checkpoint taken after delivery can still hand it out again; the bridge treats a repeat as a new turn. A reply naming any pending message of the same machine is accepted once. The inbox holds 32 messages and is written through to `InboxPath` (0600, broker-held like the journal; owner text only after the channel has stripped codes), so a broker restart redelivers unanswered chat instead of dropping it; a destroyed machine's messages are dropped. A message not marked public raises the machine to private before the guest can read it (REV-5). | ARC-6, REV-5, OP-4 | — |
| G6 | ARC-6 (d), uncredentialed egress by label, is not served: machines have no network but their socket. | ARC-6 | Later package. |
| G7 | Model calls are metered (OP-8) at the socket before any provider sees them. `Start` charges one call, the input estimated from the request's size (bytes/4), and an output reservation from the request's own limit (`max_tokens`, `max_completion_tokens`, `max_output_tokens`; reasoning budgets sit inside it), clamped to 32768 and defaulting to 8192, so parallel calls cannot overshoot a cap. `Done` settles by the arbitrator's rule. A response that completed normally (a parsed JSON body, or a stream that reached `[DONE]` or `message_stop`) and carries provider-reported usage is charged that usage: OpenAI `usage` (the egress proxy forces `stream_options.include_usage` on streams; `completion_tokens` includes hidden reasoning), Anthropic `message_start`/`message_delta`. Cached input counts at the provider's cached weight: Anthropic reads 0.1 and writes 1.25; OpenAI 0.5, the smallest discount it offers. Otherwise (no usage, a truncated body, a hang-up) output is the content, argument, and reasoning characters the broker counted, not framing, and on a stream cut off before its end that count is the least output charged. The call runs on a context the guest cannot cancel (10 min bound), and keeps reading after the guest hangs up, so hanging up does not shrink the charge. Exhaustion answers 429 in OpenAI's `insufficient_quota` shape and is journaled once per exhausted scope; a task's owner notice is sent once, until the owner extends the task. Default caps (300 calls and 3M tokens per machine per 24 h; 1500 calls and 15M tokens overall; owner extensions up to 300 calls and 3M tokens a day) are placeholders until sized from measured task usage. | OP-8 | Tune in `meter.Default*`. |
| G8 | `agentosd` forwards each machine's model route, after the OP-8 meter, to the vault process `agentos-egress` (P2-4a, egress K4), which holds the unlocked vault and runs the proxy; `agentosd` links neither. Until the owner unlocks the vault (egress K5) model calls answer 503. The chain is also composed in one process in `e2e/a14_test.go`, the A5 canary target. That harness runs the guest side in-process rather than inside gVisor; the gVisor boundary is proven separately by the vm integration tests and `TestIntegrationOpenClawGuest`. | CRED-1, CRED-5, ARC-6 | — |
| G9 | There is no modem driver before P2-3, so owner texts arrive only through the owner socket and the channel's outbound texts, including guest answers, are not sent on the box. `e2e/owner_test.go` proves the path with the modem simulator. | CH-1, ARC-6 | P2-3. |
| G10 | The guest bridge (`cmd/agentos-guest-bridge`) is guest code: PID 1 inside the machine, root-replaceable, trusted by nothing in the broker. It passes loopback HTTP to the socket and owner messages to OpenClaw's chat-completions API with a random guest-local token. Everything it could do, the guest could do itself through the socket. | ARC-7 | — |
| G11 | The OpenClaw image is a test rig (`guest/openclaw/build-rootfs.sh`): Node and OpenClaw pinned by version and hash, install scripts off, the S4 profile, and the host's shell and a few tools for OpenClaw's exec tool. The box's real image comes from P2-1. The guest profile is defense in depth only (ARC-7): containment, custody, and spend do not depend on it. | ARC-3, ARC-7, DEP-1 | P2-1. |
| G12 | No grants, approval policy, or adapters are wired on the box yet. `agentosd` sets no `Route`, so every `effect_request` is refused before the journal (G3); with a route, `daemon.Run`'s deny-all policy journals and denies it. The end-to-end tests use a route and an allow-all policy to prove the path. So no intent can be waiting on owner approval yet, and P1-5's carry-forward (close approval-pending intents that have no live request after a restart) has nothing to close; it moves to the package that connects policy to `Channel.Request`. An intent left `pending` by a crash between submit and authorize is finished when the guest retries the same `request_id`. `Boot` runs on every start. | OP-4, OP-5, CH-13 | Grants and approval policy package. |
| G13 | Guest answers reach the owner through `owner.Channel.Notify`, which always starts them with `Agent: ` so agent text cannot pass for a broker template (an approval request, a code prompt), and replaces secret-shaped text with a pointer (CH-19). They are not yet paced or held for quiet hours (CH-15). | CH-15, CH-19 | Put agent replies under CH-15 pacing with the digest. |
