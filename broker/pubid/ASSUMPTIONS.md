# Publication identity: assumptions

Built for BOARD OSS-6 against SPEC v0.12 OSS-6, with OSS-4, OSS-8 and OSS-9 in view. Each row is a reading of the spec, or a gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| P1 | **The key comes from crypto/rand and nothing else.** No owner name, number, account, host name, serial or vault material goes into it. The identity file holds exactly `epoch` and `seed` (strictly parsed: no other, repeated or nested key), mode 0600; a file others could read gets a fresh key at once, written 0600 (L3 SHOULD 8 on #163). `Key` hands out a copy, and a rotated-out key is zeroed in memory. An import test shows the package links no other broker package and no network or process package, so it cannot read an owner store. A damaged file is refused, never silently replaced. | OSS-6 | — |
| P2 | **Every installation rotates at the same instants.** Epochs are fixed 28-day UTC periods from one public reference (Sunday 2026-01-04 00:00 UTC). A per-box schedule would let an observer match the day one key stops and another starts. Each epoch's key is fresh, and nothing (no cross-signature, no record) links it to the previous one. The new file replaces the old one in one rename, so the old seed is not left beside it. Whenever the clock is in another epoch than the key's, earlier or later, the box draws a fresh key for that epoch, so a key never outlives a global boundary, even after a clock that was far ahead is corrected (L3 MUST 1 on #163); an old key is never made again. Whoever can set the clock can force extra rotations, which yield new keys and reveal nothing. Every write syncs the directory after its rename. | OSS-6 | Shorter or longer epochs change only the constant. |
| P3 | **Gap: the old seed is overwritten logically, not erased physically.** Flash may keep the old blocks. State-disk encryption (P2-1) covers that, as it does for the vault. | OSS-6 | Host image. |
| P4 | **Batched and delayed.** `Queue` never publishes. Each item waits a whole number of extra days, drawn when it is queued: 1 to `MaxDelayDays` (default 3), from crypto/rand. It then leaves in that day's single batch, at the fixed release time (05:00 UTC, an hour after the hint emitter's 04:00). Each item is signed at release with the epoch's key and the batch is sorted by its signed bytes, so neither the hour nor the day an event happened, nor the queue order, shows. A day with nothing due publishes nothing. The day draw is one byte mod 3 (86/85/85 of 256); that bias is immaterial. The queue holds at most 256 items of at most 1 MiB each, and a refusal never echoes the payload. | OSS-6 | — |
| P5 | **Each day is published at most once, a crash cannot re-sign, and no clock change shortens a delay.** A batch is recorded before the `Sender` is called and confirmed after it. One that is not confirmed is resent unchanged (same bytes, same day) at the next release, even after a restart or a key rotation, and no new batch forms in that call. So the same items never appear under two keys. **Clock model (DECISIONS.md "OSS-6 clock"; rounds 4 and 5; `outbox` in publisher.go):** the wall clock is the only time the box keeps across restarts, and it can be wrong by any amount either way and change at any moment, so no item carries a date. An item stores how many counted days it still waits. A release with a plausible clock (below), after the release time, steps when it moves on from the day the last release saw by one to three days; it counts its day only if that last release had itself stepped, the day was never counted (the newest 400 are remembered), and, on the same boot, at least 20h of monotonic time (CLOCK_BOOTTIME, which counts suspend; OSS-6c; the outbox keeps that reading and the boot id, OSS-6e) have passed since the last count; a day the floor defers stays unseen, so a later release that day counts it. A step back or a larger move is a jump; the release after a jump never counts. A batch forms only on a counted day. An item queued before a release has counted today waits one day more. G1: within one process an item with delay k leaves no sooner than (k−1)·20h after it was queued, whatever the clock does; with a right clock, no sooner than k−1 days and the release time. G2: a broker restart on the same boot does not open the 20h floor. A stored reading ahead of the clock is corrupt and counts no day; another boot id is ignored. Someone who controls the clock and can force new boots can make one day count per boot without real time passing, so the bound is (k−1−r)·20h for r boots during the wait (wiring condition W5 narrows this). G3: off days only lengthen waits; a box off for up to two days in a row keeps counting a day each time it is on; after three or more, the first two days it sees do not count. G4: no remembered day gets two batches; no stored date can freeze the outbox. Checked by `TestOSS6ClockModel` (random offsets −71h to +71h in 7h steps, days to months back, days ahead, +100y; off spans; restarts), `TestOSS6StepBackOntoAnOffDay`, `TestOSS6MonotonicFloor` and `TestOSS6OffDaysKeepCounting`. Residual: a clock behind by more than the remembered span can reuse a day label. **Clock plausibility (round 2):** a clock is plausible when it is not before `pubid.Reference` (2026-01-04T00:00Z, the public start of epoch 0; an unset clock reads earlier) and its year is at most 9999. Any other clock neither queues (`ErrClock`) nor counts. Start sweeps temporary files a crash left (the identity and the outbox belong to one broker process, which opens each once at start, so no other writer's file is in flight), and refuses an identity or outbox directory that is a symlink, belongs to another user, or is writable by its group or others (round 3 SHOULD 3; round 4 SHOULD 2). An item whose signer fails is dropped, so one bad item cannot hold the outbox back, and the error gives only a count. A loaded outbox is checked: items of a kind with no signer are dropped (and the drop saved), and a malformed day, wait, payload, batch or item count refuses the outbox rather than crash at release (MUST 2). Outboxes from earlier rounds no longer load; none exist outside tests before release. | OSS-6 | — |
| P6 | **Nothing calls the publisher yet.** Conditions for wiring: (a) Clean-room artifacts (cleanroom C13 K2) and attestations (OSS-8) leave the box only through `Publisher.Queue`, under a `Signer` per kind. Allow-listed UPD-8 attestors (the interim maintainer test box and listed outside attestors) do not use this package: they sign with their stable, pinned key and publish promptly, with no rotation and no delay, because update counting depends on that key being known (potency C1 on #163). Only ordinary installations' OSS-8 attestations go through `Publisher.Queue`. (b) Turning sharing off (OSS-7 `never`, or "stop sharing" by text) calls `Publisher.Clear`, which discards every queued item and any unconfirmed batch, so what was already queued is not published (UX on #163); cleared payloads stay in the broker's memory until the garbage collector reclaims them, and are gone from disk at once; a batch the sender accepted before an error may already be out. (c) Only a fixed broker timer calls `Release`, never anything an agent machine can reach, because the moment `Release` runs is the moment the batch leaves (as hint K3). (d) The attestation signer must fill `Statement.Attestor` from the key it is handed at release. `update.Attest` takes a `*Verified`, so the OSS-8 wiring either keeps the verification result until release or adds an `update` helper that signs a statement already checked against a verified release. That change is on the update-signing path and needs the strongest reviewer. | OSS-6, OSS-8 | The OSS-8 and clean-room publisher packages. |
| P7 | **The hint emitter publishes nothing itself.** Its `Outbox` is the box's own clean room (cleanroom C1), so hints cross no network and carry no publication key. BOARD's "used by the hint emitter" is read as: what the clean room builds from hints is published through this outbox. | OSS-1, OSS-2, OSS-6 | — |
| P8 | **Within one epoch, an installation's publications are linkable to each other.** That is by design, because attestations need a stable signer for OSS-9's weighting. Across epochs they are not linkable. OSS-9 must therefore never treat distinct keys as distinct installations (one box is a new attestor every 28 days), and it already must not count attestations blindly. | OSS-6, OSS-9 | OSS-9 weighting. |
| P9 | **Network metadata is out of scope here.** The spec's optional anonymity-network routing belongs to the `Sender`, which is not built. Until then a publication shows that some installation at that IP address published. | OSS-6 | The Sender package adds the setting. |

## Conditions for wiring (security on #163)

- **W1 (P6):** every `Signer`'s caller strips installation-unique content (the box's email, owner IDs, host names, serials, timestamps finer than a day) before `Queue`, with a test that plants a canary identifier and shows it never reaches a batch.
- **W2 (P6(d)):** wiring `update.Attest` (or a statement signer beside it) goes to the strongest review tier with an explicit threat check.
- **W3 (P9):** the `Sender` adds network-level unlinkability: an anonymity transport, or a fixed cadence padded to a constant batch size. This is a requirement of the Sender package, BOARD row OSS-6s.
- **W4 (P8, OSS-9):** consumers never count distinct keys as distinct boxes, and never join keys across epochs.
- **W5 (P5, security R1 on #163):** once HOST-1b provides verified time (NTS first, or plain NTP with at least three sources), the publisher counts a day only while the clock is verified, so G2's clock attacker must also defeat NTS. Carried to the HOST-1b wiring row.
