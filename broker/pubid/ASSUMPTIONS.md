# Publication identity: assumptions

Built for BOARD OSS-6 against SPEC v0.12 OSS-6, with OSS-4, OSS-8 and OSS-9 in view. Each row is a reading of the spec, or a gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| P1 | **The key comes from crypto/rand and nothing else.** No owner name, number, account, host name, serial or vault material goes into it. The identity file holds exactly `epoch` and `seed` (strictly parsed: no other, repeated or nested key), mode 0600. An import test shows the package links no other broker package and no network or process package, so it cannot read an owner store. A damaged file is refused, never silently replaced. | OSS-6 | — |
| P2 | **Every installation rotates at the same instants.** Epochs are fixed 28-day UTC periods from one public reference (Sunday 2026-01-04 00:00 UTC). A per-box schedule would let an observer match the day one key stops and another starts. Each epoch's key is fresh, and nothing (no cross-signature, no record) links it to the previous one. The new file replaces the old one in one rename, so the old seed is not left beside it. The clock only moves the epoch forward: a clock stepped back keeps the newest key, and an old key is never made again. Whoever can set the clock can force an early rotation, which yields a new key and reveals nothing. | OSS-6 | Shorter or longer epochs change only the constant. |
| P3 | **Gap: the old seed is overwritten logically, not erased physically.** Flash may keep the old blocks. State-disk encryption (P2-1) covers that, as it does for the vault. | OSS-6 | Host image. |
| P4 | **Batched and delayed.** `Queue` never publishes. Each item waits a whole number of extra days, drawn when it is queued: 1 to `MaxDelayDays` (default 3), from crypto/rand. It then leaves in that day's single batch, at the fixed release time (05:00 UTC, an hour after the hint emitter's 04:00). Each item is signed at release with the epoch's key and the batch is sorted by its signed bytes, so neither the hour nor the day an event happened, nor the queue order, shows. A day with nothing due publishes nothing. The day draw is one byte mod 3 (86/85/85 of 256); that bias is immaterial. The queue holds at most 256 items of at most 1 MiB each, and a refusal never echoes the payload. | OSS-6 | — |
| P5 | **Each day is published at most once, and a crash cannot re-sign.** A batch is recorded before the `Sender` is called and confirmed after it. One that is not confirmed is resent unchanged (same bytes, same day) at the next release, even after a restart or a key rotation, and no new batch forms in that call. So the same items never appear under two keys. A clock behind the last published day publishes nothing until it passes that day. | OSS-6 | — |
| P6 | **Nothing calls the publisher yet.** Conditions for wiring: (a) Clean-room artifacts (cleanroom C13 K2) and attestations (OSS-8) leave the box only through `Publisher.Queue`, under a `Signer` per kind. Allow-listed UPD-8 attestors (the interim maintainer test box and listed outside attestors) do not use this package: they sign with their stable, pinned key and publish promptly, with no rotation and no delay, because update counting depends on that key being known (potency C1 on #163). Only ordinary installations' OSS-8 attestations go through `Publisher.Queue`. (b) Turning sharing off (OSS-7 `never`, or "stop sharing" by text) calls `Publisher.Clear`, which discards every queued item and any unconfirmed batch, so what was already queued is not published (UX on #163); a batch the sender accepted before an error may already be out. (c) Only a fixed broker timer calls `Release`, never anything an agent machine can reach, because the moment `Release` runs is the moment the batch leaves (as hint K3). (d) The attestation signer must fill `Statement.Attestor` from the key it is handed at release. `update.Attest` takes a `*Verified`, so the OSS-8 wiring either keeps the verification result until release or adds an `update` helper that signs a statement already checked against a verified release. That change is on the update-signing path and needs the strongest reviewer. | OSS-6, OSS-8 | The OSS-8 and clean-room publisher packages. |
| P7 | **The hint emitter publishes nothing itself.** Its `Outbox` is the box's own clean room (cleanroom C1), so hints cross no network and carry no publication key. BOARD's "used by the hint emitter" is read as: what the clean room builds from hints is published through this outbox. | OSS-1, OSS-2, OSS-6 | — |
| P8 | **Within one epoch, an installation's publications are linkable to each other.** That is by design, because attestations need a stable signer for OSS-9's weighting. Across epochs they are not linkable. OSS-9 must therefore never treat distinct keys as distinct installations (one box is a new attestor every 28 days), and it already must not count attestations blindly. | OSS-6, OSS-9 | OSS-9 weighting. |
| P9 | **Network metadata is out of scope here.** The spec's optional anonymity-network routing belongs to the `Sender`, which is not built. Until then a publication shows that some installation at that IP address published. | OSS-6 | The Sender package adds the setting. |

## Conditions for wiring (security on #163)

- **W1 (P6):** every `Signer`'s caller strips installation-unique content (the box's email, owner IDs, host names, serials, timestamps finer than a day) before `Queue`, with a test that plants a canary identifier and shows it never reaches a batch.
- **W2 (P6(d)):** wiring `update.Attest` (or a statement signer beside it) goes to the strongest review tier with an explicit threat check.
- **W3 (P9):** the `Sender` adds network-level unlinkability: an anonymity transport, or a fixed cadence padded to a constant batch size.
- **W4 (P8, OSS-9):** consumers never count distinct keys as distinct boxes, and never join keys across epochs.
