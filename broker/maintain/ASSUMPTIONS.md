# Loop 3 (maintenance): assumptions

Built for P3-5 (BOARD.md) against SPEC v0.12 §11A, LOOP-11, on the loop scheduler (P3-2, `broker/loops`) and the update verifier (P4-3, `broker/update`). Covers `broker/maintain`. Each row is a reading of the spec, or a gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| M1 | **Scope.** Loop 3 is one `loops.Source` (`loops.Maintain`) whose only job is an update check: read the owner's mirrors through `update.Store.Check` and send what qualifies to the change pipeline with `ProposeRelease(Checked.Verified(...))`. It builds no release, stages nothing, and never touches an image slot: A/B staging, health check, commit (`Store.Commit`), quiet windows (UPD-6) and HTTP mirrors are the updater's (update U6, U8). "Upstream intake" for a box means AgentOS releases only: upstream projects such as OpenClaw main reach a box only inside a qualified AgentOS release (UPD-5 table, change C7), so evaluating raw upstream is maintainer-side work, not this package. | LOOP-11, UPD-5, CHG-3 | — |
| M2 | **Never "current" when unsure (LOOP-11).** `Status().Current` is true only when the box is online now, update checks are on (`Config.Settings`), the last check passed every TUF check (`Store.Check`) within twice the interval (48 h), it found nothing newer on the box's channel, and no drive install is waiting for its online freshness check. Every other case says why in one line: offline (with the time of the last good check), checks off (with `LOOPS ON` or `UPDATE CHECKS ON`, the name HELP LOOPS gives), no update source, an unreachable source, a frozen source (expired timestamp, which may hide a security fix, or a wrong box clock), bad signatures or rolled-back metadata, a stale check ("I have been busy and will check again soon"; Loop 3 makes no model calls, so the spare budget never holds it back), a box clock behind the last check (security C1, which also makes a check due at once), a drive install not yet checked online, a pinned box, or a newer release waiting (an approval since a date, UX-53-5). The owner-channel STATUS reply and the local page show `Status().Line`. The digest shows it whenever the box is not current, and says "up to date" only once when it becomes so (UX-53-4). Owner text says "update source", not server (UX-53-3). | LOOP-11, UPD-8 | — |
| M3 | **Cadence.** A check is offered daily (UPD-5), within the hour after a failed check or while a security fix waits for its attestation, at once when the box comes back online, and at the end of a soak. Nothing is offered while `Online` is false, so being offline does not count as dry runs that would park the loop (scheduler L5). **Parking (#53 L3 review, arbitrator ruling (b)):** values stay honest (a proposed release 1, a security fix 2, anything else 0), and the scheduler exempts Loop 3 from dry-run parking while `Urgent()` (a security fix waiting for its attestation or a retry, a failed check being retried, or a box back online since its last offer), shows its share while it is, and `Scheduler.Wake` unparks every loop. `Urgent()` samples `Online`, since it is all the scheduler asks a parked loop, so going offline and coming back are noticed while parked (#53 L3 round 2); the check owed for coming back stays due until one runs. `Urgent` is called under the scheduler's lock, so `Online` must not call into the scheduler. Both are in `broker/loops/scheduler.go` (the `Urgent` interface), tested here under `loops.Scheduler`. Checks run only in spare time like all loop work (LOOP-1); a box busy for days goes stale and says so (M2). Potency PM3 recommends running the daily check even while busy, since it is metadata only: that is a scheduler change (a Source that may run while `Busy`), left to the scheduler package. **Wiring:** call `Scheduler.Wake` when the network comes up and when the owner changes channel; pass the scheduler's `Settings` as `Config.Settings`. | UPD-5, LOOP-1 | Scheduler lets metadata-only jobs run while busy. |
| M4 | **Security first, D6 as ruled (arbitrator, 2026-10-05).** Only attestors on an allow-list count (`Config.Attestors`): pinned in the installed image and the owner's configuration, changed only by an update the current list attested, or by the owner with a code-generator code plus local confirmation. Loop 3 passes the list to `update` as `Options.Attestors` (#46 B1), which ignores a report from any other key, including a signing-key holder's and this box's own. A security fix (manifest `security`) with a passing report from a listed attestor goes to the pipeline as `Security()` and auto-stages under the standing `SecurityAutoStage` policy (change C7). **Interim (Mark, 2026-10-05, "Project test box"):** the project's test box key, pinned in the image and passed as `Config.InterimAttestors` (`update.Options.InterimAttestors`), counts as the check while every listed key is such a key and no outside attestor was ever listed on this box (`update` decides this and remembers the first outside listing for good; the signed maintainer list never turns it on), and the status says `Security update N is ready and installs at the next quiet time. It was tested by the AgentOS project's own test box, not an independent tester.` (`Verified.InterimAttestation`); with an outside tester's report it says `An independent tester's report passed.` instead. Without a counted report: if the list is empty, it goes to the owner at once through the pipeline's owner path (CH-3, asked with a code); if the list has entries, Loop 3 re-checks hourly for up to `AttestWait` (24 h) with the line `Security update N is waiting for an independent test report before it installs.`, then goes to the owner. Either way the status says `Security update N needs your approval: no trusted independent test report yet.` A security fix skips the soak and reports value 2 against 1 for an ordinary release (LOOP-3). Install-now from the local page is the owner channel's and LocalUI's (CH-3), held while there is no LocalUI. | UPD-8, UPD-5, LOOP-3, CH-3 | Attestors are added by the owner or by an attested update. |
| M5 | **A security fix behind a newer release.** `Store.Check` returns the newest release above the installed one on the box's channel, and `Result.SecurityFix` names the highest security release above the installed one (#46, security C2). Releases are full images, so the newest carries the fix: when `SecurityFix` is set, Loop 3 handles the newest as a security update (no soak, "Security update N" wording, value 2). `update` judges auto-staging on the newest release's own flag, so a newer release not itself marked security cannot auto-stage and goes to the owner at once (CH-3). Closes potency PM1. | UPD-5, UPD-8 | Let maintainers mark a release as carrying an earlier fix so it can auto-stage. |
| M6 | **Soak for ordinary stable releases (UPD-5).** A stable box proposes an ordinary stable release only 7 days (the owner's `UPDATE SOAK`, loops L23) after it first saw that release's image, on either channel, and, when any attestor is listed, with at least `MinPasses` (1) passing reports from listed attestors; with none listed the soak alone applies, since the owner approves every image release anyway (change C7). Each check on a stable box also runs a fast-channel check that only records first sightings (potency PM2). An image is keyed by its `/usr` root hash and every file's signed path and hash, so a fast release republished as stable under a new version is not soaked twice. Release metadata carries no publish date, so this is first sight by this box; sightings are kept 90 days. A fast box takes fast and stable releases with no soak and no attestation, since fast boxes are the ones that produce attestations (UPD-7). Behavior-changing releases still need the owner (CHG-3, change C7). | UPD-5, UPD-7 | Add a signed publish date to the manifest and measure the soak from it. |
| M7 | **Channel and pinned (UPD-4).** The channel is the owner's setting (`Settings().Updates`, loops L23), read at each check, so a change takes effect at the next one. With `SECURITY UPDATES ASK` a security fix goes to the owner at once, proposed without its attestations so it never stages on its own and never waits for a report. A pinned box is checked as stable but proposes nothing. A security fix gets the notice `Security update N is out. This box is pinned, so it won't install it. Reply UPDATES STABLE to take it and later tested releases.` (UX-130-2); ordinary releases are not mentioned beyond `this box is pinned`. A pinned box is never reported current while a newer release exists. | UPD-4 | — |
| M8 | **Proposed once.** The pipeline's answer (adopted, awaiting owner, rejected) and when it was asked are saved per version; a rejected or adopted release is not proposed again. Proposals awaiting the owner are held in the pipeline's memory only (change C9), and the owner's pending request dies with them at a restart, so Loop 3 forgets them too and proposes again at its next check: re-asking is the only way the owner's approval can still take effect. Potency PM4 (do not re-ask after a restart) needs the pipeline to persist proposals (change C9's "if it changes" column), not a change here. A proposal error retries within the hour. **Dropped unanswered (P2-2a f3, L3 on #363):** Loop 3 keeps the pipeline's proposal ID per version; at each check, a version awaiting the owner whose proposal the pipeline dropped because the request closed unanswered (`Proposer.Lapsed`, change C25) is forgotten and proposed again in that check, without a restart. The owner's NO is not a lapse, and neither is a release left out of a partial YES (change C25), so neither is re-asked until a restart (above). Until that check (at most the daily interval) STATUS still says the version is waiting for approval. | CHG-3, OP-2, UPD-5 | Pipeline persists proposals. |
| M9 | **Mirrors.** `Mirrors` returns the owner's configured sources, tried in order; the first that passes every check wins. When all fail, the line reports the most telling failure (bad signatures or rollback, then expiry, then unreachable). A drive (DEP-4) is not a mirror: installing from one is the updater's, and the next online check clears its pending freshness check; the digest reports "has now been checked online" once, and only when that check found nothing newer. A release the box cannot read fails the check (fails closed, never current). Saving Loop 3's state is reported in the job's error. The TUF threshold floor is `update`'s default (2); Loop 3 exposes no way to lower it. | UPD-2, UPD-8, DEP-4 | — |
| M10 | **Attestations** are fetched by `Config.Attestations` for the manifest path (`releases/N.json`) and judged by `update` against the allow-list in `Options.Attestors` (M4): release and manifest hash, pass, fast channel, never a root-listed key or this box's own. Wiring: pass the fetcher and an empty `Attestors` list now (arbitrator ruling); the list fills from the image, an attested update, or the owner. The first attestor is the project's test box, as an interim (M4); where reports are published is update's (U7). | OSS-8, UPD-8 | Owner adds an attestor, or an attested update does. |
| M11 | **No model calls, no inference.** Jobs are `UsesModel: false`: a check reads metadata, and the pipeline does not run replay on an image candidate (replay R5 returns not-evaluated). The package uses no inference (ARC-2). A job cancelled by `Preempt` records nothing and is offered again. | LOOP-1, LOOP-2, ARC-2 | — |
| M12 | **Not wired into `agentosd`.** Wiring: `maintain.New` with the box's `update.Store`, the owner's mirrors, network state from the modem or Wi-Fi (`Online` is required, security C4), the scheduler's `Settings` (which carry the channel and cadence, M7), the pipeline, and a `change.FileStore`; add it to `loops.Config.Sources`; show `Status().Line` in STATUS and on the local page. The security lens's conditions in `update` are met in #46: B1, the allow-list (M10); C2, `Result.SecurityFix` (M5, potency PM1); C3, a locked `update.Store`. Adding an owner attestor is a high-tier owner action (code plus local page), the wiring's job. **One attestor source (SR3-6f-1):** `Config.Attestors` returns the allow-list and interim keys from the owner's setting and is read once at the start of each check; the check passes that read to every `Store.Check` (the stable check and the fast sighting) and to its soak and attest-wait rules, so one check sees one policy and a static list never rewrites the store's `attestor_policy` after an owner narrowing. A lock (`Loop3.policy`, taken before the store's) holds from that read to the check's last `Store.Check` and around `AttestorsChanged`, so a narrowing during a check lands after it and is not written over; `AttestorsChanged` may wait out the whole check: every mirror's `Store.Check` and the fast sighting, each bounded only by its `Source` (W5b gives every mirror a deadline; Security 4a on #595, point 2). A read error fails the check closed: no `Check` runs, the store keeps its policy (so retired authority stays retired), and the failure is recorded and retried as for a failed mirror check (`could not check: my list of trusted testers could not be read`). The wiring calls `Loop3.AttestorsChanged` on each write of the owner's setting; it reads the same source and calls `update.Store.NoteAttestors`, and on a read error notes no attestor, which only narrows. Nil source: no attestor (first boot), which only narrows. **A change retires claims (SR3-6f-4):** `AttestorsChanged` also sets `State.Recheck`, which makes a check due at once (`Urgent`, `Next`) until a check that began after the change runs (a counter bumped under `Loop3.policy` tells), and unproposes each `TestedBy` version whose proposed release (held in memory) no longer reports `Security()`, or is not held after a restart (LATER SR3-6f4-restart); each check while `Recheck` holds does the same, so a claim recorded by a check that read the list before the change is retired too. The check then decides the version again under the current list, and STATUS stops saying an independent tester passed. It only retires: a re-decided release gets a claim only from the current list. `Loop3.mu` is taken only after `policy` is released, and the `Security()` reads run outside `mu`. An abandoned adoption's apply-side settle is SR3-6-f3. `Status` and `Digest` read the source for the fork line (M14) only; an unreadable list reads as none listed. Tests: `attestors_test.go`. Loop 3 itself runs one check at a time. The box clock comes from authenticated time (TIM-1). | TIM-1 | Wiring package. |
| M13 | **Open decisions not assumed.** Release signing-key custody (SPEC open question 6, update U3/U9) and offline expiry are Mark's pending decisions; Loop 3 takes whatever `update.Store.Check` accepts and adds no rule of its own on either. | §16 q6 | — |
| M14 | **On a fork (OSS-10, OSS-9).** While `update.Store.Following` names a fork, STATUS ends `Following: <name> (<first 8 of its root key fingerprint>).` (Security C7; the coordinator chose this over UX's "no line", UX may object at review), up to date reads `Updates: <name> has no release newer than yours yet` (C5), and a request waiting for the owner adds who checked it (`EvidenceLine`, UX Q-C: listed independent builders, the source's own testers, a rebuild here; never unlisted keys). With no attestor listed it also says `Security fixes: you approve each one, since no attestor is listed for the fork you follow.` (potency C1): each security fix goes to the owner once and stays in every digest until installed or declined, as on the project chain (M4, M8); once the owner lists an attestor, a fix with its report stages on its own. The digest says once `Updates now come from <name>, chosen by you on <date>. You can switch back on my Wi-Fi page.`, or after switching back `Updates now come from the AgentOS project again, chosen by you.` A check on another chain forgets what Loop 3 had proposed on the old one, since version numbers are per chain; a request the old chain left with the owner cannot stage (update U13). The page and alert wording (`FollowPrompt`, `FollowCheckHeading`, `FollowNameLabel`, `FollowAlert`) is here for P2-2 and the updater. | OSS-10, OSS-9, UPD-8 | — |
