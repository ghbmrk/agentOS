# Loop 3 (maintenance): assumptions

Built for P3-5 (BOARD.md) against SPEC v0.12 §11A, LOOP-11, on the loop scheduler (P3-2, `broker/loops`) and the update verifier (P4-3, `broker/update`). Covers `broker/maintain`. Each row is a reading of the spec, or a gap left for a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| M1 | **Scope.** Loop 3 is one `loops.Source` (`loops.Maintain`) whose only job is an update check: read the owner's mirrors through `update.Store.Check` and send what qualifies to the change pipeline with `ProposeRelease(Checked.Verified(...))`. It builds no release, stages nothing, and never touches an image slot: A/B staging, health check, commit (`Store.Commit`), quiet windows (UPD-6) and HTTP mirrors are the updater's (update U6, U8). "Upstream intake" for a box means AgentOS releases only: upstream projects such as OpenClaw main reach a box only inside a qualified AgentOS release (UPD-5 table, change C7), so evaluating raw upstream is maintainer-side work, not this package. | LOOP-11, UPD-5, CHG-3 | — |
| M2 | **Never "current" when unsure (LOOP-11).** `Status().Current` is true only when the box is online now, the last check passed every TUF check (`Store.Check`) within twice the interval (48 h), it found nothing newer on the box's channel, and no drive install is waiting for its online freshness check. Every other case says why in one line: offline (with the time of the last good check), no mirror, an unreachable mirror, a frozen mirror (expired timestamp, which may hide a security fix), bad signatures or rolled-back metadata, a stale check, a drive install not yet checked online, a pinned box, or a newer release waiting. The owner-channel STATUS reply and the local page show `Status().Line`; the digest shows it every day. | LOOP-11, UPD-8 | — |
| M3 | **Cadence.** A check is offered daily (UPD-5), within the hour after a failed check or while a security fix waits for its attestation, at once when the box comes back online, and at the end of a soak. Nothing is offered while `Online` is false, so being offline does not count as dry runs that would park the loop (scheduler L5). Checks run only in spare time like all loop work (LOOP-1); a box busy for days goes stale and says so (M2). **Wiring:** call `Scheduler.Wake` when the network comes up and when the owner changes channel. | UPD-5, LOOP-1 | Run security checks outside spare time if a busy box goes days without one. |
| M4 | **Security first.** A security fix (manifest `security`) is proposed only with the threshold signatures plus at least one independent passing fast-channel attestation, as `update` counts it: not a root-listed key and not this box's `OwnKey` (UPD-8, Mark's D6). Until then the digest says `Security update N is waiting for an independent test report before it installs.` and Loop 3 looks again hourly. It skips the soak. It reports value 2 against 1 for an ordinary release, so the scheduler's measured return favours Loop 3 when it delivers fixes (LOOP-3). The pipeline then auto-stages it under the standing `SecurityAutoStage` policy, or asks the owner (change C7). | UPD-8, UPD-5, LOOP-3 | — |
| M5 | **Only the newest release is seen.** `Store.Check` returns the newest release above the installed one on the box's channel. Releases are full images, so the newest carries every earlier fix, but if a security fix N is followed by ordinary release N+1 before the box checks, Loop 3 sees only N+1 and it soaks (M6). **Follow-up for `update`:** report whether any newer release is a security fix, so the newest is treated as one. Until then maintainers mark a release `security` when it carries an unreleased-to-stable fix. | UPD-5, UPD-8 | `update` follow-up. |
| M6 | **Soak for ordinary stable releases (UPD-5).** A stable box proposes an ordinary stable release only 7 days (`Soak`) after it first saw it and with at least `MinPasses` (1) independent passing attestations. Release metadata carries no publish time and attestations carry no date, so "7 days on fast" is measured locally from first sight; this is conservative (a release promoted to stable after its fast soak waits up to 7 more days). A fast box takes fast and stable releases with no soak and no attestation, since fast boxes are the ones that produce attestations (UPD-7). Behavior-changing releases still need the owner (CHG-3, change C7). | UPD-5, UPD-7 | Add a signed publish date to the manifest and measure the soak from it. |
| M7 | **Pinned (UPD-4).** A pinned box is checked as stable but proposes nothing. A security fix gets the notice `Security update N is out, but this box is pinned, so it will not install it on its own.`; ordinary releases are not mentioned beyond `this box is pinned`. A pinned box is never reported current while a newer release exists. | UPD-4 | — |
| M8 | **Proposed once.** The pipeline's answer (adopted, awaiting owner, rejected) is saved per version; a rejected or adopted release is not proposed again. Proposals awaiting the owner are held in the pipeline's memory only (change C9), so after a restart they are forgotten here too and proposed at the next check. A proposal error retries within the hour. | CHG-3, OP-2 | — |
| M9 | **Mirrors.** `Mirrors` returns the owner's configured sources, tried in order; the first that passes every check wins. When all fail, the line reports the most telling failure (bad signatures or rollback, then expiry, then unreachable). A drive (DEP-4) is not a mirror: installing from one is the updater's, and the next online check clears its pending freshness check, which the digest reports once. | UPD-2, UPD-8, DEP-4 | — |
| M10 | **Attestations** are fetched by `Config.Attestations` for the manifest path (`releases/N.json`) and judged entirely by `update`; malformed ones are ignored there. Where they come from (a mirror path, the fast-channel community) and where the box's own attestation key lives are open in update U7. With no fetcher, no security fix auto-stages and no ordinary stable release is offered, which is the safe direction. | OSS-8, UPD-8 | Wiring, with update U7. |
| M11 | **No model calls, no inference.** Jobs are `UsesModel: false`: a check reads metadata, and the pipeline does not run replay on an image candidate (replay R5 returns not-evaluated). The package uses no inference (ARC-2). A job cancelled by `Preempt` records nothing and is offered again. | LOOP-1, LOOP-2, ARC-2 | — |
| M12 | **Not wired into `agentosd`.** Wiring: `maintain.New` with the box's `update.Store`, the owner's mirrors, network state from the modem or Wi-Fi, the channel setting, the pipeline, and a `change.FileStore`; add it to `loops.Config.Sources`; show `Status().Line` in STATUS and on the local page. Owner commands to change channel (UPD-4) belong to the owner channel. | — | Wiring package. |
| M13 | **Open decisions not assumed.** Release signing-key custody (SPEC open question 6, update U3/U9) and offline expiry are Mark's pending decisions; Loop 3 takes whatever `update.Store.Check` accepts and adds no rule of its own on either. | §16 q6 | — |
