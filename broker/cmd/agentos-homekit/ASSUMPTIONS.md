# Assumptions: the HomeKit clerk's process (DEV-homekit part b2a, #3891)

What the process rests on. Brief: `briefs/DEV-homekit.md`, "Part (b2), settled" (b2a, DEV-homekit-host); the library's rows are `broker/clerk/homekit/ASSUMPTIONS.md` (HK-1 to HK-21).

| ID | Assumption | Serves | If wrong |
|---|---|---|---|
| HK-host-1 | **The owner side checks tier 4; the clerk trusts its socket's peer.** The owner socket admits only the owner side's uid (`sockets.ListenPeers`), as the camera clerk's does (CAM-host-1). agentosd checks the approval code of a connect, bounds or re-pin step (`localapi.HomeKitTier4`) before it relays it; its handler for the HomeKit page ops, its STOP and RESUME relay and its feed of the enforcer's listing are b2b (#3893), so until it lands no step reaches the clerk and no thermostat pairs. | DEV-10, CH-3, KRN-7 | A clerk that checked the code itself would need the code generator's seed, which only the kernel holds. |
| HK-host-2 | **Only a listed, unpaired accessory is paired.** `homekit/connect` and `homekit/repin` name the accessory by the enforcer's device ID from the last `homekit/listed`, and refuse it unless the TXT `sf` bit 0 says unpaired. No typed address is taken. The listing's address must be a private or link-local address with no zone; its entries are put back in canonical form, so no text from the enforcer's channel reaches STATUS or the page but the device ID, which is bounded to `[A-Za-z0-9._:-]`. For the pair-setup step the guard pins the listed address, then only the paired devices' `GuardPin`s (HK-21). The setup pin's key is a random placeholder that `netguard.Pin` requires: netguard checks a pin's key only at a TLS handshake and HAP is plain TCP, so the setup pin scopes the dial by address only and proves no identity. pair-setup's code, then pair-verify, is what binds the accessory (Security point 2 on 22f3e1b5). | DEV-2, DEV-10 | The enforcer relays no HAP listing (b2b files the gap): nothing can be paired. |
| HK-host-3 | **The HomeKit code is used once and kept nowhere.** It is an argument of one owner call, passed to `Clerk.Connect` and dropped; every refusal is fixed text, the file holds no code, and the page never writes it back into HTML. Go strings cannot be wiped, so the process memory may hold it until the collector reuses it. | CH-6, A16 | A code that had to survive a retry would need a sealed slot; HAP's one-attempt rule (HK-5) means none does. |
| HK-host-4 | **Devices across restarts.** `homekit.json` holds each `Device` (name, address, accessory ID and public key, AID, confirmed bounds, off) and the STOP flag, written whole with `privfile.WriteAtomic`. A malformed file is refused whole, before the key hand-off is read, and nothing is dialed. Every device that is not off opens by pair-verify at start and polls every minute; a dropped link redials with a backoff capped at five minutes and raises one counted line per drop. | DEV-3, KRN-7 | — |
| HK-host-5 | **Values are limited and counted, then dropped, until the kernel's device-report entry exists.** Each device and characteristic's values pass a restated copy of `devhost`'s DEV-8 rule (`devhost.Limit`, Burst per window, the rest counted into one coalesced event), as CAM-clerk-5 restates it. What passes is counted per device, shown in STATUS as counts only, and dropped: no value is logged. b2c wires the sink to DEVSLOT b3's entry (#3474). | DEV-8 | When b3 merges, the sink becomes the device-report call; nothing else changes. |
| HK-host-6 | **A bridge's thermostats share one pairing.** `Clerk.Resolve` names them name, name-2 and on; disconnect and re-pin act on every device of the accessory, since HAP keeps one pairing per controller. A name is refused when it or a sibling name is in use. A device paired before its accessories resolved (`ErrUnresolved`) is kept with AID 0, and its runner resolves it later and saves the thermostats. | DEV-10 | — |
| HK-host-7 | **Disconnect removes the box's own pairing over a fresh pinned session.** The device's runners stop first, then one `Open` and `Link.RemovePairing`; a device that is off (a key mismatch) is not dialed again (HK-18). Whatever the accessory answers, the devices leave the file, then their counts go; the answer's `removed: false` tells the page to ask the owner to reset HomeKit on the thermostat. The controller key stays: it is the box's for every accessory. | DEV-4, DEV-10 | — |
| HK-host-8 | **Bounds are confirmed only on an open link**, since `Link.ConfirmBounds` checks them against the characteristic's declared range read at this session's resolve. Until confirmed, every setpoint write classes `actuate-physical` (design point 6); the process serves no write at all until b2d. | DEV-4, DEV-5 | — |
| HK-host-9 | **The process's tests drive a fake that keeps `homekit.Clerk`'s contract.** The synthetic HAP accessory is test-only code inside `clerk/homekit` (an SRP server and `net/http` request parsing); exporting it would link it into this trusted process. The fake dials through the host's own guard, refuses a key other than the pin by turning the `Device` off, and records remove-pairing's pairing ID; the protocol, remove-pairing included, is tested in `clerk/homekit` against the synthetic accessory. | brief b2a tests | A shared test-only accessory package (built on exported codec pieces) would let these tests run the real clerk. |
| HK-host-10 | **The image unit, sysusers line and the kernel's `-clerk-key homekit=` entry are b2c (#3894).** The process takes every path on its command line and no unit starts it until then. Before it reads its key it refuses its owner side's uid and turns non-dumpable (`procguard.Isolate`, CLK-1). | brief b2c | — |
| HK-host-11 | **STOP stops an owner step under way** (KRN-7, Security point 1 on 22f3e1b5). connect, re-pin and disconnect dial on a step context that STOP cancels, which closes the step's connection (`homekit.Clerk`'s dial watches it); the link a disconnect opens for remove-pairing is STOP's to close. A pairing step checks STOP and keeps its devices under one hold of the host's lock, and a disconnect checks STOP before it sends remove-pairing and again before it drops the devices, so a step that finished as STOP came keeps nothing, and an accessory that took the pairing then is left for the owner to reset. STOP takes no owner-step lock, so it never waits behind a step. A remove-pairing the accessory answered before STOP closed its link stands. | KRN-7 | — |
