# Vault process (agentos-egress): assumptions

Rows are added per package that touches this command. A reading a later spec version could change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| S2-1 | The Owner Card's entry (`recovery.CardName`) in the open vault is the only proof that a card made it. Finish's seal (`sealEnroll`) is refused with a fixed reason (428, `ErrCardRequired`, mapped to `card pending`) while that entry is absent. The page's card latch and its PeerUID-only report are not consulted. The check follows the not-confirmed check, so an unconfirmed seed still answers 409. | HW-1, A1 | A card made some other way would need its own marker. |
| S2-2 | A PIN enroll whose slot change errors with `vault.ErrSlotDecided` keeps the TPM lockout (no `giveBack`): the seal landed, so the change completes at the next open and the lockout is what protects it. `trust` then tells the owner channel the PC is trusted (saving not finished) and answers that it is trusted but not yet saved, with the step (trust again, which replaces the slot for this TPM), not "nothing was changed". A decided enroll with no PIN keeps the lockout state it had (the give-back runs only on success). | CRED-8, CRED-9, HW-1 | A slot change that can be undone after the seal would make the kept lockout and the notice wrong. |
| S2-3 | The lockout authorization is made durable (`Vault.Sync`, the vault directory's sync) before the TPM takes the lockout hierarchy. A sync error stops the PIN enroll with the TPM unchanged and a new entry forgotten again. The sync covers the vault file as a whole, so an authorization written earlier whose own sync failed is covered too. Vault writes elsewhere still treat a failed directory sync as landed (#1472). | HW-8, CRED-8 | A TPM that could be changed without the authorization being kept would need no sync; a sync that is slow or fails on this drive blocks PIN enroll until it works. |
| S2-4 | A trusted-host removal (`untrust`, setup's "not mine") or a re-encryption's new slot whose slot change errors with `vault.ErrSlotDecided` has taken effect: it completes at the next slot change or open. Removal keeps this PC's lockout hierarchy while the PC's slot is still in the keys file on the drive (with it a thief could reset the TPM's guess limit and try PINs against that slot offline; Security S1 on #1821); the owner's next unlock lands the change and then gives it back (`giveBackRemoved`, run whenever the drive's keys file holds no slot for this PC). It answers that the PC is no longer trusted (`errHostRemovedDecided`, notice "removed (saving not finished)"), not "no such host"; its step is the next unlock, since untrust again would find no such host. Re-encryption counts that PC as sealed, goes on with the rest and returns success with a notice, so refresh still replaces the MAC key and seed. A decided error from `Vault.Reencrypt` itself stays an error: at its step 1 the vault is still under the old key, which the next open keeps. | CRED-8, CRED-9, REC-4, HW-1 | A slot change undone after the seal would make the "sealed" count wrong. `OpenSealed` lands a pending change before the unlock's `bind`, so the drive's keys file then is the decided one. A decided error at `Reencrypt`'s step 3 (new key in place, every trusted-host slot gone) is not told apart from step 1 here; tests in this package cannot reach it (#1741 PR, later finding). |
| S3-1 | `POST /usage?provider=<id>` on the control socket serves `PlanUsage.Snapshot` for that provider (pools and last refused login, never a credential) on the broker-owned control socket, which no other host uid can reach (#1856, RES-5). An id outside the provider pattern is refused. | RES-5 | |
| S8-1 | *Retired by WIFI-del-e (#3365, D-178): the Owner Card has no Wi-Fi, so the verify socket's `/committed-wifi` route is deleted.* | REC-4, CH-9 | — |
| S2-5 | A trust that fails after `addPolicy` writes the policy file back as it read it before (`enroll`'s deferred restore), unless the slot change errored with `vault.ErrSlotDecided` (S2-2: the PC is trusted and needs the path). The restore is a whole-file write. Every writer that changes the approved paths (`enroll`, `approve`, `reencrypt`) holds `tpmHost.mu`, as `enroll` does from the read to the restore, so none lands in between; `noteRelease` does not take the lock, but it changes only the `Release` wording hint, which a restore may put back. Vault entries the failed trust made (the PCR policy key, DA originals, a lockout auth kept on an ambiguous TPM error) stay; they unlock nothing without a policy and a slot (#1781). | HW-5a, CRED-9, HW-8 | A writer of `Policies` outside `tpmHost.mu` would need the restore to remove only the entry this trust added. |
| S2-6 | Setup's `GET /setup/providers` reports the `-private-ok` flag only as `private_by_config`; `private_ok` stays the owner's marker (D-115, Security S1 on #1588). Setup shows a configured provider's box ticked and disabled, and records no answer for it whatever is posted (a disabled box is never sent, so a missing value can't mean withdraw), so setup neither writes a lasting owner yes the owner never gave nor reads a forged untick as a withdraw. The owner's own answer for that provider stays on the providers page (#1608). | SPEC CAP-9, OWN-7; D-115 | If setup should record the owner's answer alongside the flag, `privateOK` in broker/localui/setup.go must take the posted box again and the box must be enabled. |
| CAP9-1 | A plan run's Private label reaches the vault process only through `/seed?machine=<id>&private=1` (agentosd's `planSeeder`, from `provagent.Runner`), and the binding is kept until `/close` or shutdown, across reopens. A bound route asks `/plan`'s answer (`custody.planState`: the owner's marker, not the `-private-ok` flag, the same answer admission asked) before each request on a run endpoint of kind `responses`, and refuses it with 403 and `DeniedHeader` when the answer is no or unreadable (locked vault). Requests already forwarded are not recalled; refresh, model list and sign-in calls carry no owner data and are not checked (#2359). | CAP-9, CH-3 | If admission starts honouring the `-private-ok` flag for the plan, the route must ask the same answer, or a flag-allowed run is refused mid-run. A second content endpoint kind would need adding to the check. |
| W-1 | `-holder adapter=dir` (repeatable) names every adapter's holder or none; a partial set is refused at start. With holders, the proxy is built without the vault (`egress.New` with `Holders` and the vault's keyed-hash redactor, CRED-7), so it adds no key itself; one keeper per adapter hands that account's API key from the open vault to `dir/hand.sock` and re-hands after a key store. Lock or expiry stops the keepers, waits for any hand in flight, then drops every holder's login (2s each); a holder that is not running is not reported, any other drop failure is. Lock holds `c.mu` throughout, so a holder that hangs delays it by up to about 22s (a round in flight: two 10s requests, then the 2s drop); a hung holder's own key stays held until it answers or restarts. The keeper trusts whatever listens on `dir/hand.sock` (no peer-uid check); the directory's owner and mode are the image's to set (SIM-split-wire image wiring). ARC-1 and CRED-1 are met only in part. Still to come: the image's wiring of the keyless proxy process (W-2; A5's compromised-egress clause holds on a box only after it), setup's raw-key check, which still runs in this vault process, mail, SMS, SIP and exchange logins, which stay here (SIM-split-msg, SIM-split-refresh), and SIM-split-check and SIM-split-fix. Off by default: the image passes no `-holder`. | ARC-1 (part), CRED-1 (part), CRED-7 | A partial holder set would need `egress.New` to take the vault back for the rest, which the holders spec rules out. |
| W-2 | With `serve -proxy dir` (needs every `-holder`), the vault process serves no model or routing socket: `agentos-egress proxy` does, under its own uid, from the same model flags, and never opens the vault. A view keeper hands it, on `dir/hand.sock` (peer uid `-vault-uid` only, 4 MiB cap), a view of the open vault: which providers have a stored key or a private-data marker, the locked stored-key mark, and the keyed-hash redactor (CRED-7); never a value or the vault key. The view's version is the unlock epoch and the vault's change count, so every unlock, lock and vault change re-hands it. The lock, and every value stored or deleted while open (a key, a private-data answer), hand the view before they return, so a withdraw narrows the proxy at once and a new value's keyed hash redacts at once (proxy not running: nothing to tell). A hand that does not finish within 2s (a round in flight to a proxy that hangs) is given up and notified, with `c.mu` held, and the proxy keeps its last view until a later round reaches it, as W-1's holders do; a private-data withdraw it missed is told as not yet in effect. The view keeper trusts whatever listens on `dir/hand.sock` (no peer-uid check on the server), as W-1's keepers do; the view carries names and keyed hashes only. A view that does not parse leaves the proxy locked. Under `-proxy` the proxy process owns routing: adopted routing persists only if it gets `-routing-state`; the vault process still loads its own `routing.json` but serves no routing socket. Both processes must get the same `-grant`, `-agent` and `-private-ok`; nothing checks they agree. Still to come: the image's units, uids and broker socket path for the two processes (off by default: the image passes no `-proxy`). | ARC-1, CRED-1, CRED-7, A5 | If the broker should reach model and routing sockets in a fixed place, the image sets `-run`; if the two processes' flags must be checked, the view carries a hash of them. |
| W-3 | With `serve -checker dir`, the code-generator seed lives in `agentos-checker` while the vault is open: a keeper hands it to `dir/hand.sock` (version = the vault's store count, so a replaced seed is re-handed) and lock or expiry drops it with the holders. Every code, the broker's and the unlock's, is checked on the checker against its one durable last step; the unlock passes its own last step as `after` and stores the step the checker spent. The hand socket's check (the unlock's and `confirmEnroll`'s) is charged to none of the checker's wrong-code buckets, so the broker's wrong codes never pause the owner's unlock; the vault process's own durable cap (CH-18) and enrolment bucket limit those codes, and the vault uid already holds the seed it hands. While the vault is still pending the unlock hands the seed for one check and drops it after, so a pending vault leaves no seed in the checker. This process's verify socket then checks only the unlock proof and answers 500 for a code. A checker that is down or fails refuses the unlock and every tier-4 approval. `confirmEnroll` spends its step on the checker too (it hands the pending seed for that one check and hands the channel's back unless it made the pending one the channel's). The seed goes to whoever listens on `dir/hand.sock`, with no peer-uid check (as W-1's holders), and it approves any act: the image must make the `-checker` directory writable only by the checker's uid. While one check holds a pending or locked vault's seed in the checker (under `c.mu`), the broker's verify socket can verify against it too, and a failed drop after leaves it there with only a notice. Still here (custody only; the confirmation's step is already spent on the checker): the pending enrol seed lives in this vault process until setup's confirmation. #2498 (`class:release`) moves it to the checker, and no image passes `-checker` until it closes. Off by default: the image passes no `-checker`. | CH-4, CH-10, ARC-1, CRED-1 | If the checker should hold the pending enrol seed too, `confirmEnroll` hands it under its own name and the checker takes a second seed. |
