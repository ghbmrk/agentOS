# Vault process (agentos-egress): assumptions

Rows are added per package that touches this command. A reading a later spec version could change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| S2-1 | The Owner Card's entry (`recovery.CardName`) in the open vault is the only proof that a card made it. Finish's seal (`sealEnroll`) is refused with a fixed reason (428, `ErrCardRequired`, mapped to `card pending`) while that entry is absent. The page's card latch and its PeerUID-only report are not consulted. The check follows the not-confirmed check, so an unconfirmed seed still answers 409. | HW-1, A1 | A card made some other way would need its own marker. |
| S2-2 | A PIN enroll whose slot change errors with `vault.ErrSlotDecided` keeps the TPM lockout (no `giveBack`): the seal landed, so the change completes at the next open and the lockout is what protects it. `trust` then tells the owner channel the PC is trusted (saving not finished) and answers that it is trusted but not yet saved, with the step (trust again, which replaces the slot for this TPM), not "nothing was changed". A decided enroll with no PIN keeps the lockout state it had (the give-back runs only on success). | CRED-8, CRED-9, HW-1 | A slot change that can be undone after the seal would make the kept lockout and the notice wrong. |
| S2-3 | The lockout authorization is made durable (`Vault.Sync`, the vault directory's sync) before the TPM takes the lockout hierarchy. A sync error stops the PIN enroll with the TPM unchanged and a new entry forgotten again. The sync covers the vault file as a whole, so an authorization written earlier whose own sync failed is covered too. Vault writes elsewhere still treat a failed directory sync as landed (#1472). | HW-8, CRED-8 | A TPM that could be changed without the authorization being kept would need no sync; a sync that is slow or fails on this drive blocks PIN enroll until it works. |
| S2-4 | A trusted-host removal (`untrust`, setup's "not mine") or a re-encryption's new slot whose slot change errors with `vault.ErrSlotDecided` has taken effect: it completes at the next slot change or open. Removal keeps this PC's lockout hierarchy while the PC's slot is still in the keys file on the drive (with it a thief could reset the TPM's guess limit and try PINs against that slot offline; Security S1 on #1821); the owner's next unlock lands the change and then gives it back (`giveBackRemoved`, run whenever the drive's keys file holds no slot for this PC). It answers that the PC is no longer trusted (`errHostRemovedDecided`, notice "removed (saving not finished)"), not "no such host"; its step is the next unlock, since untrust again would find no such host. Re-encryption counts that PC as sealed, goes on with the rest and returns success with a notice, so refresh still replaces the MAC key and seed. A decided error from `Vault.Reencrypt` itself stays an error: at its step 1 the vault is still under the old key, which the next open keeps. | CRED-8, CRED-9, REC-4, HW-1 | A slot change undone after the seal would make the "sealed" count wrong. `OpenSealed` lands a pending change before the unlock's `bind`, so the drive's keys file then is the decided one. A decided error at `Reencrypt`'s step 3 (new key in place, every trusted-host slot gone) is not told apart from step 1 here; tests in this package cannot reach it (#1741 PR, later finding). |
| S3-1 | `POST /usage?provider=<id>` on the control socket serves `PlanUsage.Snapshot` for that provider (pools and last refused login, never a credential) on the broker-owned control socket, which no other host uid can reach (#1856, RES-5). An id outside the provider pattern is refused. | RES-5 | |
| S8-1 | `GET /committed-wifi` on the verify socket (broker UID only) answers the stored Owner Card's Wi-Fi name and password while the vault is open, for agentosd to repair `ap-net.json` (#1696): 503 locked, 404 no card, 409 while `recovery.RotationUnfinished` lists the Wi-Fi part (a part-way commit holds the new network as a permit but the stored card may still be the old one, so the stored one is not answered as committed), JSON with `no-store` otherwise. It reads under `c.mu` and changes nothing; the `/rotate/wifi` permit stays. Any other method is 405. | REC-4, CRED-8, ARC-1 | If the broker UID stops being the only peer of the verify socket, this route hands the Wi-Fi password to that peer too. |
