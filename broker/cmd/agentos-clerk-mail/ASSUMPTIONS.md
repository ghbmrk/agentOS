# cmd/agentos-clerk-mail assumptions

Built for MAIL-main-a (#3417, briefs/MAIL-main.md). Each row is a reading a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| MAIL-main-a-1 | **Every refusal of the process comes before the key is read.** The main refuses root, then runs `procguard.Isolate` with the kernel's, the owner side's and the planner's uids (refused as a peer, then non-dumpable), then reads the anchors file; only then does it read descriptor 3. A refused start leaves the key in its pipe (`TestARefusedClerkLeavesItsKeyUnread`, and the anchors case in `TestTheAnchorsFileMustBeRootsAlone`). | CLK-1 | none |
| MAIL-main-a-2 | **The key is one 32-byte key per clerk, from which the clerk derives two.** `clerkkey.Read` takes exactly one frame naming `mail` from a pipe or a connected socket (never a file on the drive), and the main derives its sealer key and its handle secret with HKDF under separate labels, the name bound in, then wipes the raw key. The kernel's side of the hand-off is MAIL-keys (#3419). `clerkkey` is a package of its own, apart from `clerk/handoff`, so the trusted core (tools/trusted_core.txt, which links `clerk/handoff`) does not grow. | CLK-1, Mark's option A (#2682 comment 6428111900) | MAIL-keys may add fields to the frame under a new tag. |
| MAIL-main-a-3 | **The owner's anchors come from a file only root writes, never from the kernel.** The file and its directory must be owned by root and writable by no one else, and the file must be a regular file and not a link, in `handoff.ParseAnchors`' form, with at most `handoff.MaxAnchors` keys. So neither the kernel's uid nor the clerk's own can put keys of its choosing there (D-146). Who writes it at boot (the unlock step, from the store's `kernel/anchors` or, on a box set up through the log, the log's first entry, #2995) is MAIL-keys'. | D-146 | none |
| MAIL-main-a-4 | **A wrong key is not refused at start.** `run.OpenSecrets` loads the sealed slots without opening them, so a start under another key serves, and the first sign-in fails and tells the owner to set the account up again, which replaces the slots. The key is derived the same way at every start, so this happens only if the store or the derivation changes. A check at start would need a sealed canary slot. | CLK-1, STO-2 | A canary slot that start opens. |
| MAIL-main-a-5 | **The reader is a process on the main side, reached over its frame, and it fails closed; the world is the clerk's own.** Without `-reader-sock` and `-reader-uid`, `Ask` returns an error, so no mail is classed and the clerk acts on none. With them (MAIL-reader-sock-a, #3421), `Ask` is `readerwire.Dial` to that socket, refusing any listener but the reader's uid, which must be positive and none of the other three peers' (`procguard.Isolate` gets it too); every failure leaves the mail unclassified. It sits behind a per-process cache of successful replies, keyed by the prompt's SHA-256, at most 4,096 entries evicted least recently used, in memory only, so a read re-sends no mail it already classed and a restart asks each once again (CLK-7). `inbox.MaxPrompt` fits `readerwire.MaxPrompt` (`TestPromptFitsTheFrame`). No `World` is passed: the host builds its own from its clock, the shipped tables, its own `PlanSenders` read and each read's own key lookups (`DKIM`, through the policy below), so nothing of the world comes from the main side (MAIL-world-a, #3422; clerk/run MAIL-world-a-r1). Until MAIL-world-b2 VRB-2 still passes no unsubscribe (`no-history`). | PLN-2, VRB-2, D-154, CLK-7 | MAIL-reader-sock-b adds the reader's process and its unit, which passes the two flags; b2 adds the history. |
| MAIL-main-a-6 | **No IMAP is parsed in this process.** Without `-imap-conn`, every IMAP session is refused (`errNoIMAPConn`); `Conn` is never nil, since `imapsmtp` would then parse IMAP in-process (`imapconn.Pipe`), undoing #2937 gap 2. With it, each session dials the connection process's socket (#3015). | CLK-1, KRN-2 | none: the image's `agentos-imapconn.socket` admits only the clerk's user and starts a confined process per session (image ASSUMPTIONS IMAPCONN-1). |
| MAIL-main-a-7 | **The owner side's uid may be root; the kernel's and the planner's may not.** agentosd, the owner side, runs as root and calls the owner socket as root today (`localsrv/accountsock`, #3059 sets `-owner-uid`). The three uids must be distinct. | D-154 rule 2 | agentosd calls under a uid of its own, as `owner/kernelsock` does for the kernel. |
| MAIL-main-a-8 | **This process is a trusted process but not a root of the trusted core.** Its `wiring` line makes `tools/trusted_base.py` count it and its parsers (the mail clerk library already on main). Making it a `root` of tools/trusted_core.txt would grow the core by the whole mail library, which needs Mark's `Trusted-core` decision; the core stays the kernel and the clerk check path, and `TestTheMailProcessLinksNoMainSideCode` holds rule 4 here. There is no `daemon/arc2_test.go` line, as for `cmd/agentos-kernel`. | KRN-2, D-154 rule 4, D-157 | Mark widens the core to the clerk mains. |
| MAIL-world-a-m1 | **The process learns its own network** (`netguard.go`, copied from cmd/agentos-egress, which this process may not link). One policy learns the home network from `netguard.Sources` at start, on each netlink event and every 10 s, resolves only through the learned resolver, logs refusals by address and reason, and carries no pin; it is `MailConfig.Guard`, so IMAP, Gmail and the key lookups all go through it. If the unit's sandbox cannot read the routes or open netlink, the first read logs and the poll retries; until a read succeeds nothing resolves, so nothing is dialled (`TestTheMailClerkLearnsItsNetwork`). | DEV-2 | The unit's sandbox must allow netlink and `/proc/net/route` reads for the policy to learn; that is the unit's row. |
