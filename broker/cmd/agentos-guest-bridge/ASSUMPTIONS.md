# Guest bridge (agentos-guest-bridge): assumptions

Rows are added per package that touches this command. A reading a later spec version could change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| TREE-fold-wipe-1 | A `managed_tree` answer that is not `unchanged` always carries a non-empty `version` (agentosd's tree hash), and the guest plane never folds it (`guest.TreeTool`, TREE-fold-evict). So a non-unchanged answer with no version, a fold stand-in included, is not a tree, and the bridge refuses it without touching its tree directory. The bridge never calls `result_read`. | ARC-2, CAP-5 | If the plane folded `managed_tree` again, every tree over 8 KiB would be refused and the agent would keep its older skills; if an empty tree could carry an empty version, the refusal would keep a stale tree instead of emptying it. |
| TREE-fold-wipe-2 | Tree polling never touches the machine's fold store (32 records, 4 MiB, shared with the agent's own held results), whether a sync succeeds or keeps failing: the plane hands `managed_tree` back whole (TREE-fold-evict, #1461). Corrected: before #1461 this held only once a sync had succeeded, and a failing sync (unwritable tree directory, ENOSPC, a bad path) folded the tree on every 30 s poll and evicted the agent's results after about 32 polls. A failing sync still refetches the whole tree every poll, up to `guest.MaxTreeAnswer` (8 MiB) of socket traffic per 30 s. | ARC-2, CAP-5, A11 | If the plane folds `managed_tree` again, a failing sync evicts the agent's held results again. |
| TREE-answer-bound | The bridge reads a `managed_tree` answer up to `guest.MaxTreeAnswer`, the same constant the guest plane refuses answers past (guest G21), so a tree the plane sends is never cut short at the read and refetched every poll. | ARC-6, CAP-5 | If the two limits come apart again, a large tree fails every poll and the agent keeps its older skills. |
| TREE-undo-invalidate | A mirror that fails may have written part of the new tree, so the bridge then holds no version and its next fetch asks with an empty one; the broker answers that whole, never `unchanged`. So an owner's UNDO to the version held before the failure re-applies it and removes the failed tree's files (CHG-6). Any mirror failure drops the version, an answer refused for a bad path included, though that one wrote nothing; a failure before the mirror (a tool error, an answer that is not a tree, or an `unchanged` for another version) keeps it, since nothing was written. Since #1572 the mirror also clears what an earlier tree left in a new file's way (a file where it needs a directory, or a directory where it needs the file), so a tree that swaps one for the other, and an UNDO back, mirror whole; a symlink on the path of a tree file, whether a namespace (skills, procedures or context, checked first, so an empty tree or a tree with no file in it cannot walk through one), a directory below it or the file itself, is refused before anything is cleared or written, the sync fails and the link stays (TREE-clearway-symlink, #1630; before it, a symlink at the file was replaced by the rename and one that stayed inside the tree directory was followed, so a clear-way or the removal walk could delete a directory outside the namespaces). A symlink elsewhere in the tree directory is not looked at. The check is not atomic: a guest process that swaps a directory for a link between the check and the act can still redirect a removal inside the tree directory (#1732). The refusal lasts until guest root (which may be the agent), a machine reset or a reseed removes the link; the owner cannot reach into the guest, and sees nothing meanwhile, since the agent keeps its older skills and every poll refetches the whole tree and fails again (owner signal: #1733). | CHG-6, CAP-5, ARC-7 | If the broker ever answered an empty version `unchanged`, a partial tree would stay after an UNDO. If a symlink on a tree path were followed again, a sync could delete a directory inside the tree directory but outside the namespaces; only guest root can plant one (ARC-7). |
