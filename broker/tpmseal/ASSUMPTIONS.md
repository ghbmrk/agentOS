# Trusted-host TPM slot: assumptions

Built for PLAN P2-4b (cloud part) against SPEC v0.12 on top of P2-4a (#29),
which added key slots and the vault process. Covers `broker/tpmseal`, the
trusted-host parts of `cmd/agentos-egress` (`trusted.go`, `custody.go`), and
`vault.AddSlot`/`RemoveSlots`. Tested against swtpm in CI; nothing here has
run on a real TPM yet. Each row is a reading of the spec, or a gap left for a
later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| T1 | HW-5a's first option, a **signed PCR policy**, done in Go with `github.com/google/go-tpm` v0.9.8 rather than systemd tools. `systemd-cryptenroll` enrolls LUKS volumes, and the vault is a file. `systemd-creds` can seal a file to a signed policy, but that mode expects `systemd-measure` signatures over PCR 11, which only unified kernel images produce. S7's boot uses Type #1 entries behind Debian's shim, so there are no UKIs. [Inference: from systemd documentation, not exercised.] go-tpm is Google's pure-Go TPM 2.0 library and is used by go-attestation and go-tpm-tools. It is vendored and hash-pinned like x/crypto (K2). It pulls in `golang.org/x/sys/unix` for `poll`. Two of that package's files hold URLs that are text, not endpoints: a build script and a Solaris panic message. They are listed as exact path and host pairs under `not_endpoints` in `assurance/dependencies.json`, and `tools/depaudit.py` still checks the same hosts everywhere else. Only `cmd/agentos-egress` links `tpmseal` (`tpmseal/imports_test.go`), and `agentosd` links neither it nor the vault (`daemon/arc2_test.go`). | HW-5a, DEP-1, ARC-1 | Moving to `systemd-pcrlock` means swapping `tpmseal`. The slot format (T2) does not change. |
| T2 | **Seal.** The slot's key-encryption key is 32 random bytes. It is sealed as a TPM keyed-hash object under the storage root key, which is recreated each time from the owner seed with the TCG ECC P-256 template. The object is policy-only (no `userWithAuth`). Its policy is `PolicyAuthorize(box policy key, "agentos-vault-pcr-policy/v1")`, followed by `PolicyAuthValue` when a boot PIN is set. The slot records the SRK's name, and every later use checks that name before trusting the SRK as a salt key. Create and Unseal both run in sessions salted to the SRK, with AES-CFB parameter encryption, so the secret never crosses a discrete TPM's bus in the clear. An interposer cannot substitute its own salt key without changing the SRK's name. Unseal also checks the object's attributes and policy digest against the record, so a swapped object is refused. | CRED-8, HW-5a; security review #16 (TPM bus) | — |
| T3 | **Policies.** Each approved boot path is one signed policy kept in `vault.pcrpolicy` beside the keys file. A policy holds a PCR selection (SHA-256 bank), the composite digest, and the box key's ECDSA P-256 signature over the PolicyPCR digest and policy ref. The file holds no secrets. The PCR selection lives in the signed policy, not in the sealed object, so changing which PCRs are measured needs a new signature but no reseal. The default PCRs are 4 (boot loader and kernel), 9 (initrd) and 12 (kernel command line, which carries `usrhash=`), matching the Type #1 boot measured in S7. [Risk 14: unverified on Debian firmware.] Refusing an unmeasured PCR (all zeros or all ones) is a hard rule, so a wrong selection fails at trust time rather than approving every boot path. The file keeps the newest 16 policies. | HW-5a, A8 | `-pcrs` sets the selection. Prove the selection on S1 hardware. |
| T4 | **Updates.** `tpmseal.Sign` approves a release's predicted PCR values without touching the sealed object, and `TestABUpdateKeepsUnattendedRestart` proves the A/B case against swtpm. No runtime operation calls it yet: HW-5a allows signing only for a release that passed UPD-8 verification, and the updater does not exist. Until it does, the first boot after an update on a trusted PC is refused like a changed boot path (T6). The owner unlocks once with the passphrase and a code, then trusts the PC again. Predicting PCR 4 for a new kernel means replaying the firmware event log with the new image's hash, which `systemd-pcrlock` already does. The updater package should reuse it. Old signed policies remain valid, so a downgrade to an older signed release still unlocks; the cap of 16 bounds it. Fully closing it needs `PolicyAuthorizeNV` or a revocation counter, which belongs with the updater. | HW-5a, UPD-8 | Updater package (P4). |
| T5 | **Policy key.** The policy key is one ECDSA P-256 key per box, made the first time a PC is trusted. It is stored only in the vault as `pcr-policy-key`, of kind `pcr_policy_key`. The proxy cannot inject it (`apiKeysOnly`). `put` cannot overwrite it or any other non-`api_key` entry. `TestPolicyKeyStaysInTheVault` scans the drive files for it. The key never leaves the vault process. | HW-5a, ARC-1, CRED-1 | — |
| T6 | **Boot.** `serve` tries this PC's slot once at start. If it opens, the model route is served with no owner input (unattended restart). A slot with a boot PIN waits for `/unlock-pin`, and `/status` says `"pin": true`. A PC without a slot is an unknown host. A trusted PC whose boot path matches no signed policy stays locked, and the owner is told the drive may have been tampered with unless they just updated. Every refused case leaves the CRED-8 unknown-host unlock (passphrase plus code) available. The owner texts for these events wait for P2-3; for now they are logged through `custody.notify`, as K6 does. | CRED-8, HW-5a | P2-3 adds the texts. |
| T7 | **Boot PIN** (off by default; Mark's decision, D7). A PIN has 4 to 64 characters. It becomes the object's auth value as 32 hex characters of a salted SHA-256: 128 bits, with no zero byte. The hex form works around a go-tpm v0.9.8 bug: its session HMAC key is cut at the first zero byte of an auth value, so about one right PIN in eight failed. The TPM's dictionary-attack lockout limits guesses, since PIN slots are not `noDA`. Tries are also spaced 2 s apart, like passphrase tries. When the TPM is locked out, the owner unlocks with the passphrase and a code. Trusting the same PC again replaces its slot, which is how a PIN is added or removed. | CRED-8 | — |
| T8 | **Adding or removing a trusted host** (CRED-9, tier 4) needs the vault open, a request on the unlock socket (the local UI's uid, which serves as local confirmation, CH-3), and a code-generator code checked against the seed inside the vault process. The code check shares the last accepted step and the wrong-code cap with the unknown-host unlock (K5). So a code works once across both, and three wrong codes in 24 h refuse both until the oldest ages out. A wrong code here does not lock an open vault. Hosts are named by their SRK name in hex, plus the DMI product name for the owner. The recovery-key alternative in CH-3 waits for P2-8. During setup, §8.1 makes the first PC trusted by default; the setup flow (P2-2) calls `/trust` for it. | CRED-9, CH-3, CH-4, §8.1 | P2-2 wires the setup default and the local pages; P2-8 the recovery-key path. |
| T9 | **Data key in memory.** A vault opened through its slots keeps one copy of the data key so `AddSlot` can wrap it for a new PC without the card. `Close` wipes the copy. The cipher's AES key schedule is equivalent to the key and is in memory whenever the vault is open, so the copy adds no exposure. | CRED-1, CRED-8 | — |
| T10 | **Not in this package.** V6, the TPM NV rollback counter, changes the vault file format that P2-8's restore also reads, so it is split out as P2-4d. Tuning Argon2id on the N95 (HW-4) and an A8 run on a real TPM wait for hardware (S1). | CRED-8, REC-2, A8 | P2-4d; hardware. |
