# Trusted-host TPM slot: assumptions

Built for PLAN P2-4b (cloud part) against SPEC v0.12 on top of P2-4a (#29),
which added key slots and the vault process. Covers `broker/tpmseal`, the
trusted-host parts of `cmd/agentos-egress` (`trusted.go`, `custody.go`), and
`vault.AddSlot`/`RemoveSlots`. Tested against swtpm in CI; nothing here has
run on a real TPM yet. Each row is a reading of the spec, or a gap left for a
later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| T1 | HW-5a's first option, a **signed PCR policy**, done in Go with `github.com/google/go-tpm` v0.9.8 rather than systemd tools. `systemd-cryptenroll` enrolls LUKS volumes, and the vault is a file. `systemd-creds` can seal a file to a signed policy, but that mode expects `systemd-measure` signatures over PCR 11, which only unified kernel images produce. S7's boot uses Type #1 entries behind Debian's shim, so there are no UKIs. [Inference: from systemd documentation, not exercised.] go-tpm is Google's pure-Go TPM 2.0 library and is used by go-attestation and go-tpm-tools. It is vendored and hash-pinned like x/crypto (K2). It pulls in `golang.org/x/sys/unix` for `poll`. Two of that package's files hold URLs that are text, not endpoints: a build script and a Solaris panic message. They are listed as exact file and host pairs under `inert_literals` in `assurance/dependencies.json`, and `tools/depaudit.py` still checks the same hosts everywhere else. Only `cmd/agentos-egress` links `tpmseal` (`tpmseal/imports_test.go`), and `agentosd` links neither it nor the vault (`daemon/arc2_test.go`). | HW-5a, DEP-1, ARC-1 | Moving to `systemd-pcrlock` means swapping `tpmseal`. The slot format (T2) does not change. |
| T2 | **Seal.** The slot's key-encryption key is 32 random bytes. It is sealed as a TPM keyed-hash object under the storage root key, which is recreated each time from the owner seed with the TCG ECC P-256 template. The object is policy-only (no `userWithAuth`). Its policy is `PolicyAuthorize(box policy key, "agentos-vault-pcr-policy/v1")`, followed by `PolicyAuthValue` when a boot PIN is set. Every time the SRK is loaded, its public area must hash to the name the TPM returned and keep the template's shape (restricted P-256 decryption key, no policy), or nothing is salted to it (`ErrSRK`; `TestSubstitutedSRKPublicRefused` runs an interposer that swaps the public area and checks no session is started). The slot records the SRK's name, and every later use checks that name too. Create and Unseal both run in sessions salted to the SRK, with AES-CFB parameter encryption, so the secret never crosses a discrete TPM's bus in the clear. The name binding protects every use after the first. At the first seal, nothing yet ties the SRK to this TPM, so an active interposer present at that moment could answer with a key and name of its own. Closing that needs the SRK checked against the EK certificate chain (K2). Unseal also checks the object's attributes and policy digest against the record, so a swapped object is refused. | CRED-8, HW-5a; security review #16 (TPM bus) | — |
| T3 | **Policies.** Each approved boot path is one signed policy kept in `vault.pcrpolicy` beside the keys file. A policy holds a PCR selection (SHA-256 bank), the composite digest, and the box key's ECDSA P-256 signature over the PolicyPCR digest and policy ref. The file holds no secrets. The PCR selection lives in the signed policy, not in the sealed object, so changing which PCRs are measured needs a new signature but no reseal. The default PCRs are 4 (boot loader and kernel), 7 (Secure Boot state: db, dbx; the arbitrator's ruling on #42), 9 (initrd) and 12 (kernel command line, which carries `usrhash=`), matching the Type #1 boot measured in S7. The policy file also records the last approved path's PCR values, as a hint only. When nothing but PCR 7 changed, the owner sees "Secure Boot settings on this PC changed. If you updated firmware, unlock with your card to keep this PC trusted." [Risk 14: unverified on Debian firmware.] Refusing an unmeasured PCR (all zeros or all ones) is a hard rule, so a wrong selection fails at trust time rather than approving every boot path. The file keeps the newest 16 policies. | HW-5a, A8 | `-pcrs` sets the selection. Prove the selection on S1 hardware. |
| T4 | **Updates.** `tpmseal.Sign` approves a release's predicted PCR values without touching the sealed object, and `TestABUpdateKeepsUnattendedRestart` proves the A/B case against swtpm. No runtime operation calls it yet: HW-5a allows signing only for a release that passed UPD-8 verification, and the updater does not exist. Until it does, the first boot after an update on a trusted PC is refused like a changed boot path (T6). The owner unlocks once with the passphrase and a code and keeps the PC trusted in the same step. Predicting PCR 4 for a new kernel means replaying the firmware event log with the new image's hash, which `systemd-pcrlock` already does. The updater package should reuse it. **Rollback is not bounded.** A signed policy never expires. The cap of 16 only trims the owner's own policy file, and an attacker keeps every policy they copied from the drive. So any boot path the box ever approved, including an old release with a known flaw, still unlocks the vault on this PC. Only `PolicyAuthorizeNV` or a revocation counter can bound this (K3). | HW-5a, UPD-8 | Updater package (P4), K3, K4. |
| T5 | **Policy key.** The policy key is one ECDSA P-256 key per box, made the first time a PC is trusted. It is stored only in the vault as `pcr-policy-key`, of kind `pcr_policy_key`. The proxy cannot inject it (`apiKeysOnly`). `put` cannot overwrite it or any other non-`api_key` entry. `TestPolicyKeyStaysInTheVault` scans the drive files for it. The key never leaves the vault process. Within it, `Secret.Reveal` returns a Go string that cannot be wiped, so a copy of the DER key stays in the process's heap until the memory is reused. The same holds for the seed and the lockout authorization. That is the vault process's existing exposure (P2-4a's K-rows), not a new one. | HW-5a, ARC-1, CRED-1 | — |
| T6 | **Boot.** `serve` tries this PC's slot once at start. If it opens, the model route is served with no owner input (unattended restart). A slot with a boot PIN waits for `/unlock-pin`, and `/status` says `"pin": true`. A PC without a slot is an unknown host. A trusted PC whose boot path matches no signed policy stays locked. If the running image's `IMAGE_VERSION` (os-release) differs from the one recorded at the last trusted unlock, the owner sees "Box updated. Unlock once with your passphrase and a code; this PC stays trusted after that." Otherwise they see "This PC started the box in a way it hasn't before. If you didn't change anything, the drive may have been tampered with. Unlock only if you're sure." Both versions come from the drive, which an attacker can edit, so this check only picks the wording. Both cases need the same full unlock. `/status` reports `boot_changed` and `updated`. The fallback unlock then offers "Keep this PC trusted" (`keep_trusted` on `/confirm`). It is never ticked by default (the Security lens condition on #50): `updated` and `secure_boot` come from files on the drive, not from a verified release's measured boot, and a modified initrd can make only PCR 7 look changed. A tampered boot path must not become trusted unless the owner says so (`[y/N]` in the CLI, unticked on the local page). A release the updater verified (K4) has its policy signed before the reboot, so it unlocks unattended and never reaches this prompt; no strong source of `updated` is needed. It approves the running boot path with the same proof as CRED-9: the passphrase, a code, and the local page. It adds a signed policy without resealing, so a PIN slot keeps its PIN. Every refused case leaves the CRED-8 unknown-host unlock (passphrase plus code) available. The owner texts for these events wait for P2-3; for now they are logged through `custody.notify`, as K6 does. | CRED-8, HW-5a | P2-3 adds the texts. |
| T7 | **Boot PIN** (off by default; Mark's decision, D7). A PIN has 6 to 64 characters, counted as characters (the arbitrator's ruling). It becomes the object's auth value as 32 hex characters of a salted SHA-256: 128 bits, with no zero byte. The hex form works around a go-tpm v0.9.8 bug: its session HMAC key is cut at the first zero byte of an auth value, so about one right PIN in eight failed. The TPM's dictionary-attack lockout limits guesses, since PIN slots are not `noDA`. That limit means nothing while the lockout authorization is empty, as most TPMs ship: anyone could reset the counter. So when the owner turns a PIN on, the box takes the lockout hierarchy, and only then (the arbitrator's ruling: PIN only, and reversible) (`tpmseal.TakeLockout`). It stores a random 128-bit authorization in the vault first (kind `tpm_lockout_auth`, under a reserved `tpm-lockout-` name that `put` and the proxy refuse). It then sets the dictionary-attack parameters while the authorization is still empty: 10 tries, one forgiven every 2 hours, and a 24-hour lockout after a wrong lockout authorization. Last, it changes the authorization in a salted, encrypted session. A thief therefore gets about twelve PIN guesses a day. `TestPINSlotTakesTheLockoutHierarchy` checks that an empty-password reset fails, and `TestPINLockout` checks that the right PIN is refused after ten wrong ones. Setting up a PIN tells the owner "This also locks this PC's TPM reset to the box until you turn the PIN off." If other software already set the lockout authorization, the PIN is refused and that authorization is never guessed: "Another system on this PC controls the TPM…". Turning the PIN off (trusting the PC again without one) or removing this PC from the trusted hosts changes the authorization back to empty with the vault's copy (`tpmseal.ReleaseLockout`), and the vault forgets it. After a wrong lockout password, the TPM refuses even the right one for 24 hours. A give-back in that window keeps the authorization, tells the owner, and is retried at each unattended start. When the removed PC is not the one the box runs on, its TPM is out of reach, so its entry stays until that PC is trusted again without a PIN. The box never resets the guess counter itself. While a PIN is on, re-trusting the PC proves that the TPM still holds the box's value (an auth-to-auth change). A new entry is deleted only when the TPM certainly never took it. Known gap: a vault restored or rolled back to a copy without the entry, on a TPM that still holds the box's authorization, can never turn a PIN on for that TPM again until the TPM is cleared in firmware. After a TPM clear, the old `tpm-lockout-<old SRK>` entries stay in the vault unused. P2-8's restore and P2-4d should prune them. Tries are also spaced 2 s apart, like passphrase tries. When the TPM is locked out, the owner sees "Too many wrong PINs. Unlock with your passphrase and a code instead." A PIN counts characters, not bytes. Trusting the same PC again replaces its slot, which is how a PIN is added or removed. | CRED-8 | — |
| T8 | **Adding or removing a trusted host** (CRED-9, tier 4) needs the vault open, a request on the unlock socket (the local UI's uid, which serves as local confirmation, CH-3), and a code-generator code checked against the seed inside the vault process. The code check shares the last accepted step and the wrong-code cap with the unknown-host unlock (K5). So a code works once across both, and three wrong codes in 24 h refuse both until the oldest ages out. A wrong code here does not lock an open vault. Hosts are named by their SRK name in hex. The owner sees a label such as "GEEKOM Air12, trusted Oct 5", with this PC marked. Removing a host deletes its slot but does not rotate the vault's data key. A copy of the slot and the vault taken before the removal still opens on that PC's TPM, on an approved boot path. Rotating the data key belongs with P2-8's re-key. The recovery-key alternative in CH-3 waits for P2-8. During setup, §8.1 makes the first PC trusted by default; the setup flow (P2-2) calls `/trust` for it. | CRED-9, CH-3, CH-4, §8.1 | P2-2 wires the setup default and the local pages; P2-8 the recovery-key path. |
| T9 | **Data key in memory.** A vault opened through its slots keeps one copy of the data key so `AddSlot` can wrap it for a new PC without the card. `Close` wipes the copy. The cipher's AES key schedule is equivalent to the key and is in memory whenever the vault is open, so the copy adds no exposure. | CRED-1, CRED-8 | — |
| T10 | **Not in this package.** V6, the TPM NV rollback counter, changes the vault file format that P2-8's restore also reads, so it is split out as P2-4d. Tuning Argon2id on the N95 (HW-4) and an A8 run on a real TPM wait for hardware (S1). | CRED-8, REC-2, A8 | P2-4d; hardware. |

## Conditions for later packages

These came from the security review of #42. Each must hold before the trusted-host slot protects anything in production.

| # | Condition | Owner |
|---|---|---|
| K1 | **The image must keep the boot path's meaning.** The measured PCRs vouch for the kernel, initrd and command line. Everything after that has to be fixed by `usrhash=`: dm-verity over `/usr` must cover everything that runs or configures `agentosd`, the vault process and their units. State partitions are mounted `noexec,nosuid,nodev`. There is no unauthenticated rescue or emergency target, no autologin, and the boot loader's editor is off. Root services treat state files as untrusted input. Otherwise an attacker edits the writable state and the approved boot path runs their code. Consider `iommu=force` against DMA from a hostile device. | P2-1 (image) |
| K2 | **Qualify on a firmware TPM.** The SRK binding (T2) trusts the first seal. If a discrete TPM is ever used, check the SRK against the EK certificate chain before the first seal. Prove on S1 hardware that PCR 7 stays stable across normal boots. | S1 (hardware) |
| K3 | **Bound rollback before runtime signing.** Before the updater calls `tpmseal.Sign` at runtime, it must revoke old policies through `PolicyAuthorizeNV` or a monotonic counter, so that a downgrade to an old signed release stops unlocking (T4). | Updater (P4) |
| K4 | **Updater brief.** Call `tpmseal.Sign` for every UPD-8-verified release before rebooting into it. A firmware or db/dbx update the box itself applies must extend the PCR 7 prediction, or re-sign the policy, before the reboot (the arbitrator's ruling). Until the updater does this, stage updates and text the owner "update ready; it will need one unlock on the local page", then apply at a time the owner chooses. | Updater (P4), P2-3 |
| K5 | **Order.** P2-4d (V6 rollback counter) lands before #35's recovery path is wired and before production. | P2-4d |
| K6 | **Not done here: extending a PCR after unseal.** Extending a PCR once the slot is unsealed would stop anything later in the same boot from unsealing again. It would also break `SignCurrent` for "trust again" and "keep trusted" within that boot. It needs its own PCR outside the selection plus a separate policy branch, so it waits for the arbitrator. | Arbitrator |
