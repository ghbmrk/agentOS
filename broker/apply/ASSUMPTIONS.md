# Update apply, broker side: assumptions

Built for UPD-a (BOARD.md) against SPEC v0.12 UPD-1, UPD-1a, UPD-5 and UPD-6, on the update verifier (`broker/update`) and the change pipeline's staged image adoptions (`change.ConfirmStaged`, `change.StageFailed`). Covers `broker/apply`. Each row is a reading of the spec, with what changes if the reading is wrong.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| A1 | **Flow.** The change pipeline adopts an upstream image release as a staged adoption (CHG-3). The wiring then calls `Schedule` with the release's `*update.Verified` and the adoption's reference. `Tick` applies it when it is due and the box is free: it journals one `meta.release` intent (`journal.ActionReleaseActivate`, origin and executor `update`, ID `upd:apply:<version>:n<seq>`), whose executor saves the rollback point, records the release in the update store (`Store.Stage`) and has the activator write it to the inactive slot. Once the intent has succeeded, `Tick` restarts the box. After the restart, `Resume` commits the release (`Store.CommitStaged`, `ConfirmStaged`) once the new boot is blessed. If the box runs any other release, boot counting fell back: `Resume` drops the stage and reverts the adoption (`StageFailed`), with no owner action. | UPD-1, UPD-6 | — |
| A2 | **Rollback point.** The intent's params carry the release it replaces and the one it activates, each with its `/usr` root hash (UPD-1a), plus the adoption. The applier saves the same record before the handover. A fallback rewinds only the boot slot. Nothing the broker keeps lives in the image: the journal, grants and revocations, budgets, deletions, the update store's root metadata and seen keys. So the applier never snapshots or restores any of it, and a test checks that the journal and root metadata are unchanged after a fallback. | UPD-1 | If broker state ever moves into `/usr`, add an explicit carry-over. |
| A3 | **When (UPD-6).** The box is free when there is no call (`InCall`), no accepted work (`Working`) and the owner has not excluded the hour (`Excluded`). These are checked before submitting and again by `Check` at authorize and just before dispatch, so a call that starts in between stops the apply. A security fix is due at once. An ordinary release waits a random `Jitter` (default 6 hours, `crypto/rand`) and then for the box to be free (UPD-5's "quiet window with random jitter"). | UPD-5, UPD-6 | — |
| A4 | **Activator (P2-1).** `Install` writes the `/usr` image, its verity data and the boot entry to the inactive slot together and makes that entry the next boot with counted tries (UPD-1a); it does not restart. `Abandon` makes the inactive slot no longer the next boot. `Booted` reports the boot ID, the running `/usr` root hash and whether systemd-bless-boot blessed it. The release is judged by root hash, never by version. The fake in the tests stands in for systemd-sysupdate and bootctl until P2-1 lands. | UPD-1, UPD-1a | — |
| A5 | **Restarts.** A pending release is held in memory only, since a `*update.Verified` is never persisted. After a restart it is gone, and Loop 3's next check schedules it again. An apply in flight survives as the saved rollback point. If the broker stopped mid-handover, then in the same boot the apply is abandoned (`Abandon`, drop the stage). After a reboot it is judged by the boot like any other apply. A boot with the same ID as the handover is never judged, so a broker restart without a reboot is never taken for a fallback. | UPD-1 | — |
| A6 | **Policy.** `Check` allows only origin `update`, executor `update`, action `meta.release` on the broker account, for the release the applier holds, while the box is free. The grants gate has no `meta.release` delegation yet: the wiring adds it, as for `meta.loops.*` (GR18), together with reserving the `update` executor name. | OP-3, OP-5 | Wiring (W5b). |
| A7 | **Not wired.** `agentosd` does not build an applier yet. Wiring needs: the activator from P2-1; `InCall` from the modem; `Working` from accepted work in the journal and admission; the owner's excluded hours (a setting with texts and the local page); `Schedule` called from the pipeline's staged adoption of an upstream release; `Resume` at start and until it settles; and `Status` in STATUS. | UPD-6 | Wiring (W5b). |
