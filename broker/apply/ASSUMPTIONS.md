# Update apply, broker side: assumptions

Built for UPD-a (BOARD.md) against SPEC v0.12 UPD-1, UPD-1a, UPD-5 and UPD-6, and made the update clerk for MIG-4-adapters-e (#3428, brief `briefs/MIG-4-adapters.md` e) against SPEC v1.0 KRN-4, KRN-8 and CLK-2, on the update verifier (`broker/update`) and the change pipeline's staged image adoptions (`change.ConfirmStaged`, `change.StageFailed`). Covers `broker/apply`. Each row is a reading of the spec, with what changes if the reading is wrong.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| A1 | **Flow.** The change pipeline adopts an upstream image release as a staged adoption (CHG-3). The wiring then calls `Schedule` with the release's `*update.Verified` and the adoption's exact ID (`Report.ID`, never `Short`, which `ConfirmStaged` and `StageFailed` refuse). `Tick` applies it when it is due and the box is free: it submits one kernel plan (ID `upd:apply:<version>:n<seq>`) with one `change-account` step at the `update` clerk under the image-pinned update key (MIG-4-adapters-e-1), whose dispatch to `Do` saves the rollback point, records the release in the update store (`Store.Stage`) and has the activator write it to the inactive slot. The restart is its own step: once the activator took the release, `Tick` restarts only when the box is free again, since the slot write can take minutes. If the broker stopped before the restart, a later `Tick` in the same boot does it (security F1 on #133). After the restart, `Resume` commits the release (`Store.CommitRelease`, `ConfirmStaged`) once the new boot is blessed. If the box runs any other release, boot counting fell back: `Resume` drops the stage and reverts the adoption (`StageFailed`), with no owner action. A fallback does not retry the same release on its own (security C3 on #133), so the box does not reboot into the same bad release every day: the applier refuses it (#1924), recording a fallback by version (`FellBack`), and `Schedule` refuses that version with `ErrFellBack` and retires the adoption, so a wiring that schedules it again cannot reboot the box into it. A later version is admitted. An owner retry of a fallen-back release needs `Retry` to clear `FellBack` (LATER). | UPD-1, UPD-6 | — |
| A2 | **Rollback point.** The step's logged result (`Do`'s answer) carries the release it replaces and the one it activates, each with its `/usr` root hash (UPD-1a); the applier saves the same record, with the adoption, before the handover. A fallback rewinds only the boot slot. Nothing the broker keeps lives in the image: the kernel log, keys and revocations, budgets, deletions, the update store's root metadata and seen keys. So the applier never snapshots or restores any of it, and a test checks that the kernel log and root metadata are unchanged after a fallback. | UPD-1 | If broker state ever moves into `/usr`, add an explicit carry-over. |
| A3 | **When (UPD-6).** The box is free when STOP is not in force (`Stopped`; L3 on #133), there is no call (`InCall`), no accepted work (`Working`) and the owner has not excluded the hour (`Excluded`), and no message has gone between the owner and the agent in the last 10 minutes (`LastTalk`, `Quiet`; UX-133-4). That last rule holds for a security fix for at most 2 hours from when it became due (`TalkBound`). After that, only a call, accepted work or excluded hours hold it, so an agent or a spoofed sender that keeps talking cannot hold a fix forever (security ruling on UX-133-4). These are checked before submitting and again by the clerk just before it acts (CLK-2), so a call that starts in between stops the apply. A security fix is due at once. An ordinary release waits a random `Jitter` (default 6 hours, `crypto/rand`) and then for the box to be free (UPD-5's "quiet window with random jitter"). | UPD-5, UPD-6 | — |
| A4 | **Activator (P2-1).** `Install` writes the `/usr` image, its verity data and the boot entry to the inactive slot together and makes that entry the next boot with counted tries (UPD-1a); it does not restart. `Abandon` makes the inactive slot no longer the next boot. `Booted` reports the boot ID, the running `/usr` root hash and whether systemd-bless-boot blessed it. The release is judged by root hash, never by version. `broker/apply/bootab` is the activator (UPD-b3 (b), row UPD-b3-b); the fake in this package's tests stays for the applier's own tests. `bootab` passes `activatortest.Check` (A12). Condition for the real activator (security C2 on #133): `Install` writes exactly the TUF-verified files. Before it makes the entry the next boot, it runs `veritysetup verify` on the written slot against `UsrRootHash` and checks that the entry's `usrhash=` equals it, as `finish_image.py` does on #41, so a short write never gets a counted entry. | UPD-1, UPD-1a | — |
| A5 | **Restarts.** A pending release is held in memory only, since a `*update.Verified` is never persisted. After a restart it is gone: `New` retires and drops its adoption (below), and only A1's wiring offers the release again, under a new adoption (L3-2 on #605). An apply in flight survives as the saved rollback point. If the broker stopped mid-handover, then in the same boot the apply is abandoned (`Abandon`, drop the stage). `execute` succeeds only once the handover is saved as installed: if that save fails it abandons the slot and drops the stage, and the release stays pending (SR3-4). A rollback point never saved as installed is not handed over: in the same boot, or after a reboot that kept the old root, it is abandoned with no fallback recorded and no adoption reverted, so a power cut mid-handover does not mark a valid release as fallen back. If the activator cannot abandon it, the point stays and the next `Tick` or `Resume` abandons it. The cost is that a box that did try the new slot before the handover was saved tries it once more; that second try is recorded, so a real fallback is then judged as one. A boot of the new root is judged like any other apply. A boot with the same ID as the handover is never judged, so a broker restart without a reboot is never taken for a fallback. Unrecorded tries are bounded (SR3-4f-1b): the save before `Install` counts one try for the exact `update.Ref` (`Unrecorded`, saved), and the save that records the handover clears the count. An `Install` that returned an error does not count. At `maxUnrecorded` (2) the attempt is abandoned and its stage dropped. `StageFailed` is not called and `FellBack` is not set, since nothing shows the release is bad. `Last` becomes `unrecorded`, and the release is refused: `Schedule` returns `ErrRefused` naming the version and manifest digest, `Tick` drops it from pending, and `execute` does not install it. Only `Retry` admits it again. A failed `Abandon` after a failed `Install` leaves that try counted. **Drops are settled (SR3-4f-2b).** A release that leaves the applier before it is installed has its adoption retired and reverted with `StageDropped` (`WhyDropped`): `Tick`'s narrowing drop and `execute`'s `ErrPolicyMoved` drop (A9), a `Schedule` by another adoption that supersedes it, any `Schedule` refusal of an adoption the applier does not hold (`ErrRefused` included, so no adoption is left `Staged` by a refusal; until `Retry` each new adoption of a refused release is settled at once, L3 delta on #572 option (a)), the unrecorded bound, a saved `Pending` that `New` finds after a process restart, and a not-handed abandon that `Pending` no longer names. Within one boot a not-handed abandon of a release `Pending` still names settles nothing, and the next `Tick` installs it. The cost is accepted (L3 on #572 point 3): after a power cut between the pre-Install save and the handover, the release is scheduled again only under a new adoption (A1's wiring), and a release without attestor authority is asked about again. A retired adoption is never scheduled again: `Schedule` refuses it with `ErrRetired`. `Withdraw` (the owner's UNDO or a Recheck revert, through the pipeline) retires and drops an adoption without calling the pipeline, which reverts it itself. The drop is the backstop: if that revert fails or is cut short (STOP holds the pipeline's own, a nonce or run error, a cut before its journal), the next `Tick` settles it with `StageDropped`, a no-op once the revert ran, and an owner's revert that loses to it reports success (L3-1 and Security R1 on #605). `Withdraw` answers an error whose `Handover()` is true from the pre-Install save until `Resume` settles. Offering a dropped release again, under a new adoption and the current attestor policy, is A1's wiring (`maintain` M15 that did it went with #2785); an `ErrApplying` refusal of an incoming adoption while another release is in flight is one such drop (`reoffer_test.go`). If that wiring re-offers daily, a refused release is re-adopted and dropped once a day until `Retry`, and the owner of a release without attestor authority is asked again daily (LATER A5-reask). `Retired` is never pruned: one short ID per drop. | UPD-1, UPD-8, OP-4, OP-5 | If the bound needs tuning, change `maxUnrecorded`. |
| A6 | **Policy.** The clerk (`Do`) acts only on a request `check.Check` passes against the pinned update root alone, under a key off that root for `change-account` at this clerk only, for the one step of an applier plan naming exactly the release the applier holds, which `Store.Check` verified to the TUF threshold and is newer than the installed one, while the channel is not pinned and the box is free (MIG-4-adapters-e-1). The kernel must reserve the clerk name `update` for this clerk (wiring). | KRN-4, CLK-2, UPD-8 | Wiring (W5b). |
| A7 | **Not wired.** `agentosd` does not build an applier yet. Wiring needs: the activator from P2-1; `InCall` from the modem; `Working` from accepted work in the kernel log and admission; the owner's excluded hours (a setting with texts and the local page); `Schedule` called from the pipeline's staged adoption of an upstream release, with the adoption's exact `Report.ID`, never `Short`; `Resume` at start and until it settles; `LastTalk` from the owner channel; the image-pinned update root passed to `kernel.Boot` as a pinned root, never an anchor (#3701; the test rig boots that way), and `Paused` from the channel setting, before `agentosd` builds the applier; `Pin` called when the owner pins the channel, after `Paused` reports it and before the pin is reported as taken, again until it returns nil (MIG-4-adapters-e-pin); `Retry(ref)` from the owner's retry on my Wi-Fi page for a release refused as `unrecorded` (it saves the cleared count before it takes effect, and refuses with `ErrApplying` while an apply is in flight); `Status` in STATUS, where it is the only update line while an apply is pending or in flight and takes precedence over any other update line (UX R1 on #133); and `Digest` in the digest. `Status` says why an update waits (UX-133-3) and keeps a fallback until the next install. `Digest` says once that an update installed or fell back (UX-133-1, 133-2). Before wiring (potency C1 on #133): `Working` counts only the owner's work (agent work serving an owner goal); loop, replay and builder work is preemptible (RES-1) and never blocks an update. A security fix that finds no free moment within 24 hours is asked about once, paced by GR9 (`UPDATE NOW` or a time tonight), and repeated in the digest until it is installed. An ordinary release that has waited 7 days gets one digest line. Log missed free moments with their cause, so the 24 hours can be tuned. | UPD-6 | Wiring (W5b). |
| A8 | **First boot (UPD-b).** `ScheduleFirstBoot` takes a release with no adoption and no jitter, for `broker/firstboot` only (its F1, F7). With no adoption, `Resume` commits or drops the stage without calling the pipeline. A fallback is recorded by version (`FellBack`), and both `ScheduleFirstBoot` and `Schedule` refuse that version (`ErrFellBack`, checked under the applier's lock), so first boot never reboots into it again (A1). `Schedule` still requires an adoption. `ErrApplying` names the refusal while a release is in flight. | UPD-3, UPD-6 | — |
| A9 | **Narrowed attestor policy (SR3-6).** A release scheduled as a security fix whose `Security()` no longer holds (the box's attestor policy changed since its check, update U16) is dropped from pending at the next `Tick`, before any intent is submitted, and also when `Stage` refuses it with `update.ErrPolicyMoved` after a change that lands between the dispatch check and the stage. Both drops settle the adoption with `StageDropped` (A5), and A1's wiring schedules the release again only under a new adoption, under the current policy: through the owner when no listed attestor vouches for it. A narrowing after the handover is A13. Ordinary releases are not held. | UPD-8, UPD-5 | Revisit if execute's failure handling moves. |
| A10 | **Settling is durable (SR3-4).** `Resume` settles in three stores, in order: the update store (`CommitRelease`, or `DropStaged` after a fallback), the pipeline (`ConfirmStaged`, or `StageFailed`), then the applier's own state, where clearing `Applying` is the commit point. The new state is saved before it replaces the one in memory, so a failed save keeps the obligation in memory as well as on disk. Every step returns nil when it already happened for the same release and adoption, so a cut or an error at any boundary converges on a later `Resume` without installing again. The release is keyed by `update.Ref` (version, `/usr` root hash, manifest digest, saved in the rollback point as `ToManifest`), and the adoption by its exact ID, never its owner-facing short ID, which a revert frees for reuse. A rollback point saved before `ToManifest` existed takes the digest from the staged record of the same version and root; if that record is already gone, `Resume` refuses and the apply stays in flight. Until it settles, STATUS keeps the "installing" line and `Schedule` refuses with `ErrApplying`. A boot that runs neither root of the handed-over release is judged by the update store first (SR3-4f-1a). If `Installed()` already equals the exact `update.Ref`, a blessed boot of the release was being committed when the broker stopped, and a later boot came up on the previous root. That is settled as `installed_other_root`: `CommitRelease` (idempotent, it removes a leftover stage) and `ConfirmStaged`, never `DropStaged`, `StageFailed` or `FellBack`. Once committed, the adoption cannot be reverted, so this path converges where the fallback path would refuse forever. A legacy point whose `ToManifest` and staged record are both gone cannot be matched and takes the fallback path. If `Installed()` cannot be read (a torn file, a directory in its place), `Resume` returns the error and `Applying` stays set; a read error is never taken as "not installed", so it never falls back over a committed release. Drops follow the same order (SR3-4f-2b): the adoption is saved in `Retired` and `Dropped` before the pipeline is called, and leaves `Dropped` only once `StageDropped` succeeded. `Tick` (on its way out) and `Resume` call it for every ID in `Dropped`, and `StageDropped` is a no-op on an adoption already reverted, so a cut or an error converges. A drop made where no save can follow at once (`execute`'s `ErrPolicyMoved`) is saved by the same `Tick` before the call. An ID the pipeline refuses for good (an adoption already confirmed) stays in `Dropped` and is tried at every `Tick` (LATER.md). | UPD-1, UPD-1a, OP-4, OP-5 | — |
| A11 | **New outcomes (SR3-4f-1, SR3-4f-r1).** `installed_other_root`: in every boot whose `/usr` root differs from the update store's installed release (`Booted().UsrRootHash != Installed().UsrRootHash`), STATUS and the digest say "Update N is installed, but I started the previous version this time. I will start update N at my next restart. Nothing is needed from you." It is keyed on the root, not the boot it was settled in, so a later boot that again starts the previous root keeps saying so. In a boot that runs the release, STATUS is silent and the digest says "Update N is installed." A boot or store that cannot be read shows the second form: the line says what the box started, so it is shown only when that is known. `unrecorded`: STATUS (until `Retry` or the next install) and the digest once say "I could not record update N as installed, twice, so I stopped trying it. You can retry it on my Wi-Fi page." Either way, `Tick` admits the next update. The other-root line ends at the next release's `Install`: `execute`'s save before it clears an `installed_other_root` outcome, since that `Install` writes N's slot (A12(3)) and N then starts at no restart; a failed, unrecorded or withdrawn attempt does not bring the line back; the previous-version line (A17) takes its place. | UPD-1, UX-133-1, CH-12 | UX review may reword the lines. |
| A12 | **Activator after an other-root boot (P2-1, SR3-4f-1a, SR3-4f-r1).** Conditions for the real activator: (1) blessing is durable before `Booted().Blessed` reports true (the entry was renamed without its try counter and the ESP synced), so a blessed entry never runs out of tries; (2) a blessed entry stays the default boot until a later `Install` replaces it, so a box that came up on the previous root once (a manual pick, a firmware fallback) starts the installed release at its next restart, as the line promises; (3) `Install` while running the previous root treats the slot not booted as the inactive one, so it overwrites the slot holding N, and never the slot that is running; (4) before `Install` writes any byte of a slot whose entry is blessed, it takes that entry out of the boot menu and makes the running root's entry the default, durably (ESP written and synced), so an `Install` that fails or is abandoned partway never leaves the default entry, which has no tries left to fall back on (1), pointing at a half-written slot, even when a power cut drops the ESP writes not yet synced. (3) and (4) have an acceptance check (SR3-4f-r1-f1): `activatortest.Check` runs `Install` of N+1 booted on N-1 with N blessed and default, cut before each of its disk steps in turn (ESP entry writes, default, ESP sync, slot writes, slot sync), and requires that the booted slot is never written, that N-1 stays the default boot (or a whole, counted N+1 is) on both the synced and the written ESP, that no blessed entry points at a torn slot, and that an uncut `Install` after the reboot finishes. The check also judges a slot whole only when its data and verity partitions hash to the release's images and carry the UUIDs its `usrhash=` finds, and takes the next boot as systemd-boot (v260) does: `LoaderEntryOneShot`, then `LoaderEntryDefault`, then `loader.conf`'s default, each a glob matched with no boot assessment, then menu order with no-tries entries last and newer versions first. It sweeps no pin, EFI pins on N-1 and N, a one-shot pick of N and `loader.conf` pins on N and N-1, and after an uncut Install counts N+1's tries to 0 and requires N-1 next (#2094; Security finding 1 on #3964). `bootab` passes it over its `Disk` interface (`bootab_test.go::TestCheck`); (1) and (2) depend on the loader and stay on UPD-b3 (c)'s boot drill. The applier does not hold the next release until N has booted (SR3-4f-r1 (b)): that would hold every later update, security fixes included, on a restart nothing schedules, and forever if the loader never picks N (UPD-1). So after `installed_other_root` the next release N+1 installs over N's slot, with its rollback point on the root that runs (N-1). The cost is one double failure: N+1 falls back too, and the box runs N-1 while the store holds N as installed, until N+2; STATUS says so (A17). A test pins that the next release is admitted. | UPD-1, UPD-1a | If P2-1 cannot hold (1) or (2), the line's "next restart" sentence changes and the release is installed again. If the double failure above is judged worse than a held update, `Schedule` refuses the next release while the root differs, and the owner gets a restart prompt. |
| A13 | **Narrowing after the handover (SR3-4f-2c).** A security fix handed over in this boot whose release no longer reports `Security()` when the restart is due is not restarted into, and nor is one whose held release a process restart lost (it is never persisted, so it cannot be judged again: fail closed). Under the applier's lock: `Abandon`, `DropStaged`, then save `Applying = nil` with `Last` not handed and the adoption retired; `StageDropped` follows (A10). No fallback is recorded. An ordinary release is restarted into as before. Not covered: an unplanned reboot after `Install` boots the counted entry before any check runs, and `Resume` judges that boot like any other, so a release whose attestors were removed meanwhile can start once. | UPD-8, UPD-1 | Close it with the boot's health check (P2-1) or an abandon at shutdown, if the activator can tell an unplanned reboot. |
| A14 | **Security withdraw after the handover (SR3-4f-3a).** `Withdraw(adoption, WhySecurity)` for the apply in flight withdraws it when the activator took the release (`Installed`), the box still runs the boot it was handed over in, and no install is executing: it saves `Withdrawing` on the point first, then `Abandon`, `DropStaged`, and saves `Applying` cleared with the outcome `not_handed` and the adoption retired and dropped. No fallback is recorded. A failed step returns `ErrApplying` (with `Handover()` true) wrapping the cause and clears nothing; while `Withdrawing` is saved, `restartIfHandedOver` never restarts into the release and finishes the withdraw instead, across a process restart, so the next `Tick` or `Withdraw` completes it. Once the `Abandon` took, the point is saved `Abandoned` before `DropStaged` (#3852); until then a reboot boots the counted entry and `Resume` commits it, so the refusal has `Starts()` true (a failed mark save too, security fix or not) and STATUS reads the "may start" line below; with `Abandoned` saved it has `Starts()` false and STATUS reads "Update N failed a security check; I will not start it. Nothing is needed from you." Round 1 (#614): `restartIfHandedOver` rechecks the point under the applier lock after `Booted` and after the busy check, and marks `restarting` before it calls `Restart`; a withdraw then is refused with `Starts()` true, and the mark clears if `Restart` fails. A security `Withdraw` refused while an install executes, or before the point records `Installed`, returns `ErrApplying` with `Starts()` false; the refusal is kept in memory by adoption, `execute` saves the point as `Withdrawing` so the image never boots, and `Tick` drops that adoption's pending release. A refusal on a new or unread boot, or during the restart, has `Starts()` true. While a refusal stands, STATUS reads the "will not start" line, or "Update N failed a security check while it was being installed; it may start before I can undo it. Nothing is needed from you." when `Starts()` is true. If the box reboots with `Withdrawing` or `Abandoned` saved, `Resume` judges the boot: the old root settles as `not_handed` (the withdraw's `Abandon` took), not as a fallback; the new root, which booted because `Abandon` never took before the reboot, settles as installed and confirmed, and the pipeline's next `Recheck` reverts the confirmed adoption. | UPD-1, UPD-8, OP-5 | If `Recheck` stops running after a settle, a release that booted mid-withdraw stays until the next pass. |
| A15 | **Only a security failure withdraws (SR3-4f-3a).** `WhySecurity` is the pipeline's `change.WhySecurity` (a test pins them equal; apply does not import change). An owner UNDO, a regression revert or any other reason keeps the SR3-4f-2 refusal in the handover window, as do an install still executing, a point not yet `Installed`, and a new boot (`Resume` decides). Those refused reverts run once the apply settles. | UPD-1, ADP-4 | A new revert reason that must stop an image joins `WhySecurity` here. |
| A16 | **Permanent drop refusals (SR3-4f-3c).** A `StageDropped` error with a `Permanent() bool` method reporting true (`change.ErrNotStaged`: the adoption is confirmed or unknown) clears that ID from `Dropped`; any other error keeps it for the next settle. The applier tells it apart by the method, not by importing change. | UPD-1, OP-5 | — |
| A17 | **Previous-version line (SR3-4f-r1-f2).** When no apply is in flight (`Applying` nil, no install executing) and the boot and the store both read, with the store's installed root recorded and differing from the booted root, STATUS says "I am running the previous version, not update N. Nothing is needed from you; a later update will replace it." with N the store's installed release. After a fall-back or an unrecorded outcome, that outcome's line names "the version before update N" itself, so it stays one segment (#3830); after a not-installed outcome, and in the digest after any other outcome, the first sentence is added to that outcome's line; an `installed_other_root` outcome keeps its own line. The line makes no restart promise: once N+1's `Install` ran, N's slot may hold N+1's bytes (A12(3)), so N may not start. Offering N again was the alternative; it needs a fresh Stage and Install of a release the store already holds as installed, a larger change to the store and the applier. An unreadable boot or store, or a store that never recorded a root, shows nothing (CH-12). | UPD-1, UPD-1a, CH-12 | UX review may reword the line. | MIG-4-adapters-e-1 | **The image-pinned update key** (decision 2 of brief #3423, Mark's card cmsg_01R91wiieBzMSvPKFsAJVvuKUCsPpUiKJNwvXkmXsdfr63). So the image pins a standing root (`Config.Pinned`) for clerk `update` and verb `change-account` only, and the applier signs each plan as its holder (`Config.Holder`). Its authority is the project's signing threshold (UPD-2), not the owner's: the clerk acts only on the release `Store.Check` verified to the TUF threshold and newer than the installed one, so whoever holds the key can only ask for the activation the scheduler would make anyway; a holder kept in the image is therefore not a secret. Conditions on the wiring (release finding filed on the PR): the kernel admits and grants this root from the image without an owner grant, and never takes the pinned key as an anchor, since an anchor signs enrollments and cosigns for every clerk; `agentosd` supplies `Paused` from the channel setting. `kernel.Boot` takes it as a pinned root (#3701), and the rig boots that way. | KRN-4, UPD-2, UPD-3, UPD-4, UPD-8 | If Mark later moves activation under an owner key, `pinnedKey` and `Config.Pinned` give way to the owner's anchors. |
| MIG-4-adapters-e-2 | **Probe settles a lost answer (KRN-8).** The step is the handover. `Probe` answers from saved state and the boot counter: done once the activator took the release (handed over and waiting for the restart, committed, health check pending, fell back, withdrawn), unknown while an install runs or an unrecorded handover waits for `Resume` to abandon it, notdone once nothing of it is handed over. A redo after notdone is refused unless the applier still holds that release pending, and a handed-over step is answered ok without a second `Install` (`Applied`). `Applied` keeps only the latest handover, so a probe of an older plan answers notdone, and its redo is refused as not the held release. | KRN-8, UPD-1 | — |
| MIG-4-adapters-e-3 | **The kernel's duplicate guard governs retries (KRN-8).** The kernel admits no plan whose step repeats one that succeeded within 24 hours or is still unreconciled. So the same release is never activated again by a new plan within a day of its handover (it fell back or was withdrawn: only A1's wiring offers it again, under a new adoption), and an unrecorded handover in the same boot is retried by the kernel's redo of the first plan once its probe finds it not done (A5's retry), not by a second plan. A plan the kernel rejects is never dispatched, so `Tick` waits `Quiet` (`asked`) before it submits another. | KRN-8, UPD-1 | If an owner retry within the day is wanted, it is the owner's RETRY at the step's tier (KRN-8). |
