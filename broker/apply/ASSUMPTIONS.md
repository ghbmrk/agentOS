# Update apply, broker side: assumptions

Built for UPD-a (BOARD.md) against SPEC v0.12 UPD-1, UPD-1a, UPD-5 and UPD-6, on the update verifier (`broker/update`) and the change pipeline's staged image adoptions (`change.ConfirmStaged`, `change.StageFailed`). Covers `broker/apply`. Each row is a reading of the spec, with what changes if the reading is wrong.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| A1 | **Flow.** The change pipeline adopts an upstream image release as a staged adoption (CHG-3). The wiring then calls `Schedule` with the release's `*update.Verified` and the adoption's exact ID (`Report.ID`, never `Short`, which `ConfirmStaged` and `StageFailed` refuse). `Tick` applies it when it is due and the box is free: it journals one `meta.release` intent (`journal.ActionReleaseActivate`, origin and executor `update`, ID `upd:apply:<version>:n<seq>`), whose executor saves the rollback point, records the release in the update store (`Store.Stage`) and has the activator write it to the inactive slot. The restart is its own step: once the activator took the release, `Tick` restarts only when the box is free again, since the slot write can take minutes. If the broker stopped before the restart, a later `Tick` in the same boot does it (security F1 on #133). After the restart, `Resume` commits the release (`Store.CommitRelease`, `ConfirmStaged`) once the new boot is blessed. If the box runs any other release, boot counting fell back: `Resume` drops the stage and reverts the adoption (`StageFailed`), with no owner action. A fallback does not retry the same release on its own (security C3 on #133): Loop 3 keeps an adopted proposal across restarts (`maintain.New` forgets only those awaiting the owner) and never proposes it again, so the box does not reboot into the same bad release every day. It is Loop 3's record that blocks a reschedule, not `StageFailed`: the applier itself would take a `Schedule` of the same release again, so the wiring must not schedule a release Loop 3 did not just propose. The wiring still has to correct Loop 3's status line after a fallback, and give the owner a way to retry. | UPD-1, UPD-6 | — |
| A2 | **Rollback point.** The intent's params carry the release it replaces and the one it activates, each with its `/usr` root hash (UPD-1a), plus the adoption. The applier saves the same record before the handover. A fallback rewinds only the boot slot. Nothing the broker keeps lives in the image: the journal, grants and revocations, budgets, deletions, the update store's root metadata and seen keys. So the applier never snapshots or restores any of it, and a test checks that the journal and root metadata are unchanged after a fallback. | UPD-1 | If broker state ever moves into `/usr`, add an explicit carry-over. |
| A3 | **When (UPD-6).** The box is free when STOP is not in force (`Stopped`, by default the journal's; L3 on #133), there is no call (`InCall`), no accepted work (`Working`) and the owner has not excluded the hour (`Excluded`), and no message has gone between the owner and the agent in the last 10 minutes (`LastTalk`, `Quiet`; UX-133-4). That last rule holds for a security fix for at most 2 hours from when it became due (`TalkBound`). After that, only a call, accepted work or excluded hours hold it, so an agent or a spoofed sender that keeps talking cannot hold a fix forever (security ruling on UX-133-4). These are checked before submitting and again by `Check` at authorize and just before dispatch, so a call that starts in between stops the apply. A security fix is due at once. An ordinary release waits a random `Jitter` (default 6 hours, `crypto/rand`) and then for the box to be free (UPD-5's "quiet window with random jitter"). | UPD-5, UPD-6 | — |
| A4 | **Activator (P2-1).** `Install` writes the `/usr` image, its verity data and the boot entry to the inactive slot together and makes that entry the next boot with counted tries (UPD-1a); it does not restart. `Abandon` makes the inactive slot no longer the next boot. `Booted` reports the boot ID, the running `/usr` root hash and whether systemd-bless-boot blessed it. The release is judged by root hash, never by version. The fake in the tests stands in for systemd-sysupdate and bootctl until P2-1 lands. Condition for the real activator (security C2 on #133): `Install` writes exactly the TUF-verified files. Before it makes the entry the next boot, it runs `veritysetup verify` on the written slot against `UsrRootHash` and checks that the entry's `usrhash=` equals it, as `finish_image.py` does on #41, so a short write never gets a counted entry. | UPD-1, UPD-1a | — |
| A5 | **Restarts.** A pending release is held in memory only, since a `*update.Verified` is never persisted. After a restart it is gone: `New` retires and drops its adoption (below), and the release is offered again only once BOARD SR3-4f-2-r1 lands, since `maintain` today offers again only lapsed proposals awaiting the owner (L3-2 on #605). An apply in flight survives as the saved rollback point. If the broker stopped mid-handover, then in the same boot the apply is abandoned (`Abandon`, drop the stage). `Execute` succeeds only once the handover is saved as installed: if that save fails it abandons the slot and drops the stage, and the release stays pending (SR3-4). A rollback point never saved as installed is not handed over: in the same boot, or after a reboot that kept the old root, it is abandoned with no fallback recorded and no adoption reverted, so a power cut mid-handover does not mark a valid release as fallen back. If the activator cannot abandon it, the point stays and the next `Tick` or `Resume` abandons it. The cost is that a box that did try the new slot before the handover was saved tries it once more; that second try is recorded, so a real fallback is then judged as one. A boot of the new root is judged like any other apply. A boot with the same ID as the handover is never judged, so a broker restart without a reboot is never taken for a fallback. Unrecorded tries are bounded (SR3-4f-1b): the save before `Install` counts one try for the exact `update.Ref` (`Unrecorded`, saved), and the save that records the handover clears the count. An `Install` that returned an error does not count. At `maxUnrecorded` (2) the attempt is abandoned and its stage dropped. `StageFailed` is not called and `FellBack` is not set, since nothing shows the release is bad. `Last` becomes `unrecorded`, and the release is refused: `Schedule` returns `ErrRefused` naming the version and manifest digest, `Tick` drops it from pending, and `Execute` does not install it. Only `Retry` admits it again. A failed `Abandon` after a failed `Install` leaves that try counted. **Drops are settled (SR3-4f-2b).** A release that leaves the applier before it is installed has its adoption retired and reverted with `StageDropped` (`WhyDropped`): `Tick`'s narrowing drop and `Execute`'s `ErrPolicyMoved` drop (A9), a `Schedule` by another adoption that supersedes it, any `Schedule` refusal of an adoption the applier does not hold (`ErrRefused` included, so no adoption is left `Staged` by a refusal; until `Retry` each new adoption of a refused release is settled at once, L3 delta on #572 option (a)), the unrecorded bound, a saved `Pending` that `New` finds after a process restart, and a not-handed abandon that `Pending` no longer names. Within one boot a not-handed abandon of a release `Pending` still names settles nothing, and the next `Tick` installs it. The cost is accepted (L3 on #572 point 3): after a power cut between the pre-Install save and the handover, the release is scheduled again only under a new adoption, once SR3-4f-2-r1 lands, and a release without attestor authority is asked about again. A retired adoption is never scheduled again: `Schedule` refuses it with `ErrRetired`. `Withdraw` (the owner's UNDO or a Recheck revert, through the pipeline) retires and drops an adoption without calling the pipeline, which reverts it itself. The drop is the backstop: if that revert fails or is cut short (STOP holds the pipeline's own, a nonce or run error, a cut before its journal), the next `Tick` settles it with `StageDropped`, a no-op once the revert ran, and an owner's revert that loses to it reports success (L3-1 and Security R1 on #605). `Withdraw` answers an error whose `Handover()` is true from the pre-Install save until `Resume` settles. Loop 3 today keeps an adopted release as proposed and does not offer it again (A1), so a dropped release waits for BOARD SR3-4f-2-r1 or a newer release. `Retired` is never pruned: one short ID per drop. | UPD-1, UPD-8, OP-4, OP-5 | If the bound needs tuning, change `maxUnrecorded`. |
| A6 | **Policy.** `Check` allows only origin `update`, executor `update`, action `meta.release` on the broker account, for the release the applier holds, while the box is free. The grants gate has no `meta.release` delegation yet: the wiring adds it, as for `meta.loops.*` (GR18), together with reserving the `update` executor name in the daemon, as #59 did for `RecallExecutor`. Origin `update` must be producible only by the applier: no owner channel, guest, loop or pipeline path may produce it (security C1 on #133). | OP-3, OP-5 | Wiring (W5b). |
| A7 | **Not wired.** `agentosd` does not build an applier yet. Wiring needs: the activator from P2-1; `InCall` from the modem; `Working` from accepted work in the journal and admission; the owner's excluded hours (a setting with texts and the local page); `Schedule` called from the pipeline's staged adoption of an upstream release, with the adoption's exact `Report.ID`, never `Short`; `Resume` at start and until it settles; `LastTalk` from the owner channel; `Retry(ref)` from the owner's retry on my Wi-Fi page for a release refused as `unrecorded` (it saves the cleared count before it takes effect, and refuses with `ErrApplying` while an apply is in flight); `Status` in STATUS, where it is the only update line while an apply is pending or in flight and takes precedence over Loop 3's line (UX R1 on #133); and `Digest` in the digest. `Status` says why an update waits (UX-133-3) and keeps a fallback until the next install. `Digest` says once that an update installed or fell back (UX-133-1, 133-2). Before wiring (potency C1 on #133): `Working` counts only the owner's work (agent work serving an owner goal); loop, replay and builder work is preemptible (RES-1) and never blocks an update. A security fix that finds no free moment within 24 hours is asked about once, paced by GR9 (`UPDATE NOW` or a time tonight), and repeated in the digest until it is installed. An ordinary release that has waited 7 days gets one digest line. Log missed free moments with their cause, so the 24 hours can be tuned. | UPD-6 | Wiring (W5b). |
| A8 | **First boot (UPD-b).** `ScheduleFirstBoot` takes a release with no adoption and no jitter, for `broker/firstboot` only (its F1, F7). With no adoption, `Resume` commits or drops the stage without calling the pipeline. A fallback is recorded by version (`FellBack`), and `ScheduleFirstBoot` refuses that version (`ErrFellBack`), so first boot never reboots into it again. `Schedule` still requires an adoption. `ErrApplying` names the refusal while a release is in flight. | UPD-3, UPD-6 | — |
| A9 | **Narrowed attestor policy (SR3-6).** A release scheduled as a security fix whose `Security()` no longer holds (the box's attestor policy changed since its check, update U16) is dropped from pending at the next `Tick`, before any intent is submitted, and also when `Stage` refuses it with `update.ErrPolicyMoved` after a change that lands between the dispatch check and the stage. Both drops settle the adoption with `StageDropped` (A5), and the release is scheduled again only under a new adoption (once SR3-4f-2-r1 lands), under the current policy: through the owner when no listed attestor vouches for it. A narrowing after the handover is A13. Ordinary releases are not held. | UPD-8, UPD-5 | Revisit if Execute's failure handling moves. |
| A10 | **Settling is durable (SR3-4).** `Resume` settles in three stores, in order: the update store (`CommitRelease`, or `DropStaged` after a fallback), the pipeline (`ConfirmStaged`, or `StageFailed`), then the applier's own state, where clearing `Applying` is the commit point. The new state is saved before it replaces the one in memory, so a failed save keeps the obligation in memory as well as on disk. Every step returns nil when it already happened for the same release and adoption, so a cut or an error at any boundary converges on a later `Resume` without installing again. The release is keyed by `update.Ref` (version, `/usr` root hash, manifest digest, saved in the rollback point as `ToManifest`), and the adoption by its exact ID, never its owner-facing short ID, which a revert frees for reuse. A rollback point saved before `ToManifest` existed takes the digest from the staged record of the same version and root; if that record is already gone, `Resume` refuses and the apply stays in flight. Until it settles, STATUS keeps the "installing" line and `Schedule` refuses with `ErrApplying`. A boot that runs neither root of the handed-over release is judged by the update store first (SR3-4f-1a). If `Installed()` already equals the exact `update.Ref`, a blessed boot of the release was being committed when the broker stopped, and a later boot came up on the previous root. That is settled as `installed_other_root`: `CommitRelease` (idempotent, it removes a leftover stage) and `ConfirmStaged`, never `DropStaged`, `StageFailed` or `FellBack`. Once committed, the adoption cannot be reverted, so this path converges where the fallback path would refuse forever. A legacy point whose `ToManifest` and staged record are both gone cannot be matched and takes the fallback path. If `Installed()` cannot be read (a torn file, a directory in its place), `Resume` returns the error and `Applying` stays set; a read error is never taken as "not installed", so it never falls back over a committed release. Drops follow the same order (SR3-4f-2b): the adoption is saved in `Retired` and `Dropped` before the pipeline is called, and leaves `Dropped` only once `StageDropped` succeeded. `Tick` (on its way out) and `Resume` call it for every ID in `Dropped`, and `StageDropped` is a no-op on an adoption already reverted, so a cut or an error converges. A drop made where no save can follow at once (`Execute`'s `ErrPolicyMoved`) is saved by the same `Tick` before the call. An ID the pipeline refuses for good (an adoption already confirmed) stays in `Dropped` and is tried at every `Tick` (LATER.md). | UPD-1, UPD-1a, OP-4, OP-5 | — |
| A11 | **New outcomes (SR3-4f-1).** `installed_other_root`: in the boot where it was settled, STATUS and the digest say "Update N is installed, but I started the previous version this time. I will start update N at my next restart. Nothing is needed from you." In any later boot, STATUS is silent and the digest says "Update N is installed." `unrecorded`: STATUS (until `Retry` or the next install) and the digest once say "I could not record update N as installed, twice, so I will not try it again on my own. You can retry it on my Wi-Fi page." Either way, `Tick` admits the next update. | UPD-1, UX-133-1, CH-12 | UX review may reword the lines. |
| A12 | **Activator after an other-root boot (P2-1, SR3-4f-1a).** A blessed entry stays the default boot until a later `Install` replaces it, so a box that came up on the previous root once (a manual pick, a firmware fallback) starts the installed release at its next restart, as the line promises. `Install` while running the previous root must treat the slot not booted as the inactive one, and must not overwrite the committed release's slot if that is the one running. This is a condition for the real activator. | UPD-1a | If P2-1 cannot hold it, the line changes and the release is installed again. |
| A13 | **Narrowing after the handover (SR3-4f-2c).** A security fix handed over in this boot whose release no longer reports `Security()` when the restart is due is not restarted into, and nor is one whose held release a process restart lost (it is never persisted, so it cannot be judged again: fail closed). Under the applier's lock: `Abandon`, `DropStaged`, then save `Applying = nil` with `Last` not handed and the adoption retired; `StageDropped` follows (A10). No fallback is recorded. An ordinary release is restarted into as before. Not covered: an unplanned reboot after `Install` boots the counted entry before any check runs, and `Resume` judges that boot like any other, so a release whose attestors were removed meanwhile can start once. | UPD-8, UPD-1 | Close it with the boot's health check (P2-1) or an abandon at shutdown, if the activator can tell an unplanned reboot. |
