# Projections and snapshots: assumptions

Built for SIM-proj (briefs/SIM.md, D-095) against SPEC OP-4 and RES-4.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| P1 | **The journal is the only source of truth.** A projection's state is a pure function of the journal records applied to it. A snapshot is a cache tagged with the sequence number it reflects; boot ignores any snapshot it cannot verify and replays from the first record, so deleting every snapshot changes nothing but boot time. | OP-4, SIM-sd (1) | None expected. |
| P2 | **Offsets are sequence numbers, not byte offsets.** The journal numbers records from 1 with no gaps, and an erase rewrite keeps every sequence number and time, so a snapshot's offset stays valid across the rewrite where a byte offset would not. | OP-4, journal A12 | If the journal is ever compacted (records dropped), snapshots taken before it must be discarded. |
| P3 | **A snapshot is checked, not trusted.** Boot uses it only if its envelope version, projection name and SHA-256 over the data match, its offset is inside the journal, and its anchor (hash of the sequence number, type, intent ID and time of the record at that offset) matches the journal's record there; otherwise it replays in full and reports why. The checks catch damage and a snapshot from another journal (a restored backup, a reset box). They do not stop someone who can write the snapshot directory from forging one; projections are untrusted views and never decide authority, a grant or a dispatch, so a forged snapshot can mislead a view but not cause an effect. | OP-4, SIM target shape (projections untrusted) | If a projection ever gates an effect, key the checksum with a vault key. |
| P4 | **One snapshot per projection (RES-4 pruning).** `Save` replaces the projection's file atomically (temporary sibling, fsync, rename, directory fsync), so the policy for old snapshots is "keep only the latest". The snapshot directory belongs on the journal's volume, inside its storage reserve. | RES-4 | A retention of more than one snapshot needs a pruning rule here. |
| P5 | **Snapshots are periodic.** A projection is snapshotted when `every` records have been applied since its last snapshot, and at once after it applies an erase. A failed save leaves the projection current and is returned to the caller; it is retried at the next due point. | RES-4, OP-4 | None expected. |
| P6 | **Erase reaches snapshots (CAP-3).** A projection must drop what it derived from an intent when it applies that intent's `erased` record; replay from empty already reads the erased records scrubbed, so a projection that keeps erased content also breaks the snapshot-plus-tail equality the tests check. After an erase the stored snapshot is replaced at once, or deleted if the replace fails, so no snapshot outlives an erase it does not reflect. Freed disk blocks and backups are outside this, as in journal A12 (SIM-shred). | CAP-3 | SIM-shred's per-subject keys would make deletion reach backups. |
| P7 | **Pull, not push.** A projector reads the journal's tail with `RecordsAfter` when its owner calls `Sync`; the engine never calls projection code, so a slow or faulty projection cannot delay or break the journal. Wiring projectors into broker boot comes with the first consumer (SIM-owner-hold). | OP-4, SIM target shape | A push hook would need the engine to isolate projection panics. |
