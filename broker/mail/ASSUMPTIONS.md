# Mail adapter (P2-6m): assumptions

| ID | Assumption | Requirements | If wrong |
|---|---|---|---|
| M1 | **Custody split.** Package `mail` (declaration, guards, executor, verifier, watcher, undo) holds no credential and opens no connection; it reaches the mailbox only through `mail.Store`. `mail/imapsmtp` implements `Store` over IMAP and SMTP, takes the credential from a `Credential` callback on every connection, keeps none, and is to be linked only into the vault process (`agentos-egress`), which serves `Store` to `agentosd` over a socket. `TestAdapterHoldsNoCredential` checks package `mail`'s imports. Plain (unencrypted) connections are refused except to loopback; login errors carry neither the secret nor the server's words. | CRED-1, CRED-7 | Wiring must not link `imapsmtp` into `agentosd`; add it to the ARC-2/custody import test when wired. |
| M2 | **Request shapes by construction.** IMAP is not HTTP, so ADP-10's host/method/path shapes do not apply. Instead `Store` has exactly nine methods (folders, list, fetch, find, flags, move, ensure, append, submit): nothing can expunge, delete or rename a folder, or touch filters, forwarding or auto-reply settings through the credential. Moves need the server's MOVE and are sent as `UID MOVE` directly (no COPY+EXPUNGE fallback, which would also expunge whatever else the owner had marked deleted). `imapsmtp.New` refuses an unknown `Security` value, plain transport to a non-loopback host, and IMAP STARTTLS. | ADP-10 | A provider without MOVE cannot be organized; add UIDPLUS `UID EXPUNGE` if one matters. |
| M3 | **Verbs.** `organize` is added to `broker/verb` as reversible, per ADP-2 (Mark, 2026-10-05). Archive, unarchive, move, label, unlabel, mark read and unread, star and unstar map to organize, each with its declared inverse (`mail.Validate`); trash and report-spam are delete-remote; reply and send are send; draft is draft. Filters, forwarding, auto-reply settings and emptying trash are not declared, so they do not exist for agents. There is no read operation: agents read mail through recall and the bus (CAP-3, CAP-4). | ADP-1, ADP-2 | — |
| M4 | **Organize guards in the gate.** A reversible verb runs without asking (grants), so the guards reach the gate through a new optional `grants.Escalator` on the account's verifier: a target that is never allowed denies; a shared target is share; hiding an alert (archive or move out of the inbox, mark an unread message read) is change-account; past the daily bound the effect is asked at its verb. It runs at authorization and at the recheck before dispatch. Organize on an account whose verifier has no Escalator is asked, never run unasked ("no guard for this account"), so the guards fail closed. The executor checks the target again. Every escalation carries a fixed-word reason the gate shows as the approval line's detail (UX-69-2): "hides an alert from bank.example", "into shared folder Team", "past today's 200", built only from the sender's domain, owner-confirmed names and the bound, never a subject or body (CH-19), and within the owner channel's 40-character detail cap. | ADP-2, OP-3, CH-12 | — |
| M5 | **Allowed targets.** Inbox, the archive, owner-confirmed folders and labels (`Config.Folders`, `Labels`, from the grant), and the broker's `AgentOS/` namespace (created on first use). Never trash, junk, `Config.Retention`, or names that read as trash, bin, deleted, junk or spam. `Config.Shared` is share. Labels are IMAP keywords (Gmail's labels appear as folders over IMAP). Every organized item gets the `AgentOS` keyword. Sources are guarded too: nothing is organized out of trash, junk, a retention folder or a trash-named folder, and organizing out of a shared folder is share. Retention policies and sharing are not discoverable over IMAP, so they come from the grant. | ADP-2 | Gmail `X-GM-LABELS` for true labels in a later route. |
| M6 | **Alerts.** A sender counts only with an aligned DMARC pass read from the **topmost** Authentication-Results header, and only when its authserv-id is the provider's (`Config.AuthServ`): a sender can add such headers, never above the provider's. The header is parsed per RFC 8601: comments are removed and quoted strings kept whole first, so a `dmarc=pass` inside either is not a result. Then the provider's security senders, the domains of services the owner holds accounts with (`AccountSenders`, from grants and vault), and owner-marked financial or identity senders are alerts. Whoever sent it, CH-19's code patterns (`owner.SecretShaped`) and `AlertPhrases` plus `Config.Phrases` mark an alert. Labelling and starring an alert run; the evidence marks them for the digest's guard hits. A record is located across the inbox, the archive and ordinary folders; copies with the same Message-ID that differ in sender, date, subject, recipients (To, Cc), threading headers (In-Reply-To, References) or text are ambiguous and refused, so a sender cannot reuse a known ID to steer which message is judged. | ADP-2, CH-19 | Pattern misses are LOOP-10 regressions. |
| M7 | **Source deletions are recall-only (pending Mark's card).** The watcher reports messages gone from every watched folder (deleted, or moved to trash or junk) through `WatchConfig.Deleted`, only after a poll that listed every folder, so an outage never reads as deletion. Until Mark decides whether a mail deleted at the source also takes back agent work, the wiring passes a deletion that removes the item from recall and the bus only. **Wiring condition:** with #59 merged, `recall.Index.Delete` runs every `OnDelete` hook, including K2b's agent reach; the wiring package needs a recall deletion that skips the agent reach for this cause (or Mark's answer) before the watcher is wired. | CAP-3 | — |
| M8 | **Bound (UX-69-1).** 200 organize effects per account per day (`DailyLimit`), counted from the journal (`Config.Authorized`, i.e. `journal.Engine.AuthorizedSince`) so a restart does not reset it; without the hook every effect is asked. Past the bound the owner is asked **once** ("past today's 200; YES allows 2000"); while that ask is open, after a NO, or with no answer, the rest are refused as held (`Escalation.Held`: the gate's reason says to try again later), until the count falls back under the bound. A YES is the journal authorizing that one asked effect (not merely a count above the bound, which owner-approved share or alert asks can also reach); it lifts the bound for the day the ask was made to `DailyCeiling` (default 2000, owner-settable); past that each effect is asked. The YES lifts only the count: target, share and alert guards still run on every effect. The open ask lives in memory, so a restart may ask once more. The day is a sliding 24 hours. Counting and reserving a place is one step under the adapter's lock (journal-authorized intents plus places reserved but not yet journaled), so concurrent intents cannot both take the last place; an intent rechecked before dispatch keeps its place. | ADP-2, CH-13 | Held effects are denied with the gate's fixed guard reason; a distinct "held" state would be a gate change. |
| M9 | **Undo and digest.** Each organize effect's evidence (`mail.Change`) holds the folder and flags before and what the agent set. `Adapter.Undo` restores an item only if it is still where the agent put it with the flags it set (and without those it removed), and reports "Restored N; M skipped (changed since)". Evidence written by `Reconcile` (`Reconciled`) holds no prior state and is skipped. The check and the restore are separate IMAP commands without CONDSTORE, so a change landing between them is overwritten; CONDSTORE `UNCHANGEDSINCE` closes that where the server offers it (later). `Summarize` and `Digest.Line` render the digest line (senders by domain, clipped to 24 characters, so the longest line fits three text segments) with `UNDO <id>` and `MORE <id>` and the 7-day lapse. **Wiring:** the owner channel parses `UNDO <id>` / `MORE <id>` / `UNDO <id> 3 7` and the digest collects a day's evidence (CH-16). | ADP-2, CH-16 | — |
| M10 | **Replies.** A reply carries exactly `record` and `body`, so an ADP-11 rule can match it. The verifier reads recipients from the source message's From, To and Cc minus the owner's addresses (Reply-To is ignored), and verifies the thread only by walking the In-Reply-To chain through messages the mailbox holds (at most 50 links): each message's sender must have been a participant of the message it answers. Every owner message in the chain, and every one `Thread` gives a composer, is read from its Sent copy; one held only elsewhere breaks the chain. The chain's start must be the owner, as its copy in the Sent folder shows (an inbox copy with the owner's From is anyone's to plant), or a contact (`Config.Contacts`) whose message has an aligned DMARC pass. Every recipient, the latest sender included, must be a participant of a vouched-for message: one in Sent, or the contact's authenticated starter; someone a third party copied in makes the thread unverified, so an ADP-11 rule asks instead of sending. A missing, ambiguous or looping link does not verify; copies sharing a Message-ID are one message only if sender, date, subject, recipients, threading headers and text match. Text is compared as read, without normalising CRLF and LF or stripping list footers, so an honest duplicate altered in transit also reads as ambiguous (fails closed). The owner's plus-addresses (`owner+tag@`) and, on Gmail, dotted variants count as the owner. The executor re-reads the thread and refuses recipients that are not exactly its participants. `Adapter.Thread` gives a composer only the thread messages whose participants include every reply recipient. The D2 commitment filter and CH-19 run in the owner channel's `QueueAutoReply`; the PA2 light-edit count is the attention optimizer's. An auto-reply reaches this executor only when the gate releases it after its undo window (grants GR11, `DueAutoReplies`), so an UNDO inside the window means nothing is ever submitted over SMTP. Scheduled send in the owner's account (ADP-11's native undo) is not available over IMAP/SMTP. | ADP-11, CH-10 | Provider API route for scheduled send. |
| M11 | **Idempotency.** An outgoing message's Message-ID is derived from the intent's attempt key, so `Reconcile` finds a send in Sent (with `AppendSent` for servers that do not save it) and a draft in Drafts. A refused or interrupted submission is unknown until reconciled, never not-applied. | OP-1, OP-2 | — |
| M12 | **Watcher.** Polling, one connection per operation. With a Gmail-style all-mail folder, only it is watched (an archived Gmail message is in no other folder); otherwise every folder but trash, junk and drafts. Each new message is published once as a private `mail` event (ref and version = Message-ID; messages without one get a hash of their location) with headers as the summary and plain text (64 KiB) as the body; the bus's recall trigger indexes it (recall K9: the bus sets the receipt time). State is UID validity and UID-to-identity hashes only, no content. The identity is the Message-ID with a digest of sender, date and the first 256 bytes of text (72 bits, as letters so recall's scrubber keeps it), so a message reusing an ID is a separate item; one without an ID is `nomid:` with a digest of its location. A listing without an inbox is an error. A known folder missing from a listing stays as it was, and the poll counts as incomplete until three polls in a row miss it. A message is reported deleted only if every folder it was last seen in was listed and read again under the same UID validity: a folder that leaves the listing or the watched set (an all-mail view losing its role), or is renumbered, never makes its messages read as deleted, at the cost of not propagating real deletions from it. After a UID validity reset the re-read is bounded by `Backfill` too. The first poll publishes at most `Backfill` (10 000) newest messages per folder, inside recall's measured 100k ceiling (R8). Fetching uses BODY.PEEK, so nothing is marked read. `Watcher.Coverage` reports indexed of seen messages for an owner line such as "Mail indexed: newest 10,000 of 48,200" (wiring, UX R6). | CAP-3, CAP-4, REV-5 | IDLE and a kept connection when latency matters. |
| M13 | **Reuse.** `github.com/emersion/go-imap` v1.2.1 (MIT) as the IMAP client and test server library, with go-message and go-sasl; `net/smtp` for submission; stdlib for parsing. The test server (`mail/mailtest`) is our own small backend on go-imap's server, because go-imap's memory backend has no special-use folders, no MOVE and no locking. | — | — |
