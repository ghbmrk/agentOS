# Mail adapter (P2-6m): assumptions

| ID | Assumption | Requirements | If wrong |
|---|---|---|---|
| M1 | **Custody split.** Package `mail` (declaration, guards, executor, verifier, watcher, undo) holds no credential and opens no connection; it reaches the mailbox only through `mail.Store`. `mail/imapsmtp` implements `Store` over IMAP and SMTP, takes the credential from a `Credential` callback on every connection, keeps none, and is to be linked only into the vault process (`agentos-egress`), which serves `Store` to `agentosd` over a socket. `TestAdapterHoldsNoCredential` checks package `mail`'s imports. Plain (unencrypted) connections are refused except to loopback; login errors carry neither the secret nor the server's words. Wired in SR3-mail-w1: `agentos-egress` holds the account and serves `Store` on `mail.sock` (broker uid only, egress K18); agentosd's side is `mail/mailsock`, whose `TestClientLinksNoCredentialOrNetworkClient` fails if it reaches `imapsmtp`, `crypto/tls`, `net/smtp`, `net/http` or `os/exec`, and `TestDialsOnlyUnix` keeps it to `net.Conn` and `net.Dialer` dialling `unix`. | CRED-1, CRED-7 | The agentosd-wide `imapsmtp` pin and the ARC-2 fence entries are SR3-mail-w2's (W2-f). |
| M2 | **Request shapes by construction.** IMAP is not HTTP, so ADP-10's host/method/path shapes do not apply. Instead `Store` has exactly nine methods (folders, list, fetch, find, flags, move, ensure, append, submit): nothing can expunge, delete or rename a folder, or touch filters, forwarding or auto-reply settings through the credential. Moves need the server's MOVE and are sent as `UID MOVE` directly (no COPY+EXPUNGE fallback, which would also expunge whatever else the owner had marked deleted). `imapsmtp.New` refuses an unknown `Security` value, plain transport to a non-loopback host, and IMAP STARTTLS. | ADP-10 | A provider without MOVE cannot be organized; add UIDPLUS `UID EXPUNGE` if one matters. |
| M3 | **Verbs.** `organize` is added to `broker/verb` as reversible, per ADP-2 (Mark, 2026-10-05). Archive, unarchive, move, label, unlabel, mark read and unread, star and unstar map to organize, each with its declared inverse (`mail.Validate`); trash and report-spam are delete-remote; reply and send are send; draft is draft. Filters, forwarding, auto-reply settings and emptying trash are not declared, so they do not exist for agents. There is no read operation: agents read mail through recall and the bus (CAP-3, CAP-4). | ADP-1, ADP-2 | — |
| M4 | **Organize guards in the gate.** A reversible verb runs without asking (grants), so the guards reach the gate through a new optional `grants.Escalator` on the account's verifier: a target that is never allowed denies; a shared target is share; hiding an alert (archive or move out of the inbox, mark an unread message read) is change-account; past the daily bound the effect is asked at its verb. It runs at authorization and at the recheck before dispatch. Organize on an account whose verifier has no Escalator is asked, never run unasked ("no guard for this account"), so the guards fail closed. The executor checks the target again. Every escalation carries a fixed-word reason the gate shows as the approval line's detail (UX-69-2): "hides an alert from bank.example", "into shared folder Team", "past 200, YES allows 2000; alert hidden", built only from the sender's domain, owner-confirmed names and the bound, never a subject or body (CH-19). It fits the owner channel's 40-character detail cap (UX-69-3): the bound clause comes first, other clauses shorten when it is present, names are clipped, and any cut is marked with ASCII "..." (the channel drops "…"). | ADP-2, OP-3, CH-12 | — |
| M5 | **Allowed targets.** Inbox, the archive, owner-confirmed folders and labels (`Config.Folders`, `Labels`, from the grant), and the broker's `AgentOS/` namespace (created on first use). Never trash, junk, `Config.Retention`, or names that read as trash, bin, deleted, junk or spam. `Config.Shared` is share. Labels are IMAP keywords (Gmail's labels appear as folders over IMAP). Every organized item gets the `AgentOS` keyword. Sources are guarded too: nothing is organized out of trash, junk, a retention folder or a trash-named folder, and organizing out of a shared folder is share. Retention policies and sharing are not discoverable over IMAP, so they come from the grant. | ADP-2 | Gmail `X-GM-LABELS` for true labels in a later route. |
| M6 | **Alerts.** A sender counts only with an aligned DMARC pass read from the **topmost** Authentication-Results header, and only when its authserv-id is the provider's (`Config.AuthServ`): a sender can add such headers, never above the provider's. The header is parsed per RFC 8601: comments are removed and quoted strings kept whole first, so a `dmarc=pass` inside either is not a result. Then the provider's security senders, the domains of services the owner holds accounts with (`AccountSenders`, from grants and vault), and owner-marked financial or identity senders are alerts. Whoever sent it, CH-19's code patterns (`owner.SecretShaped`) and `AlertPhrases` plus `Config.Phrases` mark an alert. Labelling and starring an alert run; the evidence marks them for the digest's guard hits. A record is located across the inbox, the archive and ordinary folders; copies with the same Message-ID that differ in sender, date, subject, recipients (To, Cc), threading headers (In-Reply-To, References) or text are ambiguous and refused, except that a message from the owner resolves to its single Sent copy (M10), so a sender cannot reuse a known ID to steer which message is judged. | ADP-2, CH-19 | Pattern misses are LOOP-10 regressions. |
| M7 | **Source deletions are recall-only (pending Mark's card).** The watcher reports messages gone from every watched folder (deleted, or moved to trash or junk) through `WatchConfig.Deleted`, only after a poll that listed every folder, so an outage never reads as deletion. Until Mark decides whether a mail deleted at the source also takes back agent work, the wiring passes a deletion that removes the item from recall and the bus only. **Wiring condition:** with #59 merged, `recall.Index.Delete` runs every `OnDelete` hook, including K2b's agent reach; the wiring package needs a recall deletion that skips the agent reach for this cause (or Mark's answer) before the watcher is wired. Whatever Mark answers, a source deletion reaches agent work only once the owner confirms it, never from a sync an agent can trigger (security A1 on #59, change C19). | CAP-3 | — |
| M8 | **Bound (UX-69-1).** 200 organize effects per account per day (`DailyLimit`), counted from the journal (`Config.InUse`, i.e. `journal.Engine.InUse` for this account) so neither a restart nor a queue released long after its authorization resets it (SR3-2-f1): an intent holds a place while authorized or in flight, whatever its age, and for the 24 hours after its dispatch. The window's edge is the adapter's `Now` minus 24 hours, compared with the journal's dispatch time (dispatched at or after it counts); the two clocks are assumed to be the same host clock, so skew between them moves the edge by that skew. Without the hook every effect is asked ("past 2000 today"). Places reserved in memory cover only intents placed but not yet authorized; an intent the journal counts drops its reservation. Past the bound the owner is asked **once** ("past today's 200; YES allows 2000"); while that ask is open, after a NO, or with no answer, the rest are refused as held (`Escalation.Held`: the gate's reason says to try again later), until the count falls back under the bound. A YES is the journal authorizing that one asked effect (not merely a count above the bound, which owner-approved share or alert asks can also reach); it lifts the bound for the day the ask was made to `DailyCeiling` (default 2000, owner-settable); past that each effect is asked. The YES lifts only the count: target, share and alert guards still run on every effect. The open ask lives in memory, so a restart may ask once more. The day is a sliding 24 hours. Counting and reserving a place is one step under the adapter's lock (journal-authorized intents plus places reserved but not yet journaled), so concurrent intents cannot both take the last place; an intent rechecked before dispatch keeps its place (it is counted once, by the journal). | ADP-2, CH-13 | Held effects are denied with the gate's fixed guard reason; a distinct "held" state would be a gate change. |
| M9 | **Undo and digest.** Each organize effect's evidence (`mail.Change`) holds the folder and flags before and what the agent set. `Adapter.Undo` restores an item only if it is still where the agent put it with the flags it set (and without those it removed), and reports "Restored N; M skipped (changed since)". Evidence written by `Reconcile` (`Reconciled`) holds no prior state and is skipped. The check and the restore are separate IMAP commands without CONDSTORE, so a change landing between them is overwritten; CONDSTORE `UNCHANGEDSINCE` closes that where the server offers it (later). `Summarize` and `Digest.Line` render the digest line (senders by domain, clipped to 24 characters, so the longest line fits three text segments) with `UNDO <id>` and `MORE <id>` and the 7-day lapse. **Wiring:** the owner channel parses `UNDO <id>` / `MORE <id>` / `UNDO <id> 3 7` and the digest collects a day's evidence (CH-16). | ADP-2, CH-16 | — |
| M10 | **Replies.** A reply carries exactly `record` and `body`, so an ADP-11 rule can match it. The verifier reads recipients from the source message's From, To and Cc minus the owner's addresses (Reply-To is ignored), and verifies the thread only by walking the In-Reply-To chain through messages the mailbox holds (at most 50 links): each message's sender must have been a participant of the message it answers. A message from the owner is the owner's only as the Sent folder holds it (`locate`, so the record, the chain and `Thread` resolve alike): exactly one copy From the owner in the folder with the Sent role, whose fields are used; other copies From the owner (a list footer, a gateway disclaimer, CRLF for LF) are ignored in its favour; a same-ID copy From anyone else is ambiguous and refused; and an owner-From message with no Sent copy is refused (`ErrNotSent`). This is a reply's identity only. An organize, trash or spam effect acts on, judges (alerts, targets) and shows the owner the copy it moves (`place`): the copy in the named folder, else the copies outside Sent (differing ones are ambiguous, never picked silently); Sent is acted on only when named. It never needs a Sent copy, so spam spoofing the owner can be archived or reported. Any same-ID copy the search sees that is an alert makes the effect an alert's, so a benign twin cannot launder one. Archiving or moving a Sent copy through an explicit folder ends that message's role as a thread anchor (its replies no longer verify). The chain's start must be the owner, as its copy in the Sent folder shows (an inbox copy with the owner's From is anyone's to plant), or a contact (`Config.Contacts`) whose message has an aligned DMARC pass. Every recipient, the latest sender included, must be a participant of a vouched-for message: one in Sent, or the contact's authenticated starter; someone a third party copied in makes the thread unverified, so an ADP-11 rule asks instead of sending. A missing, ambiguous or looping link does not verify; copies sharing a Message-ID are one message only if sender, date, subject, recipients, threading headers and text match. Text is compared as read, without normalising CRLF and LF or stripping list footers; for non-owner messages an honest duplicate altered in transit therefore reads as ambiguous (fails closed). The owner's plus-addresses (`owner+tag@`) and, on Gmail, dotted variants count as the owner. The executor re-reads the thread and refuses recipients that are not exactly its participants. `Adapter.Thread` gives a composer only the thread messages whose participants include every reply recipient. The D2 commitment filter and CH-19 run in the owner channel's `QueueAutoReply`; the PA2 light-edit count is the attention optimizer's. An auto-reply reaches this executor only when the gate releases it after its undo window (grants GR11, `DueAutoReplies`), so an UNDO inside the window means nothing is ever submitted over SMTP. Scheduled send in the owner's account (ADP-11's native undo) is not available over IMAP/SMTP. | ADP-11, CH-10 | Provider API route for scheduled send. |
| M11 | **Idempotency.** An outgoing message's Message-ID is derived from the intent's attempt key, so `Reconcile` finds a send in Sent (with `AppendSent` for servers that do not save it) and a draft in Drafts. A refused or interrupted submission is unknown until reconciled, never not-applied. | OP-1, OP-2 | — |
| M12 | **Watcher.** Polling, one connection per operation. With a Gmail-style all-mail folder, only it is watched (an archived Gmail message is in no other folder); otherwise every folder but trash, junk and drafts. Each new message is published once as a private `mail` event (ref and version = Message-ID; messages without one get a hash of their location) with headers as the summary and plain text (64 KiB) as the body; the bus's recall trigger indexes it (recall K9: the bus sets the receipt time). State is UID validity and UID-to-identity hashes only, no content. The identity is the Message-ID with a digest of sender, date and the first 256 bytes of text (72 bits, as letters so recall's scrubber keeps it), so a message reusing an ID is a separate item; one without an ID is `nomid:` with a digest of its location. A listing without an inbox is an error. A known folder missing from a listing stays as it was, and the poll counts as incomplete until three polls in a row miss it. A message is reported deleted only if every folder it was last seen in was listed and read again under the same UID validity: a folder that leaves the listing or the watched set (an all-mail view losing its role), or is renumbered, never makes its messages read as deleted, at the cost of not propagating real deletions from it. After a UID validity reset the re-read is bounded by `Backfill` too. The first poll publishes at most `Backfill` (10 000) newest messages per folder, inside recall's measured 100k ceiling (R8). Fetching uses BODY.PEEK, so nothing is marked read. `Watcher.Coverage` reports indexed of seen messages for an owner line such as "Mail indexed: newest 10,000 of 48,200" (wiring, UX R6). | CAP-3, CAP-4, REV-5 | IDLE and a kept connection when latency matters. |
| M13 | **Reuse.** `github.com/emersion/go-imap` v1.2.1 (MIT) as the IMAP client and test server library, with go-message and go-sasl; `net/smtp` for submission; stdlib for parsing. The test server (`mail/mailtest`) is our own small backend on go-imap's server, because go-imap's memory backend has no special-use folders, no MOVE and no locking. | — | — |
| M14 | **Evidence delivery (CH-20).** `mail.deliver` (verb share) mails the owner a private agent reply, or a notice from the box, as plain text with no attachments and the fixed subject "Your agent's reply" (security C4 on #148). It takes only a body and its author (`from`): an agent's reply opens with "Written by your AgentOS agent. Links in it were not checked by the box."; both end with a signature line saying replies are not read. It runs only from the broker's evidence origin, and its one recipient must be one of the account's own addresses (`Owns`), re-checked at execution, so it never reaches a third party; the grants gate allows it only to the owner's set destination (grants GR24). An account marked `Box` (the box's own mailbox, ADP-13) owns no destination (security C2). Aliases come from the provider's verified send-as list, and `Owns` matches the address and aliases exactly: unlike `isSelf`, no +tag or Gmail-dot variant counts. `mail.send` to the owner's own address stays refused. `Config.Redact`, set by the vault process to its redactor, rewrites the body before it is sent (CRED-7). It reconciles from Sent like any outgoing message. | CH-20, CRED-7, OP-1 | — |
| M15 | **Message identity (SR3-5).** A message is named by `mail.Ref` (folder, UIDVALIDITY, UID), never a bare UID: `Message.Validity` comes from the SELECT that listed it, and `Store.Fetch`, `SetFlags` and `Move` take it and compare it with the validity of their own SELECT before any command, returning `ErrValidity` (validity 0 is refused too). The check is per epoch, not per mailbox state: deliveries and expunges under an unchanged validity do not refuse, and the same-message flag race stays M9's. On `ErrValidity` the executor records `NotApplied` when nothing changed yet and `Unknown` (settled by `Reconcile`) when flags were already set; it never retries by the old UID, and a new attempt passes the gate again, which reruns the guards and re-resolves by Message-ID. Evidence (`mail.Change`) records the validity and UID it acted on; undo of a flag-only change recorded under another identity is skipped, and the restore itself is validity-checked. The watcher fetches under the validity it listed; a reset in between fails that poll, and the next poll re-reads the folder (M12). SetFlags and Move stay two checked sessions, so M2's nine methods are unchanged. | ADP-2, OP-3, REV-2, OP-2, OP-4 | A reset between SetFlags and Move leaves flags set on the old message; Reconcile reports it Unknown. If that matters, combine both in one session (later). |
| M16 | **Pin (SR3-5-f1a/b).** `Escalate` on an organize intent records a pin in memory: the `Ref` it planned on, the destination, and whether it escalated hiding an alert. Every `Escalate` (authorize, each dispatch recheck, including a concurrent recheck the gate refuses) adds its judgement; none overwrites another, and a recheck that cannot plan adds a poisoned judgement (a zero `Ref`) instead of removing any, so only `Execute`'s consume removes a judgement made since the last one, apart from the 24-hour expiry below. `Execute` takes (consumes) all of them whatever the result, re-plans, and returns `NotApplied` ("changed since approval") when there is none, any two disagree on `Ref` or alert bit, the planned message's `Ref` differs from the agreed one, or the plan hides an alert they did not escalate; nothing is changed. An `Unknown` attempt keeps only the agreed pin. When an attempt ends `Unknown` its pin is kept per attempt for `Reconcile`, which judges the pinned `Ref` (the message must be at the destination and gone from the pinned `Ref`) and returns `Unknown` for a hidden alert with no alert pin. Pins live in memory, so after a restart `Reconcile` of a hidden alert is `Unknown` and a queued attempt passes the recheck again; judgements older than 24 hours are dropped only under M18. Organize, trash and spam (`verb.DeleteRemote`, SR3-5-f2a) are pinned; an `Unknown` trash or spam keeps no pin, and its `Reconcile` judges by Message-ID (its source can never be Trash or Junk). | ADP-2, ADP-9, OP-2, OP-3, OP-4 | A persisted pin would need a journal field (later). |
| M17 | **Undo needs a validity (SR3-5-f1c).** A flag-only change whose evidence carries UID validity 0 names no message, so `Undo` skips it rather than restoring flags on whichever same-ID message is in the folder now. A move is not held to this: its undo finds the message by Message-ID in the destination the agent moved it to, a folder the broker chose and the guards allowed, and restores only that message's folder and the flags the agent set; a same-ID message elsewhere is never touched. | OP-3, OP-4, ADP-2 | A same-ID message placed in the destination after the move could be moved back; that needs a second message with the ID in the broker-chosen folder. |
| M18 | **Expiry spares intents in use (SR3-5-f2b).** When `Escalate` pins and some judgement or kept pin is older than 24 hours, the adapter asks the journal's `InUse` hook (every pinned action, this account, since 24 hours ago) which intents are still live: authorized, in flight, outcome unknown, or succeeded within the day. Those keep all their judgements, so an attempt in flight, or a queue released a day after its authorization, is always checked against every judgement made since the last `Execute`. Only old judgements of the other intents (denied, not applied, long settled) are dropped. A nil hook means no intent is known to be settled, so nothing expires; memory then grows only in a configuration without the journal, where every organize is asked anyway. This was chosen over expiring into a poisoned judgement, which would refuse the first attempt of every queue released more than a day after authorization and never be removed. `setPin` calls the hook under the adapter's lock, as `reserve` already does; the journal never calls the adapter while holding its own lock. agentosd wires the hook to `Engine.InUse` for the adapter's own account, only once the engine exists (SR3-mail-w2, agentosd MW1). | ADP-2, OP-2, OP-3 | A retry of a `NotApplied` intent is not listed between its recheck and its commit. If that commit stalled for more than a day (goroutine starvation, not a lock wait), a later refused recheck could expire the retry's judgement and stand alone. |
