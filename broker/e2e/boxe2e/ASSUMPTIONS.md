# In-image end-to-end run: assumptions

Built for G1-e2e (#1688). `box-e2e` drives first-boot setup inside the booted image as an owner's
phone would; `image/ci_boot.sh` injects it on a fourth QEMU boot. Each row is a reading a reviewer
may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| E1 | The run never changes the image. Its two units (`agentos-e2e-seal.service`, `agentos-e2e.service`) and two drop-ins (`image/e2e/`) arrive as SMBIOS type 11 credentials (`systemd.extra-unit.*`, `systemd.unit-dropin.*`), which systemd imports only in a VM, and the driver on a read-only 9p share. A shipped box has neither, so the run adds no path into a production box. | HW-1, HW-5 | If systemd ever honoured SMBIOS credentials on bare metal, gate the image on `ImportCredential=` instead. |
| E2 | QEMU has no radio, so a veth pair stands in for the access point: the box end is named `wlan0` at 10.42.0.1/24, the phone end sits in its own network namespace at 10.42.0.23, and `wlan0` joins `agentos_inbound`'s `exempt` set as `ap-exempt` would add it. `agentos-ap` is stopped. The setup page's own interface binding, address checks and same-origin checks are exercised; hostapd, the radio and DHCP on the AP are not (M6 Ultra session). | ONB-1, HW-1 | Use mac80211_hwsim if the kernel ships it, to cover hostapd too. |
| E3 | The claim is sealed before the setup page first starts, as the seller does before the box ships: `agentos-e2e-seal.service` runs `box-e2e seal` after tmpfiles and before localui, which calls `claim.Seal` at `claim.StatePath`; `agentos-localui-claim.service` then moves it into localui's state before localui's first start. The code reaches the driver through root-only tmpfs (`/run/agentos-e2e/claim-code`, mode 0600), which the driver deletes on read. The seal was not ordered before agentosd or egress: the 9p mount delayed them past the first boot's `drive-id assign`, after which their `drive-id check` failed for the rest of that boot (#1716). Since #1701 the vault process is ordered after the seal (E10), which is safe only because `drive-id` now accepts this boot's own assign record. The claim's vault restart (`agentos-egress-setup.path`) runs after assign in every run, and on e8add17 it failed the same way, blocking sms-pair; that restart is the run's check of the #1716 fix. The run found the hand-over broken in the product (348e598: seal done 2.6 ms before the page started, file never moved, even after a restart): as a `+` ExecStartPre of the page, `localui-claim` ran under the page's `TemporaryFileSystem=/var/lib/agentos:ro`, which systemd 257 applies to `+` commands too (src/core/exec-invoke.c gates ProtectSystem= and the like on sandboxing, not TemporaryFileSystem=). It is now a root oneshot unit ordered before the page, and the claim step has no workaround: a broken hand-over fails it. | ONB-3 | If the seller's sealing step moves (for example into the image build), move the seal unit with it. |
| E4 | The modem is the AT simulator (`modem/atsim`, a SIMCom SIM7600G-H profile) behind a pseudo-terminal. A fake sysfs tree under `/run/agentos-e2e-sysroot` (outside the seal unit's root-only `/run/agentos-e2e`, which the bridge's user cannot traverse: there it found no modem) gives discovery its vendor and interface files, and its `ttyUSB2` node links to the pty slave, owned by `agentos-modem` as the udev rule would make it. A drop-in adds `-sys-root` and `DeviceAllow=char-pts rw`; a test keeps its command line equal to the shipped unit's plus `-sys-root`. Real USB enumeration, the udev rule and the radio are not exercised (M6 Ultra session). | CH-1, CH-12, HW-2 | If discovery reads more of sysfs, extend `buildSysroot`. |
| E5 | The phone's code generator is computed from the enrolment link's seed with the broker's own `owner.TOTP`; the card's prompt is answered from the saved sheet. Both prove the server's round trip, not an independent RFC 6238 or card implementation (those have their own package tests). | CH-10, ONB-3 | — |
| E6 | Steps run in the box's setup order (claim, network if offline, number and pairing, codes, card, recovery, this PC, AI), not the order #1688 lists them. After the first failure later steps print BLOCKED and do not run; a step on the expected-failure list prints XFAIL with its issue, and a listed step that passes fails the run (XPASS) so the list shrinks. | ONB-3 | — |
| E7 | One step is on the expected-failure list; `host` left it when #1221 served recording host trust, and `phone-control` when #1714 drove it (E9). `guest-task` (#1701): G1's model route is the ChatGPT-plan device-code sign-in through the Codex worker, and CI has no plan account, so the plan's provider is a stub behind the worker (E10); the API-key path is not used. It reads XFAIL until step 7 offers the sign-in (#1264), the route is qualified (#809, #1877) and the box ships the Codex worker image (#1721): step 7's sign-in sits behind the same gate and image as the task (E11, E12). `phone-control` runs after `guest-task` because agentosd answers texts only once setup has finished, which needs step 7's AI connection; until #1701 lands it prints BLOCKED, which is not a failure, and a run that reaches it and fails reads FAIL. | ONB-3 | Remove `guest-task` when #1701 lands. |
| E8 | Output is one console line per step. It never carries the claim code, card words, recovery key, vault passphrase, code-generator seed or a page body: a failure names the step, status codes, the location, the page's step heading and its sanitized error line. A claim failure also quotes the last localui and claim-move log lines, cut short, with the code replaced by `[redacted]`. | ONB-3 | — |
| E9 | `phone-control` proves the owner channel after setup with STATUS, which changes nothing. It first requires `GET /setup` to answer 303 to `/status`, so an unfinished setup fails as `setup not finished` and not as the owner channel; the GET also lets the page finish setup. The paired phone then texts `HELP`, which needs no code, until it gets `Commands:`: agentosd takes the modem from setup's line only after setup finishes, and the hand-over can lose the owner's texts because after setup the bridge has no `OWNER_NUMBER` (BOARD `P2-2w c4c r1`, bridge B9), so HELP repeats for up to three minutes and a timeout names the attempts. Only then does it text one `STATUS` with a code from a 30-second window the driver has not used (the box takes each window once and the enrolment used one), so the code is never read late, when it would be a wrong code that counts toward CH-11's lockout. The verdict reads the carrier's log in order from the step's start: the first reply to STATUS must be `Unlocked until` and the next `Running.` or `Stopped.`, so the session was locked and the fresh code unlocked it (CH-14); a status reply first, `You are already unlocked`, `Locked.` or `Wrong code.` fails. After the status reply an unpaired synthetic number (`+15550000102`) texts `STATUS` with a fresh code, and the paired phone texts `HELP` as a barrier. Texts are handled in arrival order but replies are not sent in that order: `STATUS` and `HELP` are run routes, each answered from its own goroutine, so a reply drawn by the stranger's text can land after the barrier's. Once the barrier's `Commands:` arrives the step keeps reading the log for a 15-second settle time, and that window is what catches a late reply to the stranger's text. Any reply to the paired phone after the stranger's text other than the barrier's `Commands:` fails, as does any text to the unpaired number (CH-1, CH-3). Failures name reply kinds and counts, never a text. `TestPhoneControlAgainstTheOwnerChannel` runs the step against a real owner channel on the carrier simulator, with mutants. | CH-1, CH-3, CH-11, CH-14 | If STATUS stops being the safe read-only command, pick another that runs only once unlocked. When `P2-2w c4c r1` is fixed, the HELP retries can go. |
| E10 | **The run proves an e2e build of the vault process, not the shipped one (#1701).** CI has no plan account, so the Codex plan's provider is a stub (`codexstub`) that the driver serves on `/run/agentos-e2e-stub/codex.sock` (0600, owned by `agentos-egress`; outside the root-only `/run/agentos-e2e`). Exactly this differs from a shipped box: (1) `image.yml` builds `cmd/agentos-egress` a second time with `-tags agentos_e2e` onto the 9p share; (2) that build links `upstream_e2e.go`, whose `planUpstream` sends https requests for `egress.Codex()`'s hosts (chatgpt.com, auth.openai.com, matched by host name whatever the port; any other scheme for them fails) to the socket and every other request to the shipped `egress.DefaultTransport`; for those two hosts it therefore skips what the shipped transport does: the netguard dial with its private-address refusal, TLS verified against the system roots, and HTTP/2 (the socket is plain HTTP/1.1); the shipped build links `upstream.go`, which returns nil, so `serveWorkerRoutes` keeps the shipped transport, and a test (`TestShippedBuildLinksNoE2EStub`) keeps `codexstub` out of the untagged binary; (3) the drop-in `image/e2e/agentos-egress.conf` bind-mounts the tagged binary read-only over `/usr/lib/agentos/agentos-egress` and orders the unit after `agentos-e2e-seal.service`, whose 9p mount it needs; command line, user and sandbox stay the shipped unit's (`TestVaultDropInSwapsOnlyTheBinary`). `egress-setup` (the unit's `+` ExecStartPre and the `agentos-egress-setup.path` restart) may run `init -setup` with the shipped binary rather than the bound one; its vault code is the same in both builds. Everything else the route does (allowlist, placeholder swap, vault writes, redirect rewrite, refusals) is the shipped code; the stub refuses a placeholder, an undeclared path, an unrewritten redirect and a run call whose `Chatgpt-Account-Id` is not the account in its id_token, as the provider would. It is not the provider in every respect: it does not check `client_id` beyond its presence, and its response stream sends `response.created`, one `response.output_item.done` and `response.completed` but no `response.output_text.delta` events, so a CLI build that renders only deltas would pass here and fail live (S8-live). The driver's harness checks before any step that the running vault process's `/proc/<pid>/exe` carries the tag (`checkVaultBuild`), so a run that silently fell back to the shipped binary fails rather than reaching the internet. There is no runtime redirect hook in the shipped binary. Ordering after the seal delays egress and agentosd past the first boot's `drive-id assign` (E3, #1716); `drive-id` accepts this boot's own record, and a regression would show as FAIL at the first vault step. Every token the stub issues is a random synthetic canary (`agentos-e2e-canary-`). Sign-in at step 7 is driven against #1264's expected page (E11); the task after it runs through `provider_run` (E12). | HW-10, CRED-5, CRED-1 | If a box ever needs a test transport at runtime, it is a defect; keep the swap a build tag on the e2e image only. |
| E11 | **Step 7 is driven against the page #1264 (c4e2) is expected to serve, not the page main serves today.** agentosd answers `StartDeviceCode` with not-served and lists no device-code provider, and serving it needs #1864's provider worker (`codex login --device-auth` runs in a worker that #1864 adds to agentosd), so `guest-task` stays XFAIL. The driver waits up to two minutes for step 7 to open (its `One is enough` line, which the page prints once the first-boot update has finished, whatever providers it lists); if it never opens, or `GET /setup` keeps failing, the step reads FAIL as `step 7 did not open`, since that is a product failure (ONB-4) and not the missing sign-in. If step 7 opens but offers no `codex` sign-in, the step fails with the not-driven text naming #1264 and the gate (#809, #1877) and image (#1721) the offer sits behind, which reads XFAIL. If the post shows no sign-in link, localui's page says only `Could not start sign-in with that provider` and vm does not log the unknown image, so the driver reads agentosd's command line (`systemctl show -p ExecStart`): with no `-image codex=` it reads XFAIL naming #1721, with one it is FAIL. That FAIL quotes agentosd's `setup:` and `provagent:` journal lines (where `StartSignIn` logs the step that refused, #1701), the last six, and the last eight 160-byte pieces of `/var/lib/agentos/runsc/exec.log`, where a worker's failed `runsc run` leaves runsc's message (vm V41), cut short, with the stub's tokens and canary cut out (E8) before the pieces are cut so none splits a token. Once offered it ticks private content, posts `/setup/ai-device`, requires the link to be exactly `https://auth.openai.com/codex/device` (`egress.Codex()`'s auth host and device page) with the words `This code is from OpenAI`, approves the shown code at the stub, reloads until `/setup` redirects to `/status`, and fails if the link is elsewhere (naming the host the page showed), the stub refused a call (naming how many), the stub never saw the code exchange, or any page showed a canary token (naming the request: the page after the post, a `/setup` reload or `/status`); the task after it is E12's. The CRED-5c consent field is not posted: its name is not decided, so c4e2 adds it to the driver's form. The parsers are pinned to localui's template (`TestDeviceOfferAndLinkMatchThePage`) and the sequence to a fake box playing the vault against the stub (`TestGuestTaskSignsInToThePlan`). | CRED-5, HW-10, ONB-3 | When c4e2 lands, run the image once before removing `guest-task` from the list; a wording or consent-field difference shows as FAIL there. |
| E12 | **The task is two `provider_run` calls made as the agent machine's guest makes it (#1701).** After step 7 the driver waits up to three minutes for the agent machine's guest-plane socket (`/run/agentos/guests/agent/broker.sock`: agentosd's `-sockets` directory, `guests/`, the `-agent-machine` id) and speaks its MCP (JSON-RPC 2.0 over `POST /mcp`) as root on the box, not from inside the guest VM, so it proves agentosd's tool, worker and route but not the guest's MCP bridge or its vsock path. It sends `initialize`, `tools/list`, then `provider_run` twice with the Codex provider, a synthetic brief and task class `code`. provagent admits one run without a usage reading per `MaxAge` (10 minutes), so the second run passes only if egress's `PlanUsage` reading from the first landed; a second run refused `pool-at-reserve` is FAIL naming the reading. Outcomes: no socket in time is FAIL with agentosd's agent-machine journal lines, cut short and with issued tokens cut out; no `provider_run` in the list reads XFAIL naming #1721 (the box ships no Codex worker image and agentosd no `-worker-image`); the closed refusal `provider_run: unqualified:` reads XFAIL naming #809 and #1877 (the qualification record and the image's pinned version); every other refusal, an RPC error or an unreadable reply is FAIL quoting the guest-facing text cut to one line, with the stub's tokens and canaries cut out of any RPC or dial error; an answer passes only when the whole raw result (every item, key and string, before any parsing) carries none of the tokens the stub ever issued, every id_token included (a refresh does not drop the earlier ones, and each id_token's signature carries the canary), and no canary but the answer's, it contains `codexstub.Answer`, the stub counted a new `responses` call and refused none during the task. The stub sends the plan's quota headers (`X-Codex-{Primary,Secondary}-{Used-Percent,Window-Minutes,Reset-At}`) on its model endpoints with fixed values (12.5% of 300 minutes, 4% of a week), which egress's `PlanUsage` reads (`TestRunCallsReportThePlanQuota`); live values and their exhausted readings are S8-live's. The sequence is pinned to a fake guest plane (`TestGuestTaskRunsOnTheCodexPlan`). | HW-10, CRED-5 | When #1721, #809 and #1877 land, run the image once; a PASS then reads XPASS and `guest-task` leaves the list. If the agent machine's id or socket layout changes, change `agentSock`. |
