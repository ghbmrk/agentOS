# In-image end-to-end run: assumptions

Built for G1-e2e (#1688). `box-e2e` drives first-boot setup inside the booted image as an owner's
phone would; `image/ci_boot.sh` injects it on a fourth QEMU boot. Each row is a reading a reviewer
may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| E1 | The run never changes the image. Its two units (`agentos-e2e-seal.service`, `agentos-e2e.service`) and two drop-ins (`image/e2e/`) arrive as SMBIOS type 11 credentials (`systemd.extra-unit.*`, `systemd.unit-dropin.*`), which systemd imports only in a VM, and the driver on a read-only 9p share. A shipped box has neither, so the run adds no path into a production box. | HW-1, HW-5 | If systemd ever honoured SMBIOS credentials on bare metal, gate the image on `ImportCredential=` instead. |
| E2 | QEMU has no radio, so a veth pair stands in for the access point: the box end is named `wlan0` at 10.42.0.1/24, the phone end sits in its own network namespace at 10.42.0.23, and `wlan0` joins `agentos_inbound`'s `exempt` set as `ap-exempt` would add it. `agentos-ap` is stopped. The setup page's own interface binding, address checks and same-origin checks are exercised; hostapd, the radio and DHCP on the AP are not (M6 Ultra session). | ONB-1, HW-1 | Use mac80211_hwsim if the kernel ships it, to cover hostapd too. |
| E3 | The claim is sealed before the setup page first starts, as the seller does before the box ships: `agentos-e2e-seal.service` runs `box-e2e seal` after tmpfiles and before localui, which calls `claim.Seal` at `claim.StatePath`; `agentos-localui-claim.service` then moves it into localui's state before localui's first start. The code reaches the driver through root-only tmpfs (`/run/agentos-e2e/claim-code`, mode 0600), which the driver deletes on read. The seal was not ordered before agentosd or egress: the 9p mount delayed them past the first boot's `drive-id assign`, after which their `drive-id check` failed for the rest of that boot (#1716). Since #1701 the vault process is ordered after the seal (E10), which is safe only because `drive-id` now accepts this boot's own assign record. The claim's vault restart (`agentos-egress-setup.path`) runs after assign in every run, and on e8add17 it failed the same way, blocking sms-pair; `drive-id` now accepts this boot's own assign record, so that restart is the run's check of the #1716 fix. The run found the hand-over broken in the product (348e598: seal done 2.6 ms before the page started, file never moved, even after a restart): as a `+` ExecStartPre of the page, `localui-claim` ran under the page's `TemporaryFileSystem=/var/lib/agentos:ro`, which systemd 257 applies to `+` commands too (src/core/exec-invoke.c gates ProtectSystem= and the like on sandboxing, not TemporaryFileSystem=). It is now a root oneshot unit ordered before the page, and the claim step has no workaround: a broken hand-over fails it. | ONB-3 | If the seller's sealing step moves (for example into the image build), move the seal unit with it. |
| E4 | The modem is the AT simulator (`modem/atsim`, a SIMCom SIM7600G-H profile) behind a pseudo-terminal. A fake sysfs tree under `/run/agentos-e2e-sysroot` (outside the seal unit's root-only `/run/agentos-e2e`, which the bridge's user cannot traverse: there it found no modem) gives discovery its vendor and interface files, and its `ttyUSB2` node links to the pty slave, owned by `agentos-modem` as the udev rule would make it. A drop-in adds `-sys-root` and `DeviceAllow=char-pts rw`; a test keeps its command line equal to the shipped unit's plus `-sys-root`. Real USB enumeration, the udev rule and the radio are not exercised (M6 Ultra session). | CH-1, CH-12, HW-2 | If discovery reads more of sysfs, extend `buildSysroot`. |
| E5 | The phone's code generator is computed from the enrolment link's seed with the broker's own `owner.TOTP`; the card's prompt is answered from the saved sheet. Both prove the server's round trip, not an independent RFC 6238 or card implementation (those have their own package tests). | CH-10, ONB-3 | — |
| E6 | Steps run in the box's setup order (claim, network if offline, number and pairing, codes, card, recovery, this PC, AI), not the order #1688 lists them. After the first failure later steps print BLOCKED and do not run; a step on the expected-failure list prints XFAIL with its issue, and a listed step that passes fails the run (XPASS) so the list shrinks. | ONB-3 | — |
| E7 | One step is on the expected-failure list; `host` left it when #1221 served recording host trust, and `phone-control` when #1714 drove it (E9). `guest-task` (#1701): G1's model route is the ChatGPT-plan device-code sign-in through the Codex worker, and CI has no plan account, so it waits on a stub behind the worker; the API-key path is not used. `phone-control` runs after `guest-task` because agentosd answers texts only once setup has finished, which needs step 7's AI connection; until #1701 lands it prints BLOCKED, which is not a failure, and a run that reaches it and fails reads FAIL. | ONB-3 | Remove `guest-task` when #1701 lands. |
| E8 | Output is one console line per step. It never carries the claim code, card words, recovery key, vault passphrase, code-generator seed or a page body: a failure names the step, status codes, the location, the page's step heading and its sanitized error line. A claim failure also quotes the last localui and claim-move log lines, cut short, with the code replaced by `[redacted]`. | ONB-3 | — |
| E9 | `phone-control` proves the owner channel after setup with STATUS, which changes nothing. An unpaired synthetic number (`+15550000102`) texts `STATUS` first; then the paired phone texts `STATUS` with a code from a 30-second window the driver has not used (the box takes each window once and the enrolment used one), which unlocks the session and runs STATUS (CH-14). The verdict reads the carrier's log from the step's start: a text from the box to the paired number starting `Running.` or `Stopped.` passes, any text from the box to the unpaired number fails, and a `Locked.` or `Wrong code.` reply fails at once. agentosd takes over the modem from setup only after setup finishes, so an unanswered attempt repeats with a new window for up to three minutes; a 15-second quiet spell after the reply catches a late text to the stranger, whose text was read first. Failures name reply kinds and counts, never a text. | CH-1, CH-3, CH-11, CH-14 | If STATUS stops being the safe read-only command, use HELP (`Commands:`), which needs no code. |
| E10 | **The run proves an e2e build of the vault process, not the shipped one (#1701).** CI has no plan account, so the Codex plan's provider is a stub (`codexstub`) that the driver serves on `/run/agentos-e2e-stub/codex.sock` (0600, owned by `agentos-egress`; outside the root-only `/run/agentos-e2e`). Exactly this differs from a shipped box: (1) `image.yml` builds `cmd/agentos-egress` a second time with `-tags agentos_e2e` onto the 9p share; (2) that build links `upstream_e2e.go`, whose `planUpstream` sends https requests for `egress.Codex()`'s hosts (chatgpt.com, auth.openai.com) to the socket and every other request to the shipped `egress.DefaultTransport`; the shipped build links `upstream.go`, which returns nil, so `serveWorkerRoutes` keeps the shipped transport, and a test (`TestShippedBuildLinksNoE2EStub`) keeps `codexstub` out of the untagged binary; (3) the drop-in `image/e2e/agentos-egress.conf` bind-mounts the tagged binary read-only over `/usr/lib/agentos/agentos-egress` and orders the unit after `agentos-e2e-seal.service`, whose 9p mount it needs; command line, user and sandbox stay the shipped unit's (`TestVaultDropInSwapsOnlyTheBinary`). Everything else the route does (allowlist, placeholder swap, vault writes, redirect rewrite, refusals) is the shipped code; the stub refuses a placeholder, an undeclared path and an unrewritten redirect, as the provider would. The driver's harness checks before any step that the running vault process's `/proc/<pid>/exe` carries the tag (`checkVaultBuild`), so a run that silently fell back to the shipped binary fails rather than reaching the internet. There is no runtime redirect hook in the shipped binary. Ordering after the seal delays egress and agentosd past the first boot's `drive-id assign` (E3, #1716); `drive-id` accepts this boot's own record, and a regression would show as FAIL at the first vault step. Every token the stub issues is a random synthetic canary (`agentos-e2e-canary-`). The stub is served but no step drives it yet: sign-in at step 7 and the guest task wait for #1264 c4e2 and #1314. | HW-10, CRED-5, CRED-1 | If a box ever needs a test transport at runtime, it is a defect; keep the swap a build tag on the e2e image only. |
