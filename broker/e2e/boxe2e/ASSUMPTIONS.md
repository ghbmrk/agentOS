# In-image end-to-end run: assumptions

Built for G1-e2e (#1688). `box-e2e` drives first-boot setup inside the booted image as an owner's
phone would; `image/ci_boot.sh` injects it on a fourth QEMU boot. Each row is a reading a reviewer
may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| E1 | The run never changes the image. Its two units (`agentos-e2e-seal.service`, `agentos-e2e.service`) and two drop-ins (`image/e2e/`) arrive as SMBIOS type 11 credentials (`systemd.extra-unit.*`, `systemd.unit-dropin.*`), which systemd imports only in a VM, and the driver on a read-only 9p share. A shipped box has neither, so the run adds no path into a production box. | HW-1, HW-5 | If systemd ever honoured SMBIOS credentials on bare metal, gate the image on `ImportCredential=` instead. |
| E2 | QEMU has no radio, so a veth pair stands in for the access point: the box end is named `wlan0` at 10.42.0.1/24, the phone end sits in its own network namespace at 10.42.0.23, and `wlan0` joins `agentos_inbound`'s `exempt` set as `ap-exempt` would add it. `agentos-ap` is stopped. The setup page's own interface binding, address checks and same-origin checks are exercised; hostapd, the radio and DHCP on the AP are not (M6 Ultra session). | ONB-1, HW-1 | Use mac80211_hwsim if the kernel ships it, to cover hostapd too. |
| E3 | The claim is sealed before the setup page first starts, as the seller does before the box ships: `agentos-e2e-seal.service` runs `box-e2e seal` after tmpfiles and before localui, which calls `claim.Seal` at `claim.StatePath`; `agentos-localui-claim.service` then moves it into localui's state before localui's first start. The code reaches the driver through root-only tmpfs (`/run/agentos-e2e/claim-code`, mode 0600), which the driver deletes on read. The seal is not ordered before agentosd or egress: the 9p mount would delay them past the first boot's `drive-id assign`, after which their `drive-id check` failed for the rest of that boot (#1716). The claim's vault restart (`agentos-egress-setup.path`) runs after assign in every run, and on e8add17 it failed the same way, blocking sms-pair; `drive-id` now accepts this boot's own assign record, so that restart is the run's check of the #1716 fix. The run found the hand-over broken in the product (348e598: seal done 2.6 ms before the page started, file never moved, even after a restart): as a `+` ExecStartPre of the page, `localui-claim` ran under the page's `TemporaryFileSystem=/var/lib/agentos:ro`, which systemd 257 applies to `+` commands too (src/core/exec-invoke.c gates ProtectSystem= and the like on sandboxing, not TemporaryFileSystem=). It is now a root oneshot unit ordered before the page, and the claim step has no workaround: a broken hand-over fails it. | ONB-3 | If the seller's sealing step moves (for example into the image build), move the seal unit with it. |
| E4 | The modem is the AT simulator (`modem/atsim`, a SIMCom SIM7600G-H profile) behind a pseudo-terminal. A fake sysfs tree under `/run/agentos-e2e-sysroot` (outside the seal unit's root-only `/run/agentos-e2e`, which the bridge's user cannot traverse: there it found no modem) gives discovery its vendor and interface files, and its `ttyUSB2` node links to the pty slave, owned by `agentos-modem` as the udev rule would make it. A drop-in adds `-sys-root` and `DeviceAllow=char-pts rw`; a test keeps its command line equal to the shipped unit's plus `-sys-root`. Real USB enumeration, the udev rule and the radio are not exercised (M6 Ultra session). | CH-1, CH-12, HW-2 | If discovery reads more of sysfs, extend `buildSysroot`. |
| E5 | The phone's code generator is computed from the enrolment link's seed with the broker's own `owner.TOTP`; the card's prompt is answered from the saved sheet. Both prove the server's round trip, not an independent RFC 6238 or card implementation (those have their own package tests). | CH-10, ONB-3 | — |
| E6 | Steps run in the box's setup order (claim, network if offline, number and pairing, codes, card, recovery, this PC, AI), not the order #1688 lists them. After the first failure later steps print BLOCKED and do not run; a step on the expected-failure list prints XFAIL with its issue, and a listed step that passes fails the run (XPASS) so the list shrinks. | ONB-3 | — |
| E7 | One step is on the expected-failure list; `host` left it when #1221 served recording host trust, and `phone-control` when #1714 drove it (E9). `guest-task` (#1701): G1's model route is the ChatGPT-plan device-code sign-in through the Codex worker, and CI has no plan account, so it waits on a stub behind the worker; the API-key path is not used. `phone-control` runs after `guest-task` because agentosd answers texts only once setup has finished, which needs step 7's AI connection; until #1701 lands it prints BLOCKED, which is not a failure, and a run that reaches it and fails reads FAIL. | ONB-3 | Remove `guest-task` when #1701 lands. |
| E8 | Output is one console line per step. It never carries the claim code, card words, recovery key, vault passphrase, code-generator seed or a page body: a failure names the step, status codes, the location, the page's step heading and its sanitized error line. A claim failure also quotes the last localui and claim-move log lines, cut short, with the code replaced by `[redacted]`. | ONB-3 | — |
| E9 | `phone-control` proves the owner channel after setup with STATUS, which changes nothing. It first requires `GET /setup` to answer 303 to `/status`, so an unfinished setup fails as `setup not finished` and not as the owner channel; the GET also lets the page finish setup. The paired phone then texts `HELP`, which needs no code, until it gets `Commands:`: agentosd takes the modem from setup's line only after setup finishes, and the hand-over can lose the owner's texts because after setup the bridge has no `OWNER_NUMBER` (BOARD `P2-2w c4c r1`, bridge B9), so HELP repeats for up to three minutes and a timeout names the attempts. Only then does it text one `STATUS` with a code from a 30-second window the driver has not used (the box takes each window once and the enrolment used one), so the code is never read late, when it would be a wrong code that counts toward CH-11's lockout. The verdict reads the carrier's log in order from the step's start: the first reply to STATUS must be `Unlocked until` and the next `Running.` or `Stopped.`, so the session was locked and the fresh code unlocked it (CH-14); a status reply first, `You are already unlocked`, `Locked.` or `Wrong code.` fails. After the status reply an unpaired synthetic number (`+15550000102`) texts `STATUS` with a fresh code, and the paired phone texts `HELP` as a barrier: texts are read in arrival order, so the first reply to the paired phone after the stranger's text must be the barrier's `Commands:` (a reply drawn by the stranger's text fails), and any text to the unpaired number fails (CH-1, CH-3). Failures name reply kinds and counts, never a text. `TestPhoneControlAgainstTheOwnerChannel` runs the step against a real owner channel on the carrier simulator, with mutants. | CH-1, CH-3, CH-11, CH-14 | If STATUS stops being the safe read-only command, pick another that runs only once unlocked. When `P2-2w c4c r1` is fixed, the HELP retries can go. |
