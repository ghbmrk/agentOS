# broker/e2e assumptions

## S8-W1-contain (#1720): Codex CLI containment under gVisor

- E1. The scripted endpoint stands where the upstream would: the forwarder relays bytes to `route.sock`, so a plain HTTP server on that socket sees the CLI's requests exactly as egress would. Checked: the endpoint sees `Authorization: Bearer <canary>-access` and the canary account id.
- E2. Tool output reaches the test only through the CLI's `--json` result file (`command_execution.aggregated_output`). A probe line absent there fails the test: a tool that never ran is not counted as contained.
- E3. The control run (the probe started beside the CLI with the same env, without the CLI) reaches the forwarder, the socket and `CODEX_HOME`. Measured 2026-10-17: all reachable, Seccomp 0, NoNewPrivs 0. So a denial in the CLI run is the CLI's sandbox, not the machine.
- E4. **Measured 2026-10-17, gVisor release-20260928.0, CLI 0.162.1: the CLI's bundled bwrap cannot start a tool under runsc.** Every tool call failed with `bwrap: loopback: Failed RTM_NEWADDR`. Cause: runsc gives every new network namespace a loopback that already holds 127.0.0.1/8 and ::1/128 (runsc/boot/loader.go, the sandbox netstack creator), and bwrap adds 127.0.0.1/8 with `NLM_F_CREATE|NLM_F_EXCL` and dies on any error (bubblewrap network.c, unchanged on main). On Linux a new netns's lo has no address. The errno bwrap printed ("No child process") is stale: its netlink error path never sets errno from the reply. Fix: the image builds bubblewrap 0.11.2 (the release the CLI vendors, hash-pinned) with `guest/codex/bwrap-loopback.patch`, which sets errno from the reply and accepts `EEXIST` on that one address add, and installs it at both paths the CLI looks in. The address is the one bwrap would have set, so the tool's netns is unchanged. Upstream reports for gVisor and bubblewrap are drafted for Mark.
- E5. bwrap needs a user namespace in the worker: root there lacks CAP_SYS_ADMIN, so `--unshare-net` alone gets EPERM. The CLI's sandbox already unshares the user namespace.
- E6. **The CLI's shell snapshot stops every tool command when CODEX_HOME is hidden.** In 0.162.1 `shell_snapshot` is stable and on: the CLI writes `CODEX_HOME/shell_snapshots/<id>.sh` and wraps each tool command in `/bin/sh -c "if . '<snapshot>' >/dev/null 2>&1; then :; fi; ..."`. The deny list hides that file from tools, and in dash (the image's /bin/sh) a failed `.` ends a non-interactive shell with status 2 and no output; bash in POSIX mode does the same. Measured under runsc strace. `guest/codex/managed_config.toml` sets `shell_snapshot = false`; with it the probe runs and reports. It surfaced only after E4's fix, since bwrap had died before the shell ran.
- E7. Names under CODEX_HOME stay listable from a tool: the deny list covers each entry but not the directory itself, since listing the directory beside its globs stops bwrap (guest/codex/requirements.toml, guest/codex/ASSUMPTIONS.md C12). The test logs the listing but does not assert it; reading `auth.json` and writing CODEX_HOME are asserted denied.
- E8. The rootfs must be root-owned. Measured 2026-10-17 on CI: built by the runner's user, the workspace belonged to uid 1001, unmapped inside the CLI's user namespace, so the namespace's root had no override on it and every tool failed with `bwrap: Can't mkdir /var/lib/agentos-work/.git: Permission denied` (bwrap mounts a read-only `.git` over the writable root). Chowning only the workspace to 1001 reproduced it locally. CI builds the rootfs under sudo, as tests/test_codex_rootfs.py does. The test logs the tool output the CLI sends back, so a tool that fails before the probe runs shows its error.
