# Recall index: assumptions

Built against SPEC v0.12 (CAP-3, REV-5, CRED-1) and DECISIONS D1. Each row is a
reading a later spec version could change. Revised after the #38 review.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| R1 | Agent search has two forms. `PublicOnly` reads public items only and ranks them on statistics of public items only (a separate BM25 index; the normalising max over eligible items), so neither the results nor their order depend on private data, and the machine keeps its label. Any other search raises the machine to private **before** it runs, whatever it finds, because even "nothing matched" is owner data; it returns nothing if the raise fails or no labeler is wired. Scores never reach an agent (`Search` zeroes them, `Render` omits them). `PreferencesFor` raises likewise. | REV-5 ("recall results" make a machine private) | None expected. |
| R2 | Labels come from one allow-list shared with the event bus (`EffectiveLabel`): public is possible only for exact `web` (an uncredentialed fetch), `timer` and `task` (D1: marked PUBLIC), and `agent` (labelled by the broker from the source machine), and only when the caller declares exactly `public`. Every other kind, including new or misspelt ones, is private. A derived item is private if any parent is private or unknown here. Re-ingest never lowers a label. The only path that lowers one is `Relabel` to public, an explicit owner action (the D1 `PUBLIC` opt-out or a relabel on the local UI). It needs an authenticated owner-channel message whose parsed action is `recall.public` and whose target is that item; each message ID is used at most once (used IDs are persisted), so it cannot be replayed after the owner raises the item again. The message is recorded on the item (`LabelBy`). It is refused for kinds outside the allow-list and for items with a private or unknown parent. Raising is always allowed and cascades to derived items (arbitrator ruling on #38). `preference` is a reserved kind that Ingest refuses (and the bus refuses `owner` too). | REV-5, D1 | Add a kind to `publicKinds` only with a security review. |
| R3 | Preferences are written, edited and deleted only with the ID of a message the owner channel authenticated (`OwnerAuth`), which becomes the provenance. The message must ask for that action (`preference.set` or `preference.delete`) on that key, and each message ID is used once. Ingest never creates a preference, whatever the text says (A14). See K1 for who turns words into a key and value. | CAP-3 | — |
| R4 | Credential custody is by scrubbing before storage: PEM blocks, auth headers and schemes, `name: value` secrets, `otpauth://` URIs, URL userinfo (removed textually first, so unescaped `?`, `#`, `@` cannot move it), credential-named query values (REV-5's fixed patterns plus `session`, `pass`, `secret`, `otp`), grouped recovery codes (R10), any token of 16+ characters that looks random (letters-only ones by R11), and the whole object of a fact whose predicate names credential material (R11). The vault's redactor runs first when wired. It fails toward removing too much. Kept: UPS tracking numbers, undashed digit runs, and dash-written numbers whose groups differ in length (dates, `555-123-4567`, `TKT-2026-0042`). Removed: dash-written numbers in three or more even groups of 4 to 8 (order, card, ISBN and some phone numbers such as `1234-5678-9012`), because numeric backup codes have the same shape (R10). Short one-time codes are not reusable material; CH-19 governs where they may go. | CRED-1, CRED-7 | Tighten or loosen `randomLooking`. Small. |
| R5 | Identity is `Keyer.SourceID`: HMAC-SHA256 under a broker key of the **raw** (kind, account, ref), taken before scrubbing. The displayed ref is scrubbed; identity is not, so refs that scrub alike stay distinct and `DeleteSource` works by the raw name. Wiring passes a vault-held key (`WithKeyer`); without one, a random key is generated and kept in the meta log's header. | CAP-3 | — |
| R6 | Deletion removes the items and everything derived from them (transitively), records a durable tombstone (ID and time only) for each requested and removed ID, which is when the deletion takes effect; then rewrites atomically every segment that held any version of a removed item (R8) and runs `OnDelete` hooks for every one of those IDs, including requested IDs never indexed, since the event bus may still hold them. Hook errors, and a failed segment rewrite, are returned after the deletion is durable; the rewrite is retried on the next deletion and on every prune (daily when wired), `Open` erases any tombstoned content it finds (and fails to open if it cannot, rather than serve it), and tombstones are not pruned while an erase is pending. An item whose stored line cannot be read is deleted all the same (tombstone, erase), with an empty source in the report. A failed segment append is cut back to what memory knows, so its lines are gone at once. If the cut-back fails too, the segment is marked for erase like a failed rewrite (prune waits for it), but only in memory: a restart before any deletion of the item loads it as ingested, as if the write had succeeded before a crash. It never outlives a deletion: the tombstone and Open's erase remove it. Tombstones refuse content the broker **received** before the deletion (`Item.Received`, on the broker's clock: the bus passes its own publish time, whatever the source dated the item; a future receipt time is refused), so a stale delivery racing the deletion cannot bring it back, and a future-dated source time cannot either. They are replayed to every hook at registration, so a deletion a crash cut off still propagates (K2a). Freed blocks are not overwritten: erasure on the medium relies on drive encryption (HW, CRED-8). Nothing derived from a tombstoned item (`DerivedFrom`) is ingested while its tombstone stands, unless the parent itself came back live, so a deletion cannot be laundered through a note made from it. `PruneTombstones(maxAge)` drops old ones, except those `KeepTombstones` marks as still needed (an agent lineage still holds the item, recalltool W10); the policy is 30 days, far beyond the bus's last retry (minutes) and a restart's replay. `Deleted(id)` reports a standing tombstone with no live item, which recall's deletion reach reads to find what a lineage holds. | CAP-3 | Per-item keys with crypto-shredding. Medium. |
| R7 | Embeddings come from an `Embedder` with an `ID()` (model, version, dimension). Each vector stores its embedder ID, and the store header names the current one; a query compares only vectors of the current ID, so a new embedder never compares across spaces (BM25 and facts still answer). `Reembed` brings old vectors over in the background. The noise floor is per embedder (`CosineFloor`; 0.2 for the stdlib hashing embedder, which keeps recall free of inference, DEP-1). | CAP-3, DEP-1 | Reciprocal-rank fusion once a model embedder lands. Small. |
| R8 | Storage is a directory (0700): a small meta log (header, preferences, tombstones, used owner messages) and numbered item segments of at most 2048 items or 8 MiB, each a JSON-lines file with vectors quantized to int8 (base64); over synthetic mail the int8 top 10 overlaps the float32 top 10 by 0.89 on average (`TestInt8RankingAccuracy`, floor 0.85). Memory holds only what search needs: compact postings by document number, int8 vectors, facts, labels and provenance links; text, account and ref are read from the segment for the results returned. A deletion rewrites only the segments that held the item; a segment mostly made of superseded versions is compacted (until then superseded versions stay on disk, though a deletion erases every one of them); the meta log is rewritten on preference changes and when dead records dominate. Unreadable lines are skipped (counted by `Skipped`) and dropped. `IngestBatch` gives backfills one durable write per segment. Measured ceiling under Capacity below: 100k mail-sized items in about 0.5 GB. No store from the #38 single-file format exists in the field, so there is no migration. | RES-4, HW-4 | Persist postings per segment if load time matters at a larger scale. Medium. |
| R9 | The guest-facing surface is `Search`, `PreferencesFor` and `Render` only. Ingest, delete and preference writes are broker-internal. | CAP-3, ARC-6 | — |
| R10 | A grouped code (three or more dash-separated groups of 4 to 8 letters or digits) is removed when it mixes letters and digits, or when its groups all have one length, whatever its alphabet or entropy. Generated recovery and backup codes are cut evenly, and a fact object or a bare line carries no `recovery code:` key for `secretKV` to catch; before this, a base32 code with no digit and entropy under 3.5 was kept (about 1 in 1.5 million random 6×5 codes; caught by `TestCredentialsNeverStored` on #617, RECALL-canary-1). Hyphenated words and dates, whose parts differ in length, are kept. Removed as an accepted cost, toward removing too much: evenly cut words (`BLUE-FISH-TANK`, `part-time-work`) and dash-written digit runs in even groups (4-4-4 order and phone numbers, digit-only parcel tracking, ISBN-13 cut 4-4-4, card numbers); exempting all-digit runs would reopen numeric backup codes. `TestGroupedNumbersTradeoff` pins both sides; a recall user asking for such a number finds it removed and must look in the source. Ungrouped letters-only tokens are R11's. | CRED-1 | A code format with uneven groups and no digit: add its shape. Small. |
| R11 | **Letters-only floor.** An ASCII letters-only token of 16+ characters (trailing `=` padding aside) is removed unless a letter model scores it at least 24 bits likelier as English than as uniform random letters. The model (`letters.bin`, 18 KB, made by `letters_gen.go` from the distinct words of go1.26.8's source comments) is a trigram model backed off to bigrams; case boundaries (`getUserName`, `XMLHttp`) start a new word. Its entries are rounded down, so each context sums to at most one and a uniformly random string, of either case or mixed, is kept with probability at most 2^-24 (6e-8) at **every** length (Markov's inequality; `TestLetterModelNormalized`). Measured by importance sampling: at most 3e-9 for lengths 16–32, falling with length. Chosen over an entropy floor because a word and a random string of 16–24 letters have overlapping entropy (3.3–3.9 bits), so no entropy floor both keeps words and holds; over 20 or 22 bits because their bounds (1e-6, 2.4e-7) do not clear canary-1's measured 6.7e-7. Removed as the accepted cost: about 40% of real words and identifiers of 16–19 letters, 10–30% at 20–24, under 3% past 24 (Go comment words and identifiers, held out), including `responsibilities`, `acknowledgements` and non-English words (`Rechtsschutzversicherung`); before, every word of 16–19 letters was kept, but about 40% at 20–24 and 70% past 24 were removed by the entropy floor. `TestLongWordsTradeoff` pins both sides. Not covered: random strings over a small or English-weighted alphabet, including passphrases of joined dictionary words (`CorrectHorseBatteryStaple`), and non-ASCII letters (the old floors apply). **TOTP seeds:** a digit-free base32 seed (32 letters, `=` padded or not) now falls under this floor whatever its entropy, which closes the "TOTP seed without context" bullet of RECALL-canary-3 for an unbroken seed; a seed written in spaced groups (`abcd efgh …`) or with confusables is still canary-3's. **Predicates:** a fact whose predicate, split into words at case, punctuation and letter-to-digit boundaries (`recoveryCodes`, `API-Key`, `2FA seed`, `password1`; an acronym keeps its plural, `OTPs`), contains a credential word (password and its variants, pw, passkey, pin, secret, credential, api/access/private/secret/signing key, token, recovery, backup code, seed, mnemonic, totp, otp, 2fa, mfa, cookie, security answer) or ends in `key`/`keys` (`ssh_key`, `master_key`) is stored with its object removed, whatever the object looks like. Over-matches such as `recovery_time`, `seed_round`, `tokens_used`, `token_count` or `house_key` lose their object too. Not matched: homoglyph or non-English names (`p@ssword`, `Passwort`) and short-lived codes (`auth_code`, CH-19). A credential named only by the subject, or split across facts, is canary-3's. | CRED-1 | Raise the 24 bits for custody or retrain the model on more English for recall. Small. |

## Capacity (BOARD P3-3, measured 2026-10-05)

`RECALL_CAPACITY=N RECALL_CAPACITY_BATCH=500 go test ./recall -run TestCapacity -v` ingests N synthetic mails (about 2 KB of text, two facts, 512-dimension hash vectors) into a directory store, then measures. Cloud runner, 4 cores; the N95 floor host is slower, so read times as relative.

| Store | Items | Store size | RSS after reopen | Live heap | Reopen | Delete one | Search |
|---|---|---|---|---|---|---|---|
| #38 single file (at 14e31bb) | 10k | 68 MiB | 413 MiB | — | 3.2 s | 2.6 s | 44 ms |
| #38 single file (at 14e31bb) | 50k | 338 MiB | 2000 MiB | — | 18.6 s | 13.8 s | 232 ms |
| segmented (R8) | 50k | 156 MiB | 227 MiB | 106 MiB | 7.0 s | 0.12 s | 81 ms |
| segmented (R8) | 100k | 312 MiB | 462 MiB | 210 MiB | 11.8 s | 0.06 s | 168 ms |

Batched ingest runs about 1000 items/s (scrubbing and embedding bound), so a 100k-mail backfill takes under 2 minutes of CPU. The ceiling for the floor host (HW-4: 8 GB, 4.5 GB for machines, 0.6 GB headroom) is about **100k items per index at ~0.5 GB RSS**; past that, the next steps are persisting postings per segment (reopen time) and a pruned vector scan (search time). The broker should open recall off the STOP path, since reopening takes seconds.

## Conditions for wiring (from the #38 lens gate)

Status: see [recalltool W8](../recalltool/ASSUMPTIONS.md).

- **K1.** Whatever turns the owner's words into a preference key and value is broker code, or its result is echoed back to the owner in fixed wording before it counts; it is never an agent machine that has read untrusted content.
- **K2b.** Deletion also reaches journal params, agent-machine memory and snapshots, the change pipeline's held-out cases (#34) and replay recordings (#37), each through an `OnDelete` hook. Agent summaries set `DerivedFrom` from the recall results and events they consumed, so deleting a source deletes what was made from it.
- **K3.** Credentialed reads are ingested as kind `credentialed`, set by the executor, never by the caller.
- **K4.** Kind `agent` is public whenever the caller declares it public, so the broker sets that label from the source machine's REV-5 label, never from the guest.
- **K5.** Wiring passes the vault-held identity key with `WithKeyer`. The generated key kept in plaintext in the store header is for tests and development only.
- **K6.** A `Relabel` to public is a broker-state change: the broker submits it as a journaled intent (OP-5) before calling `Relabel`. The owner channel parses the message into its action and target (`OwnerMessage.Action`, `.Target`; for D1 the target is the task's recall item ID). Broker code derives the target from the owner's reply context; an agent never sets it.
- **K7.** The recall broker tool defaults public machines to `PublicOnly`, so a search does not raise them unless the agent asks for owner data.
- **K8.** The broker prunes tombstones only with the 30-day policy; `PruneTombstones` refuses anything under `MinTombstoneAge` (24 h).
- **K9.** Direct `Ingest` callers pass `Received` as the time they fetched the content. A zero receipt time is stored as now but refused for a deleted source, and `IndexInto` refuses an event without one.
- **Public items' metadata.** Considered and left: public web items keep `Account` and `Ref`, since a public item's URL is its content. If watched-URL lists turn out to be sensitive, the watcher should label those events private.
