# Recall index: assumptions

Built against SPEC v0.12 (CAP-3, REV-5, CRED-1) and DECISIONS D1. Each row is a
reading a later spec version could change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| R1 | Any recall result is owner data unless every item in it is labelled `public`. Search on behalf of an agent machine raises the machine to private before any private result is returned, and returns nothing if the raise fails or no labeler is wired. `PublicOnly` lets a public machine search without rising. | REV-5 ("recall results" make a machine private) | If all recall results must count as private, drop `PublicOnly` and raise on every non-empty result. One line. |
| R2 | Labels fail closed: anything other than the exact string `public` is private. Mail, file, calendar, contact, owner, credentialed-executor and preference items are private whatever the caller declares. Task text is private unless the caller states the owner marked the task `PUBLIC` (D1). A derived item is at least as private as each of its parents. | REV-5, D1 | None expected. |
| R3 | Preferences are written, edited and deleted only with the ID of a message the owner channel authenticated (`OwnerAuth`), which becomes the provenance. Turning the owner's words into a key and value is the caller's job; the index records them. Ingest never creates a preference, whatever the text says (A14: "an email asserting a preference creates none"). | CAP-3 | If a model extracts the key and value, the owner should see the stored preference in the reply (a P2-2 UI or owner-channel concern). |
| R4 | Credential custody is by scrubbing before storage: PEM blocks, auth headers and schemes, `name: value` secrets, `otpauth://` URIs, URL userinfo and credential-named query values (REV-5's fixed patterns plus `session`, `pass`, `secret`, `otp`), grouped recovery codes, and any token of 16+ characters that looks random. The vault's redactor runs first when wired. It fails toward removing too much: random-looking identifiers (commit hashes, some tracking IDs) are replaced too. Short one-time codes (a 6-digit 2FA code in a mail) are not reusable material and are not removed; CH-19 governs where they may go. | CRED-1, CRED-7 | Tighten or loosen `randomLooking`. Small. |
| R5 | Deletion removes the items, everything derived from them (transitively), their facts and vectors, and rewrites the store file atomically, so the live file holds no copy; `OnDelete` hooks carry it to the event bus. Blocks freed by the rewrite are not overwritten: erasure on the medium relies on the drive's encryption (HW, CRED-8), not on this package. | CAP-3 ("Deletion requests propagate") | A per-item key with crypto-shredding would make erasure independent of the drive. Medium. |
| R6 | Embeddings come from an `Embedder`. The default is a stdlib feature-hashing embedder, so recall needs no inference (DEP-1); the local inference service can replace it. The noise floor `minCosine` (0.2) is tuned for the hashing embedder. | CAP-3, DEP-1 | A model embedder may need its own floor. Small. |
| R7 | The guest-facing surface is `Search`, `PreferencesFor` and `Render` only. Ingest, delete and preference writes are broker-internal; P1-7 wires the broker tool. Render escapes all markup in content and attributes and heads results with an untrusted-content note. | CAP-3, ARC-6 | None here. |
| R8 | One JSON-lines file, rewritten on deletes, preference changes, and when replaced versions exceed half the file. Fine for a personal box's first months; a segmented store is future work if the index grows past what one rewrite should cost. | RES-4 | Segment the store. Medium. |
