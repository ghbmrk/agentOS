# Grants and approval policy: assumptions

Built for the P2 grants and approval-policy package against SPEC v0.12
(PR #15), on the journal (P1-1), the owner channel (P1-5), and the guest
plane (P1-7, PR #24). Each row is a reading of the spec, or a gap left for
a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| GR1 | The verb list and each verb's class live in `broker/verb`, shared by this package and the egress proxy. read and draft are reversible; send, post, buy, share, delete-remote, and change-account are irreversible; reveal-or-create-secret is its own class (CRED-6). | ADP-2, REV-2 | Changing the list is an owner-approved code change (OP-5, CHG-2). |
| GR2 | A grant is one of three shapes, each a `meta.grant` intent on the broker account: an **adapter grant** (account, executor, and the operations the owner accepts with the verb each maps to), a **pre-allowance** (account and rule), or a **resume** of a paused grant. Operations a grant does not list do not exist for agents. Grants are rebuilt from the journal's succeeded records on every start, so there is no second store. IDs are `G<n>`, numbered by the intent's place among all grant intents ever submitted, so replay gives every grant the ID it had live. | OP-5, ADP-1, ADP-2 | Medium: `grant.go`. |
| GR3 | Every grant shape is high risk (owner `Kind` GrantChange) and needs both the code-generator code and a local confirmation, in either order (`ConfirmLocal`, called by the P2-2 local page after it shows `Describe`). The recovery-key alternative in CH-3 is not built. Where no local page exists (`Config.LocalUI` false, which is the box today), grant intents are refused at once with the reason, rather than asking the owner for a code that cannot complete them. | CH-3, CH-10, ADP-9 | P2-2 sets `LocalUI` and calls `ConfirmLocal`. |
| GR4 | Only structural faults deny an effect: no grant, an undeclared operation, an executor the grant does not connect, a malformed grant, or a narrowing intent from anyone but the owner. Reads and drafts under a grant run at once. Every other verb is gated: it runs only under an exactly matching pre-allowance, or after the owner approves a CH-12 request through `owner.Channel.Request`. reveal-or-create-secret always asks, whatever the rules. | REV-2, CRED-6, ADP-9 | Hard constraint: irreversible effects are always gated. |
| GR5 | The approval line comes from the account's `Verifier` (the adapter reading the source system) with the verb and kind set from the grant, never from the agent. With no verifier, or when verifying fails, the line shows the operation and the intent's own recipients (what will run), marked unverified, with no verified facts, so it is high risk. No pre-allowance matches an unverified intent. No verifiers exist yet; they come with the adapters (P2-6, P2-7). | CH-10, CH-12 | — |
| GR6 | A pre-allowance matches only when all of these hold: params are exactly the rule's fixed params plus `record` (and `body` for a reply rule), so there is no free text; `record` is the record the verifier read; recipients equal, as a set, the ones that record names, and fall within the rule's list if it has one; any verified amount is at or under the cap (a zero cap means no money moves); the record is older than the hold (an unknown edit time fails the hold); and the scope bounds have room. Anything else becomes a normal approval request. | ADP-9 | `matches`. |
| GR7 | Scope bounds (per record per day, per day) count every intent on that account and operation authorized in the last 24 hours and not refused by the recheck, whether a rule or the owner allowed it. This is conservative: an owner-approved send uses up room under the rule. The count is from the journal (`Engine.AuthorizedSince`), so it survives restarts. The dispatch recheck runs under the engine's serialization, so the bound holds there; two concurrent authorizations can both pass the first check, and the later one is then refused at dispatch rather than asked. The authorization record does not say which rule allowed it. | ADP-9, OP-3 | Journal the basis if audit needs it. |
| GR8 | Owner approvals are held in memory for the recheck before dispatch (OP-3). The recheck refuses an approval that is older than `Fresh` (default 1 h, for example after a long STOP), one whose grant was paused or revoked, or one whose rendered line (object, recipient, amount, undo window, verb, kind) has changed since the owner approved it. A restart loses held approvals, so an approved intent still held by STOP across a restart is refused at its recheck. | OP-3, journal A4 | Persist approvals if this costs real work. |
| GR9 | Items asked within one tick (`DefaultTick`, 10 s) share a request, split by tier (`owner.Channel.Tier`), so one high-risk item does not raise the code needed for low-risk ones. At most 20 items go in a request. If the owner cannot be texted (no modem before P2-3, or `ErrFull`), the intent stays pending with the reason, and a retry of the same request_id asks again. The guest is told it is waiting, never the request ID. | CH-10, CH-13 | — |
| GR10 | **Restart (P1-5's carry-forward from G12).** No approval request survives a restart (owner O7), so `Attach` denies every intent left pending, with a reason telling the agent to ask again under a new request_id. That includes an intent a crash caught between submit and authorize; G12's "finished on retry" now means "denied on retry". `Boot`'s restart decisions then find these intents already settled. | OP-4, CH-13 | Re-asking automatically would re-text requests that Boot just told the owner were cancelled. |
| GR11 | **ADP-11 replies.** A reply rule covers `send` with no money. A reply matches only when the submitting origin is a reply-composer machine (`Config.Isolated`), the verifier confirms the thread starter and no attachments, and recipients are exactly the thread's participants. It then goes to `owner.Channel.QueueAutoReply`: the commitment filter turns it into a normal request, or it is queued, the owner is texted its first line and `UNDO <id>`, and it is released by `Tick` after the undo window (never while STOPped). UNDO and a restart now send the owner channel's decision for the reply (`Why` "undo" or "restart"), which closes the intent. No composer machine exists yet, so `Isolated` is nil on the box and reply rules never match. The earned count (20 unedited replies) is CAP-6's offer condition and is not checked here. | ADP-11, CH-16 | The composer pipeline sets `Isolated`. |
| GR12 | **PAUSE and REVOKE.** These are owner texts (`PAUSE G3`, `REVOKE G3`; CH-11's pause and revoke commands) that need only the owner's number, like STOP. They become narrowing intents with origin `owner`, which are exempt from STOP holds and restart fences (journal A9). A guest cannot submit one. Pausing a pre-allowance sends its operations back to approval. Pausing an adapter grant stops routing to its account. Revoking an adapter grant also removes that account's pre-allowances, so a later grant cannot silently revive them. Unpausing is a `resume` grant (GR2), because it widens authority. HELP's word list (control package) does not mention PAUSE or REVOKE yet. | ADP-9, CH-11 | — |
| GR13 | **Provenance.** Each intent records the submitting machine and its REV-5 label (`journal.Intent` Machine and Label). An unknown label is recorded as private. These are provenance, not parameters: they are excluded from the OP-1 fingerprint, and the first submission's values are kept. A repeat of the same request_id from a fork whose label has since risen is therefore the same intent. It is not re-authorized, because its effect, and so what it discloses, is fixed by the parameters the owner or a rule already judged. The approval line does not show the label yet. | REV-5, OP-1 | Re-authorize on a label rise if a lens finds a disclosure the params do not fix. |
| GR14 | Guest-submitted broker intents are refused in the guest plane by PR #24's fix-list (item 3: no `broker` account and no `meta.*` from guests). As defense in depth, this policy refuses narrowing from any origin but `owner`, and every grant needs the code plus the local page whatever its origin. | OP-5, ARC-7 | — |
| GR15 | The box's redactor is still `redactAll` until the vault's redactor is wired with the vault unlock (P2-4; `daemon.Config.Redactor`). It replaces every journaled param string, so grant specs and template params cannot be read back on the box until then. Together with GR3 (no local page) and no adapters, nothing is grantable on the box yet. Every path is proven in tests with an identity redactor and the real owner channel on the modem simulator. | CRED-7, OP-5 | P2-4. |
