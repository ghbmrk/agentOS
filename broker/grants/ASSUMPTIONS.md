# Grants and approval policy: assumptions

Built for the P2 grants and approval-policy package against SPEC v0.12
(PR #15), on the journal (P1-1), the owner channel (P1-5), and the guest
plane (P1-7, PR #24). Each row is a reading of the spec, or a gap left for
a later package, that a reviewer may want to change.

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| GR1 | The verb list and each verb's class live in `broker/verb`, shared by this package and the egress proxy. read and draft are reversible; send, post, buy, share, delete-remote, and change-account are irreversible; reveal-or-create-secret is its own class (CRED-6). `ClassOf` reports the strictest class for an unknown verb, and every caller denies on `!ok`. | ADP-2, REV-2 | Changing the list is an owner-approved code change (OP-5, CHG-2). |
| GR2 | A grant is one of three shapes, each a `meta.grant` intent on the broker account: an **adapter grant** (account, executor, and the operations the owner accepts with the verb each maps to), a **pre-allowance** (account and rule), or a **resume** of a paused grant. Each executor declares its operations and verbs (`Config.Declared`, from the adapter's own declaration); the daemon refuses an executor without one. A grant can only choose among declared operations, at the declared verb or a stricter one, and policy applies the stricter of the two, so a grant can never weaken a verb. An account has at most one adapter grant, live or paused; replacing it means revoking it first. Operations not chosen do not exist for agents. Grants are rebuilt from the journal's succeeded records on every start, so there is no second store; a grant whose replay no longer validates (say its executor is gone) is dropped and logged. IDs are `G<n>`, numbered by the intent's place among all grant intents ever submitted, so replay gives every grant the ID it had live. | OP-5, ADP-1, ADP-2 | Medium: `grant.go`. |
| GR3 | Every grant shape is high risk (owner `Kind` GrantChange) and needs both the code-generator code and a local confirmation, in either order (`ConfirmLocal`, called by the P2-2 local page after it shows `Describe`). The recovery-key alternative in CH-3 is not built. Where no local page exists (`Config.LocalUI` false, which is the box today), grant intents are refused at once with the reason, rather than asking the owner for a code that cannot complete them. | CH-3, CH-10, ADP-9 | P2-2 sets `LocalUI` and calls `ConfirmLocal`. |
| GR4 | Only structural faults deny an effect: no grant, an operation not granted, an executor the grant does not connect, a malformed grant, a broker action from a guest, or narrowing from anyone but the owner. Denial reasons are fixed wording that never echo an account, action, recipient, or grant reference, because a guest reads them back through `effect_status`. Reads and drafts under a grant run at once. Every other verb is gated: it runs only under an exactly matching pre-allowance, or after the owner approves a CH-12 request through `owner.Channel.Request`. reveal-or-create-secret always asks, whatever the rules. | REV-2, REV-5, CRED-6, ADP-9 | Hard constraint: irreversible effects are always gated. |
| GR5 | The approval line comes from the account's `Verifier` (the adapter reading the source system) with the verb and kind set from the grant, never from the agent. With no verifier, or when verifying fails, the line shows the operation and the intent's own recipients (what will run) with no verified facts, so it is high risk, and it starts with a fixed `UNVERIFIED, details on the Wi-Fi page:` prefix outside every field cap (`owner.Item.Unverified`). No pre-allowance matches an unverified intent. No verifiers exist yet; they come with the adapters (P2-6, P2-7). | CH-10, CH-12 | — |
| GR6 | A pre-allowance matches only when all of these hold: params are exactly the rule's fixed params plus `record` (and `body` for a reply rule), so there is no free text; `record` is the record the verifier read; recipients equal, as a set, the ones that record names, and fall within the rule's list if it has one; any verified amount is at or under the cap (a zero cap means no money moves); the record is older than the hold (an unknown edit time fails the hold); and the scope bounds have room. Anything else becomes a normal approval request. | ADP-9 | `matches`. |
| GR7 | Scope bounds (per record per day, per day) count every intent on that account and operation authorized in the last 24 hours and not refused by the recheck, whether a rule or the owner allowed it. This is conservative: an owner-approved send uses up room under the rule. The count is from the journal (`Engine.AuthorizedSince`), so it survives restarts. Concurrent intents fail closed: each one's authorize check counts the others already authorized, and the dispatch recheck, serialized by the engine, counts every authorized intent but itself, so two concurrent intents under a bound of 1 can both be refused at dispatch rather than one asked. The authorization record does not say which rule allowed it. | ADP-9, OP-3 | Journal the basis if audit needs it (Security, non-blocking on #27). |
| GR8 | Owner approvals are held in memory for the recheck before dispatch (OP-3). The recheck refuses an approval that is older than `Fresh` (default 1 h, for example after a long STOP), one whose grant was paused or revoked, or one whose rendered line (object, recipient, amount, undo window, verb, kind) has changed since the owner approved it. A restart loses held approvals, so an approved intent still held by STOP across a restart is refused at its recheck. An approval covers one attempt: it records how many attempts the intent had when the owner answered, and the recheck at dispatch refuses it once another has started. The journal commits a dispatch only if nothing was journaled during its check, so concurrent dispatches of one intent start at most one attempt on one YES (Security ruling on #76). | OP-3, journal A4 | Persist approvals if this costs real work. |
| GR9 | **Batching and pacing.** An item asked of the owner joins the open batch. The batch is sent when it has been quiet for `CoalesceIdle` (default 30 s) or open for `Coalesce` (default 3 min), outside the owner's quiet hours (`Quiet`), and within `RequestsPerHour` request texts (default 3, CH-15's default). It goes at once, in quiet hours too, when it holds an owner-defined urgent item (`Urgent`), and at once outside quiet hours when the owner texted within 5 minutes (`owner.Channel.Active`). Quiet hours therefore yield one batch when they end. Each batch is split by tier (`owner.Channel.Tier`) into requests of at most 20 items. If the owner cannot be texted (no modem before P2-3, or `ErrFull`), the intent stays pending with the reason, and a retry of the same request_id asks again. The guest is told it is waiting, never the request ID. "Task idle" is approximated by the quiet gap, since the broker has no task boundary yet. The CH-15 budget shared with other unsolicited texts and the digest land with the CH-15 pacing package. | CH-10, CH-13, CH-15 | Tune the defaults; owner-set values come with the local UI. |
| GR10 | **Restart re-issues (arbitrator ruling on #27, replacing restart-deny).** Every old code dies at a restart: no code is persisted and Boot retires every open request ID. `Attach` holds every intent left pending (`effect_status`: "the owner will be asked again") until the owner channel's `Boot` hands over what was open (`owner.Config.Reissue`), so a retry neither asks twice nor gets a new expiry. Boot denies items whose request expired meanwhile (Why "expired") and cancels a record it cannot trust (saved by an older build without an expiry, or asked in the future); an expiry later than `owner.MaxTTL` (24 h) after the ask is capped there. For each handed-over item the gate rechecks OP-3: the grant still makes it an ask, and the line it would show now has the same digest (`owner.ItemSum`, kept in the restart record) as the one the owner saw. A changed item is denied with a fixed reason instead of re-sent; it is rechecked again before dispatch as usual. Each unchanged item joins the GR9 batch, so coalescing and quiet hours apply. The hourly limit does not hold it back: it runs on its original expiry, so a spent budget would let it lapse unseen (security R3 on #95, W9a). Its text still counts on `RequestsPerHour`, so questions see it. It is sent through `owner.Channel.RequestEach`: one request and one fresh single-use code per intent (a code-generator code for high-tier items), all in one text when they fit. Each keeps its original expiry; one that lapses while waiting to be sent is denied. Its line ends "asked 14:02, re-sent after restart" (outside every field cap; recipients are still never cut, GR16), and the boot text says the request "will be re-sent with new codes". If the re-issued text cannot be sent, the intent stays pending with the reason, and a retry of the request_id asks again as new, as after an expiry. Intents never shown to the owner (still batched, local-only, a failed text, or a crash between submit and authorize) are asked as new. Nothing is re-issued or sent while STOP holds; `Tick` resumes it. Queued auto-replies are still cancelled at a restart (GR11). Without an owner channel nothing is held, and a retry asks again (GR9). | OP-3, OP-4, CH-10, CH-13, CH-15 | `Reissue`, `reissueDue`, `Flush`; owner `Boot`, `RequestEach`. |
| GR11 | **ADP-11 replies.** A reply rule covers `send` with no money. A reply matches only when the submitting machine (not its lineage, so a fork of a composer is not one) is a reply-composer machine (`Config.Isolated`), the verifier confirms the thread starter and no attachments, and recipients are exactly the thread's participants. It then goes to `owner.Channel.QueueAutoReply`. If the commitment filter matches, it becomes a normal request. Otherwise it is queued, the owner is texted its first line and `UNDO <id>`, and `Tick` releases it after the undo window (never while STOPped). UNDO and a restart now send the owner channel's decision for the reply (`Why` "undo" or "restart"), which closes the intent. No composer machine exists yet, so `Isolated` is nil on the box and reply rules never match. The earned count (20 unedited replies) is CAP-6's offer condition and is not checked here. | ADP-11, CH-16 | The composer pipeline sets `Isolated`. |
| GR12 | **PAUSE and REVOKE.** These are owner texts (`PAUSE G3`, `REVOKE G3`; CH-11's pause and revoke commands) that need only the owner's number, like STOP. They become narrowing intents with origin `owner`, which are exempt from STOP holds and restart fences (journal A9). A guest cannot submit one. Pausing a pre-allowance sends its operations back to approval. Pausing an adapter grant stops routing to its account. Revoking an adapter grant also removes that account's pre-allowances, so a later grant cannot silently revive them. Unpausing is a `resume` grant (GR2), because it widens authority. HELP's word list (control package) does not mention PAUSE or REVOKE yet. | ADP-9, CH-11 | — |
| GR13 | **Provenance and labels.** Each intent records the submitting machine and its REV-5 label (`journal.Intent` Machine and Label; an unknown label is recorded as private). These are provenance, not parameters: they are excluded from the OP-1 fingerprint. The guest plane partitions a lineage's requests by label. Public machines use `<lineage>/<request_id>`, private ones `<lineage>/private/<request_id>`. A public machine therefore never sees, collides with, or learns timing from a private machine's request (the #27 review's REV-5 probe). A private machine repeating a request its lineage made while public gets that intent read-only: it sees the state but never drives it, since driving would let a private machine change what a public one observes. Approvals still settle it, through the owner. Because a private machine never drives a public-namespace intent, its recorded label is always that of the only kind of machine that can dispatch it, and no "highest label seen" update is needed. **Invariants (Security, #27 review):** (i) params carry content inline or by hash, and executors never read the submitting machine's state at dispatch, so a repeat from any fork runs exactly what was judged (the first executor package adds a test for this); (ii) once REV-5 policy reads labels, an undispatched intent is judged at the higher of its recorded label and the current submitter's, and its approval line says "from a private machine". | REV-5, OP-1 | — |
| GR14 | Guests never reach broker-state actions. The guest plane refuses `broker` and any `meta.*` action before routing, unjournaled, with a fixed reason. `Gate.Route` never routes `broker`. As defense in depth, the policy denies broker actions from any `guest:` origin, refuses narrowing from any origin but `owner`, and requires every grant to carry a code plus the local page whatever its origin. This overlaps #24's item 3 on purpose. | OP-5, ARC-7, REV-5 | — |
| GR15 | The box's redactor is still `redactAll` until the vault's redactor is wired with the vault unlock (P2-4; `daemon.Config.Redactor`). It replaces every journaled param string, so grant specs and template params cannot be read back on the box until then. Together with GR3 (no local page) and no adapters, nothing is grantable on the box yet. Every path is proven in tests with an identity redactor and the real owner channel on the modem simulator. | CRED-7, OP-5 | P2-4. |
| GR16 | **Recipients are never cut, hidden, or collapsed (CH-10, CH-12; Security on #27).** The owner channel renders recipients in full and folded. An item is not approvable by text (`owner.SMSApprovable`; `Request` returns `ErrLocalOnly`) when its recipients exceed 100 characters, contain a character outside the fixed alphabet or a line break, or look secret-shaped. Such an item is never texted for a code. The owner gets "An action for N recipients needs your approval on the box's Wi-Fi page", and the intent waits for the local page (P2-2). Until that page exists it stays pending, and a restart repeats the notice (GR10). | CH-10, CH-12, CH-19 | P2-2 adds local approval. |
| GR17 | **Change intents (change C7, C8; P3-1b).** `meta.change.*` intents on the broker account go to the change pipeline (`Config.Changes`, `change.Pipeline`) after the GR14 guest check: its `Check` allows, denies with its reason, or returns `change.ErrNeedsOwner` (recognized by its `NeedsOwner()` method, since this package may not import `change`, ARC-2), which becomes a CH-10 request built from the pipeline's `Line` with no recipient or amount. Its kind is `GrantChange`, so high tier, unless the pipeline marks it `Ordinary`. The pipeline does that only for a tested, undoable, local learned skill or procedure (arbitrator on #48), which makes it low tier. The test result renders as `owner.Item.Detail`, and how to reverse the change as `UndoBy` ("can be undone later", "LEARN OFF any time") in place of "cannot be undone". Both enter `ItemSum` only when set. Grant changes need the local page (GR3). Change intents need only the high-tier code, because every adoption but a first image can be undone. There are two exceptions, and both also need `ConfirmLocal` on the local page, like a grant:
- Turning sharing on, which changes what leaves the box (CHG-4, CHG-5; Security lens R1 on #48). Without a local page it is refused outright.
- Adopting a release, an item with verb `install` (CH-3: "adopt a release"; L3 B1 on #48). Without a local page it is held pending: no code is texted for it and it is never denied, so the box can still take a security fix once the page exists. The arbitrator ruled hold (Q1 on #48). An attested security release under the standing `SecurityAutoStage` policy needs no owner at all (CHG-3). With no pipeline configured, change intents are denied. Once a change request closes, the gate calls `Decided`, with `declined` true only when the owner said NO. A refusal at the recheck, such as an approval that went stale before dispatch, is not a decline (L3 R1 on #48). Only the `NeedsOwner` sentinel itself asks: an error that wraps it or joins it with a refusal denies (L3 R2). A request that closes without the owner's NO (Why "expired", "void", "not chosen", or "restart") first drops the pipeline's proposal with no decline, then closes the intent as "lapsed, not declined" (arbitrator Q3 on #48). The intent never runs, the owner channel lists the expired item in the digest (CH-13), and neither learning nor Loop 1's backoff reads silence as a rejection. While a release is held for a missing local page, the owner gets one fixed line: "Waiting for your confirmation on the box's local page, or your recovery key." (arbitrator Q1 on #48). | OP-3, OP-5, CHG-2, CHG-3, CH-10, CH-12 | `evaluateChange`, `lapse`. |

| GR18 | **Loop settings (loops L2; P3-2 wiring).** `meta.loops.*` intents on the broker account go to the loop scheduler (`Config.Loops`, `loops.Scheduler`) after the GR14 guest check, as GR17 does for changes. Its `Check` allows the owner's own settings (off, on, a lower budget), denies any other origin (LOOP-6), and returns `loops.ErrNeedsOwner` for a budget raise. The gate recognizes that error by its `NeedsOwner()` method, never wrapped or joined, and turns it into a request built from the scheduler's `Line` ("raise spare-time AI use, from 40 to 80 paid AI calls a day", undone by "SPARE BUDGET 40 any time"). Spare calls are paid use of the owner's AI provider account, so only a small step is low tier (a texted code): to at most twice the current budget and at most `loops.LowTierRaiseMax` (500 a day). Anything larger is `GrantChange`, high tier, so a SIM swapper who has the owner's number and texted codes cannot open-endedly spend the owner's money (security B1 on #57). **Open (security R1, R2 on #57):** show an estimated daily cost once the provider's price is known, and text the owner once when spare use passes 80% of a raised budget in a day. A raise left unanswered closes as "lapsed, not declined", like a change. Without a scheduler, loop settings are denied. | LOOP-0, LOOP-2, LOOP-6, CH-10, OP-5 | Tune the step from A11. |
| GR19 | **Reversible forms (REV-3, P2-rev3).** An owner-approved effect whose operation has a declared form (`Config.Forms`) is held for its undo window, staged first if the form says so, and cancelled and unstaged by UNDO or a restart. Pre-allowed effects are never held. Details in [reversible/ASSUMPTIONS.md](../reversible/ASSUMPTIONS.md) RV1–RV10. | REV-3, CH-16 | `hold`, `unstage`, `evaluateDerived`. |
| GR20 | **Owner verdicts for learning (W3; potency PW3 on #90).** `Config.Outcome` is told the owner's verdict on a guest's effect once it is final, from `settle`'s goroutine after the journal has the final state and outside the gate's lock, at most once per intent (the last 4096 remembered; the harvester keeps only the first verdict anyway). It must not block, and a panic in it is logged and changes nothing, so learning can never fail the owner's answer (security A1, A2). The verdict is keyed only on broker-set fields (origin, goal, state) and the gate's own decision reasons, never on params or guest text: `accepted` when the owner said YES (for a held effect, at its release once the undo window passed, so YES then UNDO is `undone`, never an acceptance); `accepted-implicitly` when a pre-allowed auto-reply (ADP-11) was released unanswered on time (one the owner channel marks `Late`, owner O18, is released with its own reason and reports nothing: security B1(a) on PW3; so is one whose alert or release fell in quiet hours, `Config.Quiet`, F1 on #109); an implicit acceptance is reported only `owner.LateRelease` after its send ended, and not at all if the owner texted UNDO for it meanwhile (`Owner.UndoneAfterRelease`, owner O18; L3 MUST-4 on #109), in memory, at most 4096 waiting; `declined` on the owner's NO; `undone` on UNDO. An acceptance is reported only once the effect was sent or may have been (`succeeded` or `outcome_unknown`): an approval STOP, an account fence or a slow send holds is kept (at most 4096) and reported when its send ends, from `Dispatch` or `Tick` (L3 MUST-1 on #101). Nothing is reported for an expiry, void, restart, lapse, recheck refusal, an unstaged release, a failed send, a draft changed after the YES (the gate never reads the edit, so there is no correction to give), or any broker-state intent. | OP-7, ADP-11, CH-16 | Read an edited draft's text as the owner's correction. |
| GR21 | **Intent values for learning (W3-values; security V1 on W3 step 3).** `Config.Observe` is shown each intent the policy authorized (`PhaseAuthorize`, after the check passed, so an asked intent only after the owner's YES), as the guest wrote it, before the journal redacts it: a deep copy, never for broker-state intents. It must not block, and a panic in it is logged and changes nothing. agentosd keeps the values of guest intents only while learning is on, for the skill compiler only (agentosd's task-value record; compile K12). | LOOP-4, CAP-5, OP-7 | — |
| GR22 | **Owner questions on the request budget (W9, question Q3; PQ5 on #95).** `Reserve(aged)` takes one text of `RequestsPerHour` for an owner question, on the gate's own clock, counted in the same step as the check. Approval requests go first: while a batch waits it refuses, except that a question its book marks aged (held unsent for `question.Config.AgedAfter`, an hour) goes ahead once an hour. The budget still bounds it, so under steady approval traffic approvals keep at least 2 of the 3 texts, and no question waits indefinitely while its guest stalls. An aged reservation with no batch waiting is an ordinary one and spends no turn. The turn's time (`agedAt`) is kept in memory only, so a restart allows one more aged pass in that hour (L3 S1 on #125). Questions carry no authority (question Q8), so letting one ahead grants nothing. | CH-15, CAP-10 | Size the turn by measurement: the book logs how long each question waited for its text. |
| GR23 | **Recall rollbacks (recalltool W10).** `meta.recall.rollback` is admitted only from origin `broker:recall` with executor `recall`, and always asks the owner: a low-tier text, verb "forget", with the line recall wrote from broker-known facts (the deleted item's kind, the agent, its restore point, how many actions it carried out since). It runs only on the owner's YES; NO or a lapse closes it, the owner's NO with the reason "not approved: owner", which recall tells from no answer. Guests, the owner and the local page cannot submit one. `Withdraw` closes one still waiting as "not approved: superseded" when recall asks an earlier question for the same agent; nothing else can be withdrawn, and an answer to it later runs nothing. While a lineage still holds a record the owner deleted (`Config.Contained`), no pre-allowance acts for its intents: each irreversible one is asked. | CAP-3, OP-5, ADP-9 | — |
| GR24 | **Evidence destination (CH-20).** `meta.evidence` sets or clears the one destination private agent replies go to. Only the owner (owner text or the local page) submits it. Setting it is high tier (`GrantChange`) with local-page confirmation, and is refused without the local page. Clearing it needs no code (security C3 on #148): agentosd first emails the old destination a fixed notice. The address must be one bare, lower-case address that `Config.Destination` says is a connected account's own (v1: the mail account's own address or a provider-verified alias, never the box's own mailbox), and the intent names that account. The destination is rebuilt from succeeded records like grants. `Config.Delivery` names each executor's delivery operation (mail `mail.deliver`, verb share): it runs without asking only from `OriginEvidence`, with exactly one recipient equal to the destination, only a body and its author (`from`: agent or box), on the destination's account under a live grant that names the operation as share, while `Destination` still says the address is that account's own, and at most `DeliveryCap` (30) in any 24 hours (security C5), counted from the journal. The journal keeps the delivery intent, but agentosd's journal redactor (the daemon default) stores every free-text param as `[redacted]`, so no reply body is journaled (security R1 on #148). Once the vault's redactor replaces it (GR15), bodies would be journaled clear of vault values only: CH-20w keeps them out or redacted. Under the same default redactor the destination's own params read back as `[redacted]`, so like a grant (GR15) it does not survive a restart until then; nothing can set one in this build. Every other form, and every other action from `OriginEvidence`, is denied. | CH-20, CH-10, ADP-9 | A cloud-folder destination, and more than one destination, are later spec work. |
| GR25 | **Loop 2 containment (W5a, loops K-S2).** `meta.grant.pause` is admitted from origin `broker:loop2` (`OriginLoop2`) as well as the owner; revoke stays the owner's, and resuming is a grant change with its code and local confirmation. Only agentosd submits from that origin, in-process (security L1 on W5a): guest intents carry `guest:<lineage>` and guests cannot request `meta.` actions (`guest/mcp.go`, `TestAGuestCannotClaimTheLoop2Origin`), and `TestOnlyTheDaemonUsesTheLoop2Origin` fails any other package that names or spells it. Each pause records the check and finding behind it (`finding` param, L2). Pausing only narrows and is exempt from STOP (journal A9). `Config.Unpaused` is told when the owner ends a pause by resuming or revoking the grant, and for each pre-allowance a revoked connection takes with it (L3 S1 on #169), outside the gate's lock and never on replay, so Loop 2 stops listing it; at start agentosd reconciles Loop 2's list against `Grants` (loops S4). | LOOP-9, ADP-9, OP-5 | Executors get a pause intent of their own. |
| GR26 | **Following a fork (OSS-10; Security C6).** `meta.update.follow` (`FollowIntent`) asks to take updates from another root of trust, or to switch back. It is admitted only from the local page's origin (`local`): an owner text, a guest, the broker's own routes and every other path are refused. It carries no params: the journal redacts params (the daemon's redactor turns each into "[redacted]"), so the owner's name for the source and the digest ride in the intent ID, `follow/<nonce>/<digest>/<name>` (`FollowID`, read back by `FollowOf`), as a forget's goal does (OSS-10w; params would have been denied as malformed in production). The name is empty to switch back ("get updates from the AgentOS project again"), and the executor enforces WF1 for it; otherwise it is the owner's name for the source (1 to 40 printable characters, no control or bidi characters, no surrounding space, and at most `MaxFollowDigits` = 4 digits in any script, so it can carry a year but never a 6-digit code, spaced or not; Security R1 on #180) ; the digest is the 64-hex digest of the root summary the page showed (`update.RootSummary.Digest`), with executor `update`. It is a tier-4 act: a high-tier request (kind grant change, verb "follow") naming only the owner's name, which needs the code-generator code and `ConfirmLocal`, and it is refused outright without a local page. It is not narrowing, so it waits out a STOP. One intent runs once, so one approval buys one switch. **For the wiring:** the updater's executor calls `update.Store.FollowRoot` with the root bytes the page holds for that digest (refusing any other), records the switch in the journal (the intent is the audit entry), and sends `maintain.FollowAlert` at once. **Wiring conditions (Security, #180):** WF1: an empty name (switching back) is admitted only for the project's own root chain: the executor compares the root's root-role keys against the root the image ships and refuses an empty name for any other; WF2: `update.Options.Now` comes from the HOST-1b clock guard's `Latest`, never the raw wall clock; WF3: the follow intent needs a P2-2w L1 session token on the local page. **Built (OSS-10w):** `broker/follow` is the executor (WF1 compares root-role key material, type, scheme and public value, never the key IDs a root claims; WF2 takes `Now` from `Latest` once per attempt; Reconcile reports done only when the box trusts the held root under the intent's name, and alerts again, at least once); `localsrv` `page_follow_root` and `page_follow` need a live session token (WF3). `follow.Route` shares the `update` executor name with release activation. agentosd wiring is OSS-10w part 2. | OSS-10, CH-3, CH-10 | — |
| GR27 | **Page result for a changed release adoption (P2-2a f2).** The "changed after my Wi-Fi page showed it" notice (P2-2a f1) ends "Make the request again if still needed." for every page-confirmed item the owner asked for. A release adoption the pipeline proposed (`meta.change.*` with Origin `change`) is page-confirmed too, but the owner made no request, so its notice ends "I will ask again if it is still needed." That promise rests on `change.Decided`: the gate passes `declined=false` for this close (the reason is not "owner"), so the proposal drops with no decline recorded and the next update check (UPD-5, `maintain`) proposes it again. The origin test reads the journal intent, as the gate already does for `Decided`, and names the pipeline origin as the string `"change"` because the gate does not import `change` (ARC-2). | CH-12, UPD-5 | Add an owner-triggered update check, then name it in the notice. |
