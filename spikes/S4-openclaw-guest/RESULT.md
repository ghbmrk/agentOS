# S4 result: OpenClaw runs unmodified as a guest

**Answer: yes.** OpenClaw 2026.9.8 (`fc23bc8`) ran with no network except one loopback stub broker. Within that setup it:
- used broker-provided model access with a placeholder key;
- called a broker tool;
- ran `exec` locally;
- took owner messages through its own HTTP API.

All of it was set up through its config file. **No source patch was needed, so there is no ARC-3 fork record.**

Three seams need broker-side design rather than a patch:
- The broker must cap model spend (finding 2).
- The broker tool is reached through OpenClaw's tool search, not offered directly (finding 3).
- The gateway sometimes resolves `clawhub.ai` (finding 7).

## What ran
Every run used `unshare -n` (only loopback) and `strace`. The later runs also used a mount namespace whose `/etc/resolv.conf` points at a logging NXDOMAIN sink (`dns_sink.py`). Per-run tracing and config differences are listed in [EVIDENCE.md](EVIDENCE.md).

The stub broker [`stub_broker.py`](stub_broker.py) serves two things:
- an OpenAI-compatible endpoint, with a scripted model, that rejects any key except the placeholder;
- an MCP server with one tool, `effect_request`.

Its tests are in `tests/test_s4_stub_broker.py`. [EVIDENCE.md](EVIDENCE.md) has the per-run summary (model calls, broker tool calls, every `connect()` destination, DNS names), generated by `summarize.py` from the raw logs.

Cloud VM: 4 vCPU, 15 GB RAM. Node 24.21.0. The model is a stub that answers instantly, so these times are OpenClaw's own overhead.

## Findings and surprises
1. **The real boundary is the network, not the config.** The guest is root with `exec` (REV-1), so it can rewrite its own config, install plugins, or call `openclaw update`. The deny list and the off switches only reduce noise and accidents. Containment comes from the agent machine allowing only broker sockets (spec §4), and from ARC-4 rebuilds. Read-only config (`OPENCLAW_CONFIG_READONLY=1`) and `gateway.reload.mode:"off"` add friction.

2. **OpenClaw has no turn or tool-call cap; a runaway is bounded only by wall clock.**
   - **Reproducible run.** `SCENARIO:loop` makes the stub's model call `exec` forever. OpenClaw kept going: 156 model calls in 240 s (`loop1`, EVIDENCE.md), until the script's `timeout 240` killed it.
   - **What does bound it.** The only built-in bound is `agents.defaults.timeoutSeconds`. It was not set in these runs, so the default applied: **48 h** (`DEFAULT_AGENT_TIMEOUT_SECONDS = 48*60*60`, src/agents/timeout.ts:13). Setting it to `0` means no limit. `tools.exec.timeoutSeconds` bounds a single command only. The config schema has no turn or tool-call limit [schema search for max/limit × turn/iter/step/tool/loop].
   - **The earlier observation.** An earlier, uncommitted stub version mis-parsed OpenClaw's trailing context message (now covered by a test) and looped the same way, reaching 2,275 messages before it was killed. The "2.67 M tokens" figure from that run is **OpenClaw's own estimate**, printed in its `insufficient_output_budget … effectiveContext=128000 estimatedInput=2677992` warning, not a measured count.
   - **The context window is exceeded, not refused.** In that run OpenClaw kept sending requests about 20× over the configured 128 k window. Its OpenAI-completions transport only throws `context_length_exceeded` for reasoning models. For other models it logs the warning, clamps output, and **sends anyway** (packages/ai/src/transports/openai-completions-params.ts:526-540). A real provider would probably reject those requests, so the loop would likely end in errors rather than unbounded spend, but nothing on the guest side guarantees that.
   - **Conclusion.** Spend must be bounded at the broker's model egress, the one point a self-reconfiguring guest can't bypass (OP-8 below).

3. **Broker tools are reached through tool search.** The model sees `tool_search`, `tool_call` and `tool_describe`, not `broker__*` directly. It takes two hops, search then call, which is one extra model call per effect. The search result showed the tool's input schema as `"unknown"`, so a real model may also need `tool_describe`, a third call. A follow-up should check whether config can promote MCP tools to the direct surface. Not verified.

4. **Name collision.** OpenClaw has a built-in tool named `intent` (memory-core "standing intents"). The MCP prefix (`broker__`) avoids a clash, but the broker vocabulary should not rely on the bare word.

5. **Credential traps inside the guest:**
   - The `secrets` tool asks the human for credentials and stores them in the guest.
   - OAuth provider logins and MCP `auth:"oauth"` keep refresh tokens in `state/openclaw.sqlite`.
   - All of these must stay denied or unused (CRED-1). Never run `openclaw onboard` with real logins inside a guest.

6. **Tool results come back wrapped as `EXTERNAL_UNTRUSTED_CONTENT`.** That includes broker results. It's useful injection hygiene, and the broker should not count on its text being read verbatim.

7. **The gateway sometimes resolves `clawhub.ai`.**
   - **What was seen.** In g2–g4 the gateway sent AAAA queries for `clawhub.ai` (decoded from strace's `sendto` payload). In g1 it tried the host's 8.8.8.8 and 8.8.4.4 and failed before sending, so that name is unknown; likely the same lookup [inference]. g5, gp1 and gp2 did no lookup.
   - **What it means.** It is intermittent at startup, and the hardened config doesn't stop it. I didn't identify the calling code path. Under default-deny it fails closed, but a guest image should also set `OPENCLAW_CLAWHUB_URL` to the broker or to an unroutable address (INVENTORY §5).
   - **Gap in the evidence.** The DNS sink logged nothing in g2–g4 even though queries reached it, and its stderr wasn't captured then (the scripts now capture it). So "the sink saw no queries" is not evidence; the strace columns in EVIDENCE.md are.

8. **npm skipped the install scripts** (npm's `allowScripts`), including OpenClaw's `postinstall-bundled-plugins`. Nothing the spike used was missing. The image build should decide this explicitly.

9. **Footprint matters at the floor (HW-4).** One gateway after a turn is about 1.54 GB PSS, plus 735 MB on disk, plus a 27 s cold start. On the 8 GB N95, once the host, broker and local inference take their share, that leaves room for roughly 1–2 concurrent OpenClaw machines [inference]. That feeds S3's density numbers and CAP-1's N.

## Proposed SPEC.md diff (for v0.12; L1 to merge, Mark approves)
```diff
 - **ARC-3** Agent runtimes MUST run unmodified where their tool/plugin interfaces suffice. A runtime fork is permitted only with a recorded "interface X insufficient because Y."
+  - Qualified (S4, OpenClaw 2026.9.8): unmodified, config only. Record per qualified guest version.
+- **ARC-5** The broker's guest interface is: (a) model access as a standard provider endpoint where the guest holds only a placeholder credential (OpenAI-compatible chat completions qualified by S4; other provider APIs only once qualified); (b) broker tools over MCP (streamable HTTP); (c) owner messages delivered into the guest's own inbound API.
+  [Design decision, not an S4 result: guests use no guest-side channel plugins. S4 shows only that OpenClaw doesn't need them.]
+- **ARC-6** Guest configuration is defense in depth only. Containment MUST hold with a guest that rewrites its own configuration (root inside, REV-1).
 ...
+- **OP-8** The broker's model egress MUST meter every model call by originating agent machine and charge it to that machine's task reservation (or a per-machine rolling cap when no task is bound). On exhaustion, egress refuses further calls for that task and reports to the owner; raising a limit is a budget-change intent (OP-5). Limits hold regardless of guest configuration (ARC-6).
+  Rationale (S4): guests may loop, bounded only by wall clock (OpenClaw default 48 h).
+  Notes for L1: attribute by agent-machine identity at the socket, never by a guest-presented token (that would be reusable auth material, CRED-1); count calls and tokens at the broker, not from guest-reported usage (consumer relay routes may report none). Placement beside the budget/RES rules may fit better than §9, since model calls are not intents.
 ...
 - **CRED-1** ... readable by any model-directed process.
+  Guest profiles MUST disable credential-acquiring guest features (e.g. OpenClaw's `secrets` tool, in-guest OAuth logins).
```
For S3 and HW-4: budget about 1.54 GB PSS per OpenClaw machine when sizing CAP-1 at the floor.

## Reproduce
```sh
# Node >= 24.16 on PATH; root for unshare; strace installed
npm install openclaw@2026.9.8 && export OPENCLAW_BIN=$PWD/node_modules/.bin/openclaw
spikes/S4-openclaw-guest/run_guest.sh   /tmp/s4/a    "SCENARIO:effect_request go" --agent main --session-id a
spikes/S4-openclaw-guest/run_guest.sh   /tmp/s4/loop "SCENARIO:loop" --agent main --session-id loop
spikes/S4-openclaw-guest/run_gateway.sh /tmp/s4/g    "SCENARIO:exec go"
python3 spikes/S4-openclaw-guest/summarize.py /tmp/s4 a loop g
```
Each output directory holds:
- `broker.jsonl`: every request the broker saw;
- `dns.jsonl`: DNS queries, when there were any;
- the strace log;
- `time.txt`;
- the reply.
