## Review (c33cb5d, round 1, Potency, UX and L3 combined record)

Verdict: CHANGES. Comment: https://github.com/ghbmrk/agentOS/pull/1774#issuecomment-6182406878

#### Potency/UX/L3 review (tier A)

Head: c33cb5d6b5437383c5099796dff8b3980139ff00

Verdict: CHANGES

**Potency.** The fix covers #1558's acceptance: `takeLockout` is the only path that gives the TPM a new authorization. `enroll` calls it only when a PIN is set. `ReleaseLockout` (`giveBack`) only reads the stored value, and nothing else calls `tpmseal.TakeLockout`. `Vault.Sync` runs after both `keepDAOriginal` and `Put`, so the DA-original entry is made durable as well. The order is right: on a sync error the function returns before `TakeLockout`, and before `enroll` registers its `giveBack` defer, so the TPM is never touched. A held entry is not deleted. If the delete itself does not survive a power cut, the next enroll reuses the leftover entry as held, and `TakeLockout(held, !set)` sets it normally.

`go test -race ./cmd/agentos-egress ./vault` passes. `tools/doclint.py` exits 0. The ASSUMPTIONS ID S2-3 is the correct next ID.

Mutants (only the new test, plus the vault package):
- Remove the `v.Sync()` call (trusted.go:830): killed.
- Drop the `v.Delete(name)` on the sync-error path: killed.
- Remove the RLock in `Sync`: survives. This is acceptable, because `syncDir` touches no vault state.
- **`Sync` returns nil instead of `v.syncDir()` (rollback.go:336): survives.** See B1.

**Blocking**
- B1, broker/vault/rollback.go:330-337. The real contract of `Vault.Sync` (it syncs the vault file's directory and returns that error) is not tested anywhere. `InjectSyncFault` short-circuits before the real sync, so a `Sync` that never syncs passes every test, and that is the durability this PR exists to add. Fix: add a vault-package test. The existing `syncFails(t)` helper (dirsync_test.go:341) swaps `syncDir` to fail. The test asserts that `v.Sync()` returns an error wrapping `durable.ErrDirSync`, and nil once the helper is restored. Optionally it also records the path it was handed and checks that it is `filepath.Dir(vault path)`. Name it for behaviour, e.g. `TestSyncReportsAFailedDirectorySync`.

**Non-blocking**
- N1 class:later, UX. Message on a sync failure during a PIN enroll. The owner gets `errHostNotSaved` ("could not make this PC trusted; nothing was changed"). Two problems:
  - In the real failure mode the drive's directory sync is failing. The earlier `Put` (and the `Delete` that undoes it) then go through `landed` (vault.go:328), so the owner channel has already said "this change is saved, but a power cut before the next change could undo it", possibly twice, just before "nothing was changed". That is contradictory.
  - Neither message gives a recovery step. #1734's messages do (for example "run trust -pin again and enter the same PIN"). Suggestion: map a `durable.ErrDirSync` from `enroll` to a message such as "could not make this PC trusted: the drive did not confirm a save, so the boot PIN was not set up. Nothing on the TPM was changed; try trust -pin again, and if it keeps failing, check the drive." Also consider muting the landed warning for the undo `Delete`.
- N2 class:later, docs. The doc comment on `takeLockout` (trusted.go:794-797) still says only "stored in the vault first". Add "and synced (Vault.Sync)" so the invariant can be read where it is enforced.
- N3 class:later. S2-3's "a sync that is slow or fails on this drive blocks PIN enroll" also applies to re-enrolling with an already-held authorization, even when the TPM already has it. This is fine and stated; noted only so the scope is explicit.

**L3.**
- `REQ: HW-8` marker is present; TRACE.md is correctly left untouched (generated).
- The test name describes behaviour.
- `InjectSyncFault` follows the `InjectSealFault` pattern, including the `testing.Testing()` guard.
- No dead code.
- PR body trace table and Defect line are present.
