## L3
**Correctness: correct.**
- `childproc` runs `OnCancel` inside `exec.Cmd.Cancel`, and `Wait` does not return before the watchCtx goroutine has finished it. So the kill is registered before `gvisor.Exec` returns.
- The kill is also registered before `Manager.awaitExec` abandons the call after `ExecGrace`, because `OnCancel` runs when ctx ends.
- Every path that starts a new incarnation goes through `stopRuntime` and then `Runtime.Kill` first. That covers `restartLocked` (Rollback), Rebuild (`vm.go:1737`) and a failed launch (`launch` calls `r.Kill`). This matches the V37 assumption.
- Taking the group out of the map before `Wait` avoids reusing a WaitGroup while a `Wait` is still in progress.
- `go vet` is clean.

**Tests**
- `go test -race -count=10 -run TestKillWaitsForPendingExecKill ./vm/gvisor/` passed 10/10 in 6.8 s.
- `go test -race ./vm/...` passed: vm, vm/gvisor and vm/overlay.
- The test is ordered by a gate file, not by sleeps. Its only timing assumption is that `Kill` hasn't returned within 500 ms. That can only produce a false pass, never a false failure, so it isn't flaky.

- **Later L1: the ordering invariant isn't pinned.** The invariant that matters is that the kill is registered before Exec returns, and a refactor that registers inside the goroutine (M4) passes. I also tried a white-box check that `r.pending["wk-1"]` is set when `Exec` returns, and M4 still passed 10/10. The goroutine wins the race in practice. Pinning it needs a seam, for example a test hook between `OnCancel` and the `go`, or a comment marked load-bearing.
- **Later L2: the 5 s bound isn't tested and isn't strictly hard.** `r.run` uses no `WaitDelay`, so a `runsc kill` child that kept stderr open could keep `Wait` and the Kill wait past 5 s. That is unlikely for `runsc kill`. Even so, V37 says the wait "is bounded by `killExec`'s own 5 s timeout", which holds only for the process itself.
- **Later L3: there are small doc mismatches.** M3 and M5 aren't covered by tests, and the comment on `waitPendingKills` says "Each killExec is bounded by its own timeout, so the wait is too", which has the same caveat as L2.
