## L3 findings (all later)

**L3-1. `PutMany(nil)` or an empty slice still saves.** It writes the file and advances the rollback counter while changing nothing (checked with a probe test: err=nil, writes=1). No caller passes an empty slice today. Fix: return nil, or an error, when `len(items)==0`.

**L3-2. After a save fails post-rename, memory and the drive disagree. This is pre-existing and also true of `Put` on main.** When `writeFile` errors after the new file is in place (a failed directory sync), `PutMany` rolls memory back to the old values while the drive holds the new ones. A probe confirmed memory==new:false and drive==new:true. For a Wi-Fi/setup rotation, the owner is then told "nothing changed" and the display is erased. A restart before the next vault write brings up the new card, which the owner never printed. The next write heals the drive back to the old values. The PR's doc comment and R15 say "in memory and on the drive, holds all of them or none", which holds for each side on its own but not for the two together. `TestPutManySaveFailsAfterRenameIsWhole` checks only the drive. The PR keeps the atomicity it claims, so this is not a blocker. Suggested follow-up: decide which side wins (for example, keep the new values in memory when the rename landed, or fail closed), and state it in R15.

**L3-3. The recovery crash-point tests only inject failures before the write.** `failingCounter` fails `Read` at the start of `advance()`, so no boundary fails after the rename or at the post-write `Increment`. Because a store is now a single atomic file replace, the pre-write state is the same as the crash state, so the claim holds. The post-rename case is covered only at the vault level (see L3-2). Optional: add a `writeFile`-after-rename point to the rotation sweep.
