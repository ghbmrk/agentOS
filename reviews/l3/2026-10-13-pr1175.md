## Points

- **S-R1 (release; REC-4, #1090 R1).** Commit and cancel are not bound to the rotation they belong to. A late commit can be applied to a newer rotation (a review probe stored card A's values under rotation B), and a stale cancel can drop a newer one. Fix with a rotation ID from begin. Details are in the Security record.
- **U-R1 (release; REC-4, CH-12).** No path shows the new code generator again once the done page has been shown or skipped. The text promises one. Details are in the UX record.
- **L-l1 (later).** `commitTimeout` (2 min) is not the real limit. `UnlockClient`'s `http.Client.Timeout` is 60 s and fires first. L38 and the comment in `rotwire.go` overstate the limit. A slow recovery-key re-encryption would end on the in-effect path, which is safe, and the done notes and QR would be lost. Use a client with no fixed timeout for the commit, or correct the text.
- **L-l2 (later).** The unknown-outcome mapping is tested only against the fake vault (`TestRotationCommitWithNoAnswerIsInEffect`). Add a real-socket case, such as a listener that closes after reading the commit body.
- **L-l3 (later).** In `beginRotation`, any error other than the named ones on a passphrase or recovery rotation becomes "needs the current one from the card" (403). An internal failure, such as a vault I/O error, would then read as a wrong proof. Map only the proof-check error there, and send the rest to `errInternal`.
