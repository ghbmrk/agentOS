## Threat check

Actor: an untrusted guest (deny-all is its normal state). Asset: STOP's promptness (CH-2) and the broker's memory bound (the brief's goal). Path: the guest picks `request_id`, so it can resubmit an id the broker refused long ago. The PR answers an evicted id by reading and decoding the whole journal (`Submit` → `journalEntry` → `readJournal`; on `ErrConflict`, `guest/mcp.go:325` then calls `Get`, a second full read). `FileStore.ReadAll` holds the store mutex for the whole `os.ReadFile`, and STOP's `commit(RecStop)` needs that mutex for `Append` while holding `e.mu`, so STOP queues behind every cold read in flight. Each read also allocates the journal plus its decoded records. The per-machine bucket (burst 20, then one per 3 s) caps this per machine but not across machines, and the journal never shrinks. Before the PR this resubmission was an O(1) map hit.

## Fix-list

1. **blocker** (CH-2; brief goal and acceptance: bounded memory under deny-all, STOP independent of settled history): a guest-reachable lookup of an evicted denial (`Submit`, and `Get` on the conflict path) must not read the journal. One shape that works: keep a 16-byte hash of the entry's `fp` with its cold key, so Submit decides same-or-conflict without the journal and returns a minimal `Denied` status. Add a test with a counting store asserting a resubmitted evicted id causes zero `ReadAll`, plus STOP latency under concurrent resubmission like the probe above.
2. **blocker** (ASSUMPTIONS accuracy, OPERATING §5): the new ASSUMPTIONS bullet says cold `Get`, `Submit`, `List` and `Between` scans "do not block STOP". They do, through the store mutex. Correct it to what the fix guarantees, and correct the PR's Findings line, which calls the journal-reading paths owner-only.
3. **blocker** (mergeability): merge main and resolve the LATER.md conflict.
