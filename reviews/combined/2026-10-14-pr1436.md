### Checks

**Does the default match D-115?** Yes.
- D-115 says "Plan routes default yes" and "Private hosted keeps no". SPEC §8.1 step 6 asks "one thing per plan".
- In `boxLocked` (setup.go:1036), the box is ticked only when `form == "ai-device"`, which is the plan sign-in. The API-key box stays unticked.
- Private hosted routes are added only on the local page (CAP-9), so this setup page has no box for them. L12 says so.

**The builder's API-key call.** This matches D-115's text.
- D-115, the DECISIONS row, CAP-9 and Mark's 21:53:58Z message ("default yes on private for plan") all say "plan".
- None of them names frontier API-key routes.
- So keeping the previous default of no for API keys is the literal and narrower reading.
- The PR body already lists the question for Mark as a later recheck. A one-line change would flip it if Mark wants it.
- D-117 (Grok and Muse are plan-only) does not change this.

**Is the answer saved only after the key is stored or the sign-in has started?** Yes.
- `aiKey` calls `privateOK` only after `ConnectAPIKey` returns nil.
- `aiDevice` calls it only after `StartDeviceCode` returns nil and the link passes the https check.
- When a form does not go through, `keepAnswer` writes only the in-memory `answer` map. That map is display-only, is cleared on restart and is bounded, because `providerHas` runs first.
- The key path is tested: mutants M3 and M4 are killed. The device path is not: M5 and M6 survive (L2).

**Can a page or a forged request flip the consent?** Not through this PR.
- Every setup POST passes the Host check (DNS rebinding), `sameOrigin` (Sec-Fetch-Site and Origin), the SameSite=Strict setup cookie, and `mayLocked` (L9). L9 means only the phone that paired can post the AI step.
- The CSP sets `default-src 'none'` and `form-action 'self'`.
- Setup forms do nothing once setup is done. After that, allowing private content on the AI providers page still needs sign-in and a code.
- #1385 (a compromised page process forges "claimed") is a stronger capability than flipping consent: such a process could call `page_setup_private_ok` anyway. This PR adds no authority to the page process. The `answer` map never reaches the vault.
- The one consent-integrity gap is the page's own default overwriting a provider-wide answer (R1). That needs the owner's own submit, not a forged one.

**Is the wording true?** The new line is "Let <Provider> see your private content: mail, documents, chats, and anything made from them. Your passwords and keys are never shown to it."
- It names the provider, as the #1403 comment asked.
- It is the owner line that #1424 itself proposes.
- How credentials actually flow:
  - A typed key goes to `Hooks.ConnectAPIKey`, then the vault process. It is not kept, echoed or logged (L12).
  - The egress proxy injects the key, and a broker-held plan login (CRED-5), only into that provider's own declared endpoints, as authentication.
  - A guest machine never holds either one (CRED-1, Invariant C).
- So "never shown to it" is true for the box's own credentials, as content. It has two caveats, both carried as L3:
  - (a) The provider does receive its own key or login as authentication.
  - (b) A password that sits inside mail or a document (a password someone mailed, a reset code) is content, so a model allowed private content can see it.

**Is the device-code render fix safe?**
- The builder's diagnosis is correct. In Go templates `{{with}}` on a `[2]string` is always true, so the sign-in form never rendered.
- The new `{{$d := index $.Device .ID}}{{if index $d 0}}` is correct, and mutant M11 is killed.
- XSS or URL injection: I probed the template with the link `javascript:alert(1)"><script>` and the code `<img src=x onerror=1>`. html/template rendered `href="#ZgotmplZ"` and escaped text for both.
- Behind that, the server-side https check (now folded into `err`) and the CSP stop anything else.
- The link's host is not pinned to the provider's auth host, and the "This code is from <provider>, not from your code generator" label (§8.1 step 6) is missing. Neither is new: both are already c4e2 (#1264) acceptance (the host check comes from #1014). Device-code sign-in is still not served (L43).

**U-5.** `NoneAllowed` is set only when no *connected* provider has `PrivateOK`. That is correct, and M10 is killed.

### Findings

**R1. Release (CAP-9, D-115, §8.1 step 6; lands with c4e2 #1264). A key's unticked default undoes the plan's yes for the same provider.**
- The answer is stored per provider: `SetPrivateOK(id, ok)` goes to `page_setup_private_ok`, then the vault.
- The default, though, is per route.
- While a plan sign-in is pending, the page still shows that provider's API-key form, with its box unticked.
- Probe (a scratch test, not committed):
  1. `POST /setup/ai-device` with `private=1` records `private[anthropic]=true`.
  2. The page then shows `ai-key anthropic` unticked.
  3. Saving a key with the box as shown records `private[anthropic]=false`.
- The owner who left the plan box at its default yes ends up with no for that provider, without being told.
- This is not live: no provider reports `device_code` until c4e2. Codex (OpenAI) has both a plan and a key, so it becomes live then.
- Fix: the key box defaults to the provider's current answer, `checked = form == "ai-device" || p.PrivateOK` (`Provider.PrivateOK` is already in the list). Add a test that the sequence above keeps yes. The alternative is to key consent by route at c4e2.
- This could fold into this PR cheaply. Otherwise it must land before c4e2 serves device codes.

**L1. Process (not a code finding).** The tier is A, not C.
- `tools/risk_tier.py` prints A for this diff, because localui is on the tier-A list in OPERATING §3. The PR body's "prints **C**" is wrong.
- OPERATING §4 says tier A needs three things:
  - L3 on the strongest model with a threat check;
  - a UX and Potency lens screen;
  - Security in its own fresh session (stage 4a).
- This pass covers all four lenses, with a real security lens. The coordinator should decide whether a separate stage-4a Security sign is still owed, or record the deviation.

**L2. Later (U-4 test gap). The device-code failure path is untested.**
- M5, M6 and M7 survive. The https check had no test before this PR either.
- Add a test with three steps:
  1. `StartDeviceCode` returns an error, or an `http://` link.
  2. Check that `SetPrivateOK` is not called and no link is shown.
  3. Check that an owner who unticked the box sees it still unticked. The default is ticked, so this is the direction that matters.
- M8 and M9 (stale or restart answers) are low value. Cover them only if cheap.

**L3. Later (REV-6; rides #1424). "Your passwords and keys are never shown to it" has two caveats.**
- (a) The provider receives its own key or plan login as authentication. #1424 already covers this in SPEC wording.
- (b) A password that sits inside mail or a document is content, and an allowed provider sees it.
- Posted as a comment on #1424 (see Filed).

**L4. Later (UX, CAP-9; with #1422). Save failures and leftover copy.**
- (a) In `aiKey`, if `SetPrivateOK` fails after `ConnectAPIKey` succeeded:
  - the key is stored but the answer is lost;
  - the page says "Could not save. Try again.";
  - the provider is now connected, so the forms are gone and there is nothing to retry;
  - setup finishes on the next load.
  It fails closed (no private content), but the owner's tick is lost silently. Say "Key saved. I could not save your private-content answer; set it on the AI providers page."
- (b) A validation error (a malformed key, or `aiReady`) does not keep the answer, so a ticked key box comes back unticked. This also fails closed.
- (c) The AI providers page still says "may see your private data (mail, files) to do tasks". Align it with the new "private content: mail, documents, chats, and anything made from them" copy.

- The device line lacks §8.1 step 6's label "This code is from <provider>, not from your code generator". This is already in #1264's acceptance, so it is only a reminder that the line now renders.
