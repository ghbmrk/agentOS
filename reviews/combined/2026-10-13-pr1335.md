## Security

- **No deadlock.** `done` is closed only by the full-read goroutine (`defer close(done)`). On the ctx path that goroutine either returns from its `select`, or finishes the `Refresh` it is running and then returns. The goroutine never waits on Watch's loop: `kick` has a buffer of 1 and is sent with a non-blocking `select`. Watch holds no lock while it waits on `<-done`, and `Refresh` takes `p.mu` only briefly after `source()` returns. So nothing can cycle.
- **How long Refresh can block after ctx ends.** Refresh does not take ctx, so `<-done` waits as long as the `Config.Source` call that is in flight. In production that call is `Sources.Read`. Its router lookup has a 3 s `context.WithTimeout` (sources.go:55), and `ReadLocal` makes only local netlink/file reads. The wait is therefore bounded. A custom Source that never returns would block Watch's return forever, but before this PR that goroutine already leaked forever, so nothing is lost. Also, if `kick` and `ctx.Done` are both ready, the goroutine's `select` may pick `kick` and run one more Refresh after cancel. That Refresh has the same bound, and Watch waits for it, which matches the doc comment.
- **Production callers are unaffected.** Both callers run `go p.Watch(ctx, ev)` (resolver.go:49 and cmd/agentos-egress/netguard.go:46) and nothing waits on Watch returning. The only change they see is that Watch's own goroutine ends a little later, once any in-flight full read has finished. Policy decisions, the generation check and the events-closed path are unchanged. `go vet` is clean, and `go test -race -count=3 ./cmd/agentos-egress/` passes.

## Potency

- **The race is fixed.** On base 96253b8, `go test -race -count=50 ./netguard/` failed 2 of 4 runs with `DATA RACE`: the write is refreshGapHook at watch_test.go, and the read is at policy.go:248 from Watch's goroutine. With only the test half applied (PR tests, base policy.go), a run still races, which confirms the PR's claim that the policy.go change is needed. On head c141a6e, 5 of 5 `-count=50` runs pass with 0 races, plus 1 targeted `-run 'Watch|Refresh|QuickLearn|Stale' -count=50` run.
- **The test teardown is ordered correctly.** `defer func() { close(release); cancel(); <-watched }()` unblocks the slow `Source` before it cancels, then waits for Watch. Because it is deferred, it also runs on `t.Fatal`. The old `defer close(release)` and `defer cancel()` are removed, so nothing closes twice.
- **The doc comment matches the behaviour.** "When ctx ends, Watch returns only after that goroutine has, so no full read outlives it" describes the ctx path exactly. It does not claim anything about the events-closed path, which still returns at once and is left unchanged on purpose. The PR body explains this.
- **L1 (later): `WatchEvery` still leaves a `Watch` behind.** `WatchEvery` (resolver.go:47-59) returns on ctx end without waiting for the `go p.Watch` it started. `TestWatchEveryReplacesLearnedNetwork` (resolver_test.go:131) therefore can still have a `Refresh` in flight after it returns. That Refresh reads `refreshGapHook` at the same time `TestQuickLearnInRefreshGapIsNotOverwritten` writes it. The window is tiny: the test's Source is instant, and every test in sources_test.go and most of watch_test.go runs in between. No race showed up in 250+ iterations. A later fix could have WatchEvery wait for its Watch, or have the test hook load atomically.
- **L2 (later, noted in the PR):** when `events` closes before ctx, Watch returns without waiting, and its full-read goroutine keeps running until ctx ends. No production caller closes `events` except `WatchNetlink` on a socket error.
