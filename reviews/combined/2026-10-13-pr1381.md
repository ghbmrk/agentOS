## Security
**Does the real Codex login ever reach the worker or the sandbox?** By design, no, for runs:
- The worker holds a placeholder `auth.json` (#1015).
- The refresh override sends refresh to the forwarder, and the swap returns placeholders all-or-none, with the vault updated before release.
- The image has no `auth.json`.
- Tests and mutants pin "real token written into auth.json" and "release before vault update".

The gap is **sign-in**. #1264 says `codex login --device-auth` runs in a provider worker and "the token response passes through the egress swap". However, #1014 declares only the responses endpoint, the models list and the refresh. Only the refresh has a URL override, and nobody owns the device-auth endpoints or the swap of the first token response (finding 3). As written this fails closed, because the worker has no other route out. The risk is a builder "fixing" it by giving the sign-in worker network, which would put the real token in `auth.json`.

**Is the swap limited to the pinned OpenAI hosts?** Yes, for host and path:
- The per-worker listener forwards only declared method, host and path.
- Names resolve through netguard on every lookup, with a mutant against re-resolving at dial time.
- The guest-facing proxy keeps refusing CONNECT, with a regression test.
- Undeclared side calls fail by absence.

It is not limited by request body (finding 2).

**Does dropping the tunnel weaken containment?** For a broker-held CLI it mostly strengthens it. The broker reads every request, the worker holds nothing reusable, and the TLS/SNI and `SO_PEERCRED` questions from #1315 disappear. How the W controls map:
- **W1 (tools cannot read the login):** moot, since only placeholders are present. The kept tool-network cut stops a tool spending the plan with the placeholder.
- **W2 (volume holds the login only):** replaced by the vault entry under CRED-8.
- **W3 (inference-only scope):** replaced by ADP-10's declared endpoints, which are stronger than a token scope.
- **W4 (pinned tunnel):** replaced by request-level matching, except for its second sentence. The CLI's provider-side fetch tools were "off by managed policy". #807's Codex config lists plugins, MCP, analytics and auto-update, but not Codex's web search or other hosted tools. Those ride inside the one declared endpoint's body, so "fails by absence" does not cover them (finding 2).
- **W5 (clean sign-in, auth-host check on the shown link):** has no stated replacement (finding 3).
- **W8 (overage off):** dropped with "W1-W9 do not apply to Codex", but the money risk it covered also applies to a broker-held plan (finding 4).
- **W9:** kept in #1015.
- **W6, W7:** see finding 5 and later item 10.

**Is the Claude opt-in shape coherent?** Mostly. "The CLI holds its own credential and agentOS never reads or serves it" fits CRED-2, because the trusted base already includes the provider's CLI in worker-held mode. It also fits CRED-7, which pattern-scans output and does not read the credential, and W9, which deletes without reading. One clause breaks Invariant C: CRED-1's only exception is "a provider's plan login held worker-held under CRED-5 (W1-W5)". The new bullet exempts the Claude credential from W2's schema check. That leaves a Claude login inside the CRED-1 exception while it fails one of the exception's own conditions. D-114 and the PR body describe this as an open point "not settled here", yet the SPEC text settles it (finding 1). Two other conflicts are flagged on the PR and carried by #1380, and I agree with deferring them: W3 versus `setup-token`, and installing after opt-in versus CAP-11's image-only versions. I add the sign-in relay (finding 7).
