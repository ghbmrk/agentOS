## Security

Verdict: accept

Path: guest `ask` tool call, `Book.Ask`, a failed `persist`, `GuestTools.Call`, the machine. Before, the OS error (temp-file or rename path) reached the guest. After, the guest gets a fixed string, and the OS error goes to `cfg.Logf`, which is a broker-side log the guest cannot read (nil `Logf` is replaced by a no-op at construction, `question.go:348`). The rollback (`b.qs[:len-1]`) still runs under the lock, so a retry is not an `ErrConflict`. Structural, not procedural.

## Potency

Verdict: accept

The fix costs the agent nothing: the failure was an error before and still is, and the text now says "retry", which the rollback makes true.

1. **later (CAP-10)**: a store that fails persistently (disk full, bad directory) gives the guest the same "retry" text each time, so a guest may retry without end. Bound by the existing per-asker and open-question limits only once a question is stored, which a failing store prevents. Not a leak and not reachable by a security failure; a cap on consecutive store failures can wait until a real store fault is seen.
