## Security

The amendment changes when broker-held custody may be chosen, not how it works. The login stays in the vault process; the CLI holds a placeholder; injection happens only at declared endpoints (ADP-10); the refresh response is swapped back. **Invariant C holds structurally.** [Inference] If anything, the change improves security: a provider with silent terms can now take broker-held custody instead of being pushed toward worker-held, the one CRED-1 exception. The new risk is to the owner's provider account (a restriction), not to a credential, and the owner accepts it through recorded consent.

Adversary paths:

| Adversary | Path | Stop |
|---|---|---|
| Agent or injected content | Answering the consent ask for the owner | Structural, as long as the ask is an owner action on an authenticated channel. The spec doesn't name the channel (S1) |
| Provider | Changes its terms so a route that was permitted becomes silent | Recorded consent: the route stops until the owner is asked again |
| Provider | Refuses the login (account restriction) | Fallback to the API key route; the retry behaviour is CRED-5t |

- **S1 (release, CRED-5): the consent ask has no named channel or tier.** The spec says when consent is asked but not where. At connection it falls in §8 step 6, on the local page. When an update makes a route unconfirmed later on, the box is in daily use and the spec doesn't say whether the ask arrives by text. Proposal: the ask is a local-page or text item at the tier of other account-risk choices, and the consent record is journaled so a pause (CRED-5w) or withdrawal can cite it. UX cost: none, since it merges with U1. Potency cost: none.

## UX

- **U1 (release, CRED-5, §8 step 6): onboarding doesn't show the consent ask, and one of its lines becomes false.** Step 6 tells the owner "I use your plans first and an API key only when a plan runs out". For an unconfirmed plan without consent, the plan isn't used at all. The step's **Use the defaults** button must also not count as consent. Proposal: right after an unconfirmed plan's sign-in, show one plain line with two buttons, **Use this plan** and **Use my API key instead**. This choice stays outside **Use the defaults**. If the owner declines, the plans-first line names only the plans actually in use. Owner cost: one tap per unconfirmed plan, once.
- **U2 (release, CRED-5, ONB-9): the mid-life ask has no shape.** When a release makes a route unconfirmed, work moves silently to the paid API until the owner answers. The digest should say so once, in one line, naming the plan and the choice: "ChatGPT plan paused until you say yes; using your API key meanwhile." ONB-9's per-plan line on the Wi-Fi page shows the same state. This is merged with U1 and S1 into one proposed row.

## Potency

The change gains capability: a Codex plan route (plans before API keys, CAP-11), which was unavailable before. The only potency cost is the API fallback while consent is missing, which is the point of the gate. The no-API-key case is already carried as CRED-5f. No proposal.

## Arbitration

There's no conflict. S1, U1 and U2 point the same way: an explicit, journaled, owner-only choice in a fixed place. That improves both security and UX at no cost to potency.
