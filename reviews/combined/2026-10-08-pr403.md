## Security

| Adversary | Path | Stop |
|---|---|---|
| Prompt-injected agent | Reaches the router admin page, NAS, or cameras from a `public` machine | Structural: DEV-2 Out, checked on the connected address (closes REV-5's open LAN egress) |
| DNS rebinder | A name that resolves to a LAN address on its second lookup | Structural: connect-time check, names resolve only through the broker (DEV-2, A14) |
| Hostile LAN device | Impersonates a pinned device to collect its credential | Structural for verified devices (DEV-3); for unverified ones stated as exposed, with public content and no `actuate-physical` |
| Hostile LAN device | Compromises a Matter, ONVIF, or IPP stack | Procedural: one credential domain per executor, root key in the vault, §11 qualification (risk 17) |
| Device or agent | Fakes urgency through an event | Structural: urgency only from owner rules over verified devices (DEV-8) |
| SIM swapper | Approves low-tier device steps | Bounded to the household (risk 23). The stated "cannot start tasks" is wrong inside an unlock window (S1) |
| Number spoofer | Disconnects a device an owner urgency rule depends on | Not specified (S3) |

- **S1 (blocker, CH-10, risk 23): risk 23 says a SIM swapper "cannot start tasks (CH-14)"; inside an unlock window they can.** CH-3 lets task chat run from the owner's number while a session is unlocked within the last N days (default 7), and risk 13 already says a swapper can chat in that window. So a swapper inside the window can have the agent ask for any low-tier device step (private mail read aloud on a `local-only` household speaker, `actuate` grants, vendor-cloud cutoffs) and approve it with the texted codes they now receive. The residual harm stays in the household, so the tier choice holds. But the risk Mark is asked to accept rests on a false premise. Fix: "Outside an unlock window they cannot start tasks (CH-14); inside one (risk 13) they can, and these effects still reach no one outside the household and are bounded, undoable, or reduce exposure." UX cost: none. Potency cost: none.
- **S2 (later, DEV-2, DEV-3): DEV-2 allows only "pinned endpoints", while DEV-3 says a device's "address may change".** Read literally, a moved device would be unreachable, or an executor might send a hub token or device password to whatever now holds the old address before it checks identity. Proposal: the executor follows a moved device only through passive discovery (DEV-2), and sends no credential before the identity check (the TLS key pin or Matter CASE). For an unverified device, its credential is already stated as exposed. This rides DEV-p1's brief, with a one-clause L1 diff then if the brief can't settle it. UX cost: none. Potency cost: none.
- **S3 (later, DEV-10, DEV-8): "Revoke a grant or disconnect a device: one text from the owner's number" lets a spoofer silence a safety rule.** CH-11 lets revoke run without a code because its worst case is a pause. But disconnecting a smoke alarm that an owner urgency rule watches stops the alert that rule exists for, and reconnecting it needs tier 4. Proposal: by text, disconnect only revokes the device's grants. The pin and the event subscription an owner rule uses stay until the owner removes the device on the local page, and the confirmation says which rule still watches it. This rides DEV-p2 (events). UX cost: none (revoking still takes one text). Potency cost: none.
- **S4 (later, CH-18, CH-11): SMS doesn't guarantee delivery order.** The separate `Code <digits>` text can arrive before a multi-segment request, and a bare code approves. An owner who copies it back at once approves a low-tier request they haven't read. The request is broker-rendered and low risk, so this is minor. Proposal: the qualification that CH-18 already marks [Unverified] also records delivery order on both phone apps. If order inverts in practice, the code text adds the request ID (`Code 482113 for A7`), which CH-11's "copied whole" rule already accepts. UX cost: none. Potency cost: none.

## Potency

- **P1 (blocker, DEV-2): "exactly two exceptions" removes capability the spec still promises, and leaves the box's own name resolution undecided.** No component may reach an RFC 1918 or uplink-prefix address except a device executor and the compute-host proxy. That rule also refuses:
  - the broker resolver's upstream when the home network assigns the router as its DNS server, which is the usual case (Go's default resolver reads `/etc/resolv.conf`). DEV-net-a's hook on every dialer would hit this first;
  - BAK-1's "encrypted upload to storage the owner already has" when that storage is a NAS on the home network, which §1 lists as optional and which DEV-11 reaches only as a device executor, not as the backup component;
  - a CAP-9 private hosted route the owner runs on a home-network machine (a desktop with a GPU), unless the owner re-adds it as a CAP-13 compute host, which carries different semantics.

  None of these needs agent reach, so none needs the agent-side allowlist that D-069 rejects. Fix (resolution in [arbitration](../arbitration/2026-10-08-pr403.md)): the exception list becomes (1) a device executor to its own devices' pinned endpoints; (2) the egress proxy to a compute host's declared endpoint (CAP-13); (3) the broker's resolver to the resolver the network assigns (DHCP or RDNSS), DNS only, answers still checked at connect time; (4) a broker component to an endpoint the owner pinned on the local page (tier 4): an off-box backup target (BAK-1) or a private hosted route (CAP-9), TLS or pinned key, never reachable by an agent. Also add a sentence that the host's own link configuration (DHCP, router and neighbour discovery) is not a connection under this rule. A14 gains one clause: an agent machine reaches neither the assigned resolver nor a pinned backup or hosted endpoint. Security cost: neutral (no agent reach; each endpoint is pinned and owner-confirmed). UX cost: none.
- **P2 (later, CAP-2, DEV-11): `public` machines lose LAN reach, so an owner's self-hosted HTTP services (a local git server, a dev app on a laptop) are usable only as DEV-11 devices with declared operations.** DEV-11 names file, photo, and media servers. A generic self-hosted HTTP service needs a declaration through §11 like any adapter. That's the right trade for a default-untrusted LAN. Proposal: DEV-p1 offers a generated read-only declaration for a self-hosted HTTP service, the way CAP-9 generates one for a private hosted route. One LATER line under DEV-p1.

Device executor memory at the floor (risk 19) is already DEV-mem in LATER.md. The one-pairing-code-per-Matter-device cost is stated as an inference. Neither needs a new point.

## UX

- **U1 (release, CH-11): "a message of only 6 or more digits … that matches no open code counts as a wrong code".** This also catches an owner who texts a phone number, an order number, or a tracking code on its own. The message never reaches the agent, and five such messages lock the low tier (CH-18). Fix: count only a digits-only message whose length equals the issued code length. A guess of any other length can never match, so not counting it gives up nothing. Security cost: neutral. Potency cost: none. A16's test still holds as written. Proposed row: fold into the next CH-11 touch (CH-21e or the first device package), one clause.
- **U2 (later, DEV-10): the `CONNECT` digest line names a device by type and an 8-character key fingerprint.** Few owners can check a fingerprint against a printer. The real protection on this path is its scope (verified, non-capture `read` only, and a code-generator code), so a spoofed line costs little. Proposal: when DEV-p1 is briefed, keep the fingerprint behind `MORE <id>` and name the device by type and when it appeared ("a printer that appeared at 14:02"). Never use a device-supplied name (DEV-8).

The rest of the owner-facing text checks out. Discovery's digest line is first person and uses the one local-UI name ("my Wi-Fi page", CH-12). The extra control words, BLOCK and CONNECT, are offered only on the prompts that use them. Connection is one tier-4 visit for a whole plan with safe defaults preselected, which is the low-effort path.

## Arbitration

P1 is the one tension. Security wrote "exactly two exceptions", and potency loses the resolver, NAS backup, and LAN-hosted models. The redesign doesn't split the difference. It adds owner-pinned, broker-only exceptions, so agents gain no reach and the owner keeps BAK-1 and CAP-9 as written. That dominates both the current text and an agent-side allowlist ([record](../arbitration/2026-10-08-pr403.md)). U1 and S1–S4 are neutral or better on all three lenses and pass through. Nothing is escalated to Mark.
