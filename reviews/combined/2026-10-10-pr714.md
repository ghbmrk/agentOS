## UX

Question: does it ask attention, time, decisions, memory, checking, or recovery that the system could carry?

- **blocker (CH-15, OWN-4, A3).** The old CH-15 rate-limited *unsolicited* texts. The new text rate-limits *pushed* texts and sends "everything else" only when asked, with no word on replies. OP-11 lists "relayed guest replies" and "results" as `owner.inform` intents that pacing decides whether to push. Failure path: the owner texts a task, the agent answers in task chat (A3's "follow-up question, clarification, revision, result delivery" journey), and the third reply in an hour is held, or all are held in quiet hours, or waits for a `STATUS`. Fix in CH-15: a reply in a task chat the owner has open, and the result of a task the owner asked for by text, are conversation, not pushes, and are not counted or held; only broker-initiated texts are paced. Also fix OWN-4, which still lists "an outcome" as a notify case while CH-15 now withholds outcomes.
- **release (CH-3, CH-15, CH-12).** CH-3 requires an unlocked session for `STATUS` and `MORE STATUS`, and N is nowhere defined. Pull-first makes that code-gated read the owner's primary view, so an owner whose session lapsed must find a code generator before seeing any result. Failure path: owner texts `STATUS` after N days, gets the unlock prompt, and results stay hidden until a code is entered. Name the default N and whether a limited `STATUS` (counts only, no content) works from the owner's number. If the second, it is a Security call for Mark. Recommend: name N (default 30 days, matching CH-19) and leave content gated.
- later (recheck, CH-15): the liveness line is content-free, weekly by default. A box that is up but has a plan signed out, a held fix or a waiting question tells the owner nothing until a pull. A count ("Still running. 2 items; text STATUS.") would make pull-first self-prompting. It is a Mark choice (D-097 says "no other content"), so it stays a note for the pending liveness card.
- later (recheck, CH-15): the old text let the owner define the urgent classes; the new list is fixed plus "classes the owner adds". An owner cannot move "approvals that block work" behind quiet hours. Fails safe (a 3 a.m. prompt), not a defect.
- later (recheck, OP-11, CAP-3): a "forget" confirmation has the erased record as its subject, so the OP-3 recheck would drop it as erased. Name that the confirmation's subject is the deletion request.
- later (recheck, CH-12): a result leaves `STATUS` once a reply showed it. Say where a shown result can be read again (the local UI log, OSS-1) so a dismissed text is recoverable.

## Potency

Question: does anything cap the consequence or breadth of verified outcomes without buying security?

- **release (LOOP-3, CHG-6, CAP-13, A10).** "Off until it beats the baseline on §1's objective" has no stated place for a cost or latency win at equal acceptance. CAP-13 scores pipelines on acceptance, latency and main-route usage per accepted task, and A10 asks for lower main-route usage "at no loss of acceptance"; §1's objective counts owner effort, not spend. Read strictly, a cascade that halves main-route usage with the same acceptance is a tie and never adopts. That is a cap on what the box can verify and keep, bought for no security. Failure path: the seed extractive-reduce pipeline passes the suite with equal acceptance and 40% less usage, and stays off. Fix: define "beats" as no worse on acceptance and better on at least one of acceptance, latency, owner effort, or main-route usage per accepted task, outside noise. The PR's tie note (D-095 leaves ties undecided) then covers only true ties.
- later (recheck, LOOP-3): "above noise on independent goals" has no sample size, and a one-owner box may have few. Put the minimum and the hysteresis for "turns off again" in SIM-check so a mechanism does not flap.
- Pass (OP-7): one revisable outcome per goal, latest revision wins, re-evaluating adoptions on a changed verdict. This raises correctness and loses no reach.
- Pass (OP-10, OP-11): one log and rechecked intents add no ceiling on what the owner can do or reach. Pull-first moves effort to the system; the owner loses no capability.

## Security (cross-lens, one point)

- **blocker (CAP-3 vs REC-1, §7.5).** CAP-3 says deleting the data key erases every sealed copy "backups and snapshots included", and counts the vault's own copies. REC-1 restores "everything" from the recovery key plus a backup, and the vault text says a drive copy taken earlier still opens. A backup that holds the vault holds the key, so deleting the live key erases nothing there. Failure path: forget a subject, restore an old backup, and the sealed payloads read in plaintext. Fix: state that the key store is excluded from every backup and from snapshot restore (so a restore reads those subjects as `erased`), or limit the claim to copies made without the key store. L3 and Security should check this wording.
