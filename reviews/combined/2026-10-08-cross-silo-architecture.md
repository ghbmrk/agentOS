# AgentOS as an owner-controlled space for cross-silo work

Record: PR #447 · package ARCH1 · head c422039d41acdb4b70f89c1ece9b0fbd40191799

**Purpose:** follow-up to Mark's clarification that potency comes from combining many credentialed services, large private datasets and their devices, a diverse set of output devices/services, and—separately—heterogeneous hardware capabilities. Security and sovereignty should make the owner willing to connect these resources and delegate useful action across them. This review uses “space” as that conceptual set of resources, not a new product, global permission, or ChatGPT Space integration.

**Scope:** source review at the pinned main head above, plus explicitly identified drafts. This extends the [holistic review](2026-10-08-holistic-architecture.md), whose earlier evidence remains pinned to its own source. No runtime, authority policy, SPEC, device enrollment or account change is made here.

## Revised architectural judgment

**AgentOS should maximize useful, owner-authorized combinations.** Isolating credential custody is a means to enable broad reasoning and action across accounts. Treating every account or project as an information island would undermine the intended advantage.

The earlier review gave too little prominence to this positive composition goal. Its broad-owner recall observation is an enabling behavior under the current contract. ARCH1-L1 should offer selective owner-defined boundaries and intentional sharing across them, not establish default project silos. A narrowly supplied reply composer is one useful automation path; it must coexist with a richer planner that can reason across the owner's authorized context.

The central promise is: **combine knowledge and capabilities without automatically combining authority.** High assurance in credential custody does not make an email, document, device reading or provider result trustworthy as an instruction. A task can use wide context while having tightly bounded permission to disclose or act. Likewise, an enrolled device can be a source, processor, actuator, or several of these under independent permissions.

The spec already points in this direction: CAP-2 includes tools and explicitly granted local devices; CRED-11 defines account-to-account hand-offs; ADP-15 offers one desktop over isolated executors; CAP-12 exposes available resources; CAP-13 uses owner compute hosts. The dominant near-term gap is completing those composition contracts and proving useful combinations. General physical-device control and raw hardware federation go beyond what current main implements. [Reach](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/SPEC.md#L321), [hand-offs](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/SPEC.md#L241), [resource and compute contracts](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/SPEC.md#L331).

## Four independent permissions on the same resource

| Role | What the owner delegates | What it must not imply |
|---|---|---|
| Data source | Read selected content or observations; combine it where permitted | The source's text can issue commands, certify identity matches, or authorize recipients |
| Processing destination | Send specified inputs to this model/runtime/host | It can read other stores, receive credentials, retain data under an unstated guarantee, or issue effects |
| Effect destination | Perform declared operations on this account/device within bounds | It may see all context used by the planner or acquire another account's authority |
| Credential custody | Authenticate the qualified operation through its executor | The agent, joined dataset or remote worker receives the reusable credential |

A NAS connected as a source does not become a general shell host. A GPU host does not become a calendar client. A phone supplying observations does not thereby get permission to send messages. An output display has an audience; “on my network” does not establish that private material belongs on it. A single owner action can intentionally enroll several roles, with their consequences visible. Network discovery and human-readable names are hints until enrollment binds the actual resource identity.

This preserves breadth: the planner can select compatible roles across the space. The broker enforces the resulting grants and data destinations. Owner choice of a broad personal space remains legitimate; a connector does not silently expand it. CAP-12 requires the guest view to omit any credential or account detail; broker-resolved opaque handles and capability facts are the proposed way to support composition within that rule. [CAP-12](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/SPEC.md#L331), [account-executor routing](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/grants/gate.go#L575).

## 1. Make useful combinations discoverable

A large inventory is only useful if the agent can discover which source can supply the input another capability needs. Reuse the proposed `resources` view, adapter declarations, qualification records and current grants. For a concrete workflow, expose caller-eligible resource handles, qualified operations, input/output artifact types, readiness, data eligibility, capacity/cost and limits on observing or cancelling effects. Resolve different routes to the same underlying account/device consistently; replacement or re-pairing must not silently preserve the old identity.

Current main registers questions, managed-tree, recall and optional workers beside generic effect tools. It does not register CAP-12's full `resources` view. The pending CAP-11/12 draft supplies a narrower plan-agent inventory; neither is evidence of a general live catalog covering private sources, device actuators and hardware. Complete the existing catalog integration before creating another registry or permission store. [Live registration](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/cmd/agentosd/tree.go#L185), [effect tools](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/guest/mcp.go#L43), [resources draft](https://github.com/ghbmrk/agentOS/blob/fc2e31bd55e6aaf3b869537a6cb9620746f26ae7/broker/provagent/declare.go#L94).

For the owner, organize delegation around useful outcomes and understandable resource groups. Show which already-connected sources, processors and destinations support the task. Ask at a real widening of authority, not for every source pair or every planning step. Discovery is a view of what is already usable; it never grants permission. A stale catalog result cannot bypass final dispatch checks.

**Disposition:** existing CAP-12/POT-P7 and adapter integration, measured through ARCH1-3. Additional metadata is a bounded extension when the selected workflow needs it. A universal resource ontology is not a release prerequisite.

## 2. Preserve rich private reasoning and make joins dependable

Recall already spans accounts and retains source attribution, broker-derived lineage provenance and private-label raises. These should be preserved. Its present query is text/fact/kind search capped at 100 hits; it is not an exhaustive federation or a consistent snapshot of all connected sources. Source time is distinct from broker receipt time. Events carry a version, but the recall indexing bridge does not retain it as an explicit source-version field. A model can synthesize what it retrieves; the system cannot infer completeness or current truth from that search result. [Recall source and provenance](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/recall/recall.go#L49), [query](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/recall/recall.go#L1003), [durable delivery provenance](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/recalltool/tools.go#L193), [event indexing](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/events/bus.go#L703).

For the first useful cross-source task, carry a small evidence envelope: source identity, version when available, observed time, coverage/freshness and dependency references. Distinguish “not found in this indexed subset” from “does not exist.” Preserve conflicting records and uncertain entity matches: two records with the same name are not necessarily the same person or device. Re-read the authoritative record for a consequential precondition immediately before acting. An inference can recommend an action without becoming the verifier of its own permissions.

Large private datasets need bounded indexing and query-on-demand, not necessarily full replication into one store or one model prompt. P3-3b already carries newest-first bounded backfill, older provider search and an owner-visible coverage line; the recorded 100k-item benchmark uses synthetic mail on a cloud runner, not a proof of floor-hardware performance for every data type. Reuse that work. Device photos, recordings and changing sensor streams require their own measured ingestion and retention costs. Avoid hiding those costs outside the accepted-work measurement. [Backfill ownership](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/briefs/P3-3b.md#L5), [capacity scope](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/recall/ASSUMPTIONS.md#L18).

A join may reveal a fact no source exposes alone—for example, a calendar combined with device presence can reveal that a building is unattended. The current binary private label does not enforce a separate inference-sensitivity policy. Explain intended composition and output audiences when the owner grants the workflow; any stronger derived-inference restrictions belong to ARCH1-L1, with an explicit policy and qualification method rather than a prompt for every join. Test both useful permitted inference and prohibited output under the chosen policy.

The planner may combine a broad approved working set. Source restrictions, where the owner chooses them, follow derived artifacts and processing destinations; they are not reset by summarization. Entity resolution and large-scale query optimization can stay outside the authority path. CAP-3 already requires rebuilding/requalifying adopted skills and procedures whose evidence contains a deleted record, previewing affected skills before confirmation and removing them only when they no longer qualify. P3-3b explicitly carries the integration work. The earlier ARCH1-L2 classification as a wholly later stronger promise was incorrect: track this existing requirement under ARCH1-1/3 and its current owners. Broader guarantees about arbitrary historical influence or external recipients require separate scope and cannot be inferred. [Existing deletion contract](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/SPEC.md#L322).

**Disposition:** existing CAP-3/P3-3b/POT-P2/P4 plus ARCH1-3 acceptance. New fine-grained residency or source policy remains ARCH1-L1; a generic federation/knowledge-graph engine remains later unless measured need justifies it.

## 3. Give rich reasoning a dependable path to bounded outputs

CRED-11 is central to potency: move useful content across account executors through broker custody, without pooling browser sessions or credentials. It specifies task-lived hand-off items, label propagation, destination checks and a separate intent for the effect. ADP-15's composed desktop similarly separates the useful work surface from credential-bearing processes. Current browser part 1 has only seven action verbs and explicitly defers sessions, sandbox and effect classification; a full cross-account file workflow is designed, not established by that gate. [CRED-11](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/SPEC.md#L241), [browser protocol](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/browser/protocol.go#L38), [part-1 limits](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/browser/ASSUMPTIONS.md#L14).

Qualify an actual artifact chain: two sources → credential-free working machine → useful native artifact → granted destination. Bind the reviewed bytes/version, source provenance, destination and attempt. A handle identifies content; it is not bearer authority. Copy/paste/upload preparation never silently submits. Keep false-positive cases—ordinary document text, dates and identifiers—beside secret-canary cases so a detector cannot “pass” by destroying utility.

Broad planning and narrow unattended output are compatible only when the release contract is real. A rich planner's arbitrary summary handed to a restricted composer can still encode private information. A model's assurance that its prose is sanitized is not a data-flow guarantee. Use broker-verified fields and approved templates where the standing rule requires them; use appropriately authorized richer outputs where needed. ADP-11's specially restricted thread composer remains a separate exception, not the general reasoning architecture. [Standing rules](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/SPEC.md#L354), [composer](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/mail/verify.go#L163).

**Disposition:** existing CRED-11/CRED-4b/ADP-5/A13 and ARCH1-2/3. Stronger semantic disclosure policies need an explicit L1 decision; this review does not narrow current owner-authorized communication.

## 4. Compose actions without losing their total meaning or uncertainty

Operation gates already enforce important boundaries. Current rules describe an account/action and verified fields with rate/amount bounds; the journal rechecks authority, fences unknown effects by account and handles STOP. Goal IDs are attribution, not a complete workflow authority contract. An individually permitted action can still be the wrong next step if another service's outcome is unknown. [Rules](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/grants/grant.go#L264), [intent fields](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/journal/intent.go#L16), [dispatch](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/journal/engine.go#L207), [goal attribution](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/guest/goal.go#L58).

Start with one concrete cross-service workflow using existing task identity, reservations, intents and receipts. Dependent steps require the appropriate observed result. Unknown purchase state cannot justify a second purchase on a different provider, or a message claiming completion. Revocation holds future dependent effects while preserving already-completed work and allowing unrelated authorized work. Compensation is its own mediated effect, not a universal rewind.

Where the owner wants an aggregate cross-account limit or an explicitly forbidden action combination, it must have a deterministic contract: for example, one commitment for this task, a total bounded amount across its attempts, specified recipients, and an expiry. Splitting across accounts, workers or request IDs must not evade the chosen bound. A vague “do what is best for this purpose” description cannot supply that enforcement. Existing global/task budget mechanisms should be reused wherever they already cover the constraint. Do not impose a second approval on every sequence that existing authority permits.

Cross-silo automation also creates a source-writer problem: an agent can write a value in system A and later read it through system B as apparently verified input. Authenticated retrieval does not make a recently agent-written recipient or instruction owner authority. Qualify source-writer relationships for the selected workflow. This is a design threat to test, not a demonstrated current production bypass.

**Disposition:** observed dependency, receipt and recovery tests extend ARCH1-2/3 and POT-P2/P3. New aggregate cross-account delegation semantics are later/L1 under ARCH1-L3; reuse the existing journal and gates, not a universal transaction engine.

## 5. Close the observation/action loop before claiming device autonomy

A diverse output plane needs evidence of what happened. Distinguish command submitted, service accepted, device reports applied, and independently observed result. A successful HTTP response may establish only one of these. Device feedback has an identity and freshness requirement; a stale or spoofed reading cannot silently certify completion.

The event bus deduplicates source/version and has stable delivery keys. That does not by itself prevent a two-way sync echo or repeated actions caused by genuinely new versions produced by the system. Current production wiring registers indexing, not an event-to-work trigger. When connecting the latter, reuse event/task/intent identity, qualify causal correlation where the service supports it, and bound retries, rates and settling behavior. Do not suppress every self-caused event: some are necessary observations of successful work. [Event identity](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/events/bus.go#L29), [current wiring](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/recalltool/service.go#L104), [outcomes](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/journal/intent.go#L139).

For physical actuators, an inverse command does not reverse elapsed physical consequences. A device profile needs concrete bounds, stale/offline behavior, cancellation limits and local safety interlocks. AgentOS STOP should block new commands and honestly report what remains in progress. It cannot promise instantaneous remote cancellation across a network partition. Qualify one device/simulator and one operation before describing a general device control plane; keep safety-critical control local to the device.

**Disposition:** CAP-4 event-to-task and observed-result integration stays with current owners. General device actuation/closed-loop policy and new verb semantics are later/L1 under ARCH1-L3, independently qualified per device and operation.

## 6. Treat heterogeneous hardware as a separate composition problem

CAP-13 is a sound initial contract: compute hosts are pinned encrypted model endpoints, public-only by default with per-host private-data choice, no account credentials or broker tools, qualified models and untrusted results. It covers inference routes and local passes. It does not define general CPU/GPU/storage job federation, remote worker machines, arbitrary device accelerators or distributed inference across machines. Main explicitly has no local inference service to consume its discovered accelerator leases. The lease library is not a deployed compute fabric. [CAP-13](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/SPEC.md#L332), [live wiring](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/cmd/agentosd/main.go#L475), [accelerator leases](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/broker/accel/accel.go#L130).

Off-box processing is disclosure to that host. A pinned key authenticates the endpoint; it does not prove its OS is uncompromised, that its reported model is honest or that it forgets plaintext. Owner ownership alone does not supply those guarantees. Data eligibility must hold for every pre-pass, post-pass, retry and fallback. Losing a private compute host must not send its task to an ineligible cloud route. Revocation stops future dispatch and acceptance; it cannot reclaim bytes already received. CAP-13 already records this trust limit. [Compute-host integrity risk](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/SPEC.md#L621).

Complete the existing inference-host path first. For broader hardware, choose one bounded job kind—such as compilation or rendering of approved artifacts—before designing a general scheduler. Reuse task/artifact identity and admission. Bind input digests, runtime/job version, endpoint identity, deadline, limits and attempt; hold admission for execution; return untrusted results with provenance. Distinguish cancellation requested, confirmed, lost and expired. Fence stale results after revocation or host replacement. A remote runtime must enforce its claimed isolation/resource limits; a report from the worker is not enforcement. Do not expose a generic privileged shell as the shortcut to hardware diversity.

**Disposition:** CAP-13/POT-P8 inference integration and privacy-preserving fallback belong to existing work. General raw hardware/remote-job capabilities are later/L1 under ARCH1-L4. No new cluster, attestation requirement or cloud dependency is made a first-release prerequisite.

## What sovereignty must mean in a connected space

Sovereignty includes deciding which sources may combine, where computation runs, who sees outputs, what can act, and how each can be paused or removed. It includes exportable durable work, visible derived-data/deletion limits, replaceable providers and continued owner control when a connector disappears. It does not mean a plaintext recipient can be forced to forget or that an owner-owned remote computer is immune to compromise.

Retain DEP-1–4: no mandatory project service or control relay. A disconnected endpoint reduces capability, without sacrificing STOP, journal or recovery. Directly reaching an intermittently connected device may be unavailable; do not solve reachability by silently introducing a forbidden relay. Increasing the resource count also raises the value and blast radius of the trusted broker. Preserve isolated credential readers and a small authority decision surface, bounded connector ingestion and independently reserved control resources. [Dependency contract](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/SPEC.md#L43), [resource protection](https://github.com/ghbmrk/agentOS/blob/c422039d41acdb4b70f89c1ece9b0fbd40191799/SPEC.md#L498).

## Prove complementarity, not connector count

ARCH1-3's original one-source/one-output slice remains a construction step. **It is insufficient evidence for the clarified cross-pollination claim.** The acceptance workload must deliberately require information and capabilities that no single silo supplies.

| Experiment | Positive result to establish | Failure cases that must remain bounded |
|---|---|---|
| Cross-source deliverable | Combine at least two private sources into a native artifact and a second authorized output, with attributable inputs | Same-name identity collision, missing source, stale version, revoked destination, swapped artifact |
| Delegated multi-service workflow | Repeated useful runs within standing authority, fewer owner interventions, correct observed dependencies | Lost acknowledgment, duplicate attempt on another route, partial completion, STOP between steps |
| Private compute placement | Accepted work using an eligible host; compare floor-only and extra-host configurations | Wrong key/model, public-only host, host loss, forbidden fallback, late result after revocation |
| Event/device simulation | One observed state change causes the intended bounded downstream action | Stale telemetry, sync echo, repeated versions, partitioned cancellation; actual device qualification remains separate |
| Large connected space | Task discovery, recall and dispatch remain usable at a predeclared account/source/resource count | Connector churn, revoked handles, backfill pressure, event floods and foreground starvation |

Use synthetic services first and the existing INT-A/H6/W7-A/A10 machinery. Hold the task and its authority/data policy constant. Compare the connected workflow with disconnected tools on the same inputs. Then remove each source, output capability or compute resource in turn: does acceptance, effort, timeliness or feasible task coverage materially worsen? This measures complementarity rather than the number of integrations used. Distinguish genuine capability gains from faster execution and from gains bought by exporting more data.

Include setup, maintenance, correction, recovery, transfer/warmup, discarded work and approvals in the cost. Report accepted task coverage, owner-minutes, quality, latency, total spend, permitted data movement and violations separately. Freeze scale and success targets before qualification; do not assume every added source improves judgment or every extra host speeds work up. Broad context can add noise as well as insight. No combined-potency gain has been measured in this review.

## Repository work and evidence

This follow-up sharpens existing ARCH1 work instead of creating parallel implementation owners:

- **ARCH1-1:** independently describe source/processor/effect/custody roles and actual sovereignty guarantees.
- **ARCH1-2:** include cross-account artifacts, dependent effects, source-writer tests and truthful observed output.
- **ARCH1-3:** require a positive cross-silo workload, compute-placement variant and cardinality/churn measurements before claiming the clarified benefit; reuse CAP-12/13 and current integration owners.
- **ARCH1-L1:** owner-selected boundaries that preserve deliberate broad composition; no default per-project isolation policy.
- **ARCH1-L2 (classification corrected):** CAP-3 already requires affected learned skills/procedures to be rebuilt/requalified. Track the known integration under ARCH1-1/3 and P3-3b/current learning owners; it is release work, not a new later promise or separate runtime package.
- **ARCH1-L3 / L4:** later proposals for general cross-service/device delegation and broader raw hardware jobs; defined in LATER with adoption criteria.

Three focused source reviews examined data/authority, output composition and heterogeneous compute. A small set of existing recall/provenance tests passed with synthetic data on native macOS; the prior two-account probe establishes broad owner-scope behavior, not complete composition. No actual sensors, actuators, remote compute hosts, live accounts or large connected-space benchmark were exercised. Fresh independent review and PR checks cover this advisory delta.
