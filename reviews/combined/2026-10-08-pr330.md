## Security

The change closes the one metadata leak OSS-6 admitted: relay operators linking a home IP to months of usage hints and the installed version. Publication is already clean-room (OSS-1..3), so the content side doesn't change. No credential is involved: neither the box nor the pull job holds a write credential. The relays the spec still forbids are the ones that matter for control (§2: owner access or control).

| Adversary | Path | Stop |
|---|---|---|
| Relay operator | Links a batch to the owner's IP | Structural: Tor always, no direct fallback |
| Relay operator | Links batches across a key rotation through a shared circuit | None yet. Carried as OSS-6i (fresh circuit per batch and key) |
| Anyone | Floods the open-write relays with forged attestations | Procedural: OSS-9 weighting and maintainer review (unchanged) |
| Network provider | Sees Tor in use | None. The spec states this, and the owner is not told (S2) |
| Hostile network peer | Exploits the Tor client on the box | Not specified (S1) |

- **S1 (release, OSS-6, ARC-1): the spec doesn't say which component runs the Tor client.** A network daemon that parses untrusted input is new code in the image. Proposal: it runs in an uncredentialed component (a publication worker or the uncredentialed egress path, REV-5), never in the broker or vault process, and it is pinned through the image and dependency audit like any other dependency. UX cost: none. Potency cost: none. This should be settled in OSS-6p's or OSS-6s's brief rather than with a new row, unless those briefs are already closed.
- **S2 (release, OSS-6, LOOP-0): Tor use is visible to the network provider, and the owner never hears about it.** In some networks or jurisdictions, Tor use draws attention. With publication on by default and silent, the owner can't weigh that. See the arbitration below for the resolution.

## UX

"Silent by default" is the right default: publishing never costs an owner text. **U1 (release, LOOP-0, §8)**: the defaults line in onboarding already says "sharing on". It should add "over Tor" and keep "stop sharing" as the one-word opt-out. That one line also resolves S2. The ask-each-time interaction is carried as OSS-6a.

## Potency

There's no direct fallback, so an installation on a network that blocks Tor never publishes, and its attestations are lost to OSS-8. The spec counts a lost batch as "only a data point", and that's acceptable at this scale. **P1 (later, OSS-6)**: Tor bridges (pluggable transports) would recover those installations without weakening the no-direct rule. The Tor client's memory and CPU should also be counted against the N95 floor budget when OSS-6s is built.

## Arbitration

S2 and U1 pull against each other: security wants the owner informed, while UX wants publishing silent. [Resolution](../arbitration/2026-10-08-pr330.md): mention Tor once, in the existing onboarding defaults line, and in STATUS-by-text only if the owner asks about sharing. No recurring text. This beats both a recurring notice and full silence. Nothing is escalated to Mark.
