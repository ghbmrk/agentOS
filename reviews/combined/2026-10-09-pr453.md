## UX

Question: does the owner see or do anything different, and does any journey break?

- The wording changes nothing the owner sees. The Wi-Fi password stays the card's (CH-7, REC-4); rotating it still produces a new card.
- **Pre-unlock journey (blocker, same point as L3 point 1).** For an unknown host the owner reaches the unlock step only over the box's Wi-Fi (CRED-8 unknown-host slot, CH-7). If the access point password may be held on the drive "only under CRED-8's encryption", the access point cannot start before unlock and the owner has no page to unlock from. Whichever way Mark settles the L3 point, the owner path must stay: card, Wi-Fi, unlock page.
- A saved home network needs no pre-unlock path (Ethernet or the access point carries unlock), so r3's re-add after unlock costs the owner nothing visible. `Online` still has to say so when the home network is late (BOARD c4).

## Potency

Question: does the change cap capability, or buy any?

- It removes a reading of ARC-1 under which no Wi-Fi link could run. Nothing else in the diff moves capability.
- No cost to UX or security that the lenses can see, beyond the point above. The alternative (the broker proxying every WPA handshake) would cost latency and a large new surface for no gain; the structural choice is right.
- Considered, not proposed: widening the exception to other host-held secrets. The wording names two secrets, which keeps the exception checkable.

1. **blocker (CRED-8, CH-7)**: see L3 point 1 on the PR. The access point password cannot be encrypted at rest under a key released only at unlock if the access point must be up before unlock.
2. **release (r3, A5)**: widen r3 to the access point password and add a Wi-Fi password canary to the A5 check when c3 lands, so the "outside every model-directed process" bound has a test.
