# Potency, PR #1046 (RECALL-prov)

Record: PR #1046 · package RECALL-prov · head ddea70d

**Question:** does bounding note provenance cap what an agent can remember beyond what the bound buys, and does a long-lived agent keep its notes?

**What holds**
- **A note costs the same whatever the lineage has read.** It derives from one anchor; anchors name only the reads since the last one. `TestNoteProvenanceGrowsLinearly` and `TestProvenanceStaysLinearInReads` pass.
- **No lifetime stop on anchors.** The anchor count cap (a2981ba B2) and the 64-anchor collapse are both gone. A lineage that keeps reading keeps making notes on one chain, and `TestLongChainStillCascades` shows 70 notes on one chain, all deleted with an early source.
- **Search does not pay for compaction** any more (N1): rewrites are amortised over the appends that earn them.
- **Replacing a note key is free**, so an agent at its 1000-key cap can keep working by rewriting its own keys.

**Findings**
- **P-R1 release** (same follow-up as Security S-R1 and LATER RECALL-prov-L1; invariant CAP-3, an agent can keep notes over its lifetime).
  - Problem: a lineage's read set only shrinks when the owner deletes a source or takes the lineage back. `Check` refuses every note once the lineage has read more than `Reads` (20,000) distinct items. Now that anchors are linear in reads (R1'), the read gate on notes no longer bounds anything the read set itself does not already cost.
  - Failure path: a long-lived owner agent reading mail and pages reaches 20,000 distinct items read in a few months, and `recall_note` then fails for good. The guest text asks it to "delete old notes", which frees nothing here, and the owner has no control that frees it short of a take-back.
  - Fix: drop the per-lineage read gate from notes, or bound the read set where it grows (`Given`) in a way that keeps the deletion cascade, and add a test that a lineage past 20,000 reads can still make a note.

Findings: blocker 0; release 1; later 0.
