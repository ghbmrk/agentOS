##### Potency
- **#1442's acceptance is met.** The issue named two sites, `local.go:59` (`signInTextLocked`) and `:138` (`FlushLocal`, the Tick path). `FlushLocal`, `LocalSignIn` (local.go:390) and `LocalAnswer` (:699) all go through `signInTextLocked`, so one guard covers all three. A future `LocalAlertAt` now counts as expired, following the precedent in `recentSends` (pacer.go:315-325).
- **The fix is at the right level.** A future `LocalAlertAt` comes only from `sendSignIns` stamping `now` while the clock was ahead. The first successful send after the correction overwrites it with the corrected `now`, so the value repairs itself. Clamping at write or load time would add nothing: the read-time guard is the same pattern the pacer uses. A failed send leaves the value in the future, and every Tick then retries, which is the normal failure path.
- **The test proves the main behaviour.** It sets the value a day ahead, runs a real `LocalSignIn` with TOTP, and checks the exact text.

##### Findings
- **F1 (class:later, test strength).** The test only uses a 24 h skew, so a mutant that still holds texts for a skew of a few hours (M5) passes. Real corrections are often small (an RTC a few minutes or an hour ahead before NTP steps it back). A second case with `LocalAlertAt = now + 1 minute` (or `+1ns`) would kill every tolerance mutant. Optionally, also assert that a second sign-in right after the repaired alert is held, which shows pacing resumes from the corrected stamp. The code is correct, so this does not block.
- **F2 (class:later, same bug class outside #1442's scope).** `State.LocalStart` has the same weakness. `localLeftLocked` (local.go:325) and the reset at :409 use `!now.Before(LocalStart.Add(WrongWindow))`. A `LocalStart` left in the future by a set-back clock keeps the 24 h local sign-in window open, and any lockout in force, longer by the skew, and "paused until HH:MM" (local.go:226, :649) then names a time that has not come yet. The cost is availability (the owner is locked out longer), not a suppressed alert. O35's own "If it changes" rule ("a new gate on a stored send time must treat a time after now as elapsed") points at it. Suggest filing it as a follow-up.
- **F3 (nit).** Because of M4, the `!st.LocalAlertAt.IsZero()` term is now redundant. Keeping it for readability is fine.

##### UX
- After a correction, the owner gets the sign-in text at the next sign-in or Tick instead of hours later. The text is unchanged and its times come from the corrected clock (the test checks `r.clock()`'s HH:MM). There is no repeat: a successful send overwrites `LocalAlertAt = now`, so normal hourly pacing resumes. At most one text goes out sooner than the hourly pace, which matches O35's "at most one extra sign-in text per correction".
