# Potency, PR #434 (SR3-4, make update finalization durable and idempotent)

Record: PR #434 · package SR3-4 · head 215deaea7ee905b574f63180a58cf1d3c5e15ff1

Verdict: accept

Tier A, Potency lens only. Reviewed from the diff against its merge-base with `origin/main`, UPD-1, UPD-1a, OP-4, OP-5 and A7. Question: does durable settlement restore the update path, and does it block anything it need not?

- It restores the path. Before this, one I/O error or cut between the three stores left `Applying` set for good, and `Tick` refused every later update. Now each step is idempotent per exact release (`update.Ref`) and adoption ID, and a later valid update is admitted after recovery (brief acceptance 4). That is a real gain: a box that can never update again loses every later fix.
- Its cost is a few durable writes. A legacy rollback point with no `ToManifest` and no staged record stays in flight (apply A9). That exists only on pre-release boxes, so no point is raised.

Points:
1. **release (A7, change C25)**: the same refusal that blocks the owner's UNDO also refuses Recheck's regression and security reverts of a staged image, and it holds from adoption, not from the handover. If Recheck finds that an adopted upstream image regresses while it still waits for a free moment, the box cannot revert it. The applier then installs a release the box already knows is bad, and only the next Recheck after boot reverts it, at the cost of a regression window and a second restart. A7 needs "a bad one is rejected" on the image path too. The deadlock C25 guards against exists only once the applier has staged or handed over (`Applying` set). Before that, a revert can safely drop the applier's pending release. A new BOARD row should narrow the refusal to that window, with the applier told to drop pending, as part of W5b wiring or an SR3 follow-up, and test a Recheck revert before handover. This is not a blocker: Recheck reverts are outside the cited IDs, and Security 4a signed the deadlock trade.
