## Draft issue texts (filed as #1488)

#### L-1: Keep the agent's own managed_tree call from flooding its context
Later, tier A (broker/guest, broker/cmd/agentosd). Follow-up from the Potency review of #1484 (L-1).
Since #1484, the guest plane never folds `managed_tree`, so the bridge's polls cannot evict the agent's held results. An agent that calls `managed_tree` itself now gets the whole tree inline, up to about 5.4 MiB of JSON. Before #1484, a tree of 8 KiB to 4 MiB came back as an 8 KiB stand-in. The tool is listed in `tools/list` with a description that invites calls, yet the bridge already mirrors the tree to disk.
Options:
- (a) Leave `managed_tree` out of the plane's `tools/list`, since the bridge calls it by name.
- (b) Fold it when the call does not come from the bridge. This would need a way to tell the two callers apart.
- (c) State in the tool description that the tree is already on disk.
Test: `tools/list` on a private machine does not offer `managed_tree`, and the bridge sync still works.
Serves ARC-6, CAP-5.

#### O-1: The bridge's tree poll consumes the agent's step-snapshot note
Later, tier A (broker/guest). Pre-existing; observed while reviewing #1484.
`machine.takeNote` is one-shot and is appended to any tool result on the machine's socket, `managed_tree` included. The bridge polls `managed_tree` every 30 s and reads only `Content[0]`. A note about a failed step snapshot can therefore go to the bridge, and the agent is never told. The owner STATUS line still shows the failure.
Fix: do not attach the note to `TreeTool` answers.
Test: a failed step is followed by a tree poll, and the agent's next tool result still carries the note.
