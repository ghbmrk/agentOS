# Potency, PR #464 (P3-4b-1, Loop 2 repairs an injected finding)

Verdict: accept

Tier A, Potency lens only. Reviewed from `git diff origin/main...pr464` against LOOP-9, LOOP-10, LOOP-3, CHG-2 and A11 (briefs/P3-4b.md). Question: does this give Loop 2 a working repair path at a cost in proportion, and does it cap anything it need not?

- It is a real gain. A finding that arrives as a failing tree rule now gets contained, minimized into a permanent regression, and turned into a fix request that the §11 pipeline grades against every linked case. Tree rules are answered from the tree alone (replay R13), with no machine, recording or model, and in untested namespaces too. So qualifying a config, routing or context fix costs almost nothing per probe. That makes A11's loop 2 clause testable, and it gives P3-4b-3/-4 and P3-4c an entry point.
- Fail-closed grading (`ReasonUnlinked`, an unevaluated linked case counts as a fail, the original test linked beside the minimized one) costs nothing on the success path and only blocks weak fixes.
- LOOP-3 "unmeasured" keeps Loop 2 at the explore share until it contains a finding. On a clean box that can last indefinitely, but S3 parking after clean passes is unchanged and still bounds the spend, so it isn't raised.

Points:
1. **release (LOOP-9, budget), owner P3-4b-5**: for a reported finding, `retry` re-asks the fixer once per pass after `FixFailed` or a rejection, with no limit (loops S13 notes this). With the scripted fixer that is cheap. With P3-4b-5's model-backed fixer, every pass spends a builder job on a finding it may never qualify a fix for, for as long as the finding stays open (see UX point 1 on #464: it can stay open after it is already fixed). P3-4b-5 should cap retries per finding, for example a day-scale back-off after two rejections, and STATUS should then say the box stopped trying. It also should not re-ask when the fixer's last candidate hashes the same as one already rejected.
2. **later (LOOP-9)**: if adding the regression or the original case fails for a reason other than a duplicate, such as a store save error, the finding stays open and contained with no fix request (`waitNoTest`). Nothing retries the add: a second `Report` of the same finding returns the open record, and `Pass` skips reported records. One transient error then blocks repair of that finding for good. The known "crash between saves" item is a different path. `Pass` could retry the add for reported records with `Fix == ""`.
