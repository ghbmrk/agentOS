# Potency, PR #423 (P2-2a f3, re-offer a lapsed release)

Record: PR #423 · package P2-2a f3 · head fc0aa67677e7a7e1de6a27e6acd4598d616b07fc

Verdict: accept

Tier A, Potency lens; Security signed separately. Reviewed from `git diff origin/main...fc0aa67`, change C25, maintain M8 and UPD-5. Question: does the change cap how fast a release reaches the box without buying security or UX?

The PR lifts a cap: an unanswered release used to wait for a restart before it was offered again, and now it is offered at the next update check. A re-offer is a new request through the gate, so it adds no authority (Security, threat table).

Points:
1. **later.** The re-offer waits for Loop 3's next check, up to the daily interval. `Pipeline.lapse` could clear Loop 3's `Next` (through `Proposer`, without calling into Loop 3 under its lock), so the release is offered at the next spare slot. Security cost: none (same request path). UX cost: none (the owner already expects the request). It also shortens UX point 1's stale STATUS window.
2. **release (with UX point 1; one class per D-063).** A release left out of a partial YES is never offered again until a restart or a newer release. For an ordinary release a newer one supersedes it, so the cost is small. For a security release that never gets independent auto-stage, the fix stays uninstalled for as long as the owner does nothing, and nothing tells them (UX point 1). The re-ask policy is arbitrated in `reviews/arbitration/2026-10-09-pr423.md`, with one question escalated.

Considered, not proposed: treating "not chosen" as a lapse (re-asked at the next check) for every release. It would nag the owner about a choice they just made (UX cost) for little potency gain on non-security releases.
