# Potency, PR #466 (SR2-3n, the guest's stderr apart from runsc's fd 2)

Record: PR #466 · package SR2-3n · head 9c3c45b4c6cb5c7b7cc84a06932c10ac0e9ebdaa

Verdict: accept

Tier A, Potency lens only; Security is stage 4a. Reviewed from `git diff origin/main...pr466` against the brief (Security S2, S3, S4 on #391) and its IDs RES-4, CAP-8. Question: does the change cap what a worker command can do without buying matching security? Guest reach: `broker/guest/mcp.go:146` → `worker_exec` → `gvisor.Exec`.

- Net gain. The structural fix (`--pass-fd 3:2`, a pipe of Exec's own as the guest's fd 2) replaces content matching on a shared stream. A guest's exit 2 now loses its output only when runsc itself wrote to its own fd 2. Before, any guest text that looked like a Go trace did it, so a Go program's own panic read as a runtime failure. No security is traded for this; the S2/S3/S4 holes close at the same time.
- No new cap. The guest's stderr is still capped at `MaxOutput` and read to its end within `ExecWaitDelay`, as stdout is; Exec's return bound is unchanged.
- Reuse: runsc's own `--pass-fd` and os/exec `ExtraFiles`; no new component.

Points:
1. **release (CAP-8)**: the new rule, exit 2 plus *any* byte on runsc's own stderr ⇒ `ErrExecFailed`, is far broader than SR2-3m's marker-and-header rule. It holds only if the pinned runsc writes nothing to fd 2 on an ordinary exec. Exit 2 is common for ordinary tools (grep, diff, make, Python argparse usage errors), and a stray runsc warning on stderr would turn each such result into a ref with no output, which would be a large potency loss with no gain in security. V32 reads runsc's source for errors and info lines, but only the fake runsc tests exit 2 (`TestGuestExitTwoWithoutPanicIsAResult`); real runsc in `TestIntegrationWorkerExec` exits 3. Add a real-runsc case where the guest exits 2 with output and assert it comes back as a result. It's one argument in the integration test, so it can ride this PR if the builder is already pushing, or go in a new BOARD row.
