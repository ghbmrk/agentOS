# Potency: PR #1245 (SR3-mail-k18)

Record: PR #1245 · package SR3-mail-k18 · head 6c3d54125cc4e75be034392a3548c410b211048e

Verdict: accept

This is the tier A lens screen, Potency pass. Cited IDs: CRED-1, CRED-8, ARC-2 (and mail M1).

- **Gain.**
  - The vault process now outlives any panic in go-imap's reader goroutine. That goroutine parses and handles every response from the server.
  - The mailbox, model route and texting account stay available without a fresh owner unlock.
  - It lifts a cap the old code imposed: before, the owner had to trust the mail host not to send bad bytes. It adds no security cost, since the custody boundary is unchanged and no process split was needed.
- **Proportionate.**
  - The patch is two marked `agentos:` edits in `client/client.go`: the `recover` in `reader`, and a deferred unlock in `handle`. No response handler is edited.
  - `third_party/go-imap` and `vendor/.../go-imap` are identical except for go.mod (`diff -rq`). `date.go` differs from upstream only by a gofmt reflow.
  - ARC-2 is untouched: nothing new is linked.
  - The PR says why the fork beats reuse (M20): no released v1 recovers in the reader, and moving to v2 is a larger change.
- **Mutation probes (3)**, run on a scratch copy against `mail/imapsmtp` and `mail/mailsock`:
  - **Killed: M1.** With the `recover` removed, T1 reports the panic and T3 crashes the test binary.
  - **Survived: M2.** Restoring the non-deferred unlock in `handle` passes. Under the current wiring this path cannot be reached: the recover closes the conn, so `execute` fails at `SetDeadline` before `registerHandler` takes the lock. The edit is defence in depth.
  - **Survived: M3.** Dropping `c.conn.Close()` from the recover passes. The call still fails, through `loggedOut`. But a scratch probe showed the TCP connection then stays open after the call returns. `imapsmtp` calls `stop()` on its context `AfterFunc` and never closes the conn itself, so one connection is left until the server hangs up, which a hostile server never has to do.
- **P1 (later, recheck).** Pin M3 with a test: after a guarded panic, the server sees EOF within a bound. Pin M2 with a test that makes the deadlock reachable, if one exists, or drop the edit and its claim. This is the recurring kind "a defence can be reverted and the suite still passes". The current code is correct. Flagged to the Security section (4a), which may reclass it on this tier-A path.
- **P2 (later).** Two identical copies, with nothing checking they agree. The build uses `vendor/`, and no CI step runs `go mod vendor` and diffs. A future edit to `third_party/go-imap` alone (the place PATCH.md and M20 name) would not be built, and nothing would flag it. Proposed check: a CI step that runs `go mod vendor` and fails on any diff.
- **P3 (later).** M20 says the patched reader "logs that it happened". `imapsmtp` sets `ErrorLog = quiet{}` (imapsmtp.go:167), so in the vault the log line goes nowhere. The wording should say so, or the line should reach the vault's log in fixed words.
