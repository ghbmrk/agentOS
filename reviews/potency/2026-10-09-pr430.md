# Potency, PR #430 (SR3-6, invalidate verified updates when attestation policy narrows)

Record: PR #430 · package SR3-6 · head 84c9efcf112e7d41086bac7d01a328905a32b230

Verdict: accept

Tier A, Potency lens only. Reviewed from the diff against its merge-base with `origin/main`, UPD-8, UPD-5 and CHG-3. Question: does binding attestation authority to the policy take away automatic security updates the owner should still get?

- Only in the case the brief targets: a release checked under a policy that is no longer current. Threshold releases under the current policy still proceed (`TestSR36CurrentReleasesStillProceed`). The owner path stays open, so nothing becomes unreachable.
- Any policy change, widening included, retires authority and costs one recheck (update U16). Policy changes are rare owner or image events, so this is a fair price for a simple rule: policy is state, not a counter.

Points:
1. **later (UPD-8, wiring W5b)**: `Store.Check` rewrites `attestor_policy` from its own `Options.Attestors` and `InterimAttestors` (store.go `noteAttestors`). If two callers ever pass different lists, for example Loop 3's check and another `Check` caller, each check retires the other's `Verified`. Security fixes would then never auto-stage and would all go through the owner. This fails closed, so it has no security cost, but it silently turns off CHG-3's standing policy. The wiring should take the allow-list from one source for every `Check` and `NoteAttestors` caller, with a test that two checks in a row keep `Security()`.
2. **later (apply A7, wiring W5b)**: a pending security fix dropped by a policy change and scheduled again by Loop 3 should keep its first-scheduled time for A7's 24-hour "no free moment" ask. Otherwise a policy change resets the clock and the ask comes later than the owner would expect.
