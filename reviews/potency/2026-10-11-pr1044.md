# Potency, PR #1044 (MAIL-gen)

Record: PR #1044 · package MAIL-gen · head 73109a9

**Question:** does MAIL-gen refuse legitimate work after the owner switches accounts, beyond what the security gain needs, and is recovery clear?

**What holds**
- **Routine events refuse nothing.** The generation leaves out the password and `SetAt`, so the following keep it unchanged:
  - a password or app-password rotation;
  - re-saving the same settings;
  - a vault restart.

  Only a change to address, servers, STARTTLS or sign-in name refuses in-flight work. That is the point of the change.
- **Bounded outage on a real switch.** The rebind follows within `mailPoll` (1 min). Until then every call fails closed through mailsock. New intents submitted after the rebind run normally, with no owner step and no new grant.
- **Cost of a switch:** intents queued, asked or in flight under the old account are refused once. Each needs one new intent and, for a send, one new ask. That is the intended price.

**Findings**
- **P-R1 release** (no new row: add to SR3-mail-w2-f1 precondition (a), which already replaces this exact reason for the unbound, locked and unconnected states).
  - Problem: after a switch, the reason the guest reads for a refused intent is the gate's generic "the adapter's guard refuses this effect (ADP-2)". `errMailGen` is only logged. An agent cannot tell "the mailbox changed; ask again" from a permanent guard refusal, so it can drop legitimate work instead of resubmitting.
  - Failure path: the owner replaces the mailbox, and the agent's queued archive or reply is abandoned silently.
  - Fix: the escalator returns a sentinel that the gate maps to fixed wording such as "the mail account changed since this was asked; ask again", like the gate's existing "the details changed ...; ask again".
- **P-L1 later.** `generation()` hashes the whole serialized `mailSettings`.
  - Problem: any field added later, even one that does not route (a display name), changes every generation on upgrade and refuses all in-flight mail work once.
  - Gap: no test shows that re-saving with a new password keeps the generation. The stability check only reads it twice.
  - Fix: hash an explicit list of routing fields, and add a re-save and password-change case to `TestTheMailAccountNamesItsGeneration`.
- **Concur** with L3 delta item 3 (later). An Unknown attempt stuck for up to 24 h also holds one M8 daily-bound place, which is negligible.

Findings: blocker 0; release 1; later 1.
