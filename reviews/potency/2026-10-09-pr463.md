# Potency, PR #463 (SR2-3q, SR2-3p, runsc exec failures before the command ran)

Record: PR #463 · package SR2-3q · head 677071422b3540b171e18f938599a60d91b55eec

Verdict: accept

Tier A, Potency lens only. Reviewed from `git diff origin/main...pkg/SR2-3q-exec-not-started` against CAP-8 and RES-4. Question: does the narrower "did not start" cap what a worker-driving agent can do, beyond what it buys in not running a command twice?

- **Gain.** A missing or unloadable program now gets its own answer that says a retry fails the same way. An agent driving a worker stops spending turns on retries that cannot work, and goes straight to fixing the path or the image. This is the common failure on a fresh worker image, so the turns saved recur.
- **Cost.** It is small, and it buys the right thing. Failures that runsc does not show were before the start now answer "may have run". The agent then checks state before re-running instead of retrying blind. These failures are rare (a lost urpc answer, a runsc killed or panicking before the pid write). The extra check costs one turn, and in exchange the agent never runs a non-idempotent command twice on a false "did not start". No capability is removed: every command the agent could run before, it can still run.
- **Bounded parsing.** The classification reads at most 1 MiB of one log line per failed exec, and only on the failure path. A successful exec costs nothing extra.

Points:
1. **later (CAP-8)**: the V33 known gaps (a non-UTF-8 `argv[0]`, or an unusual PATH directory) answer "retry it" for a missing program. This costs one futile retry, since the second answer is identical. The agent's own budget bounds it, so it isn't raised. It is the same item as UX point 1/2 on #463 and the PR's Findings line.
