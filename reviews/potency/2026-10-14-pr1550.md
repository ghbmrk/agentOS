### Draft issue texts (not filed)

#### Draft A: the release residual from the PR's Findings (B3; same as Security R0)
Title: NETGUARD-neigh-event: a router swapped behind the same gateway address with no link event keeps the old router's identity until the next 10 s poll (release; from #1550)

Release (DEV-2), tier A.
- **Where.** `WatchNetlink` subscribes to LINK, IFADDR and ROUTE only, so a change in the neighbour table raises no event.
- **Failure path.** A router is swapped behind a switch. The kernel learns the new MAC through a gratuitous ARP or a re-resolve. Until the next poll (up to 10 s, plus one router read), the guard keeps the old router's (gw, MAC) entry and external address, so the new router's WAN address is allowed.
- **Fix.** Subscribe to RTMGRP_NEIGH and count RTM_NEWNEIGH/RTM_DELNEIGH for the learned gateway's address as an event. Alternatively, compare the gateway MAC on each poll.
- **Acceptance.** With the poll an hour away, a MAC change for the gateway in the neighbour table opens the hold.

#### Draft B: if B2 is not fixed in #1550 (otherwise no issue)
Title: NETGUARD-drop-hold: a full read that drops a NAT-PMP answer stores the new gateway with no external address and no hold (release; from #1550 Potency B2)

Release (DEV-2), tier A.
- **Where.** sources.go:108-117 and policy.go:288-289.
- **Failure path.** The poll's full read sees router B behind the same address (or a flushed entry) for the first time. It drops the answer, and B's WAN address, or the known router address, is allowed until the next full read (up to 10 s).
- **Fix.** `Read` returns an error when the gateway changed during the read, or it asks the end gateway again within the bound.
- **Acceptance.** A policy-level test with no event: the answer is dropped and `Check` on the new router's WAN address is held, then decided after that router's own answer.

Title: NETGUARD-gw-ident tests: two answering routers behind one address, ATF_COM vs zero-MAC rows, failed re-read (later; from #1550)
- Kill mutants M6, M14, M17 and M13 from the #1550 review:

  - M14 and M17: a `0x0` row with a non-zero MAC, and a `0x2` row with a zero MAC.
  - M13: a re-read failure after the answer keeps the learned set.

#### Draft D (later, recheck): UX of holds on same-router flaps (fold into #1539 if preferred)
Title: NETGUARD-flap-hold: a carrier flap on the same router holds public dials until a full read (later, recheck; from #1550 UX R2)
- Since #1550, a neighbour flush on the same router opens the hold: about 2 s per flap for routers that drop NAT-PMP.
