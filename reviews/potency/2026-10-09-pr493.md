Question: does this make `Guard.Report` fit to be wired by P3-4b-3 and -4 at a cost in proportion, and does it cap anything it need not?

- Real gain for the wiring rows. Before this, a crash between saves or one store error left a reported finding contained with no case and no fix request, and nothing retried it (Potency later 2 on #464). Now `Pass` and a re-report resume it, with the regression minimized before the first save so a resume adds the same test. LOOP-7 sources can call `Report` without their own repair logic.
- `LinkedHold` is cheap and structural: it answers tree-rule cases from the active tree with no evaluator run, so clearing a repaired finding costs no replay per pass. Restricting it to findings whose own cases are both in the suite keeps a partial minimized case from clearing anything.
- Item 2 turns an ID collision from a slot takeover into fail closed, at the cost of a stuck finding (UX point 1 on this PR); the right trade.
- Item 5 (S22) keeps the cap: a `config/` fix that replay cannot run stays rejected while plain security probes go unevaluated. That is a cap that buys a matching security property (LOOP-10 (f) applied to the rest of the suite), so it is not proposed for removal. S22 names the structural lift (probes declare the config paths they read) under "If it changes".

Points:
1. **later (LOOP-9, owner P3-4b-5)**: the S22 rejection is deterministic: the same unevaluated plain probes reject every config candidate until the suite or the tree changes. S13 retries a rejected fix once per pass, which is free with the scripted fixer but is a model call per pass with P3-4b-5's, for a candidate that cannot qualify; STATUS meanwhile says "I try again at the next check" each time. P3-4b-5's retry bound should skip re-asking the fixer while the rejection reason and the suite and active-tree digests are unchanged. The brief already routes unbounded retries to P3-4b-5; this names the case it must cover.
2. **later (LOOP-9, owner P3-4b-3)**: a finding stuck by an ID conflict is retried every pass and `Pass` returns the same error each time (S21), forever. The scheduler does not penalize it, so the cost is log noise, not capacity. The fix in UX point 1 (`reportable` refuses IDs ending in `/original`) removes this too.
3. **later (A11, measure)**: S22's cost ("Loop 2 cannot fix a config seed itself on a box with such probes") applies only once plain config probes are live, which today waits on K-S1 for passive fixtures. When the K-S1 row makes them live, its brief should check whether the A11 config seeds still qualify on a box with live plain probes, and take S22's lift if not.
