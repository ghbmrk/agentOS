# Potency, PR #424 (SR3-5, preserve IMAP message identity through mutations and undo)

Record: PR #424 · package SR3-5 · head 4f20c07c8e388bd412cac9cc118187cb060e7c28

Verdict: accept

Tier A, Potency lens only; Security is stage 4a. Reviewed from the diff against the merge-base with main, ADP-2, OP-2, OP-3, OP-4, REV-2 and mail ASSUMPTIONS M9/M12/M15. The L3 accept was on 866631a; the commits after it only merge main. Question: does the identity check cap capability more than the security it buys?

- No new cap in routine use. The check runs per UID-validity epoch, not per mailbox state, so deliveries and expunges never refuse (brief test 4), and M2's nine Store methods stay as they are: only the signatures change.
- A rebuild costs one re-attempt. `NotApplied` before any change sends the next attempt back through the gate, which re-resolves by Message-ID and reruns the guards. When the same message is back in the new epoch, it is the one acted on (`TestQueuedActionAfterRestartAcrossAReset`), so a provider rebuild does not strand queued work.
- The watcher fails only the poll that straddles a rebuild, and the next poll re-reads the folder (M12). Coverage is delayed by at most one poll.
- Considered, not proposed: retrying the mutation by the old UID after re-listing. It would reopen F5, which is the defect this package fixes.

Points:
1. **later (ADP-2)**: undo skips a flag-only change whose recorded Ref differs from the message found, even when the Message-ID matches. After a provider rebuild, a whole digest's label changes become un-undoable, all reported as "skipped (changed since)". The watcher's identity digest (Message-ID plus sender, date and text prefix, M12) could show it is the same message, which would let undo restore it under the new Ref at a small security cost: a 72-bit digest match instead of a UID. Rare, so later.
2. No point on SetFlags and Move as two sessions, or on CONDSTORE: LATER.md already holds them (SR3-5 f1).
