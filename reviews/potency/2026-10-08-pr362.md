# Potency lens screen: #362 SR2-3h, runsc's own messages never reach the guest (b9082c9)

**Stage:** OPERATING §4 stage 4, lens screen, Potency section. Tier A. UX is in [`../ux/2026-10-08-pr362.md`](../ux/2026-10-08-pr362.md); Security is a separate session.
**Read:** the diff against `origin/main` (32c6e67), RES-4 and CAP-8 in SPEC.md, briefs/SR2-3h.md, `broker/workers/workers.go` (`run`, `exec`, `read`). Tests pass on the branch merged with main.
**Question:** where does the change cap what the guest can do with worker machines (CAP-8) without buying matching security?
**Labels:** [Fact] checked in the diff or spec · [Inference] reasoned, untested.

Verdict: accept

- [Fact] A successful exec is unchanged: the guest's exit code, stdout and stderr come back as before, and nothing is logged (`TestGuestExitIsAResultAndLogsNothing`, `TestRunscMessagesNeverReachTheGuest` "ok" case, and the real-runsc `TestIntegrationWorkerExec` in CI's machines job).
- **release (new BOARD row, or fold into SR2-3j, which already turns denial reasons into fixed text): two fixed texts instead of one opaque ref.** [Fact] A command that cannot start (a missing or non-executable program, a typo in argv[0]) used to come back with runsc's "no such file" text; it now reads "worker_exec failed (ref …); the broker's log has the detail", and the guest cannot read that log (vm V32 lists this gap). The same ref answers a runsc failure *after* the command started (pid file written, `--log` non-empty), where the command may have run and had effects. [Inference] The first costs the agent turns guessing; the second invites a blind retry of a command that may already have run, which on a non-idempotent step (a migration, an append) makes a wrong branch look right in CAP-1's fork-and-test. Proposal: `gvisor.Exec` already tells the two cases apart (empty pid file vs. pid written); return two `vm` sentinels, and let workers map them to fixed texts: "the command did not start: check that <argv[0]> exists and is executable in the worker" and "the runtime failed after the command started; it may have run, so check the worker's state or roll back before running it again". Security cost: none [Inference]: both are broker literals plus the guest's own argv[0] (a `guest` value under K21), no runsc text. UX cost: none (agent-facing).
- Considered, not proposed: passing any filtered form of runsc's stderr through. It would recover the exact reason but reopens the leak SR2-3h closes; the two fixed texts get most of the value.
