## Potency
- Cap lifted: a hostile mail host no longer ends the vault process (stack overflow, declared-size literal, endless atom, quoted string, status text or FETCH stream), so one bad host costs one call instead of the owner's unlock and every other credentialed route the vault serves. Real gain for CAP-4 mail watching and every executor sharing the process.

- Cost to security: none (tightens). Cost to UX: none beyond P1.

## Findings
- **P1, blocker (defect, regression this diff introduces).** `fetch` keeps the first FETCH response for each requested UID (broker/mail/imapsmtp/imapsmtp.go, the `want` map). A FETCH that carries the UID and FLAGS but no body (a flag update for that message arriving during the UID FETCH, e.g. the owner reading it on the phone) now takes the slot, the response carrying `BODY[]` is dropped, and the watcher publishes a blank message and records its UID (watch.go:302-309), so the agent never sees that email. Before this PR both responses were returned and the real one was published. Reproduced with a scripted server sending `* 1 FETCH (UID 1 FLAGS (\Seen))` then the body response: on main 2 messages (the second with the subject), at d854a41 1 blank message. Which servers send UID on unsolicited FETCH is inferred, not checked; the regression holds for any that do. Fix (verified: the repro passes and `go test ./mail/...` still passes): skip a response with no body section without spending the UID's slot, `if !want[m.Uid] || len(m.Body) == 0 { continue }`, plus a test with that server script. Body-less responses stay bounded by the read budget and are not kept.
