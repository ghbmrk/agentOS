One tension, in class only: Security S2 on #434 classes an orphaned staged adoption `later` (no image boots from it, so no safety cost); UX classes it `release`, because the owner's UNDO is then refused with a restart that will never run it (CH-12). The same root cause appears on #430 (L3 point 3: a release dropped for `ErrPolicyMoved` leaves its adoption `Staged` and the digest saying it starts at the next restart), already `release`.

- Cross-check: settling the adoption when the applier drops, abandons or supersedes its release is neutral for Security (no image is booted or kept; the adoption reverts through the journaled pipeline, OP-5), improves UX (texts are true again) and improves Potency (UNDO and Recheck work again).
- Decision (D-063: one class, set by the strictest finding): `release`, one BOARD row covering #430 L3 point 3 and #434 Security S2, coordinated with W5b, which wires `Schedule` and `Resume`. Not a fork for Mark.
