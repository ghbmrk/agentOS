# Arbitration, PR #423 (P2-2a f3): a release left out of a partial YES

Record: PR #423 · package P2-2a f3 · head fc0aa67677e7a7e1de6a27e6acd4598d616b07fc

**Conflict.** C25 drops a release left out of a partial YES ("not chosen", CH-13) and does not offer it again until a restart. UX (point 1) wants no re-prompt for something the owner chose not to approve, but needs STATUS to stop saying the release is waiting for approval. Potency (point 2) notes that a security release left out this way stays uninstalled with no further prompt. Security signed C25's conservative reading (an omission never approves anything); the re-ask question is not a security finding.

**Cross-check.**

| Proposal | Security | Potency | UX |
|---|---|---|---|
| A true STATUS/digest line for a left-out or declined release (UX 1) | neutral | improves (the owner knows a fix is not installed) | improves |
| Re-ask every left-out release at the next check | neutral (a new request) | improves | costs (nags about a fresh choice) |
| Re-ask only a left-out *security* release, once, at the next check | improves (fixes get installed) | improves | small cost (one more ask, only for security fixes) |

**Resolution.** The first row passes untouched and is the P2-2a f4 fix (UX point 1, release). For the re-ask, no design removes the cost for every case. Re-asking only security releases, once, keeps an ordinary release's omission final (a newer release re-asks anyway) and costs the owner at most one extra ask per security fix, phrased as a second chance ("You left out security update N on Tue. Reply YES <code> to install it, or NO."). CH-13 is silent here (C25 says so), so the rule needs an L1 spec-diff.

**Escalated to Mark (one question).** When the owner leaves a security update out of a partial YES, should the box ask once more at its next update check? Recommendation: **yes**.

Until he answers, C25's behaviour stands. Nothing here blocks #423.
