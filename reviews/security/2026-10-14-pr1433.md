#### Security review (tier A, OP-2 e): REQUEST CHANGES

Head reviewed: `65bfc69c4617c7e0edc707ec3bc7afcc7384b3d9`

**Bottom line:** The journal engine is sound. No path I found re-executes a non-idempotent effect on its own, including the crash windows and races I tested beyond the PR's own tests. Two problems block merge. First, the owner's RETRY request does not say which effect would be retried, and one code approves all of them. Second, the tests miss two of the guards against a double send.

##### Blockers

**B1. The RETRY request does not say which effect it retries, and one code retries all of them (CH-12, CH-13, CH-5).**
- `retryItems` (`broker/daemon/retry.go`) builds every item as `Object: "<an email|an action|...> that may not have gone"`, with `Facts{Verb: "Retry", NoRecipient: true}`. It does not include the recipient, the amount, the time or the original object.
- I ran a probe with three parked emails. The owner receives:
  > `L2: 3 items. 1 Retry an email that may not have gone, it may go twice, cannot be undone. 2 Retry an email that may not have gone, ... 3 ... Reply YES L2 359362 for all, YES L2 1 2 359362 for some ...`
- `YES L2 <code>` then approves all three, so one texted code can re-send up to 20 effects that the owner cannot tell apart, payments included.
- This is the "confusing which action is retried" threat. It breaks CH-12, which says an approval text states, from verified fields, the verb, the object, and the recipient or amount.
- It also breaks CH-5, which says tiers apply to verified data. `NoRecipient: true` is false for a mail send, and `HasAmount` is dropped for a payment. Those false facts are how the item gets the low tier.
- Mark chose the texted code, so the tier itself is not in question. The fix is in what the request shows:
  - Render each item from the parked intent's verified fields, the same way its first approval was rendered: object, recipient or amount, and when it was first sent.
  - Set the low tier explicitly as Mark's OP-2 choice, instead of through false facts.
  - Do not offer "YES for all" on a RETRY request. Either ask about one effect per request, or require the item numbers.
- The digest can stay as it is: it is private and leaks nothing. Only the approval request needs these details, and the first approval already carried them.

**B2. Mutants show the tests miss some double-send guards.** I applied each mutant on its own and ran the touched packages' tests (`-run 'OP2|OP4|Retry|Unclear|Park|Settle|Reconcile|Attempts|Check|Trail'`).

| Mutant | Result |
|---|---|
| `retryDecide` ignores `d.Approved` (`if !ok \|\| !d.Approved` → `if !ok`) | **survives** |
| `keyRetry` ignores a `HonoursKey(in) == false` answer | **survives** |
| key retry of a parked attempt, with both the `keyRetry` guard and the `validate` guard removed | **survives** (each guard removed alone is covered by the other) |
| `check.attemptsSettle` accepts an owner retry of an intent that is not parked | **survives** |

- The first row matters most. `owner/boot.go:59,64` emits `Approved: false` decisions for `expired` and `restart`. Without the guard, a RETRY request that expires, or a reboot while one is open, would retry every listed effect. The code is correct today, but nothing proves it.
- Add tests for:
  - a declined, expired and restart-denied retry item;
  - an executor whose `HonoursKey` returns false;
  - a parked attempt with a key-honouring executor, which must not be retried;
  - the checker rule above.
- Six mutants are killed: automatic re-execution of an unknown attempt, `Retry` without the attempt check, `Retry` skipping `mayDispatch`, the duplicate hold, fencing parked intents on open, and `parkAfter=1`. So are the digest privacy mutants (recipients in the line, params kept in `Parked()`) and the dropped duplicate warning.

##### Release (separate issues before ship)

**R1. An owner retry's refusal or outcome is never reported.**
- `retryDecide` runs `go eng.Retry(ctx, id, n)` and discards both the status and the error. The owner sees only `Approved L2.`
- A refused retry stays parked, and since the digest generation does not change, the digest never lists it again. The owner is left believing it went.
- D-116's third open point says the owner "then sees a refusal", which is not true of this code. Please correct D-116 in this PR either way.

**R2. The idempotency-key claim is the executor's own word and has no time limit.**
- No production executor implements `KeyHonouring` today, so this path is dormant.
- `HonoursKey(in)` gets no information about the attempt's age. Providers keep keys for a limited window, typically about 24 hours.
- `keyRetry` re-executes on every settle round until the intent parks, and again after each restart, because `checks` is kept in memory only. A key retry after the provider's window can therefore pay twice.
- Before any executor implements it:
  - pass the attempt's dispatch time into the hook and refuse a retry past the provider's documented window;
  - require a Security review for each implementer;
  - add a test that fails when a registered agentosd executor implements `KeyHonouring` and is not on a reviewed allowlist.

**R3. Parking lifts the account fence, which the OP-4 text does not allow (D-116 open point 1).**
- OP-4 says "Unresolved intents are reconciled before new dispatch on that account". A parked intent is still unresolved.
- Effects with the same fingerprint stay held (tested), so this does not cause a double send.
- A *dependent* effect can now run, for example a follow-up mail saying the payment went.
- Keeping the fence forever would bring back #1373's failure, so lifting it is reasonable. But Mark did not approve this reading of OP-4. Get his confirmation and add a SPEC note.

**R4. A check that proves the effect was not done drops it without telling anyone (D-116 open point 5).**
- SPEC OP-2 step 2, as amended here, says "retry". The engine resolves the intent to `not_applied` and does nothing more.
- The intent then leaves the digest as Resolved. Nothing re-dispatches it, and the owner is never told the effect did not happen.
- Not retrying is the safer choice: today only mail drafts and some organize operations return `not_applied` from a check, and mail send never does. Either:
  - list it in the digest as "did not go; not retried" and let RETRY offer it; or
  - make the SPEC text match the code, with Mark's approval.

**R5. A retry of a payment or other high-tier effect needs only a texted code (D-116 open point 2).**
- Mark said "texted code", so this is not a blocker.
- The remaining risk: someone holding the owner's SIM can duplicate any parked payment, and with B1, up to 20 in one reply.
- Ask Mark once to confirm this explicitly for money-moving effects, or cap it, for example by requiring the high tier for amounts at or above `AmountLimit`.

**R6. Retry refs share a namespace with intent IDs.**
- `retryDecide` diverts any decision whose `Ref` starts with `retry:`, and gate refs are `in.ID`.
- This cannot be exploited today. Guest IDs are `<lineage>/<request_id>`, where the lineage comes from the broker and `request_id` matches `^[A-Za-z0-9._-]{1,64}$`, so it cannot contain `:` or start with `retry:`.
- Reserve the prefix in `Engine.Submit`, or carry retry items in a typed field, so that a future ID scheme cannot turn an ordinary approval into a retry.

##### Later
- **L1.** The digest line says "from before a restart", but an unknown outcome left during normal running parks too (`TestOP2RuntimeUnknownIsParked`).
- **L2.** O31 in the owner ASSUMPTIONS says "no hook makes RETRY not understood", but the code and the test reply "Nothing to retry.".
- **L3.** D-116 open point 4 (a parked effect holds identical intents until it is settled) is the right trade-off for at-most-once. No change is needed beyond the existing `HeldError` reply.

##### SPEC check
- **OP-2:** the rewrite matches #1373's amendment a to d and Mark's words at 23:53Z and 23:59Z ("Giving the owner work... annoying"; "double sends shouldn't ever happen").
- **Key retry:** matches 00:18Z ("Retry where idempotency keys exist is totally fine").
- **CH-11:** the RETRY control word, with a low-tier texted code, implements amendment (c) ("needs the texted code").
- **No unapproved SPEC substance**, so the SPEC diff is not a blocker. The divergences between SPEC and code are R3 (OP-4) and R4 (OP-2 step 2).

##### What I checked
- **Fresh clone at the head.**
  - `go test` for `./journal/... ./daemon/... ./owner/... ./cmd/agentosd/...`: all pass. `-race` on the journal and daemon OP-2 tests passes, and `go vet` is clean.
  - `python3 tools/doclint.py`: clean.
  - `python3 tools/risk_tier.py --git origin/main pr1433`: tier **A**.
- **Crash windows.** The PR covers the kill between intent and outcome for both a mail send and a payment stub. My own probe tests (not pushed) all pass:
  - killed between the owner retry's `dispatched` record and its outcome: after restart it is fenced, checked, and parked as attempt 2; nothing re-executes, and a stale `retry:a:1` is refused;
  - killed during a key retry: the restart reuses only the same key and attempt;
  - an executor that answers `HonoursKey` false is never re-executed;
  - a parked attempt is never key-retried.
- **Concurrency.** Two more probes pass under `-race`:
  - ten concurrent `Retry(a,1)` calls: exactly one runs;
  - interleaved `Reconcile` and `Retry`: exactly one extra execute.

  The `dispatched` record is committed under the lock before `Execute`, and `validate` repeats every state guard (which is also why some single mutants survive). An observation of an older attempt does not change the intent's state.
- **Forged checks.** Mail-send reconcile reports `succeeded` only when the Message-ID is found in the Sent folder, and otherwise `unknown`, never `not_applied`. A forged "succeeded" errs on the safe side. The engine never acts on `not_applied` by itself (see R4).
- **Other executors.** The forget, recall and follow `Reconcile` methods settle on the first call, so the new hourly rechecks repeat no side effect.
- **RETRY path.**
  - The code is the low tier and single use.
  - Requests open at a restart are denied as `restart`, so an approval cannot carry over a reboot.
  - Refs are bound to the attempt, so a stale or repeated approval runs nothing.
  - What is open is B1, R1 and R5.
- **Digest.** It names no recipients, IDs or params (`Parked()` strips params and preconditions), is GSM-7, and its acknowledgement survives a restart. No private data leaks.
