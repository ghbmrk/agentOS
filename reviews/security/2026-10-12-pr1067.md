# Security lens: #1067, CTRL-claim (one-time sticker claim for a preloaded box), head 2ee74c3

Record: PR #1067 · package CTRL-claim · head 2ee74c3

Scope: the PR at 2ee74c3. Tier A (`risk_tier.py`: broker/localui; broker/claim and broker/firstboot are tier B by path, builder release R1). `go test -race` on go1.24.7 passes for `./claim ./firstboot ./localui`. Nothing is wired yet (K8).

Question: can the sticker code be guessed, read or reused, can the lockout be reset, and does any error path open the box?

Threat check:
- Brute force: wrong codes are saved before the answer. The lock is tied to the kernel boot ID, so a daemon restart keeps it.
  - Clock rollback does nothing, because no timer is involved. Concurrent tries are serialised under one mutex, with the save inside it.
  - A failed save fails closed in memory. A full disk loses one guess per daemon restart, which is negligible against 80 bits.
  - `allowed()` floors at 1, so it cannot underflow, and the owner can always reinstall.
- Secrecy: the disk holds only a salted, domain-separated SHA-256 verifier, removed at the claim, and a hashed claimant token. The journal gets fixed strings and counts.
  - The `?code=` prefill is escaped and sent with `no-store` and `no-referrer`.
  - Compares are constant-time over full hashes.
- Scope: a claimed box refuses every code, and `Seal` refuses existing state. Racing claims give exactly one win. Setup admits only the claimant cookie (HttpOnly, SameSite=Strict), and cross-site posts are refused.
- Fail-closed: every `Open` and `Try` error path refuses. Two of those paths are untested (B2).
- Mutants:
  - Killed: lockout not persisted, re-claim allowed, reseal.
  - Survived: counter reset on a corrupt state, a Load error read as unsealed, a boot-ID error lifting the lock (B2), and a compare that accepts a code prefix or a hash prefix (B1).
  - A non-constant compare of the salted hashes is harmless and cannot be tested.
- Secrets in tests: a synthetic canary stream and codes generated per run.

Findings:
- **B1 blocker** (HW-10 acceptance 3). No test refuses a near-miss code. A compare over the first 12 symbols, or over the first hash byte (which accepts about 1 wrong code in 256), passes every test.
- **B2 blocker** (HW-10 acceptance 3). No test covers a store Load error, a corrupt state or a BootID error. Mutants that reset or lift the lock on those paths pass.
- **R3 release** (HW-10, the first phone holding the sticker claims). After three locks each boot allows one wrong code. A client on the access point that burns it after every restart blocks the owner, who must then reinstall. Goes in the R2 follow-up brief.
- **R4 release** (HW-10 acceptance 1, condition on R2's wiring). `ErrNoCode` on a box that already holds first-boot or card state must not take the flasher path. Failure path: `claim.json` is lost after the claim, and a second phone pairs.
- The builder's R1 (add `claim` to `TIER_A_BROKER`) and R2 (wiring) are agreed.

Findings: blocker 2; release 4 (2 the builder's); later 0.

Arbitration: R3 and Potency/UX L2 point the same way (a fixed per-boot allowance); no tension.
