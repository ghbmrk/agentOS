# Security, PR #434 (SR3-4, durable and idempotent update finalization)

Record: PR #434 · package SR3-4 · head 215deaea7ee905b574f63180a58cf1d3c5e15ff1

Signed at 215deae. `tools/risk_tier.py --git origin/main HEAD` prints A (broker/apply, broker/update, broker/change). L3 accepted this head. Reviewed from the diff, brief SR3-4 (UPD-1, UPD-1a, OP-4, OP-5) and the lens threat model, in a fresh context.

Threat check: can a crash, a save failure, a reused version or short ID, or an undo/revert make the box boot or keep an image that failed evaluation, or wedge updates (including security fixes) for good?

- [Fact] Exact-release keying holds. `CommitRelease(Ref)` installs only a staged record whose version, `/usr` root hash and manifest digest all match the rollback point, keeps the `ErrRollback` check, and is a no-op only when `installed.json` already holds that exact release. A different release with the same version is refused whether staged or installed. Only `Execute` writes `staged.json`, and `Tick` refuses while `Applying` is set, so no outside party can steer what gets committed.
- [Fact] Settlement order is update store → pipeline → applier state, and the applier swaps state in memory only after the save succeeds (`a.save(next)` then `a.st = next`). A cut at any boundary leaves `Applying` set, on disk and in memory, and each step is idempotent for the same release and adoption ID. Nothing is installed twice.
- [Fact] `ConfirmStaged` and `StageFailed` resolve only exact IDs, so a short ID freed by a revert can't settle another adoption. `ConfirmStaged` restores the staged state in memory when its save fails. Neither can settle an adoption the opposite way: `StageFailed` on a confirmed adoption errors, and `ConfirmStaged` on a reverted one errors.
- [Fact] An unsaved handover no longer counts as success. `Execute` reports `NotApplied` and abandons the slot, so the journal (OP-4) never records an activation done that a restart in the same boot would then undo. `Applying` and `executing` are set under one lock, and `Tick`/`Resume` skip while `executing`, so the new unhanded-abandon path in `Tick` can't race a slot write.
- [Fact] Trade-off, accepted: since `Install` arms the next boot, a cut after `Install` but before the handover save is followed by a counted-tries fallback to the old root. That case is now judged "not handed", so neither `StageFailed` nor `FellBack` runs (A5, and `TestUnrecordedHandoverThenPowerCutIsNotAFallback`), and a release that may truly have failed its health check gets one more try. That second try is recorded, so it is bounded to one. The image is signed and verity-checked, and boot counting still falls back automatically, so the cost is availability, not integrity. It is documented in A5.

## Findings

**S1 — release.** If a commit and confirm are durable but the applier's save is cut, and the next boot runs the old root, `Resume` wedges for good. Path: `Resume` on a blessed new root runs `CommitRelease` (ok) and then `ConfirmStaged` (ok), and the applier save fails or the process is cut. The next boot runs the old root (a later loader fallback, or a manual entry choice). `Resume` takes the `default` (fell-back) branch, `StageFailed` returns "not a staged adoption" because the adoption is `Confirmed`, and it fails every time. `Applying` stays set, STATUS says "Update 1 is installing", and `Tick` refuses every later update, security fixes included. That is F4's impact again through a narrower door. Reproduced with a probe test on the PR's rig, not committed: 3 consecutive `Resume` calls returned `confirmed`. The trigger needs two rare events, so it is not a blocker. Fix direction: once the release is durably installed and the adoption confirmed, a later boot on another root isn't a fallback of this apply. Settle it as installed (or report it separately) instead of calling `StageFailed`. Before W5b.

**S2 — later.** An apply abandoned as "not handed" leaves its pipeline adoption `Staged` without settling it. If Loop 3 never reschedules that release (say a newer one supersedes it), the adoption stays staged for good. The owner's UNDO is refused ("starts at the next restart"), Recheck can't revert it, and the digest offers only MORE. No image boots from it, so the cost is owner-facing accuracy, not safety. Settle orphaned staged adoptions when a newer `Schedule` replaces them, or when the not-handed path runs and nothing reschedules.
