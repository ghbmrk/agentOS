# Security 4a, PR #425 (W3-forget-b3, promised done text survives a restart)

Record: PR #425 · package W3-forget-b3 · head f1ebd2cb0019d52bc0d7eef0a9917e6643468ee9

Signed at f1ebd2cb0019d52bc0d7eef0a9917e6643468ee9. `tools/risk_tier.py --git origin/main HEAD` prints A (broker/cmd/agentosd). L3 accepted at this head. Reviewed in a fresh session from the brief (CAP-3, UX-182-3, #182 SHOULD 4) and the diff against origin/main (8e1d010).

Threat check: an attacker who controls the owner channel's timing, the stored owed state, restarts or fault timing. Can a forgotten task survive or leak through owed texts, logs or files, or can the owner be told "forgotten" when it is not?

- [Fact] No task text reaches the new store, logs or texts. `forget-owed.json` holds goal IDs (`owner:<msgID>`, guest/goal.go:20, the same IDs `forgotten.json` already keeps), the ID's time, a count and two flags. Every new `log.Printf` carries only a store or send error. The restart texts are fixed strings plus a date and a count; no text repeats words from the file (F5, F10).
- [Fact] "Forgotten now" is told only for a goal whose tombstone is on disk at start, and only after `replayForgotten` succeeded: `finishOwed` runs from `attach`, which runs only once `openLearning` returned, and `openLearning` fails if the replay fails (learn.go:222). A goal whose tombstone never saved is dropped untold (F3). Mutant M1 kills it.
- [Fact] A tampered owed file cannot widen anything. A goal key is used only for `forgotten.has` and for a forget-log append, and an append happens only for a goal already tombstoned; a duplicate append is already handled (b2c assumption 5). A future time and a negative count are sanitized (M2, M3). An unreadable file is moved to `.bad` with its 0600 mode kept, and the owner gets one fixed notice (M5).
- [Fact] Durability: `change.FileStore.Save` writes, fsyncs, renames and fsyncs the directory. The owed entry is saved before the tombstone (M6), so a tombstone that holds has its text owed unless that save failed. The entry is cleared only after the send reports success. A text that does not send is owed again with `Logged`/`Back` and retried with backoff (M8, M9); a shutdown leaves it to the next start.
- [Fact] Race: `go test -race -count=5` on the owed tests passes, and `go vet` is clean. `owedAtStart` is read and cleared only in `finishOwed`, and the owed map is under its own mutex. A forget that runs before `attach` finds no owner channel, so its text is owed and retried, not lost.
- [Fact] The tests use synthetic IDs (`owner:a` and the like). No credentials or personal data appear.
- [Fact] Mutants applied to forget.go and learn.go at f1ebd2c, each run over the whole package with -race and then reverted:
  - M1: tell without the tombstone check. Killed.
  - M2: no future-time check. Killed.

  - M5: no rename aside. Killed.

## Points

- S1 (later, crash window): learn.go renames an unreadable owed file to `.bad` before `lostForgetOwed` saves the fresh file that owes `forgetOwedLost`. A crash between the two means the next start finds no file, so the owner is never told the owed texts were lost. Fix: save the fresh file (with `!lost`) first, then rename, or write `!lost` to a temp file and rename it over the bad one.
- S2 (later, CAP-3): in `Execute`, if the owed save fails it is only logged. If the forget then goes to `retry` and the box crashes before any later owed save, the tombstone holds and the replay finishes the forget, but no done text is owed. The owner may already have been told "Not forgotten yet… I'll text you when it's done." This needs a disk failure plus a crash. Record it in ASSUMPTIONS (a failed owed save risks a lost text) or retry the save in `retry`.
- S3 (later, test gap): no test pins F4's order, which tells the owner first and drops the entry after. Mutant M4 (drop before the send) passes every test, because a failed send owes the entry again; the two orders differ only in a crash between them. Add a test whose owner send records the owed file's content at the moment of the send.
