## What changes for an attacker
Before this PR, `storeCard` wrote the Wi-Fi part, then the setup part, then the card, each with its own `vault.Put`. Suppose a rotation failed after a part was written but before the card. The vault would then hold the old card next to a new part. The old card's secret was no longer a whole entry value, so the redactor, which matches whole entries, missed it. That is a CRED-7 gap (review 12 item 1). After this PR all three go into one `vault.PutMany`, which makes one save and has one rollback.

## Threat check
| Concern | Result | How |
|---|---|---|
| Atomic on disk | yes | It makes one `save()`, so one `durable.WriteFile`. That writes a temp file in the same directory, fsyncs it, renames it, and fsyncs the directory. The whole vault is sealed in one AEAD envelope. |
| Rollback, in memory | sound | Under `mu`, replaced entries get their old record back, new entries are deleted, and the new copies are wiped. Old values are wiped only after the save succeeds. The duplicate check stops a second copy of a name from wiping a restored value. |
| Rollback, memory against drive | diverge on ErrDirSync (S1) | Memory is rolled back although the file has landed. Each side still holds a coherent card. |
| Redaction coherence | yes | `Redactor()` and `HashRedactor()` read under `RLock`, and PutMany holds `Lock` from the first change through rollback. The egress proxy builds its redactor per request (`egress/proxy.go:607-613`). |
| Provisioning crash | fails closed | `provisionCard` builds the card vault at a temp path and then swaps it in. The card entry marks the box as provisioned (`cardvault.go:68`), and a card now always comes with its parts. `LoadCard` fails closed when no card is stored. |
| Writes widened or validation bypassed | no | `Put` now goes through PutMany, with identical checks for name, kind and `MinValueLen`, all done before the lock. PutMany adds a duplicate refusal. Encryption is unchanged (whole-vault seal). `storeCard` keeps `reserved()` on all three names. |

## S1 (release, tier A; filed as #1472): the vault rolls back memory after a save whose file already landed
I put a probe in the clone and did not commit it. It does an old PutMany, then a new PutMany whose `writeFile` returns `ErrDirSync` after the rename. Result: memory holds the old card and the drive the new one. After one more unrelated PutMany, the drive holds the old card again.

Failure path (REC-4, OP-4):
1. A Wi-Fi or setup-only rotation writes no slot, so `Commit` returns a plain error.
2. `commitRotation` answers 410 "nothing changed, start again", and localui maps that to `card.ErrDiscard`, so the display erases the new card.
3. If the box restarts before any other vault save, it runs on the new Wi-Fi password and setup secret the owner was told were discarded.

Redaction holds in every state, so CRED-7 is fixed. This PR doesn't cause S1. It narrows it: under the old code, the same `ErrDirSync` on a part Put left the drive with a new part beside the old card, which was the redaction gap.

### Issue text as filed (#1472)
Title: VAULT-dirsync-published: a vault save that fails only at the directory sync keeps the new entries in memory, not the old ones

Body:
Release, tier A (vault, recovery). Found by the Security review of #1465 (ROTATE-card-atomic).

**Mechanism.** `durable.WriteFile` returns an error wrapping `durable.ErrDirSync` after the new file is renamed into place. `Vault.PutMany`, `Put` and `Delete` treat every `save()` error as "nothing written": they restore the old entries in memory, and `advance` does not adopt the new anchors. Memory then holds the old values while the drive holds the new ones, and the next save of any kind writes the old values back. A probe on #1465's head shows memory=old and drive=new after the failure, then drive=old after one unrelated save.

**Failure path (REC-4, OP-4).** A Wi-Fi or setup-only rotation writes no slot, so `recovery.Commit` returns a plain error. `commitRotation` answers 410 "nothing changed, start again", and localui maps that to `card.ErrDiscard`, so the display erases the new card. If the box restarts before another vault save, it runs on the Wi-Fi password and setup secret the owner was told were discarded. Redaction stays coherent (#1465), so this is not a CRED-7 gap.

**Fix.** In the vault, treat `errors.Is(err, durable.ErrDirSync)` from `write` as published: keep the new entries, wipe the old values, and adopt the new anchors, as `journal` and `recall` already do. Return the error as a warning, or return nil and warn through `OnWarn`. Then `Commit` reports the card as stored. Test: a `writeFile` that fails after the rename leaves memory and the drive with the same entries, for `PutMany` and `Delete`, and a later unrelated save does not revert them. Same root as #1320, which covers only settings.
