Record: PR #552 · package DEP-4 · head f39e84b

**Security 4a (tier A; `tools/depaudit*`).** Read from the diff d57476f..f39e84b against DEP-4a and DEP-4b, plus the code those IDs depend on (`_inner`, `_attempt`, `_control`, `load_registry`). No live probes were run, so every item below comes from reading the code. The hidden-mount fd/cwd issue (`/proc/1/cwd` into the overmounted original tree) is already known and routed to DEP-3, so it is not repeated here.

**Threat check: no path found by which the audited code writes to a read-only kept path, or a TRACED syscall goes unseen while the sandbox reports available.**
- **Submounts:** `mount_setattr(AT_RECURSIVE, MOUNT_ATTR_RDONLY)` runs on the fresh rbind copy at each kept path. The kernel prepares and applies the whole subtree in one step, so it never leaves a partial result. Any nonzero return raises, including ENOSYS, EPERM, EINVAL and EBUSY. In `_inner` that becomes an uncaught exception: there is no JSON line, so `_attempt` reports `error`, never `pass`. No errno is special-cased, so there is no open branch to test.
- **mountinfo parsing:** fields 4 and 5 (mount point and per-mount options) come before the optional fields, so `master:`/`shared:` tags cannot shift them. The kernel escapes only space, tab, newline and backslash, all as octal. One left-to-right `re.sub` handles `\134` correctly, so a literal `\040` in a name stays intact. An unparsable line fails closed. Judging by the per-mount `ro` flag, not the superblock options, is the right field.
- **Hidden-entry rule:** an rw entry counts as hidden only when `statvfs` on its path gives ENOENT or lands on a read-only mount. A mount that is still reachable has a listed path that resolves to it. Its mount point cannot be unlinked inside this namespace (EBUSY), and an unlink from another namespace detaches the mount, so ENOENT does not give a reachable mount a fail-open route. Any other error is treated as rw.
- **TOCTOU between the remount and the check:** the check runs after the last mount the sandbox makes (`_place`), while `_inner` is the only process in its private mount namespace and before strace starts. After that, the tracee has no CAP_SYS_ADMIN, `mount`/`umount2`/`open_tree`/`move_mount`/`fsopen`/`fsmount` are traced, and a nested user namespace gets the mounts as copies with MNT_LOCK_READONLY set. Kernel automounts take their parent's `mnt_flags` (`finish_automount`; reasoned from the kernel source, not tested).
- **strace names:** with this PR, `?` appears only on `_ABSENT` names, and the probe uses the run's exact `-e trace=`. Product targets cannot set `env` (`load_registry`), so a target cannot change which strace PATH finds.

**Points (none blocking):**
1. **later**: propagation is assumed, not set. `_set_read_only` passes `propagation=0` and relies on util-linux `unshare -m` defaulting to `--propagation private`. The check is a snapshot, so on a host whose `unshare` left mounts shared or slave, a mount the host made under a kept path after the check would arrive rw. The actor would be the host, not the audited dependency. Fix: pass `MS_PRIVATE` in the `propagation` field of the same call (one constant).
2. **later**: the in-scenario half of `control-kept-read-only` covers less than `_inner`. Its `ro_kept` leaves out `dirname(sys.executable)`, and it uses `DEPAUDIT_KEEP_RO` without `realpath`, so a symlinked keep path would match no mountinfo entry. The authoritative check in `_inner` covers both, so this only weakens the control's evidence.
3. **later**: the probe and the run can use different strace binaries. `sandbox_available()` looks up strace on the harness PATH with nothing masked; `_inner` looks it up after `/home`, `/root` and `/tmp` are masked. With `~/.local/bin/strace` on PATH, the probe checks that binary and the run uses `/usr/bin/strace`. Because names no longer carry `?`, a run strace that lacks a name exits 1 (`scenario-failed`, not `pass`). So this is silent only for the aarch64 `_ABSENT` names. Fix: resolve strace once and pass the absolute path to both.
4. **later**: DEP-4b proves strace knows every name. It does not prove strace catches every ABI entry for those names. No control shows a compat-ABI call is traced, such as a 64-bit process making `connect` through `int 0x80` (the i386 `socketcall` multiplexer or the i386 numbers). This predates DEP-4 and is outside DEP-4b's text, so it gets a LATER line, not a fix here.
