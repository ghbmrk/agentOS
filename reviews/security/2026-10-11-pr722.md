**Threat check.** Assets: journal integrity and the engine's dispatch path (OP-1, OP-4), CAP-3 erasure, the broker's disk reserve (RES-4). Adversaries: a hostile guest (no access to the snapshot directory or to projector calls); a crash, torn write or failed read; a snapshot from another journal (restored backup, reset box); a faulty projection; a false pass.

Findings:

1. **release** (CAP-3; SIM-erase acceptance, no new row). Projection is pull-only, so after `Erase` returns, `<name>.snap` keeps the erased subject's derived content until the owner of the projector next calls `Sync`, or the next boot. Failure path once a projection is wired: FORGET is confirmed while a snapshot file on the journal volume still holds the subject. SIM-erase, which "rebuilds affected projections", should sync every projector before confirming, and its checker should scan the snapshot directory as well as the in-memory projections.
2. **release** (OP-4, OP-12; SIM-owner-hold acceptance, no new row). The envelope version covers the snapshot format, not a projection's rules. Failure path: an update changes the hold projection's quiet-hours or eviction rule, boot restores a pre-update snapshot, and the restored hold state differs from what replay from empty under the new rules gives (a security alert stays held, or a text the new rule holds is released). The first gating projection should carry a rule version in its snapshot data and refuse another in `Restore`, which the interface already allows. P3's "if a projection ever gates an effect" also triggers there: pacing decides whether a text is pushed (OP-12).

No blocker.
