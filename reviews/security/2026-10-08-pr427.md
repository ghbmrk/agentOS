## Threat check (CAP-3: forgotten content must not resurface)

Asset: a task the owner told the box to forget, still held on the agent machine's disk until item 2's take-back runs. Paths followed:

- **Retry resurrects content.** Structurally stopped. `carryAgent` and `resumeAgent` only call `takeBack(since)`, which rolls the agent back and never writes recall content. A retry after an unwrapped error repeats nothing, since `Reach.TakeBack` wraps every failure after `MarkTakeBack` in `ErrCarried` (`reach.go:290–305`), and `carryAgent` stops on `ErrCarried`. `carrying` and `Handled` keep `carryAgent` and `resumeAgent` from both running.
- **Crash mid-forget (same box).** Stopped. An owed item 2 is Succeeded in the journal, which never prunes it, and `resumeAgent` reads it at every open.
- **Restore from a backup while owed.** **Not stopped.** See point 1.
- **Logs and texts leak forgotten text.** Stopped. The new `log.Printf` lines print a wrapped error (lineage name, store error) or a constant Evidence string. The three owed texts are constants with no goal text, and the IDs carry a goal ID and a time.
- **Authority.** Unchanged. Only an item 2 approved with item 1 reaches `agentBack` (`siblingApproved`). There is no new input path.

## Points

1. **blocker (CAP-3, cited; was L3 release 3 and the builder's LATER l2): an owed take-back is lost on restore, while the owner has been told it will happen.** The forget log is what a restore replays: `learn.go:243–246` turns its `Agent` entries into `restored`, and `resumeRestored` takes the agent back. The three new owed branches of `agentBack` (no agent, recall off, not saved) never call `logForget`. Only the done paths do (`forget.go:616, 680`). Take a backup made after the task ran but before the forget. After a restore, item 1 is replayed, so recall is clean, but the agent's disk still holds the task, and no path will ever take it back. Meanwhile the owner holds "I will do it … and text you". Before this PR these cases ended in a truthful "may still hold that task". The PR turns a disclosed gap into a silent broken promise on the path D-065 built the forget log to close. A crash in `carryAgent` between a successful `takeBack` and `logForget` leaves the same gap. **Fix (about 4 lines, existing pattern):** call `f.logForget(grants.ForgetAgentGoal(id), since, true)` in each owed branch before `inform`, as the `ErrCarried` branch already does ("recall owes it"). Also do it in the `queued until recall opens` branch of the same function. `resumeRestored` already keeps an entry while `a == nil` or recall is off, and skips it once `Handled`, so no new mechanism is needed. Add one test: an owed item 2 appears in the forget log before it is done. Assumption 5 and LATER l2 then go.
2. **release (CH-12): in-boot retry is unbounded in count, with no owner signal on a permanent error. Agree with L3.** From the security side it cannot resurrect content, because nothing is recorded on these errors. Its cost is only that the owner is never told a "keep trying" has stalled while the agent still holds the task. The goroutines are bounded by approved forgets and wake at most once a minute, so this is not a resource risk. Once point 1 is fixed, a stalled one also survives a restore. Keep it as L3's new row: one CH-12 text after a bound, or a STATUS line.
3. **release (test coverage): the `ErrNotOpen` no-retry guard was dropped. Agree with L3.** A regression that started `carryAgent` on `ErrNotOpen` would loop `takeBack` once a minute while recall is off. `ErrNotOpen` records nothing, so the loop could not repeat a rollback or bring content back. It is a liveness and test gap, not a privacy breach. The fix is cheap (restore the row with `ResultSucceeded, forgetAgentNotOpen` and the `sleep` guard), and the builder may take it in the same push.
