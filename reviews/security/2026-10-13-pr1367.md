## Round 1 at 0df4bf0839918e6f571eed0ad344270c49fc80e8

### What changes for an attacker
Two new routes on the vault process's unlock socket: `GET /providers` and `POST /providers/private {provider, ok, code}`. They write or delete the `private-ok-<adapter>` marker that setup already writes, which the router reads on each call (`privateAllowed`). Allowing needs a tier-4 code (`approvedLocked`). Withdrawing needs none. A new signed-in page, `/providers/`, drives both routes. The model state gains `private`, and agentosd's STATUS reads it as one more Model line.

| Path | Stop | How |
|---|---|---|
| Default sends private data | none | The setup box still has no `checked` attribute, so no tick means no marker. `privateAllowed` is true only with the vault open, a built-in adapter and a `KindPrivateOK` entry. A locked vault, an unknown name or an entry of another kind answers false, so it fails closed. The new routes add no path that writes a marker without a code. |
| Page or guest forges an allow | structural | `putPrivate` runs `approvedLocked` (a TOTP from `SeedName`, used once through `LastStep`, with wrong codes counted, texted and capped) before `putMark`. Without an enrolled seed it gives `errNoCodeGenerator`. A compromised page (the localui uid) can withdraw, but it cannot allow without the owner's code. Guests have no route to the unlock socket: `peerListener` admits one peer uid. The page sits behind `signedIn` (agentosd's session check) and `ServeHTTP`'s `sameOrigin` POST check, with SameSite=Strict cookies. |
| Flip by name confusion | structural | `privateMarkOK` accepts only `adapterNamed` providers and refuses a marker name that holds another kind. It runs before the code check, so a bad name does not use up a code. The marker name is the fixed prefix plus a known adapter, so no other entry can be deleted. |
| Withdraw without code | accepted | Withdrawing narrows what leaves the box, as STOP, NO and revoke do (OWN-9). The owner gets a text for each change. The worst a page-uid attacker can do is deny service, which it can already do. |
| Enforcement only in UI | none | The broker decides. The router asks `privateAllowed` under `c.mu` for each call, and the page only renders what the vault process returns. |
| Atomicity | structural | `vault.Put` and `vault.Delete` save under the vault lock and roll back the in-memory map if the save fails. `putPrivate` holds `c.mu` through the open check, the mark check, the code check and the write. A failed write leaves the old answer in place, with the code already used, so it fails closed. |
| Concurrency with setup ops | structural | `setupPrivate`, `setupKey`, `sealEnroll`, lock and `putPrivate` all take `c.mu`, so no interleaving changes the vault between a check and its write. During an open setup an allow still needs a code from the enrolled `SeedName` (`errNoCodeGenerator` without one). |
| Key leak | none | `providersLocked` reports `hasKind` booleans and never reads a key value (CRED-1). Refusals show the vault's text only for 403 and 429 (the code's own wording). Every other refusal shows a fixed sentence. |
| localapi | unchanged | No file under `broker/localapi` changes, so the op count stays the same. The routes are on the unlock socket, as the second line and rotation routes are. |
| Flag-allowed providers | gap (S-1) | The page and list show the marker only. A provider allowed by `-private-ok` shows as "may not see" and cannot be withdrawn there. No stock unit sets the flag. |
