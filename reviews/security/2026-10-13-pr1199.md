Threat model. The assets are the box's vault and the owner's code-generator seed. The adversaries are:
- a compromised peer on the unlock socket (the local UI uid), which wants to destroy an owned vault or plant a card it knows
- a crash or reboot at any point in provision or reset
- a disk writer

The surface is `POST /card/provision` and `POST /card/reset` on the unlock socket. Neither has a caller yet (#1115).

| Path | Stop | How |
|---|---|---|
| Caller of the ops | structural | `unlockHandler`, served by `listen(..., unlockUID)` (SO_PEERCRED; `-unlock-uid` distinct from agentosd's) |
| Reset of an owned box, vault open | structural | `closedLocked` gives `errEnrolled` and the op returns 410. Without setup-open it returns 412. `TestResetIsRefusedOnceASeedIsSealed` |
| Reset of an owned box, vault locked (S1) | structural | `sealEnroll` persists `sealed` before the seal entry. `localsrv` finish calls SealEnroll before it saves `Finished`. The check runs under `rot.mu`+`mu`, the same locks as the deletes. Tested across a restart |
| Legacy sealed box, never unlocked; a missing state file | structural | No `provisioned` mark, so the reset does nothing |
| Racing an unlock | structural | Reset returns `errBusy` in `opening`. Everything else is under `mu` |
| Provision crash between the renames | structural | Vault first, keys last (keysbind), so nothing opens. Reset removes both |
| Different card | structural | Constant-time `EncodeCard` equality, and the card's passphrase and recovery key both open the files. Tested with a forged passphrase |
| Secrets in replies and logs | structural | Fixed `uerr` texts. The logged errors name no value |
| Fresh data key | structural | HW-10. The setup factor no longer opens the vault (tested) |
| State-file tampering | residual (L1) | Setting `provisioned:true` lets a locked reset delete the vault. This is the same trust class as deleting the files |
| Leftover `.card` after a crash and an open | gap (L2, later) | See below |

## Findings

- **R1 (release).** After a reset that removes files, nothing makes a new setup vault.
  - Provision needs an open vault, so the F10 loop (reset, card 2, confirm, Provision) answers 409 forever.
  - The same follows a stop between the renames.
  - K21 says setup "starts again from `init -setup`", but nothing runs it.
  - It belongs with #1198, and is folded into it.
- **L1 (later, tier A).** K21 should name the tampering residual of the locked latch.
- **L2 (later, tier A).** A leftover `.card` temporary can outlive the reset.
  - Sequence: a crash in `buildCardVault`, then an open of the setup vault before any reset.
  - `syncMarksLocked` clears `provisioned`, and reset then returns early.
  - The temporary opens with the old card's passphrase and holds the step-3 seed and card values. That conflicts with F10's "unconfirmed card unlocks nothing".
  - Fix: reset always removes `*.card`, or the sync keeps the mark while they exist.
- **L3 (later, tier A).** `Reveal()` strings and copied bytes in the entry copy are never wiped. Same class as K19; K21 does not say so.

S1: the vault process's half is met. The record and owner-state checks are agentosd's. Because the socket peer is the local UI, the `sealed` latch is the real guard. It holds because finish seals before it records.
