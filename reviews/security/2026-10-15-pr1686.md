## Review (7ce5ed95, round 1, Security record)

Verdict: REQUEST CHANGES. Comment: https://github.com/ghbmrk/agentOS/pull/1686#issuecomment-6175953509

Security review (tier A): REQUEST CHANGES

Reviewed head `7ce5ed95e6386550b39e73a233323d2c5356b77f` against #1638 and the #1574 Security S1 finding it comes from. I read the whole diff and the code around each owner send path, plus the gate's `Reserve`/`take`/`flush` and modemlink's `Send` error mapping.

The design is right. Counting before `Modem.Send` under `c.mu`, checking and counting in one `c.mu` hold on the paced paths, and rechecking in `Release` all close the modem round-trip window that S1 described. Every unsolicited owner send in `broker/owner` now goes through `reserveLocked`. The `Run`-path replies at `channel.go:963` stay uncounted, which is by design (O22). One ordering bug still lets the same CH-15 overshoot happen, and it also erases a saved stamp, so the fix does not fully close #1638 yet.

##### Findings

**1. blocker: the clock is read before `c.mu` is taken, and `reserveLocked` then deletes any later stamp. A paced send can still go beside a reservation that is in flight, and that reservation is lost.**
`broker/owner/pacer.go:269` (`NotifyNow`), `:307` (`reserve`, used by `sendRequest`, `sendCounted`, urgent posts, auto-reply notices and `Boot`), `:211` (`postHeld`) and `:430` (the `Release` recheck) all call `c.cfg.Now()` before `c.mu.Lock()`. `allowanceLocked` and `reserveLocked` (`:318`) both go through `recentSends`, which treats a stamp after `now` as a clock step back: it skips it in the count and drops it from the saved `Sent`.

Failure path (allowance 1): `NotifyNow` reads `now = t1` and waits on `c.mu`. Meanwhile `sendRequest` reads `t2 > t1`, takes `c.mu`, stamps `t2` and starts sending. `NotifyNow` then takes `c.mu`. `allowanceLocked(t1)` skips the `t2` stamp and sees 1 left, and `reserveLocked(t1)` rewrites `Sent` without `t2`. Result: 2 texts go against an allowance of 1, and only 1 stamp is saved, so the undercount lasts for the rest of the hour. With a higher `TEXTS` setting, it allows one more text later in that hour. This happens with the real clock whenever `c.mu` is contended (Go's mutex is not FIFO), and the reverse order (`reserve` holding a stale `now` behind a `NotifyNow`) erases the `NotifyNow` stamp the same way.
- Probe (in my clone, not pushed): rig with `PerHour 1`. `Config.Now` stalls `NotifyNow` after its read. `Request` runs at `t+1ms`, then `NotifyNow` resumes. On this head, `NotifyNow` returns nil, 2 texts are sent and 1 stamp is kept. When `c.cfg.Now()` is moved under `c.mu` in `NotifyNow` and `reserve`, both stamps are kept and `NotifyNow` cannot run between the read and the count. The second text in that run comes from the unchecked request path, which is #1685's residual.
- Fix: read `now` after taking `c.mu` in `reserve`, `NotifyNow`, `postHeld` and the `Release` recheck, so stamps are ordered by lock order. Alternatively, have `reserveLocked` stamp `max(now, last stamp)` and never drop stamps that are within a small skew of `now`. Add the probe above as a regression test. The existing tests use a fixed clock, so they cannot see this.

**2. release: a send that may have gone is refunded.**
`broker/owner/pacer.go:298-299` (`sendReserved`) and `broker/owner/autoreply.go:97-99` (`sendRequest`) call `unreserve` on any error. modemlink's `Send` returns `modem.ErrDown` for `ReceiptUnknown` too (`broker/modemlink/modemlink.go:262-266`), and its own doc says "the text may have gone". The old count-on-success code behaved the same way, so this is not a regression. But this PR now writes the rollback explicitly, and O28 calls keeping a stamp "the safe side". On a flaky line, every ambiguous send hands back a text the owner may have received, so the hour can overshoot by the number of ambiguous sends. Uncount only when the send provably did not go (`ReceiptNotSent`, or a `RequestSender`/`SendReceipt` path that can say so), and keep the stamp otherwise.

**3. release: O31 understates how early the stamp is.**
`broker/owner/ASSUMPTIONS.md:39` (O31) says the stamp is "a few seconds" before delivery. `modemlink.SendWait` is `OutboxWait + 3m15s` per text, multiplied by `(ahead+1)` (`broker/modemlink/modemlink.go:39`, `:314`). A text can therefore sit in the modem for minutes, and its slot frees that much earlier. With `TEXTS 1`, the owner can get two texts well under an hour apart. Either restamp at completion on success (move the stamp from `at` to the time the send returned) or correct O31 to state the real bound.

**4. release: the #1685 deferral is acceptable, but #1685's scope understates the gate residual.**
The deferral does not need to block this PR. The gate race is pre-existing, this PR does not regress it, it is outside the diff, and the window is narrower now. However, while the owner allowance is wired, `roomLocked` (`broker/grants/gate.go:1814-1819`) returns only that allowance and ignores the gate's own `g.sent`. `flush` calls `take(paced, 1)` for every page item (`gate.go:1982-1993`) before `RequestLocalEach` sends any of them (`gate.go:1995-1998`), so every `take` reads the same unspent allowance. With allowance 1, every page item in one flush is granted. The overshoot is as many notice texts as `requestEach` packs those items into (`broker/owner/approvals.go:104-131`), not "by one" as #1685 says. I found this by reading the code and did not probe it. Please add it to #1685's failure path and test, so its `TrySpend`-at-grant fix covers multi-grant flushes too.

##### Checked, no finding
- Crash and restart: the stamp is saved before the send, so a crash after the send keeps the text spent. A crash before an uncount spends a text that never went, which is the safe side. A failed `unreserve` save leaves the stamp on disk, also the safe side. A failed `reserveLocked` save matches the old O28 behaviour, which SIM-owner-hold covers.
- Applying `f` twice in `saveLocked`/`commit`: `commit` works on a `copyState` copy and keeps `c.st` unchanged on failure, so `unreserve` removes exactly one stamp.
- `unreserve` matches with `Equal`: equal stamps can be swapped for one another, so removing any one of them is correct.
- Urgent paths and `NotifyNow` under `URGENT AGENT ON` are unpaced by design (O21/O22). Each is now counted before its send.
- Privilege boundaries: no new boundary. `Allowance()` is read-only for the gate, and nothing here grants authority.

##### Tests
`go test -race -count=1` passes on this head for `./broker/owner`, `./broker/grants`, `./broker/question` and `./broker/cmd/agentosd`. The finding 1 probe fails on this head and passes with `now` read under `c.mu`.

##### Earlier findings
- **B1 (blocker): fixed.** All four paths now read the clock after `c.mu.Lock()`: `postHeld` (`broker/owner/pacer.go:216`), `NotifyNow` (`:273`), `reserve` (`:340`), and both reads in `releasePaced` (`:414`, `:463`). - **R2: fixed.** The refund now happens only on `errors.Is(err, modem.ErrNotSent)` (`pacer.go:311`). `ErrNotSent` wraps `ErrDown`, so every `errors.Is(err, modem.ErrDown)` check still sees the line as down: `owner.LineDown`, `bridge.codeOf`, the AT driver and the grants `LineDown` reason. I grepped the tree, tests included, and found no `==`/`!=`/`case` comparison against `modem.ErrDown` and no match on its error string. modemlink returns `ErrNotSent` only for `ReceiptNotSent`: not queued (line unusable or queue full, `modemlink.go:308-316`), timed out while still in `l.queue` (checked under `l.mu`, and `outbox` hands an item out only under `l.mu`, `:557-566`, so the item cannot also have been handed out), or `CodeRecipient`. These are all definite not-sent outcomes. The AT driver, sipline and the other `Send` implementations never return `ErrNotSent`, so they keep the stamp, which is the safe side. The simulator `modem.Line` returns it only when it is down and has delivered nothing. `ErrRecipient` (wrong `to`) keeps the stamp, also the safe side. A lying bridge could get a text refunded, but the bridge can already send anything on the owner line, so this is not a new boundary.
- **R3: fixed, with one gap (finding 2).** `settle` moves the stamp to the time the send returned, under `c.mu` (`pacer.go:310-330`).
- **R4: recorded.** #1685 now says the overshoot can be a whole page, and that `take` reads at a stale `now`.
- **One-hold test and renumber: in.** The `holdMutex` counter only increments under the lock. `TestPacedCheckAndCountShareOneHold` and `TestConcurrentCountsAreAllKept` cover post, NotifyNow and release, and the second test also covers urgent. O31 is now O32. Main's highest row is O30, and no stale `O31` reference is left.

##### Restamp review (checked, no new blocker)
- Between reserve and restamp the stamp sits at `at`, inside the hour, so every reader that takes the lock counts it. The restamp only moves it later, so the count can only grow. Every stamp and every read under `c.mu` takes its time under the lock, so lock order is time order, and a moved stamp can never be later than a lock holder's `now`. This does not reopen the two-sends race for readers that hold the lock.
- Crash between the send and the restamp: the early stamp stays, which O32 documents. Crash between reserve and send: the text is counted but never went, which is the safe side.
- Double application: `saveLocked` runs `f` on a `copyState` copy (`state.go:130` clones `Sent`) and runs it again only after a failed commit, on a fresh copy. Each run finds `at` on its own, so the stamp moves once. Each reservation is settled exactly once: `postHeld` either calls `unreserve` on a stale text or goes through `sendReserved`, never both. Equal stamps are interchangeable. `Sent` can end up out of order after a restamp, but nothing depends on its order (`recentSends`, `unreserve` and `settle` all scan it).
- Other modemlink callers: the digest queue still gets its `Receipt` from `SendReceipt`, and the `errors.Is(ErrDown)` behaviour is unchanged (above). The modemlink tests are tightened to `ErrNotSent` and `!ErrNotSent` on the Unknown outcomes.

##### Findings

**1. release: a restamp can hide a sent text from a reader that took its clock outside `c.mu`, and that reader is the grants gate.**
`broker/owner/pacer.go:576` (`Allowance(now)` with the caller's `now`), `pacer.go:386-393` (`recentSends` skips stamps after `now`), and `broker/grants/gate.go:1848`/`:1870` with `:1808` (the gate reads `g.cfg.Now()` and then calls `Allowance`). Before this delta, a stamp made well before the gate's `now` was always counted. Now, if `settle` runs between the gate's clock read and its `Allowance` call, the stamp moves past the gate's `now`. The gate then skips it as a clock step back and sees one more text left. Probe (local, not pushed): allowance 1, an urgent text in flight in the modem, gate `now` read, send returns. `Allowance(gateNow)` reads 0 before the settle and 1 after it, with 1 text sent. The window is the same microsecond gap between the gate's clock read and the lock that #1685 already describes, and the overshoot is one request text, so this is not a blocker. Fix it in #1685 or here, and add the restamp variant to #1685's failure path. One fix is to have `Allowance` count stamps after the caller's `now` (it is read-only, so counting them is conservative). Another is to have it ignore the caller's time and read `c.cfg.Now()` under `c.mu`.

**2. release: a send that outlives the hour is not counted at all.**
`broker/owner/pacer.go:321-329`. `settle` restamps only if it still finds `at` in `Sent`. A send that took more than an hour (up to `(ahead+1)*SendWait` plus `SendWait`, where `SendWait` is about 3m40s and `MaxQueued` is 64) has its stamp pruned by the next `reserveLocked` → `recentSends`. When it returns `nil` or `ErrDown`, nothing is recounted, so a text that went at return time spends no allowance. Probe (local): allowance 2, a send in flight, clock +61m, another count, then the send returns. Allowance reads 1, and it should read 0. Before this delta the stamp aged out the same way, so this is not a regression, but it breaks O32's promise that a text "spends the hour from when it went". Fix: on any non-`ErrNotSent` outcome, append `now` when `at` is not found, and add the 61-minute case to `TestCountRunsFromTheSend`.
