## Threat check

Adversary: a guest command in a worker sandbox that controls its own stdout, stderr, exit code and timing. Assets: host paths and runsc diagnostics (must not reach the guest), the broker's exec log, Exec's return bound, and the classification of runsc failures.

- **Guest stderr handling.** [Fact] `res.Stderr` is filled only from `gr`, the read end of the pipe that `--pass-fd 3:2` maps to the guest's fd 2. runsc's fd 2 goes to `runscErr`, which is read only by `logExec` (gvisor.go:309). No branch returns `runscErr` to the guest. This closes the earlier leak, where runsc text on a normal result was mixed into the guest's stderr. [Fact, real runsc release-20260928.0, sha512-pinned, run here as root] `TestIntegrationWorkerExec` passes at 9c3c45b, so the guest's `oops\n` arrives exactly. A scratch guest that wrote a forged Go panic trace to stderr and exited 2 came back as an ordinary result: code 2, its own trace in `Stderr`, and exec.log empty. The guest can no longer forge, split or crowd out a runsc crash (S2–S4 on #391 are resolved by construction), and its own panic is no longer withheld.
- **Fd passing.** [Fact, same scratch run] Inside the sandbox, `/proc/self/fd` shows only host fds 0, 1 and 2, and a write to fd 3 fails with EBADF. So the mapping hands the guest the pipe and nothing else. [Fact, code] `gw` reaches runsc only through `ExtraFiles` and is fd 3 there. `r.cmd` (gvisor.go:71) passes no other ExtraFiles and no flag that claims fd 3. The parent closes `gw` right after `Start`, whether or not `Start` failed. `gr` is close-on-exec and closed by defer. The sentry holds a write end to a broker pipe, which is the same class of capability as the os/exec stderr pipe it held before.
- **Isolation and the return bound.** [Fact] Reading the guest's pipe has a deadline at the context's end or at runsc's exit, plus `ExecWaitDelay` (AfterFunc / `stop()`). A guest that holds fd 2 open cannot pin Exec past that. The context-deadline path is tested; the runsc-exit-0 path is not (already LATER.md SR2-3n f1). `go test -race -count=1 ./vm/gvisor ./workers` passes with real runsc. [Fact] `capped` is read only after `<-copied`, so the copy and the read do not race.
- **Classification.** [Fact] `crashed` = exit 2 and any bytes on runsc's own stderr. The guest cannot write there, so it cannot cause a crash verdict, and a real crash trace cannot be hidden behind guest bytes. If runsc writes to stderr for some other reason and the guest exits 2, Exec fails closed: the guest loses only its own output. [Inference] A runsc killed by a signal (exit −1) after the guest started is still returned as a result. This is unchanged by #466, and the result now carries only guest bytes.

## Points

1. **later:** on a normal result (started, no `--log` line, not `crashed`), anything runsc wrote to its own stderr is now discarded rather than logged. That is safe, because it no longer reaches the guest, but it loses diagnostics. Logging non-empty `runscErr` on that path would keep them. No requirement asks for this.
