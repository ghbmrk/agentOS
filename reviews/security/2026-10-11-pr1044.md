# Security 4a, PR #1044 (MAIL-gen)

Record: PR #1044 · package MAIL-gen · head 73109a9

**Security section (stage 4a), tier A** (`broker/mail/mailsock`, `cmd/agentos-egress`, `cmd/agentosd`). Cites CRED-1 and ADP-2. The L3 accepted at this head (6111474343), after a fix-list (6111129443: B1 approval crosses a rebind, R1 empty generation). `go test` passes at head on mailsock, agentos-egress and agentosd.

**Threat check.** Assets:
- the mailbox credential;
- the owner's authority to send from, and organize, one specific mailbox.

Adversaries:
- a hostile guest submitting mail intents;
- a race between an owner's mailbox replacement and a queued, approved or in-flight intent;
- a stale or older vault binary.

| Path | Stopped | How |
|---|---|---|
| Credential reaches the model through the generation | structurally | `mailSettings.generation()` hashes address, imap, smtp, starttls and user, never the password (a separate vault record). The hash travels only on `mail.sock` (uid-restricted to the broker) and lives in agentosd memory. `errMailGen` goes to the gate's log only: the guest reads the gate's fixed reason. The generation is not in the journal or any evidence |
| Caller sets or forges the generation | structurally | The vault derives it from its own stored settings (`mailSource`). agentosd learns it only from the `address` reply and pins it with `Pin(gen)`. `journal.Intent` has no generation field, and `stamp` is keyed by intent ID with the bound generation as its value, so a guest-chosen ID can only cause a refusal of its own intent, never an old generation for a new one |
| Approved send runs on the replaced mailbox (same process) | structurally | The mail account's verifier is an Escalator (`wire`), so the gate calls `Escalate` at the first evaluation of every non-delivery mail intent, and send is among them. That call stamps the generation. At the owner's YES, `settle` → `Authorize` re-evaluates, the stamp mismatches and the gate denies. A rebind landing between the stamp and the store call meets a store pinned to the old generation, which `call()` refuses before its switch (the check and the use read the same `acct`) |
| Grant-authorized organize runs on the replaced mailbox (same process) | structurally | The same stamp is checked in Escalate, Verify, Execute (NotApplied) and Reconcile (Unknown). A revert of `mail.go` fails `TestMailApprovalDoesNotCrossAccountGenerations` (L3 delta) |
| Unpinned or empty generation turns the check off | structurally | `call()` refuses every op except `address` when `acct.Generation == ""` or the request's generation differs. `Client.Account` rejects an empty generation, so `poll` never binds `Pin("")`. Both halves are pinned by `TestEmptyGenerationFailsClosed` (L3 revert checks) |
| Evidence delivery (`OriginEvidence`) after a replacement | structurally, by another check | `evaluateDelivery` never calls `Escalate`, so its first stamp is at `Execute`. The `Destination` check still denies unless the destination is the bound account's own address, and the recipient is fixed to it. A replacement with the same address delivers to the same address. No owner approval is involved |
| Approval crosses a daemon restart (M19 residual) | owner-approved: structurally; grant-authorized: bounded by the grant | See below |

**M19 residual and the L3's triage.** I agree with the L3 delta's analysis, and the code confirms it:
- Owner decisions (`Gate.decided`) are in memory only.
- Held sends are cancelled by a restart and re-asked as new (`unhold`, `why == "restart"`).
- A pre-switch YES therefore cannot run on the new mailbox after a restart.
- Send is irreversible and always asked, except an ADP-11 auto-reply. An auto-reply's hold is also cancelled by a restart and re-evaluated, and its rule must verify the thread in the mailbox now bound (M10).

What crosses a restart, or the 24 h `genKeep` expiry, is only an intent that a grant on account `mail` would allow if it were submitted fresh against the new mailbox. Production `mail.Config` carries no grant-supplied, mailbox-specific folders (`tune` is test-only), so the grant does not describe the old mailbox. The residual therefore gives no authority beyond the grant.

- **Release (L3 item 1): agreed.** Strengthen it from wording alone to wording plus a check. Both recheck triggers are future code changes, and only a test catches those. Text in M19 does not.
- **Later (L3 item 2, journal the generation): agreed, tagged `recheck`.** OPERATING §2 forbids `later` for tier-A security findings unless they are wording. This one stands because it is the hardening of a residual whose security content is carried by S-R1's triggers, and it has no exploit path today. If a trigger fires, this becomes a blocker.

**Findings**
- **S-R1 release** (amends L3 delta item 1; land it on this branch with that item, otherwise add it as a BOARD row under MAIL-gen). Invariant: CRED-1 and ADP-2, intent bound to its mailbox.
  - Failure path: a later package makes owner decisions or held sends survive a restart, or shortens `genKeep` below `grants.DefaultFresh`. A YES given for mailbox 1 then runs on mailbox 2, and no test fails.
  - Fix: amend M19 with the bound and both recheck triggers, as L3 item 1 says.
  - Also commit the L3's restart probe as a test: approve under gen-1, switch to gen-2, rebuild the gate, engine and `lateMail` on the same journal, rebind, Dispatch, and assert that nothing runs on either mailbox.
  - Add a one-line test that `genKeep >= grants.DefaultFresh`.
- **S-L1 later** (wording). The agentosd `ASSUMPTIONS.md` rows are stale.
  - MW2 still says a rebind is driven by "a new address" and that "a queued intent is judged afresh at its recheck". After this PR, a queued intent stamped under the old generation is refused.
  - MW9 says the `address` op returns the address only. It now also returns the generation.
  - Update both to point at M19.
- **Concur** with L3 delta items 2 to 4 as later:
  - Item 2: see above.
  - Item 3: an Unknown attempt across a rebind produces no effect.
  - Item 4: owner UNDO across a rebind is owner-only (MW5), and M9 restores only messages still where the agent put them with its flags, so on a different mailbox nothing matches. None of these is an adversary path.

Observation, not a finding: `stamp` reads `time.Now()`, not the injected clock (MW3). In production both are the host wall clock, and 24 h is far longer than `Fresh`, so the bound holds.

Findings: blocker 0; release 1; later 1.
