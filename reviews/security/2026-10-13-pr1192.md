Threat model.
- The asset is the access point's Wi-Fi password. The new one comes from a rotation. The old one is presumed lost (ARC-1: "the owner rotates it under REC-4 after a suspected loss").
- The new surface is one in-process method, `APLoader.Rekey(ctx, password)`. Nothing calls it yet (#1191). The loader also keeps the running `APConfig`, password included, in memory while the access point is up.
- The adversaries are:
  - a holder of the lost card, near the box, who wants to keep joining the access point;
  - a device on the access point that wants to reach box ports once the access point restarts;
  - any local process that wants to read the password.

## Findings

- **S-R1 (release, new issue CTRL-card-rot-ap-3, #1193).** A failed `ap.Stop` leaves the old, presumed-lost password on air, and a retried `Rekey` then returns nil.
  - Cause. `bringDown` clears `l.up` and `l.cfg` even when `BringDown` fails. A later `Rekey` sees `l.up == ""` and returns nil.
  - Review probe (not committed): a fake AP whose `Stop` errors and keeps running. The first `Rekey` returns "did not come down". The second returns `<nil>`. Afterwards `started=true`, the password is still the old one, `exempt[wlan0]=false` and `failed[wlan0]` is set.
  - Bound. The unexempt still ran, so the inbound drop covers the box's own ports. But a holder of the lost card can still associate. Forwarding is no longer held by agentos_ap's forward chain. A caller that retries on error is told the rotation took effect.
  - Requirement. REC-4 / ARC-1: rotation after a suspected loss must retire the old Wi-Fi password.
  - Failure path. hostapd refuses to stop. The loader retries `Rekey`, gets nil, and the done page says "rejoin with the new card", while the lost card still joins.
  - Not a blocker, because no caller exists until #1191.
  - Fix. While `l.failed` holds the access point's interface, `Rekey` returns an error (or keeps a "rekey pending" state), and a test covers a `Stop` failure, not only an nft one. This is a few lines, so the builder may fold it into this PR instead.
- **Note for #1191 (not a separate finding).** The wiring should state:
  - the recovery after a `Rekey` error: the access point is down, so the loader calls `Up` again with the stored new password, or `Down` then `Up` after a failed stop;
  - that it runs `Rekey` on a context that the phone's request cannot cancel, because the bring-up uses the caller's context and a cancel between down and up leaves the access point down;
  - that the AP driver writes hostapd.conf root-owned 0600, by atomic rename, outside the journal (ARC-1).
