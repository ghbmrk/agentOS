## Threat check

Actors: a hostile guest (the worker's command and anything it spawns, steered by the agent, which also picks `timeout_seconds`), and runsc panic output (a Go runtime trace on runsc's fd 2, which is the guest's stderr pipe too).

| Threat | Path | Holds at cbbf80e? |

## Findings

### S1 (blocker, defect; RES-4, CAP-8, brief): a runsc panic near the deadline reaches the agent as timed-out stderr
- [Fact] `panicked := … && ctx.Err() == nil && watch.found()`. When runsc panics while the guest command is still running, the guest keeps holding the stderr pipe, so `cmd.Wait` waits up to `ExecWaitDelay` (3 s) after runsc's exit. If the exec's deadline passes in that window, `ctx.Err()` is set, `panicked` is false, the pid file is full and `--log` is empty, so Exec returns `vm.ExecResult{Stderr: <trace>}` with `exit status 2`. `Manager.Exec` (worker.go, `DeadlineExceeded` branch) returns it as `TimedOut` with `Stderr: r.Stderr`, and `toolExec` answers it to the agent.
- [Fact] Reproduced against cbbf80e with a scratch fake runsc (pid written, a child holding stderr, the panic trace with a canary host path, exit 2; not committed): with a 10 s deadline Exec answers the error and no output; with a 1 s deadline it answers `err=exit status 2`, `ctx.Err()=context deadline exceeded`, `Stderr="panic: open /canary-host/x: permission denied\n\ngoroutine 1 gp=… [running]:\n"`.
- [Inference] The guest needs no timing: the agent sets `timeout_seconds` (any value > 0), so with a timeout under 3 s every runsc panic during the command lands in the window. It still needs a runsc panic, as the whole package does.
- **Fix:** drop `ctx.Err() == nil` from `panicked`. A cancelled exec kills runsc with SIGKILL (exit −1), so the term guards nothing; with it gone the branch already returns `(ExecResult{}, err)` on a done ctx, which `Manager` answers as `TimedOut` with no output. Add a fake-runsc case whose guest holds stderr past runsc's exit 2, run with a deadline under `ExecWaitDelay`, asserting no output in `gvisor.Exec` and no canary in the `worker_exec` answer.

### S2 (blocker, scope; OPERATING §2): the split-marker gap is classed Later

- **Fix:** move it to the Release table (or a BOARD row), together with S3's signal form; see S3 for the row's content.

### S3 (release, Low; RES-4, CAP-8): the trace form match has two holes
- [Fact] Split writes (the builder's f1): Go's runtime writes each `print` argument separately once the m is dying, so a guest writing to stderr between them breaks `goroutine [0-9]+ …\[`. A guest that can trigger the runsc panic itself knows when to write.
- [Fact] A fatal signal outside Go code prints `SIGxxx: …` and `PC=…` with no marker and exits 2. [Inference] Rare in pure-Go runsc (a nil dereference in Go code becomes `panic: runtime error`, which is matched).
- **Proposal (new row):** stop sharing the stream rather than widen the pattern: give the guest's command a stderr that is not runsc's fd 2 (for example an in-sandbox wrapper that moves the command's stderr to a separate donated fd, or a pinned runsc with a non-internal `--panic-log-fd`), then drop `panicWatch`. Until then, matching `PC=` after a `SIG[A-Z]+: ` line and tolerating interleaving are cheaper partial steps.

### S4 (release, Low): the guest picks where the logged trace starts
- [Fact] `panicWatch` keeps text from the first marker on, clipped to 16 KiB. A guest that writes `panic: ` and 16 KiB before runsc's real trace makes `exec.log` hold only its own bytes, so the broker loses runsc's trace for that failure. Output withholding is unaffected.
- **Proposal:** until the header is found, restart `text` at each new marker. Fold into S3's row.

No owner-facing or broker-control path takes guest bytes beyond those above. Pre-existing and unchanged: `exec.log` stores guest-influenced bytes raw (SR2-3h `wait` case), so its entries are evidence, not authority.
