## Round 1 (ee5a267)

This is the tier-A Security section (OPERATING §4, stage 4a). It ran in its own fresh session, apart from the L3 and Potency/UX sessions, and did not rely on the builder's reasoning. Tier A per `tools/risk_tier.py`. No new broker package.

### What changes for an attacker
In setup mode, agentosd now serves the modem bridge's ops on owner.sock through `modemlink.SetupLine`, and adds three localui.sock ops (`page_setup_line`, `page_setup_send`, `page_setup_inbound`). The box can now text and receive texts before it has an owner: it sends setup's fixed texts to numbers the page names, and it passes PAIR texts from any sender to `Server.OfferText`. agentos-modem now runs with no `OWNER_NUMBER`.

### Threat check
| Path | Stop | How |
|---|---|---|
| Another local uid drives the setup modem line on owner.sock | structural | The setup endpoint's `PeerUID`/`PeerGID` is `-modem-uid`, which `main.go:448` already refuses if negative or equal to the broker's uid (so the `ModemUID == nil` check at `setup.go:119` cannot fire in production). It is served in the same `Start` call as localui.sock and only while `run` runs. |
| Setup ops after finish | structural | `page_setup_line`, `page_setup_send` and `page_setup_inbound` go through `s.open`. Removing it from any of the three is caught by a test. `PairTexts` stops on `ErrSetupClosed` (caught too). A long poll that is already in flight at finish can still hand over one text, but `OfferText` drops it because `Owner != ""`/`Done`. The owner.sock endpoint is torn down when `run` returns. |
| The page (or a compromised localui) spends the SIM | structural | The fixed-text allow-list is anchored (`localapi/setup.go` `setupTexts`), with an E.164 `to`, 5 a minute and 20 an hour counted before the send. Removing the allow-list, either cap or the per-minute cap is caught by a test. What is left, accepted per ST3: up to 20 texts an hour of a fixed text with 6 chosen digits to any number. |
| Parsing the modem's output | structural | `setState` refuses a bad `OwnerLine`, ICCID or `Number` (`ValidNumber`, E.164). `inbound` relies on `Inbound.Valid` (length bounded) and passes on a text only if its first word is PAIR, its From is valid and its sender is not named. The inbox holds 8 and the `inIDs` TTL is 10 minutes. The number shown on the page is checked again by `phoneRe` in localsrv and in localui. No string from the modem reaches a shell, a file path or a template unescaped: `smsLink`/html/template are pre-existing. |
| Spoofed or replayed PAIR text | structural | Pairing still depends on the per-device pair code or the card code (`OfferText`, constant-time compare, `PairTriesPerHour = 10`). The pair map is cleared once a pairing succeeds, and IDs are deduplicated. A spoofed From with a valid code only binds a number the attacker does not hold. |
| SIM binding (TOFU, ST4) | structural with a test gap | `Record` runs only on `StateUnbound`, once per process. `recordOwnerSIM` is pre-existing. See F1. |
| Numbers, codes or texts in logs | structural | Nothing new in the diff logs anything. `SetupSend`/`SetupInbound` redact through `String`/`GoString`. The bridge's `Logf` lines are fixed strings. The bridge with no `OWNER_NUMBER` fails closed: `fromOwner` needs `Owner != ""` (`at/driver.go:459`), and `Link` after setup compares `From == Owner` exactly. |
| Secrets in texts | ok | The texts carry no card secret or AP PSK. The claim "Page code" goes only to the From that presented the card's code. |

### Findings
- **F1 (blocker, defect; CH-12, ST2/ST4): three gates in the new setup line have no test that fails without them.** Mutation probes:
  - `broker/modemlink/setup.go:193`: dropping `in.Named ||` survives. A named sender spelled like an E.164 number would then reach `OfferText` as a pairable number.
  - `broker/modemlink/setup.go:203`: removing the inbound per-minute cap survives. The cap is also 20 (`InboundPerMinute`), while `broker/cmd/agentosd/ASSUMPTIONS.md:237` (ST2) says "At most 5 a minute are kept".
  - `broker/modemlink/setup.go:293`: recording the ICCID on any state, not only `StateUnbound`, survives. That would re-adopt a swapped SIM during setup, which ST4 rules out.

  Fix: add a test for each of the three, and make ST2 and the code agree, either through a setup-specific cap of 5 or by correcting ST2 to 20.
- **F2 (release; A1/CH-12): "did not match" replies go to unverified senders out of setup's shared text budget.** `broker/localui/setuphooks.go:171` texts `OfferText`'s wrong-code reply (`localui/setup.go:648`) to any valid From. Failure path: a stranger who knows the box's number sends 10 wrong `PAIR` texts. That locks pairing by text for an hour (`PairTriesPerHour`), uses 10 of the 20-an-hour sends the owner's number fallback needs, and can point those replies at a third party's number by spoofing From. The attacker can repeat this every hour, so setup step 2 never passes. Proposal: send no reply to a wrong code, or give replies their own small budget per sender, separate from the page's sends.
