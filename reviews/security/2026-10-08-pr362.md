## Evidence

- [Fact] Primary source: `runsc/cmd/util/util.go`, `runsc/cli/cli.go` and `runsc/cmd/exec.go` read at tag `release-20260928.0`. `util.Errorf` writes to stderr unconditionally and a JSON line to `ErrorLogger` (the `--log` file) when set; `Fatalf` goes through `Errorf` and exits 128. With neither `--debug-log` nor `--debug-log-fd`, the debug emitter is `io.Discard` ("Stderr is reserved for the application"); `AlsoLogToStderr` is off by default. In `exec`, the internal pid file is written only after `c.Execute` returns the guest's pid; every later runsc error (`writing internal pid file`, `waiting on pid`) is an `Errorf`. V32's description matches the source.
- [Fact] So every runsc message before the guest starts is caught by the empty pid file, whether or not it reached `--log` (this includes a flag-parsing `Fatalf` before `ErrorLogger` is set, and a pre-start Go panic); every `Errorf` after the start is caught by a non-empty `--log`.
- [Fact] Mutation checks: disabling the new branch in `gvisor.Exec` fails `TestRunscFailureAnswersNoOutputAndNoRunscText`, `TestExecLogStaysWithinItsCap` and workers' `TestRunscMessagesNeverReachTheGuest` (which shows the canary host path reaching `worker_exec`'s stderr); keeping only the pid check fails both canary tests on the `wait` case. The tests bite.
- [Fact] `go test -count=1 ./vm/gvisor/ ./workers/` passes at b9082c9, and the three new gvisor tests pass under `-race -count=3`. CI at review time: canary, checks, hostcheck, machines (real runsc) and dependency-audit green; broker still running.
- [Fact] `gvisor.Runtime.Exec` has one caller (`vm.Manager.awaitExec`), and `Manager.Exec` one (`workers.Tools.run`), whose errors leave through `guestErr` (K21).

## Threat check

Asset: host-side data (host paths under the state dir, machine and container IDs, runsc diagnostics). Adversary: **G**, the guest driving a worker, who reads `worker_exec`'s answer and every worker tool error.

| Path | Stop | Kind |
|---|---|---|
| runsc fails before the guest starts; its `Errorf`/`Fatalf` text is on the shared stderr | Empty `--internal-pid-file` ⇒ `Exec` answers `ExecResult{}` and an error; workers turns it into a ref. [Fact: `prestart`, `panic` cases, both packages] | Structural |
| runsc fails after the guest started (`waiting on pid`) | Non-empty `--log` ⇒ same; the guest's own output in that call is dropped too [Fact: `wait` case, which also checks no "guest" text leaks] | Structural |
| runsc info/warning lines | `--debug-log` per exec; without it runsc discards them, never stderr [Fact: source] | Structural |
| `Exec`'s own error text, which names the exec log's host path | Reaches the guest only through `guestErr`, which refs it (K21) | Structural today; see 362-2 |
| runsc Go runtime panic after the guest started | Goes to stderr with no `--log` line and reaches the guest as its stderr (V32 known gap) | None; see 362-1 |
| Timeout or cancel mid-exec | `Manager.Exec` maps ctx errors to fixed text or `TimedOut`; when runsc also failed, the output is empty | Structural |
| The guest reads or plants files in the exec log or per-exec logs | All in the runsc `--root` state dir (0700, broker-held); files 0600 (`CreateTemp`, `keepConsole`), per-exec files removed [Fact: test checks mode and cleanup] | Structural |
| The guest fills the disk through runsc's logs (RES-4) | Each failure adds at most 3 × 16 KiB; `exec.log` rotates at 1 MiB with one old copy [Fact: `TestExecLogStaysWithinItsCap`] | Structural |
| The guest forges a "runsc failure" to hide its own output | It can only lose its own output; it cannot write the host-side `--log` or pid file | Not a gain |

Note (not a finding): `exec.log` holds guest-controlled text (argv, stderr) and a guest can rotate earlier entries out by failing execs repeatedly. It is broker-only with no automated reader, and the broker log keeps each ref line, so nothing is owed.
