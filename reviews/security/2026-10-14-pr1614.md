## Threat check

**Who can obtain or replay the permit.**
- **Where it is held.** The permit (`heldWiFi`) lives only in agentos-egress memory, under `rot.mu`. It is set only on a clean commit or on a 409 (`ErrCardNotStored`) commit whose parts include Wi-Fi.
- **How it is taken.** `takeRotatedWiFi` clears it before it checks the lapse, so a take is one-shot. My probe ran 32 concurrent takes after one commit, and exactly one succeeded (race detector on).
- **Refused commits hold nothing.** My probe covered these cases, each answering as shown:
  - wrong rotation ID (410);
  - refused card, `ErrNextCard` (400);
  - lapsed rotation (410);
  - a replayed commit after a successful one (410).
- **A cancel after a commit keeps the permit.** The no-answer path relies on this, and it holds.
- **The page sends no network.** `page_rotate_ap_net` carries only `localapi.Auth`. agentosd writes only what it took, and only if:
  - `ap-net.json` exists;
  - the SSID is unchanged;
  - `Marshal`/`Validate` passes (my probe refused an injected newline, an empty password and a non-card shape);
  - the write is durable at 0600.
- **Who can reach the take route.** It is `POST /rotate/wifi` on the verify socket. The socket is 0666, and its peer check is uid == broker uid, which is 0 in the shipped unit (`-broker-uid 0`). So any root process can take the permit, including agentos-ap's root hostapd (R2).

**Lifetime, crash and restart.**
- The permit is memory only and lapses after 5 min.
- A new begin, a lock or a take drops it. My mutants M2, M3 and M4 confirm this.
- A restart of agentos-egress or agentosd loses it, which fails closed: the old password stays and the page shows the note.
- The setup-mode paths that take `rot.mu` (`provisionCard`, `resetCardRemade`, `startSetup`) cannot coexist with a sealed-vault rotation.
- The open gap is a crash between the commit and the take (or an `ErrDirSync` followed by a power cut, now reported as "switched"). Nothing reconciles the file afterwards (R3).

**Fail-open, lock order and races.**
- **Fail-open:**
  - Every refusal in the agentosd hook returns the fixed `errRotateAPNet`.
  - localsrv checks the session before it calls the hook.
  - A nil path, nil taker or empty verify socket gives a nil hook, and the op is refused.
  - The no-answer path cancels, then hands off. A vault that never committed holds nothing, so the hand-off fails and the note is shown.
- **Lock order:** it is `rot.mu` then `c.mu` everywhere, including `custody.lock`, `commitRotation`, `takeRotatedWiFi`, provisionCard and setupopen.
- **Races:** a race-detector probe of concurrent commit, takes and lock passes.
- **No unbounded blocking:** the Verifier client has a 2 s timeout, and the localui call has `callTimeout`.

**Secrets in logs and notes.**
- `RotatedWiFi` redacts `String`/`GoString`.
- The client's errors carry only the status or fixed text.
- The vault's `notify` lists only part names.
- `card.Noted.Note` is a fixed constant (`wifiKeptInEffect`).
- The in-effect page test checks that the password is absent.
- Nothing new logs the network.

## Findings

- **R1 (release; REC-4, CH-7, ARC-1; #1522's acceptance "a session without a matching commit cannot change ap-net.json").**
  - **Gap.** No test shows that a commit which does not put the card in effect holds no permit. Holding on `ErrNextCard` (400, rotation kept) or on the spent default branch survives every suite.
  - **Failure path.** The permit would sit 5 min for a network the vault refused. Any page session could then put on the air a Wi-Fi password the owner was told to discard, which locks the owner off the Wi-Fi.
  - **Where.** The code is correct today: broker/cmd/agentos-egress/rotation.go:328-344.
  - **Fix.** Add a test to broker/cmd/agentos-egress/rotwifi_test.go that commits with a wrong ID, a refused card (`WiFiPassword: "ab"`), a lapsed rotation and a failure before any slot write, and asserts `ErrNoRotatedWiFi` after each. My probe `TestSecProbeFailedCommitsHoldNothing` covers the first three.
- **R2 (release, fold into #1426; ARC-1, CRED-1, REC-4).**
  - **Problem.** The verify socket (broker/cmd/agentos-egress/server.go:807, mode 0666; peer uid == `-broker-uid 0`) is reachable from agentos-ap's root hostapd, which parses pre-auth frames from radio range. broker/cmd/agentos-ap/agentos-ap.service:52 does not deny `/run/agentos-egress`.
  - **Effect.** A hostapd compromise can drain the permit, which suppresses the switch away from a lost card's password. It can also, as before this PR, call `/recall-key`. The added harm is small, since that root can already write `ap-net.json`.
  - **Where N5 is wrong.** broker/apnet/ASSUMPTIONS.md N5 ("broker uid, or root") does not say that the broker uid is root in the shipped unit. It also does not say that #1426 as written narrows only the AP's write set, not this socket.
  - **Fix.**
    1. Add `-/run/agentos-egress` to agentos-ap's `InaccessiblePaths`, pinned in `broker/cmd/agentos-ap/unit_test.go`.
    2. Add that line to #1426's done-when.
    3. Reword N5's "who takes" residual to name agentos-ap.
- **R3 (release, promote #1526 item 1 from later; REC-4, CH-7, CRED-8).**
  - **Problem.** P-1 (reconcile `ap-net.json` with the vault's committed card) is classed later, but it is a tier-A security path. A crash or power cut between the commit and the take leaves a lost card's password on the air with no page saying so. The same happens if the page dies before the hand-off.
  - **Newly added by this PR.** An `ErrDirSync` followed by a power cut (broker/cmd/agentosd/apnetrot.go:52) can roll the file back after the owner was told "switched", and the permit is already spent.
  - **Why it is fixable now.** The verify-socket channel from #1522 exists, so a fix is possible.
  - **Fix.**
    1. Add a read-only verify route that returns the committed Wi-Fi network while the vault is open.
    2. Have agentosd, at start and after an unlock, rewrite `ap-net.json` when it differs (same SSID, `Validate`, durable).
    3. Relabel or split #1526 item 1 to `class:release`.

## Observations (no finding)

- `TakeRotatedWiFi` maps 503 to `ErrVaultLocked`, but the route never sends 503. It is dead and harmless.
- If localui's call times out after agentosd wrote the file, the page says "could not switch" although it did. That is the conservative direction.
- The password strings stay in the Go heap until GC, as for every other card secret in the vault process.
