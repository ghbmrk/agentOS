Threat check: a mail provider that rebuilds a folder (new UIDVALIDITY, reused UIDs), a sender who chooses its own Message-ID, restarts and fault timing between the gate and Execute. Can a guarded mutation, an undo or a watcher fetch act on a message the gate never approved, hide an alert, or record evidence naming the wrong message?

- [Fact] The F5 path is closed structurally. `SetFlags`, `Move` and `Fetch` take a `mail.Ref` (or a validity) and `selectAt` compares it with the UIDVALIDITY of the SELECT in the same session before any UID command; a mismatch or validity 0 returns `ErrValidity` and nothing is sent (imapsmtp.go `selectAt`). `Find` fetches under its own SELECT's validity, so every `Message` carries the epoch it was read in.
- [Fact] No retry by the old UID. On `ErrValidity` before any change the executor returns `NotApplied`; after flags were set it returns `Unknown` with its own evidence, and `Reconcile` re-plans by Message-ID, so it reports `Unknown` or a re-checked state, never the old UID's success.
- [Fact] Evidence names the message acted on: `Change` records `Validity` and `UID`, and undo of a flag-only change skips a message whose Ref differs. Undo's restore is itself validity-checked.
- [Fact] The watcher fetches under the validity it listed; a reset between list and fetch fails that poll and the next re-reads (M12 unchanged).
- [Fact] Same-epoch deliveries and expunges are not refused (`TestSameEpochMutationsStillRun`); M9 stays separate, as the brief requires.
- [Fact] No credentials or personal data: test data are synthetic (`bank.example`, the canary word "wombatcall"). `mailtest.Reset` is test-only.
- [Fact] `go vet ./mail/...` is clean and `go test -race -count=2 ./mail/...` passes at f585b55.
- [Fact] Mutants applied at f585b55, each run over `broker/mail` with -race and reverted:
  - M1: `selectAt` never refuses. Killed.
  - M2: validity 0 accepted. Killed.
  - M3: `Find` tags messages with validity 0. Killed.
  - M4: refusal after flags reported `NotApplied` (claims nothing changed). Killed.

- [Assumption] UIDVALIDITY does not change inside one selected session without the server ending it (RFC 3501 §2.3.1.1 ties a validity change to a new session). The check-then-act in one session rests on this; a server that rebuilt a folder under an open SELECT would break any IMAP client.

## Points

- S1 (release, new BOARD row SR3-5-f1; reclassed from the PR's `later` f1 because OPERATING §2 makes a tier-A security finding never `later` unless wording; not a blocker because #424 neither introduces it nor makes it reachable through UID reuse): Execute and Reconcile re-plan by Message-ID (`planOrganize` → `place`) and recompute `pl.alert`, but never compare it, or the Ref, with what `Escalate` approved. If, between the gate and Execute, the approved message is gone and another message with the same Message-ID (unique in its candidate folders) is an alert, Execute hides it without the change-account ask. Undo of a move re-resolves the same way. Reachability today is low: the sender chooses a Message-ID, so a genuine third-party alert colliding with a recorded ID needs that sender's cooperation, and an attacker-sent fake alert is the attacker's own mail. It is still the one gap left in "a mutation lands only on the message the gate approved" (ADP-2, OP-3). Fix: carry the gate's `Ref` (or at least its alert bit) in the intent and have Execute return `NotApplied` when the re-planned Ref differs or `pl.hides && pl.alert` was not escalated. Fold in L3 point 3 (SetFlags and Move in one checked session) only if it stays small.
