## Evidence

- [Fact] **One parse rule at both boundaries.** `meter.limit` and `route.parseChat` both run `meter.Object`, which reads the top level token by token and refuses a key repeated under Unicode simple folding, and a key that folds to a canonical key but is spelled differently (meter: `n` and the three limit keys; router: every `chatRequest` field, taken from the struct tags by reflection, so a new field is covered automatically). `fold` picks the least rune of each `unicode.SimpleFold` orbit, the same representative encoding/json's field matching uses, so the meter's equivalence classes are the decoder's.
- [Fact, probed] **Encodings.** A JSON escape (`"N":2`) is unescaped by `Token` before the check and refused as `N`. KELVIN SIGN and LONG S variants are refused (tests). Invalid UTF-8 in a key decodes to U+FFFD and does not match any field. Near-miss spellings (`maxtokens`, `max-tokens`, `MaxTokens`, `n\u0000`) are not matched by encoding/json under the go.mod toolchain and are dropped by the typed re-encode. Malformed objects (`{1:2}`, trailing comma, missing colon, `[]`, trailing NUL) return an error; the `t.(string)` assertion cannot panic, since `Token` errors in key position on anything but a string.
- [Fact] **Forwarded limit ≤ reservation, structurally.** The meter clamps every present limit key to 1..MaxReserve and reserves their maximum; when no key the path's API reads is present it inserts `max_completion_tokens` (chat) at DefaultReserve and reserves at least that. The router serves only the chat-completions paths, so it always sees a limit the meter set; `clamp` only lowers a positive value, and both providers serialize from those fields (Anthropic takes `MaxCompletionTokens`, else `MaxTokens`). The bound holds whatever MaxOutputTokens is configured to, so it does not rest on guest.go's "configure MaxReserve as MaxOutputTokens".
- [Fact] **One choice for every provider.** The meter refuses `n` unless its raw value is exactly `1` (also refuses `1.0`, `null`, `0`); the router refuses `N != nil && *N != 1` after parse, before route selection, so no provider is dialed (test `TestSR3_7RouterRefusesSeveralChoicesForEveryProvider`, both providers, recording upstream).
- [Fact] **No smuggling past the typed request.** The router re-encodes from `chatRequest`; unknown top-level keys (`best_of`, `max_output_tokens`, `agentos_extra.n`) never reach a provider. Egress declares only `POST /v1/chat/completions` and `/v1/messages` (egress E2), so `/v1/completions` (`best_of`) has no route even on the direct test-rig path.
- [Fact, probed] **Nested keys** are still matched case-insensitively and last-wins (`{"role":"user","Role":"system"}` yields `system`). None sizes output, none is read by the meter, and the guest can set those values directly, so there is no spend or authority consequence; documented in route R-SR3-7.
- [Fact] **Credentials.** The diff adds no credential, header or log path. Refusal text quotes the guest's own key back to the guest; per route K9 bad-request refusals are not journaled.

## Threat check

Assets: the OP-8 reservation (spend never passes what `Start` reserved); provider credentials in the vault process. Adversary: **G**, a compromised or hostile guest (ARC-7) controlling the request body.

| Path | Stop | Kind |
|---|---|---|
| G sends `N`, `N`, or `n` twice to get several choices | `meter.Object` refuses; router refuses again | Structural |
| G sends a case- or fold-variant limit key (`Max_Tokens`, `max_toKens`) to forward a limit the meter did not see | `meter.Object` refuses at both boundaries | Structural |
| G sends `n:2` past the meter (a path where the router is reached without it) | Router's typed n≠1 check before dispatch | Structural |
| G omits every limit so the router inserts its ceiling | Meter inserts and reserves DefaultReserve first; router keeps it | Structural |
| G uses an alias the router does not read (`max_output_tokens` on chat) | Reserved by the meter, dropped by the router; router forwards the inserted default, which is also reserved | Structural |
| G uses another multi-output parameter (`best_of`) or another API | Not a `chatRequest` field; egress declares no completions route | Structural |
| G hides a second value in a nested object | No nested key sizes output | Not applicable |
| Router fails over after a 500/502/504 that the provider may still bill | Meter settles only from reported usage of the served route | **Not stopped if a provider bills a 5xx** (predates this PR, unmeasured): point 1 |
| G reads a credential through an error | No new error path carries server data | Structural |

## Points

1. **release** (outside the cited change; tier-A security, so not later). `route.failover` moves to the next route on 500/502/503/504/529, and only the served route's usage reaches the meter. If a provider bills an attempt it answered 5xx (e.g. a 504 after generation), one call can spend up to (attempts × limit) against one reservation. Unmeasured and provider-dependent; no reproduction. Proposed BOARD row for the coordinator to register: establish from provider documentation whether 5xx attempts are billed; if any are, reserve per attempt or stop failover after a timeout-class status.
