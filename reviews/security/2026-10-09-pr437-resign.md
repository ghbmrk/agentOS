## 1. Blocker 4a: closed for direct use, open through ptrace (B1)

- The scenario now runs as `strace … -- setpriv --bounding-set -sys_admin --inh-caps -sys_admin -- <cmd>` (`DROP_SYS_ADMIN`). On the setpriv exec, root's new permitted set is `bounding | (inheritable & fI)`; with sys_admin out of both, CAP_SYS_ADMIN is absent from permitted and effective; it is gone from bounding and inheritable by construction; ambient is cleared on a privileged exec and must stay a subset of inheritable. All five sets lack it, and no descendant can regain it through exec (bounding is one-way). It can still borrow it from a more-privileged process: see B1.
- Other routes back to it: a nested user namespace gets `MNT_LOCK_READONLY` mounts (`lock_mnt_tree`) and cannot clear `ro`; a `mount(2)` remount is in `TRACED` and counted as a violation.
- `sandbox_available()` now requires `setpriv`; without it `depaudit run` prints `FAIL sandbox unavailable` instead of running unconfined.
- `tools/ASSUMPTIONS.md` D8 is corrected to match (the `ro` flag was not locked inside the sandbox's own mount namespace; the drop is what holds it).

## Threat check

Attacker: the audited dependency's install or test scenario running inside the sandbox, aiming to forge or hide evidence or write a kept path.
- Clear `ro` with `mount_setattr`/`open_tree_attr`: denied, CAP_SYS_ADMIN absent (point 1); exercised by the control.
- Remount via `mount(2)`: traced → violation.
- New user namespace: locked mounts.
- Borrow CAP_SYS_ADMIN from a more-privileged process: open via ptrace (B1).
- Run without the drop: fails loudly (`sandbox unavailable`).

## Findings

- **B1, blocker (DEP-2b, defect).** The drop removes only sys_admin, so the scenario keeps CAP_SYS_PTRACE in the sandbox user namespace. `cap_ptrace_access_check` then lets it attach to `_inner` (PID 1 of the sandbox, which still holds CAP_SYS_ADMIN) or to strace, and inject `mount_setattr` to clear `ro` and rewrite a kept path. That defeats DEP-2b by the route blocker 4a was meant to close. Nothing on the path stops it: Yama's relational scope admits a tracer holding CAP_SYS_PTRACE in the target's user namespace; no_new_privs does not affect ptrace; `_inner` is uid 0 in the same user namespace and dumpable; neither `_inner` nor strace is already traced. The path was traced from the code; a live probe was not run here (blocked by this environment's permission policy), which does not lower the class.
  **Fix:** `--bounding-set -sys_admin,-sys_ptrace --inh-caps -sys_admin,-sys_ptrace`, plus a check in the `write-kept` control (or a test) that attempts `PTRACE_ATTACH`/`PTRACE_SEIZE` on PID 1 and its strace parent and treats success as a failure, so it fails if `-sys_ptrace` is removed. This also denies the `/proc/1/fd` reopen (`ptrace_may_access` READ_FSCREDS), which narrows D9 (DEP-3).
- **L1, later.** `open_tree_attr` (467) needs Linux 6.15+; on older CI kernels it returns ENOSYS, so only the `mount_setattr` half of the control bites there. setpriv still covers both.
- **L2, later.** No test covers the nested-userns claim in D8.
- **L3, later.** `probe =os.path.join(...)` spacing in `_control`.
