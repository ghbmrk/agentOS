## L6: setup's authority lives in agentosd, never in the page process

[Fact] As built in #189 (localui L26) and #367 (localui L28, `localsrv.Setup`):

1. `agentos-localui` holds no setup authority: no hooks, no store, no seed and no AP Wi-Fi password. Each setup op is a call over `localui.sock`, and agentosd treats the page process as compromised (L25).
2. agentosd serves setup's ops only in setup mode: no finish recorded in `-setup-record` and no owner-state file. Finish closes setup for good, across restarts. An unreadable record keeps setup closed. An owner-state file with no record is a hard failure.
3. Finish needs a code that agentosd saw confirmed from the newest seed, then the vault's seal (egress K17).
4. **Binding on every later setup op (c3, c4):** a new setup op is served by `localsrv.Setup` under conditions 2 and 3, as a fixed-shape request with fixed refusal codes. It is refused once setup is closed. Its effect runs in agentosd or a narrower process, never in the page.

## L7: the code seed is made in the vault and handed out once

[Fact] As built in #320 and #367 (egress K17):

1. The seed is made inside the vault process (`POST /enroll` on `verify.sock`, agentosd only).
2. Each link is answered once. A new enroll voids the earlier seed and any confirmation of it.
3. Sealing happens only at finish (`/enroll/seal`).
4. The page keeps a "shown" flag and never a seed.
5. Image boxes run `agentos-egress init -setup`, which opens enrollment and prints no seed, so setup's link is the only hand-out.
6. Accepted residual: agentosd and the page see the seed while it is shown (lens bundle b).

## L8: `agentos-netjoin` (proposed; binds P2-2w c3)

**Purpose.** On the image, joining a home network means writing a NetworkManager system connection (S7: NetworkManager runs the box's Wi-Fi, the access point included). The right to do that would let a process rewrite or delete any connection, the access point's included. L8 keeps that right out of agentosd and out of the page process. It gives the right to a helper that can do exactly one thing.

Conditions:

1. **Own user, no root.**
   - `agentos-netjoin` runs as a dedicated system user, from its own systemd unit.
   - The unit has no capabilities, `NoNewPrivileges=yes`, `RestrictAddressFamilies=AF_UNIX`, and `IPAddressDeny=any`.
   - It has read-only access to everything except its socket directory, and no environment file.
2. **Privilege through NetworkManager and polkit only.**
   - The helper talks to NetworkManager over the system D-Bus.
   - A polkit rule grants that user, and no other, `org.freedesktop.NetworkManager.settings.modify.system`. It grants no other NetworkManager action: no `network-control`, no `enable-disable-*`, no `wifi.share.*`.
   - The new connection activates by autoconnect, not by an explicit activate call.
   - [Inference, to verify in c3] polkit cannot narrow that action to one connection. The narrowing to one connection is therefore the helper's code (condition 4), and a compromise of the helper process itself reaches every system connection. That residual is accepted: it is still narrower than agentosd holding the right, and the helper's input is two bounded strings.
3. **One caller.**
   - The helper listens on one unix socket and serves only agentosd's uid, checked with `SO_PEERCRED` on each connection.
   - It refuses other peers before reading a request.
   - It caps request size, connections and idle time. It reuses `sockets.Server`, as `verify.sock` and `localui.sock` do.
4. **One op, one connection.**
   - The only request is `{ssid, psk}`. It writes the one fixed connection, id `agentos-home`: created the first time, updated in place after that.
   - It never reads, changes or deletes any other connection, the access point's included, and it never touches devices or radios.
   - The connection's other settings are fixed by the helper: Wi-Fi infrastructure mode, WPA-Personal (WPA2-PSK or SAE), DHCP. The caller can set no DNS, address, route, interface, MAC, autoconnect priority, proxy or 802.1X field.
   - Answers are fixed codes: joined, refused (bad input), not joined (wrong password or no such network, within a fixed wait), busy, failed.
5. **Input bounds, checked before any D-Bus call.**
   - SSID: 1 to 32 bytes.
   - PSK: 8 to 63 printable ASCII characters, or exactly 64 hex digits.
   - Anything else is refused. Neither value ever reaches a command line, an environment or a file the helper writes.
6. **The password is never logged or kept.**
   - The PSK goes only to NetworkManager, as a system-owned secret (`psk-flags=0`) in its root-only connection store.
   - It is not written to agentosd's state, the setup record, the journal, any log line, error text or crash output, in agentosd, the page or the helper.
   - Tests prove this with a synthetic canary.
   - [Open, for P2-1] whether NetworkManager's connection store sits on an encrypted volume. If it does not, a lost drive gives away the home Wi-Fi password. P2-1 must say which, and the answer may be a release finding there.
7. **Setup mode only.**
   - agentosd serves the join op to the page only under L6 conditions 2 and 4, at most 6 tries a minute.
   - Once setup is closed it is refused, like every setup op.
   - Changing the home Wi-Fi after setup is not served. It is LATER P2-2w c3 f1 and needs its own owner authentication.
8. **Carry (accepted residuals).**
   - Before finish, the page process still sees the home password as the owner types it, as it sees every setup field (L28 carry). agentosd checks shape only.
   - [Inference] Anyone who has the box's access-point password (on the Owner Card) can, during setup, point the box at a network they control. The uplink carries only TLS-protected and signed traffic (updates and provider calls), so this gains them availability, not custody.

**Cost.** UX: none; the page and its wording are unchanged. Potency: none in MVP; changing the home Wi-Fi after setup waits for the LATER row.
