## Security review (tier A) @ 6801dca

Verdict: CHANGES (fix-list: 1 blocker, 4 release)

Record: PR #1734 · package VAULT-slot-decided (#1557) · head 6801dca6

**What I checked.** I diffed the head against origin/main (merge base fba0c921). Main has not touched `broker/` since then. `go vet` and gofmt are clean. `go test -race -count=1` passes on `./vault`, `./recovery` and `./cmd/agentos-egress` with a real swtpm, and the new egress test runs rather than skipping. CI is green. I used a private GOCACHE and ran 11 hand mutants in a separate worktree: 7 killed, 4 survived (listed below).

### Threat check
- **Can `InjectSealFault` run in production?** It cannot be reached at runtime today. No non-test file calls it, and no init path, env var or flag turns it on. `go tool nm` on a freshly built `agentos-egress` shows `vault.crashPoint` but not `InjectSealFault`, because the linker dropped it. It is still an exported production symbol with no build tag, though (see 3).
- **Does a failed seal ever leave a slot trusted, or lose a secret?** `save()` returns an error only before the vault file lands. `landed()` turns a failed dir sync into nil, and `advance()` returns errors only before the write. So only errors after the seal carry `ErrSlotDecided`, and the typing in `replaceKeys` (keysbind.go:120-125) is correct. A decided change rolls forward through the staged `.next` file (keyslot.go:485-507), so "trusted, saving did not finish" is true: the PC opens through `.next` at the next boot even if the keys-file write never landed. An error from `slotsForChange` finishing an earlier change is left untyped, which is correct, because the current change did not happen.
- **Fail-open on the egress side.** The lockout is now kept on a decided PIN enroll, and a PIN-less enroll never gives it back on any error. Both fail closed. The rotation path takes the existing 409 `errCardInEffect` route, so nothing fails open there.
- **Fail-open on the recovery side.** A decided recovery `Rekey` stops before `storeBackupKey` and `refresh`. `markRotation` was already written, so `PartRefresh` is still owed and Backup refuses. Nothing fails open.

### Findings
1. **blocker. The passphrase half of the rotation fix has no test** (broker/recovery/rotate.go:458-467, REC-4 / CRED-8). `TestRotationWhoseSlotIsDecidedReportsWhatIsInEffect` (rotate_test.go:472) rotates only `PartRecovery`. Three mutants on the passphrase branch survive the whole recovery package:
   - `decided := err == nil` reverts this branch to the pre-PR behaviour, a 410 "nothing changed" though the passphrase changed. That is #1557 path 2.
   - Dropping `in.VaultPassphrase = next.VaultPassphrase` in the decided branch survives too.
   - So does `decided := true`, which claims a new passphrase is in effect after a failure before the seal.

   Fix: add a `PartPassphrase` case (and preferably passphrase+recovery) under `InjectSealFault` that asserts `ErrCardNotStored`, `ErrSlotDecided` and `nc.VaultPassphrase == next.VaultPassphrase`. Also add a passphrase case where `Rekey` fails before the seal and the error is not typed and not `ErrCardNotStored`.
2. **release. No test pins that a `save()` failure before the seal is not "decided"** (broker/vault/keysbind.go:107-113; CRED-8, HW-1). Wrapping the `save()` error at :113 in `ErrSlotDecided` survives all three packages. The `gamma` case (keysbind_test.go:453) covers only the `.next` write. This is the dangerous direction: `trust` would say "this PC is now trusted" when it is not, and rotation would report new factors as in effect when they are not. Acceptance test: in `TestSlotChangeErrorAfterTheSealIsTyped`, make `writeFile` fail on the vault file (a non-dirsync error) and assert the error is not `ErrSlotDecided`. Add the same check for a counter `advance()` failure.
3. **release. `vault.InjectSealFault` is an exported, untagged production API** (broker/vault/faults.go:7-15). It is the first cross-package fault hook in a tier-A package. Nothing stops a future non-test caller, and any call disables the success path of every slot change process-wide. It also writes the shared `crashPoint` with no lock, while `replaceKeys` reads it under `v.mu`, and its restore function sets a no-op instead of restoring the previous value, which clobbers a `crashAt` seam that was already set. Fix: either put it behind a build tag (`//go:build vaultfaults`, with the egress and recovery tests and CI passing the tag), or add a source-scan test in `vault/imports_test.go` style that fails on any non-`_test.go` caller. Restore the previous value too. Invariant: no test seam is reachable from a production build.
4. **release. Other slot-change callers still misreport a decided change** (CRED-9). `untrust` maps every `remove` error to `errNoSuchHost` (custody.go:1459), and `remove` returns before `giveBack` (trusted.go:925-927). A decided `RemoveSlots` therefore tells the owner "no trusted host with that id" when the PC's slot is gone. The TPM rewrap after `Reencrypt` (trusted.go:616-633) names a PC whose slot did land as "must be trusted again". Both fail closed, but neither message is true. The PR lists these as `later`, but tier-A security findings are not `later` (OPERATING §2). Failure path: the owner removing a lost PC is told the ID is wrong.
5. **release. The decided `trust` branch skips the trust record** (custody.go:1437-1439 vs 1443-1447). The PC is trusted, but `c.notify("this PC is now a trusted host…")` never runs, so the log has no record of a tier-4 trust change that took effect (CRED-9). Fix: notify, with a "saving did not finish" note, before returning `errHostSlotDecided`.

**Mutants killed (7):** giveBack ignoring decided (trusted.go:768); `trust` mapping decided to `errHostNotSaved`; the crash point untyped; the `finishKeys` error untyped; the recovery card dropping the new key; recovery `wrote` ignoring decided; recovery treating any error as decided (killed by `TestAPartialRotationReturnsWhatIsInEffect`).

**Not a finding (outside this diff, noted).** A trust that fails before the seal leaves a `.next` file whose new TPM slot unwraps the data key on that PC until `dropStaleStaged` removes it. Only the PC the owner had approved with tier-4 can use it.

Next: builder adds the blocker-1 tests and files 2-5 as one `class:release` follow-up; owed: Security re-sign on the delta, L3, lens screen (UX/Potency).
