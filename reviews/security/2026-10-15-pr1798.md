## Security review (head 7a3bb29d)

**Verdict: REQUEST CHANGES.** The three new rules do what they say for direct targets. The `var/lock` exemption is narrow. The tests kill the main mutants. But a one-component variant of #1702's own repro (finding 1) still passes, and the I21 row still says the opposite of the new rule (finding 2). Both fixes are small.

Method: fresh clone at 7a3bb29d. `python3 -m unittest tests.test_image` gives 226 tests, OK (1 skipped). I ran probe trees through `check.violations()` on `clean_tree()` and ran 13 source mutants against `ConfFilesTest`.

### Blocking

**1. A `..` after a box mount, or after a missing step, is resolved lexically, so a link reaches `/run/lock` through the tree's own `var/lock` (or `var/run`) link and passes.**
- **Where:** `image/mkosi/mkosi.finalize:864` and `:869` (`tree_chase`), together with `:201-209` (`world_writable_link`).
- **Cause:** When a target enters one of `BOX_MOUNTS` (`run`, `dev`, `proc`, `sys`, `tmp`), `tree_chase` returns the rest of the path as written. With `missing_ok`, it returns `path_parts(...)` of the rest.
  - `path_parts` then cancels the `..` lexically.
  - The prefix loop sees the tree's `var/lock`. That entry is a link, not an o+w directory, so it is not refused.
  - The loop then sees `var/lock/<x>`. There, `tree_lstat` raises ELOOP and the loop `continue`s.
  - Nothing ever chases `var/lock`.
- **On the box:** `/run/..` is `/`, so the kernel and systemd's chase reach `/var/lock`, which is `/run/lock` (1777).
- **These all pass at this head, each with `violations() == []`:**
  - `etc/udev/rules.d -> /run/../var/lock`. This is the #1702 item 1 shape: a user's `RUN+=` rule runs as root.
  - `etc/systemd/system/ssh.service.d/x.conf -> /run/../var/lock/x.conf`
  - `etc/udev/rules.d` pointing at `/dev/../var/lock`, `/tmp/../var/lock` or `/proc/../var/lock`
  - `etc/udev/rules.d -> ../../run/../var/lock`
  - With `var/run -> /run`: `-> /run/../var/run/lock` and `-> /run/../var/run/user/1000`. The second also defeats `SERVICE_DIRS`.
  - `-> /opt/nope/../../var/lock`. This is the missing-step form. It dangles on the box until `/opt/nope` exists, so it is weaker, but it is the same cause.
- **Controls:** the same links without the detour (`-> /var/lock`, `-> /var/run/lock`) are refused.
- **Introduced by this PR?** No. The into-form already passed on main (#1543 R2). But this PR's rule exists to refuse exactly these targets, so it should close them.
- **Fix:** Stop normalising the unresolved tail.
  - At `:869`, return `"/".join(cur + [name] + parts)` raw.
  - In `world_writable_link`, after the `LOCK_LINK` check, refuse when `".." in path.split("/")`. The check cannot tell where such a link ends, because box-made links like `/dev/fd` make lexical `..` unsound inside a box mount too.
  - I prototyped exactly this. Every probe above is refused, and the full `tests.test_image` stays green (226 OK). CI's stock build has to confirm that no stock link takes this shape.
  - Add one test per box mount, plus the `var/run` form and the missing-step form.

**2. I21 still says a link to a world-writable directory itself is allowed (`image/ASSUMPTIONS.md:29`).**
- The current text reads "…is refused, whatever reads it (#1543 Security R2…); a link to such a directory itself, like trixie's `/var/lock`, is not."
- That is now false, and it misstates the security boundary: it says the very hole #1702 closes is open by design.
- **Fix:** Replace the sentence with "…the directory itself included; only trixie's `var/lock` → `../run/lock` or `/run/lock` passes (I23)."

### Answers to the questions asked
- **Relative vs absolute, trailing slash, `//`, `.`, multiple hops:** All are handled when the path resolves inside the tree, because `tree_chase` follows each in-tree link and the absolute and relative forms land the same. Two-hop chains (`a -> /usr/lib/b`, `b -> /var/tmp`) and `//var//tmp/./` are refused. The only gap is finding 1.
- **Hardlinks:** A hardlink of a 0666 file from `var/tmp` into `etc/udev/` carries the inode's mode, so the o+w rule refuses it at the non-exempt path.
- **Sticky vs plain o+w:** The rule refuses both; the `skip-sticky` mutant is killed.
- **Setgid dirs:** Out of scope by design. A 2775 directory passes, as I23 states. Group write is not a rule.
- **Device nodes, FIFOs, sockets:** A 0666 FIFO in `etc` is refused. Sockets were already refused (V15). Device nodes go through the same mode rule. The boot-time 0666 nodes from `static-nodes-permissions.conf` (`/dev/net/tun`, `/dev/fuse`, `/dev/vfio/vfio`) are on devtmpfs and are not configuration.
- **Case and encoding:** Comparisons are exact strings on a case-sensitive filesystem. `VAR/lock -> /run/lock` is refused, and nothing folds case or normalises Unicode.
- **TOCTOU:** I found nothing material.
  - The check runs in `mkosi.finalize` after every package and maintainer script has run.
  - The image has no `mkosi.postoutput`, and nothing writes the tree between the check and repart/verity.
  - Every look goes through `tree_lstat`, which never follows a link on the host.
  - What can change the tree at boot is the tmpfiles allowlist. Every 1777/0666 line there is inside `WORLD_WRITABLE` or `/dev`.
- **The `/run/lock` exemption:** It is narrow. It needs `rel == "var/lock"` exactly (an entry reached without links) and a target of exactly `../run/lock` or `/run/lock`. `/run/lock/`, `//run/lock`, `var/lock -> /var/tmp` and `usr/lib/x/lock -> ../../../run/lock` are all refused. Other links that reach `/run/lock` through `var/lock` are refused by the chase, except through finding 1.
- **Tests and mutants:**
  - Killed: target-itself prefix (25 failures), `SERVICE_DIRS` removal (24), mode rule removed (7), exemption removed (2), exemption with any target (3), exemption by `endswith('run/lock')` (2), skip-sticky (3), dirs-only (3), regular-files-only (4).
  - Survived, both non-blocking:
    - `rel.endswith('lock')` in place of `rel == "var/lock"`. No test links a non-`var/lock` path to the exact stock target. Add, for example, `etc/x/lock -> /run/lock`.
    - `rel.startswith(w)` without the `/` in the o+w exemption. No test gives a sibling such as `var/tmpx` mode 0777. Add one.
- **Doc accuracy:** The builder's note is half right.
  - **I23** already names both forms ("`-> ../run/lock` or `-> /run/lock` (the stock build has the absolute form)"), so it is correct.
  - **The PR body** names only `../run/lock` (Before/After: "stock `var/lock -> ../run/lock` still passes"). That is a non-blocking doc fix; it does not mislead about security.
  - **I21** is finding 2.

### Non-blocking notes
- `world_writable_link` returns `[]` on any `OSError` from the chase (ELOOP, ENOTDIR). Today that matches the box, where the same lookups fail. A comment saying so would stop a future change to `tree_chase` from turning this into a quiet fail-open.
- Ownership is not a tree-wide rule. A 0644 unit, rules file or generator owned by a non-root uid anywhere outside the paths `conf_chase` reads passes, and so does a POSIX ACL shipped in an xattr that grants a user write. #1702 scoped only o+w, so I suggest a follow-up: refuse any entry not owned by uid 0 outside `WORLD_WRITABLE`/`SERVICE_DIRS`, and any shipped `system.posix_acl_*` xattr.
- `SERVICE_DIRS` is a hand list, and I23 records that. Debian service users own directories it does not list: `/var/lib/systemd/timesync` (systemd-timesync), `/var/cache/man` (man), and the apt `partial` directories (`_apt`). A follow-up could refuse a link whose resolved prefix is an in-tree directory owned by a non-root uid, which would cover these automatically.
- `tree_chase`'s lexical tail at `:864`/`:869` also feeds `entry_mode`/`tree_stat`. Their callers do not decide link safety, but the same note applies.
