## Evidence

- [Fact] **Where the reason comes from.** `Decided(ctx, in, why)` has two callers, both in `grants/gate.go`. `Gate.lapse` passes `d.Why` from an `owner.Decision`. `Gate.settle` passes `decision.why` when the item was not approved, and "" when it was. `owner.Decision.Why` is set only from fixed literals in `owner` (`closeLocked`: "owner"/"not chosen" or the caller's fixed reason; `boot.go`: "expired"/"restart"; `autoreply.go`: "undo"; `approvals.go`: "not held"). `decision.why` is that value or a gate literal ("it changed since the page showed it", "its staged copy could not be made", the `closeIntent` `guesterr.Literal`s). `failReason(err)` writes only to `g.failed`, never to `decision.why`. No path copies SMS text, page input or guest/agent data into the reason.
- [Fact] **Mismatches fail closed.** `change.Decided` compares exact strings: "not chosen" drops the proposal (no re-offer), "owner" settles it as a decline (no re-offer), and anything else on Pending or Denied lapses it (re-offer). A spoofed or mistyped reason can only cause an extra *request*. Nothing in this chain approves anything.
- [Fact] **A re-offer needs fresh approval.** `Lapsed(id)` only makes Loop 3 forget version v (`unproposeLocked`) and call `ProposeRelease` again. That creates a new proposal ID from the persisted `Seq`, a new evaluation, and a new `chg:<id>:adopt` intent, which goes through the gate's normal request path. The old intent stays Denied, and the dropped proposal fails `Check` (existing `TestDecidedDropsUnansweredWithoutDecline`). Auto-adoption on re-offer follows the same `AutoAdopt` and `SecurityAutoStage` policy as the first offer, so the re-offer gains no authority.
- [Fact] **A decline stays a decline.** The owner's NO arrives with Why "owner", is never rewritten on the `!Approved` path of `Gate.Decide`, and reaches `Settle`/`drive`/`drop`. `lapse` is never called for it, so `Lapsed` stays false. `Gate.Decide`'s setting branch excludes "owner" before calling `Gate.lapse`.
- [Fact] **No smuggling via partial YES.** `closeLocked` marks an unpicked item "not chosen" and does not approve it. The pipeline drops that item without a lapse report (`TestOmittedReleaseIsNotReoffered`, through the real gate). Which items a YES approves is unchanged by this diff.
- [Fact] **Recheck refusal.** An item that was approved but then Denied at recheck reaches `Decided` with "", so it lapses and is offered again under a new request. This adds a re-ask, not a run.
- [Fact] **Error paths.** If `j.Get` fails in `Decided`, it does nothing: the proposal stays, there is no lapse, no re-offer and no approval. If `eng.Get` fails in `Gate.lapse`, `Decided` is skipped. `Lapsed` returns false for an unknown ID, and Loop 3 needs a stored, non-empty `ProposalID` and `StateAwaitingOwner` before it asks. Every failure ends with no re-offer. None fails open.
- [Fact] **Locks.** `Lapsed` and `lapse` take only `p.mu`, and `Lapsed` does not call back into Loop 3. No new lock order.

## Threat check

Assets: the owner's authority over what gets installed (UPD-5, C7), and the owner's NO being final. Adversaries: **G**, a guest or agent that can reach gate inputs; **N**, someone who can send texts to the owner channel without the codes; **C**, a compromised update mirror.

| Path | Stop | Kind |
|---|---|---|
| G/N supplies a reason string that flips a lapse into an approval | Reasons are owner/gate literals, and no reason value approves | Structural |
| A re-offer stages without the owner | A new intent goes through the normal gate request | Structural |
| A NO is re-asked as a lapse | "owner" goes to `Settle`, never to `lapse` | Structural (exact-string match; see point 1) |
| A release omitted from a partial YES is re-asked, or included anyway | "not chosen" → `drop`; omission never approves | Structural |
| C replays an old release to collect a re-offer | Same verification as the first offer; a re-offer adds no authority | Structural |
| A stale `Lapsed` report hits a new proposal | IDs come from the persisted `Seq` and are never reused | Structural |

## Points

1. **later.** The cause strings "owner" and "not chosen" are compared as untyped literals across `owner`, `grants` and `change`. If an owner-side NO were ever renamed, it would be re-asked as a lapse. That is a nag, not a grant, so it fails closed. A shared typed constant, or a gate test with an "owner" row in `TestOmittedReleaseIsNotReoffered` that asserts `Lapsed` is false, would pin it.
2. **later.** `Pipeline.lapsed` entries for a version Loop 3 no longer asks about (superseded by a newer release, or cleared by a root change) are never consumed. They live in memory only, are bounded by the number of releases and are cleared on restart. This is not a security exposure.
