## What changes for an attacker
`daemon.Run` (broker/daemon/daemon.go:452) now starts `Engine.SettleUnknown` in the background. It runs `Engine.Reconcile` until no `outcome_unknown` attempt is left. A round is bounded by one minute. Waits start at 2 s and double up to 5 min. Before this PR, nothing in production called `Reconcile`. This PR makes every registered executor's `Reconcile` reachable at each start: loops, change, the grants gate, recall (`LateExecutor`), owner forget, follow (through `follow.Route`) and mail (`lateMail`).

## Threat check
| Concern | Result | How |
|---|---|---|
| Re-execution | none | `Reconcile` calls only `exec.Reconcile`, inside `safeCall`. An unknown answer is skipped. `Resolve` accepts only `succeeded` or `not_applied`, and only for an attempt that is still `outcome_unknown`, so an owner `Resolve`, a dispatch or a second round racing it gets `ErrState`. A `not_applied` result is dispatchable again, but nothing re-dispatches on its own. The gate's `settle` dispatches once, and `Tick` only reissues and flushes. M3 (`Reconcile` calls `Execute`) is killed. |
| Optimistic resolution | none in the engine | Unknown keeps the fence (M2 and M4 are killed). Each executor answers from its own durable state: loops, change and apply read saved `Applied` state; forget reads its tombstone; follow reads `TrustedRoot`, which runs `settle` first. Mail reads the mailbox, where a sent message not found is unknown, never `not_applied`. `lateMail` answers unknown while it is unbound. Two answers are fixed: the gate's `not_applied`, which is true because `Attach` rebuilds grants only from succeeded records before any round, and recall's `succeeded` "approved; not reset yet", which matches its own `Execute` contract, with `Retry` each minute carrying the reset. Forget is the exception, R1. |
| Evidence spoofing by a guest | not reachable | The guest plane's Effects are only Submit, Authorize, Dispatch and Get. `Engine.Resolve` has no production caller other than `Reconcile`. Evidence comes from broker-held host state, except mail, where it is the operator's mailbox. A guest's Message-ID is derived by the broker. It is unkeyed SHA-256 and so predictable, and it is looked up in Sent or Drafts. The worst case a guest could reach there is an under-report: a send marked succeeded that did not land, or a draft marked `not_applied`. A duplicate effect is never reachable. |
| Startup race | none | `journal.Open` writes the restart `observed unknown` records and builds the fence synchronously (engine.go:146-168), before `srv.Start` (daemon.go:440) and before `serveOwner`. `SettleUnknown` can only lift a fence, never create or delay one. While `Reconcile` waits on an executor, it holds no engine lock. |
| STOP and narrowing during and after a round | responsive | The PR's test covers the time after a round. A probe (uncommitted) blocked loops `Reconcile` mid-round. STOP over the owner channel still replied and took effect, a narrowing `meta.loops.budget.lower` dispatched, and the fence held throughout. When the probe released the round, the fence lifted with nothing re-run. |
| Owner grant intents | conservative | The gate always answers `not_applied`. No grant can become live through reconcile, because `Attach` already replayed only succeeded records. An interrupted pause or revoke stays unapplied, and the grant stays live. That was already true before this PR, and the owner received no confirmation, because the crash came before the reply. |
| Forget intents | not fully | Item 1 is `succeeded` only when its tombstone holds, and otherwise `not_applied`. An approved item 2 is reported `succeeded` "resumed when recall opens" and queued for `resumeAgent`, but the queue can be stranded (R1). |
| Same-effect holds (A2) | by design | Once evidence settles the first intent as succeeded, a held duplicate under a new ID can dispatch if it is asked to again ("a deliberate repeat may go", `TestOP2SameEffectUnderNewIDWaitsForEvidence`). Before this PR it was never released in production. It is its own authorized intent, and a guest could always change one parameter to avoid the hold, so this adds no authority. Noted for Potency. |
| Retry load and hangs | bounded | A round is capped at one minute, and executors that honour ctx return. A `Reconcile` that ignored ctx would stall only fence lifting, which fails closed. Follow re-alerts only if `Resolve` fails after a matching root (at least once, by design). |

## Findings
1. **R1 (release, CAP-3 and RCH-4; recall-on half new, recall-off half matches L3 L2).** cmd/agentosd/forget.go:1216-1228. `ownerForget.Reconcile` reports an approved item 2 as `succeeded` "resumed when recall opens" and only appends it to `f.interrupted`. It does not call `f.whenOpen()`, as the `Execute` path does for `ErrNotOpen` (forget.go:808-814). `OnOpen` callbacks fire once (recalltool/service.go:218-240), and `resumeAgent`'s journal scan picks up only intents already `succeeded`.
   - Failure path, recall on: an earlier unknown intent in the same round, such as a mail `Find` against a slow IMAP server, holds the round until recall has opened and `resumeAgent` has run. Item 2 is then marked succeeded but never taken back in this boot. The agent keeps what the owner approved forgetting until the next restart, and the journal says it was done.
   - Failure path, recall off: `go resumeAgent` (main.go:885) races the first round, and the owner's "cannot be done" text is skipped.
   - This is not a regression, since before this PR the intent stayed unknown and was never taken back. But this PR is what makes the answer live, so on tier A Security classes it release, not later.
   - Fix: in `Reconcile`, after queueing, call `f.whenOpen()` when it is set, which runs at once if recall is open. With recall off, hand the item to the same path that tells the owner, or run settle before `resumeAgent`. Add a test that runs `resumeAgent` before `Reconcile`.
2. **R2 (release, OP-2 and OP-4: "reconcile never re-executes"; merges with the builder's suggested guard and L3 L1/L2).** Each start now trusts every executor's `Reconcile` to gather evidence only, but nothing enforces that.
   - A18 is wrong on two counts. It says each `Reconcile` reads state only, but follow alerts the owner and forget queues a take-back. It names "the owner's YES/NO resolve" as the way out, but `Engine.Resolve` has no production caller besides `Reconcile`.
   - The `Resolve` guard ("unknown is not evidence") survives every journal test (M10).
   - Failure path: a future executor whose `Reconcile` resends, or retries the effect as its way of finding out, would act at every start, every round, with no test failing.
   - Fix: a daemon or agentosd test that wraps every registered executor, runs startup reconcile, and fails on any `Execute` call. List the allowed side effects (follow's alert, forget's queue) in A18. Correct the way-out sentence. Add a `Resolve(…, ResultUnknown, …)` test.

No blockers.

**On L3 R1 (follow answers unknown for a switch that did not land).** Security agrees that answering `not_applied` is sound if it does so only when the post-`settle` `TrustedRoot` digest differs from the intent's digest. `TrustedRoot` completes or forgets an interrupted switch under the store lock first. When the digest matches but `Following()` names a different source, it should stay unknown. A `not_applied` follow is safe to leave dispatchable, because the held root lives only in memory, so a re-dispatch answers "the page no longer holds the root".
