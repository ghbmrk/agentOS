### Findings
- **B1 (blocker, DEV-2).** A full read whose NAT-PMP answer was dropped ends the new gateway's hold before that router has been asked.
  - Where: sources.go:104-117 returns the end network; policy.go:279-285, on the stale path with the same gateway, calls `releaseLocked`.
  - The new router's WAN address is allowed until the queued full read gets an answer (up to 2-3 s), or until the next poll if no event queued one.
  - This is a regression against main for an address move (main keeps the hold). It is also a hole in the new same-address/new-MAC and flushed-entry cases.
  - Fix: return an error from `Read` when `!same`, or ask the end gateway again. Add a policy-level test.
- **B2 (blocker, process).** The remaining gap (R0) is classed release but has no `class:release` issue (OPERATING.md:55). File it and name it on the Findings line.
- **R0 (release).** A router swapped with no link event is noticed only at the next event or the 10 s poll. `WatchNetlink` has no `RTMGRP_NEIGH` (netlink_linux.go:23). The window is up to about 10 s after the kernel learns the new MAC.
- **R1 (release).** An empty MAC is a key shared across networks.
  - An answer read on a NOARP default route (no `/proc/net/arp` row) is filed under `(gw, "")`. That is the same key as a flushed Ethernet entry, so the old external address is reused and no hold opens.
  - Probe: `hold=false`, `External` was the previous network's, `Check(new WAN)=nil`.
  - Fix: key on `(gw, dev, mac)`.
- **R2 (later; wording only).** Keying IPv6 gateways by address alone is not a live gap. `Gateway6` has no zone, so a NAT-PMP dial to fe80:: gets EINVAL, and nothing is ever stored for an IPv6 gateway. N9 should be reworded. Recheck if PCP over IPv6 is added.

### Draft issue texts

#### R0: NETGUARD-gw-neigh: a router swapped without a link event is noticed only at the next poll (release; from #1550 Security R0)
Release (DEV-2), from the #1550 Security review (R0). This is the gap left by #1536's MAC keying.

- **Where.** `WatchNetlink` (broker/netguard/netlink_linux.go:23) subscribes to RTMGRP_LINK, IFADDR and ROUTE only. A change in the neighbour table raises no event. `quickLearn` runs only on those events and on the 10 s poll (`netWatchEvery`).
- **Failure path (DEV-2).** A home router behind a switch is replaced by another router at the same gateway address, and the box sees no link event.
  - Once the kernel's neighbour entry for the gateway takes the new MAC (from a gratuitous ARP, or a re-resolve after a failed probe), traffic flows through the new router.
  - The policy still holds the old router's identity and external address until the next poll's quick read. During that time the new router's WAN address is allowed, for up to about 10 s plus one router read.
- **Fix.** Subscribe to RTMGRP_NEIGH and count only RTM_NEWNEIGH/RTM_DELNEIGH for the learned gateway address as an event, so other hosts' changes cause no churn. Alternatively, compare the gateway MAC on a shorter timer.
- **Acceptance.** A test where the gateway's neighbour entry changes MAC with no link, address or route event, and the hold opens within the event (poll an hour away). It fails at bb08e88f.

#### R1: NETGUARD-gw-dev: an empty gateway MAC is one key across networks (release; from #1550 Security R1)
Release (DEV-2), from the #1550 Security review (R1).

- **Where.** broker/netguard/sources.go:146-153 and :110-115. `Sources` keys the external address on `(gw, mac)`, and "" means both "this link has no ARP" and "the entry was flushed".
- **Failure path (DEV-2).**
  - On a NOARP default route (ppp, tun, wwan raw-ip, `arp off`), `/proc/net/arp` has no row, so a gateway's answer is filed under `(gw, "")`.
  - Later, on an Ethernet or Wi-Fi network whose router has the same address, the quick read after a link flap (entry flushed) finds `(gw, "")`. It supplies the earlier network's external address, and no hold opens.
  - The new router's WAN address is allowed until its full read answers, or indefinitely if that router is silent.
  - Probe at bb08e88f: `hold=false`, `External` was the old address, `Check(new WAN)=nil`.
- **Fix.** Key on `(gw, dev, mac)` (`gateway4` already returns `dev`), or never file an answer under an empty MAC on an ARP device.
- **Acceptance.** A test where an answer stored with no neighbour entry on one interface is not supplied for the same gateway address with no entry on another interface. It fails at bb08e88f.

#### R2: NETGUARD-gw6-doc: N9 says IPv6 gateways are keyed by address alone, but none is ever stored (later; from #1550 Security R2)
Later (wording only), from the #1550 Security review (R2).

- `Gateway6` returns the next hop without a zone, so `ExternalAddr` to a link-local gateway cannot connect (EINVAL without a scope id). Even with a global next hop, the router would need to answer NAT-PMP v0 over IPv6, and the parser yields only IPv4.
- So no external address is learned on an IPv6 gateway, and keying by address carries nothing across routers.
- N9 (broker/netguard/ASSUMPTIONS.md:15) should say this, so the address-only sentence does not read as an open gap.
- Tag recheck if PCP over IPv6 is ever added.
