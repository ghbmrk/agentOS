## Threat check

Adversaries: the agent (it can draft a grant change and choose every value in it), a tampered record value, a replayed or substituted approval, and a compromised page process. Asset: the owner's informed consent to standing authority (ADP-9 fixed-wording approval).

- [Fact] **Terms come only from the parsed, validated spec.** `evaluateBroker` builds `Terms(s)` after `validateLocked` succeeds, under the same lock, from the `Spec` it will apply (gate.go:950). Labels are fixed broker strings. Values are what the rule itself fixes (action, account, params, recipients, numbers), never guest text outside the spec. **Holds.**
- [Fact] **Completeness.** `validateLocked` makes a spec exactly one shape. Every `Rule` field (Action, Params, Recipients, AmountCap, PerRecord, PerDay, HoldDays, Reply) and the Account have a term. An adapter grant shows Account, Executor and every op with its verb. "Without asking" is built from `verb.Reversible` verbs the grant holds, and the gate can only be stricter than that line (L3 r2). A resume carries the paused grant's `Describe` in its Detail, as before. **Holds.**
- [Fact] **Binding.** `ItemSum` appends `|T%q` of the canonical JSON only when terms are set. The prior fields all end in `%q`, `%t` or `%d`, and `%q` is unambiguous, so the two appendices cannot be read as each other and terms cannot collide with Detail/UndoBy. `requestSum` covers every `ItemSum`, so the page form token and the decide-time check bind the terms. **Holds.** Mutation, run here: dropping the `T` appendix fails `TestSR3_3EachRuleFieldChangesTheCardAndItsBinding`.
- [Fact] **Shown = bound.** Dropping the "Recent edits" term fails both grants rule tests and two localui page tests. A malformed `TermList` renders as "could not be read; deny this request", never as an empty card. **Holds.**
- [Fact] **Injection and spoofing.** Every label and value goes through `showField` (non-printable and confusable characters as `[U+XXXX]`, setting the unusual-character warning), then html/template escaping, one `<li>` per term. A newline cannot start a fake term. **Holds.**
- [Fact] **SMS (CH-12).** `line()` does not read `Terms`. A grant change asks with `local: true`, so it is never texted. **Holds.**
- [Fact] **No new authority.** The only gate change is the `Terms:` field on the ask. There is no new allow path, and approval is still one page code. An open grant change across the upgrade is closed at re-issue and asked again (owner O20), which fails safe. **Holds.**

## Points

1. **later — ADP-9: the rule card names the action but not its verb.** "Runs invoice.send on mail" does not say "send" or "pay", although the adapter-grant card does. The verb is fixed by the adapter grant the owner already approved with its verb shown, and `validateLocked` admits only irreversible, non-secret verbs, which "without asking or notifying you" already conveys. Fix when the file is next touched: add the verb, e.g. `invoice.send (send)`. UX cost: a few characters. Potency cost: none.
2. **later — ADP-9: some rule values render ambiguously.** "Fixed field" renders `k=v`, so `{template: "a=b"}` and `{"template=a": "b"}` show the same line. Recipients are joined with ", ", so `["a, b"]` and `["a", "b"]` show the same line. The digests differ, so neither can stand in for the other at approval. In both pairs the card never shows less authority than the rule gives: an entry containing ", " matches only that exact string. The risk is a confusing card, not a hidden grant. Fix: refuse `=` in param keys and `,` in rule recipients in `validateLocked`, or render key and value apart. UX cost: none. Potency cost: none.

Neither point blocks: both are outside what A13/A14 need, and neither lets a card understate the authority it binds.
