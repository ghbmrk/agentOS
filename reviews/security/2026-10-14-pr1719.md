## What I checked (first round, b8b569ec)

- **The pin is enforced before anything is unpacked or run.** `build-rootfs.sh:36-39` downloads into a private `mktemp -d` (or copies `CODEX_TARBALL` there), hashes that copy, and exits before `tar` (`:46`) on a mismatch. `tar` reads only the verified copy, so there is no gap between check and use. The URL is fixed, and `curl -f` under `set -eu` has no fallback registry or `npm install` path. A missing `openssl` fails closed (the result becomes `sha512-` and the compare fails). The integrity matches `registry.npmjs.org/@openai/codex/0.162.1-linux-x64` (`dist.integrity`, with npm signatures and SLSA provenance), and a fresh download hashes to the same value.
- **No transitive dependencies or install scripts.** The package has no `scripts`, `dependencies` or `optionalDependencies`, and npm never runs. The tarball has no symlinks and no setuid or setgid bits. Only four named members are extracted. The copied `/usr/bin/bwrap` is `chmod 0755` with no setuid.
- **No login in the image.** Built locally, 9/9 tests against the real tarball. No `auth.json`; `var/lib/agentos-codex` holds only an empty `tmp/`; the workspace is empty. Credentials still enter only through #1015/#1014's vault and egress route.
- **The managed layers take effect and fail closed.** The pinned binary's `codex doctor --all` in a bwrap over the built rootfs reported config loaded, `managed filesystem source system`, approval `Never`, filesystem and network sandbox restricted, 9 denied-read rules, no MCP servers, provider `agentos` at `127.0.0.1:18432`, WebSocket off. With `/etc/codex` owned by uid 1001 (as when CI builds without sudo) the output was identical. Tools cannot change the files because the CLI's sandbox keeps the root read-only (C3). The test checks each installed file is a byte copy of the repo file.
- **#1419/#1505 containment is unchanged.** `managed_config.toml`, `requirements.toml`, `launch.json` and `agentos-toolsh` are only installed, and pinned by the byte-equality test. The image has no `git`, so C11's git route has nothing to run.
- **The CI step does not expose secrets.** The `checks` job has `contents: read`, checkout with `persist-credentials: false`, and this step has no `env` or secrets. The download is hash-pinned; the only third-party code it runs on the runner is the pinned binary's `--version`. Supply-chain exposure is no greater than the existing gVisor download.
- **Host binaries copied in** (`build-rootfs.sh:69-73`: sh, bash, coreutils, glibc) are unpinned, as in `guest/openclaw` and `guest/builder`, and run only as tools inside the CLI's sandbox. Not a new finding.
