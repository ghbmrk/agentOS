**Threat check**
- **A refused request fails closed with no state.** `freshLowCodeLocked` (approvals.go:204-209) runs after `newIDLocked` and before `c.reqN++`, the `Pending` commit and `c.open[id]`. `newIDLocked` only reads state. A refusal returns `(nil, err)`:
  - `Request` unlocks and returns the error, and nothing is texted.
  - `requestEach` skips that item, and the others still go.
  - The gate (grants/gate.go:2163, 2243) records `failed[ref]`, so retrying the request_id asks again.
  - Nothing is persisted, and nothing is left open.
- **Bias and prediction.** Each draw is `crypto/rand` uniform over 10^6. Excluding at most `MaxOpen`=50 values moves a guesser's odds from 1/10^6 to at most 1/999,950, which an attacker cannot use. The requester never sees the code: `Request` returns only the ID.
- **Learning other open codes.** An agent that can open requests has no way to choose or observe a draw, so a refusal or a redraw reveals nothing about any open code. With a working source, a refusal needs 16 straight collisions, with probability at most (5*10^-5)^16. Only a broken RNG can reach it, and then `randInt` would more likely panic first. Timing is the same: the extra loop over at most 50 entries depends on draws the attacker cannot see.
- **Constant-time.** Both the new check (approvals.go:242) and the matcher (`findLocked`, approvals.go:541) use `eq` = `subtle.ConstantTimeCompare` (codes.go:374).
- **Approval for the wrong request.** With an ID-less `YES <code>`, `findLocked` takes the single open request, or else the low-tier request whose code matches. A code that matches nothing counts as a wrong code toward the daily lock (approvals.go:360-367). Before this PR, two open low-tier requests could share a code, and map iteration then picked one at random. With uniqueness, the match is exactly one request.
  - Residual: a stale `YES` for a request that has already closed, whose code a newer request happened to draw. The odds are about 10^-6 per open request, the same as a blind guess, and it is inside the existing wrong-code budget. A stated `YES <ID> <code>` checks only that request's code, so it is unaffected. `LowLocked` and high-tier requests still require the ID (approvals.go:404-408).
- **Concurrency.** Every caller of `openLocked` holds `c.mu` (`Request`, `requestEach`, `RequestLocal`). `c.open` is read and written only under `c.mu`. Check and insert happen under the same lock hold, so two concurrent `Request` calls cannot both pass the check with the same code. The race detector is clean.
- **Other code mints.** The RESUME code (channel.go:824) and the rename code (name.go:110) also come from `textedCode`, but they are separate single slots matched only by their own command words (`RESUME`, `NAME`). A `YES` never matches them.

**Findings**
1. **broker/owner/codeunique_test.go:84: release.** The refusal test asserts only `len(r.ch.open) == 1`. The no-state property is what makes this fail closed, and a mutant that draws the code after the `Pending` commit passes both tests while leaving an orphan `Pending` ref (which a restart would re-issue). Please also assert `len(r.ch.codes.st.Pending) == 1` (under `ch.mu`), and read `open` under `ch.mu` as `lowCodeOf` does.
2. **broker/owner/codeunique_test.go:54-71: release.** CH-18's claim is that an ID-less `YES <code>` approves the request it names. No test sends `YES <code>` with two low-tier requests open and checks that `findLocked`/`answerLocked` approves the right one (and that the other stays open). One `Handle("YES 065793")` assertion on top of the existing rig would close this gap. This raises the combined review's item 3 to release, because tier-A security findings are never `later`.
