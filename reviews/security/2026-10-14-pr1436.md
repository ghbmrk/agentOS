### Checks

**Is the default D-115?** Yes.
- `boxLocked` (setup.go:1036): `checked = form == "ai-device" || p.PrivateOK`, unless the owner left an answer on a form that did not go through.
  - A plan sign-in is ticked.
  - An API key is unticked, unless that provider already has a yes.
- Private-hosted routes are not in the setup provider list. `setuphooks.go:143` maps only the vault's providers, and CAP-9 hosted routes are added on the local page, so they keep no.
- Credentials are never private data (REV-6, D-115). The box governs content only. The key goes to `ConnectAPIKey` as a call argument and is never rendered or echoed.
- The server reads only the posted `private` value. The default changes what is rendered, never what a forged or blank POST records: a POST without `private` records no.

**Is the answer saved only after success?** Mostly, but see S1.
- `aiKey` calls `privateOK` only after `ConnectAPIKey` returns nil.
- `aiDevice` calls it only after `StartDeviceCode` returns nil and the https check passes.
- "Success" for a device sign-in means the sign-in *started*. A yes recorded then stays inert until the provider connects, and the providers page shows it with a Stop button. I accept this.
- A failed `SetPrivateOK` *after* the key is stored is silent, and it leaves the provider's previous answer in place (S1).

**R1 fix: verified by my own probe.** This was a scratch test, not committed.
1. `POST /setup/ai-device private=1` recorded `private[anthropic]=true`.
2. The key form then rendered `name="private" value="1" checked`.
3. Saving a key with the box as rendered kept `anthropic:true`.

The inverse also holds: after a plan "no", the key box is unticked. Mutant SM1 (the R1 revert) is killed by `TestAKeyAfterThePlanKeepsTheProvidersYes`.

**CSRF, forged consent and replay on the setup POSTs.** These are probed with `POST /setup/ai-device provider=anthropic private=1` from the AI step. In every case below, nothing was recorded and the owner's error was untouched.

| Probe | Result |
|---|---|
| `Sec-Fetch-Site: cross-site` | 403 |
| `Origin: http://evil.example` | 403 |
| `Host: evil.example` (DNS rebinding) | 403 |
| A different phone's 64-hex setup cookie | 303, `errElsewhere` (`mayLocked`) |
| No cookie | 303, "Reload" |

Other guards:
- The setup cookie is SameSite=Strict and HttpOnly.
- The CSP sets `form-action 'self'` and `frame-ancestors 'none'`, plus `X-Frame-Options: DENY`. So a pre-ticked box cannot be clickjacked.
- Replay by the paired phone only restarts its own sign-in. Once setup is done, every setup POST redirects to /status.
- Before an owner exists, `mayLocked` is open to any phone. `aiReady` (`st.Host`) is what keeps a stranger's phone off the AI step then, and it is untested (S4).
- #1385 is unchanged by this PR. A compromised page process can already call `page_setup_private_ok` while setup is open (`localsrv/setup.go:207`, gated by `open` only). This PR adds no authority to the page process, and the `answer` map is display-only.

**The device-code render.** These were probed through the real template.

| Link or code | Result |
|---|---|
| `https://evil.example/"><script>alert(1)</script>` | href percent-escaped, text HTML-escaped |
| code `<img src=x onerror=alert(1)>` | escaped |
| `javascript:alert(1)` | refused (no link, form re-shown) |
| `//evil.example` | refused |
| `" https://x.example"` | refused |
| `HTTPS://ok.example/x` | shown (Go lowercases the scheme; fine) |
| `https:evil.example` (opaque, no `//`) | **shown**; browsers open https://evil.example/ |
| `https://user:pw@evil.example/` | **shown**; `https://openai.com@evil.example/` would display as openai |
| any `https://` host | shown; the host is not pinned to the provider |

So there is no XSS or script injection: html/template, the https check and the CSP all hold. Provider spoofing through the link is possible if the device-authorization response is ever wrong (S2). This is not live: `StartDeviceCode` answers not served (L43).

**"Your passwords and keys are never shown to it."** This is true for credentials the box holds:
- the vault is never agent-readable (CRED-1);
- CRED-7 redacts every vault value from agent-bound output, even when one appears inside mail;
- the key reaches only its own provider, as authentication (CRED-5).

It has two caveats (S3):
- (a) The provider receives its own key or plan login as authentication. #1424 covers this.
- (b) A password the box does not hold, such as a bank password someone mailed, is content, and an allowed provider sees it.

### Findings

**S1. Release (CAP-9, U-4; new in this PR; live with c4e2 #1264). If the answer fails to save after the key is stored, the failure is silent, and the provider keeps its old answer, which can fail open.**
- This PR moved `privateOK` after `ConnectAPIKey`. On main it ran first, so a failed save stored no key and the owner could retry.
- Now, if `SetPrivateOK` fails after the key is stored:
  - the key is kept, so the provider is connected;
  - the POST sets "Could not save. Try again.";
  - the next `GET /setup` runs `maybeFinish`, finishes setup and redirects to /status, so the error is **never shown**.
- Probe (scratch test, not committed):
  1. A plan sign-in with the default yes recorded `private[anthropic]=true`.
  2. `SetPrivateOK` was made to fail.
  3. The owner unticked the key box, which R1 now pre-ticks, and saved a key.
  4. `GET /setup` returned 303 to /status, with no error text, `finishes=1` and `private=map[anthropic:true]`.
- Result: the owner's explicit no is dropped without a word. Private content goes to a provider the owner declined.
- With no earlier yes, it fails closed, but the answer is still lost silently. This corrects combined L4(a), which said the page shows the error.
- It is not live until a provider reports `device_code` (c4e2). Today no earlier yes can exist during setup.
- **Fix.** While a provider's answer failed to save after its key was stored, hold setup open: `maybeFinish` must not finish while an answer is pending. Show the error with a box-only retry for that provider (a new `/setup/ai-private` with the same guards). Alternatively, retry the save before returning.
- **Test.** Make `SetPrivateOK` fail after `ConnectAPIKey` succeeded. Then check that setup is not done, the error shows, and the retry records the owner's answer. This kills SM14.
- **When.** Before c4e2 serves device codes, or folded into this PR.

**S2. Release (rides #1264 / #1014; not live). The device link's https check accepts any host, userinfo and opaque `https:` URLs.**
- The check accepts `https:evil.example`, `https://openai.com@evil.example/` and any `https://` host.
- Pinning the link to the provider's declared auth host is already in #1264's acceptance, from #1014. That pin should also refuse userinfo (`pu.User != nil`), opaque URLs (`pu.Opaque != ""`) and an empty `pu.Host`.
- No new issue. Posted as a comment on #1264 (see Filed).

**S3. Release (rides #1424). "Your passwords and keys are never shown to it" has two caveats.**
- It is accurate for credentials the box holds, through CRED-1, CRED-5 and CRED-7 redaction.
- Its caveats are: (a) the provider receives its own credential as authentication; (b) passwords the box does not hold, sitting in mail or documents, are content.
- The owner line is the one #1424 itself proposes, and #1424 is release. Posted as a comment on #1424 (see Filed).

**S4. Release (test gap, tier A). The security guards on the AI step are untested.**
- SM19 and SM20 survive: aiDevice and aiKey accept any provider id when `providerHas` is removed. This PR's `keepAnswer` relies on `providerHas` to bound the `answer` map.
- SM22 survives: `aiReady`'s `st.Host` gate is removed. Before an owner exists, `mayLocked` lets any phone on the Wi-Fi post, so this gate is what keeps a stranger off the AI step and its consent.
- SM15 survives: aiDevice shows the link although the answer failed to save.
- SM19, SM20 and SM22 are guards that predate this PR. SM14 and SM15 are paths this PR created.
- Add tests in the S1 issue.

**S5. Later (not security). Stale display answers.**
- SM16 and SM17 survive.
- `answer` is display-only, in memory and bounded, so a stale entry only pre-sets a box the owner can see.

**Accepted notes.**
- Because of the R1 fix, a yes given at a plan sign-in's *start* pre-ticks that provider's key box, even if the sign-in is never finished. The box names the provider, the yes is per provider (CAP-9), and the providers page shows it with Stop. I accept this.
- D-115 (API keys default no) still holds for any provider without a yes.
