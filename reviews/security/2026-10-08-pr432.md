## Threat check

Adversary: a clean-room guest (controls result file paths, contents and fixture report), a hint source (controls hint content), and crash or power loss at any file operation. Asset: the artifact store's publication integrity, the job queue (no lost or endless jobs), and clean-room machine lifetime.

- [Fact] **Names are broker-chosen.** The quarantine name is `<artifact ID>-<newID()>`. The artifact ID is `a-` + job ID, and the job ID is `newID()` (12 random hex characters, intake.go). The repair queue path is `repair-<job>`, gated by `segment` and `m.ID == "a-"+m.Job`. Guest file paths pass `cleanPath` and land only under `<stage>/files/`. A guest or hint cannot influence `.quarantine` naming or the `losses` match.
- [Fact] **The loss count can't be inflated or reset from inside the threat model.** `losses` counts `.quarantine` entries matching `<id>-` followed by exactly 12 hex characters, so an ID that extends another ID can't match. Damage requires a file to mismatch its manifest. The broker computes each hash from the bytes it writes, so a guest can't submit output that later fails `verify`. Resetting the count needs write access to the broker-held store, which is out of model. A crash between `renew` and `quarantine` repeats with the same count, so the step is idempotent.
- [Fact] **The quarantine rename has no guest-reachable traversal or symlink exposure.** Stage writes only regular files with `os.Mkdir` and `OpenFile`, so no symlinks are created. `rename(2)` moves the directory entry itself. In `finish`, the ID is validated by `get` before `quarantine`. The exception, a manifest whose own ID is trusted at open, is S1. It needs store tampering.
- [Fact] **An over-bound job fails closed.** Once a job has `maxRepairs` copies, `renew` stores `Attempts = cfg.Attempts`. On the next `runJob`, `Get` finds nothing because the artifact is quarantined, and the job is logged `failed` before `Create`, so no machine starts. Probed by mutation: making `renew` ignore the bound fails `TestRepairsAreBounded`.
- [Fact] **A damaged job can't keep a machine running or stay recorded as built.** `done` destroys the machine before `finish`, and `defer b.destroy(id)` covers every other return. `settle` runs before `logOutcome` and before the queue entry is removed, so damaged output never reaches `built`. The restored-job path (`Get` succeeds before `Create`) settles without starting a machine.
- [Fact] **Fail-closed reads are retained.** `ReadFile` still checks the hash. Quarantined artifacts leave `list`, `Get` and coalescing. A persistent `settle` or `quarantine` error leaves the job queued and retried after `Retry`, with no machine created.
- [Fact] **Checks.** `go test -race -count=1 ./cleanroom/...` passes in broker/ at the head, and `go vet` is clean.

## Points

- **S1 (release).** [Fact] At open, `openStore` returns the parsed manifest, and `New` then quarantines `m.ID` from that manifest's content, not the directory it was read from. `quarantine` doesn't validate the ID. Probe (run, not committed): a damaged directory `a-zzzzzzzzzzzz` whose manifest names a healthy artifact's ID moved the healthy artifact into quarantine and left the damaged directory listed. With `m.ID = "../victim"`, a directory outside the store was moved into it as `artifacts/victim-<hex>`. `m.ID = ""` would make `New` fail, because the rename targets the store directory itself. [Inference] Reaching any of these needs a manifest that parses but names another ID. Neither a guest nor a crash can produce one: writes are atomic, and the broker sets the ID. That takes write access to the broker-held store, so it is defence in depth, not an exploitable path at this head. Fix (a few lines): in `openStore`, treat a manifest whose ID differs from `e.Name()` as unreadable (`Manifest{ID: e.Name()}`), and have `quarantine` refuse any ID that fails `segment` or starts with a dot. Add a test. UX cost: none. Potency cost: none.
- **S2 (later).** [Fact] The durability-order tests check the fault-hook trace, not the system calls. Removing `syncDir` in `fill`, or `f.Sync()` in `writeSynced`, while keeping the hook still passes (table above). The code is correct at this head, and each hook sits on the line next to its call, so this is regression protection only. A syscall seam (`syncDir` and `Sync` behind the same hook) would close it. This complements L3's l3 and is not a duplicate of it.

No blockers.
