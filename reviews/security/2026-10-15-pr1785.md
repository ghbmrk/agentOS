## Review (a06c6ab, round 1, Security record)

Verdict: ACCEPT. Comment: https://github.com/ghbmrk/agentOS/pull/1785#issuecomment-6183042056

#### Security review

**Verdict: ACCEPT**, head `a06c6abe417d2071a85431cae38749fcadd944d4`. Tier A (`tools/risk_tier.py --git origin/main HEAD`: A; the issue said B).

The guard is correct. A `LocalAlertAt` after now no longer holds the sign-in text back. The past window and the equal-timestamp case behave as before. One test-strength gap is listed below as class:release.

##### What was checked
- **Edges (`since := now.Sub(LocalAlertAt)`; held only while `0 <= since < SignInAlertEvery`).** I probed each edge on the rig, with the TOTP step taken before `LocalAlertAt` was set:
  - +1ns: sent.
  - equal: held (correct, because a text just went).
  - -1ns: held.
  - -1h exactly: sent.
- **Zero time.** `now.Sub(time.Time{})` saturates to a huge positive value, so the zero value is never held. The `IsZero` term is redundant but harmless (mutant M5 below is equivalent).
- **Clock jumps back.**
  - When `LocalAlertAt` ends up in the future, it now counts as expired, whether it is in memory or was persisted by a skewed clock before a restart. Persisted JSON has no monotonic reading, so the gate compares wall times, and that is the case the fix covers.
  - When `LocalAlertAt` is still in the past after a step back, the hold runs until wall time reaches `LocalAlertAt+1h`. That is at most `SignInAlertEvery` of real time after the step, which is the coalescing CH-15 already accepts. So clock skew can no longer suppress alerts for longer than that.
- **Flood or rate limiting.**
  - `sendSignIns` stamps `LocalAlertAt = now` after a successful send, so the normal hourly pacing resumes right away.
  - `c.local.sending` still serialises senders.
  - A text needs pending `LocalSignIns`/`LocalAnswers`, and sign-ins are bounded by `LocalBound` (24 per window).
  - An attacker who keeps stepping the clock back gets at most one extra text per step, never a silenced one, which matches O35's stated cost. This is fail-loud, and the right direction for a security alert.
- **Concurrency.** All three call sites hold `c.mu`:
  - `FlushLocal` (local.go:235-237)
  - `LocalSignIn` (local.go:390, before the `c.mu.Unlock()` at :396)
  - the page-answer path (local.go:699, before the `Unlock()` at :701)

  The new test writes `codes.st` under `r.ch.mu`. `go test -race -count=1` passed on `./owner/...`, `./localui/...`, `./localsrv/...`, `./localapi/...`, `./daemon/...` and `./cmd/agentosd/...`. `go vet ./owner/` is clean.
- **ASSUMPTIONS.** Main's highest row is O34, so O35 is free. #1745 adds O33 (a gap below O34) and #1686 adds O22/O28/O32. Neither uses O35, so **no renumber is needed** whichever lands first. Only a textual merge of adjacent table rows may be needed.

##### Findings
1. **class:release (test strength).** `TestFutureLocalAlertAtDoesNotSuppressSignInAlerts` only probes about +24h (+23h59m30s after `totp()` advances the clock). A guard with a tolerance window survives it: both `since >= -time.Minute` and `since >= -23*time.Hour` pass the whole owner suite. The second would still let a skew of up to 23h silence alerts. **Fix:** add a case where `LocalAlertAt` is a small amount ahead of the time `LocalSignIn` sees. Call `r.totp()` first, then set `LocalAlertAt = r.clock().Add(time.Nanosecond)` (or `time.Second`). I confirmed that probe kills both tolerance mutants and passes on this head. Optionally, also pin that an equal timestamp is held (today only `TestPageDecisionsAreToldNamingThePage` catches `since > 0`, and only indirectly).
2. Note, out of scope for this PR: `LocalStart` (local.go:325, :409) has the same pattern. A future `LocalStart` from a skewed clock keeps the local sign-in bound window open until real time catches up. That fails closed (local sign-in stays paused, which is availability, not alert suppression), so it is not a defect here. It may be worth filing alongside the O35 rule ("a new gate on a stored send time must treat a time after now as elapsed").
