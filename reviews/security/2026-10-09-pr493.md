## Threat check

**Clear without Loop 2's fix (item 1, `LinkedHold`, `passedReported`).**
- [Fact] A reported finding closes as cleared only when `rec.Fixture == loop2/<id>`, and `link` sets `Fixture` only when every case add for the finding succeeded or was the same case already there. `Fixture` never goes back to empty, and nothing removes security cases (`ForgetGoal` touches task cases only). So a cleared finding always has both its minimized regression and its original unminimized rule linked; the regression passing alone cannot clear it (the gap #464's Security 4a closed for fixes is not reopened here). `TestAFindingMissingACaseIsNotClearedByTheOthers` covers the refused original.
- [Fact] `LinkedHold` fails closed: no linked case means no hold, and a linked case that `AnswerTreeRule` cannot answer (not a tree rule, e.g. a held variant needing a run) never holds. It reads the active tree under the pipeline lock and changes no state.
- [Fact] Clearing keeps the pause (A-6) and the linked cases stay in the suite, so after clearing they pass on the baseline and PS1 rejects any later candidate that breaks them. Clearing therefore tightens, not loosens, the suite. The held candidate for the finding is dropped with it (`delete(s.held, id)`).
- [Fact] A rule that holds cannot be re-reported (`reportable` refuses it); if the tree regresses later, a fresh report of the same rule re-links the same cases as same-case duplicates.

**ID collisions (item 2, `ErrConflict`).**
- [Fact] `addCase` returns `ErrDuplicate` wrapping `ErrConflict` when the stored case differs in input, expect, finding or `Security`; `link` treats only a non-conflict duplicate as done. A finding reported as `X/original` therefore cannot stand in for `X`'s original slot: `X` is left unlinked, no fix is requested, and the tree is unchanged (fail closed; the brief's second acceptance option). `Class`, `Public` and `Implicit` are not compared; every Loop 2 case uses `ClassConfig` and no other path adds a security case under a `loop2/` ID, so no realistic difference is missed.
- [Fact] The only other `ErrDuplicate` caller, `harvest.go`'s `AddTaskCase`, still tolerates any duplicate as before; task cases are unaffected.

**Resume (item 3, `resumeReported`, `Told`).**
- [Fact] The minimized regression is computed before `handle`'s first save and persisted in the record (`[]byte`, exact base64 round trip), so a resume links the same bytes and does not hit a self-conflict after the tree moves.
- [Fact] A resumed finding gets its two linked cases before `Fix` becomes pending, so the fix proposed in that same `Pass` is graded by them (LOOP-10 (g) holds). Held variants the harness links after `Report` returns are added outside the Guard and are already present.
- [Fact] Resumes hold `reportMu`, so a resume and a `Report` never overlap; `Told` is set after `Notify`, giving at-least-once delivery, and S21 documents the duplicate text after a crash between the two.

**Config fixes (item 5).** [Fact] Not relaxed (S22): a `config/` fix with unevaluable plain probes stays rejected, and the suite count never drops. This is the fail-closed choice; LOOP-10 (f) is untouched.

**Credentials, PII.** [Fact] No credentials, tokens, addresses or personal data in code, tests or fixtures; test values are synthetic config. Owner texts carry only the finding's line as before.

## Findings

1. **release** (CHG-2, LOOP-10) — **A reporter that controls finding IDs can block another finding's fix by reporting `X/original` first.** The collision now fails closed (X stays contained, paused and unfixed), but X then waits indefinitely, and its resume errors on every `Pass`. Today `Report` has no production caller; P3-4b-3 and -4 are the first sources, and their IDs may be derived from fuzz or corpus input. Proposal: `reportable` refuses an `f.ID` ending in `OriginalSuffix` (and any ID that would collide with `loop2/<other>/original`), with a test, in P3-4b-3, the first package that wires `Report`. UX cost none; potency cost none.
2. **release** (LOOP-9) — **The clear check and the close are not atomic.** `passedReported` answers `LinkedHold` before `Pass` takes `s.mu` to close. An owner-path adoption or revert that changes the active tree in that window could close a finding whose cases fail again. The impact is bounded: the pause stays, the linked cases stay in the suite, and the next report of the rule re-opens it. Proposal: either re-answer `LinkedHold` for each cleared ID immediately before deleting it, or record in S19 that the close is best-effort and self-heals on re-report. UX cost none; potency cost one extra tree-rule answer per cleared finding. Classed release rather than later because it is a tier-A security point (OPERATING §2).
