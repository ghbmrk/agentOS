# Security 4a, PR #670 (ARC-6)

Record: PR #670 · package ARC-6 · head 71168ff

**Security 4a (tier A; `broker/guest`, new `broker/fold`).** Read from the diff 8420edf..71168ff against ARC-6, plus the code the new store's lifetime depends on (`guest.Plane.Open`/`close`, `vm.Manager.reserve`/`unreserve`/`Destroy`). Points 1 to 3 were confirmed with throwaway tests against the head (not committed).

**Threat check.** Adversaries: a hostile guest, a sibling machine, a later machine that reuses a destroyed machine's ID. Assets: another machine's held tool results, and the data-label boundary (REV-5) those results sit behind.
- Read isolation between live machines holds structurally: `result_read` keys on `m.id`, taken from the socket the request came in on, never from guest input, and the stand-in ID is 128 bits from `crypto/rand`.
- `result_read` is dispatched ahead of the `Tools` lineage gate. That is sound only while the store holds nothing but the calling machine's own results, which point 1 breaks.
- No credential, grant or effect path changes. The stand-in head is a prefix of a result the guest was already owed.

**Fix-list**

1. **blocker** (ARC-6, REV-5; defect): held results outlive the machine. `Plane.close` never drops the machine's `fold.Store` records, and `vm.Manager.reserve` explicitly lets an ID be reused after destroy, with a fresh lineage so it "must not inherit an old machine's" state. A new machine created under the destroyed one's ID reads the old machine's results, without the label raise the original call carried. Confirmed: `big` on m1, `Close("m1")`, reopen m1, then `result_read` with the old ID returns all 8224 bytes, `isError=false`. This contradicts the package's own claim, "A machine cannot read another's". The ID is unguessable, so the path needs a 32-hex-char leak from the old guest, but that turns a 128-bit channel into up to 4 MiB of labelled data. Fix: drop the machine's records in `Plane.close` when `forget` is set, or key records by lineage instead of ID; add a test that destroys, reopens the same ID and asserts the read fails.
2. **blocker** (ARC-6; defect, cross-machine interference): eviction is global FIFO. When the caller passes `perMachine`, `evict` pops `s.order[0]` whatever machine owns it, so every older record of every other machine goes before the caller's own. `totalBytes` is shared too. Confirmed: one m2 result, then 33 from m1, and m2's `result_read` fails. A hostile guest can flush its neighbours' held results at will. Fix: bound bytes and count per machine and evict only the caller's own oldest records. If a global cap stays, refuse to hold rather than evict another machine's records.
3. **blocker** (ARC-6; defect): a result larger than the store's byte bound gets a stand-in whose original is evicted in the same call, so it can never be read back. Confirmed: a 5 MiB body yields `folded=true` and `Read` returns false. The guest gets 256 bytes of a result it was owed whole, with no signal that it is gone. Fix: when a body cannot be held within the caller's own budget, do not fold it. Return it unchanged, or return an error result that says so, and test that boundary.
4. **later**: if `crypto/rand` fails, `newID` returns `""`, and `Hand` still returns a stand-in that `Read` can never satisfy. Return the body unchanged instead. Not reachable in practice: since Go 1.24, `crypto/rand.Read` does not return an error.

Re-sign: the fix delta is tier A by OPERATING §3, so it needs a Security re-sign. If the fix touches only `fold`, `plane.go`'s close path and tests, a short re-sign suffices.
