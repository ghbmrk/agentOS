# Security lens: #1073, CTRL-card-wire (Owner Card wired into setup and first boot), head fc07ae8

Record: PR #1073 · package CTRL-card-wire · head fc07ae8

Scope: the PR at fc07ae8. Tier A (`risk_tier.py`: cmd/agentosd, localui, firstboot). The L3 verdict is PR comment 6120563782. `go test -race` passes on `./cmd/agentosd ./localui ./firstboot ./card ./localsrv ./daemon`, and the ARC-2 guards are green.

Question: can a box finish setup, or keep a usable vault key or code seed, without a confirmed Owner Card? Can a reset destroy a confirmed owner's vault, or another localui route get past the hold?

Threat check:
- Finish bypass: on localui, `host` needs `Recovery`; `recovery()` refuses while `cardHeld()`; the `ai*` routes need `Host`; and `Hooks.Finish` is reached only through `maybeFinish`, which checks `cardHeld()` first. `/setup/restart` clears `Recovery`. On agentosd, `OpSetupFinish` is the only op that writes `Finished`, and it is wrapped by `Hold()`. Mutants that remove either localui gate or the agentosd wrapper are killed.
- Card exposure: `/setup/card` is on localui's own mux, behind the subnet, Host, same-origin and claim checks, and is served only to the setup cookie in `st.Device` while setup is open. A mutant that forces `paired` true is killed.
- Unconfirmed vault: `Provision` runs only on a correct confirm. If the latch then fails to save, the hold stays. The next start runs `ResetUnlatched` before `NewCardStep` and draws a new card (brief test 3 uses a real `vault.CreateSealed`). An unreadable latch resets nothing.
- Confirmed owner: a confirmed latch never resets. `setupMode.run` calls `Card()` only after the finished-record and owner-state checks, and a mutant that reorders them is killed.
- Production: agentosd `main` hands setup mode no step, so setup without `-owner` fails closed. The image always passes `-owner`, and agentos-localui sets no setup `Hooks`.

Findings: blocker 0; release 2, both conditions on the proposed CTRL-card-vaultop row:
- S1 (HW-1, A1). The reset's safety rests on call order alone, and a missing latch reads as unconfirmed. The vault op's reset must refuse once a seed was sealed at finish, and must be callable only from setup mode. Failure path: a lost latch, or a step built outside `setupMode.run`, wipes a finished vault.
- S2 (ONB-7, HW-1). Codes (step 3) are enrolled before the card (step 4). Provision-from-card must carry the step-3 seed into the card's vault, and the unlatched reset must discard the seed with the vault. Failure path: the owner's authenticator stops working, or a seed stays usable without a confirmed card.
