## What changes for an attacker
`custody.sealEnroll` (agentos-egress) now refuses the seal with `errCardRequired` (428) while the open vault holds no `recovery.CardName` entry. The check runs after the not-open, sealed and not-confirmed checks, and before the `Sealed` state mark and the `EnrolledName` write. `modelroute` reads 428 as `ErrCardRequired`. agentosd maps that to `localsrv.EnrollCardRequired`, and setup's finish answers the fixed code `card pending` and records nothing. Before this change, a stale page latch after a remade vault, or a page that reports the card without making one, could seal a vault that no card made. The owner's card would then open nothing, and recovery would fail (A1).

| Path | Stop | How |
|---|---|---|
| Race between check and seal | structural | `sealEnroll` holds `c.mu` from the check through `persist`, `putMark(EnrolledName)` and the deletes. Every swap or removal of `c.v` (`provisionCard`, `resetCardRemade`, `remakeSetupLocked`, lock) runs under `c.mu`. The vault cannot change between the check and the seal. |
| Other seal paths | structural | `EnrolledName` is written only in `sealEnroll`. `setupopen.go:92` and `syncMarksLocked` set only the state file's `Sealed` mark, and only from a vault that already holds the seal. They never write one. `/enroll/seal` is the only route into `sealEnroll`. |
| Entry name the caller controls | structural | `CardName` ("owner-card") is written only by `recovery.storeCard`, inside `recovery.Provision` while `buildCardVault` builds the card's vault. Caller-named writes cannot reach it. `put` and `setupKey` accept only an `adapterCredential` name and refuse another kind (`custody_test.go:396` covers "owner-card"). Pins are prefixed `netpin:`, and private marks `PrivateOKPrefix` plus a known adapter. Nothing deletes `CardName`. |
| Stale card entry | structural | The check reads the vault that is open now, not the latch or the state file. A remade setup vault (`remakeSetupLocked`, `init -setup`) holds no card entry. A card vault is built only from a confirmed seed (`errCodesUnconfirmed`). `buildCardVault` copies the setup vault's entries, but an existing card entry short-circuits to `sameCardLocked` first, so no card entry is carried in from elsewhere. |
| Empty or wrong-kind entry | accepted | The check tests presence by name, not `KindCard`. Only `storeCard` writes the name, always with `KindCard` and an encoded card, so no writer can plant an empty or other-kind entry. `hasKind` would be belt and braces with no exploit path today. |
| Error mapping leaks | none | The egress 428 body is fixed text with no vault data, and modelroute discards it, returning a fixed sentinel. agentosd returns the fixed `localapi.ErrCardPending` code. Nothing is logged. |
| Fail closed | yes | A refusal writes nothing: the `Sealed` mark comes after the check, and the test asserts that `SetupOpen` is kept and nothing is enrolled or sealed. A locked vault gives 503 and `errFailed`. An older agentosd talking to a newer vault gets 428, which hits `enrollCall`'s default error, then `errFailed`. Either way finish records nothing. The page records `Done` only on success or `AlreadySetUp()`, and agentosd stays open on this refusal. |
| Compromised page (own uid) | narrowed | The page can no longer finish without the vault holding a card. Whether the owner actually saved the card is still attested by the page alone (HW-1 hold). The vault cannot know this, and the ASSUMPTIONS row S2-1 scopes the proof to "a card made it". |
