## Review (c33cb5d, round 1, Security record)

Verdict: CHANGES. Comment: https://github.com/ghbmrk/agentOS/pull/1774#issuecomment-6182445823

#### Security review (tier A), head c33cb5d6b5437383c5099796dff8b3980139ff00

Verdict: CHANGES

The code is correct. Two tests are missing, and without them the checks that keep the lockout authorization from being lost can be broken without any test failing. The fix is tests only.

**Tier and checks.** `tools/risk_tier.py --git origin/main HEAD` prints A. `go test -race` passes on `./cmd/agentos-egress`, `./vault` and `./durable`. All CI check runs on c33cb5d6 are green.

**Threat check (durability and crash order).**
- `durable.WriteFile` fsyncs the temp file before the rename, so the file's contents are already durable when `Put` returns. The only gap was the directory entry (`landed` returns nil on `ErrDirSync`). `Vault.Sync` (broker/vault/rollback.go:330-337) fsyncs the vault directory under the read lock. This is a real `os.File.Sync` on the directory through `durable.SyncDir`. It also covers the `keepDAOriginal` write and a `held` entry from an earlier write whose sync failed.
- trusted.go:830 runs before `TakeLockout` at :837. There is no path where the TPM takes an authorization whose vault entry is not yet durable. With a counter-bound vault, a file left one ahead after the sync is the documented state that `advance` finishes, so this adds no rollback risk.
- Failure path: on a sync error the TPM is unchanged, `auth` is cleared, and only an entry this call created is deleted (`!held`, :832-834). If the `Delete` itself does not become durable, the worst a crash leaves is an unused entry next to an unchanged TPM. That is harmless: the next enroll runs with `held=true`, and `TakeLockout` sets the value from empty. `Delete` cannot remove an entry that existed earlier, because of the `!held` guard.
- Exposure: the returned error is the OS or `ErrDirSync` error. `trust` turns it into the fixed message "could not make this PC trusted; nothing was changed". No PIN or authorization reaches logs or messages.

**Mutants (run by me, against `./cmd/agentos-egress` and `./vault`)**
| Mutant | Result |
|---|---|
| M1 remove the Sync call | killed (TestLockoutAuthIsSyncedBeforeTheTPMTakesIt) |
| M2 move Sync after TakeLockout | killed |
| M3 ignore Sync's error | killed |
| M4 no Delete on a sync failure | killed |
| M5 Delete on a sync failure even when `held` | **survived** |
| M6 `Vault.Sync` returns nil without calling `syncDir` | **survived** |

**Findings**
1. **blocker:** broker/cmd/agentos-egress/trusted.go:832 has no test for the `held` case (M5 survives). If the `!held` guard is dropped, a sync failure on a re-enroll deletes the only copy of an authorization the TPM already holds. That is the lockout loss this PR exists to prevent (HW-8, CRED-8). Add a test: trust with a PIN, inject the sync fault, trust with a PIN again, then check that `lockoutEntry()` is unchanged. I checked that this test passes on c33cb5d6 and kills M5.
2. **blocker:** broker/vault/rollback.go:336. The `InjectSyncFault` check sits before the real fsync, so nothing proves that `Sync` fsyncs the directory (M6 survives). A `Sync` that does nothing makes the whole PR a no-op. Add a vault test that swaps the package `syncDir` variable, as vault/dirsync_test.go:343 already does: `Sync` returns its error, and nil when it succeeds and was called.

No class:release items.

Verdict: ACCEPT

The delta from de10a7cd is the merge of main (de6e0572) and the fix commit 7500e6aa. The lockout-loss invariant still holds, and wrapping the error does not cause any caller to treat a failed Sync as success.

**Merge of main (de6e0572).** The merge base is origin/main (8fd5bf93). `git diff --stat de6e0572^1 de6e0572 -- broker/cmd/agentos-egress broker/vault broker/durable` is empty, so the merge's 20 files touch none of the PR's paths. `git diff origin/main...HEAD` lists the same 7 files as before.

**Locking in `Vault.Sync` (rollback.go:331-344)**
- `RLock`, `v.syncDir()` and `RUnlock` run in a straight line. No early return sits between them, so there is no double unlock and no leak on any return path. The injected-fault branch never takes the lock.
- One difference from the old `defer`: a panic inside `v.syncDir()` would now leak the read lock. In production `syncDir` is `durable.SyncDir`, which only calls `os.Open`, `(*File).Sync` and `Close`. None of these panics, so this is a theoretical gap. Informational: a closure with `defer` would keep the old guarantee at no cost.
- Mutant: I dropped the `RUnlock`. `./vault` then deadlocks (test timeout at 60s), so the existing tests catch a leaked lock.

**Callers of the wrap**
- `grep -rn '\.Sync()'` over broker/ finds one `Vault.Sync` caller, trusted.go:831 (`takeLockout`). The other hits are `*os.File`, journal and clock `Sync` methods. On any error that caller clears `auth`, deletes a new entry when the entry was not held, and returns before `TakeLockout`. It never checks the error's type, so the wrap does not change its behaviour.
- The error goes up through `enroll` unchanged. `takeLockout` fails before `tookNew` is set and before the deferred `giveBack` is registered, so nothing in between looks at it. At custody.go:1450 it becomes `errHostNotDurable`, a fixed string, so the OS error and path still do not reach the response.
- Every `durable.ErrDirSync` check in broker/ (non-test):
  - "landed = success": recall/store.go:94, recall/dir.go:192, journal/store.go:113, vault/rollback.go:298, vault/vault.go:329 (`landed`), cmd/agentosd/apnetrot.go:52
  - typed mapping: loops/settings.go:843, change/pipeline.go:547, custody.go:1450

  Each one tests the result of its own `durable.WriteFile` or `Rename`, or of `v.write`. None sees the result of `Vault.Sync`. In particular, `Vault.landed` wraps only `v.write(...)` results, never `Sync`. No path treats a Sync failure as landed.

**Meaning of ErrDirSync.** durable.go:19 defines it as "the directory sync after a rename: the new name is in place but may not survive a power cut". For `Sync`, the last landed write is in place and only the directory sync failed, so the meaning roughly fits. The probe case (vault directory moved away, `open: no such file or directory`) stretches it, but its only consumer treats it as failure, so this is safe. Forward hazard, informational: if someone later routes `Sync` through `landed()` or a "landed = success" check, the failure would be swallowed and the TPM taken without a durable copy. `TestLockoutAuthIsSyncedBeforeTheTPMTakesIt` and `TestHeldLockoutAuthSurvivesAFailedSync` would catch that, because they assert `errHostNotDurable` and that the TPM is unchanged.

**Invariant tests.** Both egress tests now inject a plain error, so they go through the production wrap and mapping. With the wrap reverted (`return err`), all three new tests fail; details are in the Potency review. The M1–M7 set from the last round still applies; the fix did not touch that code.

## Review (595e011, delta 3, Security record)

Verdict: ACCEPT. Comment: https://github.com/ghbmrk/agentOS/pull/1774#issuecomment-6183079076

#### Security delta review (tier A), head 595e0111a628b466889a5359c09e42892d072292

Verdict: ACCEPT

The delta from 7500e6aa is commit 595e0111 (4 files). It changes one user-facing string and adds a test-only fault hook to production code. When the hook is not armed, behaviour is unchanged. The hook cannot be armed outside a test binary. The state it leaves on disk is the state a real failure leaves, and later trusts and boots handle it safely. On a PIN trust, the TPM lockout is handed back on this path.

**1. Can the hook be armed outside tests?**
- `InjectStageFault` (faults.go) starts with `if !testing.Testing() { panic(...) }`. That is the same guard `InjectSealFault` and `InjectSyncFault` already use in this file, and both are already in main's precedent. `testing.Testing()` is true only in a binary built by `go test`, so a production binary that called it would panic before storing anything.
- No production caller exists. `grep -rn InjectStageFault broker/` finds only the definition and trusted_test.go:1302.
- Importing `testing` into the vault package is not new: faults.go already imported it before this commit. No other non-test file in broker/ calls `testing.Testing`.
- `stageFault` is unexported, and nothing else writes it. Production code can reach it only through the guarded function.

**2. Is non-fault behaviour unchanged?**
- `replaceKeys` used to do `if err := writeFile(...); err != nil { return err }`. It now does `err = writeFile(...); if err == nil { err = injectedStageFault() }; if err != nil { return err }`.
- With no fault set, `injectedStageFault()` returns nil (`p == nil`), so the control flow is identical. Reusing the outer `err` (from `json.Marshal`, which is nil at that point) is harmless.
- The added cost is one atomic load per slot change.
- `InjectStageFault(nil)` is also inert, because of the `*p != nil` check.

**3. Is the injected state equivalent to the real failure?**
- In production, `writeFile` is `durable.WriteFile` (vault.go:363). A failed directory sync after the rename returns `fmt.Errorf("%w: %w", ErrDirSync, err)` (durable.go:104), and the `.next` file is already in place.
- The hook returns `fmt.Errorf("%w: %w", durable.ErrDirSync, *p)` after the `.next` file lands. In both cases the error has the same shape, and it is returned at the same point: before `v.nextKeys = raw` and `save`, and not wrapped in `ErrSlotDecided`.
- The one difference is that with the hook the directory sync did succeed, so the file is durable. That does not matter, because nothing in the process records the file.
- Later trust: the vault's `nextKeys` is nil, so the next `AddSlot` overwrites `.next`. The new test's "trust again" step does exactly this and passes.
- Later boot: the save never ran, so the vault file does not name the staged keys. `OpenSealed` treats a stray `.next` as inert, and `dropStaleStaged` removes it. `TestChangeBeforeSealReportsUnfinished` (interrupted_test.go:50) covers that: the staged file's slot gets `ErrNoSlotOpens`, and the file is removed.
- `AddSlot` does not change the passphrase, so no spurious `ChangeUnfinished` is reported.
- This is the same leftover state that `replaceKeys`' existing save-failure branch already accepts ("a leftover copy is inert").

**4. On a PIN trust, is the TPM lockout handed back on this path?**
- The doc comment's claim is true. In `enroll` (trusted.go:755-771), `takeLockout` runs first: the authorization is stored, `Vault.Sync` runs, and then `TakeLockout`. `tookNew = !had`. The deferred function calls `giveBack` when `tookNew && err != nil && !errors.Is(err, vault.ErrSlotDecided)`, and a staged-keys `ErrDirSync` meets those conditions.
- Probe: a throwaway test that I did not commit, with `InjectStageFault` and `trust(code, "246810")`, gave:
  - the error is `errHostNotDurable`, with the conditional `-pin` text;
  - `lockoutEntry() == ""`, so the authorization was forgotten;
  - `tpm.ThiefLockReset()` returns nil, so the TPM's lockout is empty again;
  - after the fault is cleared, a PIN trust succeeds, `ThiefLockReset` then fails with `TPM_RC_AUTH_FAIL` (the lockout was taken), and `hosts` lists 1.
- If the lockout was already held (`had`), `giveBack` correctly does not run. That entry was already synced and belongs to an existing PIN slot.
- If `ReleaseLockout` itself fails, `giveBack` keeps the entry. That entry was made durable by `Vault.Sync` before `TakeLockout`, so a staged-file sync failure cannot lose it.

**5. Message mapping**
- custody.go:1450 is unchanged. `ErrSlotDecided` is checked first, then `ErrDirSync` → `errHostNotDurable`, then everything else → `errHostNotSaved`.
- The new text is still a fixed string, so no OS error or path reaches the response.

**Checks**
- `go test -race -count=1 ./cmd/agentos-egress/... ./vault/... ./durable/...`: all ok (104s, 14s, 8s).
- `tools/risk_tier.py --git origin/main HEAD`: prints A.
- Diff vs origin/main: 8 files, all under broker/cmd/agentos-egress and broker/vault.

**Findings**
- None blocking. None class:release.
- I3 (info, no action): the doc comment says "giveBack hands it back". More precisely, that happens only when this call took the lockout. A lockout that was already held stays, which is the correct behaviour.
