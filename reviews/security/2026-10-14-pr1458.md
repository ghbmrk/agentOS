**Checked**
- Ran `tests.test_image`: 107 OK. `doclint` exits 0, and `risk_tier --git origin/main pr1458` gives A. CI is green at this head. The `checks` job ran `UplinkByNetworkd.test_the_shipped_uplink_takes_a_lease_behind_the_drop` as root and it passed (ok, not skipped). The image job (`build (a)/(b)`, which runs `ci_boot.sh` with the lease and `none` checks) and `reproduce` passed too. Locally the netns tests skip because there is no `ip` binary.
- **Inbound exposure on the uplink.** `agentos-inbound` loads at sysinit, `Before=network-pre.target`. `systemd-networkd` and `systemd-resolved` both `Requires=`/`After=` it, and the new test pins that. Nothing else in the package set configures links (there is no ifupdown and no NetworkManager), so no link is up before the drop. The drop admits only `lo`/exempt traffic, established/related traffic, RA from fe80 with hop limit 255, NS/NA, DHCPv4 replies and DHCPv6 replies from fe80. That covers the IPv4 lease, the SLAAC/DHCPv6 address and link-local. resolved's LLMNR listener (5355, on by default in Debian) and the page on :80 sit behind the same drop. mDNS is off by default. Exempt elements are added only by `ap-exempt`, which refuses non-wireless links, so `Type=ether` links can never be exempt.
- **Egress decoupled from wait-online.** `agentos-egress` keeps `Requires=`/`After=agentos-inbound`. Dropping `network-online.target` changes when egress starts, not whether the firewall is up first. With nothing learned, netguard fails closed (N10).
- **DHCP/RA-supplied data.** networkd's defaults apply (UseDNS, UseRoutes including option 121, RDNSS, route info). The resolver is *assigned*, not pinned, by design (N3/N10). It reaches only `PurposeDNS` on :53, every answer is checked against the refused set (N1/N2), and unpinned names get chain plus name TLS verification (N6). Option 121 and RA routes change the next hop only. netguard checks destinations, so a rogue router gains an on-path position that TLS already covers, not a bypass. No NTP client ships, so UseNTP is inert.
- **Setup AP to LAN path.** Nothing sets `ip_forward`. gVisor runs `--network=none`, and passthrough is refused. `agentos_ap`'s forward chain drops in and out of the AP interface. I found no bridge and no forwarding path.

**Findings**
1. **release: probe the inbound drop on the booted image (reclassify #1457 u1b from later).** This PR is the first time the shipped image has a network. DEV-2 ("no home host opens a box port") is a tier-A claim, and today it is shown only in netns on the runner's systemd (Ubuntu, 255), not on the image's trixie networkd and not with the image's own listeners (resolved 5355 tcp/udp, the page on :80). The reason given for deferring it is not right: QEMU user networking *can* open connections into the guest with `hostfwd=` (they arrive from 10.0.2.2, a LAN host from the guest's view). A tap/bridge NIC on the runner, or a `-netdev socket` peer, also works. The probe should cover the leased v4, the SLAAC v6 and the fe80 link-local address. The netns test should also probe link-local and run its potency control on IPv6, since its only control is IPv4.
2. **release (already filed): #1439 is now reachable on the image.** Before this PR the image had no uplink, so netguard never learned an external address there. Now it does, and egress starts before the lease with no network-online gate, so the first learns happen during link churn, when concurrent Refreshes are most likely. The stale Refresh that #1439 describes can then regress `External` (the hairpin to the home router's WAN address). I am not filing a new issue. #1439 must land before release.
3. **later: distro `.network` files and forwarding.** Debian's systemd ships `/usr/lib/systemd/network/80-container-ve/vz.network` and `80-vm-vt.network` (`IPMasquerade=both`, which enables forwarding) and `80-wifi-adhoc.network` (`Type=wlan`, `MulticastDNS=yes`). None of them matches a link the image creates, and creating one needs root, so there is no reachable path. However, I17 says "the image test fails if any `.network` file matches a radio", and the test globs only `mkosi.extra`. Mask them (or RemoveFiles), and have health assert `net.ipv4.ip_forward=0` / `net.ipv6.conf.all.forwarding=0`. `agentos_inbound` has no forward hook.
4. **later: uplink privacy and hardening.** By default networkd sends the hostname (`SendHostname=`), and it may form SLAAC addresses from the MAC (EUI-64), which are then visible to every provider. resolved's LLMNR sends single-label queries onto the LAN. Consider `IPv6PrivacyExtensions=` or a stable-privacy token, `SendHostname=no` and `LLMNR=no` via a drop-in.

**Not a blocker:** main now has **I18** (#1419). `image/ASSUMPTIONS.md` conflicts on merge, and this PR's row must renumber to the next free number in merge order (I19 today). The references to it in I11, I17 and the I18 row text, and in the PR body, need the same change.

## Delta round (038d484c)

- **The probe not running cannot pass.** The output goes to `console.log.probe`, and `has` greps it for each `agentos-probe: <port> dropped`. If the file is missing or the script crashes, the result is MISS and the job fails. The `|| true` on the probe call only defers the failure to those checks.
- **A failed forward cannot read as "dropped".**
  - If QEMU cannot bind a `hostfwd`, it does not start, and the boot checks fail.
  - If nothing accepts on the host port, the result is `error`, not `dropped`.
  - If the guest has shut down, QEMU has exited, so the result is also `error`.
  - The unit test `test_drop_probe_tells_a_silent_guest_from_an_answer` pins all three outcomes against a local stand-in: silent gives `dropped`, accept-then-close gives `answered`, and no listener gives `error`.
- **Potency without the drop.** No port in the probed set has a listener on the uplink. localui binds to the access point with `SO_BINDTODEVICE`. So without the drop, each SYN gets a RST, and slirp closes the host socket (EOF, read as `answered`). The probe therefore fails on an image that lost its drop.
- **Residual false pass (later).** If slirp's SYN never reached the guest, the result would also be `dropped`. `hostfwd` with no guest address aims at slirp's first DHCP address, 10.0.2.15. CI shows that the box holds exactly that lease, and the probe runs after the boot report. So this does not happen today, but nothing asserts it. A one-line `has "$W/console.log" "agentos-uplink: enp0s2 10.0.2.15/"` (or any interface with that address) would pin it.
- **No in-boot positive control.** I11 states this. The UKI command line is fixed, and masking `agentos-inbound` would take networkd down with it (`Requires=`), so a control would need a second build. The classifier control (unit test) and the drop-removed control (netns, every address) together are adequate for release.
- **IPv6 and link-local on the image.** These are not covered. QEMU's `hostfwd` aims at the IPv4 guest only. IPv6 and fe80 are covered in netns, where the control now runs at every target, but on the runner's networkd 255, not on trixie's 257. This stays as a narrowed later item, with a tap or bridge NIC as the route (I11's next step).
- **The real listener is not probed.** resolved's LLMNR on tcp/5355 is the image's only listener on the uplink, and it is not in the probed set. Every port meets the same final `drop`, so this is later: one more forward.
- The link-local target in the netns test fails loudly if no fe80 address is found (`next()` raises), so it cannot skip silently.
