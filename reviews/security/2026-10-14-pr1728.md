## Threat check

- **Who can plant a link.** Only a process that can write `/etc/agentos/tree`, which means guest root or the model-directed guest (ARC-7, REV-1). The `os.Root` still stops any escape out of the tree directory, so what is at stake is the invariant at tree.go:30: "treeNamespaces are the only directories a sync writes or removes in". #1630 exists to make that invariant hold.
- **Paths that cannot be abused.**
  - `..`, absolute paths and non-clean paths are refused at tree.go:152.
  - A hardlink is harmless, because every write is a write-aside followed by a rename, which replaces the link and never writes through it. `ReadFile` only compares content.
  - A symlink below a namespace that is not on a tree file's path is a non-directory entry for `fs.WalkDir`. The removal loop therefore unlinks the link itself and leaves its target alone, which I checked.
  - A bind mount is guest-root-only and is not a symlink. It is out of scope here, as ARC-7 already covers it.
- **Errors from `Lstat`.** `refuseLinks` returns nil on any `Lstat` error (tree.go:236-237). For ENOENT and ENOTDIR that is correct. For any other error, the `ReadFile`, `clearWay` and `MkdirAll` calls that follow hit the same error on the same path, so this does not fail open.
- **Permanent failure (denial of service).** A link on a tree path fails every 30 s poll, and each poll refetches the whole tree (up to 8 MiB) until the owner removes the link. Only the party that could delete the skills directly can plant such a link, and the ASSUMPTIONS row says so. I accept this as documented. Map order is random, so files ahead of the refused one may already be written. The version is then dropped, which TREE-undo-invalidate covers.
- **The mutant-equivalence claim.**
  - I ran `Lstat`->`Stat` at clearWay tree.go:257, at :265, and at both. All three survive.
  - They are equivalent only in the sequential model. With a concurrent writer they are not (see R1).
  - `refuseLinks` returning `continue` instead of nil on an `Lstat` error also survives, and it is equivalent.
  - These mutants were killed: removing the `refuseLinks` call, skipping the namespace component, skipping the file component, `Lstat`->`Stat` inside `refuseLinks`, and moving `refuseLinks` after the unchanged-content skip.
- **Race-freedom.** No test exercises a concurrent change, and the PR body does not claim race-freedom. However, the clearWay comment (tree.go:247-249) and the ASSUMPTIONS row state the refusal unconditionally (B2).

## Findings

1. **B1 (blocker): a namespace that is itself a symlink is followed by the removal walk whenever the tree has no file in that namespace. The sync then deletes every file under the link's target and succeeds.** tree.go:169-172 and :204-219.
   - **Mechanism.** `refuseLinks` runs only for paths in `files`. The removal loop calls `fs.WalkDir(root.FS(), ns, …)`, which `Stat`s, and so follows, the walk root. `root.Remove("context/…")` then resolves `context -> other` inside the root.
   - **Probe.**
     - Setup: `context -> other`, with files `other/a` and `other/sub/b`. The tree is `{skills/x}`.
     - Result: `syncOnce` returns `v1` with a nil error, and both `other/a` and `other/sub/b` are deleted.
     - The same happens with an empty tree (`Files: {}`) and `skills -> other`.
   - **Why it is a blocker.** It breaks the invariant at tree.go:30 that #1630 is meant to restore. It also contradicts the new ASSUMPTIONS row (L10), which says a symlink at "the namespace" is refused.
   - **Fix.** Before anything is written, `Lstat` each of `treeNamespaces` (whether or not the tree has a file there), refuse a symlink, and fail the sync. Add a test for "namespace link, no tree file in it" and one for "empty tree".
2. **B2 (blocker, wording on a tier-A path; this is the S-2 that #1630 folded in): the comment and the ASSUMPTIONS row overstate the guarantee.** tree.go:223-228 and :247-249, and ASSUMPTIONS.md:10.
   - **What they claim.**
     - "The caller has checked with refuseLinks that no symlink lies on p's path, so the Lstat and RemoveAll here act on the path they name."
     - The row says a symlink on the path "is refused before anything of that file is cleared or written".
   - **Why that is not true.** Both hold only if nothing changes the tree directory between the check and the act (R1). Once B1 is fixed, state that the check is not atomic against a concurrent writer in the guest. That writer can be guest root or the model-directed guest. Name R1's follow-up issue in the row.
3. **R1 (release; invariant tree.go:30, CHG-6 and ARC-7): there is a TOCTOU window between `refuseLinks` and the actions that follow it.** tree.go:170-197 and :250-267.
   - **Why the window exists.** `refuseLinks` `Lstat`s each component by name. `ReadFile`, `clearWay`'s `Lstat`/`Remove`/`RemoveAll`, `MkdirAll`, `OpenFile` and `Rename` all re-resolve the path from the root afterwards. `os.Root` follows a symlink that stays inside the root, so a link swapped in after the check still redirects the act. No call holds a directory fd that has been checked.
   - **Probe.**
     - Setup: a goroutine loops `renameat2(RENAME_EXCHANGE)` to swap the real directory `skills/d` with `skills/dl -> ../other`. The tree is `{skills/d/keep}`, and `other/keep/inner` exists.
     - Result: in 588 of 3000 runs, `clearWay`'s `RemoveAll` deleted `other/keep/inner`, which is outside the namespaces.
   - **Failure path.** A guest process that races the 30 s poll makes the bridge remove or write in a directory outside skills, procedures and context.
   - **Fix.** Walk with held fds:
     - `openat(O_DIRECTORY|O_NOFOLLOW)` from the root fd, one component at a time, from the namespace down to the parent of p;
     - then `fstatat(AT_SYMLINK_NOFOLLOW)`, `unlinkat`, `mkdirat`, `openat(O_CREAT|O_EXCL|O_NOFOLLOW)` and `renameat` relative to that parent fd;
     - and a recursive removal that never follows a link.

     Add a race test using RENAME_EXCHANGE, like the probe above.
   - **Why release.** Exploiting it needs a concurrent writer with guest root, who could already delete those files directly. The full fix is a redesign of how `mirror` touches the filesystem. It is not a blocker on the cited IDs, provided B2 states the window honestly.
