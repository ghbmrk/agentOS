Threat model. The assets are:
- the setup vault, which holds the step-3 seed (the owner's lasting code generator, carried into the card's vault)
- the owner's card vault

The adversaries are:
- a root or disk reader
- a crash at any point
- the unlock-socket peer
- a seller who has the box before the claim
- a writer of the state file

| Path | Stop | How |
|---|---|---|
| The setup key opens the card's vault | structural | Fresh data key and keys file (K21). The key is dropped at provision. A key put back opens nothing (tested) |
| Open or remake after seal | structural | The `sealed` latch is checked first. A seal entry found without the mark writes the mark. The key is dropped (tested) |
| Remake on an owned or legacy box | structural | Needs `setup:true` (only `init -setup` writes it) and `!sealed`. A missing state fails closed (tested) |
| Crash after the swap, before the key drop | structural | The next start gets ErrNoSlotOpens and drops the key (probe) |
| Real stop between provision's renames | structural, untested | Probe: "cannot decrypt", so the key stays and the vault stays locked. ResetUnlatched's reset remakes it (`provisioned`). L1 |
| Remake atomicity | structural | Keys are renamed last. Any crash leaves no keys file, so the next start remakes |
| Key at rest | partial | 0600 in a 0700 directory, via durable temp-and-rename, generated on the box. Remanence is L4 |
| State-file writer | residual (#1200 L1 class) | Named in K22 |

R1 from #1199 is closed, with tests. The case of a stop between the renames is covered only by a probe (L1).

## Findings

- **R1 (release, tier A).** After a remake, card 2 provisions over a seed nobody was shown.
  - Setup's record still says Enrolled, and the return to step 3 happens only at finish.
  - A restart between card 2's latch and finish leaves the card's vault locked with no usable code. The probe shows the old phone's code is refused, and ResetUnlatched does not run once latched. The box needs a reinstall.
  - Fix: provision refuses without `owner-totp-confirmed`, and/or #1115 routes to step 3 on `remade:true`. Add a test.
- **R2 (release, tier A; HW-10, K5).** Nothing binds when `init -setup` or the remake runs.
  - If it runs before the claim, a secret exists before the claim.
  - The open setup vault takes `/credential` and `/mail` writes, and provision copies every entry.
  - Fix: K22 states that the setup vault is made only after the claim. The wiring row carries it, and the K5 scan covers `setup.key`.
- **L1 (later, tier A).** Test the real stop-between-renames state. The remake should also remove `durable` temporaries and `keys.next`.
- **L2 (later, tier A).** A failed keys rename while running leaves the vault locked until a restart.
- **L3 (later, tier A).** #1200 L2 is now reached with no owner, because `startSetup` opens the setup vault automatically. Remove `*.card` in `openSetupLocked`.
- **L4 (later, tier A).** Remanence of `setup.key` and the old setup vault leaves the step-3 seed recoverable. `rk.Text()` strings are not wiped. Name this in K22, and consider a TPM-sealed setup key.
