Reviewed at head `05b44e1eafcbd6c26560ecd9ef50170736afc9fc`. PR: GVISOR-stale-kill, closes #1443, tier A.

### Is "reliability, not isolation" the right class? Yes
- **Another machine's sandbox:** not reachable. The stale kill names `cid(id)` = `id + "_"` under the broker's `--root`. The `_` stops runsc's prefix match, so `wk-1_` cannot resolve to `wk-10_`. A Destroy followed by a Create that reuses the ID still goes through `stopRuntime` → `Runtime.Kill`, so that case is waited on too.
- **The host, or a PID outside the sandbox:** not reachable. `runsc kill --pid` sends the signal through the sandbox's own control server, and the sentry resolves the PID inside the container's own PID namespace. The PID comes from `--internal-pid-file`, which runsc writes into a `CreateTemp` file in `StateDir` (0600, owned by the broker), so the guest cannot change it. The PID is passed as argv and never through a shell.
- **Worst case before the fix:** SIGKILL to a process in the *same* machine's next incarnation that happens to have the same in-sandbox PID.

### What happens when the 5 s limit expires?
The 5 s is the timeout on `killExec`'s own context, not a limit on Kill's wait. When it expires, `childproc` SIGKILLs the `runsc kill` process, and `Cmd.Wait` reaps it and its stderr copy before `wg.Done` runs. So when `waitPendingKills` returns, no runsc kill process is left in this broker. An RPC that was already sent went to the **old** sandbox's control socket, and that sandbox is then killed by Kill's own `kill`/`delete`. A stale kill cannot land in the new sandbox once the wait returns, so Rollback/Rebuild do not need to refuse to start.

**Ordering.** `OnCancel` runs from `exec.Cmd.Cancel`, which `os/exec` finishes before `Wait` returns. So `addPendingKill` happens before `gvisor.Exec` returns. `Manager.Exec` holds `mc.mu` until then, and `gvisor.Exec` returns within `ExecWaitDelay`, well inside `ExecGrace` (15 s). Every restart path (`restartHeld`, `Fork`'s cleanup, `load`, `Destroy`, `preemptLocked`, `launch`'s failure path) calls `Runtime.Kill` under `mc.mu` before Start or Restore. Preempt's unlocked `m.kill` can take the group before a late `OnCancel` registers. That kill then joins a fresh group, and `preemptLocked`'s `stopRuntime` waits on that group under the lock. This is covered.

### Races and deadlocks
I found none. The group is removed from the map under `pendingMu` before `Wait`, so no `Add` can race a `Wait` on the same group. `killExec` takes no lock that Kill or the Manager holds. `go test -race` passes.

### Findings
- **Blocker:** none.
- **Release:** none.
- **Later (reliability, not security):**
  - **L1.** `waitPendingKills` ignores Kill's `ctx`. It is bounded only by `killExec`'s 5 s timeout plus the reap. A `runsc kill` stuck in D-state would hang Kill under `mc.mu`. Suggestion: wait with the ctx and fail closed (return an error so the machine stays Running and no restart happens).
  - **L2.** No test runs a cancelled Exec concurrently with Kill (mutant M6 survives).
  - **L3.** V37 does not state that it relies on (a) Cancel finishing before Wait returns and (b) ExecWaitDelay < ExecGrace. It also does not mention that an orphaned `runsc kill` from a crashed broker is outside this guarantee, since there is no Pdeathsig. That orphan can still only reach the same machine ID.
