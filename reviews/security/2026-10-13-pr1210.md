Threat model. The assets are:
- the owner's card vault and the step-3 seed it carries
- the HW-10 promise that no secret exists before the claim

The adversaries are:
- a crash or restart at any point in setup
- a seller or someone else holding the box before the claim
- a root or disk writer

| Path | Stop | How |
|---|---|---|
| Card 2 provisions over a remade vault's unconfirmed seed (R1) | structural | Provision needs `owner-totp-confirmed` and no `owner-totp-pending`, as `sealEnroll` does. A 412 writes nothing (tested) |
| The confirmed mark survives the remake | structural | The remake deletes the vault files and `sealNew` writes only the seed and setup-open, so no mark exists on disk |
| Re-enroll after a confirmation | structural | `enroll` deletes the mark (tested) |
| Restart after the refusal | structural | The remade vault opens with its setup key. Card 2 does not open it (tested) |
| ResetUnlatched loop | structural | A vault no card made is kept, so the reset loses nothing |
| Setup vault made before the claim (R2) | structural | `init -setup` asks the read-only `claim.Claimed` before drawing or writing anything. No state, an unreadable state, or an unclaimed state is refused (tested) |
| Remake before the claim | structural | Needs `setup:true`, which only `init -setup` writes |
| Spoofed claim | residual | Needs a write to the root-owned `claim.json` (the #1200 L1 root-writer class). A seller who preloads `claimed:true` defeats the claim gate itself, outside this PR |
| Boxes upgraded mid-setup | n/a | No image unit runs `init -setup` yet, so no field box has a setup vault made before the claim |
| G1 preloaded path (D-105) | ok | The seller seals `claim.json` at `claim.StatePath`, the sticker claim flips it, then `init -setup` succeeds (tested with real Seal and Try) |
| Download path (#1209) | fail-closed | Refused. It is after G1 under D-105 |
