Can a forget report done while the task survives, can an owed done text be lost without a double fault, can a link or rename trick widen a file or write elsewhere, and does any file or log gain task words?

## Facts

- [Fact] **Crash ordering, S1.** `openOwedFile` (learn.go) removes a stale `.bad`, hard-links the unreadable file to `forget-owed.json.bad`, saves the fresh `!lost` file over the path through `FileStore.Save` (write, fsync, rename, directory fsync), then logs. A crash before the remove, between remove and link, or between link and the save's rename leaves the bad file at the path, so the next start repeats the sequence and the owner is still owed `forgetOwedLost`. After the rename the path holds the fresh file. The link is not fsynced on its own, but the save's directory fsync of the same directory covers it, and a lost link only loses the aside, never the notice. If the save fails, the notice stays owed in memory and the bad file stays in place for the next start.
- [Fact] **Crash ordering, S2.** `retry` re-owes before each `forget` until a save holds; the shutdown branch returns before it, as before. The remaining losses (every owed save failing up to the pass where the forget holds, or in `Execute` with an immediate success, then a crash before the send) need a failing disk plus a crash and are stated in ASSUMPTIONS F11, including that `forgetNotSaved` may have been said.
- [Fact] **Done while data survives.** The diff does not touch `forget`, the tombstone, the replay, or when "Forgotten." is said: the done text still follows only a nil `forget` (or, at start, a tombstone plus a successful replay). The re-owe only adds an owed entry; it cannot make a forget report done.
- [Fact] **Links and renames.** `.bad` is a hard link (same inode), so it cannot get a wider mode than the file it keeps; the test pins 0600. Go's `os.Link` (linkat, no follow flag) links a planted symlink as a symlink, and `os.Remove` of a planted `.bad` symlink removes the link, not its target. The save renames over the path, so it never writes through a hard link or symlink at the path to another file. Planting anything needs the daemon's uid on the learn dir, so the diff adds no reach.
- [Fact] **Personal data.** The owed file's format is unchanged (goal IDs, times, counts, two flags). The new log lines carry a remove/link error with the learn-dir path and the existing load error. A JSON or time-parse error can quote bytes of the owed file, as before #528; that file holds no task words. No log line carries a goal ID.
- [Fact] **Locks.** The only lock the new code takes is `forgetOwed.mu`, a leaf lock (held across `store.Save` only, which takes none). `retry` calls `owe` with nothing else held. `openOwedFile` runs in `openLearning` before `forgetOwner` is shared. No path in the diff reaches `broker/owner`'s LocalSignIn lock (#444) or `localsrv`'s routes (#522), so there is no new ordering against them.
- [Fact] **Race and vet.** `go vet ./cmd/agentosd/` clean; `go test -race -count=1 ./cmd/agentosd/ ./change/` pass; `go test -race -count=5 -run 'Owed|Forget|Unreadable' ./cmd/agentosd/` pass (go1.26.8).
