## Threat check

Adversaries: a person on the box's Wi-Fi during setup without the paired phone or the card; a holder of the card's setup secret; a local process on the verify socket; an attacker with offline write access to the drive's setup record.

1. **TOTP secret handling.** No change to how the seed is made or held: 20 bytes from `crypto/rand`, stored in the vault as `KindTOTPSeed`, leaving only as the `otpauth://` link to the setup page (length and prefix checked in `localsrv`). The new errors (`errNotOpen`, `ErrEnrollNotOpen`, `EnrollNotOpen`, `ErrEnrollUnavailable`, `ErrCodesUnavailable`, `cannotFinish`) are fixed strings with no seed, link or code in them. Structural.
2. **Enroll order (clear after the vault answers).** The vault stays the gate at the seal. `enroll` in the vault writes the pending seed before it deletes the confirmation mark; `sealEnroll` refuses while a pending seed exists or the mark is missing. So a crash, or a failed `setEnrolled(false)` save, after the vault made a new seed leaves `rec.Enrolled` true over a pending seed: `finish` gets 409, maps it to `EnrollNone`, clears the record and refuses. A refused enroll replaced nothing in the vault, so keeping the earlier confirmation is sound. Structural.
3. **Restart after a seal whose finish record was lost.** The intended recovery (test 3) lets a restarted pairing finish against the generator confirmed before the restart, which the localui `gen` counter otherwise prevents for an open vault. Only the paired phone or the card's setup secret (rate-limited, constant-time compare) can restart, and in the open-vault case that same person would enroll a generator of their own; here they get the owner number without the codes, so strictly less. It needs a crash between the seal and the record write. Accepted; no finding. The codes page tells the owner to replace a lost generator with the recovery key.
4. **Wrong-kind `owner-totp-enrolled` entry** (drive tampering). Before: 410 at the seal, which `finish` accepted with a recorded confirmation. After: 412, so enroll and finish both answer `enrollment unavailable`. Fail-closed; a hardening.
5. **Replay.** Unchanged: `confirmEnroll` uses `owner.MatchTOTP` with the stored `LastStep`, so a code's step is accepted once. The new `closedLocked` check runs before any code is compared.
6. **Timing.** The 412 vs 410 split depends only on which marks the vault holds, not on any secret or code; it answers over the verify socket with the same peer-uid check. The code comparison path is not touched by this diff. The restart secret check stays `subtle.ConstantTimeCompare`.
7. **Information to the setup page.** The page learns only "cannot finish here", with no Continue, key or "already set up". Nothing the adversary on the Wi-Fi can use beyond what setup already shows.
