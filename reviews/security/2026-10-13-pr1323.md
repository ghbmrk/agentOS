### Threat model

Asset:
- The committed rotation's `RotationResult`: notes, plus `Enrollment`, which is the new code generator's otpauth seed.

Adversaries:
- another signed-in session (another phone, or a lost phone whose session is still live; see #1173);
- a device on the AP with no session;
- a replayed or stale request;
- a commit whose answer arrives late;
- a concurrent request.

### Paths

| Path | Stop | How |
|---|---|---|
| A second signed-in session GETs `/rotate/done` after the confirmer skipped it (#1316's path) | structural | `takeResult` returns the result only when `tokenKey(cookieToken)` equals `resOwner`. A non-owner gets nil and the result stays for the owner. Tested by `TestRotationResultIsTheConfirmingSessions`. The mutant that drops the owner check is killed. |
| No session, or a well-formed token that is not signed in | structural | `Mount` applies `signedIn` (an agentosd `OpSession` check) before `rotatePages`. Probe: a fabricated 64-hex cookie redirects to `/unlock`, and so does the confirmer's own token after `/signout`. |
| The binding comes from client-chosen state | no | The binding is the SHA-256 of the same cookie that the display's `paired` check (`isSignedIn`) validated on that same request. `ConfirmAnswers`, and so `provision`, runs only after that check. |
| A replayed confirm POST (from another session or the same one) | structural | After a successful confirm the display is erased (`eraseLocked`) and every later request gets 410 (`ErrDisplayGone`). Nothing is committed again and no result is rebound. Probe: a replay from session B gives 410, B's `/rotate/done` gives 303, and the vault records 1 commit. |
| A stale tab or a late visit | structural | The result is served once (`takeResult` nils it), and every page is `no-store` (`ServeHTTP`). Expiry is checked on each fetch against `resUntil`, which is the vault's `Expires` capped at start+30 min. A zero `resUntil` reads as expired, so it fails closed. |
| A late commit answer after enroll, show or Start | structural | `provision` snapshots `gen` before `CommitRotation` and stores only if `gen` is unchanged. `void` bumps it. Start's lock order is void, then `old.Discard()`, and `Discard` waits on the display lock that is held across `provision`. So a commit in flight across a Start always sees the bump. Tested by `TestRotationLateCommitAnswerStoresNoResult`. The gen mutant is killed. |
| A commit with no confirming session | fails closed | `confirmer == ""` stores nothing. Even without that check, `takeResult` refuses an empty owner, because `tok == ""` returns and a non-empty token never hashes to `""`. The redundant mutant survives, and that is expected. |
| Races between confirm and fetch | holds | `confirmer` is written only under `postMu`. `provision` reads it on the same goroutine, inside `serveCard`'s `h.ServeHTTP`. It is the only production caller of `ConfirmAnswers`; `Display.Confirm` has no non-test caller. The lock order is postMu, then the display lock, then mu, and no path acquires them in reverse: Start takes mu and drops it before `Discard`. Probe: 20 rounds of 4 concurrent confirms by A, `/rotate/done` from both A and B, and B's `/rotate/show`, under `-race`. B never got the result, A got it at most once, and the race detector was clean. |
| Secret material in logs or replies | unchanged | No log line or journal event is added. The result is rendered only into the owner's `no-store` page. `Enrollment` is a Go string and cannot be wiped (the C13 carry). Expiry is lazy, so an expired, unfetched result stays referenced in the page process until the next `/rotate/done`, enroll, show or Start, though it is never served. This is memory-only and inside the C13 bound, so it is not a finding. |

### Findings

- **S1 (should, release; REC-4, HW-1; tier A).** The waiting display, and so the confirm and the seed, are still open to any signed-in session, and L45 attributes this residual to #1173, which does not track it. Details:
  - L37 makes "signed in" the display's paired check.
  - Probe at this head: session B, which did not start the rotation, GETs `/rotate/card` and gets 200 with the new recovery key shown. B then posts the asked group, gets 303 to `/rotate/done`, and receives the otpauth seed. The starter A gets 303 to `/home`.
  - So #1316's failure path ("a second session reads the live TOTP seed") is closed after the commit but still open before it. The same exposure also shows the new passphrase and recovery key, which is worse than the seed.
  - #1173 is "end agentosd sessions after the code generator is replaced". That is related, because a lost phone's live session is the likely adversary, but it is a different fix, and no issue tracks the display binding.
  - Fix: at Start, record the starting session's `tokenKey`. The starter is the session that gave the tier-4 proof. `serveCard` then serves the display (GET and POST) only to that session; others are sent home. The result then follows automatically. Also correct L45 and the PR text so they cite the new issue, not #1173.
  - This is pre-existing and not a regression, so it is not a blocker on this PR.
  - UX cost: the owner confirms on the phone that started, which is today's flow. Potency cost: none.
- **S2 (should, release; REC-4; tier A).** Two guards that L45 claims are not pinned by any test. Both mutants pass `TestRotation*`:
  - removing `voidLocked()` from `Start`;
  - removing the `resultTTL` cap when the vault's `Expires` is later than start+30 min.
  - Neither is exploitable today. Without Start's void, a result is still the confirmer's alone and still expires. But these are the release's stated bounds.
  - Fix: one test of a vault `Expires` at start+2h with a fetch at start+30m+1s, and one test of commit, then a new Start, then the confirmer's `/rotate/done` giving 303.
  - UX cost: none. Potency cost: none.

### Not findings (noted)

- A HEAD or POST to `/rotate/done` from the confirmer's own session consumes the result (probe: HEAD 200, then GET 303). This was already so before the PR. It is availability only, and `/rotate/show` with the recovery key gets the seed back.
- Any signed-in session's post to `/rotate/enroll` or `/rotate/show` voids the confirmer's unfetched result, even a post with a wrong code. This is availability only, it fails closed, and it has the same recovery as above.
- `resOwner != tokenKey(tok)` is not a constant-time comparison. It compares SHA-256 digests of a high-entropy token, so the timing reveals nothing usable.
