## What changes for an attacker
Before it stores a pasted key, the vault process sends one outbound request that carries the key. `custody.setupKey` first validates under `c.mu`: setup is open, the provider is a built-in adapter, the key is 1 to 512 printable non-space bytes, and the credential name holds no other kind. It then calls `Adapter.CheckKey` without the lock, within `SetupKeyCheckWait` (8 s). `CheckKey` sends one `GET https://<adapter Host><KeyCheck.Path>` with the key injected as the relay injects it. It sends this through `egress.DefaultTransport(c.guard)` (netguard, E12) as a bare `RoundTrip`. Only a 2xx answer goes on to the store. That store re-checks the setup guard and, in `putKeyLocked`, the kind.

| Path | Stop | How |
|---|---|---|
| Key to a host the caller picks (SSRF, exfiltration) | structural | The host comes from the built-in adapter (`builtinAdapter`, `api.openai.com` and `api.anthropic.com`). The path is a literal validated in `Adapter.validate` (no `{}`, `..` or query). The provider string from the page only selects an adapter, and an unknown one answers 400 before any send. Nothing on the request path takes a URL, host or header from the page. |
| Provider name resolving into the home network (DEV-2) | structural today, by review | The production branch (`keyCheck == nil`) dials through `c.guard`, the process's netguard policy built in `main.go`. The check sets no model-call purpose, so it gets the stricter default. Neither a test nor `tools/netguardcheck.py` pins this. The check is per file, and `providers.go` imports netguard for the nil fallback. See S1. |
| Redirect carrying the key elsewhere | structural today, by review | `rt.RoundTrip` follows nothing, and a 3xx answers `key unchecked`. An `http.Client` would follow redirects and forward Anthropic's `X-Api-Key` across hosts. That mutation passes every test (S1). |
| Header injection through the key | structural | Bytes are checked as printable with no space before the send (mutation M4 killed). Go's `http` also refuses CR and LF. `KeyCheck.Headers` cannot name the injection header, a forbidden header or `Accept-Encoding`. |
| Key in logs, errors or answers | none found | `CheckKey` returns two fixed sentinels and discards the transport error and the response body. The egress 403 and 502 bodies are fixed text. modelroute maps them to sentinels, agentosd and localsrv to fixed codes, and localui `keyErrText` to fixed page texts. No log line was added. netguard's `OnDeny` logs the address, port and purpose, never the request. Tests assert that the canary key is absent from every answer. |
| Key kept after a failure | none | A refused or unchecked key writes nothing (tested for 401, 403, 429, 500 and a transport error). localsrv keeps nothing. localui stores only the fixed text in `u.err`. |
| Hang | bounded | An 8 s context covers the dial, TLS, headers and the body drain (at most 64 KiB). The verifier client waits 10 s, the page's `ConnectAPIKey` waits 15 s, and localui's `WriteTimeout` is 120 s. The deadline is asserted (M6 killed). No lock is held across the check, in egress (tested by locking mid-check, which stores nothing) or in localui (`u.mu` is released around `f`). |
| Validity oracle | accepted | The page tells "refused" (401 or 403) from "unchecked". Only the controlling phone's cookie reaches `/setup/ai-key`, only while setup is open. The calls share localsrv's 10-per-minute limiter, which counts before the vault call. The limit counts failures, so the box sends at most 10 checks a minute. The provider's own API is the same oracle with no limit, so the box adds no capability. After the seal, the pre-check refuses before any send (M1 killed). |
| Abuse as an outbound request generator | bounded | At most 10 a minute, only to the two pinned provider hosts, only during setup. Each check uses a new transport, whose idle connections are closed. |
| Concurrency with other setup ops | structural | Validation, then the check, then a re-check of `setupOpen` and the kind under `c.mu`. A lock during the check stores nothing (M2 killed). A card provision during the check stores into the current vault only if setup is still open there, which is the owner's intent. Two keys checked at once each pass the check, and the last one wins. |
| Key sent to the wrong provider | accepted | When the owner picks the wrong provider, the key goes to that provider's host. Before this PR it went there on the first model call, so nothing new is exposed. |

## Findings
- **S1 (release; CRED-1, DEV-2)**: the key-check transport's guard and its no-redirect property are pinned by no test or check. Failure path: a later edit replaces `egress.DefaultTransport(g)` in `setupKey` (M5), or sends `CheckKey` through an `http.Client` (M7), and CI stays green. A provider name that rebinds into the home network then receives the owner's key, or a provider-side redirect forwards Anthropic's `X-Api-Key` to another host. Fix: two tests. (a) `cmd/agentos-egress`: with `keyCheck` nil and `c.guard` set to a netguard policy whose resolver maps the provider host to a home or loopback address, the call answers 502, nothing is stored, and no connection is made. (b) `egress`: a 307 answer with `Location` pointing to another host makes exactly one request and answers `ErrKeyUnchecked`.

Notes for the other lenses (not Security findings):
- An attempt that waits more than 2 s on `c.mu` (for example behind a card provision) can store the key after agentosd's 10 s wait has ended. The page then says "Could not save the key" while the key is stored. A retry is idempotent, and there is no security impact.
- The OpenAI restricted-key case is already raised as Potency P2.
