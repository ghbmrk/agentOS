## Findings

1. **blocker (DEP-2b, defect): a scenario clears the read-only flag on a kept path with `mount_setattr(2)`, which is not traced, and the run ends `pass`.** The scenario keeps CAP_SYS_ADMIN over its mount namespace in both modes. As root that is real root. Under `-r` it is root of the user namespace that owns the mount namespace. The `ro` flag is set inside that namespace by `_inner`, so the kernel has not locked it. `mount_setattr(AT_FDCWD, ROOT, 0, {attr_clr = MOUNT_ATTR_RDONLY})` succeeds. `_MOUNTS` lists `mount`, `umount2`, `open_tree`, `move_mount`, `fsopen`, `fsmount` and `pivot_root`, but not `mount_setattr`, so the trace is empty.
   - Reproduced through `run_target`: a target that runs this and then appends to `ROOT/tools/depaudit.py` ends `{'outcome': 'pass', 'violations': [], 'exit': 0}`, and the append is on the host file afterwards. That is the attack the brief names: rewriting `tools/depaudit.py` before the rerun executes `_inner` from it.
   - The same works under `unshare -r -n -m --pid` (standalone probe).
   - On kernels ≥ 6.15, `open_tree_attr(2)` with `OPEN_TREE_CLONE` and `attr_clr = RDONLY` gives a writable detached mount without `move_mount`. Reproduced: a file is created under ROOT and the run ends `pass`. strace 6.8 does not know that name, so adding `?open_tree_attr` to `TRACED` would be skipped silently.
   - D8's "a remount that drops `ro` is refused by the kernel (locked mount flags)" is therefore wrong for the scenario. `mount(2)` with `MS_REMOUNT` is only caught because it is traced.
   - **Fix (recommended):** drop CAP_SYS_ADMIN from the scenario, for example `setpriv --bounding-set -sys_admin --inh-caps -sys_admin` (or a capability drop in a wrapper strace execs) between strace and the command. This closes the whole mount-API family, including syscalls this strace cannot name. The drop was checked with the same probe in both modes: `mount_setattr` returns EPERM and the write gets EROFS.
   - **Fix (alternative):** trace `mount_setattr`, `open_tree_attr`, `fspick` and `fsconfig` without the `?` prefix, and fail closed when strace does not know one of them.
   - Either way, add a planted control (DEP-2b) that calls `mount_setattr` on ROOT and then tries to write. It must end with no write: EPERM or EROFS, or a `mount` violation. Correct D8 to match.
2. **release (A9, harness completeness; new BOARD row or folded into DEP-4): `?`-prefixed `TRACED` names fail open.** strace skips a name it does not know, so on an older strace a link or mount call is untraced with no warning. `sandbox_available()` should fail if the installed strace rejects any `TRACED` name without the `?`, or each traced family needs a planted control. This predates DEP-2.
3. **release (DEP-3, scope note for its brief): erasure by append, not only by drain.** Through `/proc/1/fd/<trace_w>`, which is the D9 channel, a tracee can also open the trace pipe's *write* end. It can then write a partial line with no newline just before a connect. `_LINE` is anchored (`^(?:(\d+)\s+)?(\w+)\(`), so the next strace line, `x123 connect(…`, no longer parses, and the connect is lost without draining anything. This was inferred and not reproduced. DEP-3's planted control should cover both write-end injection and drain. Uid separation as DEP-3 proposes closes both.
4. Concur with the PR's own classes: DEP-3 (D9) **release**, DEP-4 (D10) **release**, `DEP-2-join` **later**. Each is stated accurately in ASSUMPTIONS, BOARD and LATER.

## Threat check

Adversary: the traced scenario, i.e. unreviewed dependency code, running as `_inner`'s uid with full capabilities in its namespaces. Its goals are (a) to turn a connect into `pass`, and (b) to persist state or rewrite the harness between attempts or targets.

- **Trust boundaries.**
  - tracee → `_inner` evidence channels (trace pipe, stderr pipe, result stdout).
  - tracee → kept paths on the host filesystem.
  - tracee → `_inner` process (PID 1 of the namespace).
- **Evidence channels, inherited fds.**
  - [Fact] The trace pipe is not inherited. strace opens it through `/proc/<pid>/fd/N`, `Popen` uses `close_fds`, and strace's output file is close-on-exec.
  - [Fact] The result leaves on `os.dup(1)`, which is non-inheritable, while `_inner`'s fd 1 is /dev/null. `_result` accepts exactly one JSON object line with all `_RESULT_KEYS`. A forged extra line, or a partial prefix merged into `_inner`'s line, gives `error`. Both fail closed.
  - [Fact] The shared stderr pipe can only be appended to. `STRACE_FAULT` uses `search`, which is unanchored, so a partial line written before strace's message cannot hide a fault. D3's text says `^strace:`, but the code is stricter than the text.
  - [Fact] The `tamper-evidence` control rewrites all three old file names after a connect and ends `violation`.
- **Evidence channels, `/proc/1/fd` and ptrace.**
  - [Fact] These are open and stated as D9 / DEP-3 (release). Point 3 above adds the write-end variant.
  - Killing `_inner` from inside the namespace is ignored for init. Forging a result line without stopping `_inner` gives two lines, which is `error`.
- **Kept paths (DEP-2b).**
  - Plain writes get EROFS (`control-kept-read-only`).
  - A traced `mount`/`umount2` remount or unmount becomes a `mount` violation.
  - `mount_setattr` and `open_tree_attr` bypass silently: **point 1, fail-open**.
  - `--rbind` submounts are D10 / DEP-4.
  - `writes` cannot come from the product registry: `load_registry` rejects any key outside `name`, `cmd`, `expect`, `note`.
  - The parent-before-child order holds under `sorted()`, because `-` sorts before `/`.
- **Fail-open paths.**
  - Point 1 (silent bypass of read-only).
  - Point 2 (unknown traced names).
  - D9 (drain, ptrace).
  - The `join(10)` snapshot without `is_alive()` is `DEP-2-join`, later. strace has exited by then, and an injected writer is the D9 channel.
  - Every other malformed path ends `error`.
- **Credentials and data exposure.**
  - The result now carries the full trace and stderr text over the sandbox's stdout. They stay in memory and are not added to the report, which keeps `events`, `logged` and `violations` as before. The `detail` stderr tail on `error` is unchanged.
  - No credentials, tokens or personal data appear in code, tests or fixtures. The controls use documentation addresses (192.0.2.10) and loopback.
  - The scenario still inherits the harness's environment. That is unchanged by this PR and out of the cited IDs.
