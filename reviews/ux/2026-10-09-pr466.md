Tier A, UX lens only; Security is stage 4a. Reviewed from `git diff origin/main...pr466` against the brief (Security S2, S3, S4 on #391) and its IDs RES-4, CAP-8. The owner sees nothing new. The guest, the user of `worker_exec`, reaches this code through `broker/guest/mcp.go:146` → `workers` `toolExec` → `vm.ExecResult` (exit code, stdout, stderr, truncated), or through `guesterr.Filter` for the two Exec sentinels.

- The PR adds and changes no guest-facing text; the sentinel texts in `broker/workers/guesterr.go` are unchanged.
- It removes a false text from a reachable path. Before, a guest command that wrote `panic: …` plus a goroutine header and exited 2 (any Go program's own panic) was told "the runtime failed after the command started, so it may have run…", which was untrue, and lost its output. Now it gets its own exit code and output (`TestGuestPanicTextIsAResult`). That is the CH-12 recurring kind fixed, not added.
- runsc's text, which names host paths, can no longer reach the guest's stderr in any interleaving, so the guest never reads text it cannot act on.

Points:
1. **later (CAP-8, result truthfulness)**: when the guest's stderr pipe is still held open `ExecWaitDelay` after runsc exits (something left in the sandbox writing to fd 2 only), the read deadline cuts the stream and the result comes back with `truncated: false`. The guest then reads a partial stderr as complete. Stdout in the same situation surfaces os/exec's `ErrWaitDelay`. Set `Truncated` (or an equivalent flag) when the stderr copy ends on the deadline, alongside LATER SR2-3n f1's test.
