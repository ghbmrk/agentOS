# UX, PR #430 (SR3-6, invalidate verified updates when attestation policy narrows)

Record: PR #430 · package SR3-6 · head 84c9efcf112e7d41086bac7d01a328905a32b230

Verdict: accept

Tier A, UX lens only; Security is stage 4a (signed). Reviewed from `git diff origin/main...pr430` (update, apply, change, ASSUMPTIONS U16, A9, C25), UPD-8, CHG-3 and the L3 and Security comments. Question: when a queued security update loses its automatic path, what does the owner see?

- The common case is quiet: a release scheduled under a policy that has since changed is dropped from pending, and Loop 3's next check schedules it again. If it no longer qualifies as a security fix, it takes the owner's path (C25), a normal CHG-3 approval. The owner changed the attestor list (or the interim rule ended), so one ask for the next release is expected.

Points:
1. **release (CH-12, UPD-1; same fix as L3 point 3 and Security S2 on #434)**: when `Tick` or `Execute` drops a release for `ErrPolicyMoved`, the pipeline adoption stays `Staged` and the digest keeps saying "Staged update v; it starts at the next restart" for a release that will not start. On #434 the same staged adoption also makes owner UNDO answer "starts at the next restart; undo it after", a step that cannot work. One fix covers both: whenever the applier drops, abandons or supersedes a release, settle its staged adoption (`StageFailed` with a reason other than fallback, or a new `Dropped` outcome), so the digest and UNDO stop naming a restart that will not run it. Put it on the BOARD row L3 point 3 asks for, coordinated with W5b and SR3-4.
2. **later (CHG-3)**: when a release that was going to auto-stage as a security fix is re-proposed on the owner's path, the ask does not say why it now needs approval. Rare (it follows an attestor-list change the owner made or the interim rule ending), so one line in LATER: the ask text names "attestor list changed since it was checked" when that is the cause.
