# UX: PR #1175 (CTRL-card-rot-wire)

Record: PR #1175 · package CTRL-card-rot-wire · head d8dae194e7e552c10d02d7dfbb5d71145b18b8a9

Verdict: accept

This is the tier A lens screen, UX pass. The new owner-facing surface is:
- `/rotate/`: the form for the parts to replace and the proof;
- `/rotate/card`: the existing rotation display;
- `/rotate/done`: the notes and the new code generator's QR, shown once;
- `/rotate/enroll` and `/rotate/show`;
- the refusal texts on the form, taken from the vault process's fixed `uerr` messages.

The flow fits REC-4. The owner sees one form in plain words ("I make new values for the parts you choose … Nothing changes until you confirm the new card."), then the display, then a confirm. The display's own texts (C17) are unchanged. Refusals are first person, give the reason, and name a step: "I keep no Owner Card…" until #1114, "too many wrong codes; show the code again with the recovery key".

- **U-R1 (release; REC-4 and the recurring kind "a problem text names a step that cannot work", CH-12).** The done page says the code generator "is shown once; your recovery key shows it again". But the only form that shows it again (`POST /rotate/show`) is on the done page, and the done page shows its result only once (`takeResult`). `/rotate/` and `/home` offer no such form.
  - Why it matters. `recovery.Commit` replaces the seed at commit, so the old code generator has already stopped working.
  - Failure path. After a recovery-key rotation the owner reloads or leaves the done page before scanning, or the commit's reply is lost or answers 409 (the in-effect path, which never reaches the done page). The page then offers no way to show the new generator. The owner has no working code generator until they run another recovery-key rotation with the recovery key.
  - Fix. While `recovery.EnrollmentPending` holds, `/rotate/` (or home) shows "Show the new code generator" with the recovery-key form. That needs a status op on the unlock socket.
- **U-l1 (later).** After an unknown commit outcome (no reply, or a 5xx), the display shows the in-effect text "Part of your new card is already in effect…" as fact, when it only may be. The step it gives (keep both cards, start a new card now) is right for both cases. Word it as "may already be in effect" if the display gets a third outcome text.
- **U-l2 (later).** The page never says when the new card stops waiting (30 min, `PendingTTL`). `RotationStarted.Expires` is parsed but not used. A line like "Confirm within 30 minutes" on the display would save a 410 and a restart.

Considered, not proposed: one field for "code or recovery key". The two labelled fields with "Or, instead of a code" are clear enough.
