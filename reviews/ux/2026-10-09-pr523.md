Points:
1. **release (builder's item, confirmed; LOOP-9 "owner notified per severity")**: a resolved finding does not reach the owner. `Guard.Resolve` sends text only when `rec.Contained == "paused" && rec.Texted`. Loop 7 calls `Report` with no `Contain`, so nothing is ever paused, and the owner is told nothing on resolve. The owner gets a High text ("… crashes on my current setup"), then STATUS drops the wait line and the digest never mentions it, so the alert is never closed. LOOP-9 asks for notice per severity at report time, so this is not a blocker. The row should send one "Cleared: …" text for any finding the owner was texted about, paused or not, and keep the pause sentence for the paused case.
2. **release (owner wording; fold into the wiring row)**: `findingText` gives "Fuzz test sockets.FuzzRequest crashes on my current setup. I take the fix when an update has it." and "Socket probe socket.vm1 fails on my current setup. …". The name is a Go identifier, so the owner cannot tell what is affected. The text says nothing about whether anything is paused or at risk, or that no action is needed. The finding is High, so `Notify` is urgent (`urgent || Check != CheckExpiry`), which interrupts the owner for a finding with no pause and no owner step. Proposal: plain words for what was checked ("my self-check of the guest message handling crashed"), one clause saying nothing was paused and nothing is needed, and Low (digest only) unless a pause is wired. Per README, the guest does not see this text; the owner does, so it needs the screen's plain-words bar.
3. **release (wait wording; same row)**: `waitUpdate` = "one comes with an update; I recheck it every round". "Round" is not defined to the owner. In fact a LOOP-7 job runs once per `Every` (1 h) and cycles through the probe and each target, so one target is rechecked about every 7 h, in spare capacity only. Say "I check again every few hours, and after each update." The text is only true once the source is wired (point 1 of Potency); today no code outside the tests constructs it, so no owner can see it yet.
4. **later**: a fuzz finding whose corpus file is removed can never resolve (`passed` needs the stored input to be replayed), yet STATUS keeps saying "I recheck it every round". Rare, and removing a corpus file is a repository change. Add a line to `broker/loop7/ASSUMPTIONS.md` when the source is wired.
5. **later**: a probe finding's ID is derived from its `Detail`, which embeds each got/want code. A different failure set on the next round is a different finding and a second High text for the same machine. A clean round resolves all of them. Cap or fold per subject when the probe text is reworded (point 2).

Cleared-by-hand checks: `TestTheUpdateWaitWordingIsScanned` shows the new wording passes the banned-word scan. The CH-12 held-text test does not cover these texts, so they were screened by hand.
