# UX review 1: onboarding and everyday use (spec v0.11 @ 3176f2d)

**Scope:** owner-facing experience only: setup, the text/voice channel, approvals, notifications, the local Wi-Fi UI, moving PCs. Security properties are taken as fixed; where a UX change touches one, the tradeoff is stated.
**Yardstick:** the spec's own north star, owner-minutes per accepted task (§1), plus standard usability heuristics: visible system status, recognition over recall, error prevention, no repeated manual steps, minimal up-front decisions.
**Labels:** [Fact] verifiable · [Inference] reasoned, untested · [Risk] needs a spike · **[Decision]** Mark's call.

The paired spec diff (same PR) implements the findings marked **→ spec**. Findings marked **→ later** are recorded here for a future run.

## Findings

### 1. Session unlock is a repeated manual step (CH-3)
Task chat needs "a session unlocked by an approval code within the last N hours". N is unset, and the spec doesn't say what happens to a message sent while locked.

What it protects: replies go to the owner's real number, so a sender-ID spoofer never sees answers, and every external effect is separately gated (REV-2, CH-10). The unlock's real value is against a **SIM swap**, where the attacker receives replies and could read private data through chat. That is worth keeping, but it does not need a short N.

Proposal (CH-14): unlock is prompted inline: the broker holds the message, asks for a code, then runs the held message. A code may be appended to any message. N is owner-set with a default of 7 days. An unlock is also required after any unrecognized-host boot or failed code attempts.
**[Decision] D1:** default N. 7 days (proposed) favors friction; 24 h favors SIM-swap exposure. The decision boundary is how long a SIM swap could go unnoticed: the daily digest heartbeat (CH-15) going missing is the owner's main signal, so N ≥ 1 day adds little detection.

### 2. Control words (CH-2, OP-6, LOOP-0, UPD-4, ADP-9)
STOP exists; resuming does not. Other commands are scattered ("loops off", "stop sharing", pause a pre-allowance, change channel) with no rule for how they're recognized.

Proposal (CH-11): a closed set of broker-parsed control words, matched only when they are the whole message (case and punctuation ignored), so "don't stop the backup" goes to the agent. All work with models down. RESUME needs a texted low-tier code, since a spoofed RESUME could restart work the owner halted; STOP, NO, and pause commands need none (their worst case is a pause). HELP returns the list in one text. Configuration phrases stay natural language through the agent, rendered back by the broker in fixed wording before taking effect (as ADP-9).

### 3. Batch replies (CH-4, CH-10, CAP-6)
"One code covers a batch", but no grammar for approving some items, denying others, or ignoring the batch.

Proposal (CH-13): `YES <code>` approves all; `YES 1 3 <code>` approves listed items; `NO` or `NO 2` denies without a code (safe, like STOP); unanswered items expire to denied and appear in the digest. Items are numbered within the batch.

### 4–6. Onboarding minimum path (§8.1)
Step 5 asks for six things at once, including spend cap, approval list, and quiet hours, before the owner has seen the product work. Steps 6–8 add typing a phone number, a card code, and connecting every account.

Proposal (ONB-3, ONB-6):
1. Plug in, power on.
2. Join the box's Wi-Fi (QR on the card); the setup page opens by itself.
3. Pick home Wi-Fi.
4. Tap **Text my box**: the phone's Messages app opens with the box's number and a one-time pairing code already filled in; press Send. The box learns the owner's number from the message and replies, proving both directions. The page offers the box as a contact card so its texts show a name.
5. Tap **Add approval codes**: the code generator opens from an `otpauth://` link. Type the code it shows to confirm.
6. Tear off the recovery sheet and tick "stored".
7. Connect one AI provider.

Defaults (spend cap, quiet hours, digest time, loops on) are stated in one line with "change any time by text". Accounts connect **just-in-time**: when a task first needs Google Calendar, the box texts the sign-in link then.

Trusted host: the first PC becomes trusted by default (the owner holds the card, which is the stronger proof), with a "not my PC" switch on the page.

[Fact] Apple and Android both open `sms:` links with a prefilled body; syntax differs slightly per platform. [Inference] `otpauth://` links open iPhone's Passwords app; verify on current iOS with S2/A1 hardware. Typing fallbacks always remain.

### 7. Phones and internet-less Wi-Fi [Risk]
[Inference] iOS and Android detect networks without internet; iOS shows a captive-portal sheet, Android may warn or switch to mobile data. Either can stop the setup page loading. Proposal (ONB-5): the AP answers captive-portal probes so the phone opens setup automatically, and once the box has an uplink it passes client traffic through, so phones don't drop the AP later. Needs a spike on current iOS/Android. CH-9 (UI unreachable from the home network) is unaffected. Passthrough is isolated: Wi-Fi clients reach only the local UI and the uplink, never the broker, vault, executors, or guests, and guests can't reach clients (tested in A6, per L3 review).

### 8. Visible status with no screen (§8.1, UPD-3)
Until the first text, the owner can't tell booting from broken, and the first-boot update may run for minutes. Proposal (ONB-4): the AP appears within a frozen target after power-on; the setup page shows live progress; UPD-3's update runs in parallel and blocks only AI and account connection, which must wait for an up-to-date image anyway.

### 9. Message format (CH-10, CAP-6)
Proposal (CH-12): broker texts use GSM-7 only ([Fact] one emoji forces UCS-2, cutting a segment from 160 to 70 characters); target one segment, at most three; request IDs ≤3 characters; approval texts carry verb, object, recipient or amount, reversibility ("undo 5 min" or "cannot be undone"), expiry, and the valid replies. Detail beyond that: `MORE <id>`, or the local UI.

### 10. Pacing and the heartbeat (CAP-4, §8.3)
Proposal (CH-15): unsolicited texts rate-limited (default 3/hour, owner-set), urgent classes owner-defined; quiet hours hold everything but STOP confirmations and those classes. The daily digest is always sent, one line when nothing happened. With no relay, a missing digest is the only way the owner learns the box is down.

### 11–14. Smaller items
- **Undo (CH-16):** confirmations of effects with an undo window include `UNDO <id>` and the deadline.
- **Voice codes (CH-17):** keypad digits preferred (speech recognition misreads digits); same rules as text.
- **First message (ONB-8):** three concrete example tasks based on what's connected, plus "HELP for commands".
- **Card (ONB-7):** a ≤5-step quick-start and a "nothing happened" side: the Wi-Fi name to look for, how long to wait, and the boot key for major PC brands.

### 15. Terminology
"Always-approve list" (§8.1), "standing grant" (CAP-6, CHG-3), and "pre-allowance" (ADP-9) describe overlapping owner choices. Proposal: owner-facing text uses **pre-allowance** for "run without asking" and **needs approval** for the rest; "grant" stays an internal term. Spec edits: §8.1 wording and CAP-6 points to ADP-9.

### 16. Measure onboarding (A1)
A1 checks that onboarding completes, not what it costs the owner. Proposal: A1 also records active owner minutes (excluding waits), typed characters, and errors per run against frozen targets, and at least one run is done by someone who has not read the spec.

### 17. Local UI at home → later
Using the local UI means leaving home Wi-Fi for the box's. That is the deliberate cost of CH-9; no change proposed. Revisit if A1 or real use shows it hurts. One cheap mitigation later: the phone remembers the box Wi-Fi, so switching is two taps.

### 18. Carrier filtering → later [Risk]
[Inference] Some consumer plans restrict automated messaging, and carriers filter high-volume person-to-person traffic. A box that texts too often could be filtered or suspended. Pacing (CH-15) reduces this; S2 should record carrier behavior.

---

## Decisions for Mark
- **D1** Session unlock default: 7 days (proposed) or shorter.
- **D2** First PC trusted by default during setup (proposed) or opt-in as today. Valid only because setup on the box's Wi-Fi page is CH-3's local confirmation; trusting a PC later always needs code + local step or the recovery key.
- **D3** Box AP passes client internet through once it has an uplink (proposed), or captive-portal handling only.
