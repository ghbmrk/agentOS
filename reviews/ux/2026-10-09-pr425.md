# UX, PR #425 (W3-forget-b3, promised done text survives a restart)

Record: PR #425 · package W3-forget-b3 · head f1ebd2cb0019d52bc0d7eef0a9917e6643468ee9

Verdict: accept

Tier A, UX lens only; Security is stage 4a. Reviewed from the diff against its merge-base with `origin/main`, CAP-3, UX-182-3 and SHOULD 4 of L3 on #182. Question: does the owner who said YES to a forget always hear how it ended, once, in words they can place?

- Yes for every path where the tombstone holds. The done text is owed before the tombstone is written and cleared only after it sends (F9), so a crash, a shutdown mid-retry, or a modem that is down just after boot no longer loses it (UX-182-3, SHOULD 4).
- A text told after a restart names the task by its date, "Your task from <date> is forgotten now." (F5). That fits an owner who may have texted since, and it corrects an earlier "Not forgotten" when a later save wrote the tombstone. No task text is repeated.
- An unreadable owed file costs the texts, not the forgets, and the owner is told so once (F10). Its step, "Send FORGET to see your recent tasks.", works: FORGET lists what is still there. That is not the CH-12 recurring kind.
- A repeated done text over a missing one (F4) is the right trade for the owner.

Points:
1. **later (CAP-3, F3)**: a crash after the owner's YES and before the tombstone saves ends silently. Reconcile marks the intent not applied, and the owed entry is dropped untold, so the owner waits for a text that never comes. The owed file already holds the date. "Your task from <date> was not forgotten. Send FORGET to try again." would close it; F3's "If it changes" column names this. It is pre-existing and a narrow crash window, and CAP-3's condition covers a failed save, not a crash, so it is not a blocker.
2. **later**: several owed texts after one restart go as separate texts. One line per task is fine at today's volumes (F6). If forgets are ever owed in bulk, send one text listing the dates.
