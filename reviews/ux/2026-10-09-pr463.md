# UX, PR #463 (SR2-3q, SR2-3p, runsc exec failures before the command ran)

Record: PR #463 · package SR2-3q · head 677071422b3540b171e18f938599a60d91b55eec

Verdict: accept

Tier A, UX lens only; Security is stage 4a. Reviewed from `git diff origin/main...pkg/SR2-3q-exec-not-started` against CAP-8 and RES-4 and the L3 accept on #463. The PR bundles SR2-3q and SR2-3p (one classification point). The texts it changes go to the guest agent through the worker tools, not to the owner. The owner meets them only as an agent's report. Question: does each fixed text say what happened and the next step, and does none advise a step that cannot work?

- `ErrExecNoProgram`: "the command did not start: its program was not found or cannot run; check its path and that it is executable, since a retry fails the same way". It names the cause, the fix and why a retry is futile. Before this PR, the advice was "retry it", a step that could not work (the CH-12 recurring kind, applied here to guest text). This PR removes that case.
- "did not start; retry it" now appears only for a failure runsc shows was before the start, so the retry advice holds there. A spoof can only move it to the safer text (L3 threat check).

Points:
1. **later (CAP-8 guest text), wording**: `ErrExecFailed`'s text, "the runtime failed after the command started, so it may have run…", now also covers failures where runsc does not show whether the command started: no `--log` line, an unknown line, a lost urpc answer, and a runsc panic before the pid write (a case that used to answer "did not start"). The advice ("check what it changed before running it again") is right for every one of these cases. Only "after the command started" claims more than is known. Reword `vm.ErrExecFailed` and the `guesterr` text to "the runtime failed and the command may have run; …" when either file is next touched.
2. **later (CAP-8)**: the known gaps in V33 (a non-UTF-8 `argv[0]`, or a PATH directory holding a space, quote or colon) still advise "retry it" for a missing program. The guest then makes one futile retry and gets the same answer. Already on the PR's Findings line as `later`. L3 point 1 asks the coordinator to add the LATER.md line, and it covers this point too.
