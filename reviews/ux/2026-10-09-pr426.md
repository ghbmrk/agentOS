# UX, PR #426 (CRED-5t, broker-held route failure)

Record: PR #426 · package CRED-5t · head 0bba6a7f2b3d7be2a163093740ff609c63bd4054

Verdict: accept

Tier A, UX lens; Security is stage 4a. Reviewed from `git diff origin/main...0bba6a7`, egress E11, and CRED-5, ONB-9, CH-10, CH-12. Question: when a plan route stops, will the owner be told what happened and what to do, in a way that is true?

No owner text ships in this PR. `RouteFailed` is called once per stop with a fixed reason. Wiring it to STATUS, the digest and the CAP-9 fallback is CRED-5b (release, PR Findings). The points below are inputs for CRED-5b, so they are folded into that row rather than raised as new rows.

Points:
1. **release (ONB-9, CH-12; fold into CRED-5b).** The two reasons need different owner lines, and neither should be the internal reason string. Unswappable: nothing for the owner to do. Say the plan is paused until an update and work uses the API key meanwhile, or, with no key, say work waits and how to add one (CRED-5f). Refused login: say what to do ("Sign in to your Claude plan again on my Wi-Fi page"). ONB-9 already asks for "one STATUS and digest line with what to do".
2. **release (CH-12; fold into CRED-5b).** E11 records that a guest can provoke a declared refusal status (e.g. 400 on a malformed refresh), which stops the route as `ReasonLoginRefused`. A notice that says "the provider refused your login" would then be false and would send the owner to sign in again for nothing. Either the notice says only that the plan stopped and names the triggering machine (CRED-5b already plans that), or a `Refused` entry also matches the provider's error code in the body, not the status alone (Potency point 1).
3. **later.** After a refused login, E11 reopens the route through `Resume` behind a low-tier code (CH-10). If the owner has just signed in again through the provider's flow on the Wi-Fi page (an already-signed-in device), asking for a separate RESUME code is a second step for one intent. CRED-5b's "Wi-Fi sign-in exit" can make the successful re-sign-in the resume, since the page sign-in is a stronger proof than the texted code (as `owner.LocalResume` already reasons).
