# UX, PR #444 (P2-2w d2b, page control to confirm a SIM swap and set up the owner number)

Record: PR #444 · package P2-2w-d2b · head d9bf31d456ffbc263e2c795907454f7eb654b3de

Verdict: accept

Tier A, UX lens only; Security is stage 4a. Reviewed from the diff against its merge-base with `origin/main`, CH-1, CH-7, CH-19, localui ASSUMPTIONS L27 and L31, and the L3 accept on #444. Question: when the owner line is swapped or unbound, does the page say what is true and give the owner a step that works?

- It closes a CH-12-kind gap that was already on `main`: the swapped and unbound notes said "confirm it on my Wi-Fi page", and no such control existed. Now the signed-in home page shows the note ending "below" and a form directly under it. The form shows exactly when the note says "below" (`iccid != ""` in both `OwnerLineNote` and `SIM`).
- The notes now separate five cases (down, swapped and readable, swapped and unreadable, unbound with a SIM, no SIM), and each names a step the owner can take there.
- The warning ("Do this only if you put this SIM in my phone modem yourself…") states the stake in the owner's terms, and the button names the last four digits printed on the SIM card, so the owner can check the card in hand. The code field, grid-cell prompt and wrong-code texts match the unlock form.
- One extra code even within a fresh sign-in is a deliberate CH-19 cost, paid once per SIM change. Accepted.

Points:
1. **release (CH-12 recurring kind)**: `simStaleText`, "My phone modem's SIM changed since this page loaded. Check the SIM below and try again.", is also shown when the line went back to ok or the SIM became unreadable or was removed (`ErrStale` covers every case where the shown SIM is no longer offered). The re-rendered page then has no SIM form below, so the text names a step that cannot be done. This is the recurring kind in `reviews/ux/README.md` (UX run 2, #327, #423); this PR touches owner texts but does not add the test that kind is owed. Suggest "My phone modem's SIM changed since this page loaded, so I didn't use it. The note above says what to do now." Add it to the package that adds the CH-12 owner-text test.
2. **release (same defect as L3 point 1)**: once `Record` succeeds, the note says "Setting up the SIM ending in NNNN as my number. Texts with you start again within a minute." and the form is hidden, until the bridge reports another state or SIM. If the bridge never takes the file (the L31 carry: directory permissions, or the two roles paths differ), that promise stays on the page indefinitely, and the owner has no retry and no way to tell. Also, until P2-1 makes the directory writable, every adopt gets "The box isn't answering right now. Nothing changed. Reload to try again.", and reloading cannot help. Bound `adopted` and, when it expires, say plainly that the box couldn't switch to the SIM and that a restart of the box is the next step. Same row as L3 point 1.
3. **later**: the signed-out status page (the page a phone lands on) does not show the owner-line note, though untokened `page_status` carries it (L27). So an owner whose texts stopped opens the box page and sees "Actions: running" and "Sign in", with no hint why texts stopped, until they sign in and tap More. This predates the PR (d2a). If the note is ever shown there, its "below" is false before sign-in (the form needs a session). Choose the wording together with the Security lens's call on L3 point 2 (D1, the last four digits before sign-in).
