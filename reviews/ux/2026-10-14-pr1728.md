### Findings

1. **blocker**: tree.go:204-218. The removal walk still follows a namespace symlink. `fs.WalkDir(root.FS(), ns, ...)` stats its root through the `os.Root`, which follows an in-root link. If `skills -> other` is planted and the new tree has **no** file under `skills/`, `refuseLinks` never runs for that namespace. The walk then lists `other/*` as `skills/*` and `root.Remove`s every file in it. Reproduced on this head: the tree is `{procedures/p}`, `skills -> other`, and `other/f` exists. The sync **succeeds** (`v1`, nil) and `other/f` is gone. That is the out-of-namespace deletion #1630 is named for. It also falsifies tree.go:30 and the new ASSUMPTIONS text "A symlink elsewhere in the tree directory, outside a tree file's path, is not looked at", along with its If-it-changes clause, which reads as if following were now closed. Fix: before the walk, `Lstat(ns)`, and refuse if it is a symlink (or call `refuseLinks(root, ns)`). Add an "empty namespace" subtest that fails without it. A deeper link inside a namespace is not followed by WalkDir; it is unlinked as a non-directory entry, which is harmless.

2. **release**: tree.go:240 with tree.go:46. The permanent failure defeats the log dedup. `syncTree` logs only when `err.Error()` changes, but the message names `p`, and `mirror` ranges over a map. One link with N tree files under it therefore gives a different message on most polls. Probe: one `skills/l` link with 3 files under it gave 3 distinct messages in 20 syncs (14/4/2). So one planted link writes a line every 30 s or so, for as long as it stays, into the guest console, which is bounded at `vm.ConsoleMaxBytes` (8 MiB), and pushes out older lines. Fix this together with UX actionability: name the link and not the file, and say what to do. For example: `managed tree: %q in the tree directory %s is a symlink; the tree is not synced until it is removed`. The absolute tree dir (`--tree`, default `/etc/agentos/tree`) is not in the message today.

3. **release**: ASSUMPTIONS.md:10, "permanent until the owner removes the link". The owner has no path into the guest. Only guest root can plant or remove the link (ARC-7, REV-1), and that can be the agent itself. State who can actually clear it (guest root, or a reset or reseed of the machine) and what the owner sees in the meantime: nothing on the local page, and the agent keeps its older skills.

4. **later**: no owner-facing surface for a tree sync that keeps failing. This one and every earlier cause (ENOSPC, bad path, unwritable dir) appear only as a guest console line, and the agent silently runs older skills. A broker-side "tree sync failing since T: reason" signal would make this mode actionable. It is pre-existing and not this PR's to fix.

5. **later** (L3): `refuseLinks` is the simplest structure that keeps the guarantee: one Lstat walk, refuse on the first link, stop at the first missing component. `clearWay`'s ancestor loop (tree.go:256-264) now walks the same components a second time. Folding it into the same walk would leave one pass with two outcomes (link means refuse, regular file means clear). That is optional and gives no power gain, so it is not required here.
