- **Copy.** Each refusal now has its own text, and only a provider refusal blames the key (U-2 is fixed; `TestTheAIKeyErrorsNameTheirCause` checks that the texts are distinct and that no other cause says "did not accept"). The texts:
  - Refused: "The provider did not accept that key."
  - Unchecked: "I could not reach the provider to check that key, so I did not save it. Try again in a minute." It says what happened, that nothing was kept, and what to do.
  - Limited: "Too many keys tried in the last minute. Wait a minute and try again."
  - Not taken: "Paste the API key from your provider's page."
  - Closed: "Setup is already done."
  - Codes unavailable: the existing `cannotFinish` text.
  - Anything else: "Could not save the key. Try again."
  All are plain, and none shows the key back.
- **While the check runs.** "Save key" is a plain form POST (localui/pages.go:352) with no script, so it has no progress state. A check normally answers in under a second. The worst case is 8 s (`SetupKeyCheckWait`), after which the page shows the unchecked text. The page's own bound is 15 s, inside localui's 120 s WriteTimeout. During that wait the owner sees only the browser's loading bar, and the button can be tapped again. A second tap only re-checks and stores the same key, under the 10-per-minute limit, so it does no harm. See U1.
- **Offline.** The AI step already opens only after the first-boot update, which needs the uplink (ONB-4, `aiReady`). An offline box shows the existing "I am offline..." text before any key is sent. If the uplink drops after the update, the owner gets the unchecked text, and nothing is stored. That is correct.
- **G1 and bad networks.** The check does not block G1: G1 connects AI by plan login (Mark chose "Wait for plan"), and this check runs only on the API-key form. On a slow link, one GET within 8 s is generous. When the provider is down, the owner can retry or use the other provider on the same page ("One is enough").
  - Storing an unchecked key instead would bring back #1265's failure path. That path is unrecoverable, because nothing past setup replaces a key (K23, K24). Refusing to store is the right trade.
- **U1 (later).** While the key is checked, "Save key" gives no feedback for up to 8 s. Proposal: a muted line under the field ("I check the key with the provider first; this takes a few seconds."), or disable the button on submit, as localui/vault.go:303 does for photo uploads.
- **U2 (later).** The refused text names no next step. The usual cause is a truncated paste. Proposal: "The provider did not accept that key. Copy the whole key again from your provider's page and paste it here."
