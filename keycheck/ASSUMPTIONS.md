# keycheck: assumptions

Built for KEY-diff (#2933), part 1 of change 2 in the ideal-backwards answer, which Mark approved. It covers `keycheck/` and `broker/keydiff/`. Each row is a reading a reviewer may want to change.

| ID | Assumption | Rests on | If wrong |
|---|---|---|---|
| KD-a | **keycheck is a second implementation, not a clean-room one. This row says where the two share logic.** Written from SPEC KEY-1..KEY-8, KRN-5, LOG-7 and `broker/kernel/ASSUMPTIONS.md`. The builder also read these parts of `broker/kernel/key`: the wire contract (`key.go` types, encodings and IDs, `verbs.go` whole), `authorize.go` up to `Live` (types and codes), the `Limits` struct with `Fold`, `Derive` and `Narrow`, and the whole #2927 diff. That diff includes the `caps` and `Spend` doc comments and where the task check sits. It did not read `Limits.apply`, `Within`, `verifyChain`, or the bodies of `Live`, `Authorize` and `caps`. Even so, the fold follows the same per-kind conditions, and the first draft reused two phrases found only in the Go comments; this commit rewrote them. The two also agree on rules SPEC leaves open: a metered call meets the money caps alone, with no rate or use cap, no clerk or verb check and no proof of possession; the rolling day is `at > now - DAY`; a cap counts against the account for a first link and against its own prefix after that; and the seven KD-b rules. A fault in any of these is common to both checkers. A clean-room rewrite, by a session that never opens `broker/kernel/key`, is the stronger form, and Part 2's spec-diff can weigh it. | risk 32 | Each shared rule above is a common-mode fault the harness cannot see. |
| KD-b | **The first disagreements and the L3 probe settled seven boundary rules.** Each was checked against SPEC before both sides were aligned on it: a hold's novelty window is at least its base window (KEY-8, "longer novelty window"); an argument bound with min above max is malformed; a repeated task caveat naming the same task is no loosening (KRN-5 forbids moving a task, not restating it); a metered call under a key with no money cap is refused `malformed`; a root with an empty clerk or no verbs is malformed (KEY-1: "one clerk ... and a set of verbs"); an argument bound with no name is malformed; and a 32-byte holder that is not a curve point is accepted. Such a key can sign nothing, so it is dead, not malformed. | KEY-1, KEY-3, KEY-8, KRN-5, LOG-7 | A reviewer who reads one of these the other way changes both sides. |
| KD-c | **The verdicts are compared, not the order of checks.** The library returns its first refusal and keycheck returns all of them, so a case agrees when both admit, or when both refuse and the library's code is among keycheck's. For a chain, validity, the charged scopes and the hold windows must be equal. The first error kind is only reported, because the two check in different orders. | KEY-2 | A disagreement that only changes which code is logged is not caught. |
| KD-d | **Signatures use ed25519-dalek's cofactorless `verify`**, which is the same equation as Go's `crypto/ed25519`. `verify_strict` would also refuse small-order keys, which Go accepts. Both sides refuse a non-canonical S. | KEY-1, MIG-2-a | Real passkeys sign WebAuthn assertions (MIG-2-a). Both sides change when they do. |
| KD-e | **The harness reaches every rule.** The sweep fails unless every refusal code (`task` included), every chain error, an admitted step, an admitted metered call and each edge input occur at least once. The edge inputs are an empty clerk, no verbs, an empty argument name, an off-curve holder and amounts within 30 of the int64 limit. | EVL-1 | A generator that stops reaching a rule fails the sweep. It does not pass quietly. |
| KD-f | **Crates come from crates.io, pinned by `Cargo.lock`** (`--locked`), with `rust-toolchain.toml` pinning the compiler. The crates are ed25519-dalek, sha2, serde, serde_json and base64. They are not vendored. keycheck is not on the authority path yet, so it is outside the trusted-base budget. | KRN-2 | Part 2 puts it on that path, and it then needs vendoring and a trusted-base entry. |
| KD-g | **Part 2 is a later row: both checkers on the path.** For that, the kernel or the clerk would refuse an effect unless keycheck also admits it. KEY-1 says that the kernel and every clerk use "the same key-check library", so this needs an L1 spec-diff first. | KEY-1, CLK-2 | none |
| KD-h | **One known disagreement: the library's money sum wraps.** The library adds a charge to a money total without a check, so near the int64 limit the sum wraps negative and the step or call passes the cap (L3 finding 3 on #2942). keycheck sums in i128 and refuses. The harness counts and logs these cases rather than failing on them, but only when the case drew a huge amount, the library admitted it and keycheck refused with nothing but money codes. A separate defect row fixes the library. When it lands, that branch in `one` goes. | KEY-2, LOG-7 | A money disagreement that is not an overflow hides in this branch only when the case also drew a huge amount. |
