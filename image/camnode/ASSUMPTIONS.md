# Camera node image: assumptions

Built for CAM-node part (c), CAM-image (#3513, `briefs/CAM-node.md`), against DEV-2, DEV-3, DEV-7, NET-2 (Cameras), NET-4, NET-7, HW-10 and A16, on the 2026-10-28 decisions on #3513 (two-way locked TLS, release key plus passkey, OPTIGA Trust M). The node's code and its own assumptions are `broker/camnode` (CAM-server, CAM-b2, CAM-bin rows); this file covers what the image adds. Each row is a reading a later change could overturn.

| # | Assumption | Basis | If it changes |
|---|---|---|---|
| CAM-image-1 | **Buildroot 2026.02.3 (long-term), pinned by the SHA-256 in its signed release notice**, with the toolchain built from source (no prebuilt toolchain) and every download checked against Buildroot's own hash files (`BR2_DOWNLOAD_FORCE_CHECK_HASHES`; `build.sh` also fails a download with no hash file, which Buildroot only warns about). Buildroot 2026.02.3 ships the hashes of its kernel 6.18.33 and headers 6.12.91 but looks for them in directories it does not ship, so `external/patches/` carries those two lines, copied from Buildroot's `linux/*/linux.hash`; the QEMU board runs 6.18.33 for that reason. Reuse: Buildroot is the brief's pick (mature, small, read-only root); the only new component is `camnode-init` (CAM-image-2), because no initramfs tool sets up verity on a partition the bootloader picks at run time without a shell. | Brief design point 5 | A Buildroot bump is a hash and version change in `build.sh`. |
| CAM-image-2 | **A slot is one partition**: the boot FAT the bootloader reads (`boot.img`, its `boot.sig`, and a `config.txt` asking for the boot image), then the erofs root, then its verity hash tree, at offsets the command line inside `boot.img` names with the root hash and salt. So the signature over `boot.img` covers the root, an update writes and hashes one device (as `agentos-camnode`'s `Stage` and `slots.running` do), and the same slot image boots from either slot: `camnode-init` takes the partition from the bootloader's `/chosen/bootloader/partition` (CAM-bin-2), never from the image. | Brief design points 3 and 5 | A board whose bootloader cannot load a boot image from a partition needs its own layout. |
| CAM-image-3 | **The whole root is read through verity before systemd starts**, and verity runs `restart_on_corruption`: a flipped byte anywhere stops that boot, and any `camnode-init` failure restarts the board with no tryboot flag, so a trial image that does not verify returns to the slot before (CAM-b2-2). An altered root on the default slot restarts in a loop: the camera is off, never running altered code. | Brief lifecycle matrix, "altered root" | — |
| CAM-image-4 | **The disk is MBR**: 1 the boot selector (16 MiB FAT, `autoboot.txt`, which `agentos-camnode` rewrites), 2 and 3 the slots (512 MiB each; this build's slot image is about 160 MiB, mostly the boot FAT's reserve), 4 the data partition (64 MiB ext4, mounted `nosuid,nodev,noexec`). The selector is mounted `sync`: without it a power cut just after `agentos-camnode` rewrote `autoboot.txt` left a directory entry pointing at a free cluster, which the end-to-end test's bootloader could not read. Sizes are fixed once: repartitioning a node in the field is out of scope. | CAM-bin-2 | Resize before the first board is flashed (part d). |
| CAM-image-5 | **No console on the CM4**: no `console=` on the command line, `enable_uart=0`, `quiet`, no getty or `sulogin` units or binaries, and `post-build.sh` refuses a root with a shell, login path, remote shell or setuid file. The QEMU board has a serial console for the kernel and a virtio console for the journal, for the end-to-end test only; that image is never flashed. | Brief design point 5 | — |
| CAM-image-6 | **Reference wiring** (generic, no household data): the button on GPIO 17 to ground (`gpio-key`, BTN_0), the IR illuminator's driver on GPIO 27 (`gpio-led`, `ir`), the OPTIGA Trust M on `i2c_arm` (`/dev/i2c-1`), the IMX462 on the `imx290` overlay. udev names each under `/dev/camnode/` so the one unit file serves both boards [Inference: from the Raspberry Pi overlay README; part d confirms on the board]. | Brief parts | Part d's wiring changes `config.txt` and the CM4 udev rules only. |
| CAM-image-7 | **No thermal core on this build.** The flags for one (`-thermal`, `-thermal-core`) go in the CM4 drop-in with `dtparam=spi=on` when a node has a Lepton; that variant is a later row. | Brief parts ("optional thermal core") | — |
| CAM-image-8 | **The release signer holds two keys.** The root carries the Ed25519 public key `agentos-camnode` checks manifests with (`/usr/share/agentos/camnode-release.pub`, from `CAMNODE_RELEASE_PUB`); the board's secure boot checks `boot.sig` with the RSA-2048 key whose hash part d fuses [Inference: Raspberry Pi 4 secure boot signs `boot.img` with RSA-2048; part d confirms]. `build.sh` builds unsigned; the signer makes `boot.sig` over this commit's `boot.img` and the slot is assembled again with `CAMNODE_BOOT_SIG`. CI's CM4 build uses a throwaway key and is for review only. HW-10 names this as the second release-signed image, with both keys (#3756); it leaves the boot key's algorithm to part (d). | HW-10, brief question 4 | — |
| CAM-image-9 | **The firewall is the whole network policy**: in, the stream port and DHCP replies; out, replies to accepted connections and DHCP requests; forwarding off. `systemd-networkd` and the stream socket require it, so a failed load leaves no address and no port (fail closed). The kernel has no IPv6, Wi-Fi or Bluetooth (Buildroot's systemd package turns IPv6 on after the fragments; `camnode-init`'s kernel fixup turns it off again, and `build.sh` checks the built kernel against the fragments). networkd's DHCP client sends its first requests on a packet socket, which netfilter does not see; it sends DHCP only, and the end-to-end capture shows nothing else leaves. | NET-2, DEV-2 | — |
| CAM-image-10 | **The service runs in its own network namespace** (`PrivateNetwork=yes`) on the socket systemd passes, under its own uid with `CAP_SYS_BOOT` only and the node's devices only. Three failed starts within two minutes reboot the board without tryboot (`FailureAction=reboot`), so a trial image that fails to start returns to the slot before. A start that hangs before `Serve` is not caught: the binary does not tell systemd it is up, so the unit cannot time it out; a power cycle then boots the old slot, since the trial was never marked good (follow-up, PR findings). | CAM-b2-2 | `sd_notify` after `Serve`'s listener, `Type=notify` and a start timeout. |
| CAM-image-11 | **The QEMU board's stand-ins are test parts, not models of the hardware**: the element stand-in answers the OPTIGA commands `broker/camnode/se` sends, over CUSE on `/dev/i2c-1`, and keeps its key and counters on a second virtual disk, making the key at its first start as provisioning would; it has no lock states or shielded connection. The button is a uinput key held when QEMU's `fw_cfg` says so; the encoder writes generated access units. The node binary, its element driver, the units and the firewall are the CM4 image's. | Brief, "Tests use a fake element" | — |
| CAM-image-12 | **The end-to-end harness plays the bootloader**: it reads `autoboot.txt`, boots the `[tryboot]` partition once when the kernel's restart command contains `tryboot` (as `agentos-camnode`'s `reboot` sends), and gives the kernel a device tree whose `/chosen/bootloader` names the partition and the flag. It does not check `boot.sig`; signed boot is part d's [Inference: the Pi firmware reads the restart argument this way; part d confirms]. | CAM-bin-2 | — |
| CAM-image-13 | **The data partition has no `fsck`** (no e2fsprogs in the root): ext4's journal covers power cuts; a data partition too damaged to mount stops the service, and the node is re-imaged. | HW-1 | A `fsck` in the root if the field shows the need. |
| CAM-image-14 | **The "internet cut" test**: the end-to-end run's namespace has no route beyond the host, and the node's lease names the host as its router, so any packet the node sends towards the internet shows on the tap. The test streams for 30 s and requires that the node sent only the stream's segments, ARP and DHCP. | Brief lifecycle matrix, "internet cut" | — |
