# guest/codex assumptions (S8-W1 defensive half, #807)

What the Codex provider worker's managed config and tool sandbox rest on. The rootfs build (`build-rootfs.sh`, C16-C17) pins the CLI and installs the managed layers; nothing is
wired into agentosd yet. Rows marked measured were measured on Codex CLI 0.162.1 on a Linux host as root, without runsc; #809 repeats them on the
pinned CLI under runsc. The supervised containment run with the real CLI, forwarder and egress socket is #1720 (D-064's worker-held Claude version is #1380).

| # | Assumption | Spec basis | If it changes |
|---|---|---|---|
| C1 | Measured on Codex CLI 0.162.1 (as root, without runsc; #809 repeats it on the pinned version under runsc). The CLI reads `/etc/codex/managed_config.toml` as managed config: it beats `CODEX_HOME/config.toml`, a `-p` profile, `-c` flags and `-s`, key by key. Tables deep-merge, so a lower layer can add a key the managed file leaves unset (a `[model_providers.agentos] supports_websockets = true` in CODEX_HOME turned WebSocket on until it was pinned), and unset keys fall through (`model` did until C19 pinned it). `/etc/codex/requirements.toml` is a separate layer that lower layers cannot relax or extend; settings that a lower layer could extend live there (C12, C14). A workspace `.codex/config.toml` is loaded without any trust entry unless managed config marks the workspace untrusted, which it now does (its canary reached the tool environment before the pin, and was gone after). The key names in managed_config.toml are the ones the CLI read in that run (`codex doctor` and tool-visible effects); `web_search_request` and `web_search_cached` are deprecated and logged as such. Not measured: whether managed values can change within a session. A key the CLI ignores fails open, which is why #1014's request-body check, not this file, is the enforcement for hosted tools. | CRED-5, CAP-11, ARC-7 | #809 re-measures on the pinned version; tests/test_codex_worker.py's REQUIRED table and its opt-in CliSandboxTest follow. |
| C2 | The CLI honours `CODEX_REFRESH_TOKEN_URL_OVERRIDE` and `CODEX_HOME` from its environment, and `exec --json --skip-git-repo-check --cd /var/lib/agentos-work -` runs headless in the workspace, which is not a git repository (measured on 0.162.1 with a fake endpoint on the forwarder's port: the turn ran and the tool call went through the CLI's sandbox). | CRED-5 | #809; the forwarder (#1014) refuses an undeclared refresh host either way. |
| C3 | The tool boundary is the CLI's own sandbox: `sandbox_mode = "workspace-write"` runs each tool command under bwrap with a seccomp filter, no network and a read-only root apart from the workspace, and requirements.toml's `deny_read` hides CODEX_HOME (C12). Measured on 0.162.1: agentos-toolsh nested inside that sandbox fails (`bwrap: loopback: Failed to create NETLINK_ROUTE socket`), and `danger-full-access` gives tools full capabilities as root, so the wrapper is not on the run path. It stays as the reference for what the boundary must hide (forwarder port, `/run` sockets, CODEX_HOME, inherited descriptors) and the fallback if a CLI update loses its sandbox. The opt-in CliSandboxTest runs the wrapper's stub tool under the CLI's sandbox, but asserts a narrower set: no forwarder port, no egress socket, no auth.json, no write outside the workspace (CODEX_HOME, /tmp and the root included), and no lower-layer environment. It does not assert capabilities, process or session visibility, inherited descriptors or nested user namespaces. A security review measured that a tool can create a nested user namespace inside the CLI's sandbox; the mounts it inherits are locked, so it cannot uncover what they hide. Not yet measured under runsc (#809, C5). | CRED-5, A14 | If the CLI sandbox fails under runsc or a CLI update drops it, run tools through agentos-toolsh outside the CLI sandbox instead (#1452 option 2) and re-run CliSandboxTest. |
| C4 | The egress socket and any other path socket the worker gets live under `/run` (`/var/run` links there). Path sockets are not scoped by the network namespace; abstract ones are. On the run path (the CLI's sandbox, C3), `/run`, `/tmp` and `/var/tmp` stay visible read-only to a tool; what denies the egress socket is the CLI's seccomp filter, which refuses `connect` with EPERM (measured on 0.162.1 by a security review; CliSandboxTest shows the socket unreachable but not which layer stops it). In agentos-toolsh, the fallback, a `/run` tmpfs hides the path instead. Nothing in the managed config does either. | CRED-5, A14 | If a CLI update lets the sandbox connect to path sockets, the socket must move behind a mount the CLI's sandbox hides, or tools go through agentos-toolsh (C3). Add a new socket directory to the wrapper's hiding mounts and to the test's stub worker. |
| C5 | bubblewrap works inside the worker's gVisor sandbox (user, net, pid and mount namespaces), both for the CLI's own tool sandbox, which ships its own bwrap, and for agentos-toolsh at `/usr/bin/bwrap` (`--disable-userns` needs bwrap 0.8). Tested only on a Linux host as root (CI runs it under sudo). The runsc measurement is owed on #809. | A14 | If runsc refuses a namespace bwrap needs, the tool sandbox moves to a nested runsc or the worker's own seccomp/landlock, measured the same way. |
| C6 | Every tool runs with its working directory at the workspace root `/var/lib/agentos-work` or below; the wrapper refuses any other directory (resolved with `pwd -P`, so a symlink out of the workspace is refused). It binds the fixed workspace root, before its hiding mounts, and enters the checked directory with bwrap's `--chdir`; it never binds the working directory itself, because bwrap resolves a bind path again after the check and a concurrent tool could swap it for a symlink to `/` in between. This rests on `/var/lib` being read-only to tools, so no tool can rename the workspace root. | A14 | Change `WORK` in the wrapper and the test with the workspace path. |
| C7 | `/bin/bash` is in the worker rootfs (Debian marks it Essential). The wrapper needs it because dash cannot close a descriptor above 9; the test passes descriptors at 200 and 1000 to show it. Without `/proc` the wrapper refuses rather than leave descriptors open. | A14 | A rootfs without bash needs another way to close inherited descriptors before bwrap starts. |
| C8 | If the CLI runs agentos-toolsh, it runs it through its shebang, `#!/bin/bash -p`, never as `bash agentos-toolsh`, which would drop `-p`; `sh agentos-toolsh` fails with a syntax error before running anything. Privileged mode stops bash's own environment routes from running code in the wrapper before the check and outside bwrap: it skips `BASH_ENV` and `ENV`, imports no exported functions (`BASH_FUNC_*%%`), and ignores `SHELLOPTS`, `BASHOPTS`, `CDPATH` and `GLOBIGNORE`. The test shows a `BASH_ENV` file and an exported `pwd` are ignored. It does not stop the dynamic loader: `LD_PRELOAD`, `LD_LIBRARY_PATH` and `LD_AUDIT` run code in bash and bwrap before the script starts. So the CLI's tool environment is pinned to carry none of them (C15). CliSandboxTest shows both sides on the real CLI: as shipped, a CODEX_HOME `set = {LD_PRELOAD = ...}` does not reach the tool and the preload library does not run; with `include_only` dropped, the library runs in the tool (asserted when a C compiler is present to build it). No test runs the wrapper itself with `LD_PRELOAD` set. | CRED-5, A14 | If a CLI update can pass loader variables again, the prefix becomes a small static binary. |
| C9 | Plugins, hooks and the other features that load code or reach a service the forwarder does not declare are off: managed `[features]` sets `hooks`, `plugins`, `remote_plugin`, `plugin_sharing`, `apps`, `browser_use`, `browser_use_external`, `computer_use`, `multi_agent`, `skill_mcp_dependency_install` and `in_app_updates` to false. Measured on 0.162.1 against a CODEX_HOME config that turned them on: `codex doctor` lists them all false, the plugin sync's `git ls-remote` call stopped, and a workspace `.codex/hooks.json` did not run, even with `--dangerously-bypass-hook-trust`. | CRED-5 | A new feature flag in a CLI update starts at its default; #809 diffs the flag list on each pin. |
| C10 | The WebSocket transport is off: `supports_websockets = false` under `[model_providers.agentos]` (measured: `codex doctor` shows it false even when CODEX_HOME sets it true). #1014 refuses upgrades on declared endpoints either way. | CRED-5 | If the key is renamed, the CLI tries an upgrade and #1014 refuses it, which fails the turn rather than leaking. |
| C11 | The CLI runs git in the workspace outside the tool sandbox (`rev-parse`, `remote`, `status --porcelain`, `config --get core.fsmonitor`). Measured: a tool-written `.git/config` with a `filter.<x>.clean` plus `.gitattributes` ran a program there. launch.json sets `GIT_DIR=/dev/null`, so git reports "not a git repository" and reads no workspace git config, and `HOME` to CODEX_HOME, which tools cannot write, so no tool-written dotfile (`.gitconfig`, `.config/`) is read either. | CRED-5, A14 | If the CLI needs a real repository, give it a read-only one outside the workspace. |
| C12 | requirements.toml's `[permissions.filesystem] deny_read` hides everything in CODEX_HOME from tools except `tmp/`, where the CLI keeps the arg0 helpers its tools need. Measured semantics on 0.162.1: the list is expanded when each tool starts; `*` and `?` do not reliably cross `/`, so each pattern has a `/**` twin; a literal directory listed alongside a glob covering it makes bwrap fail to start, so there are none; `[!/]` does not match as expected. Fixtures denied: auth.json, `t`, `tmpx`, `tmpdir/f`, `tmp.d/f`, `tq/f`, `tmz/f`, nested directories, dotfiles and the state databases. Limits: a file the CLI creates after a tool starts is readable to that tool (measured), as an auth.json the CLI replaced by rename would be; names stay listable; `tmp/` is readable. A token refresh does not open that gap on 0.162.1: the CLI rewrites auth.json in place (inotify shows modify and close-write, no create or rename), so a tool already running still cannot read it, and the CLI writes only the refresh answer's placeholders; when the route drops the answer (502) auth.json is left as it was (#1504, `CliSandboxTest.test_a_tool_cannot_read_auth_json_after_the_cli_rewrites_it`, `test_a_dropped_refresh_leaves_auth_json_as_it_was`, which also fail if the CLI starts renaming). These are bounded because CODEX_HOME holds only the placeholder login (#1015), the refresh route answers only placeholders or drops the answer (#1749, `broker/egress` `TestWorkerRouteRefresh`, `TestWorkerRouteRefreshDropped`) and tools have no network. | CRED-5, A14 | If the CLI adds an exception syntax, deny CODEX_HOME whole and allow `tmp/`. If the helpers move, the spared name changes with them. |
| C13 | Managed config sets no permission profile (`default_permissions`, `[permissions]`): a lower layer deep-merges into a managed profile and can widen it. The read denies live in requirements.toml instead (C12). The test refuses either key in managed config. | CRED-5 | If the CLI makes managed profiles unmergeable, they can move back. |
| C14 | No program runs outside the tool sandbox from config: managed `notify = []` replaces any lower-layer notify (measured: a CODEX_HOME notify program did not run), and requirements.toml's empty `[mcp_servers]` is an allowlist that refuses a lower-layer `[mcp_servers.<name>]` (measured: the server command did not run). | CRED-5 | A new config key that runs a program needs the same treatment; #809 lists them per pin. |
| C15 | Tools get `PATH` from the CLI's environment, `HOME` and `TMPDIR` from managed `set` (both the workspace), and nothing else: `[shell_environment_policy] inherit = "core"` with `include_only = ["PATH", "HOME", "TMPDIR"]`. Without HOME and TMPDIR, mktemp and `git config --global` failed in the tool, since `/tmp` is read-only there (measured by the L3 review); with them both work. A lower layer's HOME loses to the managed value key by key (CliSandboxTest sets one to CODEX_HOME). The CLI's own HOME stays CODEX_HOME (C11), so a tool-written `.gitconfig` in the workspace is not read by the CLI's git. Measured: `include_only` also filters a lower layer's `set`, so neither a CODEX_HOME `set = {LD_PRELOAD = ...}` nor a canary reached the tool; a managed `set = {}` does not block it. The CLI still adds its own variables (`CODEX_*`, `LANG`, pagers). `inherit = "none"` gave tools no system PATH, so basic commands failed. | CRED-5, A14 | If include_only stops filtering `set`, pin `set` too and re-run CliSandboxTest. |
| C16 | The pinned CLI is the npm package `@openai/codex@0.162.1-linux-x64` (a static musl binary, the version C1-C15 were measured on), downloaded from the npm registry and checked against npm's published SHA-512 integrity before anything is unpacked. `build-rootfs.sh` installs only `codex-package.json` (without it the CLI cannot find its bundled ripgrep), `bin/codex`, `bin/codex-code-mode-host` (the CLI starts it from beside its binary), `codex-resources/bwrap` and `codex-path/rg` under `/opt/codex/vendor/x86_64-unknown-linux-musl`, and copies the bundled bwrap to `/usr/bin/bwrap` for agentos-toolsh. Whether the bundled bwrap supports C5's `--disable-userns` (bwrap 0.8) is not asserted here: its `--help` lists the option, but it is deferred to #809 and #1723. | CRED-5, A14 | A newer pin needs a new integrity and a repeat of C1-C15 on that version (#809). If the CLI needs another file from beside its binary, a headless turn fails at start: `--version` would still pass; the image test runs `codex doctor` over the built tree to catch that (package discovery, managed layers loaded, approval Never, sandboxes restricted, the default-on flags of this pin off), and #809's turn is the real check. |
| C17 | The rootfs holds no login: no `auth.json` anywhere, `CODEX_HOME` (`/var/lib/agentos-codex`) holds an empty `tmp/` only, and `etc/codex/managed_config.toml`, `etc/codex/requirements.toml`, `usr/lib/agentos/codex/launch.json` and `usr/local/bin/agentos-toolsh` are byte copies of the repo files (owned by root only when the build runs as root, as CI's does; the test checks that then). The CLI's own sandbox keeps them read-only to tools whoever owns them (C3). #1015 writes the placeholder `auth.json` at machine create. The runsc measurement of C1-C15 is not done here: it is #809's, in a live session, run in a machine from this rootfs. | CRED-5, CRED-1 | A rootfs file that differs from the repo's file means the managed layers are not the ones the tests checked. |
| C18 | **The in-worker forwarder (#1014 part c).** `agentos-codex-forwarder` listens on a literal 127.x address (default 127.0.0.1:18432) and relays each TCP connection, unparsed, to `/run/agentos/route.sock`; with no socket it closes the connection. `launch.json` `wrap` runs it before the CLI: **#1314's runner must exec `wrap` followed by `argv`, with exactly `env`**, which carries the `PATH` (`/usr/local/bin:/usr/bin:/bin`) that finds the bare `codex` and the tools' helpers (C15) and never the refresh override; run alone, `argv` finds no forwarder and every turn fails to connect (fails closed). The forwarder (source `broker/egress/cmd/agentos-codex-forwarder`) starts the CLI through `broker/childproc` with only `PATH`, `HOME`, `CODEX_HOME` and `GIT_DIR` copied by name from its own environment, plus `CODEX_REFRESH_TOKEN_URL_OVERRIDE` set to its bound port's `/oauth/token`, so the override names the forwarder by construction; `launch.json` `env` must not carry the override (childproc refuses passing on a TOKEN-named variable's value). The managed `base_url` names the same port, and tests pin that they agree. The tool boundary is the CLI's own sandbox (C3: bwrap, `network_access = false`); CliSandboxTest asserts a tool reaches neither the port nor `/run/agentos/route.sock`; agentos-toolsh is the fallback. The forwarder caps itself at 8 relays and closes a relay idle for 10 minutes. Not measured under runsc: #1720. | A14, CRED-5, A3 | A wrap, base_url or refresh URL naming a different port, or a forwarder that dials anything but the socket, is a defect. |
| C19 | **The model G1's task uses is `gpt-6.1-sol`, pinned in managed config (#1396).** G1's model-backed task is `provider_run` on the Codex plan route (broker/e2e/boxe2e E12, image I26), so its model is the one the worker's CLI asks for. Measured on the pinned 0.162.1 (integrity checked) with this managed config, before the pin, against a fake forwarder endpoint on 127.0.0.1:18432 and a synthetic ChatGPT-mode placeholder login: the CLI fetched `GET /backend-api/codex/models` at start, the fetch failed, and every `POST /backend-api/codex/responses` carried `"model": "gpt-6.1-sol"`. That is the top-priority listed entry of the bundled catalog (`codex debug models --bundled`: gpt-6.1-sol, gpt-6-astra, gpt-6-sol, gpt-6-luna, gpt-5.6-sol and others). Unpinned, the default comes from the catalog the provider serves at each start, so it could change between the qualification run (#809) and G1 with no image change; pinned in the managed layer, neither the catalog, a lower config layer, `-c` nor a trusted project config can change it (C1). The reasoning effort stays the CLI's default for the model. tests/test_codex_worker.py pins the key in REQUIRED, and its opt-in CliSandboxTest checks that every turn of a real CLI asks for it. Not measured: whether the owner's plan serves this model (the G1 run and #809's turn are the check). The OpenClaw guest's `broker-default` class (image rule.json, I14) is the agent's own model route, not this task's, and is not confirmed here. | CAP-11, A1 | A CLI pin bump re-reads the bundled catalog's default and moves this pin with it (and #809 re-qualifies). A plan that does not serve the model should fail the turn with the provider's error rather than switch models (inferred from the pin, not measured). |
| S8-W1-s8-C20 | **Plan-login traffic, the refresh included, goes through the forwarder; a refresh in the middle of a turn loses that turn on 0.162.1 (#2085).** Managed config pins `chatgpt_base_url` to the forwarder's port, so a plan login's requests reach the egress route instead of chatgpt.com, and the token refresh goes to the override the forwarder sets (C18). A login due for refresh is refreshed at startup and the turn completes (`CliSandboxTest.test_a_stale_login_refreshes_at_startup_through_the_forwarder`). When a request is refused with 401 mid-turn, 0.162.1 refreshes, writes the route's placeholders to auth.json, then sends the retried request through its route-aware client, which needs an application network policy; with none it fails closed and the turn ends with "application network policy is unavailable" (measured). No config 0.162.1 reads fixes it: `[application.network]` is read only from requirements.toml (config.toml ignores it); with `enabled = false` the error is the same, and with `enabled = true` every plain-http loopback destination is denied even when its domain is allowed (127.0.0.1, localhost and a hosts-file name, all measured), so every request fails from startup. The bound: that one turn fails, auth.json already holds the refreshed placeholders, and the next turn on it completes without refreshing again (`test_a_mid_turn_refresh_loses_that_turn_and_the_next_completes`). Nothing leaves the forwarder route either way. | CRED-5, A14 | The mid-turn test turns red if a CLI bump completes the turn or fails it another way; then re-measure and drop or restate the bound. A forwarder that served HTTPS under a worker-local CA might let an `[application.network]` policy allow it (unmeasured). |
