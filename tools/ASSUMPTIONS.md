| D8 | **Read-only means `MOUNT_ATTR_RDONLY` set recursively on every kept path, parents first** (`remount,bind,ro` until DEP-4; D10). Kept paths are bound in sorted order, so a parent is made read-only before a path inside it; a `writes` path inside a read-only parent is bound again and left writable. The `ro` flag is set inside the sandbox's own mount namespace, so the kernel does not lock it against a process holding CAP_SYS_ADMIN there, which the scenario would have as root of the sandbox's user namespace (since DEP-3 it runs as `SCENARIO_ID`, D9, and keeps no capability; the drop stays as a second layer): `mount_setattr` and `open_tree_attr` (Linux 6.15+) clear it untraced (Security on #437 reproduced a rewrite of `depaudit.py` ending `pass`). So the command runs under `setpriv`, which drops CAP_SYS_ADMIN and CAP_SYS_PTRACE from its bounding and inheritable sets after strace (`DROP_CAPS`); `control-kept-read-only` tries both calls on every read-only kept path and fails if either succeeds or a write lands. CAP_SYS_PTRACE goes because `_inner` (PID 1) and strace keep CAP_SYS_ADMIN: with it the scenario could attach to either and inject `mount_setattr` (Security re-sign on #437, B1). Without it, `cap_ptrace_access_check` denies an attach to a process whose permitted set is not a subset of the caller's, and Yama scope 1 denies attaching to an ancestor; `control-no-ptrace-ancestors` does a `PTRACE_SEIZE` on PID 1 and opens strace's `/proc/<pid>/mem` (the same attach-mode check; a real attach to strace from its own tracee deadlocks both) and passes only if both are denied (it failed at f363149, both allowed). A nested user namespace does not get it back: mounts copied into it are locked. A `mount(2)` remount is traced and is a violation by itself. The sandbox enters a user namespace (`unshare -r` until DEP-3, now the two-id map of D13) even when run as real root, so every capability the scenario keeps is scoped to that namespace: without one, real root keeps CAP_DAC_READ_SEARCH (`open_by_handle_at` on a writable mount of the same filesystem), CAP_SYS_MODULE, CAP_MKNOD and CAP_SYS_RAWIO on the host, each a way past a read-only bind (Security re-sign 2 on #437, B2).
