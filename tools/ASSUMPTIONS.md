# Harness tools: assumptions

Rows for `tools/depaudit.py`, written for HK-1 (a defect fix in P1-6's harness;
local IDs HK-1a–c in `briefs/HK-1.md`, no SPEC row) and DEP-2 (D7–D11; local
IDs DEP-2a–c in `briefs/DEP-2.md`, no SPEC row) and DEP-4 (D10, D12; local IDs
DEP-4a–b in `briefs/DEP-4.md`, no SPEC row) and DEP-3 (D9, D13; local IDs
DEP-3a–c in `briefs/DEP-3.md`, no SPEC row). Each row is something the
fix rests on that a reviewer may want to check or change.

| D1 | **The #391 straggler was a process still writing after the run.** Verified from run 37824851327 (PR #391, head 7e81122, job `dependency-audit`): `test_shipped_registry_passes` raised `OSError: [Errno 39] Directory not empty: 'go-build2650989805'` from `TemporaryDirectory.__exit__` in `run_target`. That a Go build child outlived strace is an inference from the go-build name; the log does not show the process. | HK-1a | If a straggler is seen with the PID namespace in place, the kill is not total: investigate before raising the retry bound. |
| D2 | **Killing the PID namespace kills everything the scenario started.** The sandbox runs under `unshare --pid --fork --kill-child --mount-proc`; when unshare is killed or its child (namespace init) exits, the kernel kills every process in the namespace, including one that called `setsid()` (which `killpg` alone misses: `test_a_process_that_escaped_strace_and_its_group_is_killed_with_the_run`). The work directory is removed only after that, so the ENOTEMPTY retry (50 × 0.2 s, then raise) covers writes already in flight, not a live process. Checked as root and as an unprivileged user locally; CI's runner is authoritative. | HK-1a | If a runner refuses a PID namespace or a `proc` mount, `sandbox_available()` (same flags) is false and `depaudit run` fails with exit 2, loudly, not by skipping. |
| D3 | **A strace fault is recognized by strace's own message on the scenario's stderr**, `^strace: .*Input/output error` or `^strace: .*PTRACE_`. The #378 log (PTRACE_LISTEN EIO) and the #372 log were not retrievable, so the message text is **inferred**, from strace's `ptrace_restart`, which prints `strace: ptrace(PTRACE_LISTEN,pid:N,sig:S): Input/output error`. Exit status is not part of the test: strace exits with the main tracee's status, so a fault on a child it let go of can end 0 with a partial trace. | HK-1b | A scenario that prints such a line itself only makes its own result `error`, never `pass`. If strace changes its wording, a fault reads as `scenario-failed` or `pass` again: update the pattern and its test. |
| D4 | **Each attempt runs in a fresh work directory** (`tmp/`, `home/`, build caches). Since DEP-2 the kept paths (`ROOT`, the repo and `tools/depaudit.py` included; `sys.prefix`; the target's `keep`) are mounted read-only, so they cannot carry state from attempt 1 to the rerun (L3 on #401 passed a marker that way). Paths a target names in `writes` stay writable and persist; only controls use `writes`. | HK-1b, DEP-2b | If a product scenario needs a writable path outside its work directory, add `writes` to the registry schema with its own review: that path again carries state across attempts. |
| D5 | **What a faulted attempt saw is kept.** Its violations are added to the final result whatever the last attempt's outcome: a clean rerun becomes `violation`, a sandbox error keeps them, and three faults give `error` with each attempt's violations. A scenario that fails on its own is not rerun. | HK-1b, HK-1c | — |
| D6 | **A timeout is not a fault.** A scenario that outlives its timeout is `scenario-failed` and not rerun; a sandbox that outlives timeout + 60 s still raises out of `run_target` (as before HK-1), after the kill. | HK-1a, HK-1b | — |
| D7 | **The evidence never touches the filesystem.** strace writes its trace to a pipe it opens as `/proc/<_inner pid>/fd/N`; that fd is close-on-exec in `_inner`, so the traced command does not inherit it. strace's stderr is a pipe the tracee shares; through that shared write end it can only append, and appended text can only add a fault (`error`) or nothing. The result leaves on a private dup of `_inner`'s stdout, and anything but exactly one JSON object line with the expected keys makes the attempt `error`. Checked against origin/main's harness: the tamper control passed there. | DEP-2a | This holds only against the inherited fds. Any tracee can reopen either pipe's read end through `/proc/1/fd/…` and drain it, erasing connect lines or a fault line, or ptrace `_inner` (neither is in `TRACED`): see D9. |
| D8 | **Read-only means `MOUNT_ATTR_RDONLY` set recursively on every kept path, parents first** (`remount,bind,ro` until DEP-4; D10). Kept paths are bound in sorted order, so a parent is made read-only before a path inside it; a `writes` path inside a read-only parent is bound again and left writable. The `ro` flag is set inside the sandbox's own mount namespace, so the kernel does not lock it against a process holding CAP_SYS_ADMIN there, which the scenario would have as root of the sandbox's user namespace (since DEP-3 it runs as `SCENARIO_ID`, D9, and keeps no capability; the drop stays as a second layer): `mount_setattr` and `open_tree_attr` (Linux 6.15+) clear it untraced (Security on #437 reproduced a rewrite of `depaudit.py` ending `pass`). So the command runs under `setpriv`, which drops CAP_SYS_ADMIN and CAP_SYS_PTRACE from its bounding and inheritable sets after strace (`DROP_CAPS`); `control-kept-read-only` tries both calls on every read-only kept path and fails if either succeeds or a write lands. CAP_SYS_PTRACE goes because `_inner` (PID 1) and strace keep CAP_SYS_ADMIN: with it the scenario could attach to either and inject `mount_setattr` (Security re-sign on #437, B1). Without it, `cap_ptrace_access_check` denies an attach to a process whose permitted set is not a subset of the caller's, and Yama scope 1 denies attaching to an ancestor; `control-no-ptrace-ancestors` does a `PTRACE_SEIZE` on PID 1 and opens strace's `/proc/<pid>/mem` (the same attach-mode check; a real attach to strace from its own tracee deadlocks both) and passes only if both are denied (it failed at f363149, both allowed). A nested user namespace does not get it back: mounts copied into it are locked. A `mount(2)` remount is traced and is a violation by itself. The sandbox enters a user namespace (`unshare -r` until DEP-3, now the two-id map of D13) even when run as real root, so every capability the scenario keeps is scoped to that namespace: without one, real root keeps CAP_DAC_READ_SEARCH (`open_by_handle_at` on a writable mount of the same filesystem), CAP_SYS_MODULE, CAP_MKNOD and CAP_SYS_RAWIO on the host, each a way past a read-only bind (Security re-sign 2 on #437, B2). CI runs as the unprivileged `runner`, so it always took `-r`; only a root run was exposed. `control-own-user-namespace` fails unless the scenario's `uid_map` and `gid_map` are exactly the two lines of D13 (until DEP-3: unless it was not the initial namespace's identity map `0 0 4294967295`; it failed as root at ac61b7c). Checked as root and as an unprivileged user. | DEP-2b | Submounts carried by `--rbind` are made read-only with the kept path and checked before the command runs: see D10. Without `setpriv` on PATH, `sandbox_available()` is false and the run fails loudly. |
| D9 | ~~Residual, release (DEP-3): the evidence was out of the tracee's reach only because `_inner` held capabilities the tracee lacked.~~ Closed by DEP-3 (checked). **The scenario runs under a uid and gid distinct from `_inner` and strace.** `_inner` and strace are uid 0 of the sandbox's user namespace; after strace, `DROP_CAPS` and then `AS_SCENARIO` (`python3 -I -S`: `setgroups([])`, `setresgid`, `setresuid` to `SCENARIO_ID` = 1000, `PR_SET_NO_NEW_PRIVS`, checks all ids, then `execvp`) run the command. A non-root uid keeps no capability across exec, so `ptrace_may_access` denies, by uid alone, opening `/proc/1/fd/N` (either evidence pipe, read or write end), `/proc/1/mem`, and a ptrace attach to `_inner` or strace; no_new_privs keeps a setuid or file-capability binary from giving capabilities back, and a setuid-root binary is ignored anyway since the host's root is not mapped. Not `setpriv --reuid=1000`: it looks the number up as a name first, and glibc's lookup connects to nscd's socket, a host-socket violation in every run (found building DEP-3). `control-distinct-uid` fails if the scenario shares any real, effective, saved or fs uid or gid with PID 1 or with strace (red at 958fa35: all three uid 0). `control-evidence-channels` connects to a documentation address, then tries to drain each evidence pipe through `/proc/1/fd` (O_RDONLY|O_NONBLOCK), to write a partial line into it (O_WRONLY), and `PTRACE_SEIZE` on PID 1, then connects again; it expects `violation` with both connects logged, and is run by the tests with and without `DROP_CAPS` (red at 958fa35 without it: all three channels opened, one connect lost to the partial line, `scenario-failed`). DEP-2a's invariant (a tracee can at most append to strace's stderr, never erase) now rests on that uid boundary. The work directory's `tmp/`, `home/` and `stdout` are chowned to `SCENARIO_ID` before the run and back to 0 after it, once `_end_namespace` has killed (`kill(-1)` from the namespace's init) and reaped every other process in the PID namespace, so nothing still writes; kept paths stay root-owned and read-only. `_inner`'s own cwd (D10's hidden-mount route) is now out of reach by uid. | DEP-2a, DEP-3a, DEP-3b | If the scenario needs its uid to have a name (`getpwuid`), place an `/etc/passwd` line for it with the other `/etc` binds; glibc tries nscd first either way, so expect a host-socket attempt from any program that looks it up. A path a target declares in `writes` must be writable by `SCENARIO_ID` (mode 0o777 in the controls and tests). |
| D10 | ~~Residual, release (DEP-4): rbind submounts stay writable.~~ Closed by DEP-4 (checked). **Every mount at or under a read-only kept path is read-only before the command runs.** `_set_read_only` calls `mount_setattr(AT_FDCWD, path, AT_RECURSIVE, {attr_set=MOUNT_ATTR_RDONLY})` (syscall 442 on x86_64 and the generic table) on each read-only kept path; `remount,bind,ro` reached only the top mount, and `--rbind -o ro=recursive` and `remount,bind,ro=recursive` both left a tmpfs submount `rw` (util-linux 2.39.3, kernel 6.18; brief). There is no fallback: if the call fails (ENOSYS before Linux 5.12, or anything else) the attempt is a sandbox error. Then, after every mount the sandbox makes, `_inner` reads `/proc/self/mountinfo` and refuses to run the command (exit 1, outcome `error`) if `writable_mounts` finds a mount point at or under a read-only kept path whose per-mount options lack `ro`, unless the closest declared path covering it is a `writes` path; mount points are octal-unescaped (`\040`) and an unparsable line fails closed. **Hidden entries:** mountinfo also lists mounts no path reaches any more: the host's own mount under a kept path that a masking tmpfs now covers, or the mount under a kept path that is itself a mount point and was bound over. They stay `rw`, so an `rw` entry is confirmed with `statvfs` on its mount point: path lookup lands on the topmost visible mount there, and every visible mount has its own entry, so each visible one is judged by its own flags; ENOENT (the path no longer exists) counts as unreachable, any other error as writable. A hidden mount is still reachable through an fd or cwd opened before the masking: `_inner`'s own cwd is one, out of the tracee's reach by the uid boundary of D9 (DEP-3). `control-kept-read-only` runs the same check from inside the scenario. Red at d57476f: a scenario wrote into a tmpfs submount of a `keep` entry and passed; with `/etc` kept read-only the sandbox's own `nsswitch.conf` bind is `rw` under it, and the command ran. A target that keeps `/etc` therefore cannot run; product targets cannot set `keep`. | DEP-2b, DEP-4a | A mount the sandbox adds after the kept paths (the `/etc` binds of `_place`) under a read-only kept path is a sandbox error, not made read-only: bind it read-only if a target needs that. If `statvfs` stops reporting the mount a path reaches (`ST_RDONLY`), the hidden-entry rule must move to mountinfo's parent ids. |
| D11 | **Counts are per target and cover every attempt.** `attempts`, `faults` (attempts that ended with a strace fault) and `cleanup_retries` (ENOTEMPTY retries removing work directories) are kept in each result and printed on that target's `depaudit run` line; they are not summed across targets (Potency on #437; DEP-4). | DEP-2c | — |
| D12 | **Every name in `TRACED` is one strace knows, or the run fails loudly.** strace skips a `?`-prefixed name it does not know, so that syscall would go unseen while the run said `pass` (Security on #437 point 2). `?` now marks only names the running architecture has no syscall for, from an explicit per-architecture list `_ABSENT` (`aarch64`: `symlink`, `link`, absent from the generic table, which has `symlinkat` and `linkat`); `sandbox_available()` runs strace with the same `-e trace=` as the run, so an unknown name ("invalid system call") makes it false and `depaudit run` exits 2. strace 6.8 on x86_64 knows all 15 names (checked); the aarch64 list is from the kernel's generic syscall table, not run on aarch64. An architecture not listed gets no `?`: if it lacks a name, the run fails loudly until it is listed. | DEP-4b | A new name in `TRACED` that an older strace on CI lacks makes CI fail at `sandbox_available()`, not pass: upgrade strace or list it. riscv64 and loongarch64 use the generic table too and would need the same entry. |
| D13 | **The sandbox's user namespace maps exactly two ids, through newuidmap and newgidmap.** `unshare --map-user=0 --map-group=0 --map-users=1000:S:1 --map-groups=1000:G:1`: uid 0 is the runner's euid (as `-r` did), 1000 is the first id S (G) of the runner's subordinate range in `/etc/subuid` (`/etc/subgid`), matched by name or uid. With no range, `_unshare_flags` raises and `sandbox_available()` is false; with a range but a failing newuidmap or newgidmap (missing, or refusing), unshare fails and so does the probe; either way `depaudit run` exits 2, loudly, with no fallback to `-r`'s one-id map. setgroups stays `allow` (newgidmap writes the map), so the drop's `setgroups([])` works. Checked locally as real root (kernel 6.18, util-linux 2.39.3, uidmap from apt, a `root:200000:65536` range). CI: `ubuntu-latest` runs as `runner`; the `dependency-audit` job prints whether newuidmap, newgidmap and a range exist, installs `uidmap` and adds `100000-165535` with `sudo usermod` if missing (the job already uses sudo). `SubmountTest` builds its outer namespace with the same two ids and binds a private `/etc/subuid` and `/etc/subgid` (`root:1000:1`) there, so the nested sandbox can map them again. | DEP-3a, DEP-3c | If a runner has no sudo and no range, the run fails at `sandbox_available()`; the brief's alternative (read ends outside the PID namespace, ptrace denied by seccomp) is then the route, by escalation. If S is ever an id the host uses for something else, the scenario's files are that id's on the host until the chown back: keep the range unused. |
