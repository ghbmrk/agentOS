| D7 | **The evidence never touches the filesystem.** strace writes its trace to a pipe it opens as `/proc/<_inner pid>/fd/N`; that fd is close-on-exec in `_inner`, so the traced command does not inherit it. strace's stderr is a pipe the tracee shares; through that shared write end it can only append, and appended text can only add a fault (`error`) or nothing. | D8 | **Read-only means `MOUNT_ATTR_RDONLY` set recursively on every kept path, parents first** (`remount,bind,ro` until DEP-4; D10). Kept paths are bound in sorted order, so a parent is made read-only before a path inside it; a `writes` path inside a read-only parent is bound again and left writable. The `ro` flag is set inside the sandbox's own mount namespace, so the kernel does not lock it against a process holding CAP_SYS_ADMIN there, which the scenario would have as root of the sandbox's user namespace (since DEP-3 it runs as `SCENARIO_ID`, D9, and keeps no capability; the drop stays as a second layer): `mount_setattr` and `open_tree_attr` (Linux 6.15+) clear it untraced (Security on #437 reproduced a rewrite of `depaudit.py` ending `pass`). So the command runs under `setpriv`, which drops CAP_SYS_ADMIN and CAP_SYS_PTRACE from its bounding and inheritable sets after strace (`DROP_CAPS`); `control-kept-read-only` tries both calls on every read-only kept path and fails if either succeeds or a write lands. CAP_SYS_PTRACE goes because `_inner` (PID 1) and strace keep CAP_SYS_ADMIN: with it the scenario could attach to either and inject `mount_setattr` (Security re-sign on #437, B1). Without it, `cap_ptrace_access_check` denies an attach to a process whose permitted set is not a subset of the caller's, and Yama scope 1 denies attaching to an ancestor; `control-no-ptrace-ancestors` does a `PTRACE_SEIZE` on PID 1 and opens strace's `/proc/<pid>/mem` (the same attach-mode check; a real attach to strace from its own tracee deadlocks both) and passes only if both are denied (it failed at f363149, both allowed). A nested user namespace does not get it back: mounts copied into it are locked. A `mount(2)` remount is traced and is a violation by itself. The sandbox enters a user namespace (`unshare -r` until DEP-3, now the two-id map of D13) even when run as real root, so every capability the scenario keeps is scoped to that namespace: without one, real root keeps CAP_DAC_READ_SEARCH (`open_by_handle_at` on a writable mount of the same filesystem), CAP_SYS_MODULE, CAP_MKNOD and CAP_SYS_RAWIO on the host, each a way past a read-only bind (Security re-sign 2 on #437, B2). CI runs as the unprivileged `runner`, so it always took `-r`; only a root run was exposed. `control-own-user-namespace` fails unless the scenario's `uid_map` and `gid_map` are exactly the two lines of D13 (until DEP-3: unless it was not the initial namespace's identity map `0 0 4294967295`; it failed as root at ac61b7c). Checked as root and as an unprivileged user. | DEP-2b | Submounts carried by `--rbind` are made read-only with the kept path and checked before the command runs: see D10. Without `setpriv` on PATH, `sandbox_available()` is false and the run fails loudly. |
| D9 | ~~Residual, release (DEP-3): the evidence was out of the tracee's reach only because `_inner` held capabilities the tracee lacked.~~ Closed by DEP-3 (checked). **The scenario runs under a uid and gid distinct from `_inner` and strace.** `_inner` and strace are uid 0 of the sandbox's user namespace; after strace, `DROP_CAPS` and then `AS_SCENARIO` (`python3 -I -S`: `setgroups([])`, `setresgid`, `setresuid` to `SCENARIO_ID` = 1000, `PR_SET_NO_NEW_PRIVS`, checks all ids, then `execvp`) run the command. A non-root uid keeps no capability across exec, so `ptrace_may_access` denies, by uid alone, opening `/proc/1/fd/N` (either evidence pipe, read or write end), `/proc/1/mem`, and a ptrace attach to `_inner` or strace; no_new_privs keeps a setuid or file-capability binary from giving capabilities back, and a setuid-root binary is ignored anyway since the host's root is not mapped. Not `setpriv --reuid=1000`: it looks the number up as a name first, and glibc's lookup connects to nscd's socket, a host-socket violation in every run (found building DEP-3). `control-distinct-uid` fails if the scenario shares any real, effective, saved or fs uid or gid with PID 1 or with strace (red at 958fa35: all three uid 0). `control-evidence-channels` connects to a documentation address, then tries to drain each evidence pipe through `/proc/1/fd` (O_RDONLY|O_NONBLOCK), to write a partial line into it (O_WRONLY), and `PTRACE_SEIZE` on PID 1, then connects again; it expects `violation` with both connects logged, and is run by the tests with and without `DROP_CAPS` (red at 958fa35 without it: all three channels opened, one connect lost to the partial line, `scenario-failed`). DEP-7b: it also reopens strace's stderr through the tracer's own entry, `/proc/<strace>/fd/2` (O_RDONLY|O_NONBLOCK), so `ptrace_may_access` on strace is exercised as well as the pipe's 0600 DAC; `/proc/self/fd/2` is the same pipe but skips that gate. DEP-7c: it signals strace and PID 1 with signal 0 (kill's `kill_ok_by_cred` check, nothing delivered, so an allowed one stops neither); only `PermissionError` is a refusal, and `ProcessLookupError` or a missing `/proc` entry fails the control, since nothing was denied by the uid. DEP-7d: `control-distinct-uid` also requires `NoNewPrivs:\t1` in its `/proc/self/status`, so an `AS_SCENARIO` without `PR_SET_NO_NEW_PRIVS` fails a control. | D10 | ~~Residual, release (DEP-4): rbind submounts stay writable.~~ Closed by DEP-4 (checked). **Every mount at or under a read-only kept path is read-only before the command runs.** `_set_read_only` calls `mount_setattr(AT_FDCWD, path, AT_RECURSIVE, {attr_set=MOUNT_ATTR_RDONLY})` (syscall 442 on x86_64 and the generic table) on each read-only kept path; `remount,bind,ro` reached only the top mount, and `--rbind -o ro=recursive` and `remount,bind,ro=recursive` both left a tmpfs submount `rw` (util-linux 2.39.3, kernel 6.18; brief). There is no fallback: if the call fails (ENOSYS before Linux 5.12, or anything else) the attempt is a sandbox error. Then, after every mount the sandbox makes, `_inner` reads `/proc/self/mountinfo` and refuses to run the command (exit 1, outcome `error`) if `writable_mounts` finds a mount point at or under a read-only kept path whose per-mount options lack `ro`, unless the closest declared path covering it is a `writes` path; mount points are octal-unescaped (`\040`) and an unparsable line fails closed. **Hidden entries:** mountinfo also lists mounts no path reaches any more: the host's own mount under a kept path that a masking tmpfs now covers, or the mount under a kept path that is itself a mount point and was bound over. They stay `rw`, so an `rw` entry is confirmed with `statvfs` on its mount point: path lookup lands on the topmost visible mount there, and every visible mount has its own entry, so each visible one is judged by its own flags; ENOENT (the path no longer exists) counts as unreachable, any other error as writable. A hidden mount is still reachable through an fd or cwd opened before the masking: `_inner`'s own cwd is one, out of the tracee's reach by the uid boundary of D9 (DEP-3). `control-kept-read-only` checks the same rule from inside the scenario from a second source (DEP-6b): `kept_rw_mounts` reads `/proc/self/mounts`, where field 4 says `ro` if the mount or its superblock is read-only, and `statvfs` on each mount point; it shares no code with `writable_mounts` (its own unescape, its own covering test; the closest declared path decides), so one parsing bug cannot blind both the refusal and the control. Field 4 folding in the superblock makes the control stricter than mountinfo's per-mount field only where a mount is read-only by its superblock, which is still read-only. When `_inner` refuses, the line names the mounts and says: bind it read-only, or drop the keep entry (DEP-6e). Red at d57476f: a scenario wrote into a tmpfs submount of a `keep` entry and passed; with `/etc` kept read-only the sandbox's own `nsswitch.conf` bind is `rw` under it, and the command ran. A target that keeps `/etc` therefore cannot run; product targets cannot set `keep`. | DEP-2b, DEP-4a | A mount the sandbox adds after the kept paths (the `/etc` binds of `_place`) under a read-only kept path is a sandbox error, not made read-only: bind it read-only if a target needs that. If `statvfs` stops reporting the mount a path reaches (`ST_RDONLY`), the hidden-entry rule must move to mountinfo's parent ids. |

| D12 | **Every name in `TRACED` is one strace knows, or the run fails loudly.** strace skips a `?`-prefixed name it does not know, so that syscall would go unseen while the run said `pass` (Security on #437 point 2). `?` now marks only names the running architecture has no syscall for, from an explicit per-architecture list `_ABSENT` (`aarch64`: `symlink`, `link`, absent from the generic table, which has `symlinkat` and `linkat`); `sandbox_available()` runs strace with the same `-e trace=` as the run, so an unknown name ("invalid system call") makes it false and `depaudit run` exits 2. strace 6.8 on x86_64 knows all 15 names (checked); the aarch64 list is from the kernel's generic syscall table, not run on aarch64. An architecture not listed gets no `?`: if it lacks a name, the run fails loudly until it is listed. | DEP-4b | A new name in `TRACED` that an older strace on CI lacks makes CI fail at `sandbox_available()`, not pass: upgrade strace or list it. riscv64 and loongarch64 use the generic table too and would need the same entry. Since DEP-6a the list is built by `_traced(machine)` and `TRACED = _traced(os.uname().machine)`, so the tests check the aarch64 list on any host: exactly `?link` and `?symlink`, none on x86_64 or riscv64 (removing the `?` or the `_ABSENT` entry fails them; checked). |
| D13 | **The sandbox's user namespace maps exactly two ids, through newuidmap and newgidmap.** `unshare --map-user=0 --map-group=0 --map-users=1000:S:1 --map-groups=1000:G:1`: uid 0 is the runner's euid (as `-r` did), 1000 is the first id S (G) of the runner's subordinate range in `/etc/subuid` (`/etc/subgid`), matched by name or uid. With no range, `_unshare_flags` raises and `sandbox_available()` is false; with a range but a failing newuidmap or newgidmap (missing, or refusing), unshare fails and so does the probe; either way `depaudit run` exits 2, loudly, with no fallback to `-r`'s one-id map. setgroups stays `allow` (newgidmap writes the map), so the drop's `setgroups([])` works. Checked locally as real root (kernel 6.18, util-linux 2.39.3, uidmap from apt, a `root:200000:65536` range). CI: `ubuntu-latest` runs as `runner`; the `dependency-audit` job prints whether newuidmap, newgidmap and a range exist, installs `uidmap` and adds `100000-165535` with `sudo usermod` if missing (the job already uses sudo). `SubmountTest` builds its outer namespace with the same two ids and binds a private `/etc/subuid` and `/etc/subgid` (`root:1000:1`) there, so the nested sandbox can map them again. | DEP-3a, DEP-3c | If a runner has no sudo and no range, the run fails at `sandbox_available()`; the brief's alternative (read ends outside the PID namespace, ptrace denied by seccomp) is then the route, by escalation. If S is ever an id the host uses for something else, the scenario's files are that id's on the host until the chown back: keep the range unused. |
| D14 | **`depaudit run` exits 2 naming the first need the host lacks and its remedy, and a failed `mount_setattr` inside the sandbox is one line, not a traceback.** `sandbox_available()` keeps the reason in `SANDBOX_WHY`, and the FAIL line prints it (DEP-6d, DEP-6e). The checks run in order, and each can only add a reason, never make the sandbox available: (1) `_has_mount_setattr()` calls syscall 442 with fd -1, a NULL attr and size 0, which the kernel refuses (EINVAL or EBADF) before any lookup, so it has no side effect; only ENOSYS means the call is missing (Linux before 5.12, D10). (2) unshare, setpriv, strace, newuidmap or newgidmap missing from PATH: named, with the apt package (`util-linux`, `strace`, `uidmap`). (3) no subordinate range: `_id_maps()`'s own OSError text, plus `sudo usermod --add-subuids START-END --add-subgids START-END <user>` with a 65536-id range whose START is at least 100000 (or `SUB_UID_MIN`/`SUB_GID_MIN` from `/etc/login.defs`), that lies above every uid in `/etc/passwd` and gid in `/etc/group`, and that overlaps no line in `/etc/subuid` or `/etc/subgid`, and a D13 pointer; no fixed range is printed, because one copied onto a multi-user host can overlap another user's range and share their ids (Security 4a on #568 point 1), and the floor is stated because `usermod --add-subuids` applies none, so START=0 or a login uid would map the scenario onto root or that user (Security re-sign on #568 point 1). The text is the only guard until the `_id_maps` floor check lands (BOARD DEP-7). (4) the probe not starting, or (5) exiting nonzero: its last 5 stderr lines (at most 500 characters), then the needs it checks, with `TRACED` (D12). Inside the sandbox, `_mask_or_refuse` catches the OSError of `_set_read_only` and exits 1 with `depaudit: sandbox not run, ...` naming the errno and the path, before any command runs (DEP-6c); `_inner`'s mountinfo check after it is unchanged. The probe only predicts: a seccomp filter that answers EPERM for every unknown call makes (1) pass on a kernel without the call, and then `_set_read_only` fails in the sandbox and that refusal is the check (L3 on #557 point 2). Not run on a pre-5.12 kernel; the ENOSYS branch is tested by patching the syscall number to an unused one (1000). | DEP-6c, DEP-6d, DEP-6e | If the kernel ever assigns 442 another meaning or validates attr after a lookup, the probe must move to a fd-free form. A new need goes into `_NEEDS` or `_sandbox_missing`, never into a check that can turn the result true. |
| D15 | **A count-bound `-fuzztime Nx` has no deadline, so the fuzz coordinator's deadline race cannot end a chunk.** The `internal/fuzz` coordinator stops on the `-fuzztime` deadline with `ctx.Err()` and suppresses it only if it equals its child context's error; a count stops on executions, not a context. The race is long-standing, not specific to Go 1.26 (LATER P1-4-flake l2). `fuzzrun.py` never passes a duration; `tests/test_workflows.py` fails any workflow that does or that runs `go test -fuzz` outside the tool. Read from #537's log and the coordinator's source as the brief cites them, not reproduced here. | LOOP-7 | A toolchain whose coordinator fails a count-bound run some other way shows as a chunk failing with a bare error and no crasher; the tool passes its exit status through. |
| D16 | **Chunks continue from one another through `$GOCACHE/fuzz`.** Go stores interesting inputs there per target, so chunk k+1 starts from what chunk k found; the sum of chunks is one run, not N restarts from the seeds. Not checked on CI (checked locally only that chunk 2 and 3 start with a warm build). | LOOP-7 | If the cache is cleared between chunks (a runner reset, `GOCACHE` pointed at a fresh dir per step) each chunk restarts from the seed corpus: coverage per budget drops, no failure shows. |
| D17 | **The rate estimate is executions ÷ go's own run time (`ok  pkg  Xs`), else the chunk's wall time.** A cold fuzz build took 11 s here for a 0.4 s run (wall rate 1791/s against 50761/s true), so a wall-clock rate would shrink every later chunk to a fraction of the budget. Go's figure includes the baseline-coverage pass, so it errs slightly short. The budget is spent in wall-clock time, so a chunk's build time comes out of it: a budget shorter than one build is one chunk. The calibration count (20000x) is a count, run once: a target slower than 400 execs/s (with ci.yml's 20 s) fails its cap. | LOOP-7 | If go changes its `ok` line, the wall-clock fallback undercounts the rate by the build time and the logged `/s` falls; compare the rate lines across runs. |
| D18 | **A run lasts at most the budget plus one chunk's cap.** A chunk's cap is `2.5 × E + G` (E its expected time, G the grace, 2m): go's `-timeout`, and 5 % + 2 s above it the process group is killed (exit 124, message naming package, target and chunk). The factor 2.5 lets a chunk whose rate halved as the corpus grew (2E) still pass. Soak's 5 h maximum with `--chunk 10m` is at most 5 h + 25 m + 2 m = 327 m, under its 345 m job limit. The bound on a chunk's slowdown is an assumption, not measured: soak's logged rates are the evidence. | LOOP-7 | A target whose rate falls by more than 2.5× inside one 10 m chunk fails as a hang: raise `--chunk`'s factor or lower `--chunk`, do not retry. |
