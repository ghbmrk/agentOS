# D-116: At-most-once reconcile; the owner is never asked to resolve an unclear effect

Date 2026-10-14. Source: Mark, project Questions thread, 2026-10-13 (project message cmsg_01R63S2yrPkq32thy8WQCuvDQn6x9Xdidz8M6HexdsruyX, 23:53:37Z, "Giving the owner work, especially if frequently would be very annoying"; cmsg_01R63S2yrPkq32thy8WQCuvD1iEm1cKXLd5TRfgjhaEsEw, 23:59:26Z, "Revise, but double sends shouldn't ever happen"; 2026-10-14, cmsg_01R63S2yrPkq32thy8WQCuvD3gJQYmEwvcNjPqJSsTkMgn, 00:18:53Z, "Retry where idempotency keys exist is totally fine"). These three messages are the source of the at-most-once order, the digest and RETRY itself; they do not set RETRY's approval tier. The tier follows Mark's standing two-tier approval rule of 2026-10-04 (CH-10; SPEC change log 2026-10-04): low risk takes a texted code, and CH-10 defines it as all of a recipient the broker verifies already exists, any amount under the owner-set limit and a verb the owner has not excluded; high risk takes the code-generator code or the paper grid, and CH-10 defines it as "new or wider grants or pre-allowances (except the device steps listed under Devices), money above the owner-set limit, CRED-6 actions, and recovery", with anything not low risk also high risk. That money always takes the code generator on a retry that may duplicate is a reading of this rule, pending Mark (below). Mark's decision cards of 2026-10-14 settle three further points: confirm repeats (cmsg_01R63S2yrPkq32thy8WQCuvD36X644NtbQLonpQxTP2NZd, "Confirm repeats", 12:23Z) and parking lifting the account fence (cmsg_01R63S2yrPkq32thy8WQCuvD7fH2ttYxecyKuqNf1F4GiE, "Resume", 12:24:00Z), below. Issue #1373 as amended that day.

**Question.** When the broker restarts between recording an intent and recording its outcome, and the service cannot say whether the effect happened, who settles it? The earlier #1373 plan asked the owner a YES/NO question for each such effect. Mark rejected that: owner work for every unclear effect is annoying, and a double send must never happen.

**Decision.**
- Effects are at most once. An effect whose outcome is unknown is never retried automatically.
- The broker settles an unknown outcome in this order:
  1. It checks through the same tool (the executor's Reconcile).
  2. It retries only if the check proves the effect was not done, or the executor reports that the service honours the attempt's idempotency key. A key retry reuses the same key, so the service applies the effect at most once, and is made only within the key's lifetime from the first dispatch (the executor's, else 24 hours). A clock behind the attempt's dispatch or the journal's newest record went back (as after an RTC loss at the restart) and cannot measure that lifetime, so the effect is parked at once instead. A retry after a check proves the effect was not done passes the dispatch recheck (OP-3) and the dispatch guards (STOP, the account fence, a same-effect intent ahead of it) first. If they refuse it (after a restart the gate's approvals are gone, so every effect that needed the owner's approval is refused), it is not dropped: the digest names it as "did not go; not resent", and RETRY offers it at the tier its verified facts give, without the may-go-twice warning, since the check proved it did not go.
  3. Otherwise, after a bounded number of checks (10 at daemon pacing, about 13 minutes), the effect is *parked*: it goes in the daily digest as unclear and not retried. The owner is not interrupted.
- A parked effect lifts its account's restart fence, so other work on the account resumes. It still holds any other intent with the same effect (same account, action, parameters and recipients), so a resubmission cannot send it twice. This is Mark's decision (decision card cmsg_01R63S2yrPkq32thy8WQCuvD7fH2ttYxecyKuqNf1F4GiE, "Resume", 2026-10-14 12:24:00Z; Security R3 on PR #1433): after a restart, an action parked as unclear lets the account's other work resume, and identical actions stay held.
- The broker keeps checking parked effects through the same tool on each settle round. A check that later settles one closes it.
- The digest line for a parked effect says when it was first tried.
- The owner may text RETRY to be asked about each unclear effect, one request per effect and no approval for all of them. Each request shows the effect as the gate verifies it now (recipient, amount, object), when it was first tried, and that it may happen twice. Its tier comes from those verified facts under Mark's two-tier rule (CH-10, 2026-10-04): a texted code for low risk, the code generator for high risk, and the code generator for an effect that moves money, which may already have gone. An effect the gate cannot verify is shown unverified and is high risk. Each request carries its own reference, so an approval runs only the line that request showed, and an older request's NO or expiry never drops a newer one's line. Pending Mark's confirmation: that "money always on the code generator" is how his rule applies to a retry that may duplicate, and the SPEC OP-2 and CH-11 wording that states this tier (Security B4 and R5, L3 L7 on PR #1433). SPEC.md is not changed for it here.
- The retry is a new attempt with a new key, under the same dispatch recheck (OP-3) as any other. The owner is texted how it ended: went through, did not go, unclear again, this try did not go but the first try may still have gone (the effect stays unclear and parked), or refused with the reason. A refused retry is listed again in the next digest.
- An executor with no check and no key hook gets the default: unknown, digest, no retry.

**Same effect under another request (Security B8, Potency P6 and L3 L9 on PR #1433).** Two requests with the same effect (same account, action, parameters and recipients) are one send when one of them was proved not done and the other was made after it was first tried: of those, only one may go. This rivalry is the coordinator's decision (2026-10-14), under the standing rule to restore main's behaviour where no lens is worse: a request made before the effect went, or while it waited or was unclear, is refused, and a recurring payment or a repeated owner setting is never refused for good.

**Confirm repeats (rule (b); Mark, decision card cmsg_01R63S2yrPkq32thy8WQCuvD36X644NtbQLonpQxTP2NZd, "Confirm repeats", 2026-10-14 12:23Z).** A request made *after* the effect is known to have gone is a new send, but an identical repeat (the same record to the same recipients by the same action) within 24 hours of a known success never goes out without the owner's explicit confirmation:
- Every path that would otherwise send it unseen stops and asks the owner instead: a pre-allowed send (ADP-9), an auto-reply rule (ADP-11), a guest's request, and the broker's own resend of an effect a check proved not done (refused at the dispatch recheck, then offered by RETRY).
- The ask uses the existing approval machinery and tiers (CH-10): a texted code for low risk, the code generator for high risk, such as money above the owner-set limit. It says plainly that the send was already sent and when (the first known success in the 24 hours) and asks whether to send it again: "already sent 14:02 Oct 13; send it again?".
- Declined, expired or never answered, it does not go. A repeat more than 24 hours after the success is a new send as before.
- Identical means the same account, action, verified record and recipients, and the same body where the action has one, so a reply that says something new in the same thread is a new send. An erased send (CAP-3) names no record and asks nothing.
- A repeat of a send that may have gone (in flight, or unknown and not known to have gone) is held, as before, when its effect is exactly the same (journal `duplicateOf`); one the engine's exact match misses is asked the same way, pre-allowed or not, marked "may go twice, first tried <the first try's time>" (not the time of a refused retry, Security R19), and money then takes the code generator. This part is the coordinator's reading of Mark's rule for a rival that is unclear rather than known to have gone: a may-have-gone send is at least as likely to be a duplicate as one known to have gone.
- This replaces the coordinator's earlier auto-decide for rule (b), under which such a repeat was asked only where an ask already existed (marked "may go twice") and went silently under a pre-allowance.

**Consequences.** OP-2 in SPEC.md is rewritten to this shape, and CH-11 gains RETRY. The journal gains one record kind (`parked`) and a source on `dispatched` records (`key` for a same-key retry, `owner` for the owner's retry). An older binary refuses a journal that holds them as corrupt rather than misreading it. Journals written by earlier heads of PR #1433, before 0ed23e12, that hold an erased intent whose parked try was unclear (or an intent erased in the R14 race state) are unsupported: this build refuses them as corrupt and the broker does not start, which fails closed (Security R17 on PR #1433). Only boxes that ran that unmerged branch can hold one; journals written by main replay unchanged. The gate gains the confirm-repeats rule (grants GR35) and the journal reports when a send went (`Use.Went`); the same-effect model checks that a known-success repeat never goes without a confirmation (journal A19, I5).

**Open points this decision leaves.** These are flagged on the PR for Security, not settled here.
- Parking lifts the account fence (Mark's "Resume", above). Same-effect intents stay held, but a *different* effect that depends on the parked one (for example a follow-up email) can now run while the first is unclear.
- A texted code is the low tier (CH-10). Someone holding the owner's SIM can approve a retry of a low-risk effect, and so a possible duplicate. The warning names that risk. Money and high-risk retries need the code generator; Mark is to confirm this reading of his two-tier rule and the SPEC wording.
- An owner retry still passes the dispatch recheck, so a grant that has since lapsed, or a gate freshness check, can refuse it. The owner then sees a refusal, not a retry.
- A parked effect holds same-effect intents until a check settles it or the owner retries it. A legitimately repeated identical message stays held meanwhile.
