# D-116: At-most-once reconcile; the owner is never asked to resolve an unclear effect

Date 2026-10-14. Source: Mark, project Questions thread, 2026-10-13 (project message cmsg_01R63S2yrPkq32thy8WQCuvDQn6x9Xdidz8M6HexdsruyX, 23:53:37Z, "Giving the owner work, especially if frequently would be very annoying"; cmsg_01R63S2yrPkq32thy8WQCuvD1iEm1cKXLd5TRfgjhaEsEw, 23:59:26Z, "Revise, but double sends shouldn't ever happen"; 2026-10-14, cmsg_01R63S2yrPkq32thy8WQCuvD3gJQYmEwvcNjPqJSsTkMgn, 00:18:53Z, "Retry where idempotency keys exist is totally fine"). These three messages are the source of the at-most-once order, the digest and RETRY itself; they do not set RETRY's approval tier. The tier follows Mark's standing two-tier approval rule of 2026-10-04 (CH-10; SPEC change log 2026-10-04): low risk takes a texted code; high risk, meaning money or an irreversible effect, takes the authenticator (code-generator TOTP) code. Issue #1373 as amended that day.

**Question.** When the broker restarts between recording an intent and recording its outcome, and the service cannot say whether the effect happened, who settles it? The earlier #1373 plan asked the owner a YES/NO question for each such effect. Mark rejected that: owner work for every unclear effect is annoying, and a double send must never happen.

**Decision.**
- Effects are at most once. An effect whose outcome is unknown is never retried automatically.
- The broker settles an unknown outcome in this order:
  1. It checks through the same tool (the executor's Reconcile).
  2. It retries only if the check proves the effect was not done, or the executor reports that the service honours the attempt's idempotency key. A key retry reuses the same key, so the service applies the effect at most once, and is made only within the key's lifetime from the first dispatch (the executor's, else 24 hours). A clock behind the attempt's dispatch or the journal's newest record went back (as after an RTC loss at the restart) and cannot measure that lifetime, so the effect is parked at once instead. A retry after a check proves the effect was not done passes the dispatch recheck (OP-3) and the dispatch guards (STOP, the account fence, a same-effect intent ahead of it) first. If they refuse it (after a restart the gate's approvals are gone, so every effect that needed the owner's approval is refused), it is not dropped: the digest names it as "did not go; not resent", and RETRY offers it at the tier its verified facts give, without the may-go-twice warning, since the check proved it did not go.
  3. Otherwise, after a bounded number of checks (10 at daemon pacing, about 13 minutes), the effect is *parked*: it goes in the daily digest as unclear and not retried. The owner is not interrupted.
- A parked effect lifts its account's restart fence, so other work on the account resumes. It still holds any other intent with the same effect (same account, action, parameters and recipients), so a resubmission cannot send it twice.
- The broker keeps checking parked effects through the same tool on each settle round. A check that later settles one closes it.
- The digest line for a parked effect says when it was first tried.
- The owner may text RETRY to be asked about each unclear effect, one request per effect and no approval for all of them. Each request shows the effect as the gate verifies it now (recipient, amount, object), when it was first tried, and that it may happen twice. Its tier comes from those verified facts under Mark's two-tier rule (CH-10, 2026-10-04): a texted code for low risk, the code generator for high risk, and the code generator for an effect that moves money, which may already have gone. An effect the gate cannot verify is shown unverified and is high risk. Each request carries its own reference, so an approval runs only the line that request showed, and an older request's NO or expiry never drops a newer one's line. Pending Mark's confirmation: that "money always on the code generator" is how his rule applies to a retry that may duplicate, and the SPEC OP-2 and CH-11 wording that states this tier (Security B4 and R5, L3 L7 on PR #1433). SPEC.md is not changed for it here.
- The retry is a new attempt with a new key, under the same dispatch recheck (OP-3) as any other. The owner is texted how it ended: went through, did not go, unclear again, or refused with the reason. A refused retry is listed again in the next digest.
- An executor with no check and no key hook gets the default: unknown, digest, no retry.

**Consequences.** OP-2 in SPEC.md is rewritten to this shape, and CH-11 gains RETRY. The journal gains one record kind (`parked`) and a source on `dispatched` records (`key` for a same-key retry, `owner` for the owner's retry). An older binary refuses a journal that holds them as corrupt rather than misreading it.

**Open points this decision leaves.** These are flagged on the PR for Security, not settled here.
- Parking lifts the account fence. Same-effect intents stay held, but a *different* effect that depends on the parked one (for example a follow-up email) can now run while the first is unclear.
- A texted code is the low tier (CH-10). Someone holding the owner's SIM can approve a retry of a low-risk effect, and so a possible duplicate. The warning names that risk. Money and high-risk retries need the code generator; Mark is to confirm this reading of his two-tier rule and the SPEC wording.
- An owner retry still passes the dispatch recheck, so a grant that has since lapsed, or a gate freshness check, can refuse it. The owner then sees a refusal, not a retry.
- A parked effect holds same-effect intents until a check settles it or the owner retries it. A legitimately repeated identical message stays held meanwhile.
