# D-127: Human-native texting

Date 2026-10-17. Source: Mark, Questions thread 2026-10-17 13:37:29Z ("interactions with the box should be as human native as possible (I.e. indistinguishable from texting a human assistant in user-facing ways)", cmsg_01R91wiieBzMSvPKFsAJVvuKQpzomqt7TPTWqUERXUKUYJ) and 13:44:50Z ("Reactions also, speed of response important", cmsg_01R91wiieBzMSvPKFsAJVvuK7bBMkKaaUTKHZrECS7K6WT); "Fix + redesign" on the Decisions 5 card (cmsg_01R91wiieBzMSvPKFsAJVvuKWM7kwzFkaMbd3pTF7pv4p7).

**Decision.** Texting the box should read like texting a person. What the owner can verify stays the same: codes, verified approval fields, and the CH-19, CH-20 and CH-21 checks are unchanged.
1. **Characters (CH-12).** Agent conversation text keeps emoji and line breaks and goes in UCS-2 when it needs to. Broker templates stay GSM-7. Agent text is never placed inside a template, Control characters other than line feed and bidirectional controls are removed before sending, so the order checked is the order shown; joiners and other characters are sent as written, so composed emoji arrive whole. The checks run on the whole reply before it is split, joined to the agent's earlier texts since the owner's last message, and on a fold ordered as the UTS #39 skeleton (NFKD and case folding, then the confusable mapping and NFD again, then combining marks dropped, then default-ignorable code points dropped in one pass and read as spaces in a second, then everything but letters, digits and printable ASCII read as a space, then runs of spaces read as one; withheld if either pass matches). Each step runs after every step that could add what it removes, so the class of reordering bugs is closed by construction, so an invisible or split footer is caught without listing cases one by one.
2. **Long replies (CH-12).** A long agent reply is split at natural boundaries into at most three texts (nine segments, the same bound as CH-14). Only text beyond that goes to the local UI. Before this decision, a reply was cut after three segments with "Cut here. Ask me to send it in shorter parts."
3. **Approval wording (CH-12).** The fixed wording becomes a first-person question in plain sentences. It has the same fields and the same valid-replies footer with the request ID, and the leading `<ID>:` label is dropped.
4. **No agent label (CH-21).** The `Agent: ` prefix goes. CH-21's closed check takes over its job: agent text that carries the reply-options footer, a control word with a request ID, or a broker-request opening is withheld. The prefix stays until that check is in force (package CH-21e), so there is never a window with neither.
5. **Speed (CH-15, OWN-4).** An open task chat is defined as lasting 30 minutes (owner-set) after the owner's last message to the agent. Its replies, and results the journal ties to an owner task, skip the push allowance, quiet hours and the held-push queue. Before this, agent replies were paced like pushes, which contradicted CH-15. When no reply has gone out 20 seconds after an owner message, the broker sends one fixed acknowledgement. Model time dominates reply latency, and the acknowledgement is the only fixed-cost fix for it.
6. **Reactions (CH-11).** Owner reactions are recognised from a fixed list of text forms and passed to the agent as a reaction on the message they mark. They are never a control word, code, `RUN` or approval, and while the session is locked they are held like any task message, so a spoofed tapback cannot reach the agent. A reaction on a text that expects a reply gets a one-line pointer to that text's valid replies. The agent sends reactions only after qualification shows the owner's phone renders them.

**Why.** Each of these is a sign that the owner is talking to a machine: the `Agent: ` prefix, "?" in place of emoji and line breaks, a cut-off reply, approvals worded like a form, replies held for an hour by pacing, and silence on a tapback. None of them protects anything the checks don't already protect, except the prefix, which is why it waits for CH-21e.

**Risks.**
- [Risk] Without the prefix, agent text that gets past the closed check could read as the broker's. The check withholds the footer and request grammar. A bare `YES` approves nothing, because every approval takes a code (CH-10, CH-18), so a forged question's worst case is an unanswered control word.
- [Risk] Worst case for an unlabelled agent text: it coaxes the owner into replying with a bare code from a low-tier `Code <digits>` text, which CH-11 reads as `YES <code>` on the request that code is bound to. The CH-21 vocabulary withholds agent text that mentions a code, and a bare code approves only the open request it was issued for, never one the agent chose.
- [Risk] The fold drops characters the phone may draw (combining accents, variation selectors), so the check reads a little less than the phone shows; with both passes, whether the phone draws an ignorable as nothing or as a gap, it holds at least what a check on the displayed text would. False holds from accented words folding onto the vocabulary are measured with the rest (CH-21's Risk).
- [Risk] UCS-2 cuts a segment from 153 to 67 characters, so an emoji-bearing reply uses more segments. The three-text bound limits the cost.
- [Inference] Reaction text forms are phone- and version-specific, and some phones may send reactions only over RCS or iMessage, which the box does not receive. Recognition is best-effort and grows through Loop 2.
- [Unverified] Whether a modem-sent text-form reaction renders as a reaction on the owner's phone. Qualification decides this.

**Not changed.** The 30-day unlock (CH-3, CH-14). CH-19 secret filtering. CH-20 evidence delivery. CH-21's vocabulary and footer checks, which this decision extends but does not relax.
