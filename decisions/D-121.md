# D-121: speed rules for building and reviewing

Date 2026-10-15. Source: Mark, project chat 2026-10-15, owner approvals at 14:03Z, 17:57Z, 18:48Z and 18:51Z. Procedure: docs/OPERATING.md §5 "Speed rules" and the brief's "Guard files up front".

**Decision.**
1. Builders, review workers and fix workers run the exact CI job commands from `.github/workflows/ci.yml` before opening a PR or giving a verdict: from `broker/`, `go vet ./...` and `go test -race ./...`; the `checks` job's Python tests; `tools/g1_scope.py`; `tools/risk_tier.py`; plus a `-count=N` stress run on new concurrency tests.
2. Briefs list the guard files a new package must touch (its package class in `tools/risk_tier.py`, the import allowlist in `broker/daemon/arc2_test.go`, its coverage in `tools/g1_scope.txt`) and pre-approve them in scope.
3. Readiness checks read the code paths an issue depends on, not just issue states.
4. One push per round: finish local checks, then push once; don't push while CI runs unless the run is already red.
5. On the G1 critical path, stack the next package on its prerequisite's branch once that prerequisite's interface is review-accepted, without waiting for merge.
6. Keep the G1 critical path parallel on disjoint files.
7. Tier-A builders run on Opus; tier B and C builders on Sonnet. Never switch a running session's model; if its build is done, review instead of rebuilding.
8. Fix a flaky test the second time it is seen (file it and fix it; don't just re-run).

**Not changed.** Tier A keeps two separate reviews: Security, and Potency/UX/L3. Pre-approving a guard file in a brief's scope does not change who merges: a PR touching `tools/risk_tier.py` or `tools/g1_scope.txt` still matches `premerge.py --needs-mark` and goes to Mark (D-120). The conflict guard (D-111) still applies to stacked and parallel builds.

**Reasons.** Each rule removes a round trip: a CI failure a local run would have caught, a builder stopping to ask for a guard file, a row started on an issue state that the code contradicts, a push that restarts a running CI, a package idle until its prerequisite merges, or a flake re-run on every PR it touches. Item 7 makes the Sonnet pilot's route (OPERATING §5) standing.
