# D-104: One working controller first

Date 2026-10-12. Source: Mark, waste review 2026-10-12 ("Yes all"), item 9.

**Decision.** Release work is staged behind one working controller. Acceptance gate G1 (A1), the controller's boot, phone control and one useful model-backed task, passes on one mini PC, the M6 Ultra, before anything that only widens the hardware reach is built: more controller models, the signed flasher (FLASH-1), the seller's preloaded-image self-check (CTRL-uki), routing to helpers (ROUTE-1), the workstation segment (NET-seg), workstations (WS-image, WS-rest) and the helper apps (HELPER-a, HELPER-b, HELPER-c). Those move to a new acceptance test A17 (gate G7). They come after G1, each when it solves a measured limitation. This is a staging change to the approved design, not a finding that those features are unnecessary. How G1 installs and pairs is not decided here: SPEC §8.1 and HW-10 stand.

**Unchanged.** The design (SPEC HW-9 to HW-13, REV-6, ONB-10, D-102) stays as written; only the staging changes. Rows on the G1 path keep their place: CTRL-spike, the CTRL-card rows, the CTRL-claim rows, IMG-nodump and CTRL-text.

**Board.** The rows above read `queued (after G1, D-104; ...)` and name G1 in Needs. SPEC A1, A17 and the gates line change in the same PR, which needs Mark's approval of the SPEC text (D-069, D-077).

**Reasons.** Ten rows of helper, workstation and seller code were queued before any controller had booted the image. Building them first spends the budget on breadth the owner cannot use until the controller works, and A1's three-vendor, two-path, two-helper run made G1 the gate least likely to pass.
