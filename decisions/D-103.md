# D-103: Short-secret hashes in egress

Date: 2026-10-12. Source: SIM-split-fix (briefs/SIM.md), item 1, which allows "an entropy floor per value class or a DECISIONS row accepting the class". Taken under the auto-decide rule: no lens is worse than today.

## Decision

1. Egress redacts every vault value through `vault.HashRedactor` (CRED-7). The HMAC key sits beside the hashes in egress memory, because egress must hash response bytes as they pass. Anyone who reads that memory can therefore test guesses offline against the hashes.
2. Values the box generates or a provider issues (API keys, tokens, seeds, signing keys) are long and random. Guessing them is infeasible, so they need no floor.
3. The owner-chosen password class (`mail_password`, `sip_password`) is accepted with the residual: a compromised egress can run a dictionary attack on a weak password. No floor refuses one, because the owner's existing password is what the provider accepts.
4. These passwords stay hashed rather than being dropped from the redactor. Dropping them would close the oracle but would let a leaked password pass through egress in plaintext, which is a CRED-7 loss on every response path.

## Why this is no worse than today

Until SIM-split-wire lands, production egress opens the vault and holds every secret in plaintext. A hash that can only be attacked by guessing is strictly less exposure. Once holders are wired, the only copy of a password in egress is this hash.

## Owner guidance and follow-up

Where a provider offers one, the setup flow should prefer a generated app password (typically 16 random letters, about 75 bits), which is out of dictionary reach. SIM-split-wire must not hand egress anything beyond the hash redactor. If a later design lets egress redact without holding the key, for example by doing it in the holder alone, this decision is superseded.
