# D-276: The pinned mkosi runs in its own CI job, out of build.sh's reach (#4690)

Date 2026-11-02. Source: issue #4690 (IMG-mkosi-run-bound), split from #4647 by PR #4696; Security accept 6576525355 point 2 on #4620. Standing rule: Mark's structure-first rule of 2026-10-30.

**Decision.** `image.yml` splits its build. A staging job runs `build.sh`'s staging part and uploads `$STAGE`. A separate mkosi job on a fresh runner checks out the commit, installs the pinned mkosi (v24.3) and runs it from one `image.yml` line that a test pins byte for byte: the config directory from the checkout, the flags, and `--extra-tree` from the downloaded stage. That job never runs `build.sh`. `build.sh` keeps only staging, and a local build calls the same mkosi line. `mkosi.finalize` also checks the dpkg database against the signature-checked apt lists that mkosi mounts at `/var/lib/apt` (each installed package and version must be in a Packages index from the pinned sources) and refuses a `.deb` in the tree. The `reproduce` job runs the same split, so its second build is made the same way.

**Why.** `build.sh` runs as root before mkosi, so it can repoint mkosi's config directory, change its flags, edit the files under `image/mkosi`, or replace the mkosi binary; a line pin of shell does not hold (#4620's rounds). With the run out of its reach, the run-time checks in `mkosi.finalize` belong to the committed, tested tree. The invariant is that the image's packages come only from the pinned, signature-checked sources and that the mkosi run that builds the release reads only the committed config with the pinned mkosi.

**Lens check.** Checked against the files at main: `build.sh` stages in lines 32 to 107, runs mkosi at line 109 and post-processes at line 110. The split moves line 109 into its own job and leaves every staging step once, so no build step is duplicated. The cost is one runner start, the pinned-mkosi install (already in the build job at `image.yml` lines 125 to 128) and one artifact transfer of `$STAGE`. The builder measures both and reports them in the PR; if the added time or the stage size is large, that is a finding for Mark, not a waiver.

**Order.** Touches `.github/workflows/image.yml`, `image/build.sh` and `tests/test_image.py`; starts after the #4647 PR merges (D-111). Work item: #4690.
